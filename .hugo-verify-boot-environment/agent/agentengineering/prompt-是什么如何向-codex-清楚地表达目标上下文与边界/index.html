Prompt 是什么：如何向 Codex 清楚地表达目标、上下文与边界

August 28, 2026

Prompt 是你在当前对话中交给 Codex 的任务说明。它可以是一句问题、一条命令、一个目标，也可以附带文件、截图、验收条件和限制。它的作用不是用神秘咒语操纵模型，而是让 Codex 知道：要交付什么、依据什么、做到什么程度，以及哪些事情不能擅自做。

OpenAI 对 Prompt 的说明相当朴素：它就是告诉 ChatGPT、ChatGPT Work 或 Codex 你想了解、制作或改变什么的方式。短任务通常一句话足够；任务变大、代价变高时，再补充目标、上下文、输出和边界。详见 官方 Prompting 指南 。

一、Prompt 在 Agent 工程中的位置

Prompt 是本次任务的即时意图。它回答的是“现在要做什么”，而不是“这个仓库永远遵守什么”或“某种工作以后都怎么做”。

本次用户目标
        │
        ▼
      Prompt
        │
        ├── 结合 AGENTS.md 的项目规则
        ├── 按需调用 Skill 的专门流程
        └── 必要时通过 MCP 使用外部工具

因此，Prompt 的优点是灵活、直接、可随对话调整；缺点也很明显：如果一项流程每周都要重新解释，它就不该永远停留在聊天记录里。

二、一个可执行 Prompt 的四个部分

不是每条 Prompt 都必须写成模板，但下面四项能消除大多数歧义。

部分 需要说明什么 示例
目标 最终要得到什么结果 修复登录页在移动端的布局错误
上下文 哪些资料会影响判断 问题只出现在 Safari；附有截图和复现步骤
输出 如何交付与验证 给出补丁、原因说明和测试结果
边界 什么不能改，何时必须确认 不升级依赖；不修改接口；部署前先等待确认

例如：

修复 `src/pages/Login.tsx` 在 iPhone Safari 上按钮被遮挡的问题。
只修改登录页相关样式，不升级依赖，也不要改变接口或桌面端布局。
完成后说明根因，运行现有前端检查，并列出实际执行过的命令和结果。

它没有规定每一步怎样思考，却给出了可验证的目标和边界。这比“帮我优化登录页”可靠得多；后者几乎等于把决策范围交给猜测。

三、什么时候该补充上下文

只有会改变结果的信息才值得进入 Prompt。常见的有效上下文包括：

  • 明确的文件、目录、截图、日志或错误堆栈；
  • 目标读者、运行环境、版本与复现条件；
  • 已尝试过而无效的方案；
  • 必须遵循的接口契约、设计稿或验收标准；
  • 只能使用哪些资料、哪些事实尚未确认。

相反，把完整项目历史、无关日志和长篇思考过程一股脑贴进去，通常只会稀释重点。应先给目标和关键证据；如果 Codex 仍缺信息，再通过追问逐步补足。

四、边界比步骤清单更重要

官方指南建议先描述结果，只有过程本身确实重要时才规定过程。对工程任务尤其如此：你可以要求“输出测试证据”“不要发送消息”“数据不足时标记未知”，却不必规定每一次搜索或每个命令的顺序。

下面三类边界最有价值：

  1. 变更范围：只能修改哪些模块，哪些文件、接口、数据不得触碰。
  2. 证据要求：必须运行哪些测试，不能确认时应如何说明。
  3. 外部影响：提交、推送、部署、删除、发送通知等动作是否需要先确认。
根据当前 diff 写发布说明。
只能依据 diff 和已提供的 issue，不要推测未出现的功能。
将不确定项单列；只生成草稿，不要创建 Release 或发送通知。

五、Prompt、Skill 与 AGENTS.md 怎样分工

如果你想表达的是…… 更合适的载体
这一次要修哪个问题、交付什么 Prompt
仓库都必须遵守的测试、代码风格、目录规则 AGENTS.md
反复出现的专项流程，例如排查 CI、生成发布说明 Skill
读取工单、调用数据库、访问第三方服务 MCP 提供的工具

当某段 Prompt 被反复复制，并且输入、输出、风险边界都已稳定，就应考虑把它升级为 Skill。反过来，临时探索性任务不必勉强封装；一条清楚的 Prompt 已经足够。

六、检查清单

  • 我写的是结果，还是只写了模糊动词？
  • Codex 是否拿得到完成任务所需的关键证据？
  • 输出格式和验收方式是否明确？
  • 哪些改动、外部动作或猜测是禁止的？
  • 这项流程是否已经重复到值得做成 Skill？

好的 Prompt 不追求控制每一个中间动作，它追求让目标、证据和边界足够清楚。让 Agent 有判断空间，同时不给它越界空间，才是合格的工程沟通。
