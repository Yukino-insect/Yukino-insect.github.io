大模型、调用方式与 Prompt 工程

August 15, 2026

学习目标

  • 理解大模型在 RAG 中承担的职责。
  • 区分同步调用、流式调用和工具调用。
  • 掌握 Prompt 在 RAG 中的基本结构。
  • 能识别常见 Prompt 误区。

大模型在 RAG 中做什么

在 RAG 系统里，大模型不是数据库，也不是搜索引擎。它更像一个语言推理与表达层：理解用户问题，阅读检索到的证据，归纳结论，组织自然语言答案。

因此，模型输入的质量非常重要。你交给它的是结构清楚、来源明确、与问题相关的材料，它就更容易给出可控答案；你交给它的是一堆重复、矛盾、无关的片段，它仍然可能写得很流畅，只是正确性会变得很可疑。流畅不等于可靠，这句话值得贴在每个 RAG 项目的白板上。

三种常见调用方式

同步调用适合后台任务、摘要生成、意图判断等短任务。调用方发送完整请求，等待完整响应，逻辑简单，但用户等待时间较明显。

流式调用适合在线问答。模型边生成边返回，前端通过 SSE 或类似协议逐步展示内容。它不能让模型变快，但能显著降低用户感知等待时间。

工具调用适合需要访问外部能力的场景，例如查天气、查业务系统、搜索网页或调用内部服务。模型负责判断是否需要工具以及如何组织参数，业务系统负责真实执行。

在工程上，这三种调用方式不应该混成一团。Ragent 把 Chat、Embedding、Rerank、VLM 等能力拆成不同服务，并通过路由和健康状态管理统一调度，这比在业务代码里到处写 HTTP 调用要稳得多。

Prompt 的基本结构

一个 RAG Prompt 通常包含四类信息。

角色约束：告诉模型它在当前系统里的身份，例如“你是企业知识库助手”。角色不是装饰，而是为了约束回答边界和语气。

任务说明：告诉模型要做什么，例如“根据给定资料回答用户问题，资料不足时说明无法确定”。

上下文证据：来自检索系统的 Chunk、引用信息、意图提示、工具返回结果等。

输出要求：控制格式、引用、语言、是否允许推测、是否需要列步骤。

可以把 Prompt 想成一份“临时任务书”。任务书写得含糊，执行结果自然飘忽；任务书写得过满，模型又会被噪声淹没。Prompt 工程的重点不是堆形容词，而是让输入结构化、边界明确、冲突可处理。

RAG Prompt 的典型模板

你是一个面向企业知识库的问答助手。

请只依据【参考资料】回答【用户问题】。
如果参考资料不足以支持答案，请明确说明缺少哪些信息。
不要编造政策、数字、接口字段或来源。

【参考资料】
1. 文档：...
   片段：...

【用户问题】
...

【回答要求】
- 先给结论，再给依据。
- 涉及事实时标注来源。
- 不确定时说明不确定。

这个模板并不神秘，但它把三个关键约束说清楚了：依据是什么，问题是什么，不能做什么。

常见误区

第一个误区是把 Prompt 当作补丁系统。召回差、分块差、元数据缺失，本质是数据和检索问题，不能都靠一句“请准确回答”解决。

第二个误区是角色设定过度。把助手写成“世界顶级专家”并不能自动提高事实正确率，最多提高自信程度，甚至更危险。

第三个误区是忽略冲突处理。多份资料互相矛盾时，Prompt 应要求模型说明冲突，而不是选择看起来最顺眼的一条。

第四个误区是没有输出契约。面向前端、工作流或评测系统的答案，应尽量约定字段、引用、状态或结构，否则后续处理会很痛苦。

工程落点

Ragent 中的 Prompt 不只是写在一段字符串里。问答链路会先构造意图、检索结果、可用工具和上下文，再由 Prompt 服务统一组织给模型。这样做的好处是：业务层不用关心 Prompt 细节，Prompt 层也能根据意图模板、智能体人设和证据数量动态调整。

更成熟的做法是把 Prompt 当作配置资产管理：有默认版本，有智能体级覆盖，有空槽位回退，有评测数据验证。只要 Prompt 会影响答案质量，它就不该是随手散落在代码里的魔法文本。

后面的 智能体管理与运行时 Prompt 治理 会继续展开这件事：当 Prompt 从单个模板变成多套方案、多种场景和运行时配置之后，系统应该怎样处理默认值、优先级、变量校验、缓存失效和效果验证。先把这里的基础概念看懂，再去改后台 Prompt；顺序反了，也不是不能做，只是排错时会比较像在雾里辨认家具。

小结

大模型负责理解和生成，Prompt 负责定义任务边界，RAG 负责提供证据。三者配合时，答案才有机会既自然又可靠。记住：Prompt 是控制面，不是垃圾处理站。前面链路制造出来的问题，最后通常不会凭空消失。
