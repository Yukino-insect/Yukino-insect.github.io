MCP、Function Call 与工具体系

August 15, 2026

学习目标

  • 理解 RAG 和工具调用的边界。
  • 区分 Function Call、Plugin 和 MCP 的角色。
  • 知道工具调用链路中的参数提取、权限和失败处理。
  • 能判断知识库回答何时应升级为工具执行。

为什么 RAG 需要工具

知识库擅长回答“资料中有什么”，但很多业务问题不是查文档就能完成。例如用户问“我这个订单现在到哪了”，知识库可以解释订单状态含义，却不能知道某个订单的实时状态。此时需要调用业务系统。

工具调用的价值在于把模型连接到外部能力：搜索网页、查数据库、调用业务接口、生成工单、触发审批。模型负责理解用户意图和组织参数，工具负责执行确定性动作。

这也意味着工具调用比普通问答更危险。它可能访问敏感数据、产生费用、修改状态或触发外部副作用。没有权限、审计和确认机制的工具调用，只是把事故包装成了智能化。

Function Call 是什么

Function Call 是模型侧的一种能力：开发者给模型描述可用函数，包括函数名、参数 schema 和说明；模型根据用户问题生成结构化调用请求；应用程序执行函数，再把结果交回模型生成答案。

它解决的是“模型如何表达想调用哪个函数以及参数是什么”。真正执行仍然在业务系统中完成。

MCP 是什么

MCP 可以理解为一套更通用的工具协议。它把工具能力、资源和提示等内容通过标准协议暴露出来，让不同客户端和服务端更容易集成。

如果 Function Call 更像“模型供应商 API 里的函数描述”，MCP 则更像“工具服务的标准接入层”。在 Ragent 这类系统中，MCP 工具可以作为知识库无法回答时的补充路径，也可以挂在意图节点上，让路由结果决定是否调用工具。

工具调用链路

一条典型工具调用链路如下：

用户问题 -> 意图识别 -> 判断需要工具 -> 参数提取 -> 权限校验 -> 执行工具 -> 结果格式化 -> 生成最终回答

其中最容易出错的是参数提取。用户说“查一下上周那个订单”，模型必须知道“上周”对应哪个时间范围，“那个订单”能否从历史对话中解析出来。如果参数不足，系统应追问，而不是随便补一个。

工具和知识库如何配合

知识库负责解释规则，工具负责查询事实或执行动作。以售后场景为例：

  • “退货政策是什么”：优先查知识库。
  • “我的订单能不能退”：需要工具查询订单状态，再结合知识库规则解释。
  • “帮我提交退货申请”：需要工具执行，并可能要求用户确认。

Ragent 的意图节点可以区分知识库类意图和系统交互类意图。知识库类意图绑定 Collection，系统交互类意图绑定 MCP 工具，并配置参数提取 Prompt。这种设计比让模型自由决定所有动作更可控。

工程注意点

工具描述必须简洁准确。描述越含糊，模型越容易误选工具或乱填参数。

参数 schema 必须严格。枚举、必填字段、时间格式、ID 格式都应该写清楚，并在服务端二次校验。

权限校验不能交给模型。模型可以建议调用，真正能不能执行必须由业务系统判断。

有副作用的工具要谨慎。查询类工具可以直接执行；写入、删除、支付、审批类工具通常需要用户确认和审计记录。

失败结果也要结构化。工具超时、参数错误、权限不足、业务不存在，应给模型明确状态，避免模型把失败包装成成功。

常见误区

把 MCP 当成 RAG 的替代品是错误的。MCP 负责接工具，RAG 负责接知识，两者解决的问题不同。

让模型直接拼 SQL 或调用内部接口也很危险。工具层应该提供受控能力，而不是把整个系统裸露给模型。

忽略参数追问会让体验变差。参数不足时，优雅追问比盲目调用更专业。

小结

RAG 让模型知道文档里的事实，MCP 和工具调用让模型使用外部能力。前者强调证据，后者强调执行。真正的 Agentic AI 系统，必须把两者放在受控边界内协作，而不是把“智能”当作绕过工程约束的借口。
