记忆、重写与意图路由

August 15, 2026

学习目标

  • 理解多轮对话为什么需要记忆和查询重写。
  • 掌握意图路由在 RAG 中的作用。
  • 能说明全局检索和定向检索的区别。
  • 能识别对话增强带来的风险。

多轮对话的问题

用户很少每次都把问题说完整。第一轮问“如何配置知识库”，第二轮问“那失败了怎么办”，第三轮问“这个能定时吗”。如果系统只看当前一句，就不知道“那”和“这个”指什么。

记忆的作用是保存对话上下文，查询重写的作用是把当前问题改写成可独立检索的问题。例如：

历史：用户询问知识库文档同步。
当前：失败了怎么恢复？
重写：知识库文档定时同步失败后如何恢复？

这一步看似朴素，却直接影响召回质量。检索系统需要完整问题，而不是人类对话里的省略表达。

记忆保存什么

对话记忆通常不应无限保存原文。工程上要考虑窗口大小、Token 成本、隐私和噪声。

常见做法包括：

  • 保存最近 N 轮原始消息。
  • 对更早历史做摘要。
  • 只保存和任务有关的关键信息。
  • 对敏感信息做脱敏或权限控制。

Ragent 的问答链路会围绕 conversation 维护消息记录，并在构造请求时取出必要上下文。记忆不是越多越好，越多也可能意味着越吵。

查询重写

查询重写的目标是生成一个更适合检索的问题。它可以做三类事情：

第一，补全上下文，把“它”“这个”“刚才说的”还原成具体对象。

第二，规范表达，把口语化问题改写成更稳定的检索语句。

第三，拆分复杂问题，把一个多意图问题拆成多个子问题。

但查询重写必须保持原意。不能为了召回方便而改写出用户没有问的内容。重写结果最好保留日志，便于排查“为什么搜偏了”。

意图路由

意图路由用于判断问题应该走哪个知识范围或工具能力。一个系统可能有多个知识库、多个 Collection、多个业务工具，全部一起查会导致噪声、越权和成本上升。

意图树通常包含领域、类别和主题。叶子节点可以绑定 Collection、TopK、Prompt 片段或 MCP 工具。在线问答时，系统先识别用户问题匹配哪些意图，再决定检索范围和工具候选。

Ragent 的意图节点支持知识库类和系统交互类：知识库类绑定 collection_names，系统交互类绑定 mcp_tool_id。这使得“查知识”和“调工具”可以用同一套路由结果承接。

全局检索与定向检索

全局检索是在当前可用 Collection 中广泛搜索，适合意图不明确或系统没有足够把握时使用。

定向检索是根据意图节点限定 Collection 或范围，适合业务边界明确的问题。它能减少噪声，提高命中质量，也有利于权限隔离。

风险在于路由错误。如果意图识别把问题分错了类，定向检索会把正确答案排除在外。因此成熟系统通常会设置置信度阈值：高置信走定向，低置信保留全局或补充检索。

常见误区

把历史消息全部塞进 Prompt，会增加成本和干扰。记忆需要筛选和摘要。

让重写模型自由发挥，会改变用户问题。重写应忠于原意，只补全，不扩写。

意图树越细不一定越好。节点过多会增加维护成本，也会让分类边界变模糊。

只相信第一意图也有风险。复杂问题可能跨多个 Collection，需要多意图并行处理。

小结

记忆解决“这句话依赖前文”的问题，重写解决“检索需要完整表达”的问题，意图路由解决“去哪里找答案”的问题。三者让 RAG 从单轮问答走向可用的多轮业务助手，但也必须用阈值、日志和评测控制风险。
