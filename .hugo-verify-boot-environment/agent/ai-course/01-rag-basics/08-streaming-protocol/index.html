SSE 与流式响应

August 15, 2026

学习目标

  • 理解为什么在线问答需要流式输出。
  • 掌握 SSE 的基本工作方式。
  • 知道流式链路中的取消、异常和并发问题。
  • 能区分用户感知延迟和真实模型耗时。

为什么需要流式响应

大模型生成答案通常需要几秒到几十秒。同步等待完整答案会让用户觉得系统卡住，即使后端正在正常工作。流式响应把生成中的 Token 或文本片段逐步推给前端，让用户尽快看到输出。

流式响应不能让模型计算更快，但能降低首字等待时间。对问答产品来说，这一点非常重要。用户看到内容开始出现，就会愿意继续等待；空白页面则只会让人怀疑系统已经坏了。

SSE 是什么

SSE，即 Server-Sent Events，是一种基于 HTTP 的服务端单向推送协议。浏览器或前端发起连接后，服务端可以不断发送事件。

典型事件格式如下：

event: message
data: {"content":"第一段回答"}

event: message
data: {"content":"第二段回答"}

event: done
data: {}

SSE 的优点是简单、兼容 HTTP、适合服务端持续推送文本。它不适合双向实时通信，如果需要客户端和服务端频繁互发消息，WebSocket 会更合适。

流式问答链路

一次流式问答通常包含：

创建 SSE 连接 -> 初始化任务 -> 检索和 Prompt 构造 -> 调用模型流式接口 -> 转发 Token -> 完成或异常关闭

在 Ragent 中，框架层对 SseEmitter 做了封装，问答服务通过发送器推送事件。流式任务还需要任务管理器记录取消状态，否则用户点“停止生成”后，后端可能仍在继续消耗模型资源。

首包延迟

首包延迟指从用户提交问题到收到第一个有效输出的时间。它由多段组成：

  • 排队等待时间。
  • 记忆读取和查询重写时间。
  • 意图识别和检索时间。
  • Rerank 和 Prompt 拼装时间。
  • 模型连接和首个 Token 生成时间。

优化首包不能只盯模型。检索慢、Rerank 候选过多、工具调用超时、线程池排队都会让用户等不到第一段输出。

取消任务

停止生成不是前端隐藏文本那么简单。可靠的取消至少要处理三层：

第一，前端断开或发起停止请求。

第二，后端任务状态标记为 cancelled，并让流式循环尽快感知。

第三，如果底层模型客户端支持取消，尽量关闭连接或中断读取，避免继续付费。

分布式部署时，取消状态还需要跨节点可见。只存在单机内存里的取消标记，在负载均衡场景下很容易失效。

异常处理

流式链路的异常比同步接口更麻烦，因为连接可能已经向用户输出了一部分内容。

常见异常包括：模型超时、上游 SSE 格式异常、客户端断开、发送失败、线程池拒绝、检索阶段失败。系统应尽量发送明确的错误事件，并清理任务状态。已经发送出去的内容不能撤回，所以更要在生成前控制证据质量。

常见误区

把所有中间过程都流给用户并不一定好。检索、重写、意图识别可以用于调试面板或 Trace，但普通用户通常只关心答案、来源和错误。

忽略背压会造成资源问题。用户网络慢、前端处理慢、模型输出快时，服务端要避免无限堆积。

没有心跳事件也不稳。长时间没有 Token 时，代理或浏览器可能认为连接空闲而断开。

小结

SSE 解决的是在线问答的体验和交互问题。一个成熟的流式系统，不只是把模型 Token 原样转发出来，还要处理首包、取消、异常、心跳、任务状态和资源清理。用户看到的是文字慢慢出现，工程师要负责的是背后那条连接不要悄悄失控。
