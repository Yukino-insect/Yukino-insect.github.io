RAG 评估与优化总览

August 15, 2026

学习目标

  • 理解为什么 RAG 必须做评测。
  • 区分检索评测、生成评测和系统评测。
  • 能建立基础评测集。
  • 能用数据驱动 Chunk、检索、Rerank 和 Prompt 优化。

为什么要评测

RAG 系统很容易出现“感觉变好了”的错觉。改了 Chunk 大小、换了 Embedding、调了 TopK、加了 Rerank，演示问题可能回答得更漂亮，但真实业务问题未必更好。

没有评测，优化就会变成试手气。一次改动提升了某类问题，也可能伤害另一类问题。工程上必须把问题集、期望答案、引用证据、运行参数和结果指标记录下来，才能判断系统是否真的进步。

三层评测

第一层是检索评测，关注正确证据有没有被找出来。常见指标包括 Recall@K、MRR、命中率、首条正确位置和无关召回比例。

第二层是生成评测，关注答案是否正确、忠实、完整、可读。常见维度包括答案相关性、事实一致性、引用支持度、拒答质量。

第三层是系统评测，关注延迟、成本、失败率、超时率、并发稳定性和资源占用。一个答案再准确，如果 30 秒才首包，线上体验也很难看。

这三层不能互相替代。检索好不代表生成好，生成好不代表系统可用，系统快也不代表答案可信。

评测集怎么建

基础评测集至少包含：

  • 用户问题：真实或模拟业务问题。
  • 标准答案：人工整理的期望回答。
  • 参考证据：应命中的文档、章节或 Chunk。
  • 问题类型：事实查询、流程说明、对比总结、多轮追问、拒答场景等。
  • 难度标签：简单、跨文档、歧义、需要工具、资料不足。

评测集不需要一开始很大，但必须覆盖关键业务路径。二三十条高质量问题，通常比几百条随便生成的问题更有价值。

优化闭环

一个理性的优化流程是：

发现问题 -> 定位层级 -> 提出改动 -> 固定评测集回归 -> 分析副作用 -> 决定是否上线

如果正确证据没有召回，优先看解析、Chunk、Embedding、过滤条件和检索通道。

如果证据召回了但排序靠后，优先看融合策略、Rerank 候选池和精排模型。

如果证据进入 Prompt 但答案错误，优先看 Prompt 约束、上下文格式、模型能力和冲突处理。

如果答案正确但体验差，优先看首包延迟、并发队列、Rerank 耗时、模型路由和流式发送。

常见误区

只评测最终答案会掩盖问题来源。你知道答案错了，却不知道错在召回、排序还是生成。

只用模型当裁判也有风险。LLM-as-judge 可以提高效率，但关键问题仍应有人类样本校验。

只看平均值不够。RAG 系统经常在长尾问题上失败，P95 延迟、失败样本和低分原因比平均分更能指导优化。

频繁更换评测集也不合理。评测集可以扩充，但核心回归集要稳定，否则无法比较版本。

小结

RAG 评测的目的不是给系统打一个好看的分数，而是建立可解释的改进循环。好系统不是从第一次设计就完美，而是能稳定发现问题、定位问题、验证改动。没有评测的 RAG，只是在用自信替代证据。
