宏观设计与上传链路

August 15, 2026

学习目标

  • 理解知识库模块的领域模型。
  • 掌握文件上传到可解析文档的基本流程。
  • 知道数据库、对象存储和向量库各自承担什么职责。
  • 能识别上传链路中的一致性问题。

知识库不是文件列表

一个成熟知识库至少包含三类数据。

第一类是业务元数据，例如知识库名称、描述、启用状态、Collection 名称和创建人。

第二类是文档元数据，例如文档名、文件类型、大小、来源、处理状态、解析配置、定时同步配置。

第三类是检索资产，例如 Chunk 原文、向量、元数据、分块日志、解析任务记录。

如果只有文件列表，没有状态、日志和索引，那么系统无法回答“这份文档是否已经可检索”“为什么解析失败”“哪些 Chunk 来自旧版本”这些问题。

上传链路

一次普通文件上传可以拆成以下步骤：

前端选择文件
  -> 后端校验大小、类型、权限
  -> 文件流写入对象存储
  -> 数据库创建文档记录
  -> 返回文档 ID 和初始状态
  -> 用户或系统触发解析分块

对象存储保存原始文件，数据库保存文档记录和状态，向量库保存可检索 Chunk。三者不能互相替代。尤其不要把原始文件只存在数据库字段里，除非你真的很想给数据库找麻烦。

状态设计

文档状态通常包括：

  • pending：已创建，等待处理。
  • running：正在解析、分块或向量化。
  • success：处理完成，可以被检索。
  • failed：处理失败，需要用户重试或系统恢复。

状态字段的意义在于控制用户界面和在线检索。只有成功且启用的文档，才应该进入问答链路。处理中或失败的文档如果被检索到，用户会得到半成品知识。

一致性问题

上传链路至少有两个外部资源：对象存储和数据库。常见问题包括：

  • 文件上传成功，数据库写入失败。
  • 数据库记录创建成功，文件上传失败。
  • 用户重复点击导致多条文档记录。
  • 后端超时，但对象存储里已经有文件。

解决思路不是追求分布式事务，而是让每一步可补偿、可幂等、可清理。比如对象存储路径使用业务 ID，数据库记录带状态，失败时定时清理孤儿文件，重复请求通过幂等键或内容 hash 去重。

Collection 设计

Collection 是检索隔离边界。知识库可以对应一个或多个 Collection，文档入库时写入对应 Collection，问答时按 Collection 限定召回范围。

Collection 名称不要随意拼接。它最好具备稳定规则，例如按知识库 ID、租户 ID 或业务域生成。否则后续迁移、权限过滤和排错都会变成考古工作。

工程落点

Ragent 的知识库链路中，文档表负责保存文件来源、处理模式、状态和 ingestion_spec。对象存储保存真实文件，向量表按 collection_name 保存 Chunk 和 Embedding。分块日志记录解析、分块、向量化、持久化耗时，让一次入库任务可观测。

这种分层有一个好处：用户上传文件后，不必等待整个解析完成；系统可以异步处理，也可以在失败时精准定位问题。

常见误区

把上传接口做成同步全流程，会让大文件和慢解析拖垮请求线程。

只记录成功状态，不记录失败原因，会让运维和用户都无从下手。

文档删除时只删数据库记录，不处理向量数据，会导致旧知识继续被召回。

没有区分文件来源，会让本地上传、URL 同步和外部系统推送混在一起，后续调度很难管理。

小结

知识库建设的第一步是把“文件”变成有状态、有来源、有处理配置的“文档资产”。上传链路必须关注一致性、幂等和可恢复，而不是只关心接口能不能返回 200。
