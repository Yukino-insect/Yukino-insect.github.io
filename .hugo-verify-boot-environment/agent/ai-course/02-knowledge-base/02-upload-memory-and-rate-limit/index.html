文件上传、内存占用与分布式限流

August 15, 2026

学习目标

  • 理解大文件上传对后端资源的压力。
  • 掌握流式处理和临时文件策略。
  • 知道为什么上传和解析都需要限流。
  • 能设计分布式部署下的资源保护方案。

上传为什么会拖垮系统

文件上传看起来只是一个接口，实际会占用网络连接、请求线程、内存、磁盘、对象存储带宽和数据库连接。多个用户同时上传大文件时，系统很容易出现内存飙升、GC 抖动、线程池耗尽或对象存储写入超时。

最危险的写法是把整个文件一次性读入内存，再做校验、计算 hash 或转发上传。小文件时看不出问题，一旦用户上传几百 MB 的 PDF，系统就会用非常诚实的方式告诉你它不喜欢这样。

流式上传

更合理的方式是使用流式处理：

HTTP multipart stream -> 边读边校验 -> 边写对象存储 -> 记录文件大小和 hash

流式处理的关键是不要把完整文件保存在堆内存中。需要计算 hash 时，可以在读取流的过程中增量计算。需要检测 MIME 类型时，可以读取少量头部信息并结合文件名、内容探测结果判断。

如果框架会先把 multipart 缓存在临时文件，也要配置合理的阈值和目录，避免默认配置把压力转移到不可控位置。

上传前校验

上传接口至少应该校验：

  • 用户是否有当前知识库的写权限。
  • 文件大小是否超过限制。
  • 文件扩展名和 MIME 类型是否允许。
  • 知识库当前是否达到文档数量或容量限制。
  • 文件名是否需要规范化，避免路径穿越或特殊字符问题。

这些校验越早做越好。已经把大文件传完再告诉用户“你没有权限”，系统和用户都会沉默一下。

为什么需要限流

上传限流解决的是入口压力，解析限流解决的是后续计算压力。两者都需要。

上传阶段要限制同时上传数量、单用户上传频率、单文件大小和租户总容量。解析阶段要限制同时解析任务数、Embedding 并发数、Rerank 或 VLM 调用量，以及外部解析服务的吞吐。

如果只限制上传，不限制解析，用户可以在短时间内提交大量文件，让后台任务堆积到不可恢复。如果只限制解析，不限制上传，对象存储和数据库又会被大量待处理文档填满。

分布式限流

单机限流只在一个进程内有效。多节点部署时，需要 Redis、Redisson 或类似组件做分布式计数和锁。

常见策略包括：

  • 全局并发限制：整个集群同时处理的上传或解析任务数。
  • 用户维度限制：防止单个用户占满资源。
  • 知识库维度限制：防止一个知识库大批量重建影响其他知识库。
  • 外部服务维度限制：保护 MinerU、Embedding 模型和对象存储。

限流不是为了为难用户，而是为了让所有用户都能得到可预期的服务。系统没有边界，最后边界就会由宕机来划。

排队与反馈

当任务超过即时处理能力时，系统应进入排队，而不是无差别拒绝。用户界面需要展示状态：等待中、处理中、成功、失败。后台则要记录排队时间和执行时间，便于判断瓶颈到底在上传、解析、向量化还是持久化。

对于超大文件，可以提示用户拆分文档或使用异步通知。不要让 HTTP 请求挂十几分钟等待完整处理，那不是耐心，是事故预备。

常见误区

只配置 Nginx 上传大小，不等于后端安全。后端仍要校验和保护内存。

只按文件数量限流不够。一个 500 MB 文件和一个 50 KB 文件的资源消耗完全不同。

只看平均上传耗时也不够。P95、P99 和失败率更能反映真实体验。

没有清理临时文件，会让磁盘在某个安静的下午突然满掉。系统很少会挑你有空的时候出问题。

小结

上传链路的核心是资源保护。流式处理降低内存压力，限流保护系统吞吐，排队和状态反馈保护用户体验。知识库系统接收的是文件，但真正管理的是资源。
