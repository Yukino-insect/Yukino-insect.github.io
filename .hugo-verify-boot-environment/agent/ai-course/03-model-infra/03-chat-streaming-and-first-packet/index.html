Chat 同步调用、SSE 解析与首包探测

August 15, 2026

学习目标

  • 区分同步 Chat 和流式 Chat 的工程差异。
  • 理解 OpenAI 风格 SSE 响应的解析方式。
  • 掌握首包探测的意义。
  • 能处理流式调用中的超时、异常和统计。

同步 Chat

同步 Chat 调用最容易理解：发送 messages，等待模型返回完整 answer。它适合短任务，例如意图分类、查询重写、摘要生成、参数抽取。

同步调用的优点是代码简单、异常边界清晰、结果完整。缺点是用户必须等待整个响应，长回答体验较差。

在 RAG 中，不要把所有模型任务都做成流式。查询重写和意图分类的结果通常很短，同步更方便；最终回答面向用户，流式更合适。

流式 Chat

流式 Chat 会从模型服务持续收到增量数据。OpenAI 风格接口通常以 SSE 格式返回，每行可能包含一个 data: 事件，事件里是 JSON 片段，最后以 [DONE] 结束。

服务端要做的事包括：

  • 建立上游模型流式连接。
  • 逐行读取 SSE 数据。
  • 解析增量内容。
  • 转发给前端 SSE。
  • 记录首包和总耗时。
  • 处理取消、异常和完成事件。

看起来像管道，其实每一段都可能漏水。协议解析尤其不能靠随便截字符串糊弄，供应商返回空行、心跳、异常 JSON 或结束标记时都要正确处理。

SSE 解析

一个稳健的 SSE Parser 应能处理：

  • 空行。
  • 非 data: 行。
  • data: [DONE]。
  • JSON 结构缺字段。
  • 增量内容为空。
  • 流式 reason 或 usage 信息。

Ragent 中有针对 OpenAI 风格 SSE 解析的测试，说明这部分已经被当作基础能力管理。很好，至少不是把生产协议当作“应该差不多”的字符串作业。

首包探测

首包探测关注模型是否能在合理时间内返回第一个有效片段。对流式问答来说，首包比总耗时更能影响用户体验。

首包慢可能来自：

  • 模型排队。
  • 网络连接慢。
  • 上游服务开始生成慢。
  • 请求 Prompt 太长。
  • 检索和 Rerank 在调用模型前已经耗时过多。

基础设施层可以记录首包耗时，并把异常首包作为模型健康判断的一部分。如果某个模型总是首包超时，就算最终偶尔能返回，也不适合在线问答主链路。

超时设计

流式调用至少要区分连接超时、首包超时、读超时和总超时。

连接超时表示连不上供应商。首包超时表示模型迟迟不开始输出。读超时表示输出过程中长时间无数据。总超时则控制整次请求最长生命周期。

这些超时不要混成一个数字。查询重写可以很短，最终回答可以较长；首包应该短，总输出可以相对长。不同任务需要不同预算。

指标和日志

Chat 调用应记录：

  • 模型 ID、供应商和能力。
  • 是否流式。
  • Prompt Token 和 Completion Token。
  • 首包耗时和总耗时。
  • 结束原因。
  • 错误类型。
  • 是否触发重试或切换。

日志要脱敏。用户问题、知识库内容和工具返回都可能包含敏感信息。调试需要证据，生产需要边界，两者都不能省。

常见误区

把流式输出等同于高性能。流式只是改善感知，后端总成本可能并没有下降。

首包只统计模型时间不够。用户等待的是整条链路，从提交问题到看到文字。

流式中途失败后假装完成，会误导用户。应该发送明确错误事件或结束状态。

解析器没有测试，会在供应商格式微小变化时产生奇怪问题。

小结

Chat 调用层要同时服务后台短任务和前台长回答。同步调用重在简单可靠，流式调用重在协议解析、首包体验和异常管理。把这些能力沉到基础设施层，业务问答才能专注于 RAG 流程本身。
