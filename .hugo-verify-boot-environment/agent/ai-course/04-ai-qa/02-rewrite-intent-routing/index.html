查询重写、意图树与路由决策

August 15, 2026

学习目标

  • 理解查询重写和意图识别的先后关系。
  • 掌握意图树的节点设计。
  • 能说明 Collection 绑定和 MCP 工具绑定。
  • 能设计全局检索、定向检索和补充检索策略。

查询重写先于路由

意图识别依赖问题表达。如果用户的问题是“那要怎么恢复”，分类器很难判断它属于文档同步、模型调用还是用户权限。先用会话记忆重写成完整问题，再做意图识别，结果会更稳定。

重写不是扩写。它只应该补全必要上下文、消除指代、规范表达。不能把“怎么配置”擅自改成“请给我生产环境最佳实践”，听起来更专业，但已经不是用户的问题。

意图树结构

意图树通常包含三层：

  • 领域层：例如知识库、模型基础设施、问答链路、系统管理。
  • 类别层：例如文档同步、Embedding、Rerank、权限。
  • 主题层：例如“同步失败恢复”“向量维度不一致”“停止生成”。

每个节点应有稳定编码、名称、描述、示例问题、排序字段和启用状态。叶子节点可以绑定知识库 Collection、TopK、Prompt 片段或 MCP 工具。

Ragent 的 t_intent_node 中既保留了旧的 collection_name，也支持新的 collection_names。这说明意图和知识范围不是一对一关系，一个意图可以对应多个 Collection。是的，数据库字段也会成长，只是它成长时通常会顺便让你补一条迁移 SQL。

路由输出

路由结果不应只有一个字符串。更合理的结构包括：

  • 命中的意图节点。
  • 置信度。
  • 节点类型：知识库类或系统交互类。
  • 目标 Collection 列表。
  • MCP 工具 ID。
  • 当前节点的 Prompt 片段。
  • 建议 TopK。

这些信息会继续影响检索范围、工具调用和 Prompt 拼装。

全局、定向与补充

全局检索适合意图不清或置信度低的情况。它覆盖面广，但噪声更多。

定向检索适合意图明确的情况。它只检索绑定 Collection，召回更集中，成本也更低。

补充检索用于避免过度收窄。比如系统对某个意图有较高置信，但仍保留一部分预算给相邻 Collection 或全局候选，减少路由错误造成的漏召回。

Ragent 的检索范围解析会根据意图得分、目标 Collection 和活动 Collection 计算 RetrievalScope。这类设计的核心是控制范围，而不是让每个通道自己随意决定去哪里搜。

多意图问题

用户可能一次问多个问题，例如“知识库怎么定时同步，失败了还能自动恢复吗”。这类问题最好拆成子问题，分别识别意图，再合并检索结果。

多意图处理要注意预算。每个意图都查 TopK，候选数会迅速膨胀。更好的做法是先分配总预算，再根据置信度和问题数量切分。

Prompt 片段

意图节点上的 Prompt 片段可以提供领域规则。例如售后政策类问题要求先判断订单状态，技术文档类问题要求给步骤和配置项。

但 Prompt 片段不应包含过多业务知识本体。知识本体仍应在文档和工具中维护，否则意图树会变成另一个难以治理的知识库。

常见误区

意图节点只写名称，没有描述和示例，会让分类效果很不稳定。

意图树过深会增加维护成本。分类边界越细，越需要评测和运营支持。

路由只返回第一意图，会伤害跨领域问题。

低置信也强制定向，会把正确答案排除在检索范围外。

小结

查询重写让问题完整，意图树让知识空间可治理，路由决策让检索和工具调用有边界。它们共同决定 RAG 系统是“全库乱搜”，还是“按业务语义有控制地搜索”。
