知识库答不了时如何转 MCP 与拼 Prompt

August 15, 2026

学习目标

  • 理解知识库回答和工具调用的切换条件。
  • 掌握 MCP 参数提取流程。
  • 能设计工具结果进入 Prompt 的方式。
  • 能处理参数不足、工具失败和安全边界。

什么时候转工具

知识库适合回答静态知识，工具适合处理动态数据或动作。系统可以根据意图节点类型、用户问题和检索结果判断是否需要 MCP。

典型转工具场景包括：

  • 问题需要实时状态，例如订单、库存、任务进度。
  • 问题需要外部搜索，例如最新公开信息。
  • 问题需要业务动作，例如创建工单、提交申请。
  • 知识库证据不足，但意图节点绑定了可用工具。

如果知识库已经能完整回答，就不必为了“显得智能”调用工具。额外调用只会增加延迟、成本和风险。

参数提取

工具调用前要把用户自然语言转换成结构化参数。参数提取 Prompt 应包含：

  • 工具用途。
  • 参数 schema。
  • 必填字段。
  • 字段格式要求。
  • 可从历史对话继承的信息。
  • 参数不足时的输出方式。

例如订单查询工具需要 orderId，用户只说“查一下我的订单”时，系统应追问订单号，而不是生成一个看起来像订单号的字符串。模型编 ID 的能力很强，问题是业务系统并不会因此感动。

参数校验

模型输出参数后，服务端必须再次校验：

  • JSON 格式是否合法。
  • 必填字段是否存在。
  • 枚举值是否在允许范围内。
  • ID、日期、金额等格式是否正确。
  • 当前用户是否有权限查询或执行。

校验失败时，应返回可解释状态，让模型组织追问或错误提示。不能让模型绕过服务端校验直接访问业务接口。

工具执行

工具执行结果最好结构化返回，例如：

{
  "status": "success",
  "data": {
    "orderStatus": "shipped",
    "updatedAt": "2026-08-15 10:30:00"
  }
}

失败也要结构化：

{
  "status": "permission_denied",
  "message": "当前用户无权查看该订单"
}

这样模型才能根据状态生成正确回答，而不是把异常堆栈翻译给用户。

Prompt 拼装

最终 Prompt 可以包含三类上下文：

  • 知识库证据：解释规则和背景。
  • 工具结果：提供实时事实或执行结果。
  • 意图提示：提供领域回答约束。

例如“我的订单能不能退货”需要先用工具查订单状态，再用知识库查退货政策，最后由模型综合回答。Prompt 中应明确区分“规则依据”和“实时数据”，避免模型把工具结果当作政策，或把政策当作当前状态。

权限和审计

MCP 工具尤其需要权限和审计。查询类工具要检查数据权限，写入类工具要记录操作者、参数、时间和结果。有副作用的工具通常还需要用户确认。

模型不能成为权限主体。真正的权限主体是当前登录用户和系统授权。模型只是辅助生成调用意图。

常见误区

工具参数不足时不追问，直接猜。结果通常很快，也很错。

把工具错误包装成正常答案，会让用户误以为操作成功。

工具结果直接拼进 Prompt 不做筛选，可能泄露敏感字段。

所有问题都先调工具，会把系统变慢，也增加外部依赖。

小结

MCP 让 RAG 系统能访问动态能力，但它也带来权限、参数和副作用问题。正确做法是：意图判断是否需要工具，模型提取候选参数，服务端严格校验和执行，工具结果再作为证据进入 Prompt。智能要服从边界，这一点很基本，也很容易被忽略。
