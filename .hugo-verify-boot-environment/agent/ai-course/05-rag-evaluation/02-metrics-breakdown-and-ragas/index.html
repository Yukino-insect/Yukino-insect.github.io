指标拆解、性能口径与 RAGAS

August 15, 2026

学习目标

  • 掌握检索、生成和系统性能指标。
  • 理解自动评测工具的优势和局限。
  • 能设计适合业务的综合评分。
  • 能避免指标误读。

检索指标

检索指标关注“正确证据有没有被找到”。

常见指标包括：

  • Recall@K：前 K 条候选中是否包含黄金证据。
  • Precision@K：前 K 条中有多少是相关证据。
  • MRR：第一个正确证据排名越靠前，分数越高。
  • NDCG：考虑多个相关证据和排序位置。
  • Hit Rate：是否至少命中一个正确证据。

RAG 中 Recall@K 特别重要。关键证据没有进入候选池，生成阶段就很难正确。

生成指标

生成指标关注“答案是否好”。

常见维度包括：

  • Correctness：答案是否符合标准答案。
  • Faithfulness：答案是否被给定证据支持。
  • Relevance：是否回答了用户问题。
  • Completeness：关键要点是否完整。
  • Citation Support：引用是否真的支持对应结论。
  • Refusal Quality：资料不足时是否正确拒答或说明缺口。

其中 Faithfulness 是 RAG 特有的重点。答案正确但不是来自证据，在某些场景也可能不可接受，因为它无法追踪。

系统指标

系统指标关注“能不能在线上用”。

至少应记录：

  • 首包耗时。
  • 总耗时。
  • 检索耗时。
  • Rerank 耗时。
  • 模型生成耗时。
  • 成本或 Token 消耗。
  • 错误率、超时率、取消率。
  • 并发下 P95、P99 延迟。

平均值很容易骗人。用户感受到的是长尾延迟，系统稳定性也常常死在长尾上。

RAGAS 类工具

RAGAS 是一类常见的 RAG 自动评测思路，通常会用模型判断答案相关性、上下文相关性、忠实度等指标。它的优势是效率高，可以快速跑大量样本，适合回归和趋势观察。

但自动评测不是绝对裁判。它依赖裁判模型本身，可能误判专业领域知识，也可能对格式和表达敏感。因此关键业务样本仍应保留人工复核，尤其是合规、财务、医疗、合同等高风险场景。

更稳妥的做法是：自动评测用于发现趋势和候选问题，人工复核用于校准高风险结论。

指标组合

不同场景的指标权重不同。

客服知识库更关注答案相关性、引用支持和首包体验。

研发文档助手更关注检索召回、技术准确性和代码引用。

合规问答更关注忠实度、拒答质量和审计记录。

因此不要追求一个通用总分解决所有问题。综合分可以用于看趋势，但报告里必须保留分项指标。总分上升但忠实度下降，这不是好消息，只是坏消息穿了件体面外套。

对比实验

评测常用于对比实验，例如：

  • Chunk 512 vs 1024。
  • 向量检索 vs 混合检索。
  • 无 Rerank vs 有 Rerank。
  • 不同 Embedding 模型。
  • 不同 Prompt 模板。
  • 不同候选池上限。

对比时一次最好只改一个主要变量，否则很难知道效果来自哪里。每次运行要记录配置版本和代码版本。

常见误区

只看最终答案分，不看检索指标，会掩盖召回问题。

只看 Recall@K，不看上下文噪声，会让 Prompt 被无关证据淹没。

只看准确率，不看拒答质量，会鼓励模型乱答资料不足的问题。

只看平均延迟，不看 P95 和 P99，会低估线上体验风险。

小结

RAG 指标要分层看：检索指标定位证据问题，生成指标定位答案问题，系统指标定位体验和稳定性问题。自动评测能提效，但不能替代业务判断。好指标不是为了好看，而是为了指导下一步该改哪里。
