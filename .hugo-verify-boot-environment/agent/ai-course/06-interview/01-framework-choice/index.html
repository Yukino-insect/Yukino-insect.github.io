为什么不使用 Spring AI 或 LangChain4j

August 15, 2026

面试官想问什么

这个问题表面是在问框架，实际是在问你是否理解项目边界。面试官并不一定期待你否定 Spring AI 或 LangChain4j，而是想看你能否解释：什么时候用框架，什么时候自己做基础设施，自己做又承担了哪些成本。

如果回答成“框架不好用”，就很薄。框架不是敌人，失去边界感才是。

可以这样回答

Spring AI 和 LangChain4j 都有价值，它们能快速封装模型调用、Prompt、Embedding、向量库和工具调用，对原型验证和标准 RAG 链路很有帮助。

但我们这个项目不只是做一个简单问答 Demo，而是要把 RAG 放进已有 Java 后端体系里，和权限、审计、知识库管理、模型路由、熔断、流式任务、MCP 工具、评测和数据库状态治理一起工作。我们的核心复杂度不在“怎么调模型接口”，而在这些工程边界如何统一。

所以主链路选择了自研可控的轻量抽象：模型侧按 Chat、Embedding、Rerank、VLM 分能力封装，通过路由器和健康状态做多模型选择；知识库侧自己管理上传、解析、分块、向量表和执行日志；问答侧自己编排重写、意图、检索、融合、Rerank、Prompt 和 SSE。

这样做的好处是可控性强，能贴合项目的权限、状态、日志和评测需求；代价是需要自己维护更多基础设施，比如模型适配、熔断、协议解析、Prompt 管理和测试。

如果未来业务链路更标准，或者某个框架在模型适配和工具协议上已经足够成熟，我们也可以把它作为底层适配层接入，而不是排斥它。

重点拆解

这个回答有四个关键点。

第一，承认框架价值。不要为了证明自己正确而贬低成熟项目。那会显得不专业。

第二，强调项目约束。比如已有 Java 生态、权限体系、数据库事务、流式任务、模型路由和评测闭环。

第三，说明自研范围。不是所有东西都自研，而是在核心编排和治理层保持可控。

第四，承认代价。自研意味着维护成本、测试成本和设计责任。

不要这样答

不要说“Spring AI 太简单，不适合生产”。太绝对，也不准确。

不要说“LangChain4j 性能不好”。没有数据支撑时，这类说法很危险。

不要说“我们不用框架是因为会显得技术更强”。这种回答如果出现在面试里，基本等于帮面试官节省时间。

不要把所有基础设施都说成自己写。比如 HTTP、JSON、连接池、对象存储、数据库 ORM，本来就应该复用成熟组件。

延伸追问

如果面试官问“自研会不会重复造轮子”，可以回答：

我们没有从零实现所有能力，而是在稳定通用组件之上做业务相关编排。比如模型客户端是供应商协议适配，熔断和路由是项目可用性要求，知识库状态和分块日志是业务治理要求。这些部分直接套通用框架反而需要大量绕路。重复造轮子的风险我们通过接口抽象、单元测试和配置驱动控制。

小结

这道题的好答案不是“框架不好，所以不用”，而是“框架能解决一部分问题，但当前项目的核心复杂度在工程治理和业务编排，我们选择在这些层面保持可控，同时承担维护成本”。取舍讲清楚，答案就站得住。
