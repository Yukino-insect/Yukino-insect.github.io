为什么会从 Milvus 转向 PGVector

August 15, 2026

面试官想问什么

这个问题考的是向量存储选型。面试官想知道你是否理解专用向量数据库和数据库扩展方案的差异：性能、运维、事务、一致性、数据规模、过滤查询和团队成本。

不要把答案说成“Milvus 不好”或“PGVector 更好”。更准确的说法是：不同阶段、不同规模、不同运维条件下，选择不同。

可以这样回答

Milvus 是专用向量数据库，适合大规模向量检索、高吞吐、复杂索引和独立向量检索服务。如果数据规模很大、检索吞吐高、团队有专门运维能力，Milvus 是合理选择。

但我们当前阶段的知识库规模和并发压力还没有达到必须引入独立向量数据库的程度。系统已经使用 PostgreSQL 管理业务数据，而 PGVector 可以把 Chunk 原文、元数据、Collection 和 Embedding 放在同一个数据库体系里，事务、备份、权限、迁移和运维都更简单。

所以从 Milvus 转向 PGVector，主要是为了降低系统复杂度和运维成本，同时让向量数据和业务元数据更容易保持一致。代价是当向量规模和检索吞吐继续增长时，PGVector 可能在性能、索引调优和扩展性上遇到瓶颈。到那时可以再按数据量和压测结果迁回专用向量库。

Milvus 的优势

Milvus 更适合：

  • 千万级甚至更大规模向量。
  • 高并发向量检索。
  • 独立向量检索服务。
  • 多种向量索引和检索参数调优。
  • 对检索性能要求高于系统简化的场景。

它的代价是多引入一套基础设施：部署、监控、备份、迁移、权限、数据一致性和故障恢复都要管理。

PGVector 的优势

PGVector 更适合：

  • 中小规模知识库。
  • 已经使用 PostgreSQL 的系统。
  • 需要向量和业务元数据一起事务管理。
  • 希望降低部署和运维复杂度。
  • 过滤条件较多，且希望利用 SQL 能力。

Ragent 的向量表中保存 collection_name、content、metadata 和 embedding。这类结构放在 PostgreSQL 中，和文档表、意图表、权限过滤配合起来更直接。

一致性取舍

使用 Milvus 时，业务元数据通常在 PostgreSQL，向量在 Milvus。文档重建、删除、禁用时，需要同时更新两个系统。如果中间失败，就可能出现数据库认为文档已删除，但向量库仍能召回旧 Chunk。

使用 PGVector 时，向量和元数据在同一个数据库中，一致性处理更简单。尤其在项目早期，少一套分布式一致性问题，往往比追求极限检索性能更重要。

当然，PGVector 也不是没有成本。向量维度、索引类型、表膨胀、VACUUM、查询计划、过滤条件和数据量增长都需要关注。只是这些问题可以在已有 PostgreSQL 运维体系里处理。

什么时候该用 Milvus

如果出现以下情况，就应该重新评估 Milvus 或其他专用向量库：

  • 向量数据达到千万级以上。
  • PGVector 查询延迟无法通过索引和参数优化满足要求。
  • 向量检索吞吐成为核心瓶颈。
  • 需要多租户大规模隔离和独立扩缩容。
  • 向量检索团队已有成熟运维经验。

选型不是一次宣誓，而是随规模和约束变化的决策。

不要这样答

不要说“PGVector 性能一定够”。没有数据量和压测，这句话没有意义。

不要说“Milvus 太重所以不用”。要说明重在哪里：部署、运维、一致性和团队成本。

不要说“PostgreSQL 已经有了，所以顺手”。顺手不是架构理由，除非你能说明它降低了哪些复杂度。

不要忽略迁移成本。向量模型维度变化、索引重建和历史数据重算都需要计划。

小结

Milvus 和 PGVector 的取舍，本质是在性能扩展和系统复杂度之间平衡。当前规模下，PGVector 可以用较低运维成本满足知识库检索，并让元数据和向量保持在同一数据库体系；规模继续增长时，再用压测和指标判断是否切回专用向量库。这样的回答，比简单站队要成熟得多。
