汇编代码怎么写：标签、伪指令、段与符号

September 8, 2026

第一次读 .S 文件时，最容易产生一种很自然、也很麻烦的误会：屏幕上每一行都长得像“命令”，于是便以为 CPU 会从上到下逐行执行它们。可惜事实没有这么体贴。

.section .text
.global _entry
_entry:
        la      sp, stack0
        call    start

这里只有 la、call 最终会对应 CPU 要执行的机器码；.section 是给汇编器的安排，.global 是给链接器的说明，_entry: 则只是给一个地址取名字。汇编源文件同时面对预处理器、汇编器、链接器和 CPU。如果不先分清谁负责哪一行，往后的“逐条解释”只会变成徒劳的背诵。

本文使用 GNU 工具链和 RISC-V 汇编（xv6 使用的风格）讲解这条链路。学完后，你应当能回答四个实际问题：一行汇编是什么类别；一个 C 函数为何能被 call；la sp, stack0 在目标文件中到底留下了什么；以及为什么反汇编结果有时和源代码不一样。

一、先看到全貌：源文件怎样成为 CPU 能执行的内容

CPU 不认识 start、.text 或 # 注释，它只在内存中按 PC（程序计数器）取二进制编码并执行。人写的汇编在抵达 CPU 前，会经历下面这条流水线：

entry.S ──预处理──> 临时汇编文本 ──汇编器──> entry.o
 C 源码 ──C 编译器─────────────────────────> start.o

entry.o + start.o + kernel.ld ──链接器──> kernel（ELF 内核映像）
                                          │
                                  QEMU/启动环境装入内存
                                          │
                                  PC 指向 _entry，CPU 开始取指

每一阶段做的事不同：

阶段 输入与产物 它解决的问题
预处理（仅 .S） 宏、#include 展开后的文本 #define NCPU 8 之类的 C 预处理内容从何而来
汇编 entry.S → 可重定位目标文件 entry.o 把助记符编码成指令；记录段、符号和“此处地址以后再填”的位置
编译 start.c → start.o 把 C 语句变成机器指令与数据，同时导出或引用符号
链接 多个 .o + 链接脚本 → ELF 文件 合并段、分配最终地址、解析同名符号、完成重定位
装载/启动 ELF → 内存 把相应内容放到规定地址，令 PC 从入口地址开始

.s 通常直接送入汇编器，.S（大写）通常先经过 C 预处理器。因此内核中常用 .S：它可以安全地写 #include "param.h" 或使用 #if。但在 RISC-V GNU 汇编中，# 同时也可作为汇编注释起始符；若你把一条 #define 当成会被汇编器理解的语句，当然不会得到想要的结果。它必须先由预处理器处理。

二、汇编文件不是一种句子，而是三类内容的混合

先用最常见的入口片段分类：

.section .text             # 汇编器指令（directive）
.globl _entry              # 汇编器指令：符号绑定属性

_entry:                    # 标签：给当前位置命名
        la      sp, stack0 # 伪指令：汇编器替你展开
        csrr    a1, mhartid# CPU 指令
        call    start      # 伪指令：一次函数调用

spin:                      # 另一个标签
        j       spin       # 伪指令：无条件跳转
类别 典型形式 谁主要处理 自己会不会占据一条机器指令
汇编器指令 以 . 开头，如 .section、.align 汇编器；信息传给链接器 通常不会
标签/符号定义 名字: 汇编器记录在符号表中 不会
ISA 基础指令 add、ld、sd、csrr 等 CPU 最终执行 会
伪指令 li、la、call、ret、j 汇编器将其改写为一条或多条基础指令 会，展开后会

阅读时先问：此行是在安排文件、命名地址，还是让 CPU 做事？ 这个问题比急于记助记符可靠得多。

三、最小语法：注释、记号、标签与局部标签

1. 一条指令如何阅读

GNU RISC-V 汇编的基本形式是：

助记符    目标寄存器, 源操作数1, 源操作数2    # 注释
addi      a0,       a0,       1               # a0 = a0 + 1

逗号分隔操作数；寄存器名 a0、立即数 1、符号名 start 和内存操作数 0(sp) 都是不同的词法记号。空白和对齐绝大多数时候不影响含义，但约定上标签顶格、指令缩进，能让人类快速看出控制流落点。# 之后到行尾是注释，CPU 永远看不到它。

RISC-V 的内存访问常写成 偏移(基址寄存器)：

ld      t0, 16(sp)      # 从地址 sp + 16 读取 8 字节到 t0（RV64）
sd      ra, 8(sp)       # 把 ra 的 8 字节写到地址 sp + 8

括号不是“先访问 sp”，只是地址计算的汇编写法。实际地址是寄存器值加上有符号立即数。

2. 普通标签：给当前位置的地址起一个名字

loop:
        addi    a0, a0, 1
        j       loop

汇编器把 loop 绑定为“当前位置”。假设链接完成后这里位于 0x80000020，j loop 的含义就是让 PC 跳回这一地址。loop: 本身不产生机器码，也不是一条会被 CPU 执行的“标记”；CPU执行到这个地址时，取到的是 addi 的编码。

标签能命名代码，也能命名数据：

.section .rodata
message:
        .asciz "hello\n"  # 写入字符与结尾的 \0

3. 数字局部标签：短跳转不必绞尽脑汁起名字

GNU 汇编允许数字标签重复使用，并用 f（forward，向前）和 b（backward，向后）引用最近的同号标签：

        li      t0, 3
1:
        addi    t0, t0, -1
        bnez    t0, 1b     # 跳到最近的、在前面的 1:
        j       2f         # 跳到后面将出现的 2:
        ebreak             # 此处会被跳过
2:

它适合几十行以内、只在本地有意义的循环。跨函数、跨文件或会被调试器引用的地址仍应取清楚的名字；1b 写错成 1f 并不会因为“人类显然懂你的意思”而被宽恕。

四、段（section）：先分装内容，之后才谈最终地址

段是目标文件内部的分类容器。汇编器把不同内容放进不同 section，链接器随后把同类 section 合并、排序和定位。

常用 section 内容 在最终映像中的一般权限/特点
.text 指令 可读、可执行，通常不应可写
.rodata 字符串、只读表 只读，不执行
.data 已初始化的可写全局数据 初始字节实际保存在文件中
.bss 零初始化/未显式初始化的全局数据 文件中通常只记大小；装载时得到零值空间
.init / 自定义段 启动代码等特殊用途 由项目链接脚本决定如何放置 
.section .data
.align  3                 # 在 RV64 中常使下一对象按 2^3=8 字节边界对齐
counter:
        .dword  0         # 放入一个 8 字节初始值

.section .bss
.align  4
stack0:
        .skip   4096 * 8  # 预留空间；不写入具体初始字节

.dword、.word、.byte、.asciz、.zero、.skip 都是汇编器指令，意思是“向当前 section 写入字节或预留空间”，而不是 CPU 运行时才执行的指令。.align 的精确参数含义受工具链目标影响；对 GNU RISC-V 而言通常表示按 2^n 字节对齐。阅读陌生项目时，以该项目的工具链文档和反汇编验证为准，别把其他架构的习惯硬搬过来。

一个关键但容易被混淆的区分是：section 是链接时的组织单位，segment（程序头中的加载段）是装载时的映射单位。 链接器可能把 .text 和 .rodata 放入同一个可加载区域，也可能分开；操作系统或 QEMU依据 ELF 的 program headers 把可加载部分放到内存。初学阶段先记住“源文件写 section；装载器看 segment”即可。

五、符号与可见性：名字怎样跨越文件

符号表记录“某个名字代表哪个 section 中的哪个偏移（或尚待解析）”，还记录它的绑定属性。最重要的三种情形如下：

.globl add_two            # 声明此定义可被其他目标文件使用
add_two:
        addi a0, a0, 2
        ret

.local private_loop       # 明确仅限本目标文件
private_loop:
        j private_loop

.weak optional_hook       # 弱定义；若另有强定义，强定义优先
optional_hook:
        ret

.global 和 .globl 是同义拼写。没有导出的普通标签通常是本地绑定，只能在当前目标文件内部可靠引用；.local 是把意图写得更明确。.weak 有特定的覆盖规则，内核和库有时用它做可选钩子，但不要把它误当成“更安全的全局变量”。

引用一个本文件没有定义、但预计会由别处提供的名字时，常写：

.extern start              # 可写，也常可省略：未定义引用已足够表达此事
        call    start

start 在 entry.o 中会是 未定义全局符号；链接器必须从 start.o 或某个库中找到一个兼容的全局定义，否则会报告 undefined reference to start。这不是“运行到一半找不到函数”，而是运行前链接已经失败。

在 C 中，文件作用域的非 static 函数/对象通常会导出可链接的名字：

// start.c
char stack0[4096 * NCPU];
void start(void) { /* ... */ }

相反，static void start(void) 是 C 的内部链接，其他 .o 不能以 start 解析它。C++ 还会对函数名进行 name mangling（名称改编），所以 C++ 调用汇编或让汇编调用 C++ 时，通常需要在声明处使用 extern "C"，并额外处理 ABI、异常与对象构造问题。xv6 的这段代码是 C，因此不存在这个障碍。

六、从 .o 到 ELF：链接器具体修补了什么

假设有两个文件：

# entry.S
.section .text
.globl _entry
_entry:
        la      sp, stack0
        call    start
1:      j       1b

// start.c
char stack0[4096 * NCPU];
void start(void) { for (;;) {} }

汇编器独自处理 entry.S 时并不知道 stack0、start 的最终地址。因此 entry.o 不可能已经写死“跳到 0x8000xxxx”。它会产生三样东西：

  1. .text 中 la、call 展开后的机器指令占位编码；
  2. 符号表：_entry 已定义，stack0 与 start 尚未定义；
  3. 重定位记录：说明 .text 的某个偏移应根据 stack0 或 start 的最终位置被修补。

链接器读取所有目标文件和 kernel.ld。后者可能含有这样的骨架：

OUTPUT_ARCH("riscv")
ENTRY(_entry)

SECTIONS {
  . = 0x80000000;
  .text : { *(.text .text.*) }
  .rodata : { *(.rodata .rodata.*) }
  .data : { *(.data .data.*) }
  .bss : { *(.bss .bss.*) *(COMMON) }
}

这不是 C，也不是汇编，而是链接器脚本：. 是当前输出地址；*(.text .text.*) 表示收集所有输入文件匹配的 section；ENTRY(_entry) 把 ELF 的入口信息设为该符号。真实 xv6 脚本还会处理页对齐、内核末尾和其他约束，但逻辑相同。

链接器据此分配地址，例如让 _entry 位于 0x80000000、让 stack0 落在 .bss 的某处，然后按 RISC-V 的地址编码规则补全那几条指令。call start 常需要 PC 相对的 auipc 与 jalr 组合；la sp, stack0 也常是构造 PC 相对地址的多条指令。对应的重定位名可能显示为 R_RISCV_CALL_PLT、R_RISCV_PCREL_HI20、R_RISCV_PCREL_LO12_I 等——名称会随写法、链接阶段和工具链而不同，但中心事实不变：“符号地址是多少”由链接决定，不应由源代码臆测。

七、伪指令：源代码中的一条，不保证机器码中的一条

RISC-V ISA 规定的基础指令集不追求把每个方便写法都编码成独立指令。GNU 汇编器因此提供伪指令：

源码写法 表达的意图 常见的基础指令形式（概念上）
mv rd, rs 复制寄存器 addi rd, rs, 0
nop 什么也不做 addi x0, x0, 0
j label 不保存返回地址地跳转 jal x0, label
ret 返回调用者 jalr x0, 0(ra)
li rd, imm 装入常量 小常量可一条 addi，大常量可能多条
call symbol 保存 ra 并调用符号 常为 auipc + jalr，并附重定位
la rd, symbol 取得符号的地址 常为多条 PC 相对地址构造指令

“常见”不等于永远如此。地址距离、是否启用压缩指令扩展、位置无关代码和链接器 relaxation（松弛优化）都可能改变最终序列。la sp, stack0 的含义是把 stack0 的地址 放进 sp，并不读取 stack0 保存的第一个字节；ld sp, stack0 才会是“从该地址读取数据”这一类意思。

所以应把源代码与反汇编当作两个层次：前者更接近人的意图，后者显示实际编码。二者不同不代表其中一方出错。恰好相反，这是汇编器和链接器正常工作的痕迹。

八、C 与汇编互调：名称之外还有 ABI 这份合同

仅仅“链接器找得到函数名”还不够。调用双方还必须遵守 RISC-V ABI：参数放哪里、返回值放哪里、谁保存寄存器、栈如何对齐。一个最小的例子：

# add_two.S
.section .text
.globl add_two
.type   add_two, @function
add_two:
        addi    a0, a0, 2       # 第一个 long 参数与返回值都使用 a0
        ret
.size   add_two, .-add_two

// main.c
extern long add_two(long value);

long answer(void) {
    return add_two(40);
}

调用 add_two(40) 前，C 编译器把 40 放入 a0；汇编将 a0 改成 42；ret 按 ra 返回，调用者从 a0 读回返回值。.type 与 .size 主要完善 ELF 符号的“这是函数、长度是多少”信息，利于调试、反汇编和工具分析；它们不替 CPU 调用函数。

如果汇编函数还要调用另一个函数，就必须先保护自己的返回地址。例如下面展示典型的 RV64 栈帧骨架：

.globl wrapper
.type wrapper, @function
wrapper:
        addi    sp, sp, -16     # 分配 16 字节，保持调用边界对齐
        sd      ra, 8(sp)       # 本函数还要 call，先保存调用者的返回地址
        call    add_two
        ld      ra, 8(sp)
        addi    sp, sp, 16
        ret
.size wrapper, .-wrapper

这正是 xv6 _entry 必须在 call start 前建立 sp 的直接原因：一旦进入 C 世界，编译器生成的函数就可能保存寄存器、创建局部变量或继续调用别的函数，没有有效栈就无处可放。

九、用工具亲眼验证，而不是凭印象相信它

在安装了 RISC-V ELF 工具链的环境中，以下命令很适合配合一个小例子使用。工具名前缀因环境而异；xv6 常见的是 riscv64-unknown-elf-。

riscv64-unknown-elf-gcc -c -g entry.S -o entry.o
riscv64-unknown-elf-gcc -c -g start.c -o start.o
riscv64-unknown-elf-readelf -S entry.o       # section 表
riscv64-unknown-elf-readelf -s entry.o       # 符号表：定义与未定义符号
riscv64-unknown-elf-readelf -r entry.o       # 重定位：哪些位置等待链接器修补
riscv64-unknown-elf-objdump -dr entry.o      # 反汇编，并紧邻显示重定位

链接以后再看最终映像：

riscv64-unknown-elf-readelf -h kernel/kernel # ELF 头；关注 Entry point address
riscv64-unknown-elf-readelf -l kernel/kernel # program headers：装载段
riscv64-unknown-elf-nm -n kernel/kernel      # 按地址排序的符号
riscv64-unknown-elf-objdump -d -M no-aliases kernel/kernel

特别推荐先看 .o，再看最终 kernel：前者通常能看到未解析符号和重定位，后者则应当已拥有最终地址。若只看最后结果，就很容易误以为汇编器一开始便知道所有地址——这种误解和觉得舞台魔术没有幕后一样方便，但毫无帮助。

十、初学者最常踩的坑

  1. 把标签当成运行语句。 loop: 不执行，也不自动循环；循环来自后面的分支或跳转。
  2. 把 .global 当成调用。 它只影响链接可见性。函数真的开始运行，是控制流到达标签、call 或跳转发生之后。
  3. 以为 .bss 中没有内存。 它只是文件常不保存一堆零字节；链接器仍为它保留地址范围，启动环境必须提供相应的清零/可用存储语义。
  4. 把 la 和 ld 混为一谈。 前者取得地址，后者从内存取数值。少一个字母，含义却不是少一点点。
  5. 把 call 看成单条固定机器指令。 在 RISC-V GNU 工具链中它常是伪指令，会展开并依赖重定位。
  6. 汇编函数随意改 s0～s11 后不恢复。 它们是被调用者保存寄存器；违反 ABI 可能让看似无关的 C 代码随机出错。
  7. 用 C++ 名字直接从汇编调用。 未处理名称改编时，汇编中的 call function 未必能匹配 C++ 生成的符号。
  8. 只看带别名的反汇编。 默认 objdump -d 为可读性会显示 ret、j 等别名；需追踪真实基础编码时加 -M no-aliases。

十一、把知识代回 xv6 entry.S

现在再回看入口文件，就可按阶段读，而不必把它当作一种神秘咒语：

.section .text              # 把下列代码放入 .text section
.global _entry              # 导出入口名字，供 kernel.ld 的 ENTRY(_entry) 引用
_entry:                     # 当前代码地址被命名为 _entry
        la      sp, stack0  # 生成“取得 C 全局对象 stack0 地址”的代码与重定位
        csrr    a1, mhartid # 一条真正的 CSR 读取指令
        call    start       # 生成调用序列；链接后跳入 start.o 定义的 C 函数
spin:                       # 一个本地控制流地址
        j       spin        # 不返回地址地跳回自己；若 start 意外返回则停在这里

在 .o 阶段，stack0 和 start 还是外部引用；在最终内核中，链接脚本决定 _entry 位于哪个入口地址，链接器补全对它们的引用；QEMU 装载内核后，CPU 才会从 _entry 对应的真实机器码开始取指。理解这一层之后，再学习栈、ABI 和特权级，读到的就不再是互不相干的概念。

十二、练习：用“阶段”而不是直觉分析

先不要运行，尝试回答；答案写在每题后面，避免读者把猜测误认为理解。

练习 1：给每一行归类

.section .rodata
name:
        .asciz "xv6"
.globl get_name
get_name:
        la a0, name
        ret

.section、.asciz、.globl 是汇编器指令；name:、get_name: 是标签；la、ret 是伪指令。name 代表数据的地址，get_name 代表函数入口地址。

练习 2：为何能通过链接却运行错误？

若 wrapper 调用了别的函数，却没有保存 ra，链接器仍能找到所有符号，最终却可能无法返回调用者。原因是什么？

因为符号解析只证明地址存在；call 会覆盖 ra，而 ABI 规定嵌套调用前须保护原返回地址。链接器无法从语义上替你补这份调用约定。

练习 3：应看哪一个文件？

你想知道 call start 是否仍在等待链接器修补，应看 entry.o 的什么信息？若想知道最终入口地址，应看什么？

前者使用 readelf -r entry.o 和 objdump -dr entry.o 查看重定位；后者使用 readelf -h kernel/kernel 的入口地址，并以 nm -n 或链接 map 文件核对 _entry 的地址。

小结

  • 汇编源文件经过预处理、汇编、链接和装载，CPU只执行最终映像中位于内存的机器码。
  • 汇编器指令组织 section 和符号，标签命名地址，基础指令才是 ISA 规定的直接操作；伪指令则由汇编器展开。
  • .o 文件既有指令字节，也有符号表和重定位，正因为这些信息存在，跨文件引用才不需要手写地址。
  • 链接器脚本合并 section、安排最终地址并设定入口；ELF 的 section 与装载 segment 是相邻但不同的概念。
  • C 与汇编互调还受 ABI 约束。名字能解析不代表函数调用一定正确，栈、ra 和保存寄存器同样不可忽略。
