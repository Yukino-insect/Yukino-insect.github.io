C 与 C++ 的 volatile：可观察访问、MMIO 与并发边界

August 28, 2026

volatile 常被描述为“告诉编译器变量可能被改变”。这只是动机，不是它完整且可操作的语义。更准确地说：对 volatile 对象的访问是程序的可观察访问，编译器不能像处理普通对象那样，随意删除、把多次访问合并为一次，或长期以寄存器中的旧值代替它。

这使 volatile 很适合内存映射 I/O（MMIO）和少数受严格限制的场景；却也正因为如此，它经常被误拿来处理多线程。必须先划清边界：保留一次设备寄存器访问，和建立线程之间的同步关系，是两件完全不同的事。

volatile -> 让指定对象的读写保持为可观察访问
不是      -> 原子操作、互斥、线程同步、通用内存屏障

一、普通对象为什么会被优化

考虑一个普通变量：

int status = 0;

while (status == 0) {
    /* 循环体没有修改 status */
}

从编译器只看当前线程的角度，循环体内没有改变 status 的代码；它可能将读取提到循环外，甚至推导出循环永不结束。对普通内存对象，这是合理优化：编译器没有义务猜测某块 RAM 会在背后神秘改变。

若地址实际对应硬件寄存器，或值会由当前执行流之外的受支持机制改变，这种优化便违背程序意图：

volatile int device_status;

while (device_status == 0) {
    /* 每次判断都需要重新读取 */
}

volatile 让每次条件判断中的读取成为不可随意省略的可观察访问。注意它约束的是访问，不是这个整数的值：它不会让寄存器按你希望的时间改变，也不会使设备立即响应。

二、典型场景：内存映射 I/O（MMIO）

嵌入式设备常把硬件控制器寄存器映射到一段地址空间。CPU 对该地址的 load/store 不再表示普通 RAM 读写，而是同硬件交互：

#include <stdint.h>

#define UART_STATUS (*(volatile uint32_t *)0x40001000u)

void wait_for_uart(void) {
    while ((UART_STATUS & 0x01u) == 0u) {
        /* 等待接收数据就绪 */
    }
}

这里的每一次 UART_STATUS 读取都可能得到不同值；对某些设备，读取甚至具有“读后清除”等副作用。volatile 的作用是确保编译器将该读取作为一次真实的访问保留。

但这个宏仍然隐含了设备协议：

0x40001000          -> 必须是已映射、当前上下文可访问的寄存器地址
uint32_t            -> 必须是设备要求的 32 位访问宽度
0x01u               -> 必须是手册定义的状态位
读取/写入顺序       -> 必须遵守设备与平台的同步要求

地址能通过编译，不代表地址有效。任意把整数转指针再解引用，在普通用户程序中常会导致访问异常；驱动之所以可以这样做，是因为页表、处理器架构、编译器和设备规范共同允许这次访问。

1. 访问宽度与对齐是协议的一部分

不要将下列指针类型视作可以随意互换：

volatile uint8_t  *byte_reg;  // 8 位访问
volatile uint16_t *half_reg;  // 16 位访问
volatile uint32_t *word_reg;  // 32 位访问

设备要求一次 32 位写入时，四次 8 位写入并不等价；设备可能拒绝、拆分、忽略，或产生不同副作用。地址对齐、端序和寄存器的读/写权限同样必须由芯片或设备规范确认。

2. const volatile：软件不能写，硬件仍可改变

只读硬件状态寄存器可用 const volatile 表达：

const volatile uint32_t *const status_register =
    (const volatile uint32_t *)0x40001000u;

从右向左读：status_register 是一个不可改指向的指针；它指向的 32 位对象不能通过该指针由软件写入，却可能由硬件改变，故读取仍是 volatile 访问。

这种限定只能约束 C/C++ 代码的写法，并不能阻止硬件本身更新寄存器。恰好相反，这正是它存在的原因。

三、volatile int * 与 int *volatile：修饰谁？

声明中的 volatile 紧邻谁，谁就被修饰：

volatile int *pointer_to_volatile;
int *volatile volatile_pointer;

第一行表示：*pointer_to_volatile 是 volatile int。通过该指针读写目标，都是 volatile 访问；指针变量自身未必 volatile。

第二行表示：指针变量 volatile_pointer 自身是 volatile。每次读取它保存的地址值必须保留，但它所指向的 int 不是 volatile。

若两者都需要：

volatile int *volatile pointer;

这不是语法游戏。在 MMIO 中通常想要的是第一种：设备寄存器是易变的，而保存寄存器地址的局部指针变量一般并不需要易变。声明已难以读懂时，使用 typedef、C++ using 或一个清晰的寄存器访问封装，远比让每位读者重新解析星号优先级更有效。

四、volatile 的保证边界：三层顺序问题

驱动与并发代码中，“顺序”至少有三个层面。把它们都交给 volatile，就像要求一把尺同时修理电路、校准时钟和锁门一样不切实际。

层次 关键问题 正确工具 volatile 是否足够
编译器层 一次特殊对象访问会否被删除、合并或缓存 volatile、平台 I/O 访问器 仅对 volatile 访问有效
CPU/内存系统层 RAM 与 MMIO 访问是否按协议顺序对外可见 架构内存屏障、I/O 屏障 否
设备/DMA 层 设备是否看见描述符，CPU 是否看见设备写回的数据 DMA 映射/同步、缓存维护、协议 否

例如，驱动先在普通 RAM 填写 DMA 描述符，再写一个 MMIO 门铃寄存器通知设备：

普通 RAM：描述符、队列索引
                 ↓ 必须先按协议对设备可见
MMIO：通知寄存器（doorbell / QueueNotify）

volatile 可以保证“写门铃”不是一条被优化器删除的无用写入，却不能独自保证设备在收到门铃时已观察到描述符的完整内容。此处需要什么屏障、DMA 同步或缓存操作，取决于处理器、互连、IOMMU、设备和内核提供的 I/O API。不要因为某个平台上恰好正常工作，便把偶然当作跨平台的内存模型。

五、为什么 volatile 不是线程同步工具

下面是经典但错误的 C++ 模式：

volatile bool ready = false;
int data = 0;

// 线程 A
data = 42;
ready = true;

// 线程 B
while (!ready) {
}
std::cout << data;

volatile 不能建立 C++ 线程内存模型的 happens-before 关系，也不保证 data 与 ready 的访问不存在数据竞争。即使某个 CPU、某个优化级别下看起来一直正确，它依旧不是受语言标准保证的并发程序。

C++ 应使用原子类型并选择正确的内存序：

#include <atomic>

std::atomic<bool> ready{false};
int data = 0;

// 线程 A
data = 42;
ready.store(true, std::memory_order_release);

// 线程 B
while (!ready.load(std::memory_order_acquire)) {
}
std::cout << data; // 可以观察到线程 A 在 release 前写入的 data

发布（release）与获取（acquire）配对后，线程 B 在观察到 ready == true 时，可以观察到线程 A 在 store 前的写入。若要维护多个共享变量之间更复杂的不变式，std::mutex、条件变量或更高层任务框架通常比手工设计原子协议更合适。

C11 同样提供 <stdatomic.h> 中的 _Atomic 与原子操作。无论 C 还是 C++，都不应使用 volatile 充当一般线程同步原语。

1. 原子也不等于锁

将 volatile 改为 std::atomic 只是解决了特定对象的原子访问与必要同步；它不自动让多个变量构成一致事务。例如“检查余额、扣款、记录日志”这类复合不变式，往往应由互斥锁或经过完整证明的并发数据结构保护。关键字再短，也不会替你设计临界区。

六、信号处理：有限而严格的例外

在 C 中，异步信号处理器与普通代码之间传递简单标志时，常见类型是 volatile sig_atomic_t：

#include <signal.h>

static volatile sig_atomic_t stop_requested = 0;

void handle_signal(int signal_number) {
    (void)signal_number;
    stop_requested = 1;
}

它适合非常有限的通信模式。信号处理器中可安全调用的函数、可访问的数据，以及多线程进程中的语义均受到严格限制；volatile 不会把任意信号处理代码变成安全代码。

C++ 应优先依照所用平台与标准库对信号的约束设计处理逻辑，不要把这条最小 C 模式扩大成一般异步编程方案。

七、常见错误与诊断清单

1. 用 volatile 轮询另一线程

volatile bool done = false;

这是不正确的跨线程完成标志。使用 std::atomic<bool>、条件变量、互斥锁或任务框架，并依据是否需要等待、取消、传递数据和保护不变式选择工具。

2. 把 volatile 当作万能屏障

它不替代架构 fence、DMA 同步或内核的 readl/writel 等访问器。设备驱动应先确认协议要求“哪份数据必须先对谁可见”，再使用平台规定的屏障与缓存同步操作；无差别加屏障只会降低性能并掩盖设计不清。

3. 对寄存器做未经确认的读—改—写

*reg |= MASK;

这至少是一次读取、一次运算、一次写回。寄存器可能只写、读后清除、写 1 清除，或者被中断与其他 CPU 同时访问；因此必须先查手册，不能因 C 语法看起来紧凑便假定安全。

面对一个 volatile 声明，可以依次检查：

  1. 对象为何会在当前执行流之外改变，或为何每次访问有副作用？
  2. 访问宽度、对齐、端序和读写权限是否与硬件/协议一致？
  3. 它是对象 volatile，还是仅指针变量 volatile？是否应为 const volatile？
  4. 是否存在 RAM、DMA 或其他 CPU 之间的顺序需求？它们由何种屏障/同步原语满足？
  5. 若目标是线程通信，为什么不用原子和锁？若答案只是“以前有人这样写”，那么还没有答案。

八、总结

volatile 的职责很具体：

对 volatile 对象的每次读写，都是编译器不能任意省略、合并或缓存的可观察访问。

它的正确舞台主要是 MMIO 和少数严格受限的场景。它并不提供：

  • 多线程的原子性、互斥或 happens-before；
  • CPU 与设备之间通用的内存排序；
  • DMA 缓冲区的一致性；
  • 对硬件寄存器语义的任何理解。

一旦区分“必须发出这次访问”和“其他参与者必须以何种次序看见数据”，volatile 的位置就会非常清楚：它是底层访问接口的一部分，而不是并发问题的通行答案。把它用在正确边界内，它很精确；越过边界，它只会让错误显得更像底层代码而已。
