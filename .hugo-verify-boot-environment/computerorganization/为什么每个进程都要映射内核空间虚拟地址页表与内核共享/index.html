为什么每个进程都要映射内核空间：虚拟地址、页表与内核共享

August 23, 2026

操作系统会把进程的虚拟地址空间分成两部分：

进程虚拟地址空间

+---------------------------+
|        内核空间            |
|  kernel space             |
+---------------------------+
|        用户空间            |
|  user space               |
+---------------------------+

在很多系统里，每个进程的虚拟地址空间高地址部分都会映射内核。例如 32 位 Linux 经典布局常被简化成：

0xFFFFFFFF  +------------------+
            |    内核空间       |  1GB
0xC0000000  +------------------+
            |    用户空间       |  3GB
0x00000000  +------------------+

于是很自然会产生一个问题：

既然每个进程的内核空间地址都差不多，里面还映射着同一份内核代码，那为什么不让所有进程共享同一个内核映射区域？这样不是能省下每个进程的内核空间吗？

这个问题很好，因为它抓住了一个表面矛盾：每个进程都有一份虚拟地址空间，而内核又只有一个。如果不把“虚拟地址”“物理内存”“页表”“权限”分清楚，就很容易以为系统在每个进程里复制了一份内核。

但真正的答案是：

内核空间的虚拟地址范围看起来在每个进程里都有一份，但内核代码和大部分内核数据的物理内存并没有为每个进程复制。它们通常本来就是共享映射的。

也就是说，操作系统并不是傻到给每个进程复制一份内核代码。那样当然浪费，而且完全没有必要。真实情况要细一点：

  • 每个进程有自己的页表或地址空间描述。
  • 每个进程的用户空间映射通常不同。
  • 每个进程的内核空间虚拟地址通常使用相同布局。
  • 这些相同的内核虚拟地址会映射到同一批物理页。
  • 用户态不能访问这些内核页，因为页表权限位禁止。
  • 进入内核态后，CPU 才能使用这些映射执行内核代码。

所以，这里“每个进程都有内核空间”主要消耗的是虚拟地址范围和少量页表结构，不是每个进程复制一份内核物理内存。

这篇文章就专门回答这个问题。

一、先区分三件事

讨论这个问题前，必须先把三件事分开：

  • 虚拟地址范围
  • 物理内存
  • 页表映射

它们不是一回事。

1. 虚拟地址范围

虚拟地址范围只是地址编号空间。

例如一个 32 位进程理论上可以看到：

0x00000000 ~ 0xFFFFFFFF

这只是“地址号码”的范围，不表示这些地址都真的占用了物理内存。

一个地址如果没有有效页表项，访问它就会触发缺页异常或访问错误。也就是说：

虚拟地址存在，不等于物理内存已经分配。

这点很重要。否则你会把“地址空间被划出去”误解成“内存被用掉了”。计算机不会因为这两个词都带“空间”就把它们当成同一件事。它没有这种含糊的温柔。

2. 物理内存

物理内存是真正的 RAM。

内核代码、内核数据结构、进程用户页、文件缓存、页表本身，最终都要落到物理内存里。

如果每个进程真的复制一份内核代码，那才会大量浪费物理内存。

但实际系统通常不会这么做。内核代码页一般只有一份物理页，不同进程的内核虚拟地址映射到同一份物理页。

3. 页表映射

页表描述虚拟地址到物理地址的映射关系。

简化看，一个页表项大概表达：

虚拟页 -> 物理页框 + 权限

例如：

进程 A:
  用户虚拟地址 0x00400000 -> 物理页 P1
  内核虚拟地址 0xFFFFFFFF81000000 -> 物理页 K1

进程 B:
  用户虚拟地址 0x00400000 -> 物理页 P2
  内核虚拟地址 0xFFFFFFFF81000000 -> 物理页 K1

可以看到：

  • 用户空间同一个虚拟地址，在不同进程里可能映射到不同物理页。
  • 内核空间同一个虚拟地址，在不同进程里通常映射到同一个内核物理页。

所以所谓“每个进程都有内核空间”，不是说每个进程都有一份内核副本，而是说：

每个进程当前使用的地址空间里，都能在内核态访问那套统一的内核映射。

二、其实已经共享了

用户提出的设想是：

为什么不让所有进程共享同一个内核映射区域？

从物理内存和映射内容的角度看，答案是：

它们已经在共享。

假设内核代码某一页物理地址是：

物理页 K_TEXT_1

不同进程的页表中，可以都有这样的映射：

进程 A 页表:
  0xFFFFFFFF81000000 -> K_TEXT_1   supervisor, read, execute

进程 B 页表:
  0xFFFFFFFF81000000 -> K_TEXT_1   supervisor, read, execute

进程 C 页表:
  0xFFFFFFFF81000000 -> K_TEXT_1   supervisor, read, execute

这里的 0xFFFFFFFF81000000 是虚拟地址，K_TEXT_1 是物理页。

每个进程的页表里都有这条映射，但它们指向同一个物理页。

也就是说：

多个进程的内核虚拟地址
        |
        v
同一份内核物理内存

这和动态库共享代码段有点像：

进程 A 的 libc 代码虚拟页 -> libc 物理页
进程 B 的 libc 代码虚拟页 -> libc 物理页
进程 C 的 libc 代码虚拟页 -> libc 物理页

只是内核映射权限更特殊，用户态不能访问。

所以，不需要再额外发明一个“共享内核区域”来节省内核代码物理内存。真正的系统设计早就这么做了。它没有每次创建进程都复制一份内核正文，否则机器还没跑几个进程，内存就该开始发表抗议了。

三、那为什么还说每个进程都有内核空间

因为每个进程有自己的虚拟地址空间视图。

这个视图里既包含用户空间，也包含内核空间：

进程 A 虚拟地址空间:
  用户空间: A 自己的代码、堆、栈、mmap
  内核空间: 统一内核映射

进程 B 虚拟地址空间:
  用户空间: B 自己的代码、堆、栈、mmap
  内核空间: 统一内核映射

用户空间不同，内核空间大体相同。

这样设计有一个关键好处：

无论当前正在运行哪个进程，只要 CPU 进入内核态，都能立刻使用同一套内核虚拟地址访问内核代码和内核数据。

例如用户程序执行系统调用：

read(fd, buf, len);

CPU 从用户态进入内核态后，内核要执行系统调用处理代码。如果当前进程的地址空间里没有映射内核代码，那么 CPU 就无法直接跳到内核代码地址执行。

当然，你可以说：那进入内核时先切换到一个单独的内核地址空间不就好了？

理论上可以，某些设计也会在不同程度上这么做。但这会引出新的成本和复杂性：

  • 每次系统调用、中断、异常都可能需要切换页表。
  • 切换页表会影响 TLB 和地址翻译缓存。
  • 内核处理系统调用时还需要访问当前进程的用户地址。
  • 中断可能在任何进程运行时发生，入口路径必须极其可靠。
  • 内核中的指针希望在任何进程上下文中都有一致含义。

所以，把内核映射放进每个进程的地址空间，是一种非常实用的设计：进入内核时不需要换一整套地址地图，直接提高权限后就能执行内核代码。

这不是偷懒，而是工程上很冷静的选择。

四、用户态为什么不能访问内核空间

既然内核空间映射在每个进程地址空间里，那用户程序能不能直接读写它？

不能。

关键在页表权限位和 CPU 特权级。

页表项不只记录物理地址，还记录访问权限，例如：

  • 是否 present。
  • 是否可读。
  • 是否可写。
  • 是否可执行。
  • 是否允许用户态访问。
  • 是否只允许内核态访问。

在 x86 这类架构中，页表项里有类似 U/S 的权限位：

  • user page：用户态和内核态都可以在权限允许下访问。
  • supervisor page：只有内核态可以访问。

内核空间页表项通常被标记为 supervisor。于是：

用户态访问内核地址 -> CPU 检查权限 -> 触发异常
内核态访问内核地址 -> CPU 检查权限 -> 允许访问

所以每个进程地址空间里有内核映射，并不意味着用户程序可以碰它。

这就像楼里有一扇门，你能看到门牌号，但门禁卡没有权限。硬要刷，只会被系统冷静地拒绝。嗯，至少计算机的拒绝比人类诚实。

五、为什么不单独做一个全局内核地址空间

我们把用户的想法稍微形式化一点：

进程 A 地址空间: 只放 A 的用户空间
进程 B 地址空间: 只放 B 的用户空间
全局内核地址空间: 单独放内核代码和数据

然后进入内核时切到全局内核地址空间。

这个想法并非完全不可能，但它要面对几个问题。

1. CPU 当前只能按当前页表翻译地址

CPU 执行指令时，虚拟地址到物理地址的转换依赖当前激活的页表。

在 x86 上，当前页表根地址通常由 CR3 指向。其他架构也有类似机制。

如果当前运行的是进程 A 的用户态页表，而这个页表里没有内核代码映射，那么当系统调用入口要跳到内核代码时，必须先完成某种安全可靠的切换。

问题是：切换页表本身也需要代码执行，而执行代码又需要地址映射。

所以系统至少要保留一小段入口映射，用来完成从用户地址空间到内核地址空间的切换。这条入口路径必须处理系统调用、中断、异常、缺页等各种场景，不能指望它“差不多能跑”。内核入口路径如果差不多，那系统稳定性也就差不多了。这个评价并不值得骄傲。

2. 系统调用经常要访问用户空间

内核处理系统调用时，经常需要读写用户传来的地址。

例如：

read(fd, buf, len);

其中 buf 是用户态地址。

内核读取文件后，要把数据拷贝到 buf 指向的用户空间：

内核缓冲区 -> 用户缓冲区

如果进入内核后完全切到一个独立的全局内核地址空间，而这个地址空间没有当前进程的用户映射，那么内核就不能直接通过 buf 这个用户虚拟地址找到目标物理页。

它必须额外做一些事情：

  • 临时切回当前进程页表。
  • 或者把用户页临时映射进内核地址空间。
  • 或者通过更复杂的机制手动查页表并访问物理页。

这些都不是不可能，但会增加复杂性和成本。

而如果当前地址空间同时包含：

  • 当前进程的用户映射。
  • 统一的内核映射。

那么内核在处理系统调用时就可以方便地访问当前进程的用户页。当然，访问前仍然要做权限检查和安全拷贝，例如 Linux 里的 copy_from_user、copy_to_user 这类机制。

3. 中断和异常可能发生在任意时刻

系统调用是用户程序主动进入内核。

但中断和异常未必这么礼貌。

例如：

  • 时钟中断触发调度。
  • 网卡中断通知数据到达。
  • 用户程序访问未映射页面触发缺页异常。
  • 用户程序执行非法指令触发异常。

这些事件可能发生在任何进程运行期间。

如果每个进程的当前地址空间里都有内核映射，那么 CPU 进入内核后可以直接跳到内核异常处理代码。

如果内核完全在另一个地址空间里，入口处理就要更加小心：先进入一段可访问的 trampoline，再切页表，再进入真正内核。能做，但更复杂。

4. 内核指针需要稳定含义

内核里有大量指针：

  • 指向进程描述符。
  • 指向文件对象。
  • 指向页缓存。
  • 指向 socket。
  • 指向设备结构。
  • 指向调度队列。

如果内核在不同进程上下文中使用相同虚拟地址布局，那么一个内核指针在任何进程运行时都有相同含义。

例如：

0xFFFFFFFF81234567

在进程 A 陷入内核时，它表示某个内核函数。

在进程 B 陷入内核时，它仍然表示同一个内核函数。

这让内核代码非常自然：

同一个内核虚拟地址 -> 同一个内核对象

如果不同进程的内核映射布局不一致，或者内核要频繁在多个地址空间之间切换，指针含义就会变复杂。系统可以设计得很复杂，但复杂性从来不是免费的。它只是把代价藏到调试、性能和安全边界里。

六、所谓省下内核空间，到底省的是什么

用户问题里说：

这样可以省下进程的内核空间。

这里要问：省下的是哪种空间？

1. 省物理内存吗

大部分情况下，省不了多少，因为内核代码和核心内核数据本来就不是每个进程复制一份。

它们共享同一批物理页。

每个进程可能有一些自己的内核相关资源，例如：

  • 内核栈。
  • 进程描述符。
  • 打开的文件表引用。
  • 内存描述符。
  • 信号处理状态。
  • 调度实体。

但这些不是“内核代码映射区域”的重复副本，而是每个进程本来就需要的内核数据结构。

即使你把内核地址空间单独拿出去，这些 per-process 内核对象也不能消失。进程总得有自己的身份资料。否则调度器看着一堆进程却分不清谁是谁，那就不是节省，是灾难。

2. 省页表内存吗

可能能省一点，但通常没有想象中那么大。

现代分页是多级页表。内核空间映射可以在高层页表项上共享。

简化地说，可以让不同进程页表的内核部分指向同一套下级页表：

进程 A 顶级页表
  用户部分 -> A 自己的下级页表
  内核部分 -> 共享内核下级页表

进程 B 顶级页表
  用户部分 -> B 自己的下级页表
  内核部分 -> 共享内核下级页表

这样每个进程并不需要完整复制所有内核页表项。

有些系统还会利用 TLB global bit 等机制，让内核全局映射在进程切换时尽量保留在 TLB 中，减少地址翻译缓存失效。

所以从页表开销看，系统本来就有办法共享或复用内核映射结构。它不是把同一张内核地图手抄几千份再塞进每个进程抽屉里。那样太勤奋，也太愚蠢。

3. 省虚拟地址范围吗

在 32 位系统上，这确实是个问题。

例如经典 3G/1G 分割：

用户空间 3GB
内核空间 1GB

这意味着单个用户进程最多只能直接使用低 3GB 左右的用户虚拟地址，而不是完整 4GB。

所以从“用户可用虚拟地址范围”角度看，内核映射确实占掉了一部分地址编号。

但这是一个权衡：

  • 保留内核映射：系统调用和中断进入内核更快、更简单。
  • 不保留内核映射：用户地址空间可能更大，但进入内核更复杂，访问用户内存也更麻烦。

在 32 位时代，这个权衡很明显，因此还会有 2G/2G、3G/1G、highmem 等不同设计。

到了 64 位时代，虚拟地址空间巨大，给内核划出高半部分通常不再是主要矛盾。你当然可以嫌它占地址范围，但那就像嫌图书馆目录编号太多，问题不在它占地方，而在你是否真的会用完。

七、为什么内核映射通常放在相同虚拟地址

不同进程的内核空间通常使用相同的虚拟地址布局，这也有原因。

1. 内核代码可以使用固定虚拟地址

如果内核在每个进程中都映射到同一段虚拟地址，那么内核代码、全局变量、内核对象的地址都是一致的。

这让内核可以像普通程序一样使用指针：

task_struct *current;

而不需要每次都问：

在当前进程的内核映射布局里，这个内核对象今天住在哪里？

内核已经够复杂了，不需要再把地址含义也变成谜语。

2. 进程切换更高效

进程切换时，用户空间映射要切换，因为进程 A 和进程 B 的用户内存不同。

但内核映射是相同的。

这意味着：

  • 内核代码地址不变。
  • 内核数据地址不变。
  • 某些 TLB 项可以作为 global mapping 保留。
  • 切换过程中不需要重新解释内核自身地址。

尤其是在内核执行调度代码时，它正在从一个进程切到另一个进程。如果内核地址在切换前后不一致，那调度器自己都要小心翼翼地避免踩空。一个负责切换世界的人，最好不要在切换途中连自己脚下的地板都变了。

3. 内核可以方便访问当前进程上下文

内核执行时虽然运行在内核态，但它经常处在某个进程上下文中。

例如进程 A 调用 read，进入内核后：

当前执行的是内核代码
但服务对象是进程 A

这时内核既要访问自己的数据结构，也要访问进程 A 的用户地址。

同一个地址空间里同时包含“当前进程用户映射”和“统一内核映射”，可以让这件事更直接。

八、内核空间里也不全是完全相同

前面说每个进程的内核空间“大体相同”，这个说法要留一点余地。

因为内核空间里可能包含一些和当前进程、当前 CPU 或安全策略有关的内容。

常见例子包括：

  • 每个线程有自己的内核栈。
  • 每个 CPU 有自己的 per-CPU 数据区。
  • 某些临时映射区域可能会变化。
  • 某些系统会对内核页表做特殊隔离。
  • 开启 KASLR 后，内核基址可能在每次启动时随机化。

但这些并不推翻主结论：

内核代码和大部分全局内核映射不是每个进程复制物理内存，而是通过页表映射共享。

同一份内核，可以在不同进程上下文中运行。不同的是当前进程是谁、当前线程的内核栈是谁、当前 CPU 是谁。

九、KPTI：一个有趣的反例

前面说很多系统会把内核映射放进每个进程地址空间。那是不是永远都这样？

不是。

现代系统为了安全，可能会减少用户态页表中可见的内核映射。典型例子是 KPTI，也就是 Kernel Page Table Isolation。

KPTI 的背景和 Meltdown 这类 CPU 漏洞有关。简单说，即使用户态按权限不能真正读取内核地址，某些推测执行漏洞仍可能通过侧信道泄露内核数据。

于是 KPTI 的思路是：

  • 用户态运行时，页表中尽量不映射完整内核。
  • 只保留进入内核所需的极小 trampoline 映射。
  • 真正进入内核后，再切换到包含完整内核映射的页表。

这看起来接近用户提出的“不要在每个进程里放完整内核映射”。

但注意，它不是为了节省虚拟地址空间，而是为了安全隔离。

而且它确实带来了额外成本：

  • 系统调用和中断路径更复杂。
  • 需要更多页表切换。
  • TLB 行为更敏感。
  • 需要 PCID 等硬件特性帮助降低开销。

这反而说明，传统的“每个进程地址空间都带内核映射”不是因为没人想到别的办法，而是因为它在性能和实现复杂度上很有吸引力。

当安全威胁改变时，系统才愿意付出额外成本换隔离。工程就是这样，没有永远正确的姿势，只有在约束下比较不坏的选择。听起来不浪漫，但大多数可靠系统都是这么活下来的。

十、一个系统调用例子

用 write 举例：

write(1, "hello\n", 6);

用户态看到的是：

用户缓冲区地址 -> "hello\n"

进入内核后，内核要做：

  1. 检查系统调用号。
  2. 检查文件描述符 1。
  3. 检查用户缓冲区地址是否合法。
  4. 从用户空间读取 "hello\n"。
  5. 进入 VFS 或终端/管道/socket 等写路径。
  6. 返回用户态。

为了完成这些事，内核需要同时接触两类地址：

内核代码和内核数据
当前进程的用户缓冲区

如果当前页表同时包含用户映射和内核映射：

当前进程页表
  用户部分 -> 当前进程的用户内存
  内核部分 -> 共享内核映射

内核处理起来最直接。

如果切到完全独立的内核页表，内核就必须额外解决：

我现在怎么访问刚才那个用户指针？

这就是为什么“共享一个单独内核区域”听起来省，实际会把很多成本转移到系统调用和异常处理路径上。

十一、进程的内核空间到底占了什么

可以把一个进程相关的内存分成几类：

进程用户空间:
  代码段
  数据段
  堆
  用户栈
  mmap 区域

共享内核映射:
  内核代码
  内核只读数据
  内核全局数据
  物理内存 direct map
  设备映射区域

进程自己的内核资源:
  内核栈
  task_struct / thread 信息
  文件描述符表相关结构
  虚拟内存区域描述
  信号、调度、凭证等状态

其中：

  • 共享内核映射主要是系统全局的。
  • 进程自己的内核资源是每个进程必须有的。
  • 用户空间才是各进程差异最大的部分。

所以想“省下进程的内核空间”，要小心不要省错对象。

如果你说的是内核代码物理内存：已经共享了。

如果你说的是虚拟地址范围：32 位上确实是代价，64 位上通常不缺。

如果你说的是页表项：可以共享一部分，且相对可控。

如果你说的是每个进程的内核栈和进程控制块：那不能共享，因为每个进程的执行状态本来就不同。

十二、用一张图总结

错误直觉：

进程 A -> 一份内核
进程 B -> 一份内核
进程 C -> 一份内核

更接近真实情况：

进程 A 页表                  物理内存
  用户 VA -> A 用户页  ---->  A 用户物理页
  内核 VA -> K 页      --+
                         |
进程 B 页表              |
  用户 VA -> B 用户页  -> B 用户物理页
  内核 VA -> K 页      --+
                         |
进程 C 页表              v
  用户 VA -> C 用户页    同一份内核物理页
  内核 VA -> K 页      --+

所以，每个进程“看起来”都有同样的内核虚拟地址区域，但它们指向的是同一份内核物理内容。

再换一个角度：

虚拟地址空间:
  每个进程一份视图

内核物理代码和数据:
  系统一份为主，多进程共享映射

权限:
  用户态不能访问内核页
  内核态可以访问内核页

这才是关键。

总结

操作系统把每个进程的虚拟地址空间分成用户空间和内核空间，并不意味着每个进程都复制了一份内核。

真实情况通常是：

  • 每个进程有自己的用户空间映射。
  • 每个进程的内核空间虚拟地址布局大体相同。
  • 这些内核虚拟地址映射到同一份内核物理内存。
  • 用户态不能访问内核映射，因为页表权限和 CPU 特权级会阻止。
  • 这样设计能让系统调用、中断和异常快速进入内核。
  • 内核可以在任何进程上下文中使用稳定的内核虚拟地址。
  • 32 位系统上，内核空间确实会占用用户可用虚拟地址范围；64 位系统上这个问题通常不再突出。
  • KPTI 这类机制会为了安全减少用户态页表中的内核映射，但代价是更复杂的页表切换和入口路径。

所以，那个问题可以一句话回答：

所有进程并不是各自拥有一份独立的内核物理副本；它们通常已经共享同一份内核映射内容。把内核映射放进每个进程地址空间，是为了让 CPU 在当前进程上下文中进入内核时，可以快速、稳定地执行内核代码并访问当前进程的用户内存。

如果只看虚拟地址图，确实像每个进程都被切走了一块内核空间。可是虚拟地址不是物理内存，映射存在也不等于用户能访问。把这三者分清楚，这个问题就不再神秘。

它只是一个典型的操作系统权衡：用一部分虚拟地址范围和少量页表结构，换来系统调用、中断处理、内核指针稳定性和整体性能。至于说它是不是完美设计，当然不是。只是计算机系统里能长期存在的设计，往往不是因为完美，而是因为它在麻烦之间选了一个相对可以忍受的麻烦。
