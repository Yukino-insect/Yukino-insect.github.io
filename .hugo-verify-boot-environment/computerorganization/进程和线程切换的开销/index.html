进程和线程切换的开销

February 19, 2026

进程切换和线程切换，本质上都是 CPU 从一个执行流切到另一个执行流。它们的共同成本是保存和恢复运行现场；真正拉开差距的，通常是地址空间、缓存局部性和调度副作用。

先给结论：

同一进程内的线程切换通常比进程切换轻，因为线程共享地址空间；进程切换往往要切换页表，影响 TLB 和 Cache，后续一段时间的内存访问也会变慢。

这里的“通常”很重要。实际开销取决于 CPU 架构、操作系统、调度策略、是否跨核迁移、工作集大小以及程序本身的内存访问模式。

一、什么是上下文切换？

一个执行流正在 CPU 上运行时，CPU 内部保存着它当前的执行状态，例如：

  • 程序计数器，也就是下一条要执行的指令位置。
  • 栈指针。
  • 通用寄存器。
  • 标志寄存器。
  • 浮点、SIMD、向量寄存器等扩展状态。
  • 内核调度器维护的运行状态。

当操作系统决定暂停当前执行流，改为运行另一个执行流时，就需要：

  1. 保存当前执行流的 CPU 上下文。
  2. 进入内核调度逻辑。
  3. 选择下一个可运行对象。
  4. 恢复下一个执行流的上下文。
  5. 回到用户态继续执行。

这就是上下文切换。

在现代操作系统里，调度的基本单位通常是线程或内核任务。我们平时说“进程切换”，多数情况下指的是从一个进程中的线程切到另一个进程中的线程。

二、直接开销：保存和恢复运行现场

上下文切换最直观的成本，是寄存器和运行状态的保存、恢复。

需要保存的内容可能包括：

  • 通用寄存器。
  • 程序计数器 PC。
  • 栈指针 SP。
  • 状态寄存器。
  • FPU / SIMD / 向量寄存器。
  • 线程本地存储相关状态。
  • 内核栈和调度信息。

这部分成本相对固定，但并不总是完全一样。比如某些系统会采用惰性保存策略，只有在确实使用了浮点或向量寄存器时才保存相关状态。于是，两个看起来一样的切换，实际开销也可能不同。

不过，仅仅保存几个寄存器，通常不是最可怕的部分。真正贵的地方，往往在后面。

三、调度器和内核态成本

上下文切换需要进入内核，由调度器决定下一个运行谁。这里会产生额外成本：

  • 维护运行队列。
  • 计算优先级和时间片。
  • 处理阻塞、唤醒、抢占等状态变化。
  • 在多核系统中处理锁、负载均衡和 CPU 亲和性。
  • 更新统计信息和计时器。

如果切换来自 I/O 阻塞、锁竞争、条件变量、futex 等同步原语，还会叠加睡眠队列和唤醒队列的管理成本。

在高并发程序里，频繁阻塞和唤醒会让系统看起来“很忙”，但真正用于业务计算的 CPU 时间反而下降。也就是说，CPU 在努力工作，只是没把力气用在你想要的地方。

四、进程切换更重：地址空间和 TLB

进程和线程最大的区别之一，是地址空间。

  • 同一进程内的多个线程共享同一个虚拟地址空间。
  • 不同进程通常拥有不同的虚拟地址空间。

CPU 访问内存时，需要把虚拟地址翻译成物理地址。这个翻译结果会被缓存在 TLB（Translation Lookaside Buffer） 中。

当从一个进程切到另一个进程时，页表基址通常会变化。后果是：

  • 旧进程的地址翻译缓存可能不能直接使用。
  • TLB 命中率下降。
  • 后续内存访问更容易触发页表遍历。
  • 访问延迟上升。

现代 CPU 和操作系统会用一些机制降低这个成本，例如地址空间标识符、PCID、部分 TLB 保留等。但结论并没有消失：跨地址空间切换通常比同地址空间内的线程切换更容易破坏地址翻译缓存。

所以，进程切换的开销不只是“切换那一下”。切换完成后，程序还可能经历一段 TLB 重新变热的过程。

五、Cache 污染：最隐蔽也很常见的成本

CPU Cache 保存着最近使用过的指令和数据。一个程序刚运行一段时间后，它需要的数据可能已经在 L1、L2、L3 Cache 中，这时访问速度很快。

切换到另一个进程或线程后，新的执行流可能使用完全不同的数据和代码路径，于是会发生：

  • 指令缓存命中率下降。
  • 数据缓存命中率下降。
  • 前一个执行流的热点数据被逐步挤出。
  • 再切回来时，又要重新把数据加载进 Cache。

这就是所谓的缓存污染。

它很讨厌，因为它不一定体现在“上下文切换耗时”这个单点指标里，而是体现为后续一段时间执行变慢。短任务、高频切换、工作集较大的服务，对这个问题尤其敏感。

六、分支预测和流水线扰动

现代 CPU 会提前预测分支走向，并让流水线尽量持续工作。如果切换后的执行流代码路径完全不同，之前积累的分支历史就可能不再适用。

这会导致：

  • 分支预测命中率下降。
  • 流水线更频繁清空或停顿。
  • 短时间内 IPC 下降。

这部分通常不像 TLB 和 Cache 那样容易被直观看到，但在极端低延迟场景或高频切换场景下，它也是成本的一部分。

七、跨 CPU 核迁移与 NUMA 成本

如果一个线程这次在 CPU 0 上运行，下次被调度到 CPU 7 上运行，成本可能进一步增加。

原因是：

  • 原来核心上的 L1 / L2 Cache 无法直接复用。
  • 共享 LLC 的命中情况也可能变差。
  • 跨 NUMA 节点时，访问远端内存延迟更高。
  • 线程迁移还可能带来更多调度器负担。

这就是为什么一些高性能服务会强调 CPU affinity、NUMA awareness、线程绑定和内存绑定。不是因为这些词听起来高级，而是因为缓存局部性真的会影响延迟。

八、线程切换一定便宜吗？

也不一定。

同一进程内线程切换通常省掉了完整地址空间切换，所以一般比进程切换轻。但线程切换仍然需要保存和恢复寄存器、进入调度器、更新状态，也仍然可能破坏 Cache。

下面几种情况里，线程切换也可能很贵：

  • 线程数量远大于 CPU 核数，频繁抢占。
  • 大量线程争同一把锁，反复睡眠和唤醒。
  • 工作集很大，线程之间互相污染 Cache。
  • 线程被迁移到不同 CPU 核或 NUMA 节点。
  • 线程使用大量 SIMD / 向量寄存器状态。

所以“线程比进程便宜”是一个方向正确的工程判断，不是可以无脑套用的定律。

九、如何降低切换开销？

常见思路是减少不必要的切换，并保持局部性：

  1. 避免创建过多线程

    线程数接近 CPU 核数或按业务阻塞比例合理放大，通常比随意开几百上千个线程更可控。

  2. 减少阻塞和锁竞争

    高频 mutex、条件变量、futex 唤醒会制造大量调度成本。能缩小临界区就缩小，能减少共享状态就减少。

  3. 使用线程池

    复用线程，避免频繁创建和销毁，也更容易控制并发度。

  4. 保持 CPU 亲和性

    对低延迟或高吞吐服务，可以考虑绑核、减少跨核迁移，让 Cache 更稳定。

  5. 批处理和合并 I/O

    批量处理请求、使用 pipeline、减少系统调用次数，都能减少陷入内核和调度的频率。

  6. 关注工作集大小

    数据结构太大、访问太随机，即使切换次数不多，也会让 Cache 和 TLB 很难受。

十、一句话总结

进程和线程切换都要保存、恢复 CPU 上下文，并经过内核调度。线程切换通常更轻，因为同一进程内线程共享地址空间；进程切换更容易引起页表切换、TLB 失效和 Cache 污染。真正拖慢系统的，往往不是保存寄存器那一下，而是切换后缓存局部性被破坏带来的持续影响。
