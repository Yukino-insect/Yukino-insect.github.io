响应超时

February 16, 2026

这篇笔记来自一个导出文件的场景：后端直接把 Excel 内容写入 response，结果出现超时或断连异常。后来改成先生成临时文件，再把文件拷贝到响应流中，问题缓解了。

这个现象很常见，但不能简单理解成“TCP 写入不连续就一定会超时”。更准确的说法是：

导出接口如果一边计算一边写响应，可能长时间没有稳定输出数据，触发浏览器、Nginx、网关、Servlet 容器或 HTTP 客户端的超时；先生成临时文件再输出，可以把耗时的生成阶段和连续的下载阶段分开，从而降低响应中断的概率。

一、导出接口为什么容易超时

导出 Excel、PDF、CSV 这类接口通常有几个特点：

  1. 查询数据慢。
  2. 数据转换慢。
  3. 文件生成慢。
  4. 响应体很大。
  5. 客户端等待时间长。
  6. 中间可能经过 Nginx、网关、负载均衡。

如果后端直接写 response.getOutputStream()，但中间隔很久才写出下一段数据，就可能触发某些超时限制。

这些超时可能来自不同层：

层级 常见超时
浏览器 下载等待、连接中断
Nginx / 网关 proxy_read_timeout、idle timeout
Servlet 容器 async timeout、连接写超时
HTTP 客户端 read timeout、response timeout
操作系统 TCP 连接超时、重传、发送缓冲区阻塞

所以排查时不要一上来就归因到 TCP。网络问题最讨厌的地方就是它长得都很像，但病因并不一样。

二、先生成临时文件为什么可能有效

原始方式：

查询数据
  -> 生成一部分 Excel
  -> 写一部分 response
  -> 继续查询和生成
  -> 再写 response

如果中间某一步很慢，响应流可能长时间没有新数据输出。

改成临时文件后：

查询数据
  -> 完整生成临时文件
  -> 设置响应头
  -> 连续拷贝文件到 response

这样有几个好处：

  1. 生成阶段没有急着占用客户端响应连接。
  2. 下载阶段可以更连续地输出字节。
  3. 可以提前知道文件大小，设置 Content-Length。
  4. 如果生成失败，可以返回正常 JSON 错误，而不是返回半个损坏文件。
  5. 便于重试、清理和记录导出结果。

但这不是万能解法。文件非常大时，临时文件会占用磁盘；并发导出很多时，也要考虑磁盘空间、清理策略和限流。

三、HTTP 请求常见的几类超时

1. 连接超时

连接超时发生在建立连接阶段。

例如客户端要连接服务端：

client -> server:443

如果网络不可达、端口没开、防火墙阻断，TCP 三次握手一直无法完成，就会触发连接超时。

Java 示例：

Socket socket = new Socket();
socket.connect(new InetSocketAddress("127.0.0.1", 8080), 3000);

这里的 3000 就是连接超时时间，单位是毫秒。

2. 读超时

读超时发生在连接已经建立之后，客户端等待服务端返回数据时。

Java 原生 Socket 示例：

socket.setSoTimeout(5000);

SO_TIMEOUT 对 read() 生效。如果 5 秒内读不到数据，会抛出 SocketTimeoutException。

读超时不是连接失败，而是连接建立后太久没有读到期望的数据。

3. 写超时

写超时和读超时不太一样。

应用调用 write() 时，通常只是把数据写入操作系统内核的 TCP 发送缓冲区。只要缓冲区有空间，write() 可能很快返回，并不代表对方已经收到数据。

当下面情况发生时，写操作才可能阻塞：

  1. 对端读取很慢。
  2. 网络拥塞。
  3. 对端接收窗口变小。
  4. 本机发送缓冲区被写满。
  5. 连接半开或对端异常。

在 C 语言中可以通过 SO_SNDTIMEO 设置发送超时。但 java.net.Socket 没有直接暴露写超时 API。很多 Java HTTP 客户端或服务器框架会在更上层提供写超时、响应超时或 idle timeout。

4. 整体请求超时

有些客户端提供的是整个请求的最大耗时。例如 JDK 11 HttpRequest#timeout()：

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://example.com"))
        .timeout(Duration.ofSeconds(5))
        .build();

它关注的是这次请求总共不能超过多久，而不是单纯的 TCP 读写。

5. 连接池获取超时

在微服务里，HTTP 客户端通常使用连接池。

如果连接池满了，新请求需要等待可用连接。等待太久就会触发连接池获取超时。

这类问题经常被误认为“下游接口慢”，但实际可能是本服务连接池被打满了。

四、Socket 是什么

Socket 可以从两个角度理解。

1. 编程接口

Socket 是应用程序使用 TCP 或 UDP 的编程接口。

Java 程序并不会自己实现 TCP，而是通过 JVM 调用操作系统提供的 socket 能力：

Java Socket API
  -> JDK 内部实现
  -> 操作系统 socket 系统调用
  -> TCP/IP 协议栈
  -> 网卡

2. 网络连接端点

一个 TCP 连接由四元组唯一标识：

源 IP + 源端口 + 目标 IP + 目标端口

例如：

192.168.1.10:51523 -> 10.0.0.2:8080

这里不能简单说“一个端口就是一个 Socket”。更准确地说，端口只是 socket 地址的一部分。服务端可以监听一个端口，同时和很多客户端建立不同的 TCP 连接。

五、Java 中的几种 IO 模型

1. BIO：阻塞 IO

常见类：

java.net.Socket
java.net.ServerSocket

示例：

ServerSocket server = new ServerSocket(8080);
Socket socket = server.accept();

InputStream in = socket.getInputStream();
OutputStream out = socket.getOutputStream();

特点：

  1. accept() 阻塞。
  2. read() 阻塞。
  3. 传统模型是一连接一线程。

优点是简单，缺点是高并发下线程数量、上下文切换和内存成本较高。

2. NIO：非阻塞 IO + 多路复用

常见类：

java.nio.channels.SocketChannel
java.nio.channels.ServerSocketChannel
java.nio.channels.Selector

核心思想是用一个线程监听多个连接上的事件：

Selector 监听多个 Channel
  -> 某个连接可读或可写
  -> 程序处理对应事件

示例：

Selector selector = Selector.open();
ServerSocketChannel server = ServerSocketChannel.open();
server.configureBlocking(false);
server.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();
    for (SelectionKey key : selector.selectedKeys()) {
        // 处理 accept / read / write
    }
}

NIO 常用于高并发服务器、网关、RPC 框架等。

3. AIO：异步 IO

常见类：

java.nio.channels.AsynchronousSocketChannel

基本思想是：

发起 IO 操作
  -> 方法立即返回
  -> IO 完成后回调通知

示例：

channel.read(buffer, null, new CompletionHandler<Integer, Void>() {
    @Override
    public void completed(Integer result, Void attachment) {
        // IO 完成
    }

    @Override
    public void failed(Throwable exc, Void attachment) {
        // IO 失败
    }
});

在 Java 生态中，实际高并发网络框架更常见的是基于 NIO 的 Netty、Reactor Netty 等。

六、TCP 写入、发送缓冲区和窗口

当应用调用：

outputStream.write(bytes);

大致流程是：

用户态应用
  -> 内核 TCP 发送缓冲区
  -> TCP 协议栈发送数据
  -> 对端接收缓冲区
  -> 对端应用读取

write() 成功通常只表示数据已经交给本机内核，不表示对端应用已经处理。

1. 发送缓冲区什么时候会满

常见原因包括：

  1. 对端应用读取太慢。
  2. 对端接收缓冲区快满。
  3. 网络质量差，ACK 回来慢。
  4. 拥塞控制降低发送速率。
  5. 客户端暂停下载或网络断开。

当发送缓冲区满了，阻塞 IO 的 write() 才可能卡住。

2. TCP 窗口是什么

TCP 窗口可以理解为“当前允许发送方继续发送多少数据”。

它主要涉及两个窗口：

  1. 接收窗口 rwnd：由接收方通告，表示自己还能接收多少数据。
  2. 拥塞窗口 cwnd：由发送方根据网络拥塞情况维护。

发送方实际能发送的数据量大致受下面这个值限制：

min(rwnd, cwnd)

如果接收方来不及读取数据，接收窗口可能变小，甚至变成 0。发送方继续写入时，发送缓冲区就可能逐渐被填满，最后导致写操作阻塞。

七、HTTP 客户端超时配置

真实项目里更常配置的是 HTTP 客户端超时，而不是直接操作 TCP Socket。

常见超时有三类：

  1. connect timeout：建立连接最多等多久。
  2. read/socket/response timeout：连接建立后等待响应数据最多等多久。
  3. connection request timeout：从连接池获取连接最多等多久。

1. HttpURLConnection

URL url = new URL("https://example.com");
HttpURLConnection conn = (HttpURLConnection) url.openConnection();

conn.setConnectTimeout(3000);
conn.setReadTimeout(5000);

2. JDK 11 HttpClient

HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(3))
        .build();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://example.com"))
        .timeout(Duration.ofSeconds(5))
        .build();

3. RestTemplate

RestTemplate 默认配置容易遗漏超时，项目中应明确指定。

SimpleClientHttpRequestFactory factory = new SimpleClientHttpRequestFactory();
factory.setConnectTimeout(3000);
factory.setReadTimeout(5000);

RestTemplate restTemplate = new RestTemplate(factory);

如果使用 Apache HttpClient 连接池：

RequestConfig config = RequestConfig.custom()
        .setConnectTimeout(3000)
        .setSocketTimeout(5000)
        .setConnectionRequestTimeout(2000)
        .build();

CloseableHttpClient httpClient = HttpClients.custom()
        .setDefaultRequestConfig(config)
        .build();

RestTemplate restTemplate = new RestTemplate(
        new HttpComponentsClientHttpRequestFactory(httpClient));

4. WebClient

HttpClient httpClient = HttpClient.create()
        .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 3000)
        .responseTimeout(Duration.ofSeconds(5));

WebClient webClient = WebClient.builder()
        .clientConnector(new ReactorClientHttpConnector(httpClient))
        .build();

5. OkHttp

OkHttpClient client = new OkHttpClient.Builder()
        .connectTimeout(3, TimeUnit.SECONDS)
        .readTimeout(5, TimeUnit.SECONDS)
        .writeTimeout(5, TimeUnit.SECONDS)
        .callTimeout(10, TimeUnit.SECONDS)
        .build();

OkHttp 明确提供了写超时和整体调用超时，语义比原生 java.net.Socket 更完整。

八、导出接口的推荐处理方式

1. 小文件可以直接流式写出

如果文件生成很快、数据量不大，可以直接写响应：

response.setContentType("application/vnd.openxmlformats-officedocument.spreadsheetml.sheet");
response.setHeader("Content-Disposition", "attachment; filename=\"export.xlsx\"");

try (ServletOutputStream out = response.getOutputStream()) {
    workbook.write(out);
    out.flush();
}

注意不要在已经写出部分文件后再尝试返回 JSON 错误，因为响应头和响应体可能已经提交。

2. 大文件建议先生成文件

更稳妥的流程：

生成临时文件
  -> 检查文件生成是否成功
  -> 设置响应头
  -> 设置 Content-Length
  -> 拷贝文件到 response
  -> finally 删除临时文件

示例：

Path tempFile = Files.createTempFile("export-", ".xlsx");

try {
    generateExcel(tempFile);

    response.setContentType("application/vnd.openxmlformats-officedocument.spreadsheetml.sheet");
    response.setHeader("Content-Disposition", "attachment; filename=\"export.xlsx\"");
    response.setContentLengthLong(Files.size(tempFile));

    try (InputStream in = Files.newInputStream(tempFile);
         OutputStream out = response.getOutputStream()) {
        in.transferTo(out);
        out.flush();
    }
} finally {
    Files.deleteIfExists(tempFile);
}

3. 超大文件可以改成异步导出

如果导出耗时很长，推荐改成异步任务：

用户点击导出
  -> 后端创建导出任务
  -> 返回任务 ID
  -> 后台生成文件
  -> 前端轮询或通知
  -> 用户下载已生成文件

这种方式对用户体验和系统稳定性都更友好。

九、排查响应超时的思路

遇到导出超时，可以按顺序看：

  1. 后端日志是生成阶段报错，还是写 response 时报错。
  2. 浏览器是否主动取消下载。
  3. Nginx 或网关是否有 upstream timed out。
  4. 后端是否长时间没有向响应写任何数据。
  5. 是否设置了 Content-Length。
  6. 文件是否过大，客户端下载是否很慢。
  7. 是否有连接池、线程池耗尽。
  8. 是否有代理层 idle timeout。
  9. 客户端是否设置了过短的 read timeout。

十、生产环境建议

  1. 所有 HTTP 客户端都显式设置连接超时、读取超时和连接池获取超时。
  2. 导出接口按文件大小选择直接流式、临时文件或异步任务。
  3. 网关和 Nginx 的超时要与业务耗时匹配。
  4. 大文件下载要考虑限流、断点续传、对象存储和 CDN。
  5. 避免在响应已经写出后才进行复杂业务校验。
  6. 对导出任务增加并发限制，防止拖垮数据库和磁盘。

十一、一句话总结

响应超时不一定是 TCP 问题。导出接口直接写 response 时，真正的问题往往是生成耗时、响应长时间无数据、代理 idle timeout 或客户端等待超时。先生成临时文件再输出，能把“慢生成”和“连续下载”拆开，因此更稳定。
