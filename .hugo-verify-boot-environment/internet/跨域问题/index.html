跨域问题

February 19, 2026

跨域问题本质上不是“接口不能访问”，而是浏览器出于安全考虑，对页面脚本读取跨源响应做出的限制。

更准确地说：跨域限制主要发生在浏览器环境中，由同源策略和 CORS 规则共同决定。

一、什么是同源

同源要求下面三项完全一致：

  1. 协议相同。
  2. 域名相同。
  3. 端口相同。

只要有一项不同，就属于不同源：

http://localhost:8080 -> http://localhost:8081   端口不同
http://a.com           -> https://a.com          协议不同
http://a.com           -> http://api.a.com       域名不同

同源策略限制的是：一个页面中的 JavaScript 是否可以读取另一个源的响应内容。

它不是在限制所有跨域请求都不能发出去。这个区别非常重要，别让概念自己打架。

二、为什么地址栏能打开，JS 请求却报跨域

在浏览器地址栏直接访问接口，例如：

https://api.example.com/user

这是一次页面导航。浏览器认为这是用户主动访问某个资源，不需要用 CORS 来限制。

但如果页面中的脚本执行：

fetch("https://api.example.com/user")

浏览器就会检查当前页面的源是否被目标接口允许。如果接口没有返回正确的 CORS 响应头，浏览器会拦截脚本读取响应。

也就是说：

场景 是否可能发送请求 JS 是否能读取响应
地址栏直接打开接口 可以 不涉及页面脚本
页面中 fetch 跨域接口 可以 取决于 CORS
<img src> 加载跨域图片 可以 默认不能任意读取像素
<script src> 加载跨域脚本 可以 脚本会被执行
普通表单跨域提交 可以 页面脚本不能任意读取返回内容

所以，跨域报错通常不是“后端没有收到请求”，而是“浏览器不允许前端脚本使用响应”。

三、CORS 是什么

CORS，全称 Cross-Origin Resource Sharing，中文通常叫跨源资源共享。

它是一套浏览器和服务器协商跨域访问权限的机制。服务器通过响应头告诉浏览器：

这个来源的页面，可以读取我的响应。

常见响应头如下：

Access-Control-Allow-Origin: https://www.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Allow-Credentials: true

其中最核心的是 Access-Control-Allow-Origin。

如果前端请求来源是：

https://www.example.com

那么后端至少要返回：

Access-Control-Allow-Origin: https://www.example.com

浏览器才会允许页面脚本读取响应。

四、为什么有时会出现 OPTIONS 预检

有些跨域请求在真正发送前，浏览器会先发一个 OPTIONS 请求，这叫预检请求。

预检的作用是先问服务器：

我接下来要用某个方法、带某些请求头跨域访问你，可以吗？

常见触发条件包括：

  1. 请求方法不是简单方法，例如 PUT、DELETE、PATCH。
  2. 使用了非简单请求头，例如 Authorization、X-Token。
  3. Content-Type 不是简单类型，例如 application/json。

需要注意：credentials: "include" 本身不一定触发预检。携带 Cookie 是否预检，还要看请求方法和请求头是否满足简单请求条件。

预检流程如下：

浏览器 -> OPTIONS 预检 -> 服务器
浏览器 <- 允许跨域的响应头 <- 服务器
浏览器 -> 真正的业务请求 -> 服务器

如果预检没有通过，浏览器不会继续发送真正的业务请求。

五、带 Cookie 的跨域请求要注意什么

如果跨域请求需要携带 Cookie，前端通常要写：

fetch("https://api.example.com/user", {
  credentials: "include"
});

后端也必须返回：

Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: https://www.example.com

这里有一个常见坑：带凭证的跨域请求不能使用 Access-Control-Allow-Origin: *。

也就是说，下面这种组合是无效的：

Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: *

服务器必须明确返回具体来源。

六、实际项目中的解决方案

1. 后端开启 CORS

这是最直接的方式。适合前后端确实部署在不同域名下的情况，例如：

前端：https://www.example.com
后端：https://api.example.com

后端根据允许名单返回 CORS 响应头。

2. Nginx 反向代理

让前端始终请求同源路径：

https://www.example.com/api/user

然后由 Nginx 转发到后端：

http://backend:8080/user

这样浏览器看到的是同源请求，自然不会触发跨域问题。

3. 开发环境 devServer proxy

本地开发时经常这样配置：

前端请求：/api/user
开发服务器代理到：http://localhost:8080/user

这只解决本地开发问题，生产环境仍然需要通过 Nginx、网关或后端 CORS 来处理。

七、排查思路

遇到跨域问题时，可以按下面顺序排查：

  1. 看浏览器控制台报错，确认是 CORS 还是网络请求失败。
  2. 看 Network 面板里是否出现 OPTIONS 预检。
  3. 检查后端是否返回了 Access-Control-Allow-Origin。
  4. 如果带了 Authorization，检查 Access-Control-Allow-Headers 是否包含它。
  5. 如果带 Cookie，检查 credentials 和 Access-Control-Allow-Credentials。
  6. 确认协议、域名、端口是否真的同源。

八、一句话总结

跨域不是服务器之间不能访问，而是浏览器限制页面脚本读取跨源响应。解决跨域，要么让请求变成同源，例如使用 Nginx 反向代理；要么让后端通过 CORS 明确告诉浏览器：这个来源可以访问。
