泛型、工具类型与工程建模：让类型服务真实业务

August 19, 2026

TypeScript 真正进入工程阶段，通常从泛型开始。泛型不是为了显得高级，而是为了在不丢失类型信息的前提下复用代码。

如果一个函数、组件或接口结构“外壳固定，里面的数据类型变化”，就适合用泛型。工具类型则用来在已有类型之间建立关系，避免复制出一堆相似但迟早不同步的类型。

一、泛型是什么

看一个普通函数：

function firstString(list: string[]): string | undefined {
  return list[0]
}

它只能处理字符串数组。如果要处理数字数组，又要写一个。

泛型版本：

function first<T>(list: T[]): T | undefined {
  return list[0]
}

使用时：

const name = first(['A', 'B'])
const age = first([18, 19])

name 会被推断成 string | undefined，age 会被推断成 number | undefined。

泛型的关键是：输入和输出之间的类型关系被保留下来了。

二、泛型约束

有时泛型不能完全自由，它必须具备某些字段。

function findById<T extends { id: number }>(list: T[], id: number): T | undefined {
  return list.find(item => item.id === id)
}

T extends { id: number } 表示：传进来的类型必须有 id 字段。

type User = {
  id: number
  name: string
}

const user = findById<User>(users, 1)

这就是工程里最常见的泛型模式：保留业务对象自己的字段，同时要求它满足公共操作需要的最小结构。

三、接口响应泛型

统一响应结构很适合泛型：

type ApiResponse<T> = {
  code: number
  message: string
  data: T
}

type UserProfile = {
  id: number
  username: string
}

type UserResponse = ApiResponse<UserProfile>

分页结构：

type PageResult<T> = {
  records: T[]
  total: number
  page: number
  pageSize: number
}

type PostPage = ApiResponse<PageResult<PostCard>>

这样你不必为每个接口重复定义外层结构。

四、常用工具类型

TypeScript 内置了一些工具类型。

工具类型 作用
Partial<T> 把所有字段变成可选
Required<T> 把所有字段变成必填
Pick<T, K> 从类型中挑选字段
Omit<T, K> 从类型中排除字段
Record<K, T> 构造键值映射
Readonly<T> 把字段变成只读
ReturnType<T> 获取函数返回值类型
Parameters<T> 获取函数参数元组类型
Awaited<T> 获取 Promise 完成后的值类型

示例：

type User = {
  id: number
  username: string
  password: string
  avatarUrl?: string
}

type UserPublicInfo = Omit<User, 'password'>
type UserUpdateForm = Partial<Pick<User, 'username' | 'avatarUrl'>>

这比复制一份相似类型更可靠。复制会带来同步成本，工具类型能让关系留在代码里。

五、Record 映射

Record 常用于枚举值到配置的映射。

type PostStatus = 'draft' | 'published' | 'archived'

const statusText: Record<PostStatus, string> = {
  draft: '草稿',
  published: '已发布',
  archived: '已归档'
}

如果漏掉一个状态，TypeScript 会报错。这比运行时页面显示 undefined 要体面得多。

更复杂一点，可以映射到配置对象：

type StatusConfig = {
  text: string
  color: 'gray' | 'green' | 'red'
  editable: boolean
}

const statusConfig: Record<PostStatus, StatusConfig> = {
  draft: {
    text: '草稿',
    color: 'gray',
    editable: true
  },
  published: {
    text: '已发布',
    color: 'green',
    editable: false
  },
  archived: {
    text: '已归档',
    color: 'red',
    editable: false
  }
}

六、表单类型与提交类型

表单模型不一定等于提交参数。

type PostForm = {
  title: string
  content: string
  tagIds: number[]
  agree: boolean
}

type CreatePostRequest = {
  title: string
  content: string
  tagIds: number[]
}

function toCreatePostRequest(form: PostForm): CreatePostRequest {
  return {
    title: form.title.trim(),
    content: form.content,
    tagIds: form.tagIds
  }
}

表单里可能有 UI 状态、确认勾选、临时字段，这些不应该直接提交给后端。

七、组件 Props 建模

组件参数也应该有类型。

type UserCardProps = {
  user: UserPublicInfo
  showActions?: boolean
  size?: 'small' | 'medium' | 'large'
}

Vue 中可以这样使用：

const props = withDefaults(defineProps<UserCardProps>(), {
  showActions: true,
  size: 'medium'
})

字面量联合类型能限制调用方传入合法值。

八、类型文件怎么组织

推荐按业务领域组织：

src/
  models/
    user.ts
    post.ts
    comment.ts
  api/
    user.ts
    post.ts

models 放纯类型和领域模型，api 放请求函数。不要把所有类型塞进一个 types.ts，那会变成另一个无人愿意打开的储藏室。

更具体的组织方式：

src/
  domains/
    post/
      post.model.ts
      post.api.ts
      post.mapper.ts
      post.state.ts

当业务复杂起来，按领域放比按技术类型放更容易维护。

九、类型设计检查清单

  • 这个类型是接口响应、表单模型、展示模型，还是组件参数？
  • 字段是否真的可选？
  • null 和 undefined 是否区分清楚？
  • 状态是否可以用联合类型表达？
  • 是否存在重复类型可以用 Pick、Omit、泛型抽取？
  • 是否把运行时校验误认为类型检查？
  • 是否用了太多 as 把类型问题压下去了？
  • 类型名字是否表达了业务含义，而不是只叫 Data、Item、Result？

十、练习

实现下面三个类型：

type ApiResponse<T> = {
  code: number
  message: string
  data: T
}

type PageResult<T> = {
  records: T[]
  total: number
}

type LoadState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; message: string }

然后定义 PostCard，组合出 LoadState<PageResult<PostCard>>。

type PostCard = {
  id: number
  title: string
  summary: string
  likeCount: number
}

type PostPageState = LoadState<PageResult<PostCard>>

能做到这一步，你已经能处理多数前端接口类型建模了。之后的难点不是语法，而是如何把业务边界想清楚。
