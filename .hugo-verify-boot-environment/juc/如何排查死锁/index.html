如何排查死锁

September 11, 2025

死锁是多个线程互相等待对方释放资源，导致所有相关线程都无法继续执行的并发问题。排查死锁时，不要只盯着最后报错的位置，要还原线程之间的锁持有关系。

一、死锁成立的四个条件

死锁通常同时满足四个条件：

  • 互斥：资源同一时间只能被一个线程持有。
  • 持有并等待：线程持有一个资源，同时等待其他资源。
  • 不可剥夺：资源只能由持有者主动释放。
  • 环路等待：多个线程形成循环等待链。

破坏其中任意一个条件，都可以避免死锁。

二、一个简单示例

下面的代码中，两个线程获取锁的顺序相反，因此可能发生死锁：

public class DeadlockDemo {
    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (LOCK_A) {
                sleep(1000);
                synchronized (LOCK_B) {
                    System.out.println("t1 done");
                }
            }
        }, "thread-a");

        Thread t2 = new Thread(() -> {
            synchronized (LOCK_B) {
                sleep(1000);
                synchronized (LOCK_A) {
                    System.out.println("t2 done");
                }
            }
        }, "thread-b");

        t1.start();
        t2.start();
    }

    private static void sleep(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

线程关系可以表示为：

thread-a 持有 LOCK_A，等待 LOCK_B
thread-b 持有 LOCK_B，等待 LOCK_A

这就是环路等待。

三、使用 jps 和 jstack

先找到 Java 进程号：

jps -l

再导出线程栈：

jstack <pid> > thread-dump.txt

如果存在 Java 层面的死锁，jstack 通常会直接输出类似信息：

Found one Java-level deadlock:
"thread-a":
  waiting to lock monitor ... which is held by "thread-b"
"thread-b":
  waiting to lock monitor ... which is held by "thread-a"

重点看三类信息：

  • waiting to lock：当前线程正在等待哪把锁。
  • locked：当前线程已经持有哪些锁。
  • 线程栈位置：锁是在业务代码的哪一行获取的。

四、使用 jcmd

较新的 JDK 中也可以使用 jcmd：

jcmd <pid> Thread.print > thread-dump.txt

jcmd 能输出线程栈、锁信息和线程状态。线上排障时，建议连续抓取多次线程栈：

jcmd <pid> Thread.print > dump-1.txt
sleep 5
jcmd <pid> Thread.print > dump-2.txt
sleep 5
jcmd <pid> Thread.print > dump-3.txt

如果同一批线程长期停在相同锁等待位置，问题就很可疑。

五、可视化工具

也可以使用 JDK 自带或常见诊断工具：

  • jconsole：连接本地或远程 JVM，在线程面板中检测死锁。
  • VisualVM：查看线程状态、线程 dump 和锁等待关系。
  • Arthas：线上诊断常用，可以通过 thread 命令查看阻塞线程。

可视化工具适合快速定位，最终仍然要回到线程栈和代码锁顺序上确认。

六、CPU 飙升和死锁的区别

CPU 飙升不一定是死锁。死锁线程通常处于 BLOCKED 或等待状态，并不会持续消耗大量 CPU。

排查 CPU 飙升时，一般按下面步骤：

top
top -Hp <pid>
printf "%x\n" <tid>
jstack <pid> | grep -A 30 <nid>

思路是先找到高 CPU 的线程 ID，再转换成十六进制，对应到 jstack 中的 nid，最后看线程栈停在哪段代码。

如果线程是 RUNNABLE 并持续执行同一段逻辑，可能是死循环、频繁 GC、热锁自旋或高成本计算；如果线程是 BLOCKED，再重点看锁竞争。

七、如何避免死锁

  • 统一加锁顺序，例如所有代码都先拿 LOCK_A 再拿 LOCK_B。
  • 缩小锁范围，不要在锁内执行耗时 IO、远程调用或复杂计算。
  • 使用 tryLock 设置超时时间，避免无限等待。
  • 尽量使用 BlockingQueue、Semaphore、CountDownLatch 等并发工具替代手写多锁协作。
  • 线上保留线程 dump、慢日志和关键业务日志，方便还原等待链。

八、总结

排查死锁的关键不是记住某个命令，而是画出等待关系：谁持有哪些锁，又在等谁释放锁。只要能把等待链闭环找出来，死锁就已经暴露在桌面上了。剩下的修复，通常就是统一锁顺序、减少锁范围，或者改用更合适的并发工具。
