GC

September 10, 2025

GC（Garbage Collection，垃圾回收）负责自动回收 Java 程序中不再使用的对象。它解决的是内存管理问题，但也会带来停顿、CPU 消耗和吞吐量变化。

学习 GC 时不要一开始就背收集器参数。更合理的顺序是：

  1. JVM 如何判断对象还活着。
  2. JVM 用什么算法回收垃圾。
  3. 不同垃圾回收器如何实现这些算法。
  4. 对象分配和晋升规则如何影响 GC。
  5. 如何根据日志判断 GC 是否异常。

一、如何判断对象是否可回收

判断对象是否可回收，本质上是判断它是否还可能被程序使用。

常见思路有两种：引用计数和可达性分析。

1. 引用计数

引用计数算法给每个对象维护一个计数器：

  • 有一个地方引用它，计数加 1。
  • 一个引用失效，计数减 1。
  • 计数为 0 时，对象可回收。

它的优点是实现直观，判断效率高；缺点是很难处理循环引用。

示例：

class Node {
    Node next;
}

Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;

a = null;
b = null;

a 和 b 已经无法从外部访问，但它们彼此引用。如果只靠引用计数，它们的计数都不是 0，就会出现无法回收的问题。

2. 可达性分析

Java 主流虚拟机使用可达性分析判断对象是否存活。

可达性分析从一组称为 GC Roots 的对象出发，沿引用关系向外搜索：

GC Roots
  |
  +--> object A
         |
         +--> object B

object C   object D

能从 GC Roots 走到的对象是存活对象；走不到的对象就是不可达对象，可能被回收。

常见 GC Roots 包括：

  • 虚拟机栈中局部变量表引用的对象，例如当前方法的参数、局部变量。
  • 方法区中静态字段引用的对象。
  • 方法区中常量引用的对象。
  • 本地方法栈中 JNI 引用的对象。
  • JVM 内部引用的对象，例如系统类加载器、基础异常对象等。
  • 被同步锁持有的对象。

可达性分析可以处理循环引用。即使两个对象互相引用，只要它们从 GC Roots 不可达，就仍然可以被回收。

二、Java 的引用类型

Java 引用并不只有一种强度。引用强度会影响对象在 GC 时的存活策略。

引用类型 回收规则 常见用途
强引用 只要强引用存在，对象就不会被回收 普通对象引用
软引用 内存不足时更容易被回收 内存敏感缓存
弱引用 下一次 GC 时会被回收 WeakHashMap、辅助映射
虚引用 不影响对象存活，配合引用队列感知回收 资源清理、堆外内存跟踪

1. 强引用

普通对象引用就是强引用：

Object obj = new Object();

只要 obj 仍然可达，对象就不会被 GC 回收。

2. 软引用

软引用适合描述“有内存就保留，内存紧张就回收”的对象：

Object obj = new Object();
SoftReference<Object> ref = new SoftReference<>(obj);
obj = null;

软引用曾经常被用于缓存，但现代服务端系统更推荐使用明确容量、明确过期策略的缓存组件。把缓存是否可用完全交给 GC，行为并不容易预测。

3. 弱引用

弱引用对象只能存活到下一次 GC 之前：

Object obj = new Object();
WeakReference<Object> ref = new WeakReference<>(obj);
obj = null;

WeakHashMap 使用弱引用保存 key，当 key 不再被外部强引用持有时，对应映射就可以被清理。

4. 虚引用

虚引用不能通过 get() 获取对象，也不会延长对象生命周期。它通常要配合 ReferenceQueue 使用，用来感知对象被回收的时机。

ReferenceQueue<Object> queue = new ReferenceQueue<>();
PhantomReference<Object> ref = new PhantomReference<>(new Object(), queue);

虚引用常用于更精细的资源管理，例如堆外内存释放通知。

三、垃圾回收算法

GC 分两步：

  1. 判断哪些对象存活。
  2. 回收不可达对象占用的内存。

第二步才涉及具体垃圾回收算法。

1. 标记-清除

标记-清除算法分为两个阶段：

标记存活对象 -> 清除未标记对象

优点是思路简单，不需要移动对象。缺点也明显：

  • 标记和清除都有开销。
  • 回收后会产生内存碎片。
  • 碎片过多时，大对象可能找不到连续空间。

2. 标记-整理

标记-整理算法先标记存活对象，再把存活对象向一端移动，最后清理边界外内存：

标记存活对象 -> 移动存活对象 -> 清理边界外空间

它解决了内存碎片问题，但移动对象需要更新引用，成本更高。

3. 复制

复制算法把内存分成两块，每次只使用其中一块。GC 时，把存活对象复制到另一块，再一次性清空原区域。

From: live live garbage garbage
          |
          v
To:   live live

复制算法适合新生代，因为新生代通常“对象多，但活下来的少”。如果存活对象比例很低，复制成本就比较可控。

4. 分代收集

分代收集基于一个经验：大多数对象朝生夕死，少数对象长期存活。

因此 JVM 通常会把堆按对象年龄划分：

  • 新生代：适合复制算法。
  • 老年代：适合标记-清除或标记-整理。

现代收集器不一定都使用传统连续分代布局，但“根据对象存活特征选择回收策略”的思想仍然重要。

四、GC 相关术语

GC 术语容易混乱，尤其是并行和并发。这里单独拆开，不然面试和排障时都会显得很辛苦。

术语 含义
Stop-The-World GC 期间暂停所有用户线程
串行 GC 使用单个线程工作
并行 GC 使用多个线程工作，但用户线程通常暂停
并发 GC 线程和用户线程同时运行
Minor GC / Young GC 回收新生代
Major GC / Old GC 回收老年代，具体含义依收集器和日志而定
Mixed GC G1 中同时回收年轻代和部分老年代 Region
Full GC 回收整个堆，通常还会涉及方法区或元空间

关键区别是：

  • 并行关注 GC 线程之间是否一起工作。
  • 并发关注 GC 线程是否能和用户线程同时工作。

所以“多线程 GC”不等于“低停顿 GC”。多个 GC 线程一起工作，仍然可能让用户线程全部停下来。

五、常见垃圾回收器

垃圾回收算法是思想，垃圾回收器是具体实现。不同收集器的目标不同：有的追求吞吐量，有的追求低延迟，有的更适合小堆，有的更适合大堆。

1. Serial GC

Serial GC 是单线程收集器。它在 GC 时只使用一个线程，并暂停所有用户线程。

特点：

  • 实现简单。
  • 单核或小内存环境下开销低。
  • 不适合对停顿敏感的服务端应用。

启动参数：

-XX:+UseSerialGC

2. Parallel GC

Parallel GC 以吞吐量优先。它使用多个 GC 线程并行回收，适合后台计算、批处理等更关注整体吞吐的场景。

特点：

  • 多线程回收。
  • 吞吐量表现好。
  • 停顿时间不如低延迟收集器可控。

启动参数：

-XX:+UseParallelGC

3. CMS GC

CMS（Concurrent Mark Sweep）以降低老年代停顿为目标，主要使用标记-清除算法。

它的特点是部分阶段可以和用户线程并发执行，但也有几个明显问题：

  • 标记-清除会产生内存碎片。
  • 并发阶段会和业务线程竞争 CPU。
  • 无法处理并发标记期间产生的全部浮动垃圾。
  • JDK 9 开始被标记为废弃，后续版本已移除。

CMS 在老项目里仍可能见到，但新项目一般不再优先选择它。

4. G1 GC

G1（Garbage-First）是面向服务端应用的收集器。JDK 9 之后，HotSpot 默认使用 G1。

G1 不再把堆简单地看成连续的新生代和老年代，而是划分为多个 Region：

Heap
  +--------+--------+--------+--------+
  | Eden   | Old    | Humong | Survivor|
  +--------+--------+--------+--------+
  | Old    | Eden   | Free   | Old     |
  +--------+--------+--------+--------+

G1 会评估各 Region 的回收价值，在目标停顿时间内优先回收收益高的 Region。

常见回收类型：

  • Young GC：回收年轻代 Region。
  • Concurrent Marking：并发标记老年代存活对象。
  • Mixed GC：回收年轻代和部分老年代 Region。
  • Full GC：退化路径，应尽量避免频繁发生。

启动参数：

-XX:+UseG1GC
-XX:MaxGCPauseMillis=200

MaxGCPauseMillis 是目标，不是保证。JVM 会尽力接近这个目标，但如果对象存活率、分配速率或堆大小不合理，停顿仍然可能超过目标值。

5. ZGC

ZGC 是低延迟垃圾回收器，目标是在大堆场景下把停顿控制在很低水平。它通过并发标记、并发转移、读屏障、着色指针等机制，减少必须 STW 的工作量。

适合场景：

  • 大内存服务。
  • 延迟敏感系统。
  • 希望减少长尾停顿的在线服务。

启动参数：

-XX:+UseZGC

ZGC 的优势是停顿低，代价是实现复杂，并且可能消耗更多 CPU 或内存余量。选它之前仍然要看业务目标，而不是被“低延迟”三个字带着走。

6. Shenandoah GC

Shenandoah 也是低停顿收集器，目标是把包括对象整理在内的更多 GC 工作并发化。

启动参数：

-XX:+UseShenandoahGC

它和 ZGC 的设计路线不同，但关注点相似：尽量降低 STW 时间。具体可用性与表现取决于 JDK 版本和发行版支持情况。

六、G1 和 ZGC 的停顿差异

G1 和 ZGC 都可以用于服务端应用，但它们的停顿来源不同。

G1 的回收过程里，很多标记工作可以并发完成，但对象复制转移阶段通常仍需要 STW。存活对象越多、对象图越复杂，复制和引用修正成本就越高。

G1 混合回收大致包含：

  • 初始标记：STW，标记 GC Roots 直接可达对象。
  • 并发标记：和用户线程并发，遍历对象图。
  • 再标记：STW，修正并发期间变化的引用关系。
  • 清理：统计 Region 回收价值。
  • 转移复制：STW，把存活对象复制到新 Region。

ZGC 的设计目标是让标记、转移、重定位尽可能并发完成。它仍然有少量 STW 阶段，但通常只处理 GC Roots 等较小工作集，而不是在停顿阶段搬运大量存活对象。

因此一般可以这样理解：

  • G1 适合作为通用服务端收集器，吞吐量和停顿之间比较均衡。
  • ZGC 更偏向低延迟和大堆场景，适合对长停顿敏感的在线服务。

这不是说 ZGC 永远比 G1 好。GC 选择要看应用分配速率、对象存活率、堆大小、CPU 余量和延迟目标。脱离场景谈收集器优劣，和拿尺子量空气差不多，认真但无效。

七、内存分配与回收策略

对象如何分配，会直接影响 GC 频率和停顿。

1. 对象优先在 Eden 分配

大多数对象会先在 Eden 区分配。当 Eden 空间不足时，会触发 Young GC。

Young GC 后仍然存活的对象，会进入 Survivor 区，年龄加 1。达到一定年龄后，对象可能晋升到老年代。

2. 大对象可能直接进入老年代

大对象需要连续内存空间。如果大对象在新生代来回复制，成本很高，所以 JVM 可能让它直接进入老年代。

G1 中还有 Humongous Object 的概念：超过一定 Region 比例的大对象会被特殊处理。大量大对象分配可能导致 GC 压力明显上升。

3. 长期存活对象进入老年代

对象每熬过一次 Young GC，年龄通常会增加。达到晋升阈值后，会进入老年代。

但晋升不是只看固定年龄。JVM 还可能根据 Survivor 区占用情况进行动态年龄判断。

4. 空间分配担保

Young GC 前，JVM 需要判断老年代是否有足够空间容纳可能晋升的对象。如果担保失败，可能触发更重的回收。

这也是为什么新生代和老年代比例不合适时，可能导致 GC 行为异常。

八、方法区和类卸载

GC 不只回收堆对象，也可能涉及方法区或元空间。

方法区主要回收两类内容：

  • 废弃常量。
  • 无用类。

一个类要被卸载，通常需要满足：

  • 该类所有实例都已经被回收。
  • 加载该类的 ClassLoader 已经不可达。
  • 该类对应的 Class 对象没有被任何地方引用。

元空间持续增长时，常见原因包括：

  • 动态代理或字节码增强大量生成类。
  • 自定义类加载器无法释放。
  • Web 应用热部署后旧类加载器被引用住。
  • 线程上下文类加载器、静态集合、缓存、ThreadLocal 持有旧对象。

九、如何判断 GC 是否异常

看 GC 不能只看“发生了几次”，还要结合业务影响。

常见异常信号：

  • Young GC 非常频繁，说明对象分配速率过高或新生代太小。
  • Full GC 频繁，说明老年代、元空间或直接内存可能有压力。
  • GC 后堆占用下降很少，说明大量对象仍然存活，可能存在内存泄漏或缓存过大。
  • 单次停顿时间过长，说明存活对象太多、堆过大、收集器不合适或系统资源紧张。
  • GC 占用 CPU 高，业务吞吐下降，说明回收成本已经明显影响应用。

排查时优先收集这些信息：

jcmd <pid> GC.heap_info
jcmd <pid> VM.flags
jcmd <pid> Thread.print

JDK 9+ 推荐开启统一 GC 日志：

-Xlog:gc*,gc+heap=debug:file=gc-%t.log:time,uptime,level,tags:filecount=5,filesize=20M

JDK 8 常见写法：

-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-XX:+PrintGCCause
-Xloggc:gc.log

十、总结

GC 可以用几句话串起来：

  • Java 主要用可达性分析判断对象是否存活。
  • GC Roots 是可达性分析的起点。
  • 引用类型会影响对象在 GC 中的回收时机。
  • 标记-清除、标记-整理、复制是基础回收算法。
  • 分代收集利用了“大多数对象很快死亡”的经验。
  • 并行是多个 GC 线程一起工作，并发是 GC 线程和用户线程同时工作。
  • 收集器选择要服从业务目标：吞吐量、停顿时间、堆大小、CPU 余量，一个都不能假装不存在。

学 GC 的目的不是把收集器名字背成菜单，而是在系统出问题时知道：对象为什么没被回收，GC 为什么停这么久，下一步应该看哪份证据。
