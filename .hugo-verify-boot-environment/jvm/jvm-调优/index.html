JVM 调优

September 10, 2025

JVM 调优不是背参数，也不是看到 GC 就立刻把堆调大。它的本质是：根据业务目标和运行证据，调整 JVM、应用代码和资源配置之间的关系。

多数性能问题并不需要 JVM 参数解决。慢 SQL、接口串行调用、缓存击穿、日志过量、线程池配置错误、对象创建过于粗暴，都可能伪装成“JVM 不行”。所以调优前要先确认瓶颈，别急着拿参数表开刀。那样看起来很专业，效果通常很朴素。

一、调优前先确定目标

JVM 调优至少要回答三个问题：

  1. 业务到底要什么：低延迟、高吞吐、低成本，还是稳定优先？
  2. 当前问题是什么：响应慢、CPU 高、Full GC、OOM、内存持续上涨，还是启动慢？
  3. 有什么证据：GC 日志、线程栈、堆转储、监控曲线、压测数据是否能互相印证？

没有目标的调优，只是改配置。

常见目标如下：

目标 关注指标 典型场景
高吞吐 单位时间处理任务数、GC 时间占比 批处理、离线任务、计算服务
低延迟 P95、P99、最大停顿时间 在线交易、网关、实时接口
稳定性 OOM 次数、Full GC 次数、内存增长趋势 长期运行的服务
成本控制 CPU、内存、容器资源利用率 大规模微服务

二、核心指标

JVM 调优常看的核心指标有吞吐量、停顿时间、内存占用和分配速率。

1. 吞吐量

吞吐量表示 CPU 用于执行业务代码的时间占比：

吞吐量 = 运行用户代码时间 / (运行用户代码时间 + GC 时间)

吞吐量越高，说明 GC 消耗占比越低。批处理系统通常更重视吞吐量。

2. 停顿时间

停顿时间是指 GC 或其他 JVM 活动导致用户线程暂停的时间。它直接影响接口响应时间，尤其影响 P99 和最大延迟。

低延迟系统不能只看平均响应时间，因为平均值会掩盖长尾停顿。

3. 堆内存占用

堆太小会导致 GC 频繁；堆太大可能导致单次回收成本增加，也会提高容器内存成本。

比较有价值的观察方式是看：

  • GC 前堆占用。
  • GC 后堆占用。
  • 老年代占用趋势。
  • Full GC 后内存是否明显下降。

如果 Full GC 后内存仍然降不下来，问题往往不是“堆太小”，而是对象仍然被引用。

4. 分配速率

分配速率表示应用创建对象的速度。分配速率高会推高 Young GC 频率。

常见原因包括：

  • 热点路径频繁创建临时对象。
  • 大量 JSON 序列化和反序列化。
  • 日志拼接或异常栈创建过多。
  • 批量查询一次性加载大量对象。
  • 缓存或集合无边界增长。

5. GC 频率

GC 频率要结合回收效果一起看。

  • Young GC 频繁但每次很快，业务没有明显抖动，未必是问题。
  • Full GC 频繁且回收后下降很少，通常是严重信号。
  • GC 时间占比高，说明 JVM 正花大量 CPU 处理内存回收。

三、吞吐量、停顿和内存的取舍

吞吐量、停顿时间和内存占用很难同时最优。

一般规律是：

  • 堆更大：GC 频率可能降低，但单次处理的对象更多，停顿可能变长。
  • 堆更小：单次停顿可能变短，但 GC 更频繁，吞吐量可能下降。
  • 低延迟收集器：停顿更可控，但可能需要更多 CPU 或内存余量。
  • 吞吐量优先收集器：总体处理能力强，但长尾停顿可能更明显。

所以调优不是寻找“最好参数”，而是寻找符合业务目标的平衡点。

四、推荐调优流程

一次相对可靠的 JVM 调优流程如下：

明确目标
 -> 建立基线
 -> 收集证据
 -> 定位瓶颈
 -> 小步修改
 -> 压测验证
 -> 上线观察

1. 建立基线

先记录当前状态：

  • JDK 版本。
  • JVM 参数。
  • 容器 CPU 和内存限制。
  • 平均、P95、P99 响应时间。
  • QPS 和吞吐量。
  • GC 次数、GC 时间、Full GC 次数。
  • 堆、非堆、直接内存、线程数。

常用命令：

jcmd <pid> VM.version
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print

2. 开启 GC 日志

JDK 9+ 推荐使用统一日志：

-Xlog:gc*,gc+heap=debug:file=logs/gc-%t.log:time,uptime,level,tags:filecount=5,filesize=20M

参数含义：

  • gc*：输出 GC 相关日志。
  • gc+heap=debug：输出更详细的堆信息。
  • file=logs/gc-%t.log：日志文件路径，%t 表示 JVM 启动时间。
  • time,uptime,level,tags：日志字段。
  • filecount=5,filesize=20M：最多保留 5 个文件，每个 20MB。

JDK 8 常见写法：

-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-XX:+PrintGCCause
-XX:+UseGCLogFileRotation
-XX:NumberOfGCLogFiles=5
-XX:GCLogFileSize=20M
-Xloggc:logs/gc.log

3. 收集堆和线程证据

排查 OOM、内存泄漏或 Full GC 时，堆转储很重要：

jcmd <pid> GC.heap_dump /tmp/heap.hprof

也可以提前配置 OOM 自动 dump：

-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/tmp/heapdump.hprof

排查 CPU 高、死锁、线程阻塞时，看线程栈：

jcmd <pid> Thread.print > thread.txt

Linux 上还可以结合 top -H -p <pid> 找到高 CPU 线程，再把线程 ID 转成十六进制，对应线程栈里的 nid。

五、常用 JVM 参数

参数应该服务于目标，不要无脑堆满启动脚本。

1. 堆大小

-Xms2g
-Xmx2g

常见建议：

  • 服务端应用通常把 -Xms 和 -Xmx 设置成相同值，减少运行时扩缩容。
  • 容器环境中要给堆外内存、线程栈、Metaspace、Code Cache 留空间。
  • 不要把容器内存几乎全部给 -Xmx，否则容易被系统 OOM Kill。

2. 栈大小

-Xss512k

-Xss 控制单个线程栈大小。

  • 栈太小：递归或深调用链容易 StackOverflowError。
  • 栈太大：同样内存下可创建线程数减少。

线程数很多的服务，要同时看线程池配置和 -Xss，不能只看堆。

3. 元空间

-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

MetaspaceSize 影响触发元空间 GC 的初始阈值；MaxMetaspaceSize 限制元空间最大值。

如果动态类很多，元空间持续上涨，要优先检查类加载器泄漏，而不是只把上限调大。

4. 直接内存

-XX:MaxDirectMemorySize=512m

NIO、Netty、堆外缓存可能使用直接内存。直接内存不在 Java 堆里，但仍然占用进程内存。

如果堆看起来不高，进程 RSS 却很高，就要检查直接内存、线程栈、元空间和本地库内存。

5. G1 常用参数

-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:InitiatingHeapOccupancyPercent=45

说明：

  • UseG1GC：启用 G1。
  • MaxGCPauseMillis：目标停顿时间，不是硬保证。
  • InitiatingHeapOccupancyPercent：触发并发标记的堆占用阈值。

G1 通常不建议手动强行固定年轻代大小，因为这会限制 G1 根据停顿目标自动调整。

6. ZGC 常用参数

-XX:+UseZGC
-Xms4g
-Xmx4g

ZGC 通常更关注堆大小、CPU 余量和业务延迟目标。它的大部分内部策略不需要像传统收集器那样细调。

六、垃圾回收器选择

不同收集器适合不同目标。

收集器 主要目标 适合场景
Serial 简单、低额外开销 小工具、单核、小内存
Parallel 吞吐量优先 批处理、后台计算
G1 吞吐和停顿平衡 通用服务端应用
ZGC 低延迟、大堆 延迟敏感在线服务
Shenandoah 低停顿 低延迟服务，取决于发行版支持

Java 8 中常见选择：

-XX:+UseParallelGC
-XX:+UseG1GC
-XX:+UseConcMarkSweepGC

JDK 9+ 中，G1 是 HotSpot 默认收集器。CMS 已经不适合作为新系统首选。

GC 选择的基本判断：

  • 批处理系统优先看吞吐量，可以考虑 Parallel。
  • 普通服务端应用优先从 G1 开始。
  • 大堆、低延迟、P99 敏感服务可以评估 ZGC 或 Shenandoah。
  • 老系统使用 CMS 时，应逐步评估迁移到 G1 或其他现代收集器。

七、常见调优场景

1. Young GC 频繁

可能原因：

  • 对象分配速率过高。
  • 新生代空间偏小。
  • 短时间内创建大量临时对象。
  • 批量接口一次性加载过多数据。

处理思路：

  • 先看分配热点，减少不必要对象创建。
  • 控制批处理大小和分页大小。
  • 检查日志、序列化、集合复制等热点路径。
  • 在确认代码侧合理后，再考虑堆大小或收集器策略。

2. Full GC 频繁

可能原因：

  • 老年代增长过快。
  • 大对象直接进入老年代。
  • 内存泄漏。
  • 元空间不足。
  • 显式调用 System.gc()。

处理思路：

  • 对比 Full GC 前后堆占用。
  • 如果 Full GC 后下降很少，优先分析堆转储。
  • 检查缓存、静态集合、监听器、ThreadLocal、连接对象是否释放。
  • 搜索代码和依赖中是否有 System.gc()。

可以禁止显式 GC：

-XX:+DisableExplicitGC

但这只是防御措施，不该掩盖真正问题。

3. 单次 GC 停顿过长

可能原因：

  • 堆太大且存活对象多。
  • 老年代对象图复杂。
  • 大对象过多。
  • 收集器不适合低延迟目标。
  • CPU 资源不足，GC 线程抢不到时间片。

处理思路：

  • 看 GC 日志中每个阶段耗时。
  • 降低对象存活率，减少长生命周期缓存。
  • 给容器分配足够 CPU。
  • 评估 G1 停顿目标或低延迟收集器。

4. OOM

OOM 不只有堆溢出。

错误 常见原因
Java heap space 堆对象过多或泄漏
GC overhead limit exceeded GC 花大量时间但回收很少
Metaspace 动态类过多或类加载器泄漏
Direct buffer memory 直接内存不足
unable to create native thread 线程过多或系统资源不足

处理 OOM 的关键是拿到 dump 和 JVM 参数，再根据错误类型分析。看到 OOM 就加内存，是一种很省脑子的做法，缺点是也很省效果。

5. CPU 高

CPU 高不一定是 GC。常见原因包括：

  • 业务代码死循环。
  • 正则表达式回溯。
  • 序列化过重。
  • 日志过量。
  • 锁竞争。
  • GC 线程消耗 CPU。

处理思路：

  1. 用 top -H -p <pid> 找高 CPU 线程。
  2. 把线程 ID 转成十六进制。
  3. 用 jcmd <pid> Thread.print 查对应 nid。
  4. 如果高 CPU 线程是 GC 线程，再回到 GC 日志分析。

八、容器环境注意点

现在 Java 服务经常跑在容器里，JVM 调优必须考虑容器限制。

注意事项：

  • 容器内存不是只给 Java 堆使用。
  • -Xmx 要给元空间、直接内存、线程栈、本地库留余量。
  • CPU limit 太低会影响 GC 线程和 JIT 编译线程。
  • 内存超过容器限制时，可能不是 Java OOM，而是被系统 OOM Kill。
  • 监控要同时看 JVM 内存和容器 RSS。

一个保守的起点是：堆占容器内存的 50% 到 70%，剩余空间留给非堆和本地内存。具体比例要根据线程数、直接内存和框架使用情况调整。

九、调优后的验证

每次调优都应该验证，而不是“改完感觉好多了”。

至少对比这些指标：

  • 平均响应时间、P95、P99。
  • QPS 或任务吞吐。
  • Young GC 次数和总耗时。
  • Full GC 次数和总耗时。
  • GC 后老年代占用。
  • CPU 使用率。
  • 容器内存 RSS。
  • 错误率和超时率。

一次只改少量参数。否则指标变好了也不知道是哪一项起作用，指标变坏了更不知道该撤哪一项。工程不是玄学，虽然很多线上问题确实很会伪装。

十、总结

JVM 调优可以记住几条原则：

  • 先明确业务目标，再谈参数。
  • 先收集 GC 日志、线程栈、堆转储和监控曲线，再做判断。
  • Young GC 频繁先看分配速率，Full GC 频繁先看回收效果。
  • OOM 要按类型分析，不要只会加堆。
  • G1 适合作为通用服务端起点，ZGC 更适合低延迟和大堆场景。
  • 容器环境中，堆不是进程全部内存。
  • 调优要小步修改、压测验证、上线观察。

最重要的是：JVM 参数只能改善运行时行为，不能替应用代码承担设计责任。如果对象无限增长、缓存没有边界、线程池随意创建，再优雅的 GC 也只能礼貌地把问题暴露出来。
