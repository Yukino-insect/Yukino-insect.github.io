逃逸分析

February 5, 2026

逃逸分析是 JIT 编译器的一种优化分析手段，用来判断对象引用是否会逃出当前方法或当前线程。如果对象不会逃逸，JIT 就可能把对象分配、锁和字段访问优化掉。

需要先说清楚一点：逃逸分析本身不是优化，它只是优化的前提。真正发生的优化可能是标量替换、锁消除、同步省略等。很多资料把逃逸分析直接说成“对象分配到栈上”，这个说法太粗糙，甚至容易误导。

一、什么是逃逸

对象逃逸指的是：对象引用被当前作用域之外的代码持有，导致 JVM 不能确定它只在当前范围内使用。

示例：

private Object field;

public void method() {
    Object obj = new Object();
    field = obj;
}

这里 obj 被赋值给成员变量。即使 method 执行结束，其他方法仍然可能通过 field 访问它，所以它发生了逃逸。

再看一个返回值逃逸：

public Object create() {
    Object obj = new Object();
    return obj;
}

obj 被返回给调用方，方法结束后仍然可能被外部持有，因此也逃逸了。

二、逃逸的层次

可以粗略把逃逸分成三类。

类型 含义 优化空间
不逃逸 对象只在方法内部使用 优化空间最大
方法逃逸 对象逃出当前方法，但未必逃出当前线程 仍可能做部分优化
线程逃逸 对象可能被其他线程访问 优化空间最小

1. 不逃逸

public int sum() {
    Point point = new Point(1, 2);
    return point.x + point.y;
}

如果 Point 对象只在 sum 方法内部使用，JIT 可能认为它没有逃逸。

2. 方法逃逸

public Point createPoint() {
    return new Point(1, 2);
}

对象返回给调用方，已经逃出当前方法。JIT 是否还能优化，要看调用链、内联结果和后续使用方式。

3. 线程逃逸

private volatile Point shared;

public void publish() {
    shared = new Point(1, 2);
}

对象被发布到共享字段，其他线程可能访问它。此时 JVM 必须更保守。

三、JIT 可以做哪些优化

逃逸分析常见的优化结果包括标量替换、锁消除和同步省略。

1. 标量替换

如果一个对象没有逃逸，并且可以被拆解成若干字段，JIT 可能不再真实分配这个对象，而是把字段当作局部变量处理。

示例：

public int sum() {
    Point point = new Point(1, 2);
    return point.x + point.y;
}

优化后可以近似理解为：

public int sum() {
    int x = 1;
    int y = 2;
    return x + y;
}

真实机器码不会真的长这样，但这个类比足够说明重点：对象可能被拆散，分配也可能被消除。

2. 锁消除

如果 JVM 判断某个加锁对象不会被其他线程访问，就可以去掉不必要的锁。

public String concat(String a, String b) {
    StringBuffer buffer = new StringBuffer();
    buffer.append(a);
    buffer.append(b);
    return buffer.toString();
}

StringBuffer 的方法是同步的，但 buffer 是方法内部对象，没有逃出当前方法。JIT 可能消除这些同步开销。

当然，现代代码里通常会直接用 StringBuilder。把希望寄托在 JIT 替你弥补代码选择，也不是特别值得骄傲。

3. 栈上分配

理论上，如果对象不逃逸，可以把对象分配到栈上，方法结束后随栈帧一起释放。

但在 HotSpot 中，更常见、更重要的实际效果是标量替换导致对象分配被消除。也就是说，很多时候不是“对象从堆搬到了栈”，而是“对象根本没有以完整对象形式存在”。

因此更准确的说法是：

逃逸分析可能让对象分配被优化掉，而不是简单等同于栈上分配。

四、哪些代码容易阻碍优化

JIT 是否能优化，取决于运行时信息和代码形态。下面这些情况会让分析更保守：

  • 对象被返回给外部。
  • 对象赋值给静态字段或成员字段。
  • 对象传给无法内联、无法分析的方法。
  • 对象进入集合、数组或缓存。
  • 对象被发布给其他线程。
  • 代码不够热，没有触发 JIT 编译。
  • 方法过大或调用关系复杂，导致内联失败。

示例：

public void add(List<Point> list) {
    Point point = new Point(1, 2);
    list.add(point);
}

point 被放进外部传入的集合，JVM 不能假设它只在当前方法内使用。

五、如何观察逃逸分析

逃逸分析属于 JIT 优化细节，不能只靠肉眼判断。

常见 JVM 参数：

-XX:+DoEscapeAnalysis
-XX:+EliminateAllocations
-XX:+EliminateLocks

这些参数在常见服务端 JDK 中通常默认开启。验证优化效果时，更推荐使用 JMH 做基准测试，并结合 GC 日志、分配速率和 JIT 编译日志分析。

简单看分配变化，可以关注：

  • 单次操作分配了多少字节。
  • GC 次数是否减少。
  • 吞吐量是否稳定提升。
  • 关闭逃逸分析前后是否有明显差异。

用于对比的参数：

-XX:-DoEscapeAnalysis

注意，这类对比只适合实验和定位，不适合生产环境随便关闭。生产环境里为了证明一个概念而牺牲优化，听起来就很有实验精神，也很容易被值班的人记住。

六、实践建议

逃逸分析对业务编码有几个实际启发：

  • 短生命周期对象不一定都会造成堆压力，JIT 可能优化掉一部分。
  • 不要为了“帮助逃逸分析”把代码写得晦涩。
  • 热点路径里要避免无意义地把临时对象放进集合、字段或跨线程结构。
  • 性能优化要用 JMH、GC 日志和性能分析工具验证。
  • 如果对象分配不是瓶颈，就不要围绕它做过度设计。

例如，下面这种代码如果只是为了减少对象创建，反而可能降低可读性：

// 不推荐仅凭猜测这样写
reuseMutableHolder.x = a;
reuseMutableHolder.y = b;
return reuseMutableHolder.x + reuseMutableHolder.y;

如果这个对象本来可以被 JIT 消除，手动复用可变对象不仅未必更快，还可能引入线程安全和状态污染问题。

七、总结

逃逸分析可以这样理解：

  • 它判断对象引用是否逃出方法或线程。
  • 不逃逸对象可能被标量替换，甚至消除分配。
  • 不会被其他线程访问的锁对象可能触发锁消除。
  • HotSpot 中不要把逃逸分析简单等同于栈上分配。
  • 优化是否发生取决于 JIT、代码热度、内联结果和运行时条件。

最后记住一句话就够了：写清楚代码，让 JIT 有机会优化；遇到性能问题，再用证据判断它有没有优化成功。
