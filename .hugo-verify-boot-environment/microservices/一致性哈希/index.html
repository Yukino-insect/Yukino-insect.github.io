一致性哈希

March 6, 2026

一致性哈希用于解决分布式系统中的数据或请求路由问题。它的核心目标是：节点增删时，只迁移少量 key，而不是像普通取模一样让大多数 key 重新分布。

它常见于缓存分片、分布式存储、消息分区、负载均衡和需要粘性路由的场景。

普通取模的问题

假设有 3 个节点，路由规则是：

hash(key) % 3

当节点扩容到 4 个时，规则变成：

hash(key) % 4

由于取模基数变了，大量 key 的目标节点都会变化。对于缓存系统，这意味着大面积缓存失效；对于存储系统，这意味着大量数据迁移。

哈希环

一致性哈希把哈希值空间看成一个环。例如使用 32 位哈希时，范围是 0 到 2^32 - 1。

节点和业务 key 都映射到这个环上：

  1. 对节点标识做 hash，得到节点在环上的位置。
  2. 对业务 key 做 hash，得到 key 在环上的位置。
  3. 从 key 的位置开始顺时针查找，第一个遇到的节点就是目标节点。
  4. 如果走到环尾还没找到，就回到环头继续找。

这样新增一个节点时，只会影响它在环上接管的那一段区间；删除一个节点时，也只会影响原本落在这个节点上的 key。

虚拟节点

如果每台物理机器只在环上放一个点，节点数量少时分布会很不均匀。某台机器可能刚好接管了很大的区间，另一台机器只接管很小一段。

虚拟节点的做法是：让同一台物理节点在哈希环上占多个位置。

例如物理节点 nodeA 配置 100 个虚拟节点：

nodeA#0
nodeA#1
nodeA#2
...
nodeA#99

对每个虚拟节点标识做 hash，并插入环中。路由时先命中虚拟节点，再映射回真实物理节点。

虚拟节点越多，数据分布通常越均匀，但路由表也越大，维护成本越高。节点少时可以多放一些虚拟节点，节点很多时可以适当减少。

查询流程

对业务 key user:1001：

  1. 计算 hash("user:1001")。
  2. 在有序环里找到第一个大于等于该 hash 的虚拟节点。
  3. 取出该虚拟节点对应的物理节点。
  4. 如果没有找到，就使用环上的第一个虚拟节点。

在 Java 中，TreeMap 很适合表达这个有序环：

public class ConsistentHashRouter {

    private final TreeMap<Long, String> ring = new TreeMap<>();
    private final int replicas;

    public ConsistentHashRouter(int replicas) {
        this.replicas = replicas;
    }

    public void addNode(String nodeId) {
        for (int i = 0; i < replicas; i++) {
            ring.put(hash(nodeId + "#" + i), nodeId);
        }
    }

    public void removeNode(String nodeId) {
        for (int i = 0; i < replicas; i++) {
            ring.remove(hash(nodeId + "#" + i));
        }
    }

    public String route(String key) {
        if (ring.isEmpty()) {
            throw new IllegalStateException("no available node");
        }

        long hash = hash(key);
        Map.Entry<Long, String> entry = ring.ceilingEntry(hash);
        if (entry == null) {
            entry = ring.firstEntry();
        }
        return entry.getValue();
    }

    private long hash(String value) {
        return Integer.toUnsignedLong(value.hashCode());
    }
}

示例里为了说明结构使用了 hashCode。真实系统应使用分布更均匀的哈希函数，例如 MurmurHash、xxHash 这类非加密哈希。

扩容与缩容

新增节点时：

  1. 为新节点生成虚拟节点。
  2. 把这些虚拟节点插入环。
  3. 新节点接管每个插入点前一段区间的数据。
  4. 只迁移受影响区间，不需要全量重分布。

下线节点时：

  1. 删除该节点的所有虚拟节点。
  2. 原本落在这些虚拟节点上的 key 顺时针迁移到后继节点。
  3. 对被迁移的数据做搬迁、预热或回源。

一致性哈希只决定“key 应该去哪里”，并不会自动搬数据。缓存场景可以接受回源，存储场景必须设计迁移流程。

权重节点

如果节点规格不同，可以给高配置机器更多虚拟节点：

nodeA: 200 replicas
nodeB: 100 replicas
nodeC: 50 replicas

这样高配置节点会接管更多区间。注意权重变化本身也会导致 key 迁移，不要频繁调整。

工程注意点

  1. 哈希函数要稳定。不同语言、不同版本的 hash 实现可能不一致，跨语言系统要明确算法。
  2. 路由表要一致。所有客户端必须看到同一份节点列表和权重配置。
  3. 节点上下线要有缓冲。直接删除节点会导致流量瞬间切走，缓存和存储都可能抖动。
  4. 热点 key 仍然可能打爆单节点。一致性哈希解决分布，不自动解决热点。
  5. 数据迁移要可观测。迁移进度、失败数、回源量都要能看见。

总结

一致性哈希的价值在于降低节点变化时的迁移范围，虚拟节点则用来改善分布均匀性。它是路由算法，不是完整的数据迁移系统。真正上线时，还要配合健康检查、节点权重、迁移任务、缓存预热和监控告警。
