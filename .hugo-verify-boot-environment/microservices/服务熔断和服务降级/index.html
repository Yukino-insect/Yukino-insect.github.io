服务熔断和服务降级

January 3, 2026

服务熔断和服务降级都是微服务稳定性设计里的保护手段。它们经常一起出现，但解决的问题不同：熔断决定还要不要继续调用故障依赖，降级决定依赖不可用后返回什么替代结果。

如果只做熔断不做降级，用户看到的可能只是快速失败。如果只做降级不做熔断，系统仍然会持续把请求打到故障依赖上，最后把线程池、连接池和上游服务一起拖住。

服务熔断

服务熔断是指上游调用下游服务时，如果下游在一段时间内异常比例过高、响应过慢或持续超时，系统会暂时切断对下游的调用。

熔断后的请求不会继续访问故障服务，而是直接失败或进入降级逻辑。这样可以避免调用线程长时间阻塞，防止故障沿调用链扩散。

典型触发指标包括：

  • 异常比例：一段时间内失败请求占比超过阈值。
  • 异常数：一段时间内异常数量超过阈值。
  • 慢调用比例：响应时间超过阈值的请求占比过高。
  • 超时数量：依赖持续没有在规定时间内返回。

熔断状态

熔断器通常有三种状态：

状态 含义
关闭 正常调用下游，持续统计请求结果
打开 暂时拒绝调用下游，直接失败或降级
半开 放少量探测请求过去，判断下游是否恢复

状态变化大致如下：

closed -> 指标超过阈值 -> open
open -> 熔断窗口结束 -> half-open
half-open -> 探测成功 -> closed
half-open -> 探测失败 -> open

半开状态很重要。没有半开探测，系统只能靠人工恢复；探测流量过大，又可能在下游刚恢复时再次压垮它。

服务降级

服务降级是在依赖不可用、系统压力过大或业务开关触发时，主动关闭、简化或替换部分非核心功能，保证核心链路继续可用。

常见例子：

  • 商品详情页推荐系统不可用时，返回空推荐列表。
  • 评论服务超时时，只展示商品主体信息。
  • 积分服务不可用时，先完成下单，后续异步补偿积分。
  • 风控服务异常时，对高风险操作拒绝，对低风险查询使用缓存结果。

降级不是“随便返回一个假结果”。降级结果必须符合业务语义，不能为了页面不报错而制造更严重的数据错误。

两者区别

维度 熔断 降级
关注点 是否继续调用依赖 依赖不可用后返回什么
触发方式 异常比例、慢调用、超时等运行时指标 熔断、开关、系统压力、业务预案
目标 隔离故障，保护上游资源 保住核心功能和用户体验
典型结果 快速失败、进入 fallback 空值、缓存、默认值、异步补偿

简单说，熔断是止损开关，降级是替代方案。

Sentinel 中的应用

在 Java 微服务体系中，Sentinel 常用于限流、熔断、降级和系统保护。熔断规则可以基于慢调用比例、异常比例、异常数等指标触发。

以慢调用比例为例：

统计窗口内请求数 >= minRequestAmount
并且 RT > maxAllowedRt 的请求比例 >= slowRatioThreshold
则熔断 timeWindow 秒

Sentinel 负责判断“是否应该阻断”，业务代码仍然要负责“阻断后怎么返回”。这就是 blockHandler、fallback 或统一异常处理存在的意义。

设计原则

先定义业务语义

不是每个接口都适合降级：

  • 查询推荐、评论、标签：通常可以返回空值或缓存。
  • 扣款、扣库存、发券：不能用“默认成功”降级。
  • 权限、风控、认证：多数场景应失败关闭，而不是放行。

稳定性设计必须先问：这个依赖失败时，业务允许什么结果？

超时要早于熔断

熔断依赖统计数据，而统计数据来自真实请求。如果调用没有明确超时，请求会长时间挂住，熔断还没触发，上游资源已经被耗尽。

通常应同时配置：

  • 连接超时。
  • 读取超时。
  • 线程池或隔离舱。
  • 熔断阈值。
  • 降级逻辑。

降级结果要可观测

降级不能悄悄发生。至少要记录：

  • 哪个资源触发降级。
  • 原始异常或熔断原因。
  • 降级次数和比例。
  • 对应的 traceId。

否则系统表面上“没报错”，实际核心依赖可能已经坏了很久。

常见误区

  1. 只配置规则，不写业务 fallback。
  2. 所有接口统一返回空对象，导致数据语义混乱。
  3. 写接口开启自动重试，但没有幂等设计。
  4. 熔断阈值过低，正常抖动也频繁打开熔断器。
  5. 熔断后没有告警，故障被降级结果掩盖。

总结

熔断负责隔离故障，降级负责提供替代结果。真正可靠的微服务不是永远不失败，而是在失败发生时，能把影响限制在可理解、可恢复、可观测的范围内。
