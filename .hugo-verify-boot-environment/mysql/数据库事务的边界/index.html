数据库事务的边界

February 19, 2026

判断事务能不能生效，先不要急着看注解。最底层的问题是：这些 SQL 是否在同一个数据库连接上执行。

对单机关系型数据库来说，本地事务的边界通常就是一个连接。跨连接、跨数据源、跨线程之后，事情就不再是一个 @Transactional 能轻轻盖住的了。

一、同一个连接

同一个 JDBC Connection 上执行多条 SQL，只要关闭自动提交并显式提交或回滚，就可以处在同一个事务中：

connection.setAutoCommit(false);
try {
    // sql 1
    // sql 2
    connection.commit();
} catch (Exception e) {
    connection.rollback();
    throw e;
}

Spring 的事务管理，本质上也是把连接绑定到当前线程，然后在方法执行前后控制提交和回滚。

二、同一个库的不同 schema

如果是在同一个 database、同一个连接里访问不同 schema，事务仍然可以覆盖它们：

begin;
insert into schema_a.t1 values (...);
insert into schema_b.t2 values (...);
commit;

schema 是命名空间，不等于新的数据库连接。

真正危险的是：明明只是不同 schema，却在应用层为每个 schema 配一个独立数据源。这样一个业务操作可能跨多个 DataSource，自然也就跨了多个连接。本地事务无法保证它们一起提交或一起回滚。

三、不同 database 或不同实例

不同 database、不同 MySQL 实例、不同机器之间，默认不是同一个本地事务。

如果业务必须同时写两个库：

写库 A 成功
写库 B 失败

普通本地事务无法自动把库 A 回滚。要保证强一致，需要 XA、JTA、2PC 这类分布式事务方案；更多业务系统会选择可靠消息、发件箱模式、补偿任务或最终一致。

四、Spring Transactional 的生效条件

@Transactional 是 Spring 在应用层通过 AOP 做的事务包装。它不是写在方法上就一定生效。

常见条件如下。

五、必须经过代理对象

Spring 事务依赖代理。下面这些场景容易失效：

  1. 同类内部自调用：
public void outer() {
    this.inner();
}

@Transactional
public void inner() {
}

this.inner() 没有经过 Spring 代理，事务逻辑不会被织入。

  1. 对象不是 Spring 管理的 Bean。
  2. 方法可见性不符合代理方式要求。
  3. 异常被吞掉，代理层看不到失败。

六、必须使用正确的事务管理器

单数据源时通常只有一个 DataSourceTransactionManager。

多数据源时，每个数据源可能都有自己的事务管理器。如果没有指定清楚，事务可能只管理其中一个库：

@Transactional(transactionManager = "orderTransactionManager")
public void createOrder() {
}

如果一个方法里同时写订单库和用户库，而事务管理器只绑定订单库，那么用户库操作可能仍是自动提交。出现问题时，就会形成“一个回滚了，一个没回滚”的尴尬状态。

七、必须在同一个线程上下文

Spring 通常通过 ThreadLocal 绑定事务上下文。

事务方法里开新线程：

@Transactional
public void submit() {
    executor.execute(() -> mapper.insert(...));
}

新线程拿不到原线程绑定的连接，自然不在原事务里。

类似风险还包括：

  1. @Async
  2. 手动线程池
  3. 回调异步执行
  4. 手动从 DriverManager 新建连接

八、异常类型要触发回滚

Spring 默认对 RuntimeException 和 Error 回滚，对受检异常不回滚。

如果希望受检异常也回滚：

@Transactional(rollbackFor = Exception.class)
public void importData() throws Exception {
}

如果 catch 了异常却不抛出，Spring 会认为方法正常结束，于是提交事务：

@Transactional
public void save() {
    try {
        mapper.insert(...);
    } catch (Exception e) {
        log.error("save failed", e);
    }
}

这种写法很危险。要么重新抛出异常，要么手动标记回滚。

九、总结

事务边界可以按这个顺序判断：

  1. 是否同一个数据库连接。
  2. 是否同一个数据源和事务管理器。
  3. 是否同一个线程。
  4. 是否经过 Spring 代理。
  5. 异常是否能被事务管理器感知。

@Transactional 很有用，但它不是结界。连接、线程、代理、异常规则任何一个没对齐，事务都会露出边界。
