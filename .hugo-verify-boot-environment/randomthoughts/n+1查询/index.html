N+1 查询

December 11, 2025

面试时遇到过一个查询场景：查询用户列表，支持按用户名模糊匹配、按部门名称模糊匹配、按性别精确匹配。表结构大致是用户表 sys_user 和部门表 sys_dept，用户表里有 dept_id。

题目额外限制：

  • 不能使用 JOIN。
  • 不能引入额外依赖。
  • 只能使用 MyBatis-Plus 查询。

一开始很容易想到：先查用户分页，再遍历每个用户，根据 dept_id 查部门名称。写起来很顺，但这正是 N+1 查询。

什么是 N+1 查询

N+1 查询指的是：

1 次查询主表列表
N 次循环查询关联数据

例如用户列表查出 20 条记录，然后每个用户再查一次部门：

select * from sys_user limit 20;
select * from sys_dept where id = 1;
select * from sys_dept where id = 2;
select * from sys_dept where id = 3;
...

列表页越大，请求越多。并发一上来，数据库会被这种“看起来没什么”的代码持续消耗。它不是一下把系统打死，而是很有耐心地拖慢你。

最直接的解决：JOIN

如果允许 JOIN，一条 SQL 就能解决：

SELECT
    u.id,
    u.username,
    u.real_name,
    u.gender,
    d.name AS dept_name
FROM sys_user u
LEFT JOIN sys_dept d ON u.dept_id = d.id
WHERE u.username LIKE CONCAT('%', #{username}, '%')
  AND d.name LIKE CONCAT('%', #{deptName}, '%');

但面试题限制了不能 JOIN，所以要用批量查询和内存组装。

为什么有时不能 JOIN

不能 JOIN 不一定是面试官为难人。真实项目里确实可能遇到这些情况：

  • 分库分表后，两张表不在同一个库。
  • 数据来自不同服务或第三方接口。
  • 关联后产生大量重复行，分页和排序变复杂。
  • 主表和关联表数据量差异大，JOIN 计划不稳定。
  • 团队规范要求复杂查询拆分，降低 SQL 耦合。

所以，“不用 JOIN”不是让你写 N+1，而是让你换一种批量思路。

批量查询思路

比较稳的流程是：

1. 如果传了部门名称，先按部门名称模糊查询部门 ID。
2. 如果部门条件存在但没有命中部门，直接返回空分页。
3. 查询用户分页，条件里带上用户名、性别、部门 ID 集合。
4. 从用户分页结果里提取 dept_id。
5. 批量查询这些 dept_id 对应的部门。
6. 在内存中组装 VO。

关键点是：只查当前分页真正需要的部门，而不是把部门表全量加载到内存。

示例代码

public PageResult<SysUserVO> queryUsers(SysUserQuery query) {
    List<Long> matchedDeptIds = null;

    if (StringUtils.hasText(query.getDeptName())) {
        LambdaQueryWrapper<SysDept> deptWrapper = Wrappers.lambdaQuery(SysDept.class)
                .select(SysDept::getId)
                .like(SysDept::getName, query.getDeptName());

        matchedDeptIds = sysDeptMapper.selectList(deptWrapper)
                .stream()
                .map(SysDept::getId)
                .toList();

        if (matchedDeptIds.isEmpty()) {
            return PageResult.empty(query.getPageNo(), query.getPageSize());
        }
    }

    LambdaQueryWrapper<SysUser> userWrapper = Wrappers.lambdaQuery(SysUser.class)
            .like(StringUtils.hasText(query.getUsername()),
                    SysUser::getUsername,
                    query.getUsername())
            .eq(query.getGender() != null,
                    SysUser::getGender,
                    query.getGender())
            .in(matchedDeptIds != null,
                    SysUser::getDeptId,
                    matchedDeptIds)
            .orderByDesc(SysUser::getCreateDate);

    Page<SysUser> page = sysUserMapper.selectPage(
            Page.of(query.getPageNo(), query.getPageSize()),
            userWrapper
    );

    List<SysUser> users = page.getRecords();
    if (users.isEmpty()) {
        return PageResult.of(page.getTotal(), List.of());
    }

    Set<Long> deptIds = users.stream()
            .map(SysUser::getDeptId)
            .filter(Objects::nonNull)
            .collect(Collectors.toSet());

    Map<Long, String> deptNameMap = deptIds.isEmpty()
            ? Map.of()
            : sysDeptMapper.selectBatchIds(deptIds)
                    .stream()
                    .collect(Collectors.toMap(SysDept::getId, SysDept::getName));

    List<SysUserVO> records = users.stream()
            .map(user -> SysUserVO.builder()
                    .id(user.getId())
                    .username(user.getUsername())
                    .realName(user.getRealName())
                    .gender(user.getGender())
                    .deptName(deptNameMap.get(user.getDeptId()))
                    .build())
            .toList();

    return PageResult.of(page.getTotal(), records);
}

这段代码避免了两种极端：

  • 不会每个用户查一次部门。
  • 不会为了补部门名称全量加载部门表。

部门名称筛选的代价

如果按部门名称模糊查询命中了大量部门 ID，再把这些 ID 放进 IN 条件，也可能产生问题：

  • SQL 太长。
  • 优化器执行计划变差。
  • 网络传输和解析成本上升。

可以考虑限制部门名称查询结果数量：

if (matchedDeptIds.size() > 1000) {
    throw new BizException("部门匹配范围过大，请输入更精确的部门名称");
}

或者调整产品设计，使用部门树选择器，让用户选择明确部门，而不是对超大组织表做模糊匹配。

何时用缓存

部门这类数据通常变化不频繁，可以缓存：

  • 按 deptId -> deptName 缓存。
  • 部门更新时主动失效。
  • 列表查询时批量读取缓存，缺失再查库。

但缓存不能替代查询设计。缓存只是减轻压力，不是给 N+1 查询发免罪券。

小结

N+1 查询的问题不在于“多查几次”，而在于查询次数随着结果集线性增长。能 JOIN 就 JOIN；不能 JOIN，就先分页主数据，再批量查关联数据，最后内存组装。不要全量加载关联表，也不要在循环里查数据库。数据库不是用来替循环语句赎罪的。
