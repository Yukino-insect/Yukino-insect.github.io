多数据源配置

August 6, 2025

多数据源配置是指在同一个应用中配置多个 DataSource，并根据业务场景选择不同的数据源执行 SQL。

常见场景：

  • 读写分离：写主库，读从库。
  • 业务隔离：订单库、用户库、日志库分开。
  • 多租户：不同租户使用不同数据库。
  • 新旧系统迁移：一部分数据还在旧库。

它解决的是数据库访问路由问题，但也会带来事务、排查和一致性复杂度。不要因为“能配”就到处配，多数据源不是项目成熟的勋章。

数据库连接池

应用访问数据库时，不应该每次请求都创建和销毁 JDBC 连接。创建连接成本较高，也会增加数据库压力。

连接池会提前维护一批连接，请求使用完之后归还连接池。Java 中连接池的标准接口是 javax.sql.DataSource。

常见连接池：

  • HikariCP
  • Druid
  • Tomcat JDBC Pool

Spring Boot 默认常用 HikariCP。多数业务系统里，优先使用默认方案就够了，除非确实需要 Druid 的监控能力或公司已有统一规范。

AbstractRoutingDataSource

Spring 提供了 AbstractRoutingDataSource，用于在运行时动态选择数据源。

它的核心方法是：

protected abstract Object determineCurrentLookupKey();

Spring 获取连接时，会调用这个方法得到当前数据源 key，再从目标数据源 Map 中找到对应的 DataSource。

常见做法是把当前数据源标识放在 ThreadLocal：

public final class DataSourceContextHolder {

    private static final ThreadLocal<String> CONTEXT = new ThreadLocal<>();

    private DataSourceContextHolder() {
    }

    public static void set(String key) {
        CONTEXT.set(key);
    }

    public static String get() {
        return CONTEXT.get();
    }

    public static void clear() {
        CONTEXT.remove();
    }
}

使用 ThreadLocal 必须在 finally 中清理。线程池会复用线程，如果不清理，本次请求的数据源可能污染下一次请求。那种 bug 很安静，但很恶劣。

注解切换

实际项目中常用注解切换数据源，例如：

@DS("slave")
public List<User> listUsers() {
    return userMapper.selectList(null);
}

背后通常由 AOP 实现：

1. 方法执行前读取 @DS。
2. 把数据源 key 写入 ThreadLocal。
3. 执行业务方法。
4. finally 中清理 ThreadLocal。

dynamic-datasource-spring-boot-starter 就是常见方案之一。它比手写更完整，支持注解、嵌套切换、默认数据源等能力。

事务注意点

数据源切换最容易和事务打架。

如果事务已经开启，连接通常已经从某个数据源取出。此时再切换 ThreadLocal，并不一定会影响当前事务里的连接。

错误示例：

@Transactional
public void doSomething() {
    userService.writeMaster();
    reportService.readSlave();
}

如果 readSlave() 依赖注解切换数据源，但外层事务已经绑定了主库连接，那么它可能仍然走主库。

建议：

  • 明确事务边界，不在同一个本地事务里混用多个数据源。
  • 读写分离时，写后立刻读要考虑主从延迟。
  • 跨库写入不要假装一个 @Transactional 能全管住。
  • 真正跨库一致性要考虑分布式事务、消息最终一致性或补偿任务。

读写分离注意点

读写分离不是所有查询都走从库。

这些场景应优先走主库：

  • 写入后立刻查询。
  • 强一致性读，例如支付状态、库存扣减结果。
  • 后台审核、风控判断等关键流程。

可以走从库的场景：

  • 列表页。
  • 报表查询。
  • 非关键展示信息。
  • 可接受短暂延迟的数据。

主从延迟是读写分离绕不开的问题。用户刚修改头像，下一秒列表里还是旧头像，这不是玄学，是你读了从库。

小结

多数据源的核心是运行时路由：通过 AbstractRoutingDataSource、ThreadLocal 和 AOP 注解决定当前 SQL 走哪个库。使用时要重点关注 ThreadLocal 清理、事务开启时机、主从延迟和跨库一致性。能把这些边界想清楚，多数据源才是能力；想不清楚，它只是复杂度。
