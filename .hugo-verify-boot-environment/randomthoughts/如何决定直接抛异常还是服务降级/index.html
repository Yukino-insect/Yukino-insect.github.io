如何决定直接抛异常还是服务降级

March 5, 2026

一次调用失败后，到底应该抛异常、返回空结果，还是走服务降级？判断标准可以压缩成三句话：

  • 失败会导致业务结果不可信，就抛异常。
  • 失败只影响辅助体验，可以降级。
  • 降级必须可观测，不能静悄悄地伪装成成功。

用“调用 Elasticsearch 查询”这个场景看，会更直观。

该抛异常的情况

只要失败会影响主链路正确性，就应该抛出异常，或者包装成更明确的业务异常继续向上抛。

典型场景：

  • 搜索页核心列表依赖 ES，ES 失败就无法得到可信结果。
  • 权限判断、计费、库存、状态流转依赖这次调用。
  • 上层需要根据异常决定是否切换策略。
  • 当前方法没有足够上下文判断降级是否合理。

示例：

public List<Article> searchArticles(String keyword) {
    try {
        return elasticsearchClient.search(keyword);
    } catch (IOException | ElasticsearchException e) {
        log.error("ES search failed, keyword={}", keyword, e);
        throw new ExternalServiceException("搜索服务暂时不可用，请稍后重试", e);
    }
}

这类失败不应该被改写成空列表。空列表的语义是“查到了，确实没有”，而异常的语义是“没能得到可信结果”。把二者混在一起，数据会撒谎，而且撒得很自然。

可以降级的情况

如果某个能力只是增强体验，不影响核心结果，可以记录日志后返回降级结果。

典型场景：

  • 推荐列表、相似内容、热榜等辅助模块。
  • ES 只是加速查询，失败后可以回退 MySQL。
  • 页面允许某一块区域暂时为空。
  • 对外接口更重视可用性，但业务能接受精度下降。

示例：

public List<Article> recommendArticles(Long userId) {
    try {
        return elasticsearchClient.recommend(userId);
    } catch (IOException | ElasticsearchException e) {
        log.warn("ES recommend degraded, userId={}, reason={}", userId, e.toString());
        metrics.counter("es.recommend.degraded").increment();
        return Collections.emptyList();
    }
}

这里返回空列表是有前提的：推荐模块允许缺失，而且日志和指标能看出它不是“真的没有推荐内容”。

不要随手吞异常

最危险的写法是：

try {
    return doSearch();
} catch (Exception e) {
    log.error("search failed", e);
    return List.of();
}

问题在于：

  • 上层无法区分“没有数据”和“查询失败”。
  • 监控指标会被污染，业务侧会误判转化率、搜索命中率。
  • 调用方失去了补救机会。
  • 异常只剩日志，系统行为却显示“成功”。

如果确实要吞异常，至少给代码一个明确名字：

public List<Article> searchWithMysqlFallback(String keyword) {
    try {
        return elasticsearchClient.search(keyword);
    } catch (IOException | ElasticsearchException e) {
        log.warn("ES search failed, fallback to mysql, keyword={}", keyword, e);
        metrics.counter("es.search.fallback").increment();
        return articleMapper.searchByKeyword(keyword);
    }
}

fallback 写在方法名里，后来的人才不会以为这是正常查询。代码不是谜语，别让同事靠占卜维护系统。

决策表

问题 倾向
失败后结果是否会错误？ 抛异常
上层是否更适合决定策略？ 抛异常
当前能力是否只是辅助展示？ 降级
是否有可靠的备用数据源？ 降级
降级后用户是否会误解业务结果？ 抛异常或返回明确提示
是否已经有日志、指标、告警？ 没有就先补上

边界层的职责

Service 层更适合保留真实失败语义，Controller 或接口编排层更适合决定对用户返回什么。

例如：

  • Service 抛 ExternalServiceException。
  • ControllerAdvice 统一转换成错误响应。
  • 如果某个页面允许降级，由页面聚合服务捕获异常并填充默认模块。

这样做的好处是：底层不擅自替业务做决定，上层也能看到足够清晰的失败原因。

小结

“抛异常还是降级”不是代码风格问题，而是业务语义问题。强依赖就失败，弱依赖才降级；能降级也要留下日志、指标和告警。最糟糕的不是系统报错，而是系统明明错了，却装作什么都没发生。
