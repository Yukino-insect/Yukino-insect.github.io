组件通信、插槽与组合函数：把复杂页面拆得有秩序

August 19, 2026

Vue 项目变复杂，首先复杂在组件。一个页面里可能有筛选区、列表、卡片、弹窗、表单、分页、空状态、加载状态。如果全写在一个文件里，后续维护会很难。

组件化的目标不是把文件拆多，而是让职责变清楚。

这一篇从整体角度讲组件通信、插槽和组合函数。如果你刚开始接触 props、emits、defineProps、defineEmits，可以把《组件通信与 props emits：父组件怎样把数据交给子组件》 当作本篇的基础补充。那篇会把父子组件通信的每一行代码拆开讲，本篇则更偏向项目中如何取舍。

一、组件边界

适合拆组件的情况：

  • 模板超过一屏，阅读困难。
  • 某块 UI 有独立业务含义。
  • 需要复用。
  • 有明确输入和输出。
  • 内部状态可以独立管理。

不适合拆的情况：

  • 只有两三行简单结构。
  • 拆完后父子之间传参更复杂。
  • 组件没有独立语义，只是为了显得“工程化”。

抽象要服务维护，不要服务自我感动。

拆组件时可以先问一个问题：这块代码未来会因为什么原因而变化？

例如文章列表页里，搜索区可能因为筛选条件变化而改，文章卡片可能因为展示字段变化而改，分页可能因为加载策略变化而改。它们变化原因不同，就适合拆开。反过来，如果两个小片段总是一起变化，强行拆开只会增加传参成本。

组件边界通常由三件事决定：

  • 数据归属：谁拥有这份状态，谁负责修改。
  • 展示职责：这个组件主要负责展示结构，还是负责业务流程。
  • 变化原因：后续需求变化时，哪些代码应该一起改，哪些不应该一起改。

一个比较稳的拆分方式是：

页面组件：负责请求、组合状态、协调子组件
业务组件：负责某块业务 UI，例如文章卡片、评论列表
基础组件：负责通用结构，例如按钮、弹窗、空状态
组合函数：负责复用逻辑，例如分页、请求状态、事件监听

如果父组件开始把十几个 prop 传给一个子组件，或者子组件不断向外发很多事件，就要停下来检查：组件边界可能切错了。代码不会因为被拆进不同文件就自然变清楚，这一点很遗憾，但也很公平。

二、组件通信方式怎么选

Vue 组件通信方式很多，但不要把它们当作同等选项随便挑。可以按下面的顺序判断：

场景 推荐方式
父组件把数据交给直接子组件 props
子组件把用户行为通知父组件 emits
输入类组件需要双向绑定 v-model / defineModel
父组件决定子组件某块模板内容 插槽
子组件管理流程，父组件决定每项怎么渲染 作用域插槽
多层组件共享局部上下文 provide / inject
多页面共享登录、权限、缓存等状态 Pinia

最常见、也最应该优先掌握的是：

props down
events up

也就是数据向下传，事件向上传。父组件掌握状态，子组件表达用户做了什么。只要这个方向清楚，很多组件问题都会变得简单。

三、props

父组件向子组件传数据。

<PostCard
  :post="post"
  :show-actions="true"
/>

子组件：

type Props = {
  post: PostCard
  showActions?: boolean
}

withDefaults(defineProps<Props>(), {
  showActions: true
})

props 是只读的。子组件不应该直接修改父组件传进来的对象，除非团队明确约定并知道后果。

设计 props 时，不是把父组件里所有变量都倒给子组件。比较推荐的做法是：子组件需要什么，就传什么；子组件不该知道的业务细节，就不要传。

1. 拆开传还是整个对象传

两种写法都常见。

第一种是拆开传：

<PostCard
  :title="post.title"
  :summary="post.summary"
  :liked="post.liked"
/>

优点是组件依赖很明确。缺点是字段多时模板会比较长。

第二种是传整个对象：

<PostCard :post="post" />

优点是调用简洁，也方便后续增加展示字段。缺点是子组件可能逐渐依赖整个业务对象，边界变模糊。

一般可以这样判断：

  • 组件是业务组件，例如 PostCard，传 post 对象通常可以接受。
  • 组件是基础组件，例如 BaseButton、BaseDialog，props 应该尽量小而明确。
  • 如果子组件只用对象里的两三个字段，拆开传会更清楚。
  • 如果对象本身就是这个组件的核心语义，整体传入会更自然。

2. props 不负责表达动作

props 适合表达“当前状态是什么”，不适合表达“要做什么动作”。

推荐：

<PostCard
  :post="post"
  @like="handleLike"
/>

不推荐把函数当作普通 prop 到处传：

<PostCard
  :post="post"
  :on-like="handleLike"
/>

函数 prop 不是绝对不能用，但在 Vue 组件通信里，用户行为通常用 emits 更清楚。因为事件名表达的是“发生了什么”，父组件再决定“怎么处理”。

3. 用默认值降低调用成本

可选 prop 应该有明确默认值。

type Props = {
  title: string
  summary?: string
  showActions?: boolean
}

withDefaults(defineProps<Props>(), {
  summary: '',
  showActions: true
})

默认值不是为了偷懒，而是为了让组件在缺少非核心配置时仍然稳定。真正必需的数据，例如 title、id、post，不应该随便设默认值掩盖调用错误。

4. props 是只读边界

子组件不应该直接修改 props：

props.post.liked = true

尤其是对象和数组，虽然 JavaScript 层面可能改得动，但这样会让数据归属变混乱。更稳的写法是让子组件发事件：

emit('like', props.post.id)

父组件收到事件后修改真正的数据源。这样调试时只要顺着父组件找，就能知道状态在哪里改变。

四、emits

子组件通过事件通知父组件。

<PostCard
  :post="post"
  @like="handleLike"
/>

子组件：

const emit = defineEmits<{
  like: [postId: number]
}>()

function onLikeClick() {
  emit('like', props.post.id)
}

这样父组件仍然掌握业务决策权。子组件只负责表达用户行为。

事件名应该表达已经发生的用户意图，而不是父组件内部要执行的函数名。

推荐：

emit('submit', form)
emit('remove', id)
emit('select', option)
emit('refresh')

不推荐：

emit('callParentMethod')
emit('changeData')
emit('doSomething')

好的事件名让父组件模板读起来像业务流程：

<PostEditor
  @submit="savePost"
  @cancel="closeEditor"
/>

这表示编辑器告诉外部“用户提交了”“用户取消了”。至于保存接口、关闭弹窗、刷新列表，是父组件自己的决定。

1. 事件要不要带参数

如果父组件只关心“发生了”，事件可以不带参数：

const emit = defineEmits<{
  refresh: []
}>()

emit('refresh')

如果父组件需要知道“对谁发生了”，事件应该带上最小必要数据：

const emit = defineEmits<{
  like: [postId: number]
}>()

emit('like', props.post.id)

不要把整个内部状态都作为事件参数丢出去。事件参数越大，子组件和父组件的耦合越深。

2. emits 和 props 要配对理解

一个子组件通常像这样工作：

props：外部给我什么状态
emits：我向外报告什么行为

例如 PostCard：

props.post：当前文章是什么样
emit('like', post.id)：用户点击了点赞

它不负责请求接口，不负责修改列表，也不负责决定点赞失败怎么回滚。否则一个卡片组件就会开始拥有太多权力，组件当然不会拒绝权力，但维护者会付出代价。

五、v-model 组件

自定义组件也可以支持 v-model。

<SearchBox v-model="keyword" />

子组件：

const model = defineModel<string>({
  required: true
})

模板：

<input v-model="model">

v-model 适合输入类组件。对于复杂业务动作，仍然推荐明确事件名，如 submit、remove、refresh。

在 Vue 3.4 之后，defineModel 可以让自定义输入组件写得很简洁：

<script setup lang="ts">
const keyword = defineModel<string>({
  required: true
})
</script>

<template>
  <input v-model="keyword" />
</template>

父组件使用：

<SearchBox v-model="keyword" />

如果组件有多个可双向绑定的值，可以使用具名 v-model：

<RangeInput
  v-model:min="minPrice"
  v-model:max="maxPrice"
/>

子组件：

const min = defineModel<number>('min', {
  required: true
})

const max = defineModel<number>('max', {
  required: true
})

但不要因为 v-model 方便，就把所有状态都做成双向绑定。适合双向绑定的是输入值、开关值、选择值这类“控件状态”。保存、删除、刷新、提交这些业务动作，仍然应该使用明确事件。

六、插槽

插槽让父组件传入一段模板。

<BaseCard>
  <template #header>
    <h3>文章标题</h3>
  </template>

  <p>正文内容</p>
</BaseCard>

子组件：

<article class="card">
  <header>
    <slot name="header"></slot>
  </header>
  <main>
    <slot></slot>
  </main>
</article>

插槽适合封装布局骨架，让内容由调用方决定。

可以把插槽理解成：子组件提供结构，父组件提供内容。

比如 BaseCard 只关心卡片结构：

<template>
  <article class="card">
    <header v-if="$slots.header" class="card-header">
      <slot name="header"></slot>
    </header>

    <div class="card-body">
      <slot></slot>
    </div>

    <footer v-if="$slots.footer" class="card-footer">
      <slot name="footer"></slot>
    </footer>
  </article>
</template>

父组件决定每个区域放什么：

<BaseCard>
  <template #header>
    <h2>文章标题</h2>
  </template>

  <p>文章摘要内容</p>

  <template #footer>
    <button>查看详情</button>
  </template>
</BaseCard>

这里的边界很清楚：

  • BaseCard 负责外壳、间距、区域顺序。
  • 父组件负责标题、正文、按钮这些具体内容。

1. 默认插槽

没有名字的插槽叫默认插槽。

<BasePanel>
  <p>这里会进入默认插槽。</p>
</BasePanel>

子组件：

<section class="panel">
  <slot></slot>
</section>

2. 具名插槽

多个区域需要分别填充时，用具名插槽。

<BaseDialog>
  <template #title>
    删除文章
  </template>

  <p>删除后无法恢复。</p>

  <template #actions>
    <button>取消</button>
    <button>确认删除</button>
  </template>
</BaseDialog>

子组件：

<template>
  <section class="dialog">
    <h2>
      <slot name="title"></slot>
    </h2>

    <div>
      <slot></slot>
    </div>

    <footer>
      <slot name="actions"></slot>
    </footer>
  </section>
</template>

3. 后备内容

插槽可以有默认内容，也叫后备内容。

<button class="empty-action">
  <slot>返回列表</slot>
</button>

如果父组件没有传内容，就显示“返回列表”；如果传了内容，就显示父组件传入的内容。

<EmptyAction>重新搜索</EmptyAction>

4. 什么时候用插槽，什么时候用 props

如果只是传文本、数字、布尔值，用 props：

<EmptyView
  title="暂无文章"
  description="换个关键词再试试。"
/>

如果要传一段结构，用插槽：

<EmptyView>
  <template #action>
    <button @click="resetFilter">清空筛选</button>
  </template>
</EmptyView>

判断标准很简单：传的是数据，用 props；传的是模板，用插槽。不要为了显得高级，把两个字的标题也塞进插槽里。那不是灵活，是过度设计。

七、作用域插槽

子组件可以把数据传给插槽内容。

<DataList :items="posts">
  <template #default="{ item }">
    <PostCard :post="item" />
  </template>
</DataList>

子组件：

<template>
  <div>
    <slot
      v-for="item in items"
      :key="item.id"
      :item="item"
    ></slot>
  </div>
</template>

作用域插槽适合封装列表逻辑、表格列、弹窗内容等高级场景。

普通插槽是父组件把模板交给子组件；作用域插槽则多了一步：子组件把自己的数据暴露给父组件传入的模板。

这在列表组件里非常常见。子组件负责列表状态，父组件决定每一项怎么显示。

<DataList :items="posts">
  <template #default="{ item, index }">
    <PostCard
      :post="item"
      :rank="index + 1"
    />
  </template>
</DataList>

DataList 可以这样写：

<script setup lang="ts">
defineProps<{
  items: Array<{ id: number }>
}>()
</script>

<template>
  <section class="list">
    <slot
      v-for="(item, index) in items"
      :key="item.id"
      :item="item"
      :index="index"
    ></slot>
  </section>
</template>

这段代码表示：

DataList 负责循环和列表容器
父组件通过插槽决定每个 item 渲染成什么

表格列也是同样思路：

<UserTable :users="users">
  <template #role="{ user }">
    <RoleTag :role="user.role" />
  </template>

  <template #actions="{ user }">
    <button @click="editUser(user.id)">编辑</button>
  </template>
</UserTable>

子组件负责表格结构，父组件负责角色标签和操作按钮。这样比给 UserTable 塞进一堆 showEditButton、roleRenderType、onEdit 更清爽。

不过作用域插槽也有代价：父子组件的配合更复杂。只有当“结构可复用，但内容必须交给调用方决定”时，它才值得使用。

八、provide 与 inject

多层组件传递公共数据时，可以使用 provide 和 inject。

父级：

provide('theme', theme)

后代组件：

const theme = inject<Ref<string>>('theme')

它适合主题、表单上下文、局部组件树共享状态。不建议拿它替代 Pinia 做全局状态。

更严谨的写法是使用 InjectionKey，避免字符串 key 写错。

import type { InjectionKey, Ref } from 'vue'

export const themeKey: InjectionKey<Ref<string>> = Symbol('theme')

提供方：

provide(themeKey, theme)

使用方：

const theme = inject(themeKey)

if (!theme) {
  throw new Error('theme provider is missing')
}

如果注入的是可修改状态，最好把修改函数一起提供出去，而不是让后代组件随便改共享状态。

provide(formContextKey, {
  readonlyValues: readonly(values),
  updateField
})

这样后代组件可以读状态，也可以通过明确方法提交修改。状态的入口越清楚，调试时越不会像在雾里散步。

九、组合函数复用逻辑

当多个组件共享逻辑，而不是共享 UI，就用组合函数。

export function usePagination() {
  const page = ref(1)
  const pageSize = ref(20)

  function resetPage() {
    page.value = 1
  }

  return {
    page,
    pageSize,
    resetPage
  }
}

组合函数适合：

  • 分页。
  • 加载状态。
  • 弹窗开关。
  • 表单校验。
  • 请求状态。
  • 事件监听。

组合函数和普通工具函数不同。普通工具函数通常接收参数、返回计算结果；组合函数可以创建和返回响应式状态。

export function formatDate(date: Date) {
  return date.toLocaleDateString()
}

这是普通工具函数。

export function useDialog() {
  const open = ref(false)

  function show() {
    open.value = true
  }

  function hide() {
    open.value = false
  }

  return {
    open,
    show,
    hide
  }
}

这是组合函数，因为它拥有响应式状态，并且服务于组件逻辑。

1. 组合函数应该返回什么

返回值应该让调用方能完成一个完整小流程。

const {
  page,
  pageSize,
  finished,
  resetPage,
  nextPage
} = usePagination()

这比只返回一个 page 更有意义，因为分页逻辑不只是一个数字，还包括重置、下一页、是否结束等行为。

2. 组合函数可以接收外部参数

export function useSearch<T>(items: Ref<T[]>, getText: (item: T) => string) {
  const keyword = ref('')

  const matchedItems = computed(() => {
    const text = keyword.value.trim().toLowerCase()
    if (!text) {
      return items.value
    }

    return items.value.filter((item) => {
      return getText(item).toLowerCase().includes(text)
    })
  })

  return {
    keyword,
    matchedItems
  }
}

调用方：

const { keyword, matchedItems } = useSearch(posts, (post) => post.title)

这样组合函数只关心搜索逻辑，不关心文章对象具体长什么样。

3. 组合函数要清理副作用

如果组合函数里注册了事件监听、定时器、订阅，就要在组件卸载时清理。

import { onUnmounted } from 'vue'

export function useWindowSize() {
  const width = ref(window.innerWidth)
  const height = ref(window.innerHeight)

  function update() {
    width.value = window.innerWidth
    height.value = window.innerHeight
  }

  window.addEventListener('resize', update)

  onUnmounted(() => {
    window.removeEventListener('resize', update)
  })

  return {
    width,
    height
  }
}

有副作用却不清理，页面短时间内也许没事，时间一长就会出现重复监听、重复请求、状态错乱。这类问题很安静，但并不温柔。

十、组件设计检查清单

  • 组件是否有清晰职责？
  • props 是否足够少且语义明确？
  • emits 是否表达用户行为，而不是内部细节？
  • 插槽是否真的必要？
  • 状态属于当前组件还是父组件？
  • 组件是否依赖过多全局对象？
  • 是否为了复用 UI 拆组件，还是为了复用逻辑写组合函数？
  • 作用域插槽是否真的降低了重复，还是让调用关系更难读？
  • 多层共享状态是否只是局部上下文，而不是应该放进 Pinia 的全局状态？

十一、拆组件时的工程判断

组件拆分不是把一个文件切成几块，而是把“变化原因”隔离开。搜索框因为输入逻辑变化而改，文章卡片因为展示规则变化而改，分页因为加载策略变化而改。它们不应该互相牵连。若拆完之后每个组件都要知道所有业务细节，那只是把混乱搬了家。

十二、练习讲解：拆一个文章列表页

拆一个文章列表页：

PostListPage
 -> SearchBar
 -> PostList
 -> PostCard
 -> EmptyState
 -> LoadMoreButton

要求：

  • 搜索关键字由页面维护。
  • PostCard 只接收文章并发出点赞事件。
  • 空状态组件不依赖业务接口。
  • 分页逻辑放到组合函数。

这样拆完，页面才像页面，组件才像组件。

3. 创建 src/composables/usePagination.ts

import { computed, ref } from 'vue'

export function usePagination(pageSize = 3) {
  const page = ref(1)

  const offset = computed(() => {
    return (page.value - 1) * pageSize
  })

  function nextPage(total: number) {
    const maxPage = Math.ceil(total / pageSize)
    if (page.value < maxPage) {
      page.value++
    }
  }

  function resetPage() {
    page.value = 1
  }

  return {
    page,
    pageSize,
    offset,
    nextPage,
    resetPage
  }
}

这个组件用到了两个插槽：

  • 默认插槽：让父组件决定空状态文案。
  • action 插槽：让父组件决定是否展示操作按钮，以及按钮具体做什么。

EmptyState 不需要知道“清空搜索”这个业务动作，它只提供展示位置。页面知道当前搜索条件，所以按钮逻辑留在页面里。

<script setup lang="ts">
import { computed, ref, watch } from 'vue'
import EmptyState from './components/EmptyState.vue'
import LoadMoreButton from './components/LoadMoreButton.vue'
import PostList from './components/PostList.vue'
import SearchBar from './components/SearchBar.vue'
import { usePagination } from './composables/usePagination'
import type { Post } from './types'

const keyword = ref('')
const { page, pageSize, offset, nextPage, resetPage } = usePagination(3)

const posts = ref<Post[]>([
  { id: 1, title: '组件边界怎么判断', summary: '根据职责和变化原因拆分。', likes: 11, liked: false },
  { id: 2, title: 'props 和 emits 的职责', summary: '父传子数据，子通知父事件。', likes: 6, liked: false },
  { id: 3, title: '插槽适合封装什么', summary: '封装结构，把内容交给调用方。', likes: 4, liked: false },
  { id: 4, title: '组合函数不是工具函数', summary: '组合函数可以拥有响应式状态。', likes: 13, liked: true },
  { id: 5, title: '空状态组件如何设计', summary: '不依赖业务接口，只表达通用状态。', likes: 2, liked: false }
])

const matchedPosts = computed(() => {
  const text = keyword.value.trim().toLowerCase()
  if (!text) {
    return posts.value
  }
  return posts.value.filter((post) => post.title.toLowerCase().includes(text))
})

const visiblePosts = computed(() => {
  return matchedPosts.value.slice(0, offset.value + pageSize)
})

const finished = computed(() => {
  return visiblePosts.value.length >= matchedPosts.value.length
})

watch(keyword, () => {
  resetPage()
})

function handleLike(postId: number) {
  const post = posts.value.find((item) => item.id === postId)
  if (!post) {
    return
  }
  post.liked = !post.liked
  post.likes += post.liked ? 1 : -1
}
</script>

<template>
  <main class="page">
    <h1>文章列表页拆分练习</h1>
    <SearchBar v-model="keyword" @search="resetPage" />
    <EmptyState v-if="visiblePosts.length === 0">
      没有找到标题包含“{{ keyword }}”的文章。

      <template #action>
        <button class="text-button" @click="keyword = ''">清空搜索</button>
      </template>
    </EmptyState>
    <template v-else>
      <PostList :posts="visiblePosts" @like="handleLike" />
      <LoadMoreButton :disabled="finished" @load-more="nextPage(matchedPosts.length)" />
    </template>
  </main>
</template>
