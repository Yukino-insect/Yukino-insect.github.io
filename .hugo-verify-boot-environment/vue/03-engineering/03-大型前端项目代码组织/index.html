大型前端项目代码组织：目录分层、模块边界和可维护性

August 19, 2026

小项目靠直觉就能写，大项目靠结构活下来。随着页面变多、组件变多、接口变多，前端项目最容易失控的不是技术点，而是边界混乱。

这篇文章讨论大型 Vue 项目怎么组织代码。

一、目录不是装饰

目录结构表达的是职责边界。

src/
  app/
  pages/
  features/
  components/
  api/
  models/
  stores/
  composables/
  utils/
  styles/

一种可行解释：

  • app：应用启动、插件注册、全局配置。
  • pages：路由页面。
  • features：按业务模块组织的功能。
  • components：跨业务复用组件。
  • api：接口请求。
  • models：类型定义。
  • stores：全局状态。
  • composables：组合函数。
  • utils：纯工具函数。
  • styles：全局样式。

目录越多不代表越专业。关键是每个目录有明确职责。

二、按技术分层还是按业务分层

按技术分层：

components/
api/
stores/
models/

适合小到中型项目，简单直接。

按业务分层：

features/
  post/
    api.ts
    model.ts
    store.ts
    components/
  user/
    api.ts
    model.ts
    store.ts
    components/

适合业务模块多、团队多人协作的项目。

选择标准：

  • 页面少、业务简单：技术分层。
  • 模块多、边界清晰：业务分层。
  • 团队多人维护：业务分层更容易控制影响范围。

三、组件分类

组件可以分为：

类型 示例 特点
基础组件 Button、Modal、EmptyView 无业务或弱业务
业务组件 PostCard、UserProfile 和领域模型有关
页面组件 PostListPage 路由入口
布局组件 AppLayout、TabLayout 管整体结构

基础组件不要依赖业务 store。业务组件可以接收业务类型，但也要控制职责。

四、API 层边界

API 层负责和后端通信：

export function fetchPostDetail(id: number) {
  return request<PostDetail>(`/api/posts/${id}`)
}

API 层不应该直接操作组件状态，也不应该弹窗。它只负责请求和返回数据。

页面或 store 决定如何展示错误、是否跳转、是否缓存。

五、Store 边界

Store 适合管理跨页面共享状态。

不要把所有接口结果都塞进 Store。判断标准：

  • 多个页面需要吗？
  • 离开页面后还要保留吗？
  • 多个组件会修改吗？
  • 是否需要统一缓存或同步？

如果答案都是否，放页面里就可以。

六、组合函数边界

组合函数适合复用逻辑。

export function useDialog() {
  const visible = ref(false)

  function open() {
    visible.value = true
  }

  function close() {
    visible.value = false
  }

  return {
    visible,
    open,
    close
  }
}

组合函数不要变成万能对象。一个组合函数只解决一类问题。

七、工具函数边界

工具函数应该尽量纯。

export function formatCount(count: number) {
  if (count >= 10000) {
    return `${(count / 10000).toFixed(1)}w`
  }
  return String(count)
}

工具函数不应该偷偷读 store、改路由、发请求。否则它就不再是工具函数，而是披着工具函数外衣的业务逻辑。

八、样式组织

推荐分层：

styles/
  variables.css
  reset.css
  base.css
  utilities.css

组件样式写在组件内，主题变量和全局 reset 放全局。不要让全局样式随意覆盖组件内部结构。

九、命名规范

建议：

  • 组件使用 PascalCase：PostCard.vue。
  • 组合函数使用 use 开头：usePagination.ts。
  • API 函数使用动词：fetchPostPage、createPost。
  • 类型名称表达领域：PostCard、PostDetail、CreatePostRequest。
  • Store 使用领域名：useAuthStore、usePostStore。

命名不是小事。命名混乱时，项目会像没有路牌的城市。

十、重构信号

出现下面情况，说明该重构：

  • 一个页面文件超过数百行且包含多块独立 UI。
  • 组件 props 超过十几个。
  • 一个 store 同时管理多个领域。
  • API 调用散落在很多组件里。
  • 类型重复定义。
  • 相对路径层级太深。
  • 修改一个功能需要同时猜多个文件。

重构不等于推倒重来。多数时候，只要先拆清职责，就已经能改善很多。

十一、代码评审关注点

评审 Vue 代码时重点看：

  • 状态放置是否合理。
  • 组件输入输出是否清楚。
  • 接口错误是否处理。
  • 类型是否表达真实业务。
  • 是否有重复逻辑。
  • 是否破坏已有模块边界。
  • 是否能通过构建和类型检查。

这比单纯看缩进和分号更有价值。格式可以交给工具，边界要靠人判断。

十二、总结

大型前端项目的核心不是多会用 API，而是能维护边界：

  • 页面管流程。
  • 组件管展示。
  • Store 管共享状态。
  • API 管通信。
  • 组合函数管复用逻辑。
  • 工具函数管纯计算。
  • 类型管契约。
  • 构建工具管交付。

边界清楚，项目就算变大，也还可以被理解。边界混乱，项目很小也会令人疲惫。

十三、练习讲解：按 feature 组织文章模块

这个练习把文章模块按业务 feature 收拢。适合中大型项目：模块内部有自己的 API、类型、store、组合函数和组件，外部只通过明确出口使用它。这样修改文章模块时，影响范围会更可控。

7. 创建 src/features/post/store.ts

import { defineStore } from 'pinia'
import { ref } from 'vue'
import { fetchPostCards } from './api'
import type { PostCard } from './model'

export const usePostStore = defineStore('post', () => {
  const posts = ref<PostCard[]>([])
  const loading = ref(false)

  async function loadPosts() {
    loading.value = true
    try {
      posts.value = await fetchPostCards()
    } finally {
      loading.value = false
    }
  }

  return {
    posts,
    loading,
    loadPosts
  }
})

8. 创建 src/features/post/usePostSearch.ts

import { computed, type Ref } from 'vue'
import type { PostCard } from './model'

export function usePostSearch(posts: Ref<PostCard[]>, keyword: Ref<string>) {
  const matchedPosts = computed(() => {
    const text = keyword.value.trim().toLowerCase()
    if (!text) {
      return posts.value
    }

    return posts.value.filter((post) => {
      return post.title.toLowerCase().includes(text)
        || post.summary.toLowerCase().includes(text)
        || post.author.toLowerCase().includes(text)
    })
  })

  return {
    matchedPosts
  }
}

<script setup lang="ts">
import { storeToRefs } from 'pinia'
import { onMounted, ref } from 'vue'
import { PostCard, usePostSearch, usePostStore } from './features/post'

const keyword = ref('')
const postStore = usePostStore()
const { posts, loading } = storeToRefs(postStore)
const { matchedPosts } = usePostSearch(posts, keyword)

onMounted(() => {
  postStore.loadPosts()
})
</script>

<template>

    <h1>Feature 分层文章模块</h1>
    <input v-model="keyword" placeholder="搜索文章" />

    <section v-else class="list">
      <PostCard v-for="post in matchedPosts" :key="post.id" :post="post" />
    </section>
  </main>
</template>

13. 练习要点

  • features/post/index.ts 是模块出口，外部不需要知道模块内部文件怎么放。
  • shared/utils/delay.ts 不依赖文章业务，所以放在 shared。
  • usePostSearch 只处理搜索派生逻辑，不负责请求。
  • store.ts 负责跨组件共享的文章列表状态。

目录结构的价值不是显得专业，而是让修改路径变短、影响范围变小。工程上的美德大多如此，朴素，但很有效。
