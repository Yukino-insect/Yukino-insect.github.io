## 学习目标

- 理解 RAG 的基本定义和出现背景。
- 区分大模型自身知识、外部知识库和业务系统数据。
- 能画出 RAG 的离线入库链路与在线问答链路。
- 能判断一个场景是否真的需要 RAG。

## 为什么需要 RAG

大模型擅长语言理解、归纳和表达，但它并不天然拥有你的私有知识。模型训练完成后，参数里的知识相对固定；企业制度、产品手册、业务工单、接口文档和数据库记录却每天都在变化。直接把这些内容塞进 Prompt，轻则成本高、上下文超限，重则混入无关信息，答案更不稳定。

RAG 的思路是：不要指望模型记住所有事实，而是在回答前先把相关事实找出来，再交给模型组织答案。也就是说，知识不完全存放在模型参数里，而是存放在可更新、可追踪、可治理的外部知识系统里。

这也是 RAG 和“微调模型”的核心区别。微调更适合调整表达风格、任务格式或稳定行为模式；RAG 更适合注入高频变化、需要引用来源、需要权限隔离的知识。

## 两条核心链路

RAG 系统通常有两条主链路。

第一条是知识入库链路：

```text
文档上传 -> 对象存储 -> 文档解析 -> 文本清洗 -> Chunk 分块 -> Embedding -> 向量索引/元数据索引
```

第二条是在线问答链路：

```text
用户问题 -> 上下文记忆 -> 查询重写 -> 意图路由 -> 检索召回 -> 融合/Rerank -> Prompt 拼装 -> 模型生成
```

这两条链路之间通过 Chunk、向量、元数据、意图和引用来源连接起来。Ragent 的实现里，知识库侧会围绕文档、分块日志、解析配置和向量表组织数据；问答侧则把记忆、意图树、多通道检索和流式输出组合成一条在线 Pipeline。

## RAG 解决什么问题

RAG 主要解决四类问题。

第一是知识更新。新文档入库后，只需要重新解析、分块和建索引，不必重新训练大模型。

第二是事实可追踪。答案可以带上引用片段、文档名、Chunk 来源，方便用户核验，也方便系统排错。

第三是上下文可控。系统只把和当前问题高度相关的内容放进 Prompt，避免把整份文档都交给模型。

第四是权限和租户隔离。检索时可以按知识库、Collection、组织、角色和文档状态过滤，减少越权回答的风险。

## RAG 不解决什么问题

RAG 不是万能药。它不能保证模型永远不胡说，也不能替你修复质量低劣的原始文档。它只是把“知识从哪里来”这件事显式化，让系统有机会通过检索、排序、Prompt 约束和评测持续改进。

如果业务问题需要实时交易、强一致写入、精确计算或审批动作，RAG 只能提供解释和辅助信息，真正的执行仍然应该交给业务系统或工具调用。把所有问题都塞进知识库，是一种很省脑子的设计方式，也是一种很昂贵的事故制造方式。

## 适合 RAG 的场景

- 企业内部知识问答：制度、流程、产品手册、接口说明。
- 售前和客服辅助：基于知识库回答用户问题，并给出引用来源。
- 研发助手：检索设计文档、代码规范、排障记录。
- 合规和审计辅助：从文档中定位依据，帮助人工判断。
- 多文档综合问答：把分散材料组合成一份回答。

## 不适合直接用 RAG 的场景

- 必须返回数据库最新精确值的场景，例如账户余额、订单状态。
- 需要复杂计算和强校验的场景，例如报价、税费、库存扣减。
- 原始知识没有整理、互相矛盾且无人负责治理的场景。
- 对答案责任要求极高，但没有人工复核流程的场景。

这些场景并非完全不能用 AI，而是需要 RAG、工具调用、权限系统、审计和人工流程共同设计。

## 工程落点

判断一个 RAG 系统是否成熟，可以看五件事。

1. 入库是否可重复：同一文档重新处理后，状态、日志和索引能否稳定更新。
2. 检索是否可解释：每条候选结果来自哪个文档、哪个 Chunk、哪个通道。
3. Prompt 是否有边界：模型是否被明确要求基于证据回答，不知道就说明不足。
4. 输出是否可追踪：答案能否关联来源和一次请求的 Trace。
5. 评测是否闭环：每次优化是否能用数据说明变好还是变差。

## 小结

RAG 的本质是把外部知识接入大模型的回答过程。它不是一个单独算法，而是一套工程系统：知识生产、检索召回、排序过滤、Prompt 约束、模型生成和评测反馈缺一不可。理解这一点，后面谈 Chunk、向量库、Rerank、MCP 和流式输出时才不会迷路。
