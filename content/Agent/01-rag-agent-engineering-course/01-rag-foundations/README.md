RAG 的完整名称是 Retrieval-Augmented Generation，即检索增强生成。它的关键不在“检索”或“生成”这两个词本身，而在二者之间的分工：由检索系统提供可追溯的外部事实，由大模型负责理解问题、组织答案和生成自然语言。

本章先把 RAG 的基本链路拆清楚。后续章节会不断回到这些概念，所以这里请不要只记缩写。缩写背下来而链路没想明白，和把接口名背下来却不知道事务边界在哪里差不多，听起来努力，实际上危险。

## 学习目标

- 能解释 RAG 解决了大模型的哪些实际缺陷。
- 能画出“文档入库”和“用户问答”两条核心链路。
- 能区分解析、分块、Embedding、向量检索、Rerank、Prompt 拼装各自的职责。
- 能说清楚记忆、意图路由、MCP 和 SSE 为什么会出现在一个 RAG 系统里。
- 能从召回率、准确性、延迟和成本四个角度评估 RAG 方案。

## 一条主线

可以先把 RAG 想成两条流水线。

第一条是离线或准实时的知识生产线：原始文件进入系统，经过对象存储、文档解析、结构清洗、分块、Embedding 和索引写入，最终变成可检索的 Chunk。

第二条是在线问答链路：用户问题进入系统，经过历史记忆补全、查询重写、意图识别、检索召回、融合排序、Rerank、Prompt 拼装和流式生成，最终变成答案与引用来源。

这两条链路互相影响。入库质量差，再聪明的检索也只能在脏数据里挣扎；检索策略粗糙，再好的文档也到不了模型上下文；Prompt 没有限制，模型又会把不确定性包装成自信。RAG 工程的难点，就藏在这些接口之间。

## 本章检查清单

- 你能否不用“让模型更聪明”这类空话解释 RAG 的价值？
- 你能否说明 Chunk 过大和过小分别会造成什么问题？
- 你能否解释为什么多路检索结果不能直接按原始分数混排？
- 你能否说清楚 SSE 解决的是用户体验问题，而不是模型能力问题？
- 你能否指出一次坏回答可能来自入库、召回、排序、Prompt 或模型本身？
