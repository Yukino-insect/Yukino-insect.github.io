## 学习目标

- 理解为什么模型调用需要基础设施化。
- 掌握能力抽象、供应商客户端和路由服务的分层。
- 能设计模型配置、日志、指标和错误处理边界。
- 能避免业务代码直接依赖模型供应商。

## 为什么要单独做基础设施层

RAG 系统会使用多种模型能力：Chat 用于问答和重写，Embedding 用于向量化，Rerank 用于精排，VLM 可能用于图片或复杂文档理解。每种能力又可能接多个供应商。供应商之间的鉴权方式、请求字段、响应格式、错误码和流式协议并不完全一致。

如果业务层直接调用模型 API，代码会很快变成条件判断展览馆。今天加一个模型，明天改一个字段，后天处理一个供应商特有错误，所有业务链路都要跟着震动。这种设计看起来快，后面还债也很快。

基础设施层的目标是把变化收拢：业务层调用统一接口，基础设施层负责适配供应商、路由、熔断、重试、日志和指标。

## 分层模型

可以把模型基础设施分成四层。

第一层是能力接口，例如 `LLMService`、`EmbeddingService`、`RerankService`、`VlmService`。业务层只依赖这些接口。

第二层是路由服务，例如 `RoutingRerankService` 或 Chat 路由实现。它根据能力类型、模型档位、健康状态和配置选择候选模型。

第三层是供应商客户端，例如 OpenAI 风格客户端、百炼 Rerank 客户端、自定义 Rerank 客户端。它们负责把统一请求转换成供应商协议。

第四层是支撑组件，例如 `ModelSelector`、`ModelRoutingExecutor`、`ModelHealthStore`、SSE Parser、Token Counter 和日志脱敏工具。

## 配置驱动

模型配置不应硬编码在业务逻辑里。至少应配置：

- 模型 ID 和供应商。
- 支持能力：Chat、Embedding、Rerank、VLM。
- 档位或用途：快速、均衡、高质量。
- 超时时间。
- 最大重试次数。
- 熔断阈值和恢复窗口。
- API Key、Base URL 和模型名称。

配置驱动的价值在于：切换模型、调整优先级、临时下线供应商，都可以通过配置完成，而不是重新发布一堆业务代码。

## 错误分类

模型调用失败不能都当作同一种异常。至少要区分：

- 配置错误：Key 缺失、模型名错误、Base URL 错误。
- 客户端错误：请求参数不合法、上下文超长。
- 供应商限流：429 或配额不足。
- 网络错误：连接失败、读取超时。
- 服务端错误：5xx 或模型服务不可用。
- 协议错误：流式响应格式异常、JSON 解析失败。

不同错误对应不同策略。有些可以重试，有些应立即失败，有些要触发熔断，有些应该提示管理员检查配置。

## 可观测性

模型基础设施至少应记录：

- 请求使用的能力、供应商和模型。
- 首包耗时、总耗时和 Token 消耗。
- 成功率、失败率、超时率。
- 熔断状态变化。
- 路由选择原因。
- 异常类型和脱敏后的错误信息。

日志不能泄露用户隐私、Prompt 全文或 API Key。调试方便和安全边界之间需要取舍，不能把生产日志当私人笔记本。

## 与业务层的关系

业务层应该表达意图：我要生成答案、我要改写问题、我要生成向量、我要精排候选。基础设施层负责决定具体使用哪个模型。

这种边界让业务链路更稳定。例如问答流程不必知道当前 Rerank 是百炼还是自定义服务，只需要拿到排序后的 Chunk。未来增加新供应商时，只需要新增客户端并接入路由。

## 小结

AI 基础设施层的核心价值是隔离变化。模型供应商会变，参数会变，限流会变，协议也可能变；业务链路不应该跟着频繁改。把模型能力抽象、路由、健康状态和客户端适配做好，RAG 才能从 Demo 走向长期维护。
