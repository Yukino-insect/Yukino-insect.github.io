## 学习目标

- 能组织一次完整 RAG 评测运行。
- 掌握评测报告的基本结构。
- 能从失败样本中定位问题层级。
- 知道常见评测陷阱。

## 运行前准备

跑评测前要固定四件事：

- 代码版本。
- 知识库快照。
- 模型和 Prompt 配置。
- 评测数据集版本。

否则本次结果无法和上次比较。比如你以为 Rerank 提升了效果，实际可能只是知识库里新增了更好的文档。工程评测最怕变量偷偷增殖，像没关好的抽屉，拉开时什么都滚出来。

## 运行流程

一次评测运行可以按以下步骤执行：

```text
创建运行记录
  -> 遍历评测样本
  -> 调用完整问答 Pipeline
  -> 保存原问题、重写问题、意图、检索候选、Prompt、答案
  -> 计算检索指标、生成指标和系统指标
  -> 聚合统计
  -> 输出报告
```

建议不要只调用最终接口然后保存答案。中间过程越完整，失败分析越容易。

## 报告结构

一份有用的评测报告至少包含：

- 本次运行配置：代码版本、知识库版本、模型配置、Prompt 版本。
- 总览指标：样本数、成功数、失败数、平均分、P95 延迟。
- 检索指标：Recall@K、MRR、无召回样本。
- 生成指标：正确性、忠实度、引用支持、拒答质量。
- 成本指标：Token、模型调用次数、Rerank 次数。
- 分组指标：按业务域、问题类型、难度分组。
- 失败样本：问题、期望、实际、检索证据、错误归因。
- 改进建议：下一步应该改入库、检索、排序、Prompt 还是模型。

报告不是为了堆图表，而是为了让团队知道下一步该做什么。

## 失败归因

可以按下面方式定位失败：

如果黄金证据没有出现在候选里，问题在入库、Chunk、Embedding、过滤或召回通道。

如果黄金证据在候选里但排名很低，问题在融合、权重、Rerank 候选池或精排模型。

如果黄金证据进入 Prompt 但答案错，问题在 Prompt、模型理解、证据冲突或输出约束。

如果答案正确但没有引用，问题在引用元数据、上下文格式或后处理。

如果答案正确但太慢，问题在检索并发、Rerank、模型路由、首包或队列。

## 回归门禁

评测可以作为上线门禁。比如：

- 核心样本正确率不能下降。
- 高风险拒答样本不能变成编造答案。
- Recall@5 不能低于某个阈值。
- P95 首包不能超过预算。
- 失败率不能上升。

门禁阈值要结合业务风险设定。不要为了让流水线通过而把阈值调得毫无意义，那不叫自动化，那叫安慰自己。

## 常见陷阱

评测集泄漏到 Prompt 或样例中，会让结果虚高。

只评测单轮问题，会忽略多轮记忆和重写问题。

只保留成功样本，会让失败率被美化。

评测时使用和生产不同的模型配置，结果无法代表线上。

自动裁判模型和被评测模型相同，可能带来偏好偏差。

每次失败都立即改 Prompt，会掩盖检索和数据问题。

## 运营闭环

评测不是一次性活动。线上反馈应定期进入样本池，重点关注：

- 用户点踩的回答。
- 人工客服纠正的问题。
- 高流量问题。
- 高风险业务问题。
- 新增文档对应的问题。

每次迭代后，把失败样本归档并复测。时间久了，评测集就会成为系统经验的记忆。

## 小结

跑评测的关键是固定变量、记录过程、分层归因和形成门禁。好的报告不只是告诉你分数，而是告诉你哪里坏了、为什么坏、下一步改什么。RAG 优化需要证据，和 RAG 回答本身一样。
