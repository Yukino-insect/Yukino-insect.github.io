第一次运行 PaddleOCR 时，终端往往会提示下载模型；自己部署 rerank（重排序）模型时，也会看见下载仓库、缓存文件或指定本地目录。它们并不是在下载一段会“思考”的程序。更准确地说，你得到的是一套**训练完成后的数据文件**，其中最重要的是大量数字参数；运行库再用这些数字把固定的模型结构实例化，并在收到图片或文本后进行推理。

结论先说清楚：**PaddleOCR 与 rerank 的部署逻辑是同一类问题——代码负责如何计算，模型文件提供已经学到的参数，前后端负责把输入送到计算处、再把结果交还给用户。**差别在于 PaddleOCR 通常是一条由多个小模型组成的图像处理管线，而一个 cross-encoder rerank 服务通常加载 tokenizer 加一个文本模型。不要因为前者叫 OCR、后者被放进大模型项目，就把它们当成两种完全不同的东西；那只是名称制造的雾气而已。

## 先把“模型”拆成代码与数据

以一个极简线性层为例，程序定义了计算规则：

$$
y=xW+b
$$

这里 `x` 是输入，`W` 和 `b` 是参数。写出这条公式、实现矩阵乘法的 PyTorch 或 PaddlePaddle 代码，都还不是一个训练好的模型；只有训练数据反复调整 `W`、`b` 后，将它们保存下来，才得到可用于推理的 checkpoint（检查点）或 inference model（推理模型）。

因此一次“加载模型”实际做了四件事：

```text
模型目录 / 在线仓库
  -> 读取配置：层数、隐藏维度、词表大小、任务类型等
  -> 由运行库创建相同形状的网络结构
  -> 读取权重：将磁盘上的参数数字填入每一层
  -> 同时加载输入输出规则：tokenizer、标签、字符字典、预处理配置等
```

少了配置，程序未必知道应创建多少层、每层多宽；少了权重，创建出来只是随机初始化的空网络；少了 tokenizer 或字符字典，文本和识别结果就无法与模型中的整数 ID 正确对应。把 `model.safetensors` 单独复制出来，通常不足以构成一个可部署的模型目录。

### 权重为什么看起来像一堆无法阅读的文件

神经网络参数本质上是张量：不同形状的浮点数组。例如一个大小为 `[32000, 768]` 的词嵌入矩阵，就表示 32,000 个 token 各有 768 个浮点数。权重文件把成百上千个这类数组以二进制格式紧凑保存；它不包含自然语言知识库的原文，也不是 Python 源码。

文件为什么很大，原因也并不玄妙。若有 `N` 个 FP32 参数，单权重理论大小约为 $4N$ 字节；FP16/BF16 约为 $2N$ 字节。一个 1 亿参数、FP32 保存的模型，仅参数就约为 400 MB，还没有算配置、词表和运行时内存。推理时，框架还会把权重读入 CPU 内存或 GPU 显存，并产生输入张量和中间结果，所以“磁盘能放下”不等于“显存一定够”。

### 一个模型目录通常有哪些角色

文件名随框架、模型作者和版本变化，不能靠死记硬背；下表看的是职责。

| 角色 | 常见文件或形式 | 缺失时的典型后果 |
| ---- | -------------- | ---------------- |
| 模型结构配置 | `config.json`、YAML、推理配置 | 无法正确创建网络或任务头 |
| 权重参数 | `model.safetensors`、`pytorch_model.bin`、Paddle 推理权重 | 只有结构，没有训练结果 |
| 文本编码规则 | `tokenizer.json`、`vocab.txt`、`merges.txt` | 同一句话会被编码错，结果不可信 |
| OCR 字符字典 | `dict.txt`、字符表或语言配置 | 类别 ID 无法还原为正确文字 |
| 图像预处理/后处理配置 | 尺寸、归一化、阈值、标签等配置 | 图像尺度或输出解释错误 |
| 元数据 | 版本、许可证、README、哈希值 | 难以复现、审计和排查 |

Hugging Face 的 `from_pretrained()` 会按仓库或本地目录读取权重与配置；它也支持固定 `revision`、指定缓存目录和只读本地文件。可参阅其[模型加载文档](https://huggingface.co/docs/transformers/models)。PaddleOCR 当前文档同样允许把检测、识别等模块显式指向本地模型目录；这说明“自动下载”只是方便的默认行为，模型本体仍是本地可管理的文件。[PaddleOCR 的本地模型路径说明](https://paddlepaddle.github.io/PaddleOCR/main/en/version3.x/pipeline_usage/OCR.html)写得很明确。

## PaddleOCR 下载的究竟是什么

把“PaddleOCR”当成一个单一模型，是最常见也最容易造成误解的简化。一个常见 OCR 流程至少有两个职责不同的模块：

```text
原始图片 / PDF 页面
  -> 文本检测模型：哪里有文字？输出文本框
  -> 裁剪与方向校正：把每个文本框变成可读的小图
  -> 文本识别模型：框中的字符是什么？输出文字和置信度
  -> 后处理：按版面顺序组织结果
```

按场景还可能再有文档方向分类、文本行方向分类、版面分析、表格结构识别、公式识别等模块。每个模块的输入输出、网络结构和权重都不同，所以一次初始化可能下载**多个模型目录**，而不是一个名为“PaddleOCR”的巨型文件。关于检测、识别、版面与表格为何不能混为一谈，可先阅读[文档理解与 OCR 基础](../03-document-intelligence-ocr/01-document-understanding-and-ocr-basics.md)和[PaddleOCR、版面与结构化解析](../03-document-intelligence-ocr/02-paddleocr-layout-and-structure.md)。

### 自动下载、缓存与本地路径

开发阶段的代码通常只给出模型名。运行库据此找到默认来源，下载尚未命中的文件，并将它们放入缓存；下次加载命中同一版本的文件便不必重复联网。缓存是为了方便，不是可靠的生产发布方式：它的位置可能依赖当前用户、容器文件系统或环境变量，删除缓存后也会再次触发下载。

更可控的做法是将模型作为一个明确的部署资产准备好，并把各模块路径写进应用配置。下面是**配置关系示意**，字段名应以你正在使用的 PaddleOCR 版本文档为准：

```yaml
ocr:
  text_detection_model_dir: /opt/models/paddleocr/text_detection
  text_recognition_model_dir: /opt/models/paddleocr/text_recognition
  textline_orientation_model_dir: /opt/models/paddleocr/textline_orientation
```

这段配置表达的不是“把图片传到这几个目录”，而是“进程启动时从这些目录读取各模块的模型资产”。当前 PaddleOCR 文档中的参数名是 `text_detection_model_dir`、`text_recognition_model_dir` 等；不同主版本的初始化 API 和默认模型会变，生产代码应固定依赖版本并在升级前做回归测试。

## 自己部署 rerank 模型时，是否也是下载同一种东西

是，核心完全相同，不过输入和模型组合不同。以 cross-encoder rerank 为例，它不直接读取图片，也不负责生成回答；它接收一个 query 与多个 candidate 文本对，对每一对输出相关性分数，再按分数重新排序。

```text
query + candidates
  -> tokenizer：文字转 token ID、截断和补齐
  -> cross-encoder 权重：计算每个文本对的分数
  -> 排序代码：保留原下标，按 score 降序
  -> JSON 结果
```

一个 Transformers 风格的 rerank 目录常包含模型配置、权重和 tokenizer 文件。下面的代码刻意只从本地目录加载，目的是把“下载阶段”和“服务运行阶段”分开；`MODEL_DIR` 应是完整的模型目录，而不是只指向某一个权重文件。

```python
from pathlib import Path

from transformers import AutoModelForSequenceClassification, AutoTokenizer

MODEL_DIR = Path("/opt/models/bge-reranker-base")

tokenizer = AutoTokenizer.from_pretrained(
    MODEL_DIR,
    local_files_only=True,
)
model = AutoModelForSequenceClassification.from_pretrained(
    MODEL_DIR,
    local_files_only=True,
).eval()
```

预期行为是：目录完整时，进程不访问网络便能完成加载；目录不完整时，程序立即报出缺少配置、权重或 tokenizer 的错误。不要通过关闭 `local_files_only` 来“修复”生产故障——那只会把版本漂移、网络异常和启动变慢藏到下一次发布里。

PaddleOCR 的检测模型与识别模型，相当于 rerank 服务里的 tokenizer 与 cross-encoder 一样，都是某项计算不可替代的组成部分；它们的数量和格式不同，**代码 + 配置 + 权重 + 输入输出规则**这一部署结构却是一致的。

## 前端、后端与模型分别在什么位置

“使用了模型”不等于“前端或后端被模型取代”。前端、后端和模型按照职责协作：

```text
浏览器前端
  -> 上传图片，或提交 query 与候选列表
  -> 后端 API：鉴权、校验大小/长度、创建任务或同步调用
  -> 模型运行进程：加载 OCR / rerank 模型并执行推理
  -> 后端：保存结果、施加权限与业务规则、组织响应
  -> 前端：显示文字框、排序列表、进度或错误信息
```

对于小型项目，后端 API 与模型运行进程可以是同一个 Python 服务；这只是物理部署合并，职责并没有消失。对于耗时的 PDF OCR，后端通常先返回任务 ID，再由 worker 异步处理；对于一次只重排几十条候选的 rerank，API 在一个请求内同步返回往往更合理。选择同步还是异步由耗时、并发和用户体验决定，而不是由“这是不是大模型”决定。

### 不该交给模型的后端职责

模型分数和识别文本都可能错，因此以下事情仍应由确定性代码和数据库负责：

- 身份认证、租户隔离与权限判断；
- 文件类型、大小、页数、文本长度和候选数限制；
- 任务状态、重试、超时、幂等和审计记录；
- 库存、地域、合规、黑白名单等硬规则；
- 原文件、结果、模型版本及人工修正的保存与追溯。

例如 rerank 的 `score` 只适合同一个 query 内的相对排序，不能拿 `0.8` 当成“80% 正确”的授权依据；OCR 的高置信度也不等于身份证号、金额或药品剂量无需校验。模型负责概率性判断，后端负责不可含糊的边界。后者若让模型代劳，便是在把责任交给一枚骰子，只是骰子的外壳比较昂贵。

## 把“首次下载”变成可发布的部署流程

本地电脑上第一次运行时自动下载没有问题；真正部署时，建议将它改造成可重复的资产准备步骤。

### 第一步：在受控环境准备完整目录

下载时记录模型名称、来源、精确版本或 commit、运行库版本、文件清单和哈希。若模型有许可证或访问限制，也应在这一阶段确认，而不是等发布机器启动失败才发现。不要把访问令牌写进镜像、代码库或日志。

目录可按模型与版本组织：

```text
/opt/models/
  paddleocr-pp-ocrv5/
    text_detection/
    text_recognition/
    textline_orientation/
  bge-reranker-base/
    config.json
    model.safetensors
    tokenizer.json
    tokenizer_config.json
```

这只是便于理解的布局，实际目录应保持下载工具或框架所需的文件结构。尤其不要擅自把 tokenizer 文件挪进另一个模型目录：两个模型即使名字相近，也可能使用不同的词表和特殊 token。

### 第二步：在构建或发布阶段交付模型

常见交付方式有三种，选择取决于模型大小、网络条件与更新频率：

| 方式 | 适合情况 | 主要注意点 |
| ---- | -------- | ---------- |
| 镜像构建时复制模型 | 小模型、离线环境、版本强绑定 | 镜像会很大，更新模型需重建镜像 |
| 只读挂载模型卷/共享存储 | 多个服务副本共用同一版本 | 校验挂载完成，防止运行期被悄悄替换 |
| 发布前由制品流程拉取 | 模型较大、需要独立版本治理 | 使用固定 revision 和校验值，不能依赖 `main` |

无论选哪一种，服务启动后都应加载本地文件，并在健康检查或启动日志中记录**不含敏感信息的模型版本、设备和加载状态**。在隔离网络环境测试一次启动，能直接验证你的服务是否仍偷偷依赖外网缓存。

### 第三步：加载一次，按请求复用

模型权重通常很大。若把 `PaddleOCR()` 或 `from_pretrained()` 写进每个 HTTP 请求的处理函数，就会重复读磁盘、占用内存，甚至重复触发下载。正确的生命周期通常是：进程启动时加载模型，等待请求时只做预处理与推理，进程退出时由运行时回收资源。

```text
服务进程启动
  -> 校验本地模型目录和版本
  -> 初始化 tokenizer / OCR 管线 / 模型，并放到 CPU 或 GPU
  -> 标记 ready

每次请求
  -> 校验输入
  -> 预处理
  -> inference_mode 下推理
  -> 后处理并返回结构化结果
```

关于设备、精度、批处理和 OOM 的具体处理，可接着阅读[PyTorch 推理实践](03-pytorch-loading-device-and-precision.md)；关于把 rerank 包成输入边界明确的 HTTP 服务，可阅读[FastAPI 文本排序服务](04-fastapi-rerank-service.md)。

## 三个容易混淆的边界

### 下载模型不是训练模型

下载预训练权重是在复用别人已经训练好的参数；微调是在你的数据上继续修改参数；导出推理模型则是在训练后将权重和图结构整理成更适合部署的格式。三者都可能产生文件，但目的、成本和可复现要求不同。若只想使用 OCR 或 rerank，通常只需要下载并加载已发布的推理资产。

### 模型缓存不是知识库，也不是业务数据

OCR 模型不会因为你处理了十万张发票，就把每一张发票自动“记住”；rerank 模型也不会保存用户的每次查询来自动学习。模型缓存保存的是可复用的模型文件，业务原文与结果应由对象存储、数据库或搜索系统按权限和保留期单独管理。

### 本地部署不等于离线、私密或安全

只有当运行期没有外部下载、遥测或第三方 API 调用，并且模型、依赖、日志和输入输出都在你的受控边界内，才能讨论离线或数据不出域。即使模型在本机，若上传接口无鉴权、日志记录了原文、缓存目录可被其他用户读取，系统仍然不安全。

## 排查：看到下载或加载失败时应问什么

按下面的顺序检查，比反复删缓存或盲目重装更有效：

1. **它想下载哪个组件？**查看日志中的模型名、URL、文件名；PaddleOCR 要分辨是检测、识别还是附加模块。
2. **本地目录是否完整且匹配？**核对配置、权重与 tokenizer/字典是否来自同一模型版本；不要混用不同仓库的文件。
3. **加载器版本是否兼容？**模型仓库更新、PaddleOCR/PaddlePaddle 或 `transformers` 版本变化，都可能改变所需文件和参数名。
4. **资源是否足够？**磁盘空间只解决下载；加载后的 CPU 内存、GPU 显存、批量大小和最大输入长度决定是否能稳定推理。
5. **网络是否本来就不该出现？**生产环境若应离线，却发生联网请求，优先检查是否漏传本地路径、漏固定版本或缓存未被交付。

## 小结

- 下载的模型主要是训练后的权重参数，加上让运行库正确使用它们的配置、tokenizer/字典与预处理文件；它不是一段独立运行的应用程序。
- PaddleOCR 往往会为检测、识别、方向、版面等多个模块下载多组资产；rerank 常见的是 tokenizer 加一个文本打分模型。二者的部署本质相同。
- 前端负责交互与展示，后端负责边界、权限、任务和业务规则，模型进程负责概率性推理；小项目可以合并进程，但不能混淆职责。
- 将模型版本化地准备、交付为本地目录，并在启动时加载一次、请求时复用，才能让部署摆脱对临时网络和隐式缓存的依赖。
