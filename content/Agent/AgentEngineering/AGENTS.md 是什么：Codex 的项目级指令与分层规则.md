`AGENTS.md` 是提供给 Codex 的持久化项目指令文件。它把“如何在这个项目里工作”的共同约定放进仓库：构建命令、测试要求、目录边界、代码规范、评审关注点和需要确认的高风险动作，都可以写在这里。

它解决的不是某一次对话的目标，而是每次进入项目时都应成立的前提。官方文档明确说明，Codex 会在开始工作前读取 `AGENTS.md`，并将全局规则与项目内不同目录的规则组成一条指令链。完整规则见 [Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

## 一、它的核心作用

没有 `AGENTS.md` 时，团队成员需要在每次任务里重复说明“用什么包管理器”“测试怎么跑”“哪些目录不要碰”。有了它，这些规则可以随仓库提交、评审和演进。

适合写入：

- 项目启动、构建、测试、格式化和静态检查命令；
- 代码组织、命名、依赖与文档更新约定；
- 不可修改的目录、接口或安全规则；
- 对提交、部署、密钥、数据库迁移等动作的确认要求；
- 代码审查中必须检查的领域规则。

不适合写入：一次性任务的背景、会频繁变化的大段文档、只属于一项专项工作的完整流程，以及秘密信息。前两者应该放到 Prompt、文档或配置文件，专项流程应考虑 Skill；密钥则不该出现在版本库的 Markdown 中，事情不必弄得那么惊险。

## 二、Codex 怎样发现并合并指令

Codex 会按作用域读取指令：先是用户级全局文件，再从项目根目录一路走到当前工作目录。越靠近当前目录的指令越晚拼接，因此可以覆盖更上层的通用规则。

```text
~/.codex/AGENTS.md
        ↓
repository/AGENTS.md
        ↓
repository/services/payments/AGENTS.override.md
        ↓
当前目录中的最终约束
```

每一级目录中，`AGENTS.override.md` 的优先级高于 `AGENTS.md`；Codex 在同一目录只使用其中一个非空文件。官方默认还限制合并后的项目指令大小为 32 KiB，因此不应把它写成百科全书。大而杂的说明不会变得更权威，只会更难被遵守。

## 三、一个务实的仓库根目录示例

```markdown
# AGENTS.md

## 项目约定

- 使用 `pnpm` 管理前端依赖，不要同时生成其他锁文件。
- 修改 TypeScript 后运行 `pnpm lint` 和相关测试。
- 公共接口行为变化时，同步更新 `docs/`。

## 安全与发布

- 不要提交密钥、令牌或真实生产数据。
- 不执行部署、数据库迁移、提交或推送，除非用户明确要求。
- 新增生产依赖前，说明理由并等待确认。
```

这里的每一项都应该是稳定、可操作、团队认可的约定。避免“保持代码优雅”这种无法检验的要求；如果没有可观察的行为或例外条件，Codex 和人一样，都只能猜。

## 四、何时添加嵌套规则

单仓库中不同服务往往使用不同的测试入口或安全要求。这时应在专属子目录放置更具体的指令，而不是让根目录的文件膨胀。

```text
repository/
├── AGENTS.md
├── web/
│   └── AGENTS.md
└── services/
    └── payments/
        └── AGENTS.override.md
```

根目录写公共规则；`web/` 写前端工具链约定；`payments/` 写支付域的特殊测试和密钥限制。只有确实需要覆盖本目录默认规则时才使用 `AGENTS.override.md`，并在文件中说明覆盖原因，免得后来的人把“覆盖”误当成“补充”。

## 五、与其他概念的边界

| 概念 | 主要回答的问题 |
| --- | --- |
| Prompt | 这次任务要完成什么？ |
| `AGENTS.md` | 在这个项目或目录中，始终应如何工作？ |
| Skill | 某项可复用的专项任务应按什么流程完成？ |
| MCP | 能连接和调用哪些外部工具、数据或服务？ |
| Plugin | 如何把 Skills、MCP 连接和相关资源打包分发？ |

`AGENTS.md` 是基础规则层，不应抢走 Skill 的专项流程职责，也不能替代工具权限。它能告知 Codex“不要部署”，但实际能否部署仍由环境权限、审批配置和工具本身决定。

## 六、维护建议

- 保持短小、命令化、可验证；将长背景文档链接出去。
- 把规则放在最接近其适用代码的位置，避免无关模块被误约束。
- 把安全边界和测试命令写清楚，别假定“大家都知道”。
- 修改规则后，使用一个小任务确认 Codex 实际加载了哪些指令来源。
- 将它与代码一起评审：规则本身也是工程行为的一部分。

一个好的 `AGENTS.md` 不会替团队做决定，但会把本不该每次重新讨论的事情提前说清。项目越复杂，这种克制的共同语言越重要。
