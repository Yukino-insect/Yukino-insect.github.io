当你反复要求 Codex「按团队格式写变更说明」「排查 CI 时先看某几份日志」「生成文章后再跑一遍校验」时，真正需要的通常不是更长的聊天记录，而是一份能被反复发现和执行的工作说明。**Skill** 正是为这类需求准备的：它把一项明确任务所需的指令、资料和可选脚本封装起来，让 Codex 在合适的时候使用。

可以把它先理解为给 Agent 准备的“小型操作手册”。不过，手册不等于魔法。Skill 能让流程更一致、知识更靠近项目，却不会自动获得权限、也不会替你判断一段脚本是否安全。把两者混为一谈，往往就是问题开始变得不那么优雅的时刻。

本文以 Codex 中的 Agent Skills 为对象。有关能力范围、目录规则和命令的表述，以 OpenAI 官方文档 [Build skills](https://learn.chatgpt.com/docs/build-skills) 为准；产品会持续演进，实际可用项应以你的 Codex 界面和版本为准。

## 一、Skill 到底是什么

一个 Agent Skill 是一个**目录**，其中必须有名为 `SKILL.md` 的说明文件；目录还可以带上脚本、参考资料、模板和展示元数据。Codex 会先看到每个 Skill 的名称、简介和路径；当任务与它相关，或者用户明确点名它时，再读取该 Skill 完整的 `SKILL.md`。

这种“先看摘要、按需展开”的机制叫作**渐进披露**（progressive disclosure）。它避免每一轮对话都把全部流程细节塞进上下文，也让一个项目可以积累多项工作流，而不是让总提示词无限膨胀。

最小结构如下：

```text
release-note-checker/
└── SKILL.md
```

稍完整一些时则可能是：

```text
release-note-checker/
├── SKILL.md                 # 必需：元数据和执行说明
├── scripts/                 # 可选：确定性脚本
├── references/              # 可选：规范、接口文档、示例
├── assets/                  # 可选：模板、图标等资源
└── agents/
    └── openai.yaml          # 可选：界面和依赖声明
```

官方文档要求 `SKILL.md` 的 YAML front matter 至少有 `name` 与 `description`。其中 `description` 不只是展示文案，也是 Codex 判断是否应该自动使用该 Skill 的重要线索。

## 二、它和 Prompt、AGENTS.md、MCP、Plugin 有什么不同

这些概念常常一起出现，却处在不同层次。把职责分开理解，才不至于见到任何 Markdown 文件都叫它“Agent 配置”。

| 概念 | 解决的问题 | 适合放什么 | 不适合承担什么 |
| --- | --- | --- | --- |
| Prompt | 当前这一次对话想让模型做什么 | 临时目标、上下文、验收要求 | 可复用且很长的固定流程 |
| `AGENTS.md` | 这个仓库或目录长期遵守什么规则 | 构建命令、代码风格、目录约定、禁止事项 | 某一种专门任务的完整操作教程 |
| Skill | 某项可复用任务应如何完成 | 步骤、参考资料、模板、可选脚本 | 全项目无差别生效的通用规则 |
| MCP | Agent 如何连接外部工具与数据 | 工具、资源、鉴权后的服务连接 | 任务决策和流程说明 |
| Plugin | 如何把一个或多个 Skills 与连接器打包分发 | 可安装的共享能力包 | 取代 Skill 的具体内容 |

一句话概括：`AGENTS.md` 像项目公约，Skill 像岗位操作规程，MCP 像接入外部系统的标准接口，Plugin 则像可分发的软件包。它们可以协作，但不是彼此的替身。

例如，“所有提交前必须运行测试”适合写进 `AGENTS.md`；“修复 GitHub Actions 失败时，怎样收集日志、定位失败阶段、产出修复报告”适合做成 Skill；“读取 CI 平台日志”可能由 MCP Server 提供。只有这样分工，维护者才不会在三处同时修改同一条规则。

## 三、Codex 如何发现 Skill

在本地开发中，Codex 会从不同作用域发现 Skills。对仓库而言，它会从**启动 Codex 的当前工作目录**一路向上扫描到 Git 仓库根目录中的 `.agents/skills`；也会读取用户、管理员和系统级位置。官方列出的典型位置如下。

| 作用域 | 位置 | 适用场景 |
| --- | --- | --- |
| 仓库 / 子目录 | `$CWD/.agents/skills` | 只适用于当前模块的流程 |
| 仓库 / 父目录 | 当前目录上级的 `.agents/skills` | 被多个相邻模块共享的流程 |
| 仓库根目录 | `$REPO_ROOT/.agents/skills` | 团队共同遵守的仓库级流程 |
| 用户 | `$HOME/.agents/skills` | 个人在多个项目间复用的习惯和工具流程 |
| 管理员 | `/etc/codex/skills` | 共享机器或受管环境的统一能力 |
| 系统 | 由 Codex 随附 | 例如 Skill 创建、安装等通用能力 |

因此，一个最适合被版本控制、也最容易被团队复用的仓库级目录通常是：

```text
your-repository/
└── .agents/
    └── skills/
        └── release-note-checker/
            └── SKILL.md
```

这里有两个容易被忽略的细节：

- 扫描起点是你启动 Codex 时的工作目录，不是随便某个绝对路径；在大型单仓库中，这会影响哪些 Skill 被发现。
- 同名 Skill 不会被合并成一份。为了让选择器和自动匹配不产生歧义，团队应使用稳定、具体的名称，例如 `github-ci-triage`，而不是宽泛的 `helper`。

Codex 会自动侦测 Skill 的改动；如果界面里没有出现更新，官方建议重启 Codex。符号链接的 Skill 目录也可以被发现，但应确保链接目标可信且在团队约定的维护范围内。

## 四、Codex 如何触发和使用 Skill

Codex 使用 Skill 有两条路径。

### 1. 显式调用：你明确指定要用哪个 Skill

在 Codex CLI 或 IDE 扩展中，可以先通过 `/skills` 查看可用项，再在提示中用 `$` 点名一个 Skill：

```text
$release-note-checker 为这次改动生成发布说明，并先执行其中的校验步骤。
```

显式调用适合三种情况：你知道该用哪项能力；任务和多个 Skill 都有一点关系、需要明确优先级；或者你不希望 Codex 根据描述自行猜测。它也使协作记录更清楚——别人能知道这次并非临时编了一套流程。

### 2. 隐式调用：任务匹配时由 Codex 选择

当用户任务与 `description` 的范围相符时，Codex 可以自行选择并使用对应 Skill。例如一个描述为“排查 GitHub Actions 失败；读取日志、定位失败步骤并给出最小修复方案；不负责修改业务需求”的 Skill，遇到“CI 红了，帮我定位”就有较高的匹配度。

这也是为什么描述应当短而具体，并且把**触发词、核心任务和边界**放在前面。不要写成“一个有用的开发助手”。那种描述几乎等于什么也没说，只会迫使模型在含糊中作出选择。

如果某个 Skill 涉及高风险操作、只想在人工明确确认后使用，可以在 `agents/openai.yaml` 中设置：

```yaml
policy:
  allow_implicit_invocation: false
```

这样它仍能通过 `$skill-name` 显式调用，但不会因任务相似而自动触发。

## 五、从零创建一个 Skill

创建 Skill 的关键不在于先写很多话，而在于先把任务边界说清楚。一个好的 Skill 只解决一个足够明确的工作：例如“根据仓库约定生成发布说明”，而不是“负责所有 Git 相关工作”。

### 1. 先写清楚输入、输出和停止条件

在新建目录前，先回答下面四个问题：

1. 它在什么任务出现时触发，什么情况**不**应触发？
2. 它需要哪些输入，例如 Git diff、版本号、日志或模板？
3. 它应输出什么可检查的结果，例如 Markdown 报告、JSON、补丁或待确认问题？
4. 哪些动作必须停止并向用户确认，例如发布、删除数据、发送消息、提交代码？

如果这四个问题回答不清楚，直接让模型“照着流程做”只会把不确定性包装得更像自动化。先缩小任务，往往比增加提示词更有效。

### 2. 创建最小的 `SKILL.md`

下面是一个可放在 `.agents/skills/release-note-checker/SKILL.md` 的指令型示例。它不需要脚本，因为这里最重要的是判断和写作；脚本只应在必须获得确定性行为时加入。

```markdown
---
name: release-note-checker
description: 根据 Git diff 生成并校验中文发布说明。仅在用户要求发布说明、变更摘要或版本公告时使用；不执行发布、提交或推送。
---

# 发布说明校验流程

1. 读取当前工作区的 Git diff 和用户提供的版本背景。
2. 将变更按“新增、修复、兼容性影响、运维事项”归类；没有证据的内容不要猜测。
3. 使用 `references/release-note-template.md` 中的模板生成中文 Markdown。
4. 在结尾列出尚不能确认的风险和需要产品或发布负责人确认的项目。
5. 不执行发布、提交、推送、打标签或调用外部通知工具。
```

这个例子里的 `name` 适合使用小写字母、数字与连字符，便于在 `$release-note-checker` 中引用。`description` 则同时明确了“何时使用”“产出是什么”“不做什么”。正文应使用可执行的动词，写明先后顺序、输入来源和输出要求，而不是留下“尽量做好”一类无法验收的句子。

### 3. 需要时再添加资料和脚本

Skill 的内容应按需拆分，而不是把几十页文档塞进 `SKILL.md`。

- `references/`：放长规范、字段字典、API 约定和模板说明。在主流程中注明何时读取哪一个文件。
- `assets/`：放需要复用的模板、图片、样例文件等非代码资源。
- `scripts/`：放格式校验、生成器、解析器等需要稳定重复执行的程序。脚本应接受明确输入、输出可检查结果，并在失败时给出可理解的错误。
- `agents/openai.yaml`：放显示名、简短介绍、默认提示词、图标和工具依赖等可选信息；不要把核心工作流藏在这里。

官方建议优先使用指令，而非脚本；只有确定性、外部工具调用或大量重复计算确有必要时，再引入脚本。这既减少维护成本，也让 Skill 的真实行为更容易审查。

### 4. 使用内置创建器

如果不想手写骨架，Codex 提供了 Skill Creator。可在 Codex 中输入：

```text
$skill-creator
```

它会询问 Skill 做什么、何时触发，以及应当只包含指令还是加入脚本。若一个流程“做一遍比描述一遍更清楚”，也可以使用官方提供的 Record & Replay 功能录制示范，再把流程整理成可复用 Skill。无论通过哪种方式创建，最终仍应人工审阅 `SKILL.md` 和任何被引入的脚本。

## 六、安装、禁用与分发

### 安装已有 Skill

对于官方或其他仓库中经过审核的 Skills，可以调用内置安装器。例如安装 `linear`：

```text
$skill-installer linear
```

安装器也可以用于从其他仓库下载 Skill。这里最重要的前提并不浪漫：**把 Skill 当作要审查的工作流和代码，而不是无害的提示词片段。** 尤其当它包含 `scripts/`、外部工具依赖、网络访问或会读取工作区文件时，应先检查来源、完整指令、脚本行为、所需权限和实际写入位置。

### 临时禁用，不必删除

官方文档给出了在 `~/.codex/config.toml` 中禁用单项本地 Skill 的方式：

```toml
[[skills.config]]
path = "/path/to/skill/SKILL.md"
enabled = false
```

修改配置后需要重启 Codex。禁用是可逆的，适合处理暂时失效、存在冲突或正处于审查中的 Skill；不要为了“清理一下”就直接删除团队正在使用的流程资产。

### 何时应使用 Plugin

直接放置 Skill 目录适合本地编写和仓库内协作。如果要跨项目分发、多项 Skill 打包，或将 Skill 与 MCP 连接器一起交付，应使用 Plugin。一个 Plugin 可以包含一个或多个 Skills，也可附带已注册的 MCP Server 连接或相关配置。

可以按下面的标准判断：

| 需求 | 更合适的方式 |
| --- | --- |
| 只为当前仓库服务，想随代码一起评审和提交 | `.agents/skills/` 中的仓库级 Skill |
| 个人在多个仓库里都要使用 | 用户级 Skill |
| 需要让其他团队方便安装、版本化复用 | Plugin |
| 除流程说明外还需要连接 GitHub、工单、数据库等外部系统 | Skill + MCP；需要分发时再打包为 Plugin |

## 七、让 Skill 真正可靠的写法

Skill 的质量取决于可执行性，而不是文采。下面这些原则比“写得很长”更有用。

### 聚焦一个工作

“根据 PR diff 写发布说明”和“修复 CI、打版本、通知群组”是不同工作，应该拆开。每项 Skill 的触发条件越清晰，自动匹配越可靠，权限和验收也越容易控制。

### 明确输入与证据边界

指明应查看哪些文件、命令输出或用户输入；对缺失信息应提问或标注未知，不可把猜测写成事实。特别是变更说明、迁移方案和安全报告，错误的确定性比坦诚的不确定性更危险。

### 用可验收的输出替代模糊要求

不要只写“给出高质量报告”。可以写成“输出包含摘要、影响范围、验证结果、回滚建议四个二级标题；不确定项单列为待确认”。这样用户和模型都知道完成的标准。

### 将安全边界写进流程

若 Skill 可能涉及删除、部署、提交、发消息、读取敏感资料或调用付费服务，必须写清：哪些步骤只做检查，哪些需要用户确认，哪些操作永远不执行。Skill 是指令和资源的载体，不是权限模型；实际权限仍取决于 Codex 所处环境、工具配置和审批策略。

### 以真实提示测试触发效果

至少准备三类测试：应触发的提示、相近但不应触发的提示、同时匹配多个 Skill 的提示。检查它是否被恰当地发现，是否读取了必要资料，是否严格遵守“不做什么”，以及输出能否由人复核。官方同样建议以测试提示验证 `description` 的触发行为。

## 八、一个实用的落地流程

如果你准备在团队项目里引入 Skills，可以按这条短路线开始：

```text
观察重复任务
-> 选一个低风险、高频、边界明确的任务
-> 写最小 SKILL.md
-> 用真实任务测试显式和隐式触发
-> 补充 references 或 scripts
-> 代码评审与版本控制
-> 必要时打包为 Plugin
```

建议优先挑选“生成变更摘要”“按团队模板创建文档”“排查固定类型的构建错误”“检查配置完整性”这类低风险任务。它们能较快验证流程是否有价值。等目录、命名、审查与权限边界形成习惯后，再处理部署、跨系统操作等更敏感的自动化工作。

## 九、常见误解

### Skill 是不是一个更高级的 Prompt？

它包含 Prompt 式指令，但不止于此。Skill 是可发现、可触发、可带资料和脚本、可被版本控制和分发的任务包。一次性 Prompt 仍适合临时工作；只有重复且稳定的流程才值得沉淀为 Skill。

### 写了 `SKILL.md` 就一定会自动触发吗？

不一定。自动触发依赖任务与 `description` 的匹配，并受到已发现 Skill 数量、描述质量和环境配置影响。需要确定行为时，使用 `$skill-name` 显式调用；不要把关键业务流程建立在“模型大概会猜对”的期待上。

### Skill 能否代替 MCP？

不能。Skill 告诉 Codex“如何完成一项任务”；MCP 提供“能够调用哪些外部能力”。一个分析工单的 Skill 可以指导检索、归类和输出报告，而具体读取工单或创建任务的能力仍可能来自 MCP。

### 每个项目都应该有很多 Skill 吗？

不应该。安装太多、描述太相似的 Skill 会增加选择成本，还可能挤占初始技能列表的上下文预算。先维护少量、边界清晰且确实高频的 Skills，定期删除或禁用失效项，比把任何经验都立刻封装更可持续。

## 十、总结

Skill 的价值不在于让 Codex“多一个命令”，而在于把已经验证过的工作方法变成可复用的工程资产。

- Skill 是以 `SKILL.md` 为核心的任务目录，可以附带资料、模板和脚本。
- Codex 会发现不同作用域的 Skills，并通过 `$skill-name` 显式调用或根据描述隐式选择。
- 创建时先定义触发范围、输入、输出和停止条件；描述要具体，正文要可执行。
- `AGENTS.md` 管通用项目规则，Skill 管专项工作流，MCP 管外部能力连接，Plugin 管分发。
- 安装和编写 Skills 都应遵循最小权限、人工审查和可验证输出的原则。

当重复劳动开始有稳定边界时，就值得把它写成 Skill。至于把所有习惯、偏好和偶发操作都塞进去——那不是工程化，充其量只是把混乱保存成了 Markdown。
