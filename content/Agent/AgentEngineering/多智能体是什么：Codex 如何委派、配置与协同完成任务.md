多智能体（Multi-Agent）并不是让同一个 Agent 把同一句话说很多遍，而是让一个**主 Agent** 把可独立推进的子任务委派给多个**子智能体**（subagents），并在它们完成后汇总结果、作出最终判断。在 Codex 中，这种机制通常被称为**子智能体工作流**（subagent workflow）。

它最适合代码库探索、PR 审查、日志分析、测试缺口排查、资料核对等可并行的复杂任务。主线程保留需求、约束、决策和最终交付；子线程处理大量中间搜索、命令输出与局部推理，只把经过整理的结论带回。这样做的目的不是制造热闹，而是减少主对话被杂讯淹没的概率。

本文针对 Codex 的本地客户端（桌面应用、CLI、IDE 扩展）说明。行为与配置依据 OpenAI 官方的 [Subagents 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)；具体可用模型、界面和账户能力仍应以当前安装版本为准。

## 一、先分清几个名词

| 名词 | 含义 | 在协作中的职责 |
| --- | --- | --- |
| 主 Agent | 接收用户任务的主线程 | 拆分任务、委派、汇总、作最终决策与交付 |
| 子智能体 | 被主 Agent 启动的专门 Agent | 完成一个有边界的子任务，返回结果摘要 |
| Agent thread | 子智能体运行的独立线程 | 承载搜索、工具调用、日志和中间推理 |
| 子智能体工作流 | 多个子智能体并行后由主 Agent 汇总的过程 | 协调分工、等待、追问和收口 |

可以把它理解为一次小型的工程协作：主 Agent 是负责人，子智能体是各自有明确产出的执行者。但它们不是彼此完全隔离的“虚拟团队”。它们仍处在同一任务授权和环境约束之下，最终责任也不会因为分工而凭空消失。

```text
用户目标
   │
   ▼
主 Agent：拆解、约束、汇总
   ├── 子智能体 A：探索代码路径
   ├── 子智能体 B：运行或检查测试
   ├── 子智能体 C：审查安全与边界
   └── 子智能体 D：核对外部文档
   │
   ▼
主 Agent：合并证据、解决冲突、交付结论
```

## 二、它解决的核心问题

即使上下文窗口很大，主对话也不适合长期堆积无关细节：数百条搜索命中、冗长测试日志、失败堆栈和试错记录会掩埋真正的需求。这常被称为**上下文污染**（context pollution）或**上下文退化**（context rot）。

子智能体将这类噪声留在各自线程中，再返回文件引用、验证结果、风险等级和简短结论。于是主线程能够持续聚焦：

- 用户真正要解决的问题是什么；
- 方案之间有什么冲突与取舍；
- 哪些结论有证据，哪些仍需确认；
- 最终应改什么、验证什么、向用户说明什么。

并行也可能缩短墙钟时间。例如，安全审查、测试缺口检查和依赖文档核对互不依赖时，没有理由让它们排队等待。不过每个子智能体都会进行自己的模型和工具调用，token、时间和工具开销并不会神奇地消失。

## 三、什么时候值得使用多智能体

适合的任务有一个共同特点：能拆成**相对独立、输入明确、输出可合并**的工作包。

| 场景 | 合理分工 |
| --- | --- |
| Pull Request 审查 | 安全风险、行为回归、测试缺口、可维护性分别检查 |
| 陌生代码库定位问题 | 一个 Agent 绘制调用链，一个复现或读日志，一个核对配置 |
| 多步骤功能方案 | 分别调研现状、接口契约、数据模型、测试计划，再由主 Agent 整合 |
| 文档与迁移核对 | 分别检查 API 文档、兼容性、受影响模块和回滚方案 |
| 大量只读资料分析 | 按模块、主题或文件集合并行归纳，返回带来源的摘要 |

不适合的任务同样需要直说：

- 一个文件里的小修复，拆分成本通常高于收益；
- 子任务高度串行，后一步必须依赖前一步的精确结果；
- 多个 Agent 会同时改同一批文件；
- 问题本身尚未定义清楚，连主 Agent 都不知道应该委派什么。

官方建议优先将**只读型**工作并行化，例如探索、测试、分诊和总结；对并行写入则要谨慎，因为冲突和协调成本会迅速抵消速度优势。先并行调查，再由一个明确负责人实施修改，通常更稳定。

## 四、Codex 如何开启和触发子智能体

当前 Codex 版本默认启用子智能体工作流。最直接、也最可控的方式是在任务中明确说明要怎样委派：

```text
审查当前分支相对 main 的改动。
并行启动三个子智能体：
1. 审查安全问题和权限边界；
2. 检查行为回归与缺失测试；
3. 评估可维护性和文档影响。
等待三者全部完成后，按类别汇总真实问题；每项附文件位置、影响和复现或验证依据。
不要直接修改代码。
```

这样的指令包含了五件重要的事：任务如何拆分、每人负责什么、是否需要等待全部结果、返回什么格式、是否允许写入。只说“开几个 Agent 看看”当然也能得到结果，只是结果大概也会相应地随意一些。

不同客户端的入口如下：

| 使用位置 | 触发与查看方式 |
| --- | --- |
| Codex 桌面应用聊天 | 直接要求委派独立子任务；可打开每条子线程查看进度与结果 |
| Codex CLI 交互会话 | 直接要求使用子智能体；使用 `/agent` 查看或切换 Agent thread |
| Codex IDE 扩展 | 直接要求并行委派；支持时可从编辑器上方的后台 Agent 面板检查状态 |

除了直接要求，适用的 `AGENTS.md` 或 Skill 也可以要求 Codex 在满足条件时委派工作。对于团队习惯，建议把委派规则限制得具体一些，例如“PR 审查且改动超过三个模块时，并行执行只读审查”；不要写成“所有任务都必须开五个 Agent”，那只是把成本制度化。

## 五、用 `config.toml` 显式配置

默认启用并不意味着不能管理。可以在用户级 `~/.codex/config.toml`，或受信任项目的 `.codex/config.toml` 中设置全局子智能体选项：

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 4
default_subagent_model = "gpt-5.6-terra"
default_subagent_reasoning_effort = "medium"
```

字段含义如下：

| 字段 | 作用 |
| --- | --- |
| `agents.enabled` | 是否启用多智能体工具；当前默认值为 `true` |
| `agents.max_concurrent_threads_per_session` | 单个主会话最多并发打开多少个子线程，不计主线程 |
| `agents.default_subagent_model` | 未显式指定时，子智能体使用的默认模型 |
| `agents.default_subagent_reasoning_effort` | 未显式指定时，子智能体使用的默认推理强度 |
| `agents.interrupt_message` | 子线程被中断时，是否记录模型可见的中断消息 |

实际模型名称和可用推理档位会随版本与账户而变化，所以配置前应检查本机支持项。若不设置模型和推理强度，子智能体会继承父 Agent 的配置。显式的本次 spawn 参数优先于这些默认值。

如果需要临时关闭多智能体，不必删除自定义 Agent 文件，只需设置：

```toml
[agents]
enabled = false
```

## 六、如何创建专门的自定义 Agent

内置 Agent 通常包含通用的 `default`、偏执行的 `worker` 和偏只读探索的 `explorer`。当团队有稳定而狭窄的分工时，可以为项目创建自定义 Agent：将一个 TOML 文件放在 `.codex/agents/`；个人跨项目复用则放在 `~/.codex/agents/`。

每个自定义 Agent 至少要定义 `name`、`description` 和 `developer_instructions`。以下是一个仅用于 PR 审查的项目级示例：

```toml
# .codex/agents/pr-reviewer.toml
name = "pr_reviewer"
description = "只读 PR 审查员，关注正确性、安全风险和缺失测试。"
model_reasoning_effort = "high"
sandbox_mode = "read-only"

developer_instructions = """
审查当前改动中可证明的行为回归、安全问题和测试缺口。
每项发现必须包含文件位置、影响说明和复现或推理依据。
忽略纯风格偏好；不要修改文件，不要执行有外部副作用的操作。
"""
```

随后可以用清楚的角色名委派：

```text
审查这个分支：让 pr_reviewer 寻找真实风险，让 explorer 绘制受影响的调用链。
等待两者完成后，按严重程度整理结果；不要修复。
```

自定义 Agent 的价值不在于给模型换一个响亮称号，而在于固定**职责、工具面、权限和输出标准**。越窄、越可验证的 Agent，通常越容易调度和维护。

## 七、模型与推理强度怎样搭配

不要让所有子智能体都使用同样昂贵的配置。工作负载不同，适合的速度、深度和成本也不同。

| 子任务类型 | 常见选择思路 |
| --- | --- |
| 大范围搜索、文件盘点、日志筛选 | 选更快、较低成本的模型和中低推理强度 |
| 安全审查、复杂逻辑追踪、竞态分析 | 选更强模型与较高推理强度 |
| 格式检查、固定模板转换、批量摘要 | 选较轻量的模型与低推理强度 |
| 主 Agent 的最终整合 | 保留足够推理能力，负责处理冲突和缺失证据 |

官方文档将更高推理强度与更高耗时、token 使用相关联。实务上可以先用少量轻量只读 Agent 收集证据，再让主 Agent 或一个高强度审查 Agent 对关键风险复核，而不是在所有地方都堆满最大配置。

## 八、权限、审批与写入冲突

子智能体继承父任务当前的沙箱和审批策略，也会继承父 Agent 可用的工具。它们不能因为“是子线程”就绕过用户批准；非交互流程中，如果新动作需要审批却无法展示请求，操作会失败并把错误返回主工作流。

因此，开始委派前先在主任务确定权限模式。对于探索、审查、核对和日志分析，优先设置只读；对于实施修改，最好指定单一写入负责人，并让其他 Agent 只提供证据。下面这种分工比四个 Agent 同时改一个目录可靠得多：

```text
并行：explorer 定位调用链，test_auditor 找测试缺口，docs_researcher 核对 API。
汇总后：仅 worker 根据已经确认的结论实施最小修复并运行相关验证。
```

多智能体不会替你解决代码冲突、需求冲突或权限冲突。它只会更快地把这些冲突暴露出来。这个事实并不浪漫，但相当有用。

## 九、一套可直接复用的工作模板

对中等规模的修复或审查任务，可以从下面模板开始：

```text
目标：<要解决或审查的问题>。

请并行委派下列独立子任务：
1. <角色 A>：输入 <范围>，输出 <证据和结论>，不修改文件。
2. <角色 B>：输入 <范围>，输出 <证据和结论>，不修改文件。
3. <角色 C>：输入 <范围>，输出 <证据和结论>，不修改文件。

等待全部结果后：
- 合并重复发现，说明相互矛盾的结论；
- 按严重程度输出，附文件位置和验证依据；
- 仅在证据足够时提出修复方案；
- <是否允许写入、测试、提交、部署等边界>。
```

这里最值得保留的是“输入、输出、边界、等待与收口”五项。没有收口要求时，子智能体可能各自完成得不错，主 Agent 却没有把结果组织成你真正需要的结论。

## 十、落地检查清单

- 子任务是否真的互不依赖，能否并行？
- 每个 Agent 是否有清晰的输入范围、职责边界与可验收输出？
- 是否优先让并行 Agent 做只读工作？
- 是否限制了并发数量，避免无意义地增加 token 与工具开销？
- 父任务的沙箱、审批和外部工具权限是否合适？
- 谁负责最终整合，谁拥有实际写入权？
- 是否要求返回文件引用、命令结果或其他可复核证据？

多智能体的重点从来不是“Agent 数量”，而是**可并行的工作划分与可靠的汇总机制**。先让一个主 Agent 把任务边界理清，再让多个子智能体处理互不阻塞的部分；这比让一群 Agent 同时奔向同一处模糊目标，更接近真正的协作。
