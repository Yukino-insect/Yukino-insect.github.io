网上常见的“同时派出多个 Agent 完成任务”，很容易让人产生一个略带科幻色彩的误会：是不是模型自己忽然决定分身，再让这些分身自行协作？结论并不复杂：**能否创建并行执行单元、最多创建几个、它们拥有什么权限，首先由程序员和运行平台设计；至于某一次任务要不要使用这些单元，则可以由固定规则、人工指令，或主 Agent 在被允许的范围内作出选择。**

换句话说，模型可以参与“调度决策”，却不能凭空获得调度能力。没有编排程序提供 `spawn_agent`、队列、并发额度、工具权限与结果汇总，模型生成再漂亮的“请启动三个专家”也只是一段文字。把文字变成真实并行任务的，仍然是软件系统。

本文从这个边界出发，解释多智能体并行究竟是谁决定的，并给出一套从简单规则到“主 Agent 动态委派”的实现方法。读完后，应当能判断一个任务值不值得并行，以及知道要在程序中实现哪些关键部件。

## 一、先把“自主”拆成三个不同的问题

“Agent 自己决定并行”这句话混合了至少三层含义。把它们拆开，讨论才不会飘到概念之外。

| 层次 | 真正的问题 | 通常由谁决定 |
| ---- | ---------- | ------------ |
| 能力层 | 系统能否创建多个独立工作单元并同时运行 | 平台与程序员 |
| 策略层 | 哪些任务满足并行条件、最大并发是多少 | 程序员、运维策略或用户 |
| 选择层 | 当前这个具体任务是否值得委派给哪些角色 | 规则引擎、用户或主 Agent |

例如，一个代码审查系统预先定义了“安全审查员”“测试审查员”“依赖审查员”三个工作者，并设置最大并发为 3。这是能力层和策略层的设计。主 Agent 读到“审查支付模块的改动”后，调用 `delegate` 工具选择其中两个工作者，这是选择层的自主性。

因此，比较准确的表述是：**Agent 可以在受控的行动空间中自主选择是否委派；并行机制本身、可选角色和安全边界由程序定义。** 把两者都归为“完全由 AI 决定”，或都归为“模型毫无决策权”，都不够准确。

## 二、一个 Agent 不是模型的“复制粘贴”

很多演示把多个对话窗口都叫作 Agent，这并非绝对错误，却掩盖了工程上真正重要的部分。一个可工作的 Agent 通常至少包含：

- 模型与系统提示词：负责推理、规划和生成内容；
- 独立上下文：它看见哪些任务材料、历史记录和中间结果；
- 工具集合与权限：能否读仓库、联网、运行测试、写文件或调用生产接口；
- 状态与预算：超时时间、token 或费用上限、重试次数、取消信号；
- 输入输出契约：接收什么，必须返回什么，如何让主流程验证结果。

所以“开三个 Agent”通常意味着运行时建立三个隔离或半隔离的执行上下文，再让调度器并发执行它们。它们可能都调用同一个大模型，也可能使用不同模型；真正让它们成为协作单元的，是不同的职责、上下文和可验收输出。

```text
用户目标
   │
   ▼
编排器 / 主 Agent
   ├── 安全审查 Agent：只读代码，返回漏洞证据
   ├── 测试分析 Agent：只读代码和测试，返回覆盖缺口
   └── 文档核对 Agent：查接口文档，返回兼容性结论
   │
   ▼
结果校验、去重、冲突处理与最终答复
```

这里的并行并不要求“多模型”。三个任务即使使用同一个模型 API，只要请求、上下文、工具执行和结果处理能重叠进行，仍然是并行的多 Agent 工作流。

## 三、究竟有哪几种决定方式

实际系统常见四种模式，它们不是互相排斥的关系，而是控制力度不同。

### 1. 人工明确指定

用户或开发者直接说：“同时检查安全、性能和测试，不要修改代码。”编排器依照指令创建固定数量的工作者。

这种方式最透明，适合开发工具、审查任务和成本敏感的场景。它的缺点是每次都需要人知道如何拆分任务；但对风险较高的操作而言，这恰恰是优点，而不是缺陷。

### 2. 规则驱动的固定编排

程序员把判断写入工作流。例如：当变更涉及认证目录时，必跑安全审查；当改动文件超过 20 个时，再增加影响范围分析；其他小改动只由一个 Agent 处理。

```text
if changedFiles > 20:
    并行运行：依赖分析、测试影响分析
if touchesAuthentication:
    额外运行：安全审查
最后：主流程汇总并决定是否阻断发布
```

这本质上与传统工作流、CI 流水线很接近，只是其中若干节点由模型完成。优点是可预测、可审计；缺点是规则需要持续维护。

### 3. 主 Agent 通过工具动态委派

程序给主 Agent 一个受限的工具，例如 `delegate(tasks)`。模型先分析任务，再提交结构化的委派请求；**程序并不盲从**，而是校验任务数量、角色白名单、路径范围、并发额度和权限，校验通过后才真正启动子 Agent。

这正是许多看起来“Agent 自己会开分身”的产品的工作原理。模型决定的是一次工具调用的参数，运行时决定这次调用是否允许执行。

### 4. 由外部调度器自动扩缩容

在处理大批文档、客服工单或离线评测时，队列长度、SLA 和预算会触发调度器增加或减少 worker 数量。此时甚至不需要一个“主 Agent”逐一决定；Kubernetes、任务队列或云函数平台按照指标调度多个执行器。

模型依然只负责每个任务的智能处理。把“根据负载启动 100 个 worker”误称为模型自主决策，会错过可靠性、成本控制和容量治理这些更实际的部分。

## 四、先判断任务是否真的适合并行

并行的前提不是任务看起来很大，而是存在**相互独立的工作包**。一个简单判断方法是问：子任务 A 的可靠完成，是否必须等待子任务 B 的具体输出？如果必须等待，它们多半应串行；如果只共享原始材料、能各自得出可合并的结论，则适合并行。

| 适合并行 | 应优先串行 |
| -------- | ---------- |
| 分别检查安全、性能、测试缺口 | 先定位根因，再据此修改实现 |
| 按目录或文档分片提取信息 | 下一步计算依赖上一步的精确结果 |
| 分别核对多个外部 API 的兼容性 | 多人同时修改同一组文件 |
| 并行生成候选方案，再统一评审 | 任务目标和验收标准尚不明确 |

还有一个常被忽略的条件：结果必须能合并。让四个 Agent 各写一份架构方案很容易；真正困难的是定义统一输出，例如“每项风险必须含文件位置、严重等级、证据和建议”，并由一个负责人处理重复与矛盾。没有这一层，所谓协作很可能只是把四份噪声叠在一起。

## 五、最小可用架构：程序负责生命周期，模型负责局部智能

从工程角度看，一个稳妥的最小架构可以分成五个部件：

1. **任务分解器**：来自人工规则或主 Agent，产出边界明确的任务描述。
2. **任务校验器**：检查角色、权限、目标范围、预算与并发限制。
3. **执行池**：真正并行地运行子 Agent，并处理超时、取消和重试。
4. **结果存储与校验**：保存原始输出，并验证它是否符合约定的结构。
5. **汇总器**：去重、追溯证据、处理冲突，形成最终结论或下一轮任务。

职责流向如下：

```text
主 Agent / 规则
      │  提交任务计划
      ▼
校验器 ──拒绝越权、超预算或不合格计划
      │
      ▼
并发执行池 ──启动受权限约束的子 Agent
      │
      ▼
结构化结果 ──证据、状态、耗时、失败原因
      │
      ▼
汇总器 ──结论、冲突与后续动作
```

需要特别强调的是，主 Agent 不应直接拥有“无限创建任意 Agent”的能力。它只应能提出计划；校验器和执行池才拥有实际资源控制权。这类似应用程序可以请求创建线程，但操作系统仍会管理可用资源。所谓自主，不是取消边界，而是在边界内作出选择。

## 六、用 TypeScript 实现受控的并行委派

下面的示例刻意不绑定某个 Agent 框架。`runOneAgent` 可以替换成任意模型 SDK、Agent 平台或内部 RPC；值得学习的是编排层的约束，而非某个库的函数名。

### 1. 定义任务和结果契约

先要求每个子任务指定角色和只读范围，并让每个结果包含状态和可复核证据。

```ts
type Role = "security_reviewer" | "test_reviewer" | "docs_reviewer";

type AgentTask = {
  id: string;
  role: Role;
  prompt: string;
  readOnlyPaths: string[];
};

type AgentResult = {
  taskId: string;
  status: "ok" | "failed" | "timed_out";
  findings: Array<{
    severity: "low" | "medium" | "high";
    evidence: string;
    recommendation: string;
  }>;
  error?: string;
};
```

如果只返回自由文本，主 Agent 很难稳定地识别失败、引用证据或去重。让模型输出 JSON 并使用 schema 校验，会比“请认真总结”可靠得多。

### 2. 在启动前校验计划

以下校验是安全边界的一部分，不能仅写进提示词。提示词可以要求“只读”，真正阻止写入的必须是工具权限和沙箱。

```ts
const ALLOWED_ROLES = new Set<Role>([
  "security_reviewer",
  "test_reviewer",
  "docs_reviewer",
]);

function validatePlan(tasks: AgentTask[], maxTasks: number): void {
  if (tasks.length === 0 || tasks.length > maxTasks) {
    throw new Error("委派数量不在允许范围内");
  }

  for (const task of tasks) {
    if (!ALLOWED_ROLES.has(task.role)) {
      throw new Error(`不允许的角色：${task.role}`);
    }
    if (task.readOnlyPaths.some((path) => path.startsWith("../"))) {
      throw new Error(`越出仓库的路径：${task.id}`);
    }
  }
}
```

在正式项目中还应校验路径是否经过规范化后仍位于工作区内、任务是否重复、总 token 预算和预期工具成本。只检查字符串前缀并不足以抵御所有路径绕过；这里仅用于展示责任应放在哪里。

### 3. 限制并发并保留失败结果

不应对几百个任务直接 `Promise.all`。那会同时挤压模型配额、文件系统和外部 API，也让取消和重试变得困难。下面的简单 worker pool 同时最多执行 `limit` 个任务，并且把失败转为结果，而不是让一次失败丢掉所有已完成的工作。

```ts
async function runWithConcurrency<T, R>(
  items: T[],
  limit: number,
  work: (item: T) => Promise<R>,
): Promise<R[]> {
  const results: R[] = [];
  let nextIndex = 0;

  async function worker(): Promise<void> {
    while (nextIndex < items.length) {
      const item = items[nextIndex++];
      results.push(await work(item));
    }
  }

  const workerCount = Math.min(limit, items.length);
  await Promise.all(Array.from({ length: workerCount }, worker));
  return results;
}

async function runOneAgent(task: AgentTask): Promise<AgentResult> {
  try {
    // 在这里调用模型；工具层只暴露 task.readOnlyPaths 的读权限。
    const findings = await callModelAndValidateJson(task);
    return { taskId: task.id, status: "ok", findings };
  } catch (error) {
    return {
      taskId: task.id,
      status: "failed",
      findings: [],
      error: error instanceof Error ? error.message : "unknown error",
    };
  }
}

validatePlan(plan.tasks, 6);
const results = await runWithConcurrency(plan.tasks, 3, runOneAgent);
```

示例为了简洁使用了共享数组；JavaScript 单线程事件循环使这段同步的 `nextIndex++` 不会被抢占。若换成多进程或分布式 worker，则必须把领取任务改为队列的原子操作，例如数据库的行锁或消息队列确认机制，否则同一个任务可能被执行两次。

### 4. 让主 Agent 有选择权，但没有越权权

若希望由主 Agent 动态决定是否并行，可以要求它只返回计划，而不是直接执行动作。

```json
{
  "shouldDelegate": true,
  "reason": "安全审查、测试缺口与文档兼容性互不依赖",
  "tasks": [
    {
      "id": "security",
      "role": "security_reviewer",
      "prompt": "审查本次 diff 中的权限绕过与敏感信息泄露。",
      "readOnlyPaths": ["src/auth", "src/api"]
    },
    {
      "id": "tests",
      "role": "test_reviewer",
      "prompt": "识别未覆盖的失败分支，给出测试场景。",
      "readOnlyPaths": ["src", "tests"]
    }
  ]
}
```

程序拿到此 JSON 后依次执行：schema 校验、`validatePlan`、预算检查、受限启动、结果汇总。模型提议的 `shouldDelegate` 为 `false` 时，主流程可单 Agent 执行；它为 `true` 时，也不代表一定会被批准。这正是“有决策参与，但系统仍可控”的实现形态。

## 七、结果汇总比启动更多 Agent 更重要

并发流程的末端绝不能只把多个回答拼接起来。汇总器至少需要处理四类情况：

- **重复发现**：三个 Agent 都指出同一处空指针风险，应合并成一项并保留最强证据；
- **相互矛盾**：一个认为接口兼容，另一个找到破坏性变更，应回到源码或文档复核；
- **部分失败**：测试 Agent 超时不等于“没有测试风险”，最终结论必须标出未完成项；
- **证据不足**：模型的推测应与可定位的日志、代码位置或文档链接区分开。

尤其不要让汇总 Agent 因为“多数投票”就宣判事实。三个使用相同上下文和相似提示词的 Agent 很可能共同犯同一个错误；投票只能增加独立证据的权重，不能代替验证。

一个实用的结果格式可以是：

| 字段 | 用途 |
| ---- | ---- |
| `claim` | 要表达的结论或风险 |
| `evidence` | 代码位置、命令输出、文档片段等可复核依据 |
| `confidence` | 已验证、较可信、待确认等状态 |
| `owner` | 哪个 Agent 或哪个后续步骤负责处理 |
| `nextAction` | 修复、复核、补测或明确不处理 |

这会迫使系统将“语言模型的回答”转化为可追踪的工程产物。没有这种转化，并行只会更快地产生更多难以判断的文字。

## 八、权限、写入冲突与成本边界

多 Agent 不是把单 Agent 风险除以人数，反而可能把工具调用、上下文泄露和写入冲突同时放大。因此实践中应坚持以下边界：

- 优先把并行任务设计为只读探索、审查、检索和测试分析；
- 对修改、提交、部署、发送消息等外部副作用，指定一个明确的执行负责人；
- 每个子 Agent 使用最小权限，不因“主 Agent 有权限”就默认继承全部能力；
- 设置单任务超时、总 token 或费用预算、最大并发与取消机制；
- 记录任务输入、工具调用、原始结果和汇总依据，便于审计与复现；
- 将可重试的瞬时错误与需要人工处理的授权、参数错误区分开。

一个很稳妥的模式是“**并行调查，串行写入**”：多个只读 Agent 同时收集证据，主 Agent 汇总并给出计划，最后只由一个拥有写权限的 Agent 实施最小变更并运行验证。这样并行带来的是信息收集速度，而不是文件冲突速度。

## 九、从小处开始的落地路线

第一次实现时，不需要先搭建一个会递归分裂、自动扩容的“Agent 公司”。那样通常只会比需求更早失控。可以按下面的顺序演进：

1. 选一个高价值且只读的场景，例如 PR 审查或文档检索。
2. 固定 2 到 3 个角色、输入范围和 JSON 输出 schema。
3. 用规则决定是否并行，设置很小的并发上限和超时。
4. 保存结果并建立人工可查看的汇总页面或日志。
5. 观察失败率、耗时、成本和最终结论质量，再调整角色与规则。
6. 只有在规则已无法覆盖足够多任务时，再让主 Agent 提议委派计划，并保留严格校验。

这条路线看起来没有“让 AI 自己组织团队”那么戏剧化，却能让你在真正需要时知道每一个任务为什么被启动、花了多少成本、发生问题后应该在哪里停止它。工程系统首先要可解释，之后才谈得上聪明。

## 十、总结

并行运行多个智能体并不是单一主体决定的事情，而是多层协作：

- **程序员与平台**提供 Agent 创建、并发、权限、预算、工具和汇总机制；
- **规则、用户或主 Agent**决定当前任务是否值得使用这些机制；
- **校验器与调度器**把模型的提议限制在安全、成本和资源边界之内；
- **汇总与验证**决定多个输出能否变成可靠结论。

所以，对“这是 Agent 自己决定的吗”的最佳回答是：**可以部分是，但前提是程序员先把“可以决定什么、不能决定什么、决定后怎样执行”设计清楚。** 真正成熟的多 Agent 系统，不是让模型无边界地增加同伴，而是让它在合适的时候提出可验证的分工，并由稳定的编排层把分工落实为可控的并行工作流。
