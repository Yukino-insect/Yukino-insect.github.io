## 学习目标

- 理解 Embedding 的作用和局限。
- 知道向量数据库保存的是什么。
- 能解释相似度检索、索引和维度的基本概念。
- 能判断何时需要混合检索和 Rerank。

## Embedding 是什么

Embedding 是把文本转换成一组数字向量的过程。向量中的每个维度没有直接的人类语义标签，但整体上会把语义相近的文本映射到更接近的位置。

例如，“如何重置密码”和“忘记密码怎么办”字面不同，但语义接近，Embedding 后应该更容易互相匹配。这就是向量检索相对关键词检索的优势：它能处理同义表达、近义问题和自然语言变化。

但 Embedding 不是理解一切的万能装置。它容易受模型、语言、领域术语、文本长度和噪声影响。把低质量 Chunk 向量化，只会得到一批低质量向量，形式上很先进，实际效果很普通。

## 向量库保存什么

向量库保存的不只是向量。一个可用的 RAG 向量表通常至少包含：

- Chunk 原文：用于 Prompt 和引用。
- Embedding 向量：用于相似度召回。
- Collection 或知识库标识：用于隔离不同知识空间。
- 元数据 JSON：用于文档来源、页码、标题路径、权限和过滤。
- 索引：用于加速近似最近邻搜索。

Ragent 当前使用 `t_knowledge_vector` 保存知识库向量数据，其中 `collection_name` 用于区分 Collection，`metadata` 保存扩展信息，`embedding` 存储向量。维度必须和 Embedding 模型输出一致，例如 1024 维模型就不能写入 1536 维表结构。

## 相似度如何计算

常见相似度包括余弦相似度、内积和欧氏距离。RAG 文本检索里常用余弦相似度，因为它更关注向量方向，而不是向量长度。

向量检索的基本过程是：

```text
用户问题 -> 生成 query embedding -> 在指定 Collection 中查找相似 Chunk -> 返回 TopK
```

如果数据量小，可以精确扫描；数据量大时通常需要 HNSW、IVF 等近似索引。近似索引会用少量准确性换取速度，所以检索参数需要结合评测调优。

## 为什么还需要关键词检索

向量检索擅长语义相似，但不一定擅长精确符号。产品型号、错误码、接口字段、合同编号、人名和缩写，往往是关键词检索的强项。

因此成熟系统常用混合检索：向量检索找语义相关，关键词检索找精确命中，图谱或结构化检索找关系证据。多路结果再通过 RRF 等方法融合，最后交给 Rerank 精排。

这也是为什么“用了向量库”并不等于“检索就完成了”。向量库是一类召回通道，不是全部答案。

## Collection 的意义

Collection 可以理解为知识空间的边界。不同业务线、租户、智能体或意图节点，可以绑定不同 Collection。在线检索时先确定范围，再在范围内召回，能减少无关知识污染，也能降低越权风险。

Ragent 的意图节点支持 `collection_names`，意味着一个意图可以绑定多个 Collection。这样做比单一 Collection 更灵活：例如“售后政策”意图可以同时检索“保修条款”和“退换货流程”两个知识空间。

## 常见误区

第一个误区是只看 TopK。TopK 越大，召回越多，但成本、延迟和上下文噪声也会上升。更大的候选池不等于更好的答案。

第二个误区是混用 Embedding 模型。文档向量和问题向量必须来自兼容模型，否则相似度没有意义。

第三个误区是忽略重建成本。换 Embedding 模型或维度，通常意味着历史向量需要重算，索引也要重建。

第四个误区是把向量分数当作跨通道统一分数。BM25、向量相似度和图谱置信度的量纲不同，直接比较会制造排序偏差。

## 小结

Embedding 让文本可以做语义检索，向量库让检索在工程上可扩展。但它们只解决“候选证据如何被找到”的一部分问题。真正可靠的 RAG 还需要元数据过滤、混合召回、融合排序、Rerank 和评测。
