## 学习目标

- 理解上传接口和入库处理接口为什么要分离。
- 掌握文档处理任务的幂等设计。
- 知道解析、分块、Embedding 和持久化的阶段边界。
- 能设计面向用户和运维的状态反馈。

## 为什么分成两个接口

很多系统会把“上传文件”和“解析入库”放在一个接口里同步完成。这样写演示很方便，工程上却不稳。文档解析、OCR、表格抽取、Embedding 和向量写入都可能耗时很长，还可能依赖外部服务。

更合理的设计是：

```text
上传接口：只负责接收文件、保存对象存储、创建文档记录。
开始分块接口：负责触发解析、分块、向量化和索引写入。
```

这样用户可以先看到文档已上传，再通过状态查看处理进度。系统也可以把重任务放到线程池、队列或调度器中执行。

## 上传接口职责

上传接口应该完成：

- 鉴权和知识库权限校验。
- 文件大小、类型和 MIME 校验。
- 文件流写入对象存储。
- 创建 `t_knowledge_document` 记录。
- 保存 `source_type`、`source_location`、`file_url`、`file_size`、`mime_type` 等信息。
- 初始化处理状态，例如 `pending`。

上传接口不应该直接把文档切块并写向量库。它最多可以在小文件场景下触发异步任务，但不应让请求线程承担完整入库链路。

## 开始分块接口职责

开始分块接口负责启动入库任务。典型流程是：

```text
校验文档状态 -> 创建分块日志 -> 读取原始文件 -> 解析文本 -> 生成 Chunk -> 调用 Embedding -> 写入向量表 -> 更新文档状态
```

这里的关键是状态和日志。每次处理都应生成一条执行记录，保存解析耗时、分块耗时、向量化耗时、持久化耗时、Chunk 数量和错误信息。没有这些字段，线上排错就只能靠猜，猜得准还好，猜不准就很符合人类工程史。

## 幂等设计

开始分块接口很容易被重复调用：用户重复点击、前端重试、网关超时、后台补偿都可能触发它。幂等设计必须回答三个问题：

1. 同一文档正在处理中时，再次调用怎么办？
2. 上一次失败后，再次调用是否允许重试？
3. 重新处理成功后，旧 Chunk 如何替换？

常见策略是：running 状态拒绝重复启动；failed 状态允许重试；success 状态如需重建，应先创建新执行记录，再在事务或可恢复步骤中替换旧索引。

## 解析配置

不同文档不应使用完全相同的解析策略。`ingestion_spec` 可以保存文档级配置，例如：

- 解析档位：轻量解析、标准解析、OCR 或外部解析。
- Chunk 大小和 overlap。
- 是否保留标题路径。
- 是否解析表格和图片说明。
- 最大页数或最大 Token 预算。

配置落在文档级别，方便后续重试、审计和效果对比。否则你只知道“这份文档处理过”，不知道当时按什么规则处理。

## 异步解析服务

复杂 PDF 或扫描件可能交给外部解析服务，例如 MinerU 类服务。此时链路会变成：

```text
提交解析任务 -> 保存外部 task_id -> 等待回调或轮询 -> 获取解析结果 -> 继续分块和向量化
```

异步任务表应记录外部任务 ID、状态、请求 ID、提交时间、回调时间、完成时间和错误信息。外部服务不可靠时，系统必须能识别超时任务并恢复。

## 常见误区

接口返回成功不等于文档可检索。上传成功只是第一步，处理成功才代表能问答。

只保存最终状态不够。中间耗时和错误阶段决定了能否优化。

重试时直接追加 Chunk 会污染索引。重建必须处理旧数据。

把解析配置写死在代码里，会让不同文档类型无法调优。

## 小结

上传接口负责把文件安全地带进系统，开始分块接口负责把文档变成检索资产。二者分离后，系统才能支持异步处理、重试恢复、状态展示和任务观测。知识库的可靠性，从接口职责清楚开始。
