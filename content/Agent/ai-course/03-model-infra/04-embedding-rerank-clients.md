## 学习目标

- 理解 Embedding 和 Rerank 在链路中的位置。
- 掌握批量 Embedding 的工程注意点。
- 知道 Rerank 客户端为什么需要统一抽象。
- 能设计降级、去重和候选池控制。

## Embedding 客户端

Embedding 客户端负责把文本转成向量。它服务两条链路：

第一条是入库链路，把每个 Chunk 转成向量并写入向量表。

第二条是问答链路，把用户问题或改写后的问题转成 query vector，用于向量检索。

这两条链路使用的模型必须兼容。文档向量如果是 1024 维，查询向量也必须是同一维度、同一语义空间。否则向量相似度就没有意义，系统只是非常认真地比较了两组不该比较的数字。

## 批量处理

入库时通常需要批量生成 Embedding。批量能提高吞吐，但要注意：

- 单批文本数量不能超过模型接口限制。
- 单条文本 Token 不能超过限制。
- 批量失败时要能定位到具体 Chunk。
- 部分成功时要能重试未成功项。
- 写入向量表前要校验维度。

批量大小不是越大越好。过大会导致超时、失败重试成本高；过小又浪费网络和模型吞吐。需要结合模型限制和入库任务量调优。

## Rerank 的位置

Rerank 位于召回之后、Prompt 之前。它输入用户问题和一组候选 Chunk，输出重新排序后的候选列表。

向量检索只看向量空间相似，关键词检索只看词项匹配，RRF 只融合名次。Rerank 则能更细地判断“这个 Chunk 是否真的回答当前问题”。因此它适合做最后一道相关性过滤。

但 Rerank 通常成本更高，延迟也更明显。不能把全部召回结果都送进去，必须先通过候选池上限控制规模。

## Rerank 客户端抽象

不同供应商的 Rerank API 可能差异很大：字段名、分数范围、TopN 参数、最大候选数、错误码都不同。统一客户端抽象可以让业务层只关心输入和输出。

Ragent 中 `RerankClient` 定义供应商客户端接口，`AbstractRerankClient` 负责公共逻辑，例如候选去重、TopN 保护和异常处理；具体实现可以是百炼、自定义 Rerank 服务或 Noop Rerank。

Noop Rerank 并不是没用。它可以作为降级方案，在外部 Rerank 不可用时保留粗排结果，保证问答链路不完全中断。

## 候选去重

Rerank 前必须处理重复候选。同一个 Chunk 可能被向量、关键词和图谱多个通道同时召回。重复候选如果直接进入 Rerank，会浪费名额，也可能让某份证据被重复加权。

去重通常按 Chunk ID 或内容 hash 进行。去重后还要保留来源通道信息，便于后续归因分析：哪些通道贡献了最终答案，哪些通道只是制造成本。

## 分数解释

Rerank 分数适合在同一次请求的候选之间比较，不一定适合跨请求比较。不同模型、不同问题、不同候选池下，分数分布可能不同。

因此不要轻易写死“分数低于 0.7 一律丢弃”这类规则，除非经过评测验证。更稳妥的做法是结合名次、候选数量、问题类型和业务阈值综合判断。

## 常见误区

换 Embedding 模型后不重建历史向量，会直接破坏检索。

Rerank 候选池太大，会让延迟和费用上升；太小，又会错过好证据。

把 Rerank 当成召回补救工具也不对。它只能重排已有候选，不能找回没召回的证据。

只看最终 TopK 不看输入候选，会错过召回阶段的问题。

## 小结

Embedding 决定语义召回的基础，Rerank 决定候选证据进入 Prompt 前的精排质量。二者都需要统一客户端、配置驱动、维度校验、候选控制和降级策略。模型能力越靠近基础设施，业务链路越能保持清爽。
