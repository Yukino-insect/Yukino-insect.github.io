## 学习目标

- 理解评测集在 RAG 优化中的作用。
- 能设计评测样本字段。
- 掌握评测运行的基本流程。
- 能区分离线评测和线上反馈。

## 为什么先建评测集

RAG 系统的改动很多：解析器、Chunk 大小、Embedding 模型、检索通道、RRF 参数、Rerank 候选池、Prompt 模板、模型路由。任何一项变化都可能影响答案。

如果没有固定评测集，每次优化只能凭几个演示问题判断。演示问题通常会越调越好，因为你已经知道它们怎么答；真实用户问题则不一定。固定评测集的价值，是让系统面对同一批问题反复考试。

## 样本字段

一条高质量评测样本至少包含：

- `question`：用户问题。
- `expected_answer`：人工整理的标准答案或要点。
- `golden_sources`：应命中的文档、章节、页码或 Chunk ID。
- `answer_type`：事实查询、流程说明、对比总结、跨文档、多轮追问、拒答。
- `difficulty`：简单、中等、困难。
- `tags`：业务域、知识库、意图节点、是否需要工具。
- `must_not_answer`：资料不足时不应编造的内容。

标准答案不一定要写成唯一表述，但要明确关键事实和判断标准。否则自动评测和人工复核都会失去依据。

## 样本来源

评测样本可以来自四个地方。

第一，真实用户问题。它最贴近生产，但需要脱敏和清洗。

第二，业务专家整理的问题。它覆盖关键流程和高风险场景。

第三，历史故障样本。每次线上坏回答都应该进入回归集。

第四，构造的边界样本。例如资料不足、文档冲突、权限限制、多轮指代。

不要只用简单问题。简单问题适合冒烟测试，不能代表系统能力。

## 初始化流程

评测系统初始化可以按以下步骤：

```text
准备知识库快照
  -> 固定评测问题集
  -> 标注黄金证据和标准答案
  -> 固定运行配置
  -> 执行问答 Pipeline
  -> 保存检索结果、Prompt、答案和耗时
  -> 计算指标并生成报告
```

知识库快照很重要。如果文档一直变化，评测结果就很难比较。可以定期更新评测快照，但每次对比时要明确版本。

## 评测系统表设计

评测系统可以抽象为四类数据：

- 数据集：一组样本的集合。
- 样本：问题、标准答案、黄金证据和标签。
- 运行记录：某次使用哪个代码版本、配置版本和知识库快照。
- 样本结果：检索候选、最终答案、指标分数、耗时和错误。

这样才能比较不同运行之间的差异。例如“开启 Rerank 后，跨文档问题忠实度提升，但 P95 首包增加 800ms”。

## 离线与线上

离线评测用于版本回归和方案对比。它稳定、可重复，但覆盖不了所有真实问题。

线上反馈用于发现长尾问题。它真实、丰富，但噪声大，用户反馈也不一定完整。

成熟做法是把线上差评、人工纠正和高频问题沉淀到离线评测集，让评测集持续长出业务经验。

## 常见误区

用模型生成一大批问题却不人工审核，会得到数量很多但价值有限的数据。

只标标准答案，不标黄金证据，会导致检索层无法单独评估。

评测时知识库版本不固定，会让结果不可比较。

只保留最终分数，不保留中间检索和 Prompt，会失去定位能力。

## 小结

评测集是 RAG 优化的坐标系。它让系统改动可以被比较，让坏答案可以被复现，让经验可以沉淀。没有评测集，优化就是凭感觉航行；有评测集，至少你知道自己偏到哪里去了。
