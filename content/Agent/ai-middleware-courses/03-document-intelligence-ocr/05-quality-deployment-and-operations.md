把 OCR 跑出一段文字不等于它已经可用。真正困难的部分在于：你如何知道新模型没有把关键字段读坏？文件突增时为什么不把机器拖垮？保留原件多久才合规？服务升级后如何回退？本章把这些问题变成可测量、可执行的日常规则。它同样适用于本地脚本、内网服务和云上部署。

## 先定义“好”的含义

不同任务对错误的容忍度不同。把一页古籍用于全文检索，可以容忍少量错字；提取银行卡号、药品剂量或付款金额，则一个字符错误就可能不可接受。因此不要只问“准确率多少”，先定义用途和人工复核边界。

一组最小质量指标如下：

| 层次 | 指标 | 回答的问题 |
| --- | --- | --- |
| 字符 | CER | 字符改错多少 |
| 词语 | WER | 词或词组错多少 |
| 检测 | 召回、精确率 | 文字框漏了多少、错框多少 |
| 结构 | 表格/字段准确率 | 值是否落在正确单元格或字段 |
| 运行 | 成功率、P95 时延、页/分钟 | 服务能否按时完成 |
| 风险 | 人工复核命中率 | 阈值是否真的找到了危险结果 |

**CER（character error rate）**是字符编辑距离除以参考字符数。编辑距离计算把参考答案改成预测文本所需的插入、删除、替换次数。例如参考 `合计128`，预测 `合汁128`，通常有一次替换，CER 为 `1/5`。它不是业务正确率：金额小数点丢失与一个普通错别字的风险完全不同。

## 建立一个小而固定的评测集

一开始不需要十万页。收集 30 到 100 个经过授权和脱敏的代表性页面，覆盖你真正会遇到的条件：

- 清晰扫描、手机拍摄、旋转和阴影；
- 中文、英文、数字、日期和金额；
- 单栏、多栏、带边框表格、无线表；
- 文本层 PDF 与纯扫描 PDF；
- 容易失败的低清、小字号和印章遮挡页。

每个样本都需要人工确认的参考文本或关键字段，且版本控制。不要用 OCR 自己的旧结果当“正确答案”，那只能测量新旧模型是否相同，测不出是否正确。

目录可以简单到：

```text
eval/
  images/invoice-001.png
  truth/invoice-001.json
  images/two-column-002.png
  truth/two-column-002.json
  manifest.json
```

`manifest.json` 应记录样本许可、来源类别和标注版本，不要把真实用户信息塞进 Git 仓库。

## 计算 CER 与字段准确率

安装 `jiwer` 后，可以计算基本字符错误率：

```python
from jiwer import cer

reference = "订单编号A20261002合计128.00元"
hypothesis = "订单编号A20261002合计128.00元"
print(f"CER={cer(reference, hypothesis):.4f}")
```

完全相同的预期结果是 `CER=0.0000`。再故意删掉小数点，观察数值上升。对中文，先统一全角/半角、空白和换行规则；否则版面换行会被误计为识别错误。归一化规则必须固定并写入评测说明，不能在模型表现不好时临时更改。

关键字段应单独评估：

```python
def field_exact_match(reference: dict, prediction: dict, field: str) -> bool:
    return reference.get(field) == prediction.get(field)

truth = {"invoice_no": "A20261002", "amount": "128.00"}
pred = {"invoice_no": "A20261002", "amount": "128.00"}
print(field_exact_match(truth, pred, "amount"))  # True
```

预期是金额、日期、编号等字段分别统计准确率。若表格要求行列关系，还要将“单元格位置 + 值”一起比较；只比较拼接文本会掩盖错列问题。

## 置信度如何用于复核，而不是自欺欺人

可以制定简单策略：低于 0.80 的文字行进人工队列，金额/编号即使高于 0.95 仍做格式与校验和检查。但阈值必须由验证集校准：统计不同分数区间的真实错误率，看看 0.80 是否真的分开了高风险样本。

```text
低置信度或规则失败
  -> 展示原页、检测框和模型文本
  -> 人工确认/修改
  -> 保存修正作为未来评测候选
```

不要把“低分全部删除”当作质量控制。删除会让漏检不可见，尤其当整个关键字段被漏掉时，系统甚至没有分数可供判断。

## 性能基准：测量端到端，而非只测模型

一次文档任务的耗时可能包括上传、病毒扫描、Office 转换、PDF 渲染、排队、模型预热、OCR、结果上传和回调。只打印模型 `predict` 的时间，无法说明用户为什么等了两分钟。

至少记录：

```text
queue_wait_ms
convert_ms
render_ms
ocr_ms
persist_ms
total_ms
pages
input_bytes
worker_version
model_version
```

用固定评测集分别跑冷启动和热启动：冷启动包括进程启动与权重加载，热启动表示模型已常驻。报告中分开两者；把第一次的慢下载当作常态，或把缓存后的速度承诺给新节点，都会误导容量规划。

### 并发不是越高越好

设单页渲染图占 25 MiB、模型与运行时占数 GiB、每个任务又可能保留多页中间图；盲目启动 16 个 worker 往往首先导致内存交换、GPU OOM 或磁盘写满。逐级压测：从 1 个并发开始，观察吞吐、P95 时延、内存、显存、队列长度，直到出现拐点，再预留安全余量。

当队列持续增长时，优先做**背压**：限制上传、按租户配额、拒绝超大任务或扩容 worker。让请求无限进入只会把“稍后失败”变为“所有人一起超时”。

## 一个可部署的最小分层

```text
客户端
  -> API：认证、文件限制、创建任务
  -> 对象存储/受管卷：原件与页级产物
  -> 数据库：任务状态、审计、幂等键
  -> 队列：等待执行的工作
  -> OCR worker：转换、渲染、模型推理
  -> 结果 API / 回调：读取 manifest 与状态
```

这张图不是要求你第一天就部署六个组件。小规模可以从 API + 单 worker + 本地受管目录开始；但每一层的职责要清楚，规模增加时才能替换实现而不改接口。尤其不要把大文件二进制塞入关系数据库行，也不要让 API 进程承担无限长的 GPU 任务。

## 安全与隐私是功能的一部分

- 用 TLS 传输，访问原件和结果时做身份认证与最小权限授权。
- 对象存储或文件目录按租户/项目隔离；临时文件目录不可被 Web 直接下载。
- 日志中不记录原文、身份证号、访问令牌和预签名 URL；必要调试使用脱敏样本。
- 对上传文件设置格式、大小、页数、图像像素和解压深度上限。
- 明确保留期限：原件、页图、结果和日志的保留期可以不同；到期删除要可审计。
- 模型、转换器和系统镜像及时更新；转换器应在低权限、资源受限环境运行。

## 备份、恢复与升级

备份不等于“数据目录还在”。至少定期验证三件事：任务数据库能恢复、原件/结果对象能读取、恢复后 manifest 仍指向实际存在的文件。恢复演练必须在隔离环境进行，避免把旧数据覆盖正在运行的服务。

模型或管线升级前，使用固定评测集跑新旧版本对比，并保存版本号和指标。若新版本出现关键字段回归，应能把新任务切回旧 worker 或旧模型；已经生成的结果应保留 `pipeline_version`，不能在原地悄悄改写。

## 运行故障的第一响应

| 信号 | 常见原因 | 先做什么 |
| --- | --- | --- |
| 成功率下降 | 新格式、依赖故障、模型加载失败 | 按错误码和版本分组，抽查失败输入 |
| 队列积压 | 流量突增、worker 卡死、单页太慢 | 看等待时间与活跃 worker，启用配额/扩容 |
| GPU OOM | 分辨率、批量、并发过高 | 降并发和图像大小，重启泄漏 worker |
| 磁盘增长 | 页图、失败任务、日志未清理 | 分析目录与保留策略，勿直接删生产证据 |
| 结果质量突降 | 输入分布或模型版本变化 | 跑固定集，回滚或隔离新版本 |

## 小结

- OCR 质量必须按用途衡量：CER/WER 之外，还要看字段、结构和人工复核效果。
- 固定、脱敏、有人工真值的评测集是模型升级的安全带。
- 端到端指标、队列长度与资源占用比单次模型耗时更能指导部署。
- 可恢复的存储、版本记录、权限与保留策略，是文档智能系统的组成部分，不是上线后的装饰。
