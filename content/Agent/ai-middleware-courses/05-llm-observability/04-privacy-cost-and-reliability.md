trace 能解释某一次请求，却不能公平回答“换了模型或提示词后是否更好”。线上流量每天都不同：节假日、客户来源、语言和输入长度都会变化。要比较改动，必须冻结一批经过授权的样本，用固定规则同时运行基线与候选版本。本讲把质量、成本、隐私和告警放到同一个可复现的治理流程中。

## 前置与实验目标

需要理解第一讲的 token、延迟和 trace，Python 标准库即可完成核心实验。完成后，你会得到一份不可变 JSONL 小数据集、一段确定性评分器和一份能解释“为什么告警”的指标规则。真实模型可后接，但不应阻断学习。

## 什么是评测集

评测集不是任意导出的生产对话，而是**有用途、版本、许可和判定规则的样本集合**。每次修改提示词、模型、路由或工具后，使用相同输入运行，才有比较基础。

下面创建 `eval-v1.jsonl`。内容为合成文本；真实场景需要完成脱敏、授权和访问控制后再入库：

```json
{"id":"copy-001","input":"为环保水杯写一句标题","expected":{"max_chars":20,"must_not_contain":["保证","治疗"]},"tags":["short","safety"]}
{"id":"support-002","input":"订单延迟三天，如何回复？","expected":{"must_contain":["订单号"],"must_not_contain":["已经退款"]},"tags":["support","policy"]}
```

不要修改已经用于报告的 `eval-v1`；修正标注应建立 `eval-v2`。一次实验至少记录数据集版本、应用提交版本、提示词版本、模型标识、参数、评分器版本、价格表版本和执行时间。这些字段就是实验的“配方”。

## 从确定性规则开始评分

大模型裁判可以处理开放式质量，却也会引入版本、成本和随机性。小白应先使用可解释的规则，让评分失败时知道问题在哪。保存为 `score.py`：

```python
def score(output: str, expected: dict) -> dict:
    failures = []
    if len(output) > expected.get("max_chars", float("inf")):
        failures.append("too_long")
    for word in expected.get("must_contain", []):
        if word not in output:
            failures.append(f"missing:{word}")
    for word in expected.get("must_not_contain", []):
        if word in output:
            failures.append(f"forbidden:{word}")
    return {"passed": not failures, "failures": failures}

print(score("环保水杯，轻装出行", {"max_chars": 20}))
print(score("我们已经退款", {"must_not_contain": ["已经退款"]}))
```

预期第一行的 `passed` 为 `True`；第二行是 `False` 且包含 `forbidden:已经退款`。这不是“衡量所有语言质量”的万能方法，而是把明确的合规、格式和事实约束从模糊感受中分离出来。

## 如何比较基线和候选

对同一数据集同时得到 `baseline.jsonl` 和 `candidate.jsonl`，按 `id` 对齐后计算通过率、成本和延迟。不要只看总平均；按语言、输入长度、风险标签切片，才能发现候选模型只在某类用户退化。

通过率为：

$$
pass\_rate = \frac{\text{passed samples}}{\text{all evaluated samples}}
$$

如果基线 100 条通过 92 条、候选通过 93 条，不能仅凭一个百分点断言升级成功。应查看失败样本、置信区间或至少重复运行；若模型有随机性，固定种子（若供应商支持）、温度和重试策略，并记录无法固定的条件。

## 成本不是一个魔法数字

每条 generation 的成本应由实际 usage 与版本化价表计算。把输入、输出、缓存读取等不同计费类别分开；没有 usage 时只记录估算，不能与账单做严格对账。把总成本除以成功数可得到“每次成功成本”，它比“请求平均成本”更能暴露失败重试造成的浪费。

同时观察这组指标：

- 请求量、成功率、可重试错误率和最终失败率。
- TTFT、总耗时的 p50/p95，以及按模型和输入长度切片的值。
- 输入/输出 token 分布、截断率、重试次数和每次成功成本。
- 质量规则的失败类别，而不是只有一个总分。

## 告警要能让人采取动作

告警不是把所有曲线都设阈值。好的告警描述影响、窗口和第一步处理：

| 条件示例 | 可能影响 | 首先检查 |
| --- | --- | --- |
| 15 分钟最终失败率持续超过基线 | 用户得不到结果 | 上游模型状态、超时和部署变更 |
| p95 TTFT 持续升高且请求量未增 | 首字等待变慢 | 模型端、网络、连接池、输入长度 |
| 队列最老任务等待持续增加 | trace 延迟出现或丢失风险 | Worker 数、失败重试、下游存储 |
| 每次成功成本突增 | 预算风险 | 模型路由、输出长度、价格表版本 |

阈值来自自己的历史基线和服务目标，不应照抄别人的 `p95 < 2s`。告警触发后应有 runbook 链接、负责人和静默规则；没有行动路径的告警只是噪声。

## 隐私与保留期是数据模型的一部分

用户输入、模型输出、工具参数和错误堆栈都可能含个人信息、商业秘密或提示词注入载荷。先定义：哪些字段允许采集、谁能查看、保留多久、怎样删除、导出如何审批。应在 SDK 发送前脱敏和截断，不能依赖 UI 的隐藏按钮。将原文加密也不自动解决过度采集问题。

一个实用的默认值是：默认只传长度、哈希、分类、版本、用量、耗时和错误类别；只有得到明确授权的低风险样本才保留内容，并设置更短的保留期。把这个策略版本记录到 trace，未来才能解释历史数据的缺口。

## 常见错误与排查顺序

1. **评测每次结果都不同**：检查模型参数、随机种子、外部工具和数据集文件哈希；先把不稳定因素写入实验记录。
2. **高分但线上投诉**：规则覆盖面太窄。收集经过审查的失败模式，新增标签和断言，不要只提高一个总分阈值。
3. **成本与账单对不上**：区分请求发生时间与账单结算时间，核对模型、区域、缓存和重试；检查是实际 usage 还是估算值。
4. **告警太多被忽略**：合并重复条件，按影响分级，给每条告警写首个排查动作，并定期回顾误报。

## 小结

- 离线评测用冻结输入和版本化“配方”让模型改动可比较。
- 先使用确定性规则，再逐步引入人工或模型裁判，才能知道评分的可信边界。
- 成本、延迟、质量、隐私和告警是同一运行治理问题的不同面，不应各自孤立。
