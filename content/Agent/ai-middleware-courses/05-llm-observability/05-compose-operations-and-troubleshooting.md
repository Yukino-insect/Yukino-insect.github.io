当观测平台本身不可见时，应用往往仍能继续回答用户；这正是它危险的地方。你可能数小时后才发现 trace 一直没被处理。本讲不把任何项目的 Compose 文件当成教材，而是从通用职责理解自托管平台，并给出可在隔离环境演练的恢复方法。

## 前置与实验目标

需要完成第二讲，且只在个人开发机或专门测试环境练习。目标是能读懂一套 Compose 中的组件职责，能区分“接入成功”和“已可查询”，能做可验证的备份恢复。绝不要在唯一生产实例上为了练习而停止数据库、清空队列或执行带 `-v` 的删除命令。

## 将部署拆成四个职责

不管产品名称如何，通常都能归为下列职责：

```text
接入层：认证、HTTP/OTLP 接收、限流
处理层：队列、Worker、重试、死信或失败记录
数据层：事务元数据、分析查询数据、对象附件
控制层：Web、权限、配置、健康检查与告警
```

这比死记容器名有用。例如关系数据库擅长项目、用户、权限和配置的事务一致性；列式分析库擅长在大量 span 上按时间与属性聚合；对象存储适合较大附件；队列暂存突发写入。它们不是可随意互换的四个“数据库”。

## 先建立健康基线

启动前把当前 Compose 展开并记录服务、卷与端口；不做写操作：

```powershell
docker compose config --quiet
docker compose config --services
docker compose ps
docker volume ls
```

随后发送第二讲的一条合成 trace，并记录从 `flush()` 到页面可见的时间。这个时间是你的基线。若有健康端点，则把它区分为 liveness（进程活着）与 readiness（能连接必要依赖并提供功能）；不要因为某一个容器 `running` 就断言整个数据管道正常。

## 队列：缓冲不是无限容量

队列将接入和写入解耦。入队速率大于消费速率时，队列深度增长；当达到内存、磁盘或配额上限，新的事件可能被拒绝、淘汰或长期延迟。每个队列至少监控：等待数、运行数、失败数、最老消息年龄、重试次数和死信数。

一个近似关系很有帮助：若平均入队速率为 $\lambda$、平均处理速率为 $\mu$，长期只有 $\mu > \lambda$ 才能消化积压。短时突发可以靠容量吸收，但不能修复持续的处理能力不足。发现积压时先查 Worker 错误、下游数据库延迟和毒消息，再谨慎扩容；盲目增加 Worker 可能进一步压垮已经变慢的存储。

## 存储：每一种都要备份和恢复验证

备份不是“某个目录存在压缩包”。一个可信流程包含：

1. 明确需要恢复的范围：事务数据、分析数据、对象附件、配置与密钥引用各是什么。
2. 按各存储产品支持的方式创建一致性备份；运行中的数据库不要用随意复制数据目录代替官方工具。
3. 记录备份时间、版本、校验和、加密位置与保留期。
4. 在**隔离的新实例**恢复，不覆盖原实例。
5. 用已知 trace 查询、对象读取和权限登录验证恢复结果，并记录恢复时间目标。

对象附件、分析数据和事务元数据经常具有不同的保留期与成本。删掉分析表未必会删对象，反之亦然；生命周期策略必须协调，否则会出现页面仍有链接但附件已消失，或对象无限累积的情况。

## 一个安全的恢复演练模板

下面是操作顺序，不绑定某一个数据库命令。每种存储请替换为其官方备份/恢复工具，并先在测试环境验证。

```text
1. 记录版本、镜像摘要、服务状态和数据量
2. 生成一致性备份，计算或读取校验信息
3. 新建隔离网络、卷和恢复实例
4. 恢复备份；不要连接原生产队列或对象桶
5. 查询一条已知测试 trace，并读取关联测试对象
6. 记录恢复耗时、缺失项、版本兼容问题
7. 清理隔离环境前保留演练报告
```

预期不是“恢复命令没有报错”，而是第 5 步的业务可读验证通过。恢复演练失败本身是有价值的结果：它说明当前备份不能作为事故时的承诺。

## 升级与回滚

升级前阅读目标版本的迁移说明，备份并在副本上演练。尤其要确认数据库 schema、队列格式和分析库文件格式是否向后兼容。很多系统的迁移只支持向前，简单把镜像 tag 改回旧版本并不等于安全回滚。

一个保守流程是：冻结变更，备份，复制生产代表性数据到隔离环境，升级并执行合成 trace 回归，观察 Worker 和查询，再分批部署。若失败，优先切回旧的**应用流量**或从已验证备份恢复；不要猜测性删除卷来“重置”。

## 常见故障的证据链

| 现象 | 先看什么 | 常见原因 |
| --- | --- | --- |
| 应用 SDK 不报错但页面没有 trace | 接入日志、队列深度、Worker 错误 | 异步积压、凭据/目标错误、Worker 停止 |
| 页面有新 trace 但很慢 | 分析库资源、查询时间范围、索引/分区 | 宽时间查询、磁盘压力、小文件或小 part 过多 |
| 事件突然丢失 | 接入拒绝、队列淘汰策略、应用 exporter 指标 | 队列上限、网络故障、采样或内存队列满 |
| Worker 不断重试 | 首个失败堆栈、失败消息类别、下游存储 | schema 不匹配、权限、毒消息、连接耗尽 |
| 磁盘持续增长 | 各卷、对象保留期、备份目录 | 无 TTL、附件未清理、查询日志或备份无轮转 |

排查始终从“最后一个已知成功点”往下游推进：应用是否创建事件，接入是否接受，是否成功入队，Worker 是否处理，目标存储是否写入，查询是否可见。这个顺序避免在页面上猜测。

## 生产前还缺什么

本机 Compose 适合理解和开发，但生产还必须决定网络隔离与 TLS、管理员身份与审计、密钥轮换、资源限额、自动扩缩、跨故障域备份、保留期、容量预算、升级窗口和责任人。若这些没有明确答案，就不能因为“容器全绿”而称为生产可用。

## 小结

- 自托管观测平台是接入、处理、数据和控制四类职责的组合，不是一个 Dashboard。
- 队列积压和存储恢复都需要独立指标与演练；HTTP 接收成功不表示数据可查询。
- 恢复的验收标准是隔离环境中读回已知数据，而不是命令返回零退出码。
