事件监听和函数回调看起来相似：都是“先把一段代码交出去，以后再由别人调用”。区别在于关注点。监听器通常订阅用户或系统事件，例如按钮被点击；**回调接口**则把一次异步操作的成功、失败或进度交还给调用方，例如网络搜索完成。它是 Java 没有一等函数时表达“将来执行什么”的常用方式。

真正棘手的地方不在于写一个接口，而在于异步完成时页面可能已经离开，且后台线程不能触碰 View。本章先建立线程模型，再实现一个可运行的最小搜索任务，最后讨论生命周期与内存泄漏的边界。

## 为什么耗时操作不能直接写在点击回调中

Android 有一个 UI 主线程（也称 main thread）。创建 Activity、分发点击、测量布局、绘制 View 都主要在它上面进行。若点击事件里同步等待网络 3 秒，主线程在这 3 秒内既不能绘制“加载中”，也不能响应返回或滚动；时间再长，系统会认为应用无响应。

因此要把工作拆成两个阶段：

```text
主线程：点击 -> 校验输入 -> 显示加载状态
工作线程：执行网络/磁盘/计算
主线程：收到结果 -> 更新 TextView、Button、列表
```

回调接口描述“工作线程完成后要通知什么”，而 `Handler(Looper.getMainLooper())` 描述“把 UI 更新安排回主线程执行”。二者的职责不同，缺一不可。

## 先定义一个有成功和失败分支的回调契约

下面的 `Callback<T>` 是泛型接口：`T` 表示成功结果的类型。调用者不需要知道任务内部怎样执行，只需要承诺怎样消费成功和失败结果。

```java
package com.example.callbackdemo;

public interface Callback<T> {
    void onSuccess(T value);

    void onError(Throwable error);
}
```

接口是一个契约，而不是线程策略。`onSuccess` 到底在哪个线程运行，必须由 API 文档或实现明确说明；否则调用者很容易在后台线程更新 UI，得到 `CalledFromWrongThreadException` 或更隐蔽的问题。本章接下来的 `SearchRepository` 会明确规定：它在工作线程完成查询，但把回调切换到主线程。

## 一个最小的异步 Repository

此例不访问真实网络，以 `Thread.sleep` 模拟延迟。实际项目把 `loadFromNetwork` 换成 HTTP 客户端调用即可，但网络失败、超时和取消策略仍必须保留。

```java
package com.example.callbackdemo;

import android.os.Handler;
import android.os.Looper;

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class SearchRepository {
    private final ExecutorService executor = Executors.newSingleThreadExecutor();
    private final Handler mainHandler = new Handler(Looper.getMainLooper());

    // 约定：callback 的两个方法都在主线程调用。
    public void search(String query, Callback<String> callback) {
        executor.execute(() -> {
            try {
                String result = loadFromNetwork(query);
                mainHandler.post(() -> callback.onSuccess(result));
            } catch (Exception error) {
                mainHandler.post(() -> callback.onError(error));
            }
        });
    }

    private String loadFromNetwork(String query) throws InterruptedException {
        Thread.sleep(800); // 仅模拟网络延迟，真实代码不能用它代替网络库
        if (query.equalsIgnoreCase("error")) {
            throw new IllegalStateException("模拟的网络错误");
        }
        return "“" + query + "” 的搜索结果：Android 回调示例";
    }

    public void shutdown() {
        executor.shutdownNow();
    }
}
```

`ExecutorService` 拥有工作线程，`Handler` 关联主线程的 `Looper`。`post` 不会立即在当前工作线程执行 lambda，而是把它放进主线程消息队列，等主线程取到消息后执行。于是 `TextView.setText` 发生在正确线程。这也是“异步 UI 更新”的完整因果链，而不只是多写一层回调。

## 在 Activity 中使用回调，并处理页面离开

布局可沿用上一章的 `EditText`、`Button` 和 `TextView`。下面的 `SearchActivity` 展示了加载态、重复点击保护和生命周期检查：

```java
package com.example.callbackdemo;

import android.os.Bundle;
import android.widget.Button;
import android.widget.EditText;
import android.widget.TextView;

import androidx.annotation.Nullable;
import androidx.appcompat.app.AppCompatActivity;

public class SearchActivity extends AppCompatActivity {
    private final SearchRepository repository = new SearchRepository();
    private boolean pageActive;
    private Button searchButton;
    private TextView resultText;

    @Override
    protected void onCreate(@Nullable Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_search);

        EditText queryInput = findViewById(R.id.queryInput);
        searchButton = findViewById(R.id.searchButton);
        resultText = findViewById(R.id.resultText);

        searchButton.setOnClickListener(view -> {
            String query = queryInput.getText().toString().trim();
            if (query.isEmpty()) {
                queryInput.setError("请输入关键词");
                return;
            }
            search(query);
        });
    }

    @Override
    protected void onStart() {
        super.onStart();
        pageActive = true;
    }

    @Override
    protected void onStop() {
        pageActive = false;
        super.onStop();
    }

    private void search(String query) {
        searchButton.setEnabled(false);
        resultText.setText("正在搜索…");
        repository.search(query, new Callback<String>() {
            @Override
            public void onSuccess(String value) {
                if (!pageActive) {
                    return;
                }
                resultText.setText(value);
                searchButton.setEnabled(true);
            }

            @Override
            public void onError(Throwable error) {
                if (!pageActive) {
                    return;
                }
                resultText.setText("搜索失败：" + error.getMessage());
                searchButton.setEnabled(true);
            }
        });
    }

    @Override
    protected void onDestroy() {
        repository.shutdown();
        super.onDestroy();
    }
}
```

这里的 `pageActive` 只是让初学者看清“回调可能晚于页面”的事实，不是大型应用中的最终方案：如果 Activity 因旋转而重建，旧任务被中断，新页面也没有自动恢复结果。生产项目通常使用 ViewModel 保存界面状态，用生命周期感知的可观察数据把状态交给当前 Activity/Fragment 渲染；网络库也会提供取消、超时和结构化并发能力。

同时要注意：匿名内部回调隐式持有外部 `Activity`。若任务比页面寿命长，强引用会阻止旧页面回收。因此 Repository 不应该保存 Activity、View 或 `Context` 的强引用；页面停止时要取消不再需要的请求，或让结果进入与页面分离的状态层。不要把 `TextView` 直接传给 Repository 让它更新——这会把数据层和 UI 线程耦死。

## 回调、监听器和返回值如何区分

| 机制 | 谁触发 | 何时发生 | 示例 |
| --- | --- | --- | --- |
| 普通返回值 | 当前调用者 | 方法同步结束时 | `String.trim()` |
| 事件监听器 | View 或系统 | 用户/系统事件出现时 | `OnClickListener` |
| 业务回调 | 异步任务提供者 | 请求成功、失败或进度变化时 | `Callback<String>` |

它们都可能使用接口或 lambda，但时间模型不同。普通返回值必须等到工作完成，不能用于不阻塞主线程的网络请求；回调允许现在返回、以后通知。调用回调时仍要规定线程、异常、只调用一次还是多次、以及取消后是否还会通知。

## 让接口保持可维护

回调接口应该表达一个清楚的业务结果，而不是泄露过多内部细节。例如 `Callback<User>` 比 `Callback<String>` 更适合真实的用户资料场景；错误不应只给布尔值，因为调用方需要区分网络不可用、权限问题和服务端错误。对于持续数据流或多个复杂状态，单个回调会形成“回调嵌套”，此时应改用 ViewModel 管理 `Loading / Content / Error` 等状态，而不是在 Activity 里层层传匿名类。

回调本身也会抛异常。任务实现者不应让一个 UI 回调异常杀死工作线程；调用方则应保证 `onSuccess` 只做渲染和轻量逻辑，把下一次耗时操作重新交给受控的异步层。

## 小结

- 回调接口把异步结果交还给调用方；监听器处理用户或系统事件，两者的时间模型不同。
- 工作线程负责耗时 I/O 和计算，`Handler` 把 View 更新投递回 UI 主线程。
- 回调抵达时页面可能不可见或已销毁；必须取消无用工作或交给生命周期感知的状态层。
- 不让 Repository 持有 Activity/View，接口要明确线程、成功、失败、取消和调用次数的契约。
