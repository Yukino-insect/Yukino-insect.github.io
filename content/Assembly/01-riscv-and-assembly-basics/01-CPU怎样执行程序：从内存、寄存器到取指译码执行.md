在学习汇编前，最值得先弄清的并不是某条指令怎么拼写，而是一个更朴素的问题：**CPU 到底在做什么？**

它不会阅读 C、Java 或 Python 的源代码；也不知道“变量”“函数”“循环”这些高级概念。CPU 所能处理的是一串符合特定规则的二进制位。它反复做同一件事：找到下一条指令，把指令读进来，按规则解释并执行，然后决定下一条指令的位置。看似复杂的软件，归根结底都由这个循环展开。

本文不要求任何汇编基础。读完后，你应当能回答这些问题：程序为什么能被 CPU 执行？PC、寄存器和内存分别是什么？为什么“地址”和“地址里的值”不是同一回事？一条加法、一次内存访问、一个 `if` 或一次函数调用，怎样改变机器状态？这些就是阅读后续 RISC-V 与 xv6 启动代码所需的地基。急着背指令名称反而没有意义；没有地基的宏伟视角，只是把人送到高处再撤走梯子而已。

## 一、先建立一台“足够简单”的计算机

先暂时忽略缓存、多核、虚拟内存等细节，把一台能运行程序的机器想成下面这样：

```text
                         地址、数据、指令
┌──────────────────┐  <────────────────────>  ┌────────────────────┐
│       CPU        │                            │        内存        │
│                  │                            │                    │
│  PC：下一条位置   │                            │  指令的机器码      │
│  通用寄存器       │                            │  程序的数据        │
│  运算/控制部件    │                            │  调用栈、全局变量  │
└──────────────────┘                            └────────────────────┘
```

这里有三个必须分开的角色：

- **内存（memory）**：容量大，保存程序和数据；每个位置都有地址。
- **寄存器（register）**：CPU 芯片内部少量、很快的存储格，用来放眼下正在计算的值或地址。
- **PC（Program Counter，程序计数器）**：一个特殊寄存器，保存“下一条要执行的指令在哪个地址”。在 RISC-V 文档中通常直接写 `pc`。

CPU 并不是从头到尾“阅读整个程序”。在任意一个瞬间，它只关心 PC 指向的一条指令、这条指令所涉及的寄存器，以及必要时访问的内存。

## 二、从人写的代码到机器能执行的二进制

你写的 C 代码是文本，适合人和编译器理解：

```c
int add_one(int x) {
    return x + 1;
}
```

它不会原封不动地躺进 CPU。常见的转换过程如下：

```text
C 源文件 .c
  │ 编译器：分析语法、类型、变量和函数
  ▼
汇编文本 .s
  │ 汇编器：把助记符编码为二进制指令
  ▼
目标文件 .o（机器码 + 符号 + 重定位信息）
  │ 链接器：合并多个目标文件，解决“函数/变量到底在哪”
  ▼
可执行文件或内核映像
  │ 加载器、操作系统或模拟器放入内存，并设定起始 PC
  ▼
CPU 从 PC 指向的位置开始执行机器码
```

例如，RISC-V 汇编中的：

```asm
addi    a0, a0, 1
```

是人类可读的**助记符**，含义是“把寄存器 `a0` 的值加 1，再写回 `a0`”。CPU 实际读到的不是字符 `a`、`d`、`d`、`i`，而是固定长度的比特字段，例如其中一部分表示“加立即数”，一部分表示源寄存器和目标寄存器，一部分表示常数 `1`。汇编器负责把文本变为这些比特；反汇编器则能把比特尽量翻回 `addi a0, a0, 1` 这样的文本。

这带来一个重要结论：**同一段内存中的比特本身没有“天生是代码”或“天生是数据”的标签。**CPU 把 PC 指向的内容按指令格式解码时，它是指令；一条加载指令把某处内容读出来时，它是数据。操作系统通常会用页面权限规定哪些内存区域可执行、哪些只能存数据，以避免这种界限被随意混淆。

## 三、二进制、字节、字与地址：别被进制吓住

计算机中的开关可抽象为 0 和 1，因而底层通常用二进制表示信息。为了书写方便，程序员还常用十六进制：每一位十六进制数正好对应 4 个二进制位。

```text
十进制  26  = 二进制 0001 1010 = 十六进制 0x1A
十进制 255  = 二进制 1111 1111 = 十六进制 0xFF
```

前缀 `0x` 表示十六进制。因此 `0x80000000` 不是某种神秘口令，只是一个用十六进制写出的数。在 xv6 启动语境中，它恰好是 QEMU 放置内核代码的一个地址。

### 1. 内存最小可寻址单位通常是字节

可以把内存看作极长的编号抽屉，每个抽屉保存 8 个二进制位，即 **1 字节（byte）**：

```text
地址             一个字节的内容（十六进制）
0x1000           0x2A
0x1001           0x00
0x1002           0x00
0x1003           0x00
```

`0x1000` 是位置，`0x2A` 是该位置存放的内容。两者绝不能混为一谈：

```text
“a0 = 0x1000”                 只是 a0 保存了一个地址数值
“读取内存[0x1000]”            才是在取该地址中的内容
```

整数、指针和指令通常会占用多个连续字节。RISC-V 的 `RV64` 环境中，常说的 64 位整数是 8 字节；一条基本 RISC-V 指令通常是 4 字节。于是连续的指令地址常像这样增长：

```text
0x80000000  第一条 4 字节指令
0x80000004  第二条 4 字节指令
0x80000008  第三条 4 字节指令
```

这里的“通常”很重要：RISC-V 也可启用 16 位压缩指令扩展，因此真实 PC 的步长不必永远是 4。初学阶段可先把普通 32 位指令理解为顺序执行时 `pc + 4`，等需要读压缩指令时再补这一层例外。

### 2. “字（word）”是约定，不是总等于一个字节

一个字节固定为 8 位；而“字”是体系结构术语，含义会随语境变化。在 RISC-V 指令名中，`lw` 是读 32 位的 word，`ld` 是读 64 位的 doubleword。不要看到“内存地址”就想象它只装一个完整数字：地址先定位到字节，指令再决定从那里连续取多少字节、怎样解释这些字节。

## 四、寄存器：CPU 正在手边使用的小纸条

内存能存很多内容，但 CPU 不会把算术直接对所有内存格进行。它会先把眼下需要的数据放进寄存器，在寄存器之间运算，必要时再存回内存。

RISC-V 有 32 个通用整数寄存器，编号为 `x0` 到 `x31`。汇编中经常使用更有意义的别名：

```text
编号/别名       初学时可以先这样理解
x0 / zero       永远读作 0；写进去的值会被丢弃
x1 / ra         返回地址（函数调用后回到哪里）
x2 / sp         栈指针（当前栈顶的位置）
x10 / a0        第一个参数，也常存函数返回值
x11 / a1        第二个参数
x5-x7 / t0-t2   临时工作寄存器
x8 / s0 或 fp   需按调用约定保存的寄存器，也可作帧指针
```

寄存器名不等于数据类型。`a0` 并不“只能存参数”，`sp` 也不是特殊内存区域；这些别名主要是 ABI（调用约定）给出的分工，让不同编译器、不同函数写出的代码能协作。CPU 看到的仍是 `x10`、`x2` 这样的编号。

特别要记住两点：

1. `zero` 恒为 0，因而可用来实现清零或与 0 比较。
2. 寄存器保存的是一串位。`42`、地址 `0x1000`、字符 `'A'`，在寄存器眼中都只是位；“它代表什么”取决于接下来的指令和程序约定。

## 五、CPU 的核心循环：取指、译码、执行、更新 PC

现在把前面拼起来。对每条指令，CPU 的概念性工作流是：

```text
             ┌───────────────────────────────────────────┐
             │ 1. 取指：用 PC 从内存取得下一条机器指令    │
             ▼                                           │
      ┌───────────────┐                                  │
      │ 2. 译码        │ 识别操作、寄存器编号、立即数等    │
      └───────┬───────┘                                  │
              ▼                                          │
      ┌───────────────┐                                  │
      │ 3. 执行        │ 运算、加载、存储或改变控制流      │
      └───────┬───────┘                                  │
              ▼                                          │
      ┌───────────────┐                                  │
      │ 4. 写回/更新   │ 写寄存器或内存，并得到下一个 PC    │
      └───────┬───────┘                                  │
              └──────────── 回到第 1 步 ──────────────────┘
```

现实 CPU 为了性能会流水线执行、乱序执行、预测分支，甚至同时准备多条后续指令。但这些优化不改变程序可观察到的基本效果：它必须表现得像是遵守 ISA 规定的指令顺序和结果。初学时先使用这个顺序模型，才不会被硬件实现细节淹没。

### 1. 取指：PC 告诉 CPU 去哪里拿指令

若 `pc = 0x80000000`，CPU 从内存该处取出指令编码。这个过程可能经过指令缓存、虚拟地址翻译与执行权限检查；不过逻辑上就是：

```text
pc = 0x80000000  ──> 读取内存[0x80000000..下一条指令末尾]
```

如果这个地址不存在、没有执行权限，或字节组合不是合法指令，就不会“勉强执行”；硬件会产生异常并转交给系统的异常处理机制。

### 2. 译码：同一串位如何告诉 CPU 要做什么

CPU 按 RISC-V 的 ISA（Instruction Set Architecture，指令集架构）规则切分指令编码。概念上，一条指令会指出：

```text
操作：加法 / 读取内存 / 条件跳转……
输入：读哪几个寄存器，或使用什么立即数
输出：结果写进哪个寄存器，或写到哪个内存地址
```

所谓 **ISA**，就是软件与硬件之间的公开契约：只要都遵守 RISC-V 指令规则，同一份机器码就可以由不同厂商的 RISC-V CPU 执行。以后看到 `addi`、`ld`、`beq` 等名字，真正的重点不是名字本身，而是它们分别怎样读状态、怎样改状态。

### 3. 执行与写回：状态真的发生了什么变化

以 `addi a0, a0, 1` 为例：CPU 从旧 `a0` 取数，加上指令自带的常数 1，把结果写回 `a0`。若执行前 `a0 = 41`，执行后 `a0 = 42`。

顺序执行时，下一个 PC 指向紧随其后的指令；如果本条是分支、跳转、调用、返回或异常，下一个 PC 则会变成另一个地址。可以把 **寄存器、内存和 PC** 合称为机器当前的“状态”。阅读汇编的本质，是每读一条就追踪这三者怎么变。

## 六、例子一：逐条追踪“把内存中的数加 1”

下面的程序片段做了一件极普通的事：从地址 `0x1000` 读一个 64 位整数，加 1，再写回原处。为了聚焦 CPU 行为，先把 `la` 当作“把标签地址放进寄存器”的方便写法：

```asm
        la      t0, number       # t0 = number 的地址；假设 number 位于 0x1000
        ld      t1, 0(t0)        # t1 = 内存[t0 + 0] 的 64 位值
        addi    t1, t1, 1        # t1 = t1 + 1
        sd      t1, 0(t0)        # 内存[t0 + 0] = t1 的 64 位值
```

假设执行前的状态是：

```text
pc = 0x80000000
t0 = 未关心                 t1 = 未关心
内存[0x1000..0x1007] = 41    # number 的值为 41
```

为了清楚起见，以下把每条普通指令都视为 4 字节：

| 当前 PC | 取到的汇编含义 | 执行后发生的变化 |
| --- | --- | --- |
| `0x80000000` | `la t0, number` | `t0 = 0x1000`，PC 顺序到 `0x80000004` |
| `0x80000004` | `ld t1, 0(t0)` | 用 `t0 + 0` 算出地址 `0x1000`；读出 41，故 `t1 = 41`；PC 前进 |
| `0x80000008` | `addi t1, t1, 1` | `t1 = 42`；内存此刻还没有变化；PC 前进 |
| `0x8000000c` | `sd t1, 0(t0)` | 把 42 写回内存地址 `0x1000`；PC 前进 |

最终状态：

```text
t0 = 0x1000
t1 = 42
内存[0x1000..0x1007] = 42
pc = 0x80000010
```

这个例子包含汇编阅读中最常见的模式：**先取得地址，再加载数据，在寄存器中运算，最后存回内存。**`t0` 内的 `0x1000` 和 `number` 的值 `41` 绝不是一个东西。前者是“门牌号”，后者才是该门牌号所在位置的内容。

## 七、load/store：为什么加法通常不能直接对内存做

RISC-V 是典型的 **load/store 架构**。这句话的意思是：普通算术和比较指令的操作数来自寄存器；只有专门的加载（load）和存储（store）指令能直接访问普通内存。

```asm
ld      a0, 0(sp)    # 从地址 sp + 0 读 8 字节，写入 a0
sd      a0, 0(sp)    # 将 a0 的低 8 字节写到地址 sp + 0
```

若 `sp = 0x81001000`，那么 `0(sp)` 是一种地址计算写法，表示 `0x81001000 + 0`。它不是函数调用；括号只是汇编语法中“以某寄存器为基址、加一个偏移”的提示。

常见加载/存储指令可先这样记：

```text
lb / lbu      读 1 字节（有符号 / 无符号扩展）
lw            读 4 字节（32 位）
ld            读 8 字节（64 位，RV64 中常见）
sb / sw / sd  分别写 1 / 4 / 8 字节
```

使用哪一种取决于数据宽度和有无符号规则。以 `ld` 为例，它不是读取“一个变量”，而是从一个具体地址开始读取连续 8 字节，并按 RISC-V 的字节序把它们组合为一个 64 位值。初学时知道这一点就足够；字节序将在遇到内存布局时再仔细讨论。

## 八、例子二：一个 `if` 如何变成分支与 PC 改写

高级语言中的条件不是 CPU 能直接理解的概念。比如：

```c
if (x == 0)
    y = 1;
else
    y = 2;
```

设 `a0` 保存 `x`，`a1` 保存 `y`，可能对应如下汇编：

```asm
        beq     a0, zero, is_zero  # 若 a0 == 0，跳到 is_zero
        li      a1, 2               # 否则：y = 2
        j       done                # 跳过 is_zero 分支
is_zero:
        li      a1, 1               # y = 1
done:
        # 后续代码
```

标签 `is_zero:`、`done:` 是地址的名字，本身不是 CPU 要执行的指令。真正的关键在 `beq` 和 `j`：它们决定下一次取指的 PC。

假设 `beq` 位于 `0x2000`，下一条 `li` 位于 `0x2004`，`is_zero` 位于 `0x200c`。

```text
情形 A：a0 = 0
  pc=0x2000 执行 beq，条件成立
  下一 pc 直接变为 0x200c
  CPU 不会执行 0x2004 的 “y=2”，而执行 “y=1”

情形 B：a0 = 5
  pc=0x2000 执行 beq，条件不成立
  下一 pc 为顺序位置 0x2004
  CPU 执行 “y=2”，随后 j 将 pc 改到 done
```

```text
                   a0 == 0？
pc -> [beq] ──是──> is_zero: [a1 = 1] ──> done
              │
              否
              ▼
          [a1 = 2] ──> [j done] ────────> done
```

所以，`if` 的本质不是“CPU 知道条件语句”，而是 CPU 根据比较结果把 PC 设为不同的地址。循环也一样：循环尾部的条件分支若跳回开头，CPU 就再次取到那一段指令；若不跳，就继续往后执行。

## 九、函数调用：除了跳转，还要记得回来

函数调用比普通跳转多了一项任务：调用结束后，要回到调用点的下一条指令。因此 RISC-V 的调用机制需要一个返回地址寄存器 `ra`。

```text
调用前：pc 指向 call start
调用时：ra = “call 后的下一条指令地址”
        pc = start 的入口地址
返回时：pc = ra
```

汇编中常将调用写为：

```asm
        call    start
```

它是汇编器提供的伪指令，底层会被展开为合适的跳转/链接指令序列。你暂时只需把它理解为“跳到 `start`，同时保存返回位置到 `ra`”。函数若不再调用其他函数，往往能直接用 `ret`（回到 `ra` 指向的位置）返回；若它还要调用别的函数，就要先把原来的 `ra` 存到栈中，否则新的调用会覆盖它。

这就是为什么 xv6 的入口汇编要先建立 `sp`，再执行 `call start`：**C 函数通常需要栈来保存返回地址、局部变量和暂时值。**关于栈如何向低地址增长、`sp` 怎样划出一个函数的工作空间，会在“函数调用与栈”一文展开。

## 十、CPU 不是无条件服从：异常、权限与特权级的直觉

“PC 指向哪里就执行哪里”是必要的第一模型，但现代 CPU 还会先检查这件事是否允许。以下情形不会得到正常结果：

- 指令编码不合法，例如当前 RISC-V 实现不支持这条指令；
- 访问的地址不存在，或没有读/写/执行权限；
- 访问要求某种对齐而地址不满足；
- 普通程序试图执行只有操作系统内核才能做的特权操作。

这些情形会产生**异常（exception）**或**中断（interrupt）**，CPU 暂停原先的控制流，保存必要的信息，并把 PC 转去一个由系统预先安排的处理入口。粗略区别是：异常通常由当前指令引起（例如非法访问），中断通常来自外部事件（例如定时器到点）。

RISC-V 还定义了不同特权级。你可以先把它理解为权限由低到高的三层：

```text
U-mode（用户态）  普通应用程序
S-mode（监管态）  操作系统内核常用层
M-mode（机器态）  最底层硬件控制层，启动时常从这里开始
```

后续 xv6 文章中的 `mhartid`、CSR、`mret` 正是在这层机制中出现的名字。此刻不必背它们；只需知道 CPU 不只是算术器，它也负责受控地转换执行位置与权限状态。

## 十一、把模型接回 xv6 的 `entry.S`

现在可以不依赖神秘感地描述 xv6 的最初几步：

```text
1. QEMU 把内核映像放进一段内存，并把某个 hart 的 pc 设到入口地址。
2. hart 从 pc 指向的地址取指，开始执行 entry.S 汇编后生成的机器码。
3. 这段机器码读取当前 hart 的编号，计算并写入 sp，给它分配私有栈顶。
4. call start 既写入 ra，又改写 pc，于是 CPU 开始执行第一个 C 函数 start()。
5. 若 start 意外返回，入口的自旋跳转会反复改写 pc 到自己，避免落入未知字节。
```

注意第 3 步并没有“创建一个神奇的栈对象”。它只是把一个事先准备好的内存区域的高端地址写进 `sp`；之后按 ABI 编译出的 C 代码会把 `sp` 当作自己可用的栈顶。知道这点，再读 `la sp, stack0`、`csrr a1, mhartid`、`call start` 就不再是逐字硬背。

## 十二、初学者最容易混淆的几件事

### 1. “寄存器里有地址”不等于“已经读到了那个地址的值”

若 `a0 = 0x1000`，这只说明 `a0` 的比特恰好被程序当作地址使用。必须执行 `ld t0, 0(a0)` 之类的加载指令，`t0` 才会获得内存 `0x1000` 处的内容。

### 2. 汇编一行不必恰好对应一条机器指令

`li`、`la`、`call`、`j` 常是伪指令。汇编器可能将它们翻成一条或多条真实指令，具体形式还与常数大小、目标距离、链接布局有关。理解语义优先于猜测其二进制长度；需要精确验证时再看反汇编。

### 3. PC 不一定每次都加 4

普通顺序的 32 位指令常使 PC 前进 4 字节，但分支、跳转、异常会选择其他地址；启用了 RISC-V 压缩指令扩展时，指令也可能只有 2 字节。PC 的本质定义始终是“下一条指令地址”。

### 4. CPU 不能理解 C 变量名

`int count`、`struct task`、`for` 是编译器在翻译阶段理解的概念。运行时 CPU 只看到寄存器编号、地址和机器码。调试信息能帮助工具把地址重新显示为源代码变量，但那是工具提供的解释，不是 CPU 在识别变量名。

### 5. 不是所有内存都能执行，也不是所有地址都能随便读写

程序的正确性还受地址映射、读写执行权限和特权级限制。遇到“明明数值像个地址却访问失败”的情况，不能只怀疑数值计算，也要想到权限和映射。

## 十三、动手追踪练习

先独立写下每一步后的寄存器、内存或 PC，再展开答案。能追踪状态，才算真正读懂一小段汇编。

### 练习 1：寄存器算术

执行前：`t0 = 7`。依次执行：

```asm
addi    t1, t0, 3
addi    t0, t1, -2
```

执行后 `t0` 和 `t1` 分别是多少？

#### 参考答案

第一条读旧 `t0=7`，所以 `t1=10`；第二条读 `t1=10`，所以 `t0=8`。因此最终 `t0=8`、`t1=10`。

### 练习 2：地址与值

执行前：`sp = 0x2000`，内存地址 `0x2008` 中存放 64 位值 `9`。执行：

```asm
ld      a0, 8(sp)
addi    a0, a0, 4
```

最终 `a0` 是什么？内存 `0x2008` 中的数改变了吗？

#### 参考答案

`8(sp)` 先计算为 `0x2000 + 8 = 0x2008`，所以加载后 `a0=9`；加法后 `a0=13`。没有 `sd` 一类的存储指令，内存仍为 `9`。

### 练习 3：控制流

执行前 `a0 = 0`。阅读：

```asm
        beq     a0, zero, yes
        li      a1, 20
        j       done
yes:
        li      a1, 10
done:
        # 后续代码
```

`a1` 最终是多少？如果把 `a0` 改为 `3`，结果又是什么？提示：分支跳转会使中间某些指令根本没有被取到。

#### 参考答案

当 `a0=0` 时，`beq` 跳到 `yes`，`a1=10`；`li a1,20` 和其后的 `j` 都被跳过。当 `a0=3` 时，条件不成立，顺序执行 `li a1,20`，随后 `j done` 跳过 `yes`，故 `a1=20`。

### 练习 4：为什么先有 `sp` 再 `call`

为什么 xv6 入口代码在调用 C 函数 `start()` 前计算 `sp`，而不直接 `call start`？

#### 参考答案

`call` 本身负责设置返回地址并跳转，但进入的 C 函数很可能要建立栈帧、保存寄存器或使用局部变量，这些都依赖有效的 `sp`。如果 `sp` 未指向一段可用且对齐的内存，函数可能向未知地址写数据，结果无法预测。

## 小结：阅读汇编时该盯住什么

面对任何短小汇编片段，先不要逐字翻译。依次问自己：

1. 当前 `pc` 指向哪条指令，顺序执行后的下一条在哪里？
2. 该指令读了哪些寄存器、常数或内存地址？
3. 它改写了哪个寄存器或内存位置？
4. 它是否通过分支、调用、返回或异常改变了下一条 PC？
5. 某个数当前是普通整数、地址，还是按 ABI 约定承担参数/返回地址等角色？

掌握这五个问题，你已经拥有理解汇编的最小工具箱。下一篇再把这个模型落到 RISC-V 的寄存器命名与常用指令上；至于 xv6 的入口代码，不过是这些基础动作在一个特别早、特别需要谨慎的时刻被组合起来而已。
