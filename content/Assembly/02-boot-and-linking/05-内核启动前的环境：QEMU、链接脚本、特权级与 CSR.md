普通应用程序从操作系统获得一个已经准备好的世界：内存映射存在、栈已经分配、CPU 已处于合适的权限级别。内核启动恰好相反。它必须先回答“代码被放在哪里、CPU 从哪里取第一条指令、当前有什么权限、怎样进入日常内核模式”，然后才谈得上执行 `main()`。

xv6 的 `entry.S` 只解决最小的一步——建立早期栈并调用 `start()`。理解其中的 `0x80000000`、`_entry`、`mhartid`、Machine 模式与 `mret`，需要先建立这一章的启动环境地图。

## 〇、先把舞台看清：普通程序、裸机与启动链

### 你平时写的 `main()` 并不是程序真正的第一行

在桌面操作系统上写一个 C 程序时，我们习惯于把 `main()` 当成起点。严格地说，它只是**你的代码**的起点。在它之前，操作系统和 C 运行库已经做了大量准备：创建进程、建立虚拟地址空间、装入可执行文件、放好用户栈、准备命令行参数和环境变量，最后才由运行库调用 `main()`。

```text
CPU / 固件
    ↓
操作系统加载器：创建进程、页表、用户栈、权限边界
    ↓
C 运行库启动代码（crt）
    ↓
你写的 main()
```

因此，普通程序一开始就能调用函数、使用局部变量，并不是 C 语言天然保证了这些事，而是环境已经替它满足了前提：`sp` 有可用的栈、内存可以访问、异常可以由内核接管。

裸机（bare metal）程序没有这层现成服务。所谓“裸机”并不是没有机器，而是程序直接面对硬件或模拟硬件；引导加载器、单片机固件、操作系统刚启动的一小段代码都属于这个场景。它必须自己回答：

- 第一条机器指令存放在哪里？
- CPU 从哪个地址开始取指？
- 哪块内存可以作为栈？
- 此时能访问哪些控制寄存器和设备？
- 多个硬件线程同时启动时，谁先初始化共享资源？

xv6 是教学操作系统。它在你的电脑上看似由一个 QEMU 进程运行，但对 **QEMU 模拟出的 RISC-V 机器** 来说，xv6 正是要接管机器的内核：

```text
你的电脑硬件
  └─ 宿主操作系统（Windows / Linux / macOS）
      └─ QEMU 进程
          └─ 一台被模拟的 RISC-V 机器
              └─ xv6 内核
                  └─ xv6 用户进程
```

不要跳过这张层次图。这里的“内核启动”讨论的是倒数第二层，并不是 xv6 作为一个宿主机普通进程的启动过程。

### 从 QEMU 到 `main()` 的总路线

下面是本章所有名词所在的位置。先理解流程，再去理解每一个缩写；反过来背缩写通常只会得到一团不太体面的记忆碎片。

```text
执行 qemu-system-riscv64
      │
      ├─ 创建虚拟 CPU、RAM、串口、磁盘、定时器等设备
      ├─ 装载 kernel/kernel（一个 ELF 内核映像）到虚拟机 RAM
      ▼
把每个 hart 的 PC 放到内核的启动位置（xv6 教学配置中约为 0x80000000）
      ▼
CPU 从 PC 指向的内存取出第一条机器码
      ▼
_entry（entry.S）：为当前 hart 设置私有早期栈
      ▼
start()：仍在 M 模式，配置少量机器态状态
      ▼
mret：按 CSR 中准备好的状态切换控制流和权限
      ▼
main()：开始日常 S 模式内核初始化
```

这条链里，CPU 真正执行的只有内存中的机器码；`_entry`、`start`、`.text` 这些人类可读的名字，是编译、链接和调试阶段帮助我们定位字节的工具。

## 一、QEMU：一台可重复启动的虚拟 RISC-V 机器

QEMU 是模拟器。它可模拟 RISC-V CPU、内存、串口、磁盘、定时器等设备，让 xv6 像运行在一台确定的虚拟开发板上。教学时它尤其方便：机器布局稳定，可暂停、可重启，也可连接 GDB 单步查看寄存器。

类似启动命令：

```bash
qemu-system-riscv64 -machine virt -bios none -kernel kernel/kernel
```

| 选项 | 含义 |
| --- | --- |
| `qemu-system-riscv64` | 模拟 64 位 RISC-V 系统 |
| `-machine virt` | 选择 QEMU 的通用虚拟机器布局 |
| `-bios none` | 不额外运行 BIOS/固件，由内核直接接管 |
| `-kernel kernel/kernel` | 装载 xv6 内核映像 |

如果命令还带有如下选项，也应知道它们改变的是什么：

```bash
qemu-system-riscv64 -machine virt -bios none -kernel kernel/kernel -m 128M -smp 3
```

| 选项 | 直白解释 | 与本章的联系 |
| --- | --- | --- |
| `-machine virt` | 选择 QEMU 定义好的通用 RISC-V 虚拟开发板 | 它规定 RAM、串口和中断控制器等设备的大致布局 |
| `-m 128M` | 给虚拟机提供 128 MiB RAM | 决定内存容量，不是把入口地址改成 128 MiB |
| `-smp 3` | 创建 3 个可独立执行指令流的 hart | 三个 hart 都会进入 `_entry`，因此需要三份栈 |
| `-S` | CPU 启动后先暂停 | 常与 GDB 一起使用，便于观察第一条指令 |
| `-gdb tcp::1234` | 开一个远程调试端口 | GDB 可连接进来读 PC、`sp` 和反汇编 |

`-bios none` 是一个很重要的教学简化，不是 RISC-V 机器的普遍真相。真实硬件通常会先执行芯片中的 ROM，再执行固件；RISC-V 平台上常见的 OpenSBI 固件会完成部分机器态工作，然后将控制权交给操作系统。xv6 的这条 QEMU 启动路径刻意少放一层，以便你能直接追踪到内核入口。它省略的是环境层次，不是硬件规律。

还要避免一个常见想象：QEMU 并不是把 `entry.S` 的文本逐行“解释执行”。`kernel/kernel` 是 ELF 格式的二进制映像。QEMU 将应该装入内存的字节放到虚拟 RAM；之后 CPU 模型仅仅执行这些字节解码出的机器指令。

```text
entry.S、start.c（文本）
      │ 编译 / 汇编
      ▼
entry.o、start.o（机器码片段 + 符号 + 待修补的引用）
      │ 链接
      ▼
kernel/kernel（ELF：最终布局的内核映像）
      │ QEMU 装载
      ▼
虚拟机 RAM 中的字节
      │ PC 取指、译码、执行
      ▼
硬件实际执行的指令
```

### 用 QEMU 和 GDB 看见“第一条指令”

不要只相信示意图。可让 QEMU 在启动后暂停，再由 GDB 连接：

```bash
qemu-system-riscv64 -machine virt -bios none -kernel kernel/kernel -S -gdb tcp::1234
```

在另一个终端中（工具链名称以项目实际配置为准）：

```gdb
(gdb) file kernel/kernel
(gdb) target remote :1234
(gdb) info registers pc sp ra
(gdb) x/8i $pc
(gdb) si
```

`-S` 的意思是 *暂停（stop）*，并不是 Supervisor 模式；这两个字母相同只是无聊的巧合。`x/8i $pc` 会把 PC 指向的内存按八条指令反汇编，`si` 单步执行一条。若初始 PC 没有停在预期位置，首先核对 QEMU 是否真的带了 `-S`、是否使用了预期的 `-bios none` 启动路径，以及 GDB 加载的是否为当前构建出的 `kernel/kernel`。

在 xv6 的该启动约定中，QEMU 将内核放在物理地址 `0x80000000`，并让 hart 从这里开始执行。将它翻译成 CPU 语言就是：初始 PC 指向 `0x80000000`，CPU 从该地址取第一条机器指令。

## 二、链接脚本：谁决定 `_entry` 的地址

编译器和汇编器生成多个 `.o` 文件，但它们尚未决定整个内核第一条指令的最终地址。链接脚本是这份布局说明书，概念形状如下：

```ld
OUTPUT_ARCH("riscv")
ENTRY(_entry)

SECTIONS {
  . = 0x80000000;
  .text   : { *(.text .text.*) }
  .rodata : { *(.rodata .rodata.*) }
  .data   : { *(.data .data.*) }
  .bss    : { *(.bss .bss.*) }
}
```

### 为什么还需要链接器：`.o` 文件并不知道对方在哪里

编译器与汇编器分别把 `start.c`、`entry.S` 变成目标文件，例如 `start.o`、`entry.o`。目标文件中已经有机器码，但其中很多地址还不能立刻写死。譬如 `entry.S` 的 `call start` 知道有一个外部符号叫 `start`，却不一定知道 `start.c` 的代码最终会被排在什么地址。

链接器把许多目标文件组合起来，按链接脚本摆放每个节，并修补这些跨文件引用。这个过程叫**重定位**。因此，源文件的目录顺序、函数在文件中出现的先后，都不能可靠地推导最终地址；真正决定布局的是链接脚本、链接命令和输入节的大小。

理解 ELF 时，至少分清以下四个术语：

| 名称 | 作用 | 不该把它误认为 |
| --- | --- | --- |
| ELF header（文件头） | 记录架构、文件类型、入口地址等总体元数据 | 一段可直接执行的代码 |
| section（节） | 链接、调试阶段的组织单位，如 `.text`、`.data` | CPU 的某个特权级 |
| segment（程序段） | 装载阶段的组织单位，描述文件字节要放进内存的范围和权限 | section 的同义词 |
| symbol（符号） | 给地址、函数或对象命名，如 `_entry`、`stack0` | CPU 在运行时主动查询的变量名 |

通常 `.text` 放机器指令，`.rodata` 放只读常量，`.data` 放有初值的全局/静态数据，`.bss` 表示需要在内存中初始为零的一大片空间。`.bss` 不必在文件里存放同样多的零字节；装载时只需为它保留并清零相应内存。`stack0` 的具体节归属取决于其定义和编译结果，不能只凭变量名字判断。

脚本中的每一句也有不同身份：

1. `ENTRY(_entry)` 将 ELF 的入口字段设为符号 `_entry` 的最终地址；它本身不会让 CPU 执行跳转。
2. `. = 0x80000000` 修改的是链接器的“当前位置”计数器，表示之后安排的输出节从这个地址开始。
3. `.text : { *(.text .text.*) }` 不是一条 CPU 指令，而是说“把每个输入目标文件中的代码节收集为一个输出 `.text` 节”。
4. `entry.S` 里的 `.global _entry` 使这个符号对链接器和其他目标文件可见；标签 `_entry:` 把名字绑定到当前位置。

所以 CPU 不认识 `_entry` 这个拼写；它只认识 PC 中的数值。`_entry` 的价值在于：链接器能以这个名字算出地址、ELF 能记录入口、调试器能显示标签，人类终于不必靠记住一串地址工作。

关键关系只有四个：

1. `ENTRY(_entry)` 选定 ELF 入口符号；
2. `. = 0x80000000` 让后续段从这个地址开始布局；
3. `.text` 收集各个目标文件中的机器指令；
4. 符号地址随段布局确定，链接器再修补跨文件引用。

因此：

```text
QEMU 初始 PC：0x80000000
        ↓
链接脚本将 .text 放到 0x80000000
        ↓
entry.S 将全局标签 _entry 放进 .text
        ↓
CPU 开始执行 _entry 的第一条机器指令
```

CPU 不知道 `_entry` 这个名字；名称只在编译、汇编和链接阶段存在。CPU 只知道 PC 中的数值地址。

### 把“入口”变成可观察的事实

在项目根目录执行下列命令。工具链前缀在不同环境中可能不同，请以 Makefile 中实际的 `TOOLPREFIX` 为准：

```bash
# ELF 文件头：确认记录的入口地址
riscv64-unknown-elf-readelf -h kernel/kernel

# 节、程序段与符号：分别从链接、装载、命名三个视角检查
riscv64-unknown-elf-readelf -SW kernel/kernel
riscv64-unknown-elf-readelf -lW kernel/kernel
riscv64-unknown-elf-nm -n kernel/kernel | grep -E '(_entry|stack0|start|main)$'

# 机器最终看到的反汇编
riscv64-unknown-elf-objdump -d --no-show-raw-insn kernel/kernel
```

典型输出会有类似关系（中间地址会随版本变化）：

```text
Entry point address:               0x0000000080000000
0000000080000000 T _entry
00000000800000xx T start
0000000080000yyy T main
000000008000zzzz B stack0
```

`T` 常表示代码区域中的符号，`B` 常表示 bss 区域中的符号。重点不是记住示意中的 `xx`，而是检查 `_entry` 是否与入口对应、`start` 是否在代码中、`stack0` 是否有静态存储空间。反汇编中若没有原样出现 `la` 或 `call`，也不代表源代码消失了：它们常被汇编器展开为 `auipc`、`addi`、`jal` 或 `jalr` 等基础指令，再由链接器修补立即数。

## 三、物理地址、PC 和虚拟地址不是同一概念

启动处的 `0x80000000` 是物理内存布局中的地址。至少应分开三种提问：

| 说法 | 关注点 |
| --- | --- |
| “链接到 0x80000000” | 链接器为段和符号分配的地址 |
| “PC 是 0x80000000” | CPU 此刻从哪里取指 |
| “虚拟地址映射到物理页” | 启用页表后地址如何翻译 |

可以把它们放到三张不同的“地图”上理解：

```text
物理地址：虚拟机 RAM / 设备的硬件编号
      例：RAM 中某一字节的实际位置

PC：CPU 内部保存的“下一条取指地址”
      例：PC = 0x80000000，CPU 下一步从那里读取指令编码

虚拟地址：软件使用、且可能需由页表翻译的地址
      例：同一个 0x400000 可在两个进程中映射到不同物理页
```

PC 不是一种特殊的“内核地址”，而是一个寄存器。顺序执行时它前进；`j`、`call`、异常返回或 `mret` 都会修改它。CPU 取指时，地址转换若尚未开启，取指地址直接按物理内存布局使用；若已开启，则先经页表翻译并检查执行权限。

RISC-V 中与 S 模式地址翻译相关的关键 CSR 是 `satp`。它携带页表根位置和翻译模式等信息。启用页表后会出现两个很重要的现象：不同进程可以都使用看似相同的虚拟地址，却落到不同物理页；同一物理页也可能同时拥有不同的虚拟映射。早期启动阶段地址安排较直接，后续内核配置完整页表后则必须明确说清“此处是物理地址还是虚拟地址”。

一个有限但有用的类比是：物理地址像城市里建筑的真实坐标，虚拟地址像不同地图中的页码，页表像把页码查为真实坐标的索引；PC 则是导航仪当前准备前往的下一地点。别把类比用过头：真实 CPU 有 TLB、权限位和页表遍历，不是在翻纸。

在早期启动阶段，xv6 尚未建立后续内核使用的完整页表环境，地址安排比较直接。之后内核会配置地址转换；相同物理页可能由虚拟地址访问。早期某些数值碰巧相同，不代表这些概念永远可互换。

## 四、RISC-V 特权级：M、S、U

RISC-V 常见三层特权模式：

```text
M（Machine）模式：最高权限，平台级控制
S（Supervisor）模式：操作系统内核的日常运行环境
U（User）模式：普通应用程序
```

权限级不是性能档位，而是隔离边界。用户程序不能任意改写异常入口、关闭系统中断或配置机器级状态；否则每个程序都能接管整台计算机，操作系统这一层也就没有存在的理由了。

这三层不是“不同难度的指令集”，而是同一颗 CPU 对不同代码施加的访问权限。普通用户程序通常运行在 U 模式，日常操作系统内核运行在 S 模式，M 模式更接近平台级控制。真实平台中，M 模式常主要由固件使用；xv6 为了教学，会在自己的 `start()` 中直接完成一部分 M 模式工作，再降到 S 模式。不要把“xv6 的做法”误记成每个 RISC-V 操作系统唯一的启动形态。

### trap：CPU 如何有规则地中断当前控制流

trap 是“受架构约束的控制流转移”的总称。它可以由当前指令引起的异常（如非法指令、访问不允许的地址）、外部事件引起的中断（如时钟或串口），也可以由用户程序主动发起的系统调用触发。trap 不等于程序崩溃：定时器中断和系统调用都是操作系统正常工作的基础。

```text
正常执行的 U / S 模式指令
          │
          ├─ 异常、外部中断或系统调用
          ▼
硬件保存必要的返回状态，并转到该特权级规定的 trap 入口
          ▼
处理程序检查原因、处理事件
          ▼
专用返回指令恢复被打断的控制流
```

这也解释了为什么特权级和 CSR 不只是“高级概念”：异常入口若可由任何用户程序随便改写，系统调用和中断就无法安全地回到内核。M 模式的 trap 入口由 `mtvec` 一类 CSR 关联；S 模式也有对应的监管者态控制寄存器。现在只需把 trap 理解为一条受控的岔路，不必立刻背每一个位域。

xv6 最早期入口处于 M 模式，因为它需要设置一部分机器态控制状态。`start()` 完成必要准备后，通常通过 `mret` 将控制流转到 S 模式中的后续内核入口。

## 五、CSR：CPU 的控制状态寄存器

通用寄存器存放普通数值和地址；CSR（Control and Status Register）保存处理器控制/状态。启动相关的几个名字如下：

| CSR | 大意 | 在启动中的作用 |
| --- | --- | --- |
| `mhartid` | 当前 hart ID | 为不同 hart 选择不同早期栈 |
| `mstatus` | Machine 模式状态 | 控制 `mret` 后的部分状态与目标权限 |
| `mepc` | Machine exception program counter | `mret` 将跳转到这里给出的地址 |
| `mtvec` | Machine trap vector | M 模式异常/中断入口相关设置 |
| `satp` | 地址转换和保护状态 | 后续页表设置会涉及 |

```asm
csrr    a1, mhartid
```

不是读取普通内存，而是从 CPU 的控制状态中读取当前硬件线程编号：

```text
a1 = CSR[mhartid]
```

CSR 的可访问性受特权级限制，所以它们是内核和启动代码的重要概念，而不是普通用户程序可以随意读写的变量。

把 CSR 想成 CPU 的控制面板比想成“全局变量”更准确。通用寄存器 `a0`、`sp`、`ra` 用来放普通计算结果、参数和地址；CSR 则描述 CPU 正在如何工作。它们通常要用 `csrr`、`csrw`、`csrrw` 一类专门指令读写，并且硬件会按当前特权级检查访问是否允许。

下面几个名字最容易在启动代码里相遇：

| CSR | 零基础直觉 | 启动阶段为何出现 |
| --- | --- | --- |
| `mhartid` | “我是第几个硬件线程” | 同一入口代码为不同 hart 计算不同早期栈 |
| `mstatus` | M 模式的一组状态与控制位 | 影响 `mret` 返回/移交后的权限和部分中断状态 |
| `mepc` | M 模式专用的返回目标 PC | `mret` 执行时会从这里取得跳转目标 |
| `mtvec` | M 模式 trap 的处理入口 | 机器态异常/中断不能掉进未知内存 |
| `satp` | S 模式地址翻译与页表的关键配置 | 后续启用虚拟内存时需要它 |
| `mie` / `mip` | M 模式中断的使能和待处理状态 | 定时器等机器态初始化可能会接触 |

表格只在建立职责感，不应被误读为“每一版 xv6 必须以相同顺序写完全部 CSR”。真正的写入位置、掩码和值以当前 `start.c` 为证据。

## 六、`mret`：从机器态交给后续入口

`start()` 配置好必要状态后执行 `mret`（machine return）。概念上它会：

```text
1. 按 mstatus 的相关字段恢复目标特权状态；
2. 将 PC 设置为 mepc；
3. 继续执行目标地址处的代码。
```

更具体地说，xv6 的启动代码会先把 `mepc` 设置为一个后续入口（通常是 `main`），再在 `mstatus` 中配置 `mret` 之后应处的特权级，最后执行 `mret`。可以将其记为以下**概念伪代码**，它不是可直接编译的 C：

```c
mepc = 地址(main);          // 下一阶段从哪里继续
mstatus.MPP = S模式;         // mret 后应处的特权级
配置必要的中断、定时器等状态;
mret;                        // PC ← mepc，并依据 mstatus 完成移交
```

因此必须把两种“返回”严格分开：

| 指令 | 依据什么决定下一条 PC | 用在什么场景 |
| --- | --- | --- |
| `ret` | 通用寄存器 `ra` | 普通函数按 ABI 返回调用点 |
| `mret` | `mepc` 与 `mstatus` 等机器态状态 | M 模式 trap 返回，或像 xv6 启动这样完成受控移交 |

`mret` 不是“高级版的 C `return`”。它不会看 `ra`，也不会自然回到 `call start` 的下一条。把这一区分清楚，`spin` 标签的意义才会显得合理：若 `start()` 意外以普通函数路径返回，入口代码让 CPU 在确定的死循环里停下，而不是掉进后续未知字节。

典型路径更接近：

```text
entry.S → start()（M 模式）→ mret → main()（S 模式）
```

而不是普通的 `start() → ret → entry.S`。这也解释入口代码中为何有 `spin: j spin`：如果 `start()` 异常地按普通函数返回，控制流会停在可预测的循环里，而不是继续将未知字节当指令执行。

## 七、多个 hart：同一段代码如何获得不同栈

多个 hart 可从同一个 `_entry` 地址开始执行，但它们读取的 `mhartid` 不同：

```text
hart 0：mhartid = 0 → stack0 的第 0 份
hart 1：mhartid = 1 → stack0 的第 1 份
hart 2：mhartid = 2 → stack0 的第 2 份
```

同一份程序文本因此计算出不同的 `sp`。每 hart 独立栈只解决调用帧互不覆盖；共享内存、设备和全局初始化仍需要锁、原子操作与内存顺序等并发规则，不能由 `mhartid` 自动解决。

### “栈分开了”之后，为什么还要等

私有栈只是把每个 hart 的局部变量、保存的返回地址和函数调用帧隔离开。它并不把全局变量、内存分配器、设备寄存器或页表自动复制成多份。假设 hart 0 负责初始化一个共享设备表，hart 1 却在表写到一半时读取它，结果仍然是错误的。

```text
hart 0：写共享初始化数据 ─── 完成 ─── 发布 ready 标志
hart 1：                    等待 ─── 观察到 ready 后才读取数据
```

这里的“发布 ready 标志之前不能使用、之后才能使用”的分界，就是**启动同步边界**。多核下还要考虑编译器优化和 CPU 的内存重排：一个随手写的普通全局变量，并不必然表达“此前全部初始化写入都已经对其他 hart 可见”。实际内核会用锁、原子操作或内存屏障来建立这个保证。

教学内核常采用如下角色分工：

```text
全部 hart：进入 _entry → 各自设置早期栈 → 进入 C 启动代码
                         │
                         ├─ hart 0：完成一次性的全局初始化
                         └─ 其他 hart：等待全局状态就绪，再做各自的初始化
```

具体哪项工作只应由 hart 0 完成，不能凭印象判断，必须读当前 xv6 版本的条件判断和同步代码。此处要形成的习惯是：`mhartid` 告诉程序“我是谁”，却没有自动给出“共享状态何时可用”。

## 八、如何验证而不只相信源码

可以用工具检查这条启动链：

```bash
riscv64-unknown-elf-readelf -h kernel/kernel
riscv64-unknown-elf-nm -n kernel/kernel | grep -E '(_entry|stack0|start)'
riscv64-unknown-elf-objdump -d -M no-aliases kernel/kernel
```

- `readelf -h` 查看 ELF 入口地址；
- `nm -n` 查看 `_entry`、`stack0`、`start` 的最终符号地址；
- `objdump` 查看伪指令在链接后展开的真实基础指令。

这三者分别验证“入口是谁”“符号在哪里”“CPU 最终会看到哪些编码”。不要只根据源文件顺序猜地址，最后说了算的是链接结果。

## 九、几种特别常见的误解

### 误解 1：`0x80000000` 永远等于“内核虚拟地址”

不对。本章首先把它作为 xv6/QEMU 启动约定下的物理装载地址和早期取指地址理解。页表启用前后、不同内核布局下，虚拟地址可以不同。遇到地址先问：此时地址翻译是否开启？这句话讨论的是物理地址、虚拟地址，还是 PC 的当前值？

### 误解 2：`ENTRY(_entry)` 会让 CPU 自己找到标签

不对。`ENTRY` 影响 ELF 的入口元数据，标签帮助链接器和调试器定位；CPU 不会在运行时搜索符号表。真正让 CPU 从某地址开始执行的是启动链中的 QEMU、固件或 bootloader 对 PC 的设置。

### 误解 3：`-bios none` 说明所有 RISC-V 系统没有 BIOS

不对。它仅说明这个 QEMU 实验刻意不额外运行固件。现实机器常有 ROM 与固件；不同平台把内核交到 M 模式还是 S 模式，也可能不同。

### 误解 4：hart 就是“一个物理核心”

不严格。hart 是硬件线程，表示可独立执行一条指令流的上下文。一个核心可以实现多个 hart。对本章的 QEMU 入门实验，将它近似当作独立 CPU 执行流足够，但不要把近似当作定义。

### 误解 5：每个 hart 有自己的 `sp`，多核启动就安全了

不对。它只保证各自的栈帧不重叠；共享内存初始化的先后、可见性和设备访问仍需同步。

### 误解 6：`mret` 与普通 `ret` 的区别只是名字多了一个 `m`

不对。`ret` 使用 `ra` 遵守函数调用约定；`mret` 使用 `mepc/mstatus` 所代表的特权状态来完成机器态返回或移交。这是 ABI 与特权架构两套不同规则。

## 十、练习：用因果关系检查自己是否真的理解

### 练习 1：补全启动链

将 `链接脚本`、`QEMU 装载`、`初始 PC`、`_entry`、`start()`、`mret`、`main()` 按合理顺序连成图，并为每个箭头写一句原因。

**参考要点：** 链接脚本先把 `_entry` 所在的代码安排到地址并写入入口元数据；QEMU 按启动约定装载映像、设置初始 PC；CPU 从 `_entry` 取指，入口建立栈后调用 `start()`；`start()` 准备 `mepc/mstatus` 等，`mret` 才将控制流和权限移交到 `main()`。

### 练习 2：判断并解释

1. “CPU 执行时会查询 ELF 符号表来找到 `_entry`。”
2. “只要将 `mepc` 写成 `main`，执行普通 `ret` 就会进入 `main`。”
3. “两个 hart 的 `sp` 不同，所以它们对全局变量的访问天然隔离。”

**答案：** 三句都错误。第一句混淆构建期符号与运行期取指；第二句混淆 `ret` 与 `mret`；第三句混淆私有栈和共享内存同步。

### 练习 3：解释一个调试现象

若 `readelf -h` 显示入口是 `0x80000000`，但 GDB 连上后 PC 并未停在这个地址，写出至少两种可能原因。

**参考要点：** QEMU 可能没有使用 `-S`，所以 CPU 已跑过入口；启动命令可能运行了固件而不是 `-bios none` 的直接内核路径；GDB 加载的符号文件可能与正在运行的映像不匹配；也可能当前项目的链接脚本和示例使用了不同地址。应先核对构建产物、启动命令和链接脚本，别急着把 `0x80000000` 改成另一个“看起来合理”的数。

## 小结

- QEMU 按启动约定装载内核并设置初始 PC；CPU 从该地址开始取指。
- 链接脚本以 `ENTRY(_entry)`、段布局和起始地址，把汇编中的入口符号连接到启动地址。
- 物理地址、PC 当前地址与页表启用后的虚拟地址要分别理解。
- M、S、U 是权限层级；xv6 先在 M 模式完成机器态准备，再转交 S 模式内核。
- CSR 保存 CPU 控制状态，`mhartid` 用于区分硬件线程，`mepc`/`mstatus` 与 `mret` 服务于后续移交。
- 现在再读 `entry.S`，它不再孤立，而是启动链中“建立第一个可调用 C 环境”的一环。
