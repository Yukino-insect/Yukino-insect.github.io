很多人第一次接触 QEMU 时，会把它理解成“运行另一个系统的工具”。这不算错，却遗漏了决定使用方式的关键：QEMU 可以模拟一台带 CPU、内存、固件和设备的完整机器，也可以只在当前操作系统中代为执行另一种 CPU 架构的普通程序。两种模式面对的对象、启动方式和调试手段并不相同。

本文的目标是建立一条完整而不过度神秘化的线索：先区分 QEMU 的两种运行模型，再理解 BIOS、引导扇区、DOS 程序和 Linux 可执行文件为什么不能互换，最后在 WSL 中用 NASM 写出并运行一个 16 位 x86 引导程序。读完后，应能判断一个二进制文件该交给哪一种 QEMU，以及出问题时该从装载、入口、设备还是代码本身开始检查。

> 本文以 Linux/WSL 下的命令为例，x86 示例使用 NASM 语法。QEMU 支持的机器模型、CPU 型号和设备会随安装包版本而变化；遇到参数差异时，请以 `qemu-system-i386 -help`、`-machine help` 和本机版本输出为准。

## 一、QEMU 到底模拟了什么

QEMU 是一套可模拟多种 CPU 架构和硬件设备的软件。它并不是只会“开虚拟机”的单一程序；不同可执行文件对应不同使用层级。

| 命令形态 | 模拟范围 | 典型用途 |
| --- | --- | --- |
| `qemu-system-i386` | 一台完整的 32 位 x86 PC：CPU、内存、磁盘、显示、固件和设备 | 启动镜像、操作系统、引导扇区、裸机程序 |
| `qemu-system-riscv64` | 一台 RISC-V 虚拟机器 | 运行 xv6、内核、固件或 RISC-V 裸机程序 |
| `qemu-aarch64` | 一个 AArch64 Linux 用户进程及其系统调用适配 | 在 x86 Linux 上运行 ARM64 Linux 程序 |
| `qemu-i386` | 一个 32 位 x86 Linux 用户进程及其系统调用适配 | 运行 i386 Linux ELF 程序 |

这正是最容易混淆的分界线：

```text
系统模拟（system emulation）
    模拟计算机
    → 可以从固件和启动设备开始
    → 适合 BIOS、bootloader、内核、完整操作系统

用户态模拟（user-mode emulation）
    模拟一个普通进程的 CPU 指令与系统调用边界
    → 仍借用宿主操作系统的文件、进程和内核服务
    → 适合跨 CPU 架构运行 Linux/BSD 用户程序
```

QEMU 官方把用户态模拟定义为：在**同一操作系统语义**下启动为另一 CPU 架构编译的程序。[QEMU User Mode Emulation 文档](https://www.qemu.org/docs/master/user/index.html) 因而 `qemu-aarch64 ./app` 不是启动了一台 ARM PC，更没有替程序提供 BIOS、磁盘控制器或 ARM Linux 内核；它只是在现有 Linux 进程环境里翻译该程序的指令和系统调用。

反过来，系统模拟会创建一个“客体机”（guest machine）。例如 `qemu-system-i386` 对应的是一台 x86 PC：它拥有客体 CPU 寄存器、客体物理内存、可连接的虚拟磁盘和显示设备。你在命令行中给它的 `boot.img` 是客体机的磁盘内容，不是让宿主 Linux 直接 `exec` 的文件。

## 二、CPU 模拟、硬件虚拟化和 TCG

在系统模拟中，QEMU 需要让客体 CPU 指令真正产生效果。这里有两条常见路径：

- **TCG**（Tiny Code Generator）：QEMU 将客体指令动态翻译为宿主 CPU 可执行的代码。它可以跨架构工作，例如在 x86 主机上模拟 RISC-V；代价是通常比原生执行慢。
- **硬件加速**：客体与宿主 CPU 架构兼容时，QEMU 可在平台支持的情况下使用 KVM、HVF、WHPX 等能力，让部分客体代码更直接地在硬件上运行。QEMU 的命令文档将 TCG 列为默认加速器，并列出各平台可能提供的 KVM、HVF、WHPX 等替代项。[QEMU Invocation 文档](https://www.qemu.org/docs/master/system/invocation.html)

两者影响的主要是性能，不会改变“客体是一台独立机器”这一事实。编写 512 字节引导扇区、学习 BIOS 或运行一个很小的教学内核时，TCG 的性能通常已经足够；不必因为没有 KVM 就认为实验无法进行。

这几个缩写不需要神秘化。它们都是 QEMU 可选的**硬件虚拟化加速后端**，只是依赖的宿主平台不同：

| 名称 | 全称/来源 | 主要宿主平台 | 简单理解 |
| --- | --- | --- | --- |
| KVM | Kernel-based Virtual Machine | Linux | Linux 内核提供的虚拟化接口；QEMU 在 Linux（包括满足条件的 WSL 2）中通常优先检查它。 |
| HVF | Hypervisor.framework | macOS | Apple 提供的 Hypervisor Framework；macOS 上的 QEMU 可借助它运行同架构客体。 |
| WHPX | Windows Hypervisor Platform | Windows | Windows/Hyper-V 提供的虚拟化接口；原生 Windows 上的 QEMU 可使用它。 |

它们不是不同的“虚拟机格式”，也不会让一个 8086 boot sector 变成另一种程序。对同一份客体镜像而言，差别主要在 QEMU 如何更快地执行客体 CPU 指令。特别是在 WSL 内运行 Linux 版 QEMU 时，应检查 `/dev/kvm`，而不是把 Windows 上的 WHPX 名称直接写进 WSL 终端；二者所处的宿主接口层不同。

在 WSL 2 中，可先检查 KVM 设备是否存在：

```bash
test -r /dev/kvm && echo 'KVM 可用' || echo '将使用 TCG 或其他可用加速器'
```

只有该设备存在且当前环境允许使用时，才考虑显式指定：

```bash
qemu-system-x86_64 -accel kvm ...
```

不要把这行当成通用“加速咒语”。在跨架构模拟、WSL 未暴露 KVM，或目标程序极小的场景中，它要么不可用，要么没有必要。让 QEMU 使用默认加速器，先把启动链和镜像格式确认正确，远比过早优化更有效。

## 三、系统模拟的启动链：QEMU、固件与程序分别做什么

`qemu-system-i386` 默认模拟传统 x86 PC 的启动方式。启动时并不是 QEMU 猜测某个 `.bin` 应从哪里执行，而是大致遵循下面的职责分工：

```text
QEMU 创建客体 CPU、RAM 与设备
        ↓
客体固件（传统 PC 常为 BIOS）初始化并选择启动设备
        ↓
启动设备首段代码（例如 MBR / boot sector）被装入内存
        ↓
固件跳转到该段代码
        ↓
bootloader、DOS 或操作系统继续装载下一阶段
```

因此，“QEMU 可以运行 8086 汇编”应理解为：**QEMU 可以模拟会从实模式固件启动的 x86 PC，使符合该启动约定的 16 位机器码获得入口和环境**。它不是把任意汇编文本或任意二进制文件自动识别后执行。

### 1. BIOS、UEFI 与 `-bios none`

传统 x86 PC 上常见的是 BIOS：CPU 复位后先进入固件，固件完成最初的设备初始化，并从启动盘读取首个扇区。UEFI 是另一套固件和启动协议，常从 EFI System Partition 中装载 EFI 程序。两者都属于“在操作系统之前建立启动环境”的固件层。

某些 QEMU 机器和教学内核会使用：

```bash
qemu-system-riscv64 -machine virt -bios none -kernel kernel/kernel
```

`-bios none` 的含义不是“QEMU 不再需要入口”，而是该机器模型与 `-kernel` 装载约定直接为内核提供入口，刻意省去一层额外固件。xv6 的 RISC-V 启动正是这种教学简化；关于它如何与链接脚本、初始 PC 和特权级配合，可继续阅读 [内核启动前的环境：QEMU、链接脚本、特权级与 CSR](<05-内核启动前的环境：QEMU、链接脚本、特权级与 CSR.md>)。

同理，`-kernel` 也不是“执行任意二进制文件”的通用参数。它依赖目标机器和加载协议；裸机文件应使用哪种装载方式，必须由该机器模型、文件格式和运行时约定共同决定。

### 2. 同为 16 位代码，运行环境也可能完全不同

下面三类文件都可能含有 16 位 x86 指令，却不能相互替代：

| 文件/程序 | 入口由谁建立 | 可依赖的服务 | 能否直接当作启动盘交给 `qemu-system-i386` |
| --- | --- | --- | --- |
| 引导扇区 | BIOS 从启动介质加载并跳转 | 少量 BIOS 中断、实模式硬件环境 | 可以 |
| DOS `.COM` 程序 | DOS 装载到约定内存位置 | DOS `int 21h`、PSP、文件系统服务 | 不可以 |
| Linux ELF 程序 | Linux 内核与动态加载器 | Linux 系统调用、用户栈、共享库 | 不可以 |

例如，DOS 程序中的：

```asm
mov ah, 0x09
int 0x21
```

依赖的是 DOS 的 `int 21h` 服务。BIOS 不提供这项服务，因此把 `.COM` 文件伪装成磁盘首扇区后启动，并不会神奇地打印字符串。正确的关系应该是：

```text
QEMU → BIOS → FreeDOS（或其他 DOS）→ DOS 装载器 → hello.com
```

而引导扇区只能依赖 BIOS 或自己直接驱动硬件，不能假设已有 DOS、Linux、C 运行库或已分配好的用户栈。

## 四、认识一条 QEMU 系统命令

以启动一个原始磁盘镜像为例：

```bash
qemu-system-i386 \
  -m 64M \
  -drive format=raw,file=boot.img \
  -boot c
```

可将常用选项理解为“拼装客体机”的部件，而不是一串需要死记的字符：

| 选项 | 作用 | 常见误解 |
| --- | --- | --- |
| `qemu-system-i386` | 选择系统模拟器与 x86 目标 | 它不是 NASM，也不会汇编源代码 |
| `-m 64M` | 分配 64 MiB 客体 RAM | 这是客体内存，不等于宿主程序占用恰好 64 MiB |
| `-drive format=raw,file=boot.img` | 将文件作为原始格式虚拟磁盘连接 | `raw` 是镜像格式，不是“任意裸程序”格式 |
| `-boot c` | 优先从第一块硬盘启动 | 它只选择启动设备，不修改镜像内容 |
| `-machine ...` | 选择虚拟主板/机器布局 | 不同机器模型可拥有不同设备与启动约定 |
| `-cpu ...` | 选择客体 CPU 模型或特性 | 它不等于选择汇编器的输出格式 |
| `-smp N` | 创建 N 个虚拟 CPU 执行流 | 多核并不会自动让客体程序线程安全 |

QEMU 支持使用 `-machine help` 和 `-cpu help` 检查当前安装包实际支持的机器和 CPU 模型；官方命令文档也明确说明 `-machine` 用于选择模拟机器。[QEMU Invocation 文档](https://www.qemu.org/docs/master/system/invocation.html)

对可写磁盘镜像做实验时，有一个很实用的习惯：先复制镜像，或者以快照方式启动。

```bash
qemu-system-x86_64 -snapshot -drive file=disk.img,format=raw
```

`-snapshot` 会让本次写入不直接持久化到基础镜像，适合测试安装、分区或文件系统实验。它不是备份策略，但能避免一次试验把唯一的原始镜像改得面目全非。

## 五、WSL 中的最小 8086 实模式实验

现在用一个小实验验证整条链。它不依赖图形窗口，也不依赖 DOS：程序作为 boot sector 被 BIOS 装载，再将字符写入 QEMU 的调试控制台端口。这样输出会直接出现在 WSL 终端，便于先确认“代码是否真的运行”。

### 1. 安装工具

Ubuntu、Debian 等基于 `apt` 的发行版可安装：

```bash
sudo apt update
sudo apt install -y nasm qemu-system-x86
```

确认工具存在：

```bash
nasm -v
qemu-system-i386 --version
```

其他发行版的包名可能不同；原则不变：需要一个能输出平坦二进制文件的汇编器，以及 x86 系统模拟器。

### 2. 编写可启动扇区

新建 `boot.asm`：

```asm
; boot.asm
; BIOS 从磁盘首扇区装载到物理地址 0x7C00 后开始执行

bits 16
org 0x7C00

start:
    cli                     ; 初始化栈期间先禁止可屏蔽中断
    xor ax, ax
    mov ds, ax
    mov es, ax
    mov ss, ax
    mov sp, 0x7C00
    sti

    mov si, message

.print:
    lodsb                   ; AL = [DS:SI]，SI 自动加一
    test al, al
    jz .halt

    out 0xE9, al            ; 输出到 QEMU debug console
    jmp .print

.halt:
    cli
.loop:
    hlt
    jmp .loop

message db 'Hello from 16-bit real mode!', 13, 10, 0

; BIOS 启动扇区必须是 512 字节，最后两个字节为 0x55、0xAA
times 510 - ($ - $$) db 0
dw 0xAA55
```

这里有几个不能含糊的事实：

- `bits 16` 告诉 NASM 按 16 位模式解析和编码指令；它不负责把程序放进内存。
- `org 0x7C00` 告诉 NASM 标签应按 BIOS 约定的装载地址计算。由于示例令 `DS = 0`，`message` 的偏移量可直接对应物理地址附近的位置。
- `0x7C00` 是传统 BIOS 读取启动扇区后的约定地址，不是 8086 指令集自行规定的常数。
- `times` 填充到 510 字节，`dw 0xAA55` 写入两个字节的启动签名。x86 小端序下，镜像末尾实际字节顺序为 `55 AA`。
- `out 0xE9, al` 是为了与 QEMU 的 debug console 配合，**不是**真实 IBM PC 上用于普通屏幕输出的标准接口。它让调试输出无需依赖图形显示。

汇编为原始镜像：

```bash
nasm -f bin boot.asm -o boot.img
```

检查大小与结尾签名：

```bash
stat -c '%s bytes' boot.img
xxd -g 1 -l 16 -s 496 boot.img
```

应看到大小是 `512 bytes`，最后两个字节为 `55 aa`。这一步很朴素，却能比盲目重试 QEMU 更早发现汇编输出格式或填充计算错误。

### 3. 在终端中启动并查看输出

执行：

```bash
qemu-system-i386 \
  -drive format=raw,file=boot.img \
  -display none \
  -debugcon stdio \
  -global isa-debugcon.iobase=0xe9
```

预期终端输出：

```text
Hello from 16-bit real mode!
```

命令中的 `-display none` 不创建图形显示，`-debugcon stdio` 将调试控制台连到当前终端，最后一项把该设备的 I/O 端口设为代码中使用的 `0xE9`。程序随后进入 `hlt` 循环，所以按 `Ctrl+C` 结束 QEMU 即可。

这条命令也回答了一个常见问题：**不是“只有 BIOS 才能被 QEMU 模拟执行”，而是系统模拟需要一个定义入口与环境的启动路径**。本例中 BIOS 负责把引导扇区送入 `0x7C00` 并跳转；此后执行的正是你写出的机器码。

### 4. 为什么不直接运行 `.COM` 文件

若将同一份源代码改成：

```asm
bits 16
org 0x100

mov dx, message
mov ah, 0x09
int 0x21

mov ax, 0x4C00
int 0x21

message db 'Hello, DOS!$'
```

它就变成了一份依赖 DOS 的 `.COM` 程序：`org 0x100` 和 `int 0x21` 都以 DOS 的装载协议与服务存在为前提。正确做法是准备可启动的 FreeDOS 镜像，让 QEMU 先启动 DOS，再在 DOS 提示符中运行它；或者直接选择 DOSBox-X 这类更专注 DOS 应用的模拟器。

把这两份程序都称为“8086 汇编”没有错，但这只能说明它们使用的指令集相近，不能说明它们拥有相同的运行时契约。运行环境不同，入口、段寄存器、可用中断和文件格式都可能不同。

## 六、WSL 下的显示、串口与调试选择

QEMU 默认可能尝试打开图形显示。使用 WSL 时，优先决定你需要观察什么：

| 目标 | 推荐方式 | 适用情形 |
| --- | --- | --- |
| 只看引导日志或调试字符 | `-display none -debugcon stdio` | boot sector、内核早期调试 |
| 使用串口控制台 | `-nographic -serial mon:stdio` | Linux 内核、串口输出的裸机程序 |
| 查看 VGA 文字/图形界面 | 使用默认显示或指定 GTK/SDL 显示后端 | 已配置 WSLg，且客体确实需要显示设备 |
| 单步查看寄存器和 PC | `-S -gdb tcp::1234` 配合 GDB | 定位入口、段寄存器、跳转与异常 |

WSL 2 的 WSLg 可以运行 Linux GUI 应用；但学习引导过程时，图形窗口并不是必要条件。Microsoft 的说明也指出，WSLg 提供的是与 Windows 桌面的 GUI 应用集成，并非完整 Linux 桌面环境。[在 WSL 中运行 GUI 应用](https://learn.microsoft.com/windows/wsl/tutorials/gui-apps)

### 用 GDB 停在客体启动前

#### GDB 能调试 8086 汇编吗？

**可以**。GDB 并不只用于 C/C++；它能查看寄存器、内存和反汇编，也能单步执行机器指令。对 8086 实模式程序，常见做法是让 QEMU 提供 GDB 远程调试接口，然后由 GDB 调试 QEMU 中那颗虚拟 x86 CPU：

```text
GDB
  ↕ 远程调试协议
QEMU 的 GDB stub
  ↕
模拟的 x86 CPU（先执行 BIOS，之后执行 16 位 boot sector）
```

它能帮助你观察 `CS`、`IP`、`DS`、`SS`、`SP` 等实模式状态，反汇编当前 `PC` 附近的机器码，并逐条执行 `si`。但引导扇区通常是 NASM 生成的平坦 `.bin` 文件，不含 ELF/DWARF 调试符号；因此 GDB 往往不能像调试带 `-g` 编译的 C 程序那样稳定显示源文件行号或函数名。此时以**地址、寄存器、内存和反汇编**为准，反而更符合裸机调试的本质。

将示例 QEMU 改为：

```bash
qemu-system-i386 \
  -drive format=raw,file=boot.img \
  -display none \
  -debugcon stdio \
  -global isa-debugcon.iobase=0xe9 \
  -S -gdb tcp::1234
```

`-S` 让客体 CPU 创建后立刻暂停，`-gdb tcp::1234` 开启 GDB 远程调试端口。另开一个终端：

```gdb
gdb
(gdb) set architecture i8086
(gdb) target remote :1234
(gdb) info registers
(gdb) x/10i $pc
(gdb) si
```

`set architecture i8086` 让 GDB 以 16 位 x86 的视角解释指令和寄存器。不同 GDB 版本和 QEMU 目标对实模式地址、段:偏移显示的细节可能不同，但检查思路不变：先看 `CS`、`IP`/`PC` 与段寄存器，再反汇编当前地址，最后单步执行。QEMU 启动后最初执行的仍是 BIOS；若目的是检查自己的引导扇区，应继续运行或设置合适断点，直到控制流到达 BIOS 约定装载的 `0x7C00` 附近。不要只盯着源代码行号；CPU 实际执行的是某个线性地址处的机器码。

若想保留较粗粒度的执行记录，也可让 QEMU 写出日志：

```bash
qemu-system-i386 \
  -drive format=raw,file=boot.img \
  -display none \
  -d in_asm,cpu \
  -D qemu.log
```

日志通常较大，适合在最小复现程序上使用。调试时一次只增加一种观察手段：先确认镜像被识别为可启动，再确认入口地址，最后追踪指令；同时打开图形、串口、GDB、日志和复杂设备，只会让问题更难归因。

## 七、常见失败现象与排查顺序

| 现象 | 常见原因 | 优先检查 |
| --- | --- | --- |
| QEMU 提示不可启动 | 镜像不是有效启动扇区、签名缺失、启动设备错误 | 是否为 512 字节、末尾是否 `55 aa`、`-drive` 是否指向正确文件 |
| 运行后没有任何输出 | 程序未到 `out`、端口与 `-debugcon` 不匹配、字符串未以零结束 | `org`、段寄存器、`0xE9`、`message` 与死循环位置 |
| `.COM` 文件不能启动 | 将 DOS 用户程序误当 boot sector | 改用 DOS 镜像/DOSBox，而非继续改 QEMU 参数 |
| GDB 连上后 PC 不在预期入口 | 未使用 `-S`、固件已经运行、连接到错误进程 | 启动参数、端口、当前镜像和机器模型 |
| `-accel kvm` 报错 | 当前 WSL/宿主未提供 KVM，或客体/宿主不满足条件 | `/dev/kvm`、去掉该选项并用默认 TCG 验证功能 |
| 写实验后原镜像被改坏 | 客体对虚拟磁盘有写入 | 复制镜像或使用 `-snapshot` |

排查顺序应尽量沿启动链向下：

```text
文件是否是预期格式
    → QEMU 是否连接了正确设备
        → 固件/加载器是否有入口
            → CPU 是否跳到预期地址
                → 段、栈与寄存器是否满足代码假设
                    → 代码逻辑与设备访问是否正确
```

例如“没有打印字符串”绝不自动等价于“QEMU 不支持 8086”。更常见的是镜像末尾签名错误、`org` 与实际装载地址不一致，或者输出送往了没有连接的设备。先以可观察的事实逐层排除，结论才不会沦为猜测。

## 八、QEMU 的适用边界

QEMU 非常适合：

- 学习 BIOS、boot sector、操作系统启动与内核调试；
- 跨架构启动完整系统，例如在 x86 主机上模拟 RISC-V `virt` 机器；
- 为操作系统、设备驱动和嵌入式软件提供可重复的机器环境；
- 在 CI 中自动运行镜像、内核或裸机测试；
- 用用户态模式验证另一架构的 Linux 用户程序。

但也要知道它不替你保证什么：

- QEMU 能执行 16 位实模式程序，不等于逐周期复刻最初的 Intel 8086/8088；对精确时序、历史硬件边缘行为或特定外设兼容性有严格要求时，应评估 Bochs、86Box、PCem 或真实硬件。
- `qemu-i386` 面向 Linux 用户态 ELF，不是 DOS 运行时，也不能取代 BIOS 启动过程。
- `-kernel`、`-bios none`、`-machine virt` 都是特定机器模型和加载约定的一部分，不能从一个架构不加思考地复制到另一个架构。
- 客体中的漏洞和错误配置仍然值得认真对待；“它运行在虚拟机里”不是把不可信镜像接入宿主目录、网络或敏感凭据的理由。

QEMU 的价值不在于隐藏计算机如何启动，恰恰在于它把启动、CPU、内存、固件和设备这些边界变得可以重复构造、暂停和观察。理解这些边界之后，命令行参数不再是一张需要背诵的清单，而是对一台客体机作出的明确配置。

## 小结

- QEMU 有**系统模拟**和**用户态模拟**两条主要路径：前者模拟整台机器，后者只帮助另一架构的普通用户进程运行。
- `qemu-system-*` 需要明确启动链；传统 x86 常由 BIOS 从启动设备将 boot sector 装入内存并跳转。
- 引导扇区、DOS `.COM` 和 Linux ELF 即使都含 x86 指令，也依赖不同的入口和系统服务，不能互相直接替换。
- 在 WSL 中，`NASM + qemu-system-i386` 足以完成 16 位实模式的入门实验；`-display none -debugcon stdio` 能让输出直接回到终端。
- 遇到问题时，按“镜像格式 → 设备连接 → 启动入口 → CPU 状态 → 程序逻辑”的顺序排查，比凭感觉修改参数可靠得多。
