RISC-V 的特权级并不是给 CPU 贴上“管理员/普通用户”标签那么简单。它规定的是：**当前代码能执行哪些指令、能读写哪些 CSR、能否配置页表与中断入口；当异常、系统调用或中断发生时，硬件怎样保存现场、改变控制流，并在适当时恢复原来的权限。**

如果没有这一套机制，用户程序可以自行改写页表、关闭其他进程的中断、把 trap 入口指向任意代码，操作系统的“隔离”就只剩下礼貌性的建议。页表负责决定地址能否访问，特权级则决定谁有资格配置这套规则；二者缺任何一个都不构成可靠的内核边界。

本文以 RISC-V 的 M/S/U 模型和本地 xv6 RISC-V 代码为线索，专门讲清特权级与 trap。页表负责决定地址能否访问，特权级则决定谁有资格配置这套规则；二者缺任何一个都不构成可靠的内核边界。

### 1. 先能分清“顺序执行、函数调用和 trap”

CPU 在最普通的情况下只做一件事：从 PC 指向的地址取一条指令，执行，再让 PC 指向顺序上的下一条。`call` 改变这种顺序，但它仍是**当前代码主动发起的函数调用**：编译器/汇编器安排将返回位置保存在 `ra`，并跳到一个已知目标；被调用函数最终以 `ret`（通常是 `jalr x0, 0(ra)` 的别名）回到该位置。

```text
调用者：call f
  -> ra = “call 的下一条指令地址”
  -> PC = f
f：ret
  -> PC = ra
```

trap 的起因和保存位置都不同。它可能由正在执行的 `ecall`、非法指令、缺页，或一项与当前指令无关的定时器中断触发。硬件不会把“返回地址”写给 `ra`；它会把被打断的 PC 写入 `mepc` 或 `sepc`，把原因写入 `mcause` 或 `scause`，再根据 trap 配置改写 PC 和特权级。这个差别解释了为什么一个普通函数序言不能替代 trap 入口，也解释了为什么 `ret` 不能从 trap 返回。

### 2. 为什么还要知道 `ra`、`sp` 和栈帧

硬件在 S 模式 trap 时会保存 `sepc`，但一个用户程序的现场远不止“下一条要执行的 PC”。它可能在 `a0`–`a7` 中放着系统调用号和参数，在 `sp` 中放着用户栈位置，在 `ra` 中放着用户函数调用链的返回点。trap 入口如果立即使用这些寄存器做自己的临时变量，却没有先保存，用户态恢复时就会得到被内核破坏的现场。

这就是 xv6 的 trampoline 会把通用寄存器写入 `struct trapframe` 的原因。`sepc` 负责恢复控制流位置，trapframe 负责恢复 ABI 可见的寄存器状态；二者缺一不可。之后内核才可以使用自己的栈和寄存器调用 C 函数，例如 `usertrap()`。

### 3. CSR 不是“地址很特殊的全局变量”

`mstatus`、`sepc`、`stvec` 等 CSR 有名字和数值编号，但它们不位于当前进程可任意解引用的普通虚拟内存中。下面两种写法的含义完全不同：

```asm
csrr    a0, sstatus   # 读取 CPU 的 S 模式状态 CSR
ld      a0, 0(a1)     # 从 a1 指向的普通内存读取 8 字节
```

第一条会受到 CSR 本身的特权级、只读属性和扩展支持约束；第二条会走当前地址空间的页表翻译和普通内存权限检查。把 `sstatus` 想成一块“某个固定地址的内存”，再用指针代替 `csrr/csrw`，从访问路径开始就错了。

### 4. 为什么源码助记符还要区分伪指令

例如：

```asm
csrr    a0, sstatus
```

表达的目标是“读取 CSR”，但真正编码是：

```asm
csrrs   a0, sstatus, x0
```

`CSRRS` 的本义是“读取 CSR，并将源寄存器中为 1 的位设入 CSR”；这里源寄存器为恒为零的 `x0`，所以不会设置任何位，恰好退化为纯读取。类似地，`csrw sstatus, a0` 只是 `csrrw x0, sstatus, a0` 的友好写法。读源码时可以先记住短写法；分析真正副作用、反汇编或内联汇编约束时，则必须回到实际编码和操作数。

## 与本主题直接相关的汇编指令

以下指令或汇编器别名构成特权级控制流的最小词汇。先记住它们**改变的是哪一类硬件状态**，比死背编码更有用。

| 源码写法 | 分类 | 常见执行位置 | 核心效果 |
| --- | --- | --- | --- |
| `ecall` | 真实 SYSTEM 指令 | U/S/M 均可执行，但原因编码随当前模式而变 | 主动产生 environment-call 异常，进入相应 trap 路径 |
| `mret` | 真实特权返回指令 | M 模式 trap 返回路径 | 按 `mstatus` 与 `mepc` 恢复 PC、权限及相关状态 |
| `sret` | 真实特权返回指令 | S 模式 trap 返回路径 | 按 `sstatus` 与 `sepc` 恢复 PC、权限及相关状态 |
| `csrr rd, csr` | 汇编器伪指令 | 具有该 CSR 读取权限的模式 | 展开为 `csrrs rd, csr, x0`，读取 CSR 且不写回 |
| `csrw csr, rs` | 汇编器伪指令 | 具有该 CSR 写入权限的模式 | 展开为 `csrrw x0, csr, rs`，写 CSR 并丢弃旧值 |
| `csrrc rd, csr, rs` | 真实 CSR 读改写指令 | 例如 S 模式锁/中断代码 | 读取旧 CSR 值，并按掩码清位 |

### 1. `ecall`：把“请求服务”变成受控异常

用户程序执行：

```asm
li      a7, SYS_write  # 依 ABI 放入系统调用号；具体约定由操作系统定义
ecall
```

`ecall` 本身不读取 `a7`，也不知道 xv6 的 `SYS_write` 是什么；它只产生一项 environment-call 异常。当前模式决定 `scause`/`mcause` 中对应的原因编码，例如 U 模式执行的 `ecall` 与 S 模式执行的 `ecall` 是不同原因。硬件随后把返回 PC 放入 xepc、记录原因、按委托和向量配置进入 M 或 S 模式 trap 入口。**系统调用号、参数解释、权限检查和返回值写回 `a0` 都是内核软件后续做的事。**

因此 `ecall` 是一扇受硬件监管的门：用户能敲门，但不能在指令中指定门后应执行哪段内核代码，更不能直接取得内核栈或内核页表。

### 2. `mret`：M 模式交接时真正发生的状态恢复

在本地 xv6 的 `start()` 中，先有：

```c
x = r_mstatus();
x &= ~MSTATUS_MPP_MASK;
x |= MSTATUS_MPP_S;
w_mstatus(x);
w_mepc((uint64)main);
asm volatile("mret");
```

这段代码不是“把一个函数地址放进变量后跳过去”。`mret` 读取机器态的返回状态：`mepc` 给出新 PC，`mstatus.MPP` 给出应恢复的特权级，并按规范恢复机器态中断相关状态。于是流程从 M 模式的 `start()` 进入 S 模式的 `main()`。

如果只执行普通 `j main` 或 `call main`，PC 也许能到达 `main`，但当前模式仍然是 M 模式；随后对 CSR 的权限、trap 的归属以及内核安全边界都会变成另一回事。因此启动代码选择 `mret` 不是为了绕远路，而是因为它同时完成了控制流和权限状态的交接。

### 3. `sret`：返回用户态前为什么要准备 `SPP` 与 `SPIE`

`sret` 的对应状态位位于 `sstatus`：

- `SPP` 记录返回目标是 S 模式还是 U 模式；`SPP=0` 表示返回 U 模式。
- `SPIE` 保存 trap 前的 S 模式中断使能状态；`sret` 按规则将它恢复到 `SIE`。
- `sepc` 给出返回 PC。

所以用户返回路径必须先完成“恢复用户寄存器、选择用户页表、写好 `sepc`、使 `SPP=0`、准备 `SPIE`”等步骤，最后才执行 `sret`。先执行 `sret` 再补设这些状态是不可能的：执行后 CPU 已经在用户权限和用户控制流中，不应再有资格继续配置 S 级 trap 返回状态。

### 4. CSR 指令怎样支持中断控制

以 xv6 关闭当前 hart 的 S 模式可屏蔽中断为例：

```c
uint64 flags = rc_sstatus(SSTATUS_SIE);
```

该封装的核心是：

```asm
csrrc   rd, sstatus, rs
```

它先把旧 `sstatus` 写入 `rd`，再按 `rs` 中为 1 的掩码位清除 CSR 对应位。于是内核可从旧值判断进入临界区前 `SIE` 是否开启，同时立即关闭当前 hart 中断。若改成先 `csrr`、中间执行若干普通指令、最后 `csrc`，中间窗口仍可能接收中断；也不应把 `csrrc` 的“单 CSR 读改写”夸大成跨 hart 的互斥锁。

同样，`csrs sstatus, mask`（置位）与 `csrc sstatus, mask`（清位）是常用别名。它们只改掩码指定的状态位，比“读完整 `sstatus`、在 C 中改一位、再 `csrw` 覆盖写回”更不易意外覆盖其他可写字段。

`ecall` 不会像 `call handler` 那样在指令中携带某个内核函数地址。它只报告“当前模式请求环境服务”；硬件再依据委托设置、当前模式和 trap 向量 CSR 决定把控制流送往 M 或 S 模式入口。`mret`/`sret` 也不是 ABI 的 `ret` 别名：`mret` 和 `sret` 读取特权 CSR，普通 `ret` 才只从 `ra` 返回函数调用点。

本地 xv6 的 `riscv.h` 将这些 CSR 操作包进 `r_mstatus()`、`w_mepc()`、`r_sstatus()`、`w_stvec()` 等 `static inline` C 函数。源码出现的 `csrr`、`csrw` 并非独立机器编码；RISC-V 将其定义为基于 `CSRRS`、`CSRRW` 的汇编器伪指令。[RISC-V Zicsr 规范](https://docs.riscv.org/reference/isa/v20260120/unpriv/zicsr.html)

## CSR 与 trap 指令参考：每个名字到底保存什么、何时改变

前面的概览只给出名称和职责。真正读 `start.c`、`trampoline.S` 或 trap 处理代码时，还必须知道：**哪个 CSR 是硬件在 trap 时写入的，哪个是软件必须预先配置的，哪些状态位会在进入和返回时自动搬运。**以下均以支持 M/S/U 的 RV64 实现为模型；某个 CSR 是否实现、是否可从当前模式访问，仍由特权架构版本、扩展和平台决定。

### 1. 先按角色给 CSR 分组

| 组别 | M 模式 CSR | S 模式 CSR | 谁主要写入 | 它们解决的问题 |
| --- | --- | --- | --- | --- |
| trap 向量 | `mtvec` | `stvec` | 各级初始化代码 | trap 到来时 PC 从哪里开始执行 |
| trap 现场 | `mepc`、`mcause`、`mtval` | `sepc`、`scause`、`stval` | 硬件在 trap 进入时；软件可为返回/模拟而改写 | 被打断位置、原因和附加信息是什么 |
| 返回状态 | `mstatus` | `sstatus` | 硬件在 trap 进入/返回时，软件在准备返回时 | 之前的特权级和中断使能如何恢复 |
| 中断许可/挂起 | `mie`、`mip` | `sie`、`sip` | 许可位通常由软件写；挂起位多来自硬件/平台 | 哪一类中断能否交付、是否正在等待处理 |
| 委托 | `medeleg`、`mideleg` | — | M 模式/固件 | 低特权级发生的事件送 M 还是 S 处理 |
| 地址翻译 | — | `satp` | S 模式内核 | 当前 hart 采用哪个分页模式、ASID 与根页表 |
| 交换用 scratch | `mscratch` | `sscratch` | 软件 | trap 入口用来暂存每 hart 指针或交换寄存器；硬件不会自动替你保存通用寄存器 |

名称中的 `m`、`s` 表示该 CSR 属于 Machine 或 Supervisor trap 机制；`xepc`、`xcause`、`xtval` 中的 `x` 只是“某一级的对应版本”的统称。它们不是一组内存地址，不能用指针读写。

### 2. `mtvec` / `stvec`：trap 到底跳到哪里

`mtvec` 和 `stvec` 的低两位是 MODE，其余高位组成 BASE：

```text
XLEN-1                              2 1       0
+------------------------------------+-----------+
| BASE                               | MODE      |
+------------------------------------+-----------+
```

| MODE | 名称 | trap 后的 PC |
| --- | --- | --- |
| `0` | Direct | 所有异常和中断都从 `BASE` 开始 |
| `1` | Vectored | 异常从 `BASE` 开始；中断从 `BASE + 4 × cause` 开始 |

因此：

```c
w_stvec((uint64_t)supervisor_trap_entry);
```

写的不是“发生异常时调用这个 C 函数”，而是在 `stvec.MODE=Direct` 时把 CPU 的下一条 PC 配成 `supervisor_trap_entry`。该地址必须对当前将启用的地址翻译有效、具有可执行权限，并满足实现对对齐的要求。Vectored 模式的 `4 × cause` 是固定的指令槽步长；即便某些指令可压缩为 16 位，向量偏移规则也不是按 2 字节计算。

`stvec` 只决定**进入的第一条指令**，不会提供内核栈、不会保存通用寄存器，也不检查入口代码是否适合当前页表。trap 入口常先在极少数汇编指令中交换 scratch、保存寄存器、建立可信栈，之后才安全调用 C 函数。

### 3. `mepc` / `sepc`、`mcause` / `scause`、`mtval` / `stval`

这六个 CSR 是 trap 的最小“为什么来、从哪里回”的记录。以 S 模式为例：

| CSR | 硬件在 trap 进入时做什么 | 软件在处理/返回时怎样使用 |
| --- | --- | --- |
| `sepc` | 写入被中断或发生异常的指令地址 | 修复后以它作为 `sret` 的返回 PC；对 `ecall` 通常需软件把它前移一条指令，避免再次执行同一条 `ecall` |
| `scause` | 写入中断标志和原因码 | 分支到系统调用、缺页、定时器、外部中断等处理路径 |
| `stval` | 在规范定义的情形写入附加值 | 很多 page fault 中是相关 VA；非法指令等情况的含义应按 cause 和实现判断，不能永远叫作“错误地址” |

`mcause` 与 `scause` 的最高位是 Interrupt：在 RV64 中为 bit 63。为 1 表示异步中断，为 0 表示同步异常；余下位是 cause code：

```text
63 62                                                     0
+--+-------------------------------------------------------+
| I|                   exception code                      |
+--+-------------------------------------------------------+
 I = 1：interrupt；I = 0：exception
```

几个最常见的异常原因码如下。原因码空间可被扩展，表中不是全部情况：

| cause code | 同步异常含义 |
| ---: | --- |
| `2` | illegal instruction |
| `8` | environment call from U-mode |
| `9` | environment call from S-mode |
| `11` | environment call from M-mode |
| `12` | instruction page fault |
| `13` | load page fault |
| `15` | store/AMO page fault |

因此，U 模式 `ecall` 后 `sepc` 指向的通常是 **`ecall` 那条指令本身**，不是自动加 4 后的位置。内核若决定正常返回，就必须按实际指令长度推进 `sepc`；常见的 `ecall` 是 32 位 SYSTEM 指令，所以教学内核通常加 4。这个 `+4` 是处理系统调用协议的一部分，不是 `sret` 自动完成的工作。

### 4. `mstatus` 与 `sstatus`：进入 trap 时哪些位真的变化

`mstatus` 是机器态总体状态 CSR，`sstatus` 是 S 模式可见的状态字段集合。两者有许多与浮点、内存访问等扩展相关的字段；trap/中断路径最先需要理解的，是下列位：

| CSR 位 | 含义 | trap 进入时的关键变化 | 对应返回指令 |
| --- | --- | --- | --- |
| `mstatus.MIE`（bit 3） | 当前 M 模式全局可屏蔽中断开关 | 原值复制到 `MPIE`，再清 `MIE` | `mret` 将 `MPIE` 恢复到 `MIE` |
| `mstatus.MPIE`（bit 7） | trap 前的 MIE 保存槽 | 接收旧 `MIE` | `mret` 后按规范置为 1 |
| `mstatus.MPP`（bits 12:11） | trap 前的特权级/`mret` 将恢复的目标级 | 进入 M trap 时记录此前级别 | `mret` 以它决定返回 M/S/U，并清到最低支持级 |
| `sstatus.SIE`（bit 1） | 当前 S 模式全局可屏蔽中断开关 | 原值复制到 `SPIE`，再清 `SIE` | `sret` 将 `SPIE` 恢复到 `SIE` |
| `sstatus.SPIE`（bit 5） | trap 前的 SIE 保存槽 | 接收旧 `SIE` | `sret` 后按规范置为 1 |
| `sstatus.SPP`（bit 8） | trap 前的权限，0=U、1=S | 接收被 trap 时的 U/S 模式 | `sret` 以它选择返回 S 或 U，并清为 0 |

可将硬件核心动作写成两个小状态机：

```text
进入 S trap：SPIE = SIE；SIE = 0；SPP = 进入前的 U/S 模式；sepc/scause/stval = trap 信息；PC = stvec 指定位置
sret：         特权级 = SPP；SIE = SPIE；SPIE = 1；SPP = 0；PC = sepc

进入 M trap：MPIE = MIE；MIE = 0；MPP = 进入前的模式；mepc/mcause/mtval = trap 信息；PC = mtvec 指定位置
mret：         特权级 = MPP；MIE = MPIE；MPIE = 1；MPP = 最低支持级；PC = mepc
```

这里的“进入前模式”指发生 trap 前的当前权限。`SPP` 只有一位，因为 S trap 只需区分来自 U 还是 S；若事件最终进入 M，则 `MPP` 需要编码 M/S/U。`mret` 还可能涉及规范定义的其他状态字段，例如返回到较低权限时的 `MPRV` 处理；上表列出的是读这篇文章中启动、trap 和中断代码不可省略的核心位，而不是宣称 `mstatus` 只有这些位。

`MPP` 的常用编码为 `00=U`、`01=S`、`11=M`；`10` 保留。因而启动代码中“清掉 `MPP` 掩码，再置入 S 的编码”并不是在改变一个任意整数，而是在为下一条 `mret` 规定返回后的权限。`SPP` 则只有 `0=U`、`1=S` 两种含义。

`sstatus` 还常出现 `SUM`（允许 S 模式在受控条件下访问带 `U=1` 的页面）和 `MXR`（允许将可执行页作为可读页的相关规则）等字段。它们影响页表权限检查，却不改变 `sret` 的返回级别；涉及用户内存复制时必须按页面权限和当前内核策略审查，不能把 `S` 模式误解成无条件绕过所有 PTE 限制。

### 5. `mie` / `mip` 与 `sie` / `sip`：许可和挂起必须同时满足

中断能否交付并不只取决于 `SIE` 或 `MIE` 一位。对于某一级的某类可屏蔽中断，至少要同时考察全局开关、分类使能和挂起状态。最常见的位如下：

| 中断类别 | M 模式许可/挂起位 | S 模式许可/挂起位 | 典型来源 |
| --- | --- | --- | --- |
| software interrupt | `MSIE`（bit 3）/`MSIP`（bit 3） | `SSIE`（bit 1）/`SSIP`（bit 1） | 核间软件通知或平台机制 |
| timer interrupt | `MTIE`（bit 7）/`MTIP`（bit 7） | `STIE`（bit 5）/`STIP`（bit 5） | 定时器比较器或平台转发 |
| external interrupt | `MEIE`（bit 11）/`MEIP`（bit 11） | `SEIE`（bit 9）/`SEIP`（bit 9） | PLIC/中断控制器或其他外设逻辑 |

`mie`/`sie` 中的对应位是“愿不愿意接收这一类”的**许可位**；`mip`/`sip` 是“这一类是否已挂起”的**状态位**。后者常由硬件或中断控制器驱动，有些位在某平台上可由软件置/清，有些必须通过设备寄存器、PLIC claim/complete 或定时器寄存器消除来源。不要把清 `sip` 某个位当成跨平台确认设备中断的通用办法。

此外，`sie`/`sip` 可视为 S 模式可见、可控制的中断位集合，与 M 模式的 `mie`/`mip`、委托配置和平台来源共同作用；它们不是四个完全互不相关的“软件布尔数组”。只有事件已挂起、该类别已启用、全局开关允许，并且特权级/委托条件使其应在当前级处理时，当前 hart 才会进入相应 trap。

### 6. `medeleg` / `mideleg`：委托的是“处理入口”，不是权限

`medeleg` 和 `mideleg` 的每一位以 cause code 为索引：某一位为 1，表示该异常或中断若从较低特权级发生，M 模式将它委托给 S 模式处理。它们的效果不是“把 M 模式 CSR 的读取权限授予 S 模式”，也不会把已经在 M 模式执行时发生的 trap 再委托到 S 模式；**发生在 M 模式的 trap 始终在 M 模式处理。**

例如可以从概念上读：

```text
medeleg[8] = 1  -> 来自 U 模式的 environment call 可由 S trap 处理
mideleg[5] = 1  -> S 定时器中断按配置可由 S trap 处理
```

实际哪些位可写、哪些事件可委托、某类中断怎样产生，依实现与平台而异。把 `w_medeleg(0xffff)` 读成“低 16 位事件采用 S 模式处理的教学内核策略”是合理的；把它读成“任何 RISC-V 都应该写全 1”则没有根据。

### 7. `satp`：地址翻译状态不是 `sret` 自动恢复的内容

在 RV64 支持 S 模式地址转换的实现上，`satp` 的字段为：

```text
63          60 59                  44 43                         0
+--------------+----------------------+-----------------------------+
| MODE (4 bit) | ASID (16 bit)        | 根页表 PPN (44 bit)         |
+--------------+----------------------+-----------------------------+
```

`MODE=0` 表示 Bare，`MODE=8` 表示 Sv39。根页表基址写入的是 `PPN = root_pa >> 12`，并非普通 C 指针。`satp` 是当前 hart 的 S 模式 CSR：内核可据此切换用户/内核地址空间，但 U 模式不能随意写它。

尤其要分清：`sret` 只依据 `sepc/sstatus` 恢复 PC、特权级和中断相关状态，**不会**替软件改写 `satp`；写 `satp` 也不会替软件保存通用寄存器或自动清除旧地址翻译缓存。切换或修改页表后应按影响范围执行 `sfence.vma`，多 hart 情形还要完成 TLB shootdown。Sv39 的 VPN、PPN、PTE 与 `satp` 字段推导见 [RISC-V 底层编程前置知识：内联汇编、CSR、TLB 与内存顺序](RISC-V 底层编程前置知识：内联汇编、CSR、TLB 与内存顺序.md)。

### 8. `ecall`、`ebreak`、`wfi`、`mret` 与 `sret` 的边界

| 指令 | 是否主动触发 trap / 改变控制流 | `xepc` 的典型含义 | 关键误解 |
| --- | --- | --- | --- |
| `ecall` | 主动产生 environment-call 异常 | 指向 `ecall` 本身；正常返回前常由软件推进 | 不读取 `a7`，不直接调用内核 C 函数 |
| `ebreak` | 主动产生 breakpoint 异常 | 指向 `ebreak` 本身 | 不是普通“打印调试信息”指令；调试器或异常处理器决定后续动作 |
| `wfi` | 等待可能的中断条件，随后继续执行 | 不适用 | 不是内存屏障、不是原子操作；实现可将它实现得接近 no-op |
| `mret` | 从 M trap 返回，使用 `mepc/mstatus` | `mepc` 成为新 PC | 不是从 `ra` 返回的 ABI `ret` |
| `sret` | 从 S trap 返回，使用 `sepc/sstatus` | `sepc` 成为新 PC | 不会自动切换 `satp`，也不会恢复通用寄存器 |

`wfi` 常用于空闲循环，以避免持续忙等；其正确性不能依赖“它一定睡到下一次中断”这种过强假设。唤醒、是否立即返回以及可观察行为仍受中断许可、实现和平台规则影响。它与 `fence`、锁或关闭中断没有可互换关系。

### 9. `mscratch` / `sscratch`：只是一格 CSR，不是一块自动 trapframe

`mscratch` 与 `sscratch` 是每 hart 的 scratch CSR，供相应级别的软件约定用途。常见 trap 入口会使用一条 CSR 读改写指令把它与通用寄存器交换，例如先得到当前 hart 的 trapframe 指针或内核栈相关指针，再把被占用的用户寄存器临时保存起来。

硬件在进入 trap 时**不会自动交换** `sscratch`，不会自动把它指向当前进程，也不会据此保存 `ra`、`sp` 或 `a0`。它的价值只在于软件在进入用户态或调度新任务前已预先写入了正确的每 hart/每线程上下文；若这个约定错了，trap 入口的第一条取指之后就可能已经没有可信状态可用。

## 一、先建立正确直觉：权限属于当前 hart 的执行状态

一个 hart 在任一时刻都处于某种特权级。它不是 C 变量，不由内核写 `current_mode = S` 就改变；它是 CPU 执行状态的一部分，由硬件受控地转换。

标准 RISC-V 体系结构定义的三个常见级别是：

| 级别 | 名称 | 典型职责 | 能否自由读写机器态 CSR |
| --- | --- | --- | --- |
| M | Machine mode，机器态 | 最低层硬件初始化、平台/固件策略、特权委托 | 可以访问机器态控制状态 |
| S | Supervisor mode，监管者态 | 操作系统内核、页表、中断与进程管理 | 只能访问被授权的 S 级状态，不能任意改 M 级状态 |
| U | User mode，用户态 | 普通应用程序 | 不能配置内核控制状态；受页表和 trap 机制约束 |

实现可以支持更多扩展状态，例如虚拟化相关的 H 扩展；也可以在非常小的系统中只使用 M 模式。但 xv6 的典型分工是：启动时短暂使用 M 模式，日常内核运行在 S 模式，应用程序运行在 U 模式。

请不要把它机械等同于某些其他架构的“ring 编号”。概念上的共同点是访问控制，具体的 CSR、trap 入口、返回指令和委托规则都由 RISC-V 定义。判断一段代码能否执行时，必须看当前模式和目标资源的权限编码，不能只看函数名里有没有 `kernel`。

## 二、哪些操作会因为权限不足而失败

特权级的效果最容易从“用户态不能做什么”看出来。

| 操作 | U 模式通常为何不能做 | xv6 中由谁完成 |
| --- | --- | --- |
| 写 `satp` 切换页表 | 否则进程可映射任意物理内存 | S 模式内核、trap 返回路径 |
| 写 `stvec`/`sepc` | 否则用户可劫持 trap 入口或返回位置 | S 模式 trap 初始化与返回代码 |
| 写 `sstatus.SIE`、`sie` | 否则用户可随意控制内核中断策略 | 内核中断/锁代码 |
| 读写 `mstatus`、`mepc`、`medeleg` | M 模式必须保留最终机器控制权 | `start.c` 的早期 M 模式代码或固件 |
| 执行特权返回 `mret`/`sret` | 否则低权限代码可伪造提升或跳转 | 相应特权级的受控返回路径 |
| 访问未授权页面或设备 MMIO | 页表与权限检查应阻断它 | 硬件触发 page fault，内核决定后果 |

“通常”二字不可省略：具体 CSR 可访问性和扩展支持由规范与平台组合决定。有些计数器可通过 `mcounteren` 授权给较低模式读取；有些 CSR 的个别位是只读、WARL 或实现定义。安全代码应按目标平台规范验证，而不是把一次 QEMU 实验结果抬升为所有 RISC-V 的真理。

## 三、trap：不是普通函数调用，而是硬件接管控制流

**trap** 是 RISC-V 对受控异常控制转移的总称。它包括同步异常和异步中断：

| 事件 | 是否与当前指令同步 | 典型例子 | xv6 中的含义 |
| --- | --- | --- | --- |
| exception，异常 | 是 | 非法指令、缺页、U 模式 `ecall` | 系统调用、错误地址访问、程序错误 |
| interrupt，中断 | 否 | 定时器、UART、VirtIO 外部中断 | 时钟调度、设备输入输出完成 |

普通 `call` 是当前代码主动跳到已知地址，并按 ABI 把返回地址写到 `ra`；trap 则由硬件依据当前模式、CSR 配置和事件原因保存必要状态，进入预先设置的 trap 向量。触发 trap 的代码不能自由选择“跳到哪个内核函数”，更不能把 `ra` 当成唯一恢复依据。

以 S 模式接收的 trap 为例，硬件会围绕以下状态工作：

| CSR | trap 进入时/之后的作用 |
| --- | --- |
| `stvec` | S 模式 trap 入口的基址与 direct/vectored 模式 |
| `sepc` | 保存被打断的 PC，`sret` 以它为返回目标 |
| `scause` | 保存原因：最高位区分中断与异常，其余编码说明类别 |
| `stval` | 保存与某些异常相关的附加值，例如很多缺页场景的相关 VA |
| `sstatus` | 保存/更新返回权限与中断使能相关位，如 `SPP`、`SPIE`、`SIE` |

硬件保存的是最小的 trap 控制状态，**不是自动保存全部通用寄存器**。因此 xv6 的 trampoline/trap 汇编入口还必须把 `ra`、`sp`、`a0` 等通用寄存器保存到每个进程的 trapframe；若只相信 `sepc` 已经存在就直接调用大量 C 代码，早已被覆盖的寄存器会立刻让返回路径失去意义。

## 四、M/S/U 间怎样转移：不是任何代码都能跳级

### 1. M 模式到 S 模式：准备状态后执行 `mret`

本地 xv6 的 `start()` 处于 M 模式。它先完成：

```c
x = r_mstatus();
x &= ~MSTATUS_MPP_MASK;
x |= MSTATUS_MPP_S;
w_mstatus(x);
w_mepc((uint64)main);
```

然后执行：

```asm
mret
```

`MPP` 的含义是 **Machine Previous Privilege**：它描述 `mret` 返回后将恢复到的模式，并不是一个可随意解释为“CPU 当前正在哪个模式”的普通变量。`mepc` 则给出目标 PC。于是 `mret` 将执行状态从 M 模式切到 S 模式，并从 `main()` 开始继续。

这也说明 `mret` 不等同于 C 的 `return` 或汇编的 `ret`：

```text
ret   → 按 ABI 从 ra 取普通函数返回地址；不改变特权级
mret  → 按 mstatus/mepc 恢复机器态 trap 返回状态；可能改变特权级
sret  → 按 sstatus/sepc 恢复监管者态 trap 返回状态；可能改变特权级
```

### 2. S 模式到 U 模式：准备用户返回状态后执行 `sret`

内核在完成进程调度、用户寄存器恢复和地址空间准备后，会在 trap 返回路径配置 `sepc`、`sstatus.SPP` 等状态，再执行 `sret`。当 `SPP=0` 时，`sret` 返回 U 模式；`sepc` 则成为用户程序继续执行的 PC。

这不是内核简单地 `call user_main()`。用户代码使用用户页表、用户栈和较低权限；而且从用户态回到内核时会由下一次 trap 再次走反向的硬件入口。把它看成两个 C 函数互相调用，会错过最关键的隔离边界。

### 3. U 模式回到 S 模式：`ecall` 与硬件 trap

用户程序请求内核服务时执行 `ecall`。对用户态发出的 `ecall`，其效果不是直接跳转到某个公开 C 函数，而是产生异常；在 xv6 的委托配置下，硬件通过 `stvec` 进入 S 模式 trap 入口，内核从 `scause` 判断这是用户系统调用，读取保存在 trapframe 中的参数，再决定是否以及如何返回用户态。

同样，用户页错误、设备中断或时钟中断也可以将执行流带回内核；区别在于 `scause`、`stval` 与内核处理策略，而不是“谁主动写了一条跳转指令”。

## 五、委托：M 模式把哪些事件交给 S 模式

如果实现支持 M、S 两级，M 模式不必亲自处理每一次低层事件。`medeleg` 和 `mideleg` 允许 M 模式按原因位图将异常或中断委托给 S 模式。

本地 `start.c` 中有：

```c
w_medeleg(0xffff);
w_mideleg(0xffff);
```

它表达的是 xv6 的启动政策：教学内核日常关心的低编号异常/中断应由 S 模式的 trap 代码处理，而不是每次先陷入 M 模式再转发。委托不是“把 M 模式权限交给 S 模式”，也不是让 U 模式可以读写机器态 CSR；它只是 M 模式决定某些来源于较低模式的事件应该送往哪一级 trap 入口。

可以把它理解为：

```text
事件发生在较低特权级
  ├─ 未委托：由 M 模式的 trap 机制处理
  └─ 已委托：在满足条件时由 S 模式的 trap 机制处理
```

M 模式仍拥有最终配置权。真实硬件常由固件（例如 OpenSBI）在内核启动前完成部分 M 模式工作；xv6 的 QEMU 教学配置用 `-bios none` 将这段关系简化为内核自己的 `start()`。

## 六、中断为什么不是“打开一个 bool”就结束了

以 S 模式中断为例，是否真正进入 trap 至少涉及三层状态：

| 层次 | 代表状态 | 回答的问题 |
| --- | --- | --- |
| 全局开关 | `sstatus.SIE` | 当前 hart 是否总体允许可屏蔽 S 中断？ |
| 分类许可 | `sie` 中的 `SEIE`、`STIE` 等 | 此类外部/定时器中断是否被允许？ |
| 事件挂起 | `sip` 或平台设备/PLIC 状态 | 这类事件此刻是否确实已发生？ |

`intr_on()` 只置位 `sstatus.SIE`；它不替你在 `sie` 中打开定时器类别，也不会配置 PLIC、清掉未处理设备状态或安装正确的 `stvec`。反过来，`intr_off()` 只禁止当前 hart 接收可屏蔽 S 模式中断，并不等价于“设备停止工作”或“挂起事件消失”。

这正是自旋锁代码使用 `push_off()`/`pop_off()` 而不随意调用 `intr_on()` 的理由：嵌套临界区需要记住最外层进入前的旧 `SIE` 值，不能由内层武断地重新开中断。`csrrc` 能在单条 CSR 读改写中取得旧状态并清位；其内联汇编细节可见：[xv6 RISC-V 的 `riscv.h`：C 内联汇编、CSR、TLB 与内存屏障](xv6 RISC-V 的 riscv.h：C 内联汇编、CSR、TLB 与内存屏障.md)

## 七、一次用户 trap 的状态变化

把用户态系统调用或缺页简化为一条可检查的时间线：

```text
U 模式：用户 PC 执行 ecall / 发生异常
  ↓ 硬件
保存返回 PC 到 sepc，写 scause/stval，更新 sstatus 的返回相关位
按 stvec 跳入 S 模式 trap 向量
  ↓ trampoline / trap 汇编
保存通用寄存器到 trapframe，切换内核需要的寄存器与页表上下文
  ↓ usertrap() 等 C 代码
按 scause 处理系统调用、缺页或设备事件
  ↓ 返回路径
准备 sepc、sstatus.SPP/SPIE，恢复用户寄存器和用户地址空间
  ↓ sret
回到 U 模式，从 sepc 指向的位置继续
```

两个细节尤其关键：

1. trap 入口的代码必须在切换 `satp` 前后都可取指。xv6 因而把 trampoline 映射在用户页表和内核页表中相同的最高虚拟地址。
2. `sret` 后是否允许中断，取决于硬件根据 `SPIE` 恢复 `SIE` 的规则；不能只用“刚才 C 代码写过某个变量”来推断。

这条路径中既有特权级转换，也有页表切换，但它们是两项独立硬件状态：`sret` 负责 trap 返回的权限/PC 语义，`satp` 负责随后地址翻译使用的根页表。某次代码常把它们相邻执行，并不表示一条指令隐含完成另一条的工作。

## 八、特权级与页表怎样共同形成边界

保护不是由一个单独开关完成的，而是几层机制叠加：

```text
U 模式执行用户代码
  ├─ 页表：PTE_U、R/W/X 决定该 VA 能否被该模式访问
  ├─ 特权级：U 模式不能改 satp、stvec、S/M 级 CSR
  ├─ trap：违规访问、ecall、外部事件受控进入内核
  └─ 内核策略：检查原因、参数与进程状态，决定修复、终止或返回
```

例如用户程序即使猜中了 UART MMIO 的物理地址，也没有意义：用户页表通常没有把该物理页以 `PTE_U` 映射到可访问用户 VA；即使它设法执行某些 CSR 助记符，也会因特权不足陷入异常。反过来，内核若错误地把设备页带 `PTE_U` 映射，或错误地把 `stvec` 交给可写用户内存，单靠“CPU 有 M/S/U”也无法自动补救。

## 九、最常见的误解

### 1. “S 模式就是绝对最高权限”

不对。存在 M 模式时，S 模式仍受机器态 CSR、PMP、委托和平台固件策略约束。xv6 日常运行在 S 模式，并不意味着它能绕过一切底层硬件限制。

### 2. “发生 trap 时，CPU 会自动保存所有寄存器”

不对。硬件保存 `xepc`、`xcause`、`xstatus` 的相关状态；通用寄存器保存是 trap 入口汇编与 trapframe 的职责。

### 3. “`ecall` 是一次特殊的普通函数调用”

不对。它是同步异常。参数通常按 ABI 放入寄存器，但控制流经过硬件 trap、权限转换、原因编码和内核检查，而不是用户代码直接跳进一个可调用的内核 C 地址。

### 4. “关闭中断就获得了多核锁”

不对。关闭本 hart 中断只避免本 hart 被可屏蔽中断抢占；其他 hart 仍可并发访问共享内存。共享数据需要自旋锁、原子操作与正确内存顺序。

### 5. “`mret`/`sret` 与 `ret` 的差别只是名字”

不对。`ret` 依 ABI 使用 `ra`；`mret`/`sret` 是特权返回指令，读取不同 CSR，恢复不同模式与不同返回 PC。

## 十、怎样验证而不是只背图

在 xv6/QEMU 调试环境中，可以把观察点放在真实 CSR 状态上：

```gdb
(gdb) b start
(gdb) c
(gdb) display/i $pc
(gdb) display/x $a0
(gdb) si                 # 观察配置 mstatus/mepc 的代码

(gdb) b main
(gdb) c                  # mret 之后应已进入 S 模式的 main

(gdb) b usertrap
(gdb) c                  # 运行用户程序并触发系统调用/中断后观察
```

不同 GDB 与 QEMU 版本对 `$mstatus`、`$sstatus`、`$sepc` 等 CSR 的名称支持不同。若不能直接打印 CSR，可在 `r_sstatus()`/`r_scause()` 的内联汇编附近观察输出寄存器，或用 QEMU monitor/反汇编确认 trap 入口。真正要验证的是因果关系：`stvec` 是否已安装、trap 后 `sepc` 是否指向被打断位置、`scause` 是否符合事件、`sret` 后是否回到了预期用户 PC。

RISC-V 对各级 xstatus、xepc、xcause、委托与 trap 返回的精确定义以官方特权架构规范为准；不同扩展和平台会补充可用功能。[RISC-V Privileged Architecture Specification](https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html)

## 总结

RISC-V 特权级不是内核代码的装饰背景，而是操作系统能够存在的控制骨架：

- M 模式制定最底层启动、委托和平台访问政策；S 模式运行内核；U 模式运行应用。
- trap 让异常、系统调用和中断受硬件控制地进入预配置入口；它不同于普通函数调用，且不会自动保存全部通用寄存器。
- `mret` 和 `sret` 根据 CSR 恢复 PC、权限和中断相关状态；它们不能用 `ret` 替代。
- `medeleg`/`mideleg` 决定哪些低级事件由 S 模式处理，但不会把 M 模式权限交出去。
- 页表限制“某个地址可否访问”，特权级限制“谁能配置访问规则”；两层共同构成用户/内核边界。

理解特权级后，读 `start.c`、`trampoline.S`、`trap.c` 时不应再只问“这行跳到了哪里”，还应问：**此刻是哪一级模式？硬件保存了什么？谁有权改这些 CSR？下一次返回将从哪个 CSR 取 PC，并恢复成什么权限？**
