当 QEMU 启动 xv6 时，最早执行的不是 `main()`，也不是任何看起来比较体面的 C 函数，而是一小段 RISC-V 汇编。它的任务非常有限：**为每个 hart 准备一块不会与其他 hart 重叠的栈，然后调用第一个 C 函数 `start()`。**

这件事看似只有几条指令，却把启动地址、链接脚本、特权级、CSR、寄存器调用约定、栈增长方向、多核隔离和汇编伪指令都串在了一起。若只把它读成“算个地址然后 `call`”，当然不算错；只是会错过它为什么必须在 C 代码之前存在。C 函数刚开始执行就可能保存寄存器、分配局部变量并继续调用别的函数，没有一个有效栈，这些最普通的动作都无处安放。

本文以题目给出的 xv6 `entry.S` 为线索，目标是能够独立回答：CPU 从哪里开始执行？`sp` 为什么这样计算？每个寄存器装着什么？`call start` 之后发生了什么？它是这组文章的收束章节，而不是零基础学习的第一站。

## 读到这里时，你应当能够回答什么

这一篇不是要求你背出 RISC-V 指令表，而是训练一种可迁移的读启动代码的方法。完成本文后，请合上文章，尝试不用看答案回答下列问题：

1. **CPU 为什么不是从 `main()` 开始？** 你应能说明：CPU 只认 PC 中的地址；QEMU 的装载/复位约定、链接脚本和 `_entry` 符号共同决定第一条指令。
2. **为什么第一段代码不能直接写成 C？** 你应能说明：C 编译出的函数会假设 `sp` 已经指向可写且对齐的栈，函数序言可能立刻用它保存 `ra` 或局部变量。
3. **hart 1 执行完六条栈计算指令时，`sp` 是什么？** 给定 `stack0 = 0x81000000`，应能自己推出 `0x81002000`，而不是只记住一个公式。
4. **`call start` 和 `mret` 分别做什么？** 前者是同一特权级内、遵守 ABI 的函数调用；后者读取机器态返回状态并改变特权级/PC。两者都“跳转”，却绝不是同一件事。
5. **`spin` 为什么不是多余的死代码？** 你应能解释它是“意外返回的确定性停机点”，避免 CPU 顺序执行到未知字节。

若其中某题说不清，回到相应小节并拿纸把 PC、`sp`、`ra`、`a0`、`a1` 写成状态表。汇编最怕把“好像懂了”当成懂了；寄存器的具体值不会配合这种含糊。

## 一、先看完整代码

下面是本文分析的代码。注释很详细，正文会把其中的结论逐一还原为可检查的推理。

```asm
# xv6 的最早期内核入口。
#
# QEMU 以 `-bios none -kernel kernel/kernel` 启动时，会把内核映像
# 装入物理地址 0x80000000，并让每个 hart（RISC-V 对硬件线程/CPU
# 核的称呼）从该地址开始执行。kernel.ld 将 _entry 放在 .text 段
# 的开头，且将该段定位到 0x80000000，因此控制流会到达这里。
#
# 此时仍在 Machine（M）模式，C 运行环境尚未就绪：尤其是 sp
# 没有可供 C 函数使用的栈。此文件的职责仅是为当前 hart 选定
# 一段私有栈，然后转交给 start.c 中的 start() 完成后续初始化。
.section .text
.global _entry
_entry:
        la      sp, stack0
        li      a0, 1024*4
        csrr    a1, mhartid
        addi    a1, a1, 1
        mul     a0, a0, a1
        add     sp, sp, a0

        call    start
spin:
        j       spin
```

## 代码先分成三段：不要把七行当作一团

在逐条解释之前，先按**职责**而不是按行号切分。这样以后面对更长的启动文件，也不会因为指令数量增加就失去方向。

```asm
.section .text                 # A. 把下面内容放入代码段
.global _entry                 # A. 导出启动符号
_entry:                        # A. 此处是汇编入口标签

        la      sp, stack0     # B. 取得栈池基址
        li      a0, 1024*4     # B. 取得每片栈的大小
        csrr    a1, mhartid    # B. 取得“我是谁”
        addi    a1, a1, 1      # B. 转换为上边界编号
        mul     a0, a0, a1     # B. 算出字节偏移
        add     sp, sp, a0     # B. 得到本 hart 的栈顶

        call    start          # C. 把控制权交给 C 的机器态初始化
spin:                          # C. 若调用意外返回，停在可预测位置
        j       spin
```

| 段 | 代码 | 回答的问题 | 不能替代的工作 |
| --- | --- | --- | --- |
| A：可被找到 | 段、全局符号、标签 | 链接器怎样把第一条代码放到正确地址？ | 它不设置任何寄存器 |
| B：可调用 C | 六条计算指令 | 当前 hart 的栈到底在哪一段内存？ | 它不设置页表、时钟或中断 |
| C：移交与兜底 | `call`、`spin` | 初始化由谁继续？返回时怎么办？ | 它不负责正常返回到调用者 |

这个划分也揭示了启动汇编的边界：它不是缩小版的内核。它只解决一个极早期问题——在一个刚被硬件带到入口地址、尚未有正常函数运行环境的 hart 上，建立最小的调用条件。

汇编的缩进和标签位置不是装饰：没有缩进的 `_entry:`、`spin:` 是地址标签；缩进后的 `la`、`add`、`call` 才是指令或伪指令；以 `.` 开头的 `.section`、`.global` 是给汇编器和链接器的指令。把这三类东西先分开，阅读汇编会轻松很多。

## 二、启动全景：从 QEMU 到 `start()`

先建立一条粗略但正确的控制流：

```text
QEMU
  │  装载 kernel/kernel，初始 PC 指向 0x80000000
  ▼
_entry（entry.S，M 模式）
  │  根据 mhartid 计算并设置当前 hart 的 sp
  ▼
start()（start.c，仍处于早期启动阶段）
  │  设置后续特权级、中断、定时器等机器态状态
  │  设置 mepc，执行 mret
  ▼
main() / kernel_main（通常在 S 模式中继续内核初始化）
```

其中有几个名字必须先认清。

| 名称 | 含义 | 在这里的作用 |
| --- | --- | --- |
| QEMU | 模拟器 | 模拟 RISC-V 机器、内存和多个 hart，并加载内核映像 |
| hart | hardware thread | RISC-V 对硬件执行上下文的称呼，可近似理解为一个 CPU 核/硬件线程 |
| PC | program counter | 保存下一条要执行的指令地址 |
| M 模式 | Machine mode | RISC-V 最高特权级，负责最早期机器初始化 |
| S 模式 | Supervisor mode | 操作系统内核运行的常用特权级 |
| `mret` | machine return | 从 M 模式按 `mstatus`、`mepc` 的设置切换到目标特权级并跳转 |

`entry.S` 并不负责完成全部内核初始化。它刻意保持短小：此时没有可供普通 C 调用使用的栈，也不应在没有初始化基础设施时贸然做复杂工作。它只建立“能够调用 C 函数”这一最低前提，随后让 `start()` 接手。

### 启动时到底发生了哪一种“执行”

把 CPU 想成会读源代码的东西，是初学者最常见、也最容易留下后患的误解。它在此刻只重复一个硬件层面的循环：

```text
PC 给出地址
  → 从该地址取出一条机器码
  → 按指令编码选择寄存器/ALU/CSR 等动作
  → 写回结果
  → 把 PC 改为顺序下一条，或被跳转指令改到新地址
```

例如，`add sp, sp, a0` 不会“知道你正在设栈”；译码器只看到一条寄存器加法，读取旧 `sp` 与 `a0`，相加后写回 `sp`。反过来，`call start` 的机器码会把 `ra` 写成返回地址，并把 PC 改到 `start`。**“设栈”“调用函数”是我们根据指令序列和 ABI 赋予的程序含义，不是 CPU 额外理解的高级概念。**

还要注意一项容易被示意图掩盖的细节：源文件中一行伪指令不一定对应一条机器指令。`la` 和远距离的 `call` 可能展开成两条甚至更多真实指令。因此不要试图从源代码行号推断精确 PC 加了几个字节；应当用 `objdump` 观察最终 ELF。下面的推导只依赖每条伪指令的语义，不依赖其固定编码长度。

### 此处的地址、模式和“普通程序”有什么不同

启动时至少有三层边界，混在一起会让看似简单的代码变得神秘：

| 边界 | `_entry` 所处状态 | 后续变化 | 初学者常见误会 |
| --- | --- | --- | --- |
| 取指地址 | QEMU/链接结果让 PC 从内核装载地址附近开始 | `call`、`mret` 会改变 PC | 以为 ELF 中有 `main` 名字就会自动跳过去 |
| 特权级 | 此处是 M 模式，可读取 `mhartid` 等机器 CSR | `start()` 准备状态后以 `mret` 进入 S 模式 | 以为 `call` 本身会切换特权级 |
| C 运行时 | 代码和静态对象已被装载，但当前 hart 的调用栈尚未建立 | 本文设置 `sp` 后，C 函数才能正常使用栈 | 以为“能取到 C 的代码”就等于“C 环境完全就绪” |

所以它并不是一个普通用户程序的 `main`：没有操作系统替它创建进程、分配用户栈、安排 C 运行库入口；它本身正在负责建立操作系统最初所需要的一部分条件。`start()` 也不是应用层的 `main()`：它是被汇编直接调用的早期机器态函数，职责是准备下一阶段。把这三层分开，`entry.S` 的位置就很明确了。

## 三、为什么 CPU 会执行 `_entry`

### 1. QEMU 给出的初始地址

在 xv6 的 RISC-V/QEMU 教学环境中，以：

```bash
qemu-system-riscv64 -bios none -kernel kernel/kernel
```

这一类方式启动时，内核映像被安排到物理地址 `0x80000000` 附近，CPU 的初始执行位置也指向这里。CPU 并不会根据 C 函数名自动找到 `main`；它只会取 PC 指向的机器指令，一条一条执行。

因此，启动代码必须满足一个非常具体的条件：**内核文件的入口符号所对应的第一段机器码，必须被链接到 CPU 将开始取指的地址。** 这个约定由 QEMU 的机器模型、启动参数和 xv6 的链接脚本共同建立。

### 2. 链接脚本把符号与地址接起来

xv6 的 `kernel.ld`（链接脚本）承担“各段放到哪里”的工作。其核心意图可以概括为：

```ld
OUTPUT_ARCH("riscv")
ENTRY(_entry)

SECTIONS
{
  . = 0x80000000;

  .text : {
    *(.text .text.*)
  }
  /* 后面还有 rodata、data、bss 等段 */
}
```

真实文件细节可能略有不同，但关键关系不变：

1. `ENTRY(_entry)` 记录 ELF 的入口符号；
2. `.` 设为 `0x80000000`，表示当前位置从该地址开始；
3. `.text` 段放置机器指令；
4. 本文件把 `_entry` 放进 `.text`，并确保它处在最早位置。

于是地址关系成为：

```text
QEMU 初始 PC：0x80000000
                 │
                 ▼
链接脚本的 .text 起点：0x80000000
                 │
                 ▼
_entry 的第一条机器指令
```

如果 `_entry` 没有被放在预期位置，或链接脚本入口写错了，CPU 仍会忠实地从初始地址取指，只是取到的可能不是你希望执行的内容。硬件并不会因你的目标是“启动内核”就额外体贴一点。

### 3. `.section .text`、`.global` 与标签分别是什么

```asm
.section .text
.global _entry
_entry:
```

可逐行理解：

- `.section .text`：告诉汇编器，后续代码应进入名为 `.text` 的代码段。
- `.global _entry`：把 `_entry` 导出为全局符号，链接器脚本和其他目标文件才能引用它。GNU 汇编器中 `.global` 与更常见的 `.globl` 等价。
- `_entry:`：定义一个符号，其值就是当前指令位置的地址。它本身不生成机器指令。

汇编源文件不会直接交给 CPU 执行。汇编器先把它变成目标文件，保留段、符号和重定位信息；链接器再把多个目标文件按链接脚本排布为 ELF 内核映像。CPU 最终看到的只有地址处的机器码。

## 四、进入逐指令分析前：需要认识的寄存器

RISC-V 的通用寄存器名有两套：硬件编号如 `x2`、`x10`，以及 ABI 约定名如 `sp`、`a0`。启动代码使用后者，因为人类并不喜欢在每次读代码时把 `x10` 翻译成“第十号寄存器”。

| ABI 名 | 硬件编号 | 全名/角色 | 本段代码中的用途 |
| --- | --- | --- | --- |
| `sp` | `x2` | stack pointer，栈指针 | 最终指向当前 hart 私有栈的栈顶 |
| `ra` | `x1` | return address，返回地址 | `call start` 时保存返回位置 |
| `a0` | `x10` | argument 0，第一个参数/临时寄存器 | 暂存每栈大小与最终字节偏移 |
| `a1` | `x11` | argument 1，第二个参数/临时寄存器 | 暂存当前 hart ID 和 `hartid + 1` |
| `x0` | `x0` | zero 寄存器 | 永远读为 0；伪指令常隐式使用它 |

RISC-V ABI 规定，`a0` 到 `a7` 通常用于传递前八个整数或指针参数，也是**调用者保存（caller-saved）**寄存器。这里在调用 `start()` 前用 `a0`、`a1` 做临时计算完全合理：代码不需要把这些中间值交给 `start()`，而且被调用函数本来也有权覆盖它们。

需要特别记住的是 `sp`。它不是普通的“暂存地址”寄存器；编译器生成的函数序言、局部变量访问、保存 `ra` 与被调用者保存寄存器，都会默认它指向一段合法、对齐、可写的栈空间。因此，`sp` 必须在第一条 C 调用之前正确设置。

## 五、栈是什么，为什么要为每个 hart 单独准备

### 1. 栈是函数调用的工作区

一个函数可能需要：

- 保存返回地址 `ra`；
- 保存调用者要求保留的寄存器；
- 存放局部变量、临时对象和溢出的参数；
- 调用另一个函数时建立新的调用帧。

这些数据通常放在栈上。以简化的函数序言为例：

```asm
addi    sp, sp, -16  # 为当前栈帧向低地址腾出 16 字节
sd      ra, 8(sp)    # 保存返回地址
sd      s0, 0(sp)    # 保存被调用者保存寄存器
```

这段代码一开始就以 `sp` 为基准写内存。若 `sp` 未初始化，它可能写到任意地址，覆盖代码、设备映射或根本不存在的内存。因此在 `entry.S` 里，设置栈不是性能优化，而是执行 C 代码的入场券。

### 2. RISC-V 栈向低地址增长

RISC-V ABI 使用向低地址增长的栈。若一块可用栈区间是：

```text
[low, high)
```

初始 `sp` 应放在 `high`，即栈顶。函数分配栈帧时通过：

```text
sp = sp - frame_size
```

不断向 `low` 方向移动。

这里的 `[low, high)` 是左闭右开区间：包含 `low`，不包含 `high`。把 `sp` 初始化为 `high` 很自然，因为还没有任何数据占用栈；第一次减去栈帧大小后，实际写入会落在该区间内部。

### 3. 多个 hart 不能共用同一个早期栈

QEMU 可以同时启动多个 hart。若所有 hart 都把 `sp` 设为同一个地址，那么它们会同时保存返回地址、局部变量，互相覆盖，启动过程会立即变成不可预测的内存破坏。

xv6 因而在 C 文件中预留一块连续数组，概念上类似：

```c
#define NCPU 8

__attribute__((aligned(16)))
char stack0[4096 * NCPU];
```

它不是“一个栈”，而是被切成 `NCPU` 份的栈池。对编号为 `i` 的 hart：

```text
第 i 份的低端：stack0 + i * 4096
第 i 份的高端：stack0 + (i + 1) * 4096
可用区间：      [stack0 + i * 4096, stack0 + (i + 1) * 4096)
```

把 `sp` 放到第 `i` 份的高端，就得到：

```text
sp = stack0 + (hartid + 1) * 4096
```

`+ 1` 并不是为了“跳过第一个栈”。hart 0 对应的栈是 `[stack0, stack0 + 4096)`，它的正确栈顶正是 `stack0 + 4096`；每一份栈都从自己的上边界开始向下使用。

```text
地址增长方向 →

stack0
  │ [ hart 0 的 4096 字节 ] │ [ hart 1 的 4096 字节 ] │ [ hart 2 ... ]
  │                         │                         │
  │ sp(hart 0)              │ sp(hart 1)              │
  ▼                         ▼                         ▼
base                    base + 4096             base + 8192
```

图中每个 hart 的 `sp` 位于自己那一格的右边界；实际调用时栈帧往左生长。只要每个 hart ID 小于 `NCPU`，这些区间就不会重叠。

### 4. 为什么大小是 4096，且要 16 字节对齐

`1024 * 4` 是 `4096`，也就是 4 KiB。它在早期启动阶段只需容纳相对浅的调用链；后续内核会建立更完整的每 CPU 栈与内存管理结构。

RISC-V ELF psABI 要求在过程调用边界，栈指针满足 16 字节对齐。这里有两个保障：

1. `stack0` 本身按 16 字节对齐；
2. `4096` 可以被 16 整除。

所以：

```text
若 stack0 mod 16 = 0，
则 stack0 + 4096 * (hartid + 1) mod 16 = 0。
```

每个 hart 得到的初始 `sp` 都是 16 字节对齐。这个看似小的约束会影响编译器生成的调用代码、保存的寄存器布局以及与其他遵循 ABI 的函数协作；对齐不是“让内存看起来整齐”，而是调用约定的一部分。

## 六、逐条执行：从 `stack0` 到正确的 `sp`

现在回到核心七行：

```asm
la      sp, stack0
li      a0, 1024*4
csrr    a1, mhartid
addi    a1, a1, 1
mul     a0, a0, a1
add     sp, sp, a0
```

### 1. `la sp, stack0`：取得栈池基地址

```asm
la      sp, stack0
```

`la` 是 **load address** 的伪指令，意思是将符号 `stack0` 的地址装入 `sp`：

```text
sp = &stack0[0]
```

它不读取 `stack0` 数组的内容，也不是“把某个值加载到栈里”；它只得到地址。链接器最终决定 `stack0` 的实际地址，并通过重定位让这里的指令能够得到正确结果。

在 RISC-V 上，`la` 往往会被汇编器展开成多条真正的机器指令，例如基于 PC 相对寻址的 `auipc` 加 `addi`。具体展开取决于代码模型、是否开启位置无关代码和链接结果；源代码写 `la` 的意义是表达“我需要符号地址”，而不是强行指定编码细节。

执行后状态：

```text
sp = stack0
```

此时 `sp` 只是整个栈池的低端，仍不是当前 hart 应使用的栈顶。

### 2. `li a0, 1024*4`：装入每份栈的大小

```asm
li      a0, 1024*4
```

`li` 是 **load immediate** 伪指令，把立即数放进寄存器：

```text
a0 = 4096
```

汇编器先计算常量表达式 `1024*4`，再生成装入 `4096` 所需的真实指令。`4096` 是否恰好能用一条指令装入，取决于立即数字段宽度与汇编器选择；作为阅读者，先把它理解为“a0 存每个 hart 的栈大小”即可。

### 3. `csrr a1, mhartid`：读取当前 hart 编号

```asm
csrr    a1, mhartid
```

`mhartid` 是 Machine 模式的一个 **CSR**（Control and Status Register，控制与状态寄存器），保存当前硬件线程的 ID。`csrr rd, csr` 的语义是读取 CSR：

```text
rd = CSR[csr]
```

所以本句是：

```text
a1 = mhartid
```

若当前是第 0 个 hart，`a1=0`；第 1 个则 `a1=1`。不要把 hart ID 想成操作系统分配的进程 ID：它是硬件/平台给执行上下文的编号，早在内核调度器出现之前就存在。

`csrr` 是真实 RISC-V 指令，不是普通通用寄存器之间的 `mov`。CSR 有各自的特权级访问规则；在此处处于 M 模式，读取 `mhartid` 是符合启动环境的。

### 4. `addi a1, a1, 1`：得到栈顶边界编号

```asm
addi    a1, a1, 1
```

`addi` 是 **add immediate**，将寄存器值与立即数相加：

```text
a1 = a1 + 1
```

于是：

```text
a1 = hartid + 1
```

如前所述，这一步的意义是从“第几块栈”转换为“第几个 4096 字节边界”。若省掉它，hart 0 的 `sp` 会等于 `stack0` 的低端；第一次函数序言再向下减栈帧，就会越过数组起点，直接写到不属于其栈的内存。

### 5. `mul a0, a0, a1`：计算字节偏移

```asm
mul     a0, a0, a1
```

`mul rd, rs1, rs2` 为乘法指令：

```text
rd = rs1 * rs2
```

故：

```text
a0 = 4096 * (hartid + 1)
```

此处隐含一个 ISA 前提：`mul` 属于 RISC-V 的 M（乘除法）扩展。xv6/QEMU 的目标配置包含它，因而可以直接使用。若目标只有最基础的 RV64I 而没有 M 扩展，汇编器不能凭空执行硬件乘法，代码必须改为移位/加法或调用软件例程。

### 6. `add sp, sp, a0`：定位到当前 hart 的栈顶

```asm
add     sp, sp, a0
```

`add rd, rs1, rs2` 是通用寄存器加法：

```text
sp = sp + a0
```

结合前面每一步：

```text
sp = stack0 + 4096 * (hartid + 1)
```

这正是所需的栈顶。假设 `stack0 = 0x81000000`，可以把三个 hart 的结果列出来：

| hart ID | 分配区间 | 初始化后的 `sp` |
| --- | --- | --- |
| 0 | `[0x81000000, 0x81001000)` | `0x81001000` |
| 1 | `[0x81001000, 0x81002000)` | `0x81002000` |
| 2 | `[0x81002000, 0x81003000)` | `0x81003000` |

每个值都是对应区间的上端点。函数调用向低地址压栈，因此不同 hart 的帧不会交叠。

### 7. 一张寄存器跟踪表

以 `mhartid = 1` 为例，执行过程如下：

| 指令后 | `sp` | `a0` | `a1` | 含义 |
| --- | --- | --- | --- | --- |
| 初始 | 未定义 | 未定义 | 未定义 | 尚不能调用 C 函数 |
| `la sp, stack0` | `stack0` | — | — | 栈池低端 |
| `li a0, 4096` | `stack0` | `4096` | — | 一份栈大小 |
| `csrr a1, mhartid` | `stack0` | `4096` | `1` | 当前 hart ID |
| `addi a1, a1, 1` | `stack0` | `4096` | `2` | 第二个边界 |
| `mul a0, a0, a1` | `stack0` | `8192` | `2` | 需要前进的字节数 |
| `add sp, sp, a0` | `stack0 + 8192` | `8192` | `2` | hart 1 的栈顶 |

阅读汇编时，像这样手动记录寄存器内容非常有用。不要急着给每条指令套上玄妙含义；先持续问“这一句后哪个寄存器变成了什么”，控制流和地址计算通常就会自行显形。

### 两个 hart 同时到达入口时：用十六进制把隔离看清楚

现在不再使用符号，假设链接后的 `stack0` 首地址确实是 `0x81000000`，每份早期栈仍为 `0x1000`（4096）字节。hart 0 和 hart 1 可以执行同一份机器码；差别只来自各自读取到的 `mhartid`。

| 执行阶段 | hart 0：`mhartid = 0` | hart 1：`mhartid = 1` |
| --- | --- | --- |
| 刚进 `_entry` | `sp` 没有可用含义 | `sp` 没有可用含义 |
| `la sp, stack0` | `sp = 0x81000000` | `sp = 0x81000000` |
| `li a0, 4096` | `a0 = 0x1000` | `a0 = 0x1000` |
| `csrr a1, mhartid` | `a1 = 0` | `a1 = 1` |
| `addi a1, a1, 1` | `a1 = 1` | `a1 = 2` |
| `mul a0, a0, a1` | `a0 = 0x1000` | `a0 = 0x2000` |
| `add sp, sp, a0` | `sp = 0x81001000` | `sp = 0x81002000` |

因此它们随后各自可用的栈范围是：

```text
hart 0: [0x81000000, 0x81001000)  ← 初始 sp = 0x81001000
hart 1: [0x81001000, 0x81002000)  ← 初始 sp = 0x81002000
```

假设两个 hart 进入 `start()` 后，编译器都先生成一个 32 字节栈帧：`addi sp, sp, -32`。那么它们的 `sp` 分别变成 `0x81000fe0` 和 `0x81001fe0`，仍分别落在自己的半开区间中。即使它们在真实机器上并发执行，也不会因为这一步覆盖对方的返回地址。

这里有两个值得刻意检查的边界：

- 若误写为 `sp = stack0 + 4096 * mhartid`，hart 0 得到 `0x81000000`；一分配栈帧就落到 `0x80ffffe0`，越过数组低端。
- 若误把分片长度写成 `2048`，而 C 端仍认为每片为 `4096`，不同 hart 可能在较深调用时使用重叠地址。汇编端常量和 C 端数组布局必须是同一个约定，不能各自“看起来合理”。

### 从地址公式反推每一步：这比背指令可靠

先只写目标，不看实现：

$$
\begin{aligned}
\text{stack\_low}(i) &= B + iS \\
\text{stack\_high}(i) &= B + (i+1)S \\
sp &= \text{stack\_high}(\text{mhartid})
\end{aligned}
$$

其中 $B = \&stack0[0]$，$S = 4096$。代入后正好得到：

$$
sp = B + S \times (mhartid + 1).
$$

再把右侧从内向外拆为可由寄存器完成的中间量：`a1 = mhartid`，`a1 = a1 + 1`，`a0 = S`，`a0 = a0 * a1`，最后 `sp = B + a0`。这就是那六条指令的来源。换句话说，汇编不是奇特的谜语，只是把一个地址表达式拆成 CPU 能执行的非常小的读写步骤。

## 七、`call start`：从汇编跨入第一个 C 函数

栈就绪后，代码执行：

```asm
call    start
```

`call` 是汇编伪指令，表达“调用符号 `start`”。其效果等价于两个概念动作：

```text
ra = 下一条指令的地址
pc = start 的地址
```

RISC-V 的基础跳转指令是 `jal rd, offset`（jump and link）。`call start` 通常会由汇编器和链接器展开为适合目标距离的跳转序列，并把返回地址写入 `ra`。具体机器码可能是单条 `jal ra, ...`，也可能是使用 `auipc` 和 `jalr` 的更远距离调用；“保存返回地址并跳到 `start`”才是它不变的语义。

### 1. 为什么此时才能进入 C

编译器为 `start()` 生成的代码可以遵循 ABI，默认：

- `sp` 是有效且按 16 字节对齐的；
- 当前代码有可访问的全局数据与代码地址；
- 基本处理器状态允许执行所生成的指令；
- 调用者和被调用者遵循同一调用约定。

其中最先会造成灾难的就是 `sp`。现在它已被设置为当前 hart 的私有栈顶，所以 `start()` 的函数序言可以安全地减小 `sp`、保存寄存器、继续调用初始化函数。

### 2. `a0`、`a1` 为什么可以随意占用

有人会发现：`a0`、`a1` 在 ABI 中通常传递参数，而这段代码把它们用于算栈，最后没有清零。这没有问题。

调用约定只规定被调用函数如何解释它所声明的参数。若 `start()` 不需要这两个参数，它不会把寄存器中碰巧残留的数值当成某种神谕。并且 `a0`、`a1` 是 caller-saved，`start()` 本就可以自由覆盖它们。启动汇编不会把“计算栈时用过的临时值”泄漏成 C 语言参数。

### 3. `start()` 后续大致做什么

在 xv6 的典型启动路径中，`start()` 仍在 M 模式中完成少量机器态准备工作，例如：

- 设置 `mstatus` 中与后续返回特权级有关的字段；
- 将后续入口（常为 `main`）写入 `mepc`；
- 设置物理内存保护、异常/中断委托、定时器等机器态机制；
- 最终执行 `mret`。

`mret` 会依据 `mstatus` 恢复目标特权级，并把 PC 置为 `mepc`，从而进入 S 模式中的内核主初始化。这里不需要死记每个 CSR 的位定义；要先理解分工：`entry.S` 解决“有栈才能运行 C”，`start()` 解决“从 M 模式转到内核日常工作的特权环境”。

### `call`、`ret`、`mret`：三个“跳转”必须分开

它们都让 PC 不再顺序加到下一条指令，所以初学时很容易把它们归为“跳转而已”。但它们依赖的状态、目的和后果不同：

| 指令/伪指令 | 主要写入或读取 | 典型用途 | 是否改变特权级 |
| --- | --- | --- | --- |
| `call start` | 写 `ra`，PC 前往 `start` | 普通函数调用 | 否 |
| `ret` | 读取 `ra`，PC 回到调用点之后 | 普通函数返回 | 否 |
| `mret` | 读取 `mepc` 和 `mstatus` 的返回相关字段 | 从机器态交给下一阶段 | 是，按状态字段恢复 |

可以用一个控制流时间线把它们连起来。为清楚起见，省略具体机器指令的展开：

```text
M 模式的 _entry
  PC = _entry
      │  设置当前 hart 的 sp
      │
      ├─ call start ──► ra = spin 的地址，PC = start
      │                         │
      │                         │  start() 在 M 模式配置 CSR
      │                         │  mepc = 后续 C 入口（例如 main）
      │                         │  mstatus 指定 mret 后的目标模式
      │                         │
      │                         ├─ mret ──► PC = mepc，进入 S 模式后续初始化
      │                         │
      └─ （仅当 start 普通 ret）► PC = spin
                                      │
                                      └─ j spin，停住
```

正常 xv6 路径中，`mret` 不是“从 `start()` 返回给 `_entry`”；它改变控制流去往 `mepc` 指定的下一个入口，因此 `ra` 在这个正常路径上并不用于回到 `spin`。但 `call` 仍必须正确写入 `ra`，因为它表达的是一次遵守 ABI 的 C 函数调用；而且一旦你暂时修改 `start()` 让它普通返回，防御性路径就会立即生效。

一个实用的读代码技巧是：每遇到跳转，不只问“跳到哪里”，还问**PC 的新值来自哪里、返回位置保存在什么地方、是否同时改变了特权状态**。这三问能区分绝大多数看上去相似的控制流指令。

## 八、`spin`：为什么返回后要原地循环

```asm
spin:
        j       spin
```

`j` 是无条件跳转伪指令；`j spin` 的效果是把 PC 再次设为 `spin` 的地址。因此这两行形成无限循环。

它看上去像没做事，但承担明确的防御职责。正常流程中，`start()` 通过 `mret` 转去后续入口，而不是通过 `ret` 回到 `_entry`。如果 `start()` 因为错误、修改或调试代码意外返回，`ra` 会让控制流落到紧随 `call start` 的 `spin` 标签。

此时最安全的行为不是继续顺序执行后面的未知字节，而是停在一个确定位置：

```text
start() 意外返回
      ↓
spin: j spin
      ↓
反复执行同一跳转
```

调试器可以看到 hart 停在这里；系统不会把数据段、填充或随机机器码误当指令继续跑。无限循环不是“忘了写代码”，而是早期启动失败时的一道护栏。

## 九、几个容易读错的点

### 1. `la sp, stack0` 不是把 `stack0` 的内容装到栈里

`la` 中的 A 是 address。它取符号地址，等价概念是 `sp = &stack0[0]`；数组里的字节此时甚至通常尚未被使用。

### 2. `sp` 不是指向栈中第一个可写字节

栈向低地址增长，初始化时 `sp` 等于区间上边界。第一次建立栈帧时会先减小 `sp`，再写入 `[sp, old_sp)` 区间。把它放到低端反而会让第一次压栈越界。

### 3. `hartid + 1` 不会浪费 hart 0 的栈

hart 0 的栈是第一段 `[stack0, stack0 + 4096)`；`+1` 只是让 `sp` 指向它的高端。若没有 `+1`，才会让 hart 0 从数组低端向更低地址生长，真正浪费并破坏内存。

### 4. `call` 与 C 函数调用不是两套机制

C 中的：

```c
start();
```

编译后同样会遵循 RISC-V ABI，最终形成保存返回地址、跳转、使用 `sp` 的调用序列。`entry.S` 里的 `call start` 只是编译器没有替你生成函数序言之前，手工完成第一次跨语言调用。

### 5. `mul` 不保证存在于所有 RISC-V CPU

RISC-V 是模块化 ISA。`mul` 来自 M 扩展，xv6 的运行环境包含它；在别的裸机板或极简模拟器上，需检查目标 ISA 字符串，例如 `rv64imac` 中的 `m` 就表示包含乘除法扩展。源码能被你当前的工具链汇编，不自动意味着目标硬件能执行每条指令。

### 6. 早期“物理地址”不等于以后一直没有虚拟地址

启动初期的地址安排非常直接，随后内核会建立页表和特权级下的地址转换环境。阅读时应区分：链接时把符号放到哪里、CPU 当前按什么地址取指、以及启用页表后软件所见的虚拟地址。它们在教学环境的某些时刻可能恰好相同，但概念上不是一回事。

## 十、修改这段代码时最容易造成的真实故障

下面不是抽象的“注意事项”。这些错误会直接导致启动挂死、异常或只在多核时失败；把症状和破坏的合同连起来，才知道该从哪里查。

| 改动/误解 | 可能症状 | 被破坏的约定 | 第一检查点 |
| --- | --- | --- | --- |
| 删除 `addi a1, a1, 1` | hart 0 刚进 `start` 就异常或写坏相邻内存 | 初始 `sp` 必须在分片高端 | `sp` 是否等于 `stack0` 而非 `stack0+0x1000` |
| 将 `add sp, sp, a0` 写为 `sub sp, sp, a0` | `sp` 落在 `stack0` 之前 | 栈池基址是低端，栈向低地址生长不等于初值也要向低端取 | 比较 `sp` 与 `&stack0` |
| 所有 hart 读取同一个常量 ID | 单核看似正常，多核随机卡死/数据损坏 | 每个 hart 必须选择不同分片 | 多线程 GDB 中的 `sp` 是否相等 |
| `stack0` 未做 16 字节对齐，或分片大小不是 16 的倍数 | 某些编译代码/调用约定下出现异常行为 | RISC-V ABI 的调用边界对齐 | `sp & 0xf` 是否为 0 |
| 把 `la sp, stack0` 理解成读内存，改成 `ld sp, stack0` | `sp` 变成数组前 8 字节的“内容”而非地址 | `sp` 需要有效地址，`stack0` 是数组对象 | 反汇编和 `p/x $sp` |
| 在 `call start` 前插入会调用 C 的辅助函数 | 辅助函数序言先使用未初始化/错误栈 | 任何普通 C 调用都以有效 `sp` 为前提 | 检查第一条 `call` 前的 `sp` |
| 假定 `mul` 在任意 RISC-V 上可执行 | 非 M 扩展硬件触发非法指令 | 目标 ISA 必须包含 M 扩展 | 编译目标 `-march` 与硬件 ISA |
| 让 `start()` 普通返回后删除 `spin` | PC 掉入段填充或未知指令 | 启动代码没有正常的上层返回者 | 在 `call` 后保留明确兜底 |

还存在一个更隐蔽的工程问题：`hartid < NCPU` 是这里未经检查的前提。若 QEMU 启动的 hart 数量超过 `stack0` 预留的分片数，公式本身仍会计算出地址，但地址已越出数组。这不是算术错，而是平台配置与内核常量不一致。早期入口通常没有足够的设施优雅处理这种失配，所以构建配置必须先保证它不发生。

## 十一、带推导的练习：确认你会算，也会判断边界

先独立作答，再展开答案。这里刻意不考“第几行是什么指令”，而考你能否从布局、ABI 和控制流推出结论。

### 练习 1：hart 3 的栈在哪里？

假定：`stack0 = 0x80204000`，一片栈大小 $S=4096=0x1000$。求 hart 3 的可用栈区间、刚执行完 `add sp, sp, a0` 的 `sp`，以及 `start()` 再分配 `0x50` 字节栈帧后的 `sp`。判断它是否仍在区间内且保持 16 字节对齐。

#### 答案与推导

hart 3 的低端：

$$
0x80204000 + 3 \times 0x1000 = 0x80207000.
$$

高端（初始 `sp`）：

$$
0x80204000 + (3+1) \times 0x1000 = 0x80208000.
$$

因此区间是 `[0x80207000, 0x80208000)`，初始 `sp=0x80208000`。减去 `0x50` 后为 `0x80207fb0`，它大于等于低端、小于高端，仍在区间中。`0x50` 可被 16 整除，且初始地址以 `0` 结尾，因此新 `sp & 0xf = 0`，对齐仍满足。


### 练习 2：为什么数组的总大小是 `4096 * NCPU`，初始栈顶却要乘 `hartid + 1`？

请从半开区间 `[low, high)` 和“向低地址增长”两点推导，不要只回答“代码就是这样写的”。

#### 答案与推导

总数组需要容纳编号 `0` 到 `NCPU-1` 的 $NCPU$ 个不重叠分片，所以长度是 $S \times NCPU$。编号 $i$ 的分片从 $B+iS$ 开始，到 $B+(i+1)S$ 结束。由于栈向低地址增长，尚未使用任何字节时 `sp` 应放在结束边界，而不是起始边界；因此是 $B+(i+1)S$。`+1` 描述的是“本分片的高端”，不是多分配了一片栈。


### 练习 3：把 `call start` 换成 `j start` 可以吗？

分别讨论“当前版本 `start()` 正常执行 `mret`、永不普通返回”和“某次调试中 `start()` 临时改为普通返回”两种情形。

#### 答案与推导

若只看当前正常路径，`start()` 最终 `mret`，不依赖返回到 `_entry` 的 `ra`，所以 `j start` 可能表面上也能到达后续阶段。然而它不再表达/提供一次正常 ABI 调用的返回地址：一旦 `start()` 或其调试版本执行 `ret`，`ra` 并非指向 `spin`，控制流将跳向旧的未知值。使用 `call` 的成本很小，却保留了正确的函数调用语义和清晰的防御路径；因此不应为了“反正不返回”把它替换为 `j`。


### 练习 4：若 `NCPU = 8`，能否让 `mhartid = 8` 的 hart 继续执行？

假设 `stack0` 恰好只分配了 `4096 * 8` 字节，回答地址公式会给出什么、为什么它不等于“第九个可用栈”。

#### 答案与推导

数组合法范围是 `[B, B+8S)`。hart 8 根据公式得到 `sp=B+9S`，它对应的假想分片是 `[B+8S, B+9S)`，整个都在数组末尾之外；甚至它的初始栈顶也越过数组。`mhartid` 只是硬件报告的 ID，不会自动受 `NCPU` 限制。平台启动的 hart 数必须和内核的分片数匹配，或由更早代码将多余 hart 停住。


## 十二、如何自己验证这段启动代码

理解汇编不应只依赖注释。下面的工具链命令能分别检查“符号和段在哪儿”“伪指令展开成什么”“运行时寄存器是否如预期变化”。具体工具名前缀会随交叉编译器安装位置变化。

### 1. 查看 ELF 入口与符号地址

```bash
riscv64-unknown-elf-readelf -h kernel/kernel
riscv64-unknown-elf-nm -n kernel/kernel | grep -E '(_entry|stack0|start)'
```

`readelf -h` 可查看 ELF header 中的 Entry point address；`nm -n` 按地址列出符号。你应能验证 `_entry` 是否处在预期代码起点，也能看到 `stack0`、`start` 的链接地址。不要只根据源文件顺序猜最终地址，链接器才拥有最后决定权。

### 2. 反汇编，观察伪指令真正变成了什么

```bash
riscv64-unknown-elf-objdump -d -M no-aliases kernel/kernel
```

加上 `-M no-aliases` 后，`objdump` 尽量显示基础指令而不是 `la`、`call`、`j` 等友好别名。你可能会看到：

```asm
auipc   sp, ...
addi    sp, sp, ...
/* ... */
jalr    ra, ...
```

这并不说明源代码和反汇编“不一致”。恰恰相反：伪指令本来就是汇编器为表达常见意图提供的简写，实际编码由距离、重定位与目标架构决定。

### 3. 用 GDB 观察某个 hart 的寄存器

可让 QEMU 暂停并开放调试端口，再连接 RISC-V GDB：

```bash
qemu-system-riscv64 -machine virt -bios none -kernel kernel/kernel -S -s
riscv64-unknown-elf-gdb kernel/kernel
```

在 GDB 中可以：

```gdb
break _entry
continue
info registers sp a0 a1 ra pc
si
```

逐条单步执行 `la`、`li`、`csrr`、`addi`、`mul`、`add`，再检查 `sp` 是否按公式变化。多 hart 调试还需注意 GDB 当前选中的线程/执行上下文；先验证 hart 0 的路径，通常已经足够确认地址计算。

### 4. 一次可复现的单步验证记录

光输入 `si` 而不预先知道要验证什么，很容易得到一长串地址后就失去结论。可按下面的最小实验记录。命令中的符号名以你的 xv6 版本实际输出为准；若 GDB 提示找不到 `_entry`，先用前面的 `nm` 确认你连接的是刚编出的 `kernel/kernel`。

```gdb
(gdb) break _entry
(gdb) continue
(gdb) p/x $pc
(gdb) p/x $sp
(gdb) si                 # 走过 la 的实际展开；可能不止一次 si
(gdb) p/x $sp
(gdb) display/i $pc
(gdb) display/x $sp
(gdb) display/x $a0
(gdb) display/x $a1
(gdb) stepi              # 继续直到执行到 call 对应的真实跳转
(gdb) info registers pc sp ra a0 a1
```

应验证的不是某一条反汇编恰好长什么样，而是这四个不变量：

1. 执行地址计算前，`sp` 尚不是 `stack0 + 0x1000 * (hartid + 1)`；
2. 地址计算完成、进入 `call` 前，`sp` 等于该公式并且 `sp & 0xf == 0`；
3. 跳进 `start` 后，`ra` 指向 `spin` 附近的返回位置；
4. `start()` 的函数序言若减小 `sp`，新 `sp` 仍位于当前 hart 的那 4 KiB 区间内。

可用下面的 GDB 计算快速检查第二项（GDB 中 `$` 表示寄存器）：

```gdb
(gdb) p/x $sp & 0xf
$1 = 0x0
(gdb) p/x (unsigned long)&stack0 + 0x1000 * ((unsigned long)$mhartid + 1)
```

`mhartid` 是 CSR，不一定会被 GDB 显示为名为 `$mhartid` 的普通寄存器。最稳妥的做法是：刚单步执行完 `csrr a1, mhartid` 时记下 `$a1` 的值为 $h$，然后在 `add` 完成后检查：

```gdb
(gdb) p/x (unsigned long)&stack0 + 0x1000 * (h + 1)
```

其中把 `h` 替换为你记录的实际十六进制值。也可以直接比较当前 `sp` 和 `stack0` 的已知地址。调试的目标是验证启动合同，不是和调试器的显示形式争论输赢。

### 5. 验证“为什么每个 hart 不会共用栈”

若启动参数配置多个 CPU（xv6 的 Makefile/QEMU 参数随版本不同），GDB 常会把 hart 显示为多个线程。可以在 `_entry` 处观察不同线程，并分别记录：`mhartid`、最终 `sp`、`sp - &stack0`。正确结果应满足：

```text
sp - &stack0 = 0x1000 * (mhartid + 1)
```

相邻 hart 的最终 `sp` 应正好相差 `0x1000`。若差值为 0，说明它们共享栈；若差值不是分片大小，说明 `mhartid`、乘法、数组布局或观察的线程至少有一项出了问题。这样检查比“系统似乎能启动”可靠得多，因为共享栈的问题往往只在并发时偶发。

## 十三、读其他启动汇编时的通用检查表

不同架构的启动代码指令不同，骨架却很相似。读到任何“第一段汇编”时，都可以依次问：

1. **入口从哪里来？** 是固件复位向量、Boot ROM、引导加载器，还是模拟器约定？
2. **链接地址由谁决定？** 链接脚本的 `ENTRY`、段地址与符号如何对应？
3. **当前是什么特权级？** 哪些寄存器、CSR、内存访问在这一阶段允许使用？
4. **栈在哪里建立？** 栈增长方向是什么？是否满足 ABI 对齐？多核是否各有一份？
5. **调用约定是否已满足？** `sp`、参数寄存器、返回地址和保存寄存器如何处理？
6. **第一段 C 代码做什么？** 它是否负责页表、异常向量、特权级切换或 BSS 初始化？
7. **异常返回或意外返回怎么办？** 是否有 `spin`、`wfi` 或安全停机路径？

按这张清单阅读，启动汇编不再是一堆只能“从上往下看”的缩写，而是一份明确的环境初始化合同。

## 总结

这段 xv6 `entry.S` 的实际工作可以压缩为：

```text
读取 mhartid
  → 选择 stack0 中属于当前 hart 的 4 KiB 区间
  → 将 sp 放到该区间高端且保持 16 字节对齐
  → 调用 start()
  → 若意外返回，则在 spin 中安全停住
```

其中最重要的地址公式是：

$$
sp = stack0 + 4096 \times (mhartid + 1).
$$

- `_entry` 能被执行，是 QEMU 的初始 PC、链接脚本的段地址和全局入口符号共同配合的结果。
- `la`、`li`、`call`、`j` 是便于书写的伪指令；`csrr`、`addi`、`mul`、`add` 则表达实际的读取、运算和地址计算语义。
- `sp` 必须在调用 C 函数前有效；栈向低地址增长，因此初值应位于每块私有栈的高端。
- `mhartid` 让多个 hart 获得互不重叠的早期栈；`4096` 与数组起始对齐共同保持 16 字节 ABI 对齐。
- `entry.S` 只搭好最小运行舞台，`start()` 才继续处理机器态设置并转交后续内核初始化。

理解这几行代码之后，你看到的不再是“用寄存器绕一圈再跳转”的仪式，而是内核在没有 C 运行时、没有调用栈、甚至还没有进入日常内核特权级之前，为自己搭起的第一块可靠立足点。它很短，也很诚实：先站稳，之后才谈得上运行整个系统。
