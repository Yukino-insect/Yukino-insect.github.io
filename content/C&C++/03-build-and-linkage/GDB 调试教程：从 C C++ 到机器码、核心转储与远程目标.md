当程序在某个函数里崩溃、变量莫名改变，或只留下一份 core 文件时，日志往往只能告诉你“它死了”。GDB（GNU Debugger）做的事情更接近于把程序暂停在某个确定状态，再让你检查它当时的控制流、调用栈、变量、内存和寄存器。它并不神奇地读懂业务意图，却能把“似乎有问题”收束成可验证的机器状态。

先给出本文最重要的结论：**GDB 可以调试多种 CPU 架构上的机器级执行状态，但源码级调试体验依赖调试信息**。C/C++ 通常编译为本地机器码，并能由编译器附带源文件、行号、类型和变量位置等调试信息，所以 GDB 很适合调试 C/C++。反过来，没有调试信息的二进制、8086 boot sector、内核和 JIT 代码也能由 GDB 观察，但通常只能以地址、反汇编、寄存器和内存为主要线索。

本文以 Linux/WSL 上的 GDB、GCC/G++ 为例。GDB 官方将自己称为 GNU 的**符号调试器**；它的手册同时覆盖断点、栈、源码、数据、优化代码、多种语言和远程调试。[Debugging with GDB 官方手册](https://sourceware.org/gdb/current/onlinedocs/gdb.html/)

## 一、先纠正一个说法：GDB 不是“直接调试 C++ 语法”

下面的说法有一半正确：

> C/C++ 会编译为机器码，所以可以用 GDB 调试。

正确的部分是：运行时真正被 CPU 执行的确实是机器码，GDB 可以暂停进程、读取 CPU 状态、读取进程内存、设置断点，并通过操作系统或远程调试协议控制继续执行。

不完整的部分是：**仅有机器码不足以让 GDB 自动还原源代码行、局部变量名和对象类型**。这些高级信息来自编译阶段写入的调试信息，Linux/ELF 世界最常见的是 DWARF。

```text
C/C++ 源代码
    │ 编译时加入 -g
    ▼
机器码 + 符号 + DWARF 调试信息
    │ 装载并运行
    ▼
进程的寄存器、虚拟内存、线程、指令地址
    ▲
GDB：根据调试信息把地址重新映射为源码、函数、类型和变量
```

因此，GDB 的能力应拆为两层：

| 层次 | GDB 能看到什么 | 是否必须有调试信息 |
| --- | --- | --- |
| 机器级 | 指令地址、寄存器、内存字节、线程、信号 | 否 |
| 符号级 | 函数名、全局符号、较有限的地址定位 | 不一定；未剥离的符号表可能仍存在 |
| 源码级 | 文件/行号、局部变量、类型、结构体字段、源码单步 | 通常需要 DWARF 等调试信息 |

这也是为什么同一个崩溃地址，在带 `-g` 的开发构建中可能显示为 `src/order.cc:57` 和 `Order::commit()`，在被 `strip` 过的发布二进制中却只剩 `0x00007f...`。调试器没有变笨；只是程序没有留下足够的地图。

关于 ELF 中代码、符号表、程序段和调试信息的关系，可配合阅读 [C 与 C++ ELF 文件格式：目标文件、可执行文件与动态链接](<C 与 C++ ELF 文件格式：目标文件、可执行文件与动态链接.md>)。

## 二、GDB 能支持哪些 CPU：它调试状态，不负责模拟 CPU

GDB 可支持 x86、x86-64、ARM、AArch64、RISC-V、MIPS 等多种目标架构。具体可用范围取决于你安装的 GDB 构建、交叉工具链和远程目标的描述；Linux 发行版常提供 `gdb-multiarch`，嵌入式/内核项目也常提供如 `riscv64-unknown-elf-gdb` 这样的专用交叉 GDB。

但要分清职责：

```text
GDB          ：暂停、读写状态、设置断点、解释调试信息
CPU / 操作系统：实际执行进程、处理异常和内存映射
QEMU         ：需要时模拟 CPU 与设备，并可把状态暴露给 GDB
```

GDB **不是**通用 CPU 模拟器。调试本机 C++ 程序时，程序由你的真实 CPU 执行；调试 ARM 开发板时，程序由开发板 CPU 执行；调试 RISC-V 内核或 8086 引导代码时，常由 QEMU 模拟 CPU，GDB 通过网络或串口式协议连接进去。

GDB 官方文档将远程调试描述为适合内核或资源不足、无法运行完整调试器的小系统的方式；目标端需要 `gdbserver` 或实现 GDB 远程协议的 stub。[GDB Remote Debugging 文档](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Remote-Debugging.html)

所以，更严谨的表述应是：

> GDB 能在它支持的目标架构上调试机器级状态；若二进制携带并匹配源码的调试信息，GDB 就能进一步提供源代码级调试。

## 三、为什么 C/C++ 特别适合用 GDB

C/C++ 编译后的程序通常直接在操作系统进程中以本地代码运行，函数调用、栈帧、全局变量和线程都能对应到操作系统与 CPU 的真实状态。编译器若输出调试信息，GDB 可以把这些状态还原为接近源代码的视图。

推荐的入门构建命令是：

```bash
g++ -std=c++20 -g -Og -Wall -Wextra demo.cpp -o demo
```

其中：

| 选项 | 作用 | 与调试的关系 |
| --- | --- | --- |
| `-g` | 生成调试信息 | 让 GDB 能关联源文件、行号、类型和局部变量 |
| `-Og` | 使用面向调试体验的优化级别 | 常比完全不优化更接近日常构建，同时尽量保留可理解的调试行为 |
| `-Wall -Wextra` | 开启更多编译期告警 | 很多错误本应在运行前被发现，没必要全部留给调试器 |
| `-o demo` | 指定输出文件 | 运行 GDB 时需要指向这个与符号匹配的二进制 |

GCC 的官方说明指出，通常只要加 `-g` 就会生成供调试器使用的额外信息；`-g` 可以与优化选项结合使用，但优化会让变量消失、控制流重排或源码行与指令不再一一对应。GCC 也建议在没有其他优化选项时考虑 `-Og`，以获得较好的调试体验。[GCC 调试选项文档](https://gcc.gnu.org/onlinedocs/gcc/Debugging-Options.html)

### 1. `-g` 与 `-O0` 不是同一个选项

常见命令是：

```bash
g++ -g -O0 demo.cpp -o demo
```

它当然适合初学与逐句观察，但两项职责不同：

- `-g` 决定是否输出调试信息；
- `-O0` 决定基本不做优化。

发布构建若使用 `-O2 -g`，GDB 仍可调试，但你可能看见：

- 局部变量显示为 `<optimized out>`；
- 单步执行跳过某些源代码行，或看似来回跳动；
- 函数已被内联，调用栈结构与源码中的函数调用不同；
- 尾调用、寄存器复用或代码移动改变了变量可观察的位置。

这不意味着 GDB 不可靠，而是优化器的职责本来就是改变实现方式，只要保持程序可观察语义。调试生产问题时，应尽量保留**与出问题构建严格匹配**的可执行文件和独立调试符号；为了“好调试”而换成另一份 Debug 二进制，反而可能把问题一起换掉。

### 2. 符号、调试信息与源代码必须匹配

GDB 显示正确函数名和变量，至少依赖三者一致：

```text
正在运行的进程 / core 文件
        ↕ 同一次构建
可执行文件及其共享库
        ↕ 同一次构建
调试符号与源代码
```

若程序升级过、容器中运行的是另一份文件、源码被修改但没有重建，GDB 可能显示错误行号、找不到断点或把内存按错误的结构体布局解释。此时首先确认构建 ID、版本、容器镜像和符号文件，而不是急着怀疑一条普通的 `print` 命令。

## 四、一个最小 C++ 实战：从异常回到越界条件

下面的程序希望找到第一个偶数的下标；但循环条件写成了 `<=`。当数组中没有偶数时，`i == values.size()` 会访问越界元素。这里故意使用 `at()`，使错误以 `std::out_of_range` 异常表现出来；真实项目中若使用 `operator[]`，同一个错误可能变成未定义行为，表现反而更不稳定。

```cpp
// demo.cpp
#include <iostream>
#include <stdexcept>
#include <vector>

int first_even_index(const std::vector<int>& values) {
    for (std::size_t i = 0; i <= values.size(); ++i) {
        if (values.at(i) % 2 == 0) {
            return static_cast<int>(i);
        }
    }
    return -1;
}

int main() {
    const std::vector<int> values{3, 5, 7};
    std::cout << first_even_index(values) << '\n';
}
```

编译：

```bash
g++ -std=c++20 -g -Og -Wall -Wextra demo.cpp -o demo
```

启动 GDB：

```bash
gdb ./demo
```

进入 GDB 后，先让输出易读，再设置断点和异常捕获点：

```gdb
(gdb) set pagination off
(gdb) set print pretty on
(gdb) break first_even_index
(gdb) catch throw
(gdb) run
```

`break first_even_index` 在函数入口暂停；`catch throw` 会在 C++ 异常被抛出时暂停。GDB 把普通断点、监视点和异常等事件捕获点统一为可管理的停止点：断点可按函数名、行号或精确地址设置，监视点则在表达式值发生变化时停止。[GDB Breakpoints 文档](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Breakpoints.html)

当 GDB 因异常停下后，按以下顺序缩小问题：

```gdb
(gdb) bt
(gdb) frame 1
(gdb) info locals
(gdb) print i
(gdb) print values.size()
(gdb) list
```

命令含义如下：

| 命令 | 作用 |
| --- | --- |
| `bt` 或 `backtrace` | 显示调用栈，先确认异常是从哪条业务路径来的 |
| `frame N` | 选择第 N 个栈帧；查看局部变量前，先确保站在真正相关的函数中 |
| `info locals` | 显示当前栈帧可识别的局部变量 |
| `print expr` 或 `p expr` | 按当前源语言解释并打印表达式 |
| `list` | 显示当前位置附近的源码 |

预期会看到 `i` 已等于 `values.size()`。此时错误不是“`at()` 有问题”，而是循环允许下标走到最后一个有效元素之后。修复应为：

```cpp
for (std::size_t i = 0; i < values.size(); ++i) {
```

GDB 的价值在于把这条因果链展示出来：调用栈说明从哪里进入，局部变量说明何时越界，异常停止点说明真正失败的位置。修复后仍应加入单元测试，例如空数组、没有偶数、偶数在首尾等边界输入；调试器帮助定位一次错误，测试才负责阻止它悄悄回来。

> `print values.size()` 可能触发对目标进程的函数调用。对简单、无副作用的 `const` 成员函数通常没有问题，但在锁、崩溃现场、嵌入式目标或不可信状态中，不应随意让 GDB 调用业务函数；优先检查已有变量、内存和调用栈。

## 五、最常用的 GDB 命令：按问题而不是按字母记

GDB 命令很多，但日常排障先掌握下表已足够。不要孤立地背 `n`、`s`、`c`；每条命令都应该对应一个问题。

| 我想知道什么 | 常用命令 | 说明 |
| --- | --- | --- |
| 程序为什么停在这里 | `bt`、`info threads`、`thread apply all bt` | 看当前调用栈、线程与所有线程的栈 |
| 某函数何时被调用 | `break function_name`、`run`、`continue` | 在函数入口设置断点，然后启动或继续 |
| 某一行是否被执行 | `break file.cpp:42`、`continue` | 依赖文件/行号调试信息 |
| 变量现在是什么 | `print value`、`ptype value`、`info locals` | 分别查看值、类型与当前局部变量 |
| 变量何时被改坏 | `watch value`、`watch *ptr` | 值改变时暂停；硬件监视点数量通常有限 |
| 下一步去哪 | `next`、`step`、`finish` | 源码级单步、不进入/进入函数、运行到当前函数返回 |
| 实际执行哪条指令 | `x/10i $pc`、`nexti`、`stepi` | 查看 PC 附近反汇编，按指令而非源码单步 |
| 某块内存是什么 | `x/16xb address`、`x/8gx address` | 以字节、8 字节十六进制等格式检查内存 |
| 寄存器是否符合预期 | `info registers`、`p/x $rsp` | 当前架构的寄存器以 `$` 引用 |
| 让每次停止都显示重点状态 | `display expr`、`undisplay N` | 自动展示表达式，适合循环变量和 PC |

### 1. `next`、`step` 与指令级单步

下面四条命令经常被混淆：

```text
next / n      ：执行到下一条源码语句，通常越过函数调用
step / s      ：执行到下一条源码语句，进入可用源码的函数调用
nexti / ni    ：执行一条机器指令，通常越过 call
stepi / si    ：执行一条机器指令，并进入跳转/调用目标
```

调 C++ 业务逻辑时优先使用 `next` 和 `step`；怀疑 ABI、汇编、JIT、编译器优化或裸机入口时再切到 `nexti`/`stepi`。源码级“下一行”与 CPU 的“下一条指令”并不等价：一行 C++ 可能展开为几十条指令，一条指令也可能被多个源码行共享。

### 2. 条件断点、命中次数和观察点

若循环会执行百万次，不要每次停下来：

```gdb
(gdb) break process_item if index == 4096
(gdb) condition 1 index > limit
(gdb) ignore 1 999
```

- 第一行只在条件满足时停；
- 第二行给编号为 1 的断点设置条件；
- 第三行忽略前 999 次命中。

变量“某时被改坏”时，观察点尤其有价值：

```gdb
(gdb) watch session->state
(gdb) continue
```

一旦表达式的值改变，GDB 会暂停并显示写入前后的值与当前位置。观察点可能使用 CPU 硬件调试寄存器，也可能由调试器用较慢的方法实现；可用数量和适用性依赖架构与目标，不应把它当作无限免费的断点。

## 六、从源码下降到机器码：寄存器、栈与内存

即使调试的是 C++，最终也常要回答“这一指针为何无效”“函数参数究竟传成了什么”“返回地址是否被破坏”。此时应从当前源码位置有控制地下降到机器级视图。

假设在 x86-64 Linux 上停止，可以先执行：

```gdb
(gdb) info registers
(gdb) p/x $rip
(gdb) x/12i $rip
(gdb) x/16gx $rsp
(gdb) disassemble /m first_even_index
```

| 命令 | 关注点 |
| --- | --- |
| `info registers` | 通用寄存器、指令指针与标志位的当前值 |
| `p/x $rip` | 以十六进制显示下一条指令地址；x86-64 中为 `rip` |
| `x/12i $rip` | 将 `rip` 附近内存按指令反汇编 |
| `x/16gx $rsp` | 从栈指针处按 8 字节十六进制单元查看栈内容 |
| `disassemble /m name` | 尝试把函数反汇编与源码行混合显示；需要相应调试信息 |

寄存器名随架构而变：AArch64 常见 `pc`、`sp`、`x0`，RISC-V 常见 `pc`、`sp`、`a0`，x86 16 位实模式则涉及 `CS`、`IP`、`DS`、`SS`、`SP`。不要把某个平台的寄存器名当成 GDB 的固定语法；固定的是“用 `$寄存器名` 访问目标当前寄存器”的思路。

### 1. 源码行和机器指令为何对不上

即使使用 `-g -Og`，也不要假设每一次 `next` 都准确走到视觉上的下一行：

- 一条源语句可能包含函数调用、临时对象构造、析构和异常处理；
- 编译器可能内联小函数，导致调用栈出现内联帧或函数边界变化；
- 一段源代码可能没有对应机器指令，例如编译器已证明其结果无用；
- 同一条指令可能同时对应多个内联调用位置；
- 高优化下，变量可以只在某个短暂区间存在于寄存器中。

因此，源码单步是理解程序的便利视图，反汇编、寄存器和内存才是运行状态的最终事实。两者不一致时，先确认优化级别和实际反汇编，不要为了让调试器显示“更顺眼”而假定 CPU 会配合你的直觉。

### 2. GDB 与 AddressSanitizer 不是替代关系

内存越界、use-after-free 和未定义行为常适合先用 Sanitizer 捕获：

```bash
g++ -std=c++20 -g -Og \
  -fsanitize=address,undefined \
  -fno-omit-frame-pointer \
  demo.cpp -o demo
```

AddressSanitizer/UndefinedBehaviorSanitizer 会在运行时插桩并报告许多内存与未定义行为问题；GDB 则适合继续检查触发点的调用路径、变量状态、线程关系和底层指令。一个负责更早地喊“这里非法”，另一个负责让你问清“为什么会走到这里”。二者一起使用，比要求任一工具独自包办全部错误更现实。

## 七、四种常见调试对象：启动、附加、core 与远程

GDB 不只可以从头启动一个程序。面对不同现场，应选择不同入口。

### 1. 启动新进程

```bash
gdb --args ./demo input.txt --verbose
```

在 GDB 中：

```gdb
(gdb) break main
(gdb) run
```

`--args` 之后的内容原样作为被调试程序的参数。适合能稳定复现的问题；你可以先设置断点、环境变量或信号处理规则，再运行程序。

### 2. 附加到正在运行的进程

```bash
gdb -p 12345
```

也可以先启动 GDB：

```gdb
(gdb) attach 12345
(gdb) info threads
(gdb) thread apply all bt
```

这适合 CPU 占满、请求卡住、死锁或只在长时间运行后出现的问题。附加通常会暂停目标进程及其线程，因此线上环境应先评估影响与权限边界；不要对关键生产进程随手执行会继续运行、写内存或调用函数的命令。

### 3. 分析 core dump

Linux 可先允许当前 shell 产生 core：

```bash
ulimit -c unlimited
```

当程序崩溃并生成 core 文件后：

```bash
gdb ./demo core
```

进入后优先执行：

```gdb
(gdb) bt
(gdb) info threads
(gdb) thread apply all bt full
```

core 是某个时刻的进程内存和线程状态快照，不是可继续正常运行的进程。因此它特别适合事后还原崩溃路径，却不能替代重现问题时的交互式单步。分析 core 时，`./demo` 与 core 必须来自相同构建；若使用了动态库，也要准备对应版本的库及其调试符号。

### 4. 连接远程目标

在目标 Linux 机器上运行：

```bash
gdbserver :2345 ./demo input.txt
```

在开发机运行：

```bash
gdb ./demo
```

然后连接：

```gdb
(gdb) target remote target-host:2345
(gdb) continue
```

这里的 `gdbserver` 运行在目标机，负责暂停和报告目标进程；完整 GDB 运行在开发机，负责读取符号、源码和提供交互界面。对于交叉编译目标，应使用匹配目标 ISA 的 GDB，并确保开发机加载的是与目标机程序严格一致的带符号文件。

## 八、GDB 如何调试 QEMU、内核与 8086 汇编

**可以使用 GDB 调试 8086 汇编**，但它和调试 C++ 程序的呈现形式不同。8086 boot sector 通常是 NASM 输出的平坦二进制文件，缺少 ELF/DWARF 信息；GDB 仍可以读取寄存器、反汇编、查看内存、单步和下断点，但未必能稳定显示“第几行 NASM 源码”。

典型关系如下：

```text
GDB
  ↓ GDB Remote Serial Protocol
QEMU 的 GDB stub
  ↓
模拟的 x86 CPU、BIOS、内存和启动设备
  ↓
16 位 boot sector 的机器码
```

例如 QEMU 启动时暂停并开放调试端口：

```bash
qemu-system-i386 \
  -drive format=raw,file=boot.img \
  -display none \
  -S -gdb tcp::1234
```

另一终端中：

```gdb
gdb
(gdb) set architecture i8086
(gdb) target remote :1234
(gdb) info registers
(gdb) x/10i $pc
(gdb) stepi
```

`-S` 让 QEMU 在客体 CPU 开始执行后立即暂停；`set architecture i8086` 让 GDB 以 16 位 x86 的视角解码指令；`stepi` 按机器指令单步。开始时 CPU 正在执行 BIOS，而不是你的引导扇区。若要观察自己的 boot sector，应继续执行或在 BIOS 装载后的 `0x7C00` 附近设置合适断点，并检查 `CS:IP`、`DS`、`SS:SP` 是否符合代码的假设。

完整的 WSL、QEMU、NASM 和 16 位引导扇区实验，可参阅 [QEMU 教程：从模拟整台机器到在 WSL 调试 8086 引导程序](<../../Assembly/02-boot-and-linking/06-QEMU 从模拟整台机器到调试 8086 引导程序.md>)。

内核、单片机或 QEMU 中的其他架构目标也遵循同一思想，只是 GDB 架构和目标端不同：例如 RISC-V 裸机项目通常使用 `riscv64-unknown-elf-gdb`，由 QEMU 或板载调试器提供远程 stub。GDB 远程协议让“调试器在哪台机器运行”与“代码在哪颗 CPU 上执行”不再必须相同。

## 九、Java、Python 为什么通常不用 GDB 调业务代码

Java、Python 当然最终也会经过机器指令层，但日常业务调试一般使用语言运行时更懂语义的工具：

| 语言 | 常用业务调试路径 | GDB 更常出现的场景 |
| --- | --- | --- |
| Java | IDE 通过 JDWP/JDI 与 JVM 交互 | JVM 崩溃、JNI、本地库、JIT 或 native 线程问题 |
| Python | `pdb`、`debugpy`、PyCharm 等，围绕 Python 帧和对象调试 | CPython 崩溃、C 扩展、NumPy/PyTorch 等 native 代码问题 |
| C/C++ | IDE 或命令行前端调用 GDB/LLDB 等原生调试器 | 日常源码级、内存级和 core 分析都常见 |
| 裸机/内核/汇编 | GDB 通过远程协议连接 QEMU 或硬件调试 stub | 寄存器、内存、反汇编与启动状态分析 |

Java 的 JVM 知道字节码、对象、垃圾回收和 Java 栈帧；Python 解释器知道 Python 帧、异常与对象。GDB 若附加到它们，首先看到的是 JVM 或 CPython 这个**本地进程**，而不是语言层自动整理好的业务调用栈。因此 GDB 并非不能调 Java/Python，而是调试层级已经下降到运行时、JIT 或 C 扩展，通常不是普通业务断点最合适的工具。

## 十、常见误解与可靠的排查顺序

### 1. “我能在函数名处下断点，说明一定有完整调试信息”

不一定。动态符号表或未剥离的符号表可能还保留函数名，但局部变量、类型和精确行号仍可能缺失。确认方式是查看 GDB 能否正确显示源码、`info locals` 和 `ptype`，以及用 `readelf --debug-dump=info` 等工具检查调试段，而不是只看到一个函数名就下结论。

### 2. “`<optimized out>` 表示变量不存在过”

不对。它可能曾经存在，但优化器把值折叠成常量、保存在已复用寄存器中、移动到另一控制流位置，或证明后续不再需要保存。调试优化构建时应结合反汇编、寄存器和源码上下文；若问题可复现，也可构建 `-g -Og` 版本交叉验证，但不能将两份构建的地址混为一谈。

### 3. “GDB 能看到内存，就能安全地修改任何变量”

不对。`set variable`、调用函数、修改寄存器或跳转 PC 都会改变被调试进程。它们适合受控实验和验证假设，不适合在未知的生产状态中随意尝试。观察与篡改是两种权限完全不同的动作。

### 4. “断点没有停，所以代码一定没执行”

也不一定。常见原因包括：调试的不是实际运行的二进制、共享库尚未加载、断点设置到内联/优化后不存在的位置、子进程/fork 路径不同，或目标因权限与地址随机化条件发生变化。先看 `info breakpoints`、`info sharedlibrary`、`info inferiors` 和当前 `bt`，再判断程序路径。

### 5. 推荐排查顺序

```text
确认正在调试哪一份进程、二进制和符号
    ↓
用调用栈确定失败路径和当前线程
    ↓
检查相关局部变量、参数与关键不变式
    ↓
使用条件断点或观察点找出状态首次变化的位置
    ↓
必要时下降到反汇编、寄存器和内存
    ↓
修复后补充能稳定复现该问题的测试
```

这条顺序看似普通，却能避免一种很常见的低效做法：一开始就在 `main` 单步数千行，然后因为见到太多变量和地址而失去问题本身。调试不是巡游程序，而是验证一个具体假设。

## 十一、开始使用 GDB 的最小清单

1. 编译 C/C++ 程序时至少加 `-g`；开发期推荐从 `-g -Og` 开始。
2. 让 GDB 加载与运行进程或 core **完全匹配**的二进制和符号。
3. 第一次停止后，优先执行 `bt`、`info locals` 和 `print`，先理解当前状态。
4. 循环和偶发问题使用条件断点、命中次数和 `watch`，不要手动单步到天荒地老。
5. 源码视图不能解释问题时，使用 `disassemble /m`、`x/i $pc`、`info registers` 回到机器级事实。
6. 内存安全问题同时启用 Sanitizer；GDB 负责解释路径，Sanitizer 负责尽早捕获大量非法访问。
7. 调试 QEMU、内核、嵌入式或 8086 时，使用匹配目标的 GDB 并通过远程 stub 连接；没有调试信息也仍可从寄存器和反汇编开始。

## 小结

- GDB 调试的是运行中的目标状态：控制流、线程、内存、寄存器、指令和停止事件。
- GDB 可以支持多种 CPU 架构，但不负责模拟 CPU；真实硬件、操作系统或 QEMU 才是实际执行者。
- C/C++ 能获得良好的 GDB 体验，不只因为会变成机器码，更因为 `-g` 输出的 DWARF 等调试信息保留了源码到机器码的映射。
- `-g -Og` 是学习和日常复现问题的可靠起点；优化构建也能调，但必须接受变量和控制流未必与源码逐行对应。
- GDB 可以调试 8086 汇编：通过 QEMU 等远程目标检查 `CS:IP`、寄存器、内存和反汇编，只是平坦二进制通常缺少源码级符号。
- 面对故障，先确认版本与符号，再看调用栈和变量，最后才进入指令与寄存器层。这样才是在使用调试器，而不是被它显示的一堆地址使用。
