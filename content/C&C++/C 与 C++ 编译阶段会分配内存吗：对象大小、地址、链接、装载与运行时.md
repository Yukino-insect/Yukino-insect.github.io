“C/C++ 编译时会不会给变量分配内存、决定内存地址？”这个问题的答案不能简单地用“会”或“不会”结束。这样回答虽然省事，却会把编译器、链接器、加载器和运行中的程序搅成一团；而它们本来就是四个不同阶段。

先给结论：**编译器会确定许多与内存有关的描述信息，例如对象的类型、大小、对齐、成员偏移、应放入的目标文件节，以及函数栈帧中可能使用的相对偏移；但它通常不会在编译时为“未来运行的程序”申请一块真实的运行时内存，也通常不能确定某次运行时对象的最终虚拟地址。**

真正的静态映像布局主要由链接器完成；操作系统加载器在程序启动时建立虚拟内存映射；自动存储期对象的栈空间由执行到函数时的机器指令建立；`malloc`、`new` 等动态对象则在对应调用执行时由运行库分配。至于物理页，现代操作系统还可能在首次访问时才实际提供。可见，“内存”二字本身就不够精确。

还有一个常被忽略的例外：编译器当然会消耗并申请**编译器进程自身**的内存，例如保存源文件、语法树、优化中间表示和符号表。但那是 `gcc`、`clang` 或 IDE 正在运行，不是你的 `app` 已经获得了将来要使用的内存。把宿主进程与目标程序区分开，很多困惑会立刻消失。

## 一、先把“分配内存”拆成五件事

同一句“给变量分配内存”，在不同语境中可能指完全不同的动作。

| 问题 | 主要阶段/参与者 | 得到的结果 | 是否已是目标程序可读写的真实存储 |
| --- | --- | --- | --- |
| `sizeof(T)`、成员偏移、对齐是多少？ | 编译器 | 类型布局规则和常量 | 否 |
| 局部变量在函数内怎样访问？ | 编译器 | 寄存器分配或栈帧的相对偏移 | 否 |
| 全局变量和函数在最终映像的什么位置？ | 链接器 | 节合并、符号地址、重定位结果 | 仍不是一次运行中的内存 |
| 程序启动后哪些地址区间可访问？ | 操作系统加载器、动态链接器 | 虚拟地址空间中的映射 | 是，至少建立了虚拟存储的承诺 |
| `malloc`/`new` 的对象放在哪里？ | 程序运行时的分配器，必要时操作系统 | 动态存储及其地址 | 是，发生在调用执行时 |

因此更准确的表述是：**编译阶段会分配“布局信息”和“代码中的访问方案”，不会替尚未启动的目标程序完成通常意义上的运行时内存分配。**

下面用一个小程序贯穿全文：

```c
#include <stdlib.h>

int initialized = 7;
int zero_initialized;
static int private_counter = 3;

struct Packet {
    char kind;
    int length;
};

int sum_packet(const struct Packet *packet) {
    int bias = 1;
    return packet->length + bias;
}

int main(void) {
    struct Packet packet = {'A', 12};
    int *numbers = malloc(10 * sizeof *numbers);

    if (numbers != NULL) {
        numbers[0] = sum_packet(&packet);
        free(numbers);
    }
}
```

它同时包含已初始化全局对象、零初始化全局对象、内部链接的静态对象、结构体、局部对象和动态对象。不要急着把它们统称为“都在内存里”；它们确实都会在某种时刻对应存储，但对应方式和时机不同。

## 二、语言层面先谈存储期，而不是“栈和堆”

在 C 和 C++ 的语言规则中，核心概念是**存储期**（storage duration），而不是“栈”“堆”这两个实现术语。后两者在绝大多数平台上很有用，但并不是语言标准为每个对象规定的物理位置。

| 例子 | 存储期 | 存储何时存在 | 常见实现位置 |
| --- | --- | --- | --- |
| `initialized`、`zero_initialized`、`private_counter` | 静态存储期 | 程序启动前建立，到程序结束 | 映像的数据区或零初始化区 |
| `packet`、`bias` | 自动存储期 | 执行到其声明所在块时，到离开该块 | 寄存器或当前线程栈帧 |
| `malloc(...)` 返回的对象 | 动态存储期 | 成功分配后，到 `free` | 运行库管理的动态分配区 |
| 字符串字面量、函数代码 | 静态存储期/程序映像的一部分 | 程序加载期间 | 只读映射、代码映射等 |

`static` 关键字与静态存储期、作用域、链接性之间的关系另有专文说明；这里先把它理解为：文件作用域的 `initialized` 和 `private_counter` 在程序的整个运行期间都只有相应的一份对象，区别主要是符号能否被其他翻译单元引用。[`static` 的作用域、存储期与链接性](C 与 C++ 的 static：作用域、存储期、链接与类成员.md)

自动存储期不等于“一定在栈上”。例如 `bias` 可能直接保存在寄存器中，优化后甚至会被折叠进一条加法指令，根本没有可观察的独立内存槽。只有当程序需要对象地址、对象不能被寄存器替代，或编译器出于调试、调用约定等原因保留槽位时，才常能在汇编中看到栈帧偏移。

```c
int twice(int value) {
    int result = value * 2;
    return result;
}
```

在关闭优化的调试构建中，`result` 往往会对应一个栈槽；在较高优化级别下，机器码可能只做一次寄存器加法后返回。**源代码中写了一个局部变量，不等于二进制中必有一个固定地址可供你观察。**

## 三、编译器究竟在什么时候“知道”内存布局

### 1. 类型大小、对齐和成员偏移

编译器必须知道对象的类型布局，才能生成读取和写入的代码。例如在常见 ABI 中，下面的 `Packet` 常出现 `kind` 位于偏移 `0`、`length` 位于偏移 `4` 的结果：

```c
struct Packet {
    char kind;
    int length;
};
```

中间的 3 个字节是为满足 `int` 的对齐要求而加入的填充。于是编译器可以把：

```c
packet->length
```

降低为类似“从 `packet` 地址加上固定偏移后读取一个 `int`”的机器操作。这里确定的是**相对布局**，不是某个 `Packet` 实例在本次运行中的绝对地址。

```text
Packet 对象起始地址：P

P + 0  : kind       （1 字节）
P + 1..3 : padding  （常见实现中的填充）
P + 4  : length     （4 字节）
```

`offsetof(struct Packet, length)` 得到的也是这种从对象开头算起的字节偏移，而不是一个已经存在的对象地址。具体布局会受目标 ABI、编译器、编译选项及字段类型影响，不能把某个平台的 `4` 当作跨平台常量。[`offsetof`、成员偏移与布局边界](C 与 C++ offsetof 宏：成员偏移、内存布局与可移植性边界.md)

### 2. 局部变量的“地址”常先表现为相对偏移

在未优化构建中，编译器会为函数生成一个栈帧方案。以 x86-64 上的伪汇编为例：

```asm
push    rbp
mov     rbp, rsp
sub     rsp, 16          # 运行到这里时才为当前调用腾出栈空间
mov     DWORD PTR [rbp-4], 1  # bias 的一个可能栈槽
```

编译时确定的是“若使用帧指针，`bias` 可以位于 `rbp - 4`”之类的关系。`rbp`、`rsp` 在函数被某个线程真正调用之前没有该次调用的具体值；多个线程同时调用同一函数时，各自栈帧中的 `bias` 地址也必然不同。

此外，`sub rsp, 16` 是**目标程序在运行时执行的指令**，不是编译器运行时向操作系统要 16 字节。编译器只是把这条指令写进将来的机器码。把“生成 `sub` 指令”和“执行 `sub` 指令”混为一谈，正是这个问题最常见的误区。

在 RISC-V 上，形式常变为 `addi sp, sp, -16`；含义仍是运行中的函数为自己的调用帧移动栈指针。此前 xv6 的入口汇编必须先设好 `sp`，原因也正在这里：进入 C 函数后，函数序言可能立刻使用它。[函数调用与栈：RISC-V ABI、`sp`、`ra` 和栈帧](../Assembly/04-函数调用与栈：RISC-V ABI、sp、ra 和栈帧.md)

### 3. 编译器也会生成“尚待决定”的符号引用

对同一翻译单元之外的函数或全局对象，编译器往往还不知道最终位置。例如：

```c
extern int shared_count;
int read_count(void) {
    return shared_count;
}
```

编译器知道 `shared_count` 的类型是 `int`，因而知道应生成一次 `int` 宽度的读取；但它不必、也通常不能知道这个符号最后由哪个目标文件或共享库提供。它会留下符号引用与重定位记录，让后续的链接器或动态链接器完成地址关联。

这解释了一个看似矛盾的事实：`extern` 声明让编译能通过，并不代表此时已经分配存储；真正的定义及其链接结果仍需在后续阶段满足。[`extern`：声明、定义、链接与跨语言接口](C 与 C++ 的 extern：声明、定义、链接与跨语言接口.md)

## 四、`.o` 文件里有什么：描述、字节与待修补位置

以 Linux/ELF 为例，源文件经过编译和汇编后会形成可重定位目标文件（通常为 `.o`）。它已经包含实际机器码和某些数据字节，却仍不是可以直接按最终布局运行的完整进程映像。

对于示例程序，常见的对应关系大致如下：

| 源码对象 | `.o` 中常见归宿 | 文件中是否一定有同等大小的初始化字节 | 为什么 |
| --- | --- | --- | --- |
| `initialized = 7` | `.data` | 是 | 初值 `7` 需要被保存 |
| `zero_initialized` | `.bss` | 通常否 | 只需记录“运行时要有这么大一段零初始化存储” |
| `private_counter = 3` | `.data` | 是 | 它仍是静态存储期对象，只是内部链接 |
| `sum_packet`、`main` | `.text` | 是 | 机器指令字节 |
| `malloc`、`free` 的调用 | 符号表和重定位节 | 调用位置有指令，目标地址尚可能待定 | 定义通常来自 C 运行库 |

`.bss` 特别能说明“文件大小”和“运行时内存大小”不是同一件事。声明：

```c
char buffer[1024 * 1024];
```

若它具有静态存储期且零初始化，目标文件不必真的写入一百万个 `0x00` 字节；节头只需记录其需要的内存大小。加载程序映像时，加载器会把相应内存视为零初始化。文件中没有一大段数据，并不表示程序运行时没有这块对象。

目标文件内的“地址”也要谨慎理解。某些符号值只是在某个节中的偏移，或只是配合重定位表达式使用；尚未和所有其他目标文件合并，更没有成为这次进程启动后的最终地址。因此，看到 `readelf -s demo.o` 输出一个数值，不能草率地把它称为“变量运行时的内存地址”。

## 五、链接器把许多局部布局合成一个映像布局

链接器读取多个 `.o` 文件和库，主要完成：

1. 合并相同类别的节，例如多个 `.text`、`.data`、`.bss`；
2. 解析符号定义与引用，确认 `malloc`、`shared_count` 等名字到底指向哪里；
3. 为节和符号安排映像内的位置；
4. 按重定位规则修补指令和数据中的引用；
5. 写出可执行文件或共享库。

这一步确实比编译阶段更接近“决定地址”。对于非位置无关的可执行映像，链接器可能写入一个预定虚拟地址布局；链接脚本甚至可以明确指定节的虚拟地址。这类数值仍要称为**链接视角的映像地址**，不要误解成“某次运行已经分配到的物理内存”。

位置无关可执行文件（PIE）和共享库会刻意避免把所有引用固定为一个绝对地址。代码常采用“相对当前指令位置”的计算，或通过 GOT/PLT 间接引用符号；这样加载器就能把同一份映像放到不同基址。ASLR 正是让不同进程、甚至同一程序的不同运行，看到不同虚拟地址的重要原因之一。

```text
同一份 app 文件

第一次运行：映像基址 = A
第二次运行：映像基址 = B

同一个全局对象相对映像的偏移相同，
但它的运行时虚拟地址可分别为 A + offset 与 B + offset。
```

所以“链接器已经把地址写进 ELF”与“地址在所有运行中永远相同”不是同一命题。ELF 中的节、符号、重定位、程序头及动态链接信息可参见：[C 与 C++ ELF 文件格式：目标文件、可执行文件与动态链接](C 与 C++ ELF 文件格式：目标文件、可执行文件与动态链接.md)

## 六、装载时才出现进程自己的虚拟地址空间

用户在终端执行：

```bash
./app
```

这之后，操作系统才会创建一个新进程，并由加载器根据可执行文件的程序头建立相应的虚拟内存区域。简化后可理解为：

```text
源文件
  -> 编译/汇编：.o、符号、重定位、节
  -> 链接：ELF 可执行文件或共享库
  -> exec/加载：新进程的虚拟地址空间
  -> 进入运行库和 main
```

常见映射大致包括：

| 映像内容 | 常见访问权限 | 运行时含义 |
| --- | --- | --- |
| 代码段 | `r-x` | 函数机器码，通常不可写 |
| 只读数据 | `r--` | 字符串字面量、常量表等 |
| 已初始化数据 | `rw-` | 如 `initialized`、`private_counter` |
| 零初始化数据 | `rw-` | 如 `zero_initialized` 与大型静态零数组 |
| 共享库、动态链接器 | 因库而异 | 在需要时参与符号解析和重定位 |
| 初始线程栈 | `rw-` | `main` 的参数、环境及后续调用帧 |

此刻静态存储期对象才作为新进程的一部分拥有可访问的存储。每次启动 `app` 都是新进程，因而都有属于自己的 `initialized`、`zero_initialized`；一个进程改写自己的全局变量，不会直接改写另一进程的那份变量。

还应分开**虚拟内存映射**与**物理页**。现代操作系统常使用按需分页：加载器可以先建立一段合法的虚拟地址范围，直到程序实际读取或写入相应页面时，内核才提供物理页或从文件载入内容。这个细节依赖操作系统与映射方式，但它再次说明“加载完成”也不必等于“所有字节都已经驻留在 RAM”。

## 七、函数真正被调用时，自动存储期对象才取得本次调用的存储

回到：

```c
int sum_packet(const struct Packet *packet) {
    int bias = 1;
    return packet->length + bias;
}
```

程序刚加载时，内核只知道 `sum_packet` 的机器码位于代码映射中；它不会预先为每一个未来调用准备一个 `bias`。当某个线程执行到 `call sum_packet` 后，控制流进入函数，函数序言或调用者准备代码才会按 ABI 调整该线程的栈指针、保存需要的寄存器，并在必要时使用栈槽。

因此递归调用不会互相覆盖局部变量：每一次调用都有自己的调用帧。多线程同时调用也一样，每个线程有独立的栈。反过来，若把局部对象的地址返回给调用者，函数结束后那一帧的存储期已经结束，继续解引用就是错误的；这里的问题是对象生命周期，而不是“编译器忘记分配地址”。

```c
int *bad(void) {
    int value = 42;
    return &value; // 返回后 value 的自动存储期已结束
}
```

编译器可能对此诊断，也可能在优化下让现象与调试构建不同；无论碰巧读到什么数值，程序都不能依赖它。

## 八、执行到 `malloc` 或 `new` 时，动态对象才被分配

示例中的：

```c
int *numbers = malloc(10 * sizeof *numbers);
```

在编译阶段，编译器能够完成的工作包括：

- 检查声明是否可见，推导 `sizeof *numbers` 为 `sizeof(int)`；
- 生成对 `malloc` 的调用或等价优化代码；
- 知道返回值应按 `int *` 的用途使用；
- 在需要时为外部符号引用保留重定位信息。

但 `numbers` 到底得到 `NULL` 还是哪个地址，取决于程序运行到这一行时的资源、分配器状态、大小类别和实现策略。**只有调用真的执行，动态分配器才会返回一段动态存储的地址。**

而且 `malloc` 不意味着每次都会立刻进行一次系统调用。成熟的分配器往往从已有的空闲块、线程缓存或预先向内核申请的大块区域中切分；需要扩容时才可能通过平台接口请求更多虚拟内存。对程序员而言，可靠的边界是：`malloc` 成功返回后取得一块满足其对齐要求的存储，`free` 后不能再使用它。具体“堆”如何组织是库和平台的实现细节。

C++ 的 `new` 也有两层：先取得动态存储，再在该存储上构造对象；`delete` 会先析构再释放相应存储。不要把“构造函数代码已被编译进程序”误认为对象已经提前存在。

## 九、三个很容易混淆的例子

### 1. 全局变量：早就写入文件，不等于编译时分配了进程内存

```c
int answer = 42;
```

编译后，初始值通常已经以数据字节出现在 `.o`，链接后也会成为可执行映像的一部分。这个过程会确定大量布局信息；但在你尚未启动程序时，磁盘上的 ELF 文件不是一个正在运行的进程。启动时加载器为新进程映射数据区域后，`answer` 才有该进程内可访问的地址。

### 2. 局部数组：编译器能算出大小，不等于现在占了一块栈

```c
void work(void) {
    char buffer[4096];
    (void)buffer;
}
```

编译器知道固定长度为 `4096`，也可能在函数序言中生成一次较大的栈指针调整；实际栈空间属于调用 `work()` 的线程，只有执行到这次调用时才涉及。若函数从未被调用，当然不会有“此次 `buffer` 对象”的存储被建立。

对于 C 的变长数组（VLA，C99 引入、从 C11 起由实现选择是否支持），大小甚至需要运行时计算：

```c
void work(size_t n) {
    int values[n]; // C++ 中不是标准数组语法
    (void)values;
}
```

这里编译器生成“根据 `n` 调整存储”的代码，但它无法在编译时知道这次调用的 `n`。也请避免把大数组不加判断地放到自动存储期；栈容量通常远小于可用虚拟内存，栈溢出不会因为数组语法看起来朴素就变得温柔。

### 3. `new`：编译阶段只生成调用路径，不保证成功也不预留地址

```cpp
Widget *widget = new Widget("ready");
```

编译器会检查构造函数重载、生成构造与析构所需的代码，并安排分配函数调用。运行时才可能分配存储、执行构造函数，或因分配失败抛出 `std::bad_alloc`（普通抛异常版本的 `new`）。所以把 `new` 理解为“编译时把对象放进堆”完全颠倒了时序。

## 十、优化会进一步打破“一个变量对应一个地址”的想象

在 C/C++ 的抽象语义中，对象的生命周期和可观察行为有规则；但在不改变可观察行为的前提下，优化器可以改变内部表示。常见情况包括：

- 将局部变量保存在寄存器中；
- 常量传播并删除不再需要的变量；
- 内联函数，使原本的函数栈帧不再单独存在；
- 消除未被使用的局部数组或整个函数；
- 标量替换，把一个小对象拆成几个寄存器值；
- 合并相同常量，或删去未被引用的静态对象（受链接和可见性约束）。

例如：

```c
int f(void) {
    int value = 21;
    return value * 2;
}
```

优化后很可能等价于直接返回常量 `42`。此时追问“`value` 的内存地址是多少”并没有合适答案，因为目标程序根本未必保留该对象的独立运行时存储。只有程序确实要求地址可观察时，例如 `int *p = &value;` 且指针被以不能消除的方式使用，编译器才需要满足相应的对象语义。

调试构建常故意少做此类优化，以便断点和变量查看更直观；这解释了为什么“开 `-O2` 后局部变量在调试器里消失或显示为 optimized out”不一定是调试器坏了。

## 十一、怎样亲手验证每一层

下面的命令以 Linux 上的 GCC 和 ELF 为例；不同平台的工具名称、节名或输出格式会不同，但观察思路相同。

### 1. 只编译成目标文件

```bash
gcc -std=c17 -O0 -g -c demo.c -o demo.o
readelf -SW demo.o
readelf -sW demo.o
readelf -rW demo.o
```

可分别观察节表、符号表和重定位表。此时的 `demo.o` 已含代码与数据，却还可能有未解析的 `malloc`、`free` 等外部引用。这是“编译/汇编已经产生二进制布局信息，但地址尚未完全落实”的直接证据。

### 2. 对比未优化与优化后的函数实现

```bash
gcc -std=c17 -O0 -S demo.c -o demo-O0.s
gcc -std=c17 -O2 -S demo.c -o demo-O2.s
```

比较 `sum_packet` 或一个更简单函数的汇编。`-O0` 更可能显示明确栈槽；`-O2` 可能把局部变量放入寄存器、内联或直接消去。不要拘泥于某一条固定指令，编译器版本、目标架构和 ABI 都会改变具体输出。

### 3. 链接后查看程序头与装载映射

```bash
gcc -std=c17 -O0 -g demo.o -o demo
readelf -lW demo
./demo &
pid=$!
cat /proc/$pid/maps
wait $pid
```

`readelf -lW` 中的程序头描述加载器应如何映射文件，而 `/proc/<pid>/maps` 则显示某次实际运行时的虚拟地址区域。若程序运行得太快，可在 `main` 中临时加入受控的等待，或使用调试器暂停；不要因为看不到短命进程就擅自认为映射不存在。

### 4. 观察一个对象的实际地址

```c
#include <stdio.h>
#include <stdlib.h>

int global_value = 7;

int main(void) {
    int local_value = 8;
    int *dynamic_value = malloc(sizeof *dynamic_value);

    printf("global : %p\n", (void *)&global_value);
    printf("local  : %p\n", (void *)&local_value);
    printf("dynamic: %p\n", (void *)dynamic_value);
    free(dynamic_value);
}
```

多运行几次，尤其是默认启用 PIE/ASLR 的环境中，你往往会看到地址改变。这里真正值得比较的是区域和关系：局部变量通常接近线程栈，动态对象位于分配器管理的区域，全局变量位于程序数据映射。**不要把具体十六进制数写进业务逻辑；地址每次相同只是某个构建和运行环境的现象，不是 C/C++ 的承诺。**

## 十二、把问题改写后，答案就清楚了

与其问“编译阶段会不会分配内存”，不如按下面方式提问：

| 更准确的问题 | 答案 |
| --- | --- |
| 编译器会不会知道 `struct` 的大小和成员偏移？ | 会，必须知道，才能生成访问代码。 |
| 编译器会不会决定局部变量可能位于哪个栈偏移？ | 会，但这只是运行时栈帧的相对方案，而且优化后未必有槽位。 |
| 编译器会不会替未来的 `main` 进程向操作系统申请堆或栈？ | 通常不会。编译器是另一个进程。 |
| `.o` 中是否已有全局变量的初值和大小描述？ | 通常有；零初始化对象还可能主要由 `.bss` 大小表示。 |
| 链接器会不会决定映像中的符号位置并修补引用？ | 会。 |
| 加载器会不会为每次运行建立虚拟地址空间？ | 会。 |
| `malloc`/`new` 何时真正给动态对象存储？ | 对应调用在运行时执行时。 |
| 一个对象是否总有稳定、可打印的机器地址？ | 不一定；优化、PIE、ASLR、多线程调用和对象生命周期都会影响答案。 |

## 总结

编译阶段并不是“什么内存都不管”。它严肃地决定类型布局、对象大小、对齐、成员偏移、节归属、符号引用和函数访问方案；否则生成的机器码连该读取几个字节、从哪里偏移都无从谈起。

但它也不是在提前运行你的程序：

- **编译器**生成描述内存的机器码、节与符号信息；
- **链接器**把多个目标文件组织成一个映像并解决许多地址引用；
- **加载器**为本次进程建立虚拟内存映射；
- **函数调用**在运行时建立本次调用的自动存储；
- **`malloc`/`new`** 在运行时取得动态存储；
- **操作系统**可能再按需将虚拟页关联到物理内存。

所以，当看到一行 C/C++ 变量声明时，最好的问题不是“它编译时会不会分配内存”，而是：**它是什么存储期？编译器需要确定什么布局？它在链接后的映像中如何表示？在哪个运行时事件发生后才具有本次进程中的可访问地址？**把这四层分开，地址、栈、堆、全局变量和重定位就不再互相伪装成同一件事了。
