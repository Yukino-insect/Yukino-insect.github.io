很多人第一次接触 ClickHouse 时，先听到的是「快」「适合大数据」「列式数据库」。这些结论没有错，却不足以指导第一次建表：为什么订单系统不能直接搬进去？为什么同样是一张表，写一行和写十万行的结果差得很大？`ORDER BY` 又为什么不像 MySQL 的普通排序语句？

本课程不假定你已经会数据库调优。我们从一张每天持续产生访问记录的表开始，先分清“保存一笔当前事实”和“从大量历史事实中找规律”是两类问题；随后亲手启动一个独立实例、建表、写入、查询，并在最后处理保留期限、慢查询与恢复。示例只使用虚构的网页访问事件，不依赖任何特定业务代码。

## 先回答：为什么需要另一类数据库

假设商店有两项需求：

- 顾客付款后，必须立刻把订单 `paid` 改为 `shipped`，不能改丢、不能出现两次扣款；
- 运营人员想知道过去 90 天每天的访问量、各页面的错误率和 P95 响应时间。

第一项是 **OLTP（联机事务处理）**：数据量通常围绕单个用户或订单，读取、插入、更新要在短事务中保持一致。MySQL、PostgreSQL 这类行式事务数据库很合适。

第二项是 **OLAP（联机分析处理）**：一次查询往往要在数百万到数十亿条历史记录中读取几个字段、分组和聚合。ClickHouse 是为这一类问题设计的列式分析数据库。它不替代事务库；更常见的做法是让事务库保存订单真相，再把不可变的“订单已创建”“页面被访问”等事件批量送来分析。

| 你要解决的问题 | 优先考虑 | 原因 |
| --- | --- | --- |
| 修改一个账户余额、保证订单状态一致 | MySQL / PostgreSQL | 短事务、行级更新、约束与回滚 |
| 汇总一年内每小时的访问量 | ClickHouse | 只读少数列，适合并行扫描与聚合 |
| 保存 PDF、图片、录音等大文件 | 对象存储 | 文件并非数据库行；成本和生命周期模型不同 |
| 临时缓存、分布式锁 | Redis 等缓存/协调工具 | 需要低延迟可变状态，而不是历史分析 |

这里的“事件”是一条已经发生、通常不会再修改的记录，例如“用户在 10:03 打开了商品页，耗时 42 ms”。它是学习 ClickHouse 最好的起点：既容易生成，又能自然地按时间统计。

## 这门课会建立的心智模型

ClickHouse 中最容易混淆的六个词如下。现在只需有轮廓；后面的实验会逐一验证。

| 词 | 初学者可以先这样理解 |
| --- | --- |
| 数据库 | 表的命名空间，例如 `analytics_lab` |
| 表 | 有固定列和引擎的数据集合，例如 `page_events` |
| 列式存储 | `event_time` 的值连续放在一起，`latency_ms` 的值连续放在一起；查平均耗时时无需读完整 JSON 载荷 |
| part | 一次或一批写入落盘形成的不可变小数据片段 |
| merge | 后台把同一分区的小 part 合成大 part，减少文件与查询开销 |
| 分区与排序键 | 分区管理一大块数据；排序键安排每个 part 内数据顺序，帮助查询少读数据 |

不要急着背参数。先知道：**分区不是给每个用户建目录，排序键不是唯一约束，part 也不是一行数据。**

## 学习路径与实验约定

请按顺序学习，因为后一篇会直接使用前一篇建立的概念。

1. [列式存储、MergeTree 与数据模型](01-columnar-merge-tree-data-model.md)：用小数据解释行存/列存、表、列、part、merge、分区和排序键。
2. [Docker、SQL 与系统表动手实验](02-clickhouse-docker-sql-practice.md)：启动独立容器，创建第一张表，写入和查询数据，查看 ClickHouse 自己记录的状态。
3. [摄入、分区、排序键与 TTL](03-ingestion-partition-orderby-ttl.md)：从“能跑”走向“能长期跑”，学习批量写入、重复数据、生命周期和汇总表。
4. [查询观测、备份恢复与故障排查](04-query-observability-backup-operations.md)：用系统表找证据，完成一次隔离恢复，而不是把备份文件当作成功。

命令默认在 PowerShell 中执行，容器名固定为 `ch-lab`，数据库名为 `analytics_lab`。请使用独立的本地 Docker volume；不要将实验命令指向已有的数据库服务。

## 开始前检查

需要 Docker Desktop（或可用的 Docker Engine）、PowerShell，以及约 4 GiB 空闲内存和一些磁盘空间。先执行：

```powershell
docker version
docker info --format '{{.ServerVersion}}'
```

如果这两条命令失败，先修复 Docker，再继续课程。数据库实验的第一条原则是确认目标：每次执行 `docker` 命令前都要看清容器名和 volume 名，避免把练习操作误用于其他服务。

## 本课程完成时的最低证据

读完不等于掌握。你应能保留或重新做出以下证据：

- 一份能解释 `PARTITION BY` 和 `ORDER BY` 的建表语句；
- 一次至少十万行的批量写入，以及 `system.parts` 的检查结果；
- 一条带时间范围和一条不带时间范围的查询，并能比较它们的读取量；
- 一个 TTL 表和一次可解释的过期观察；
- 一次在隔离实例恢复后的行数、分区和抽样核对。
