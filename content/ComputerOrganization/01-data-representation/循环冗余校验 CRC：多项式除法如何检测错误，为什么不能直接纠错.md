CRC（循环冗余校验）的职责是**高效地发现传输或存储中的错误**，不是在不知道错误位置的情况下直接修好数据。它的核心规则很简单：发送端构造一个“能被生成多项式整除”的比特串；接收端再除一次，余数非零就说明数据已损坏。网络协议通常丢弃损坏帧并重传，存储系统则可能从副本或纠错码恢复。

公式看起来像多项式，实际运算却只是移位和 XOR。本篇会逐步手算一个完整 CRC，解释“余数为何能检错”“为何会漏检”，再给出一段可运行的 Python 代码。若只需要理解最基础的单错检出，可以先看[《奇偶校验码：用一个校验位检测传输中的单比特错误》](奇偶校验码：用一个校验位检测传输中的单比特错误.md)。

## 一、先分清 CRC、纠错和重传

三者处理错误的方式不同：

| 机制 | 接收端知道什么 | 接收端的典型动作 |
| --- | --- | --- |
| 检错 | 数据不可信 | 丢弃、报错或请求重传 |
| 纠错 | 错误位置或原数据可唯一确定 | 修复后再交付数据 |
| 重传 | 对方仍可重新发送 | 用一份新副本替换损坏数据 |

CRC 通常提供第一种能力。校验失败产生的 `r` 位余数只有有限种，而一帧中“哪些位可能出错”的组合数量会随帧长迅速增长；许多不同错误必然映射到同一个余数。因此，仅凭余数通常不能唯一判断“哪一位该翻转”。把一个可能错误的串强行修正，只会让错误显得更有条理，并不会让它真的消失。

## 二、为什么比特串能写成多项式

将从左到右的比特看作从高次到低次的系数。例如：

```text
1101  ->  1·x³ + 1·x² + 0·x + 1  ->  x³ + x² + 1
1011  ->  x³ + x + 1
```

CRC 在 `GF(2)` 上运算，即系数只有 `0`、`1`，且不产生进位或借位：

$$
1 + 1 = 0,
\qquad
1 - 1 = 0
$$

所以多项式加法和减法都是逐位 XOR：

```text
1101
1011
---- XOR
0110
```

这就是 CRC 长除法没有普通除法中的乘法表、进位和借位的原因。把除数对齐到当前最高位，做一次 XOR；继续处理下一个最高位即可。硬件中的移位寄存器和 XOR 门正好很擅长这个过程。

## 三、发送端怎样构造可验证的码字

选择生成器 `G`。若它有 `r` 次最高项，则 CRC 字段恰有 `r` 位。设原消息为 `M`：

1. 将 `M` 末尾补 `r` 个 `0`，相当于计算 $x^rM(x)$；
2. 用 `G` 对它做模 2 除法，得到 `r` 位以内的余数 `R`；
3. 将补的 `0` 替换为 `R`，发送 $T(x)=x^rM(x)+R(x)$。

因为 `R` 正是除法余数，`T` 被 `G` 整除。接收端用同一个 `G` 除收到的整帧，合法帧的余数应为 0。

### 1. 完整手算：`1101` 配合生成器 `1011`

取消息 `M = 1101`，生成器 `G = 1011`。`1011` 代表 $x^3+x+1$，最高次数为 3，因此先补 3 个零：

```text
消息 M：      1101
补零后：      1101000
生成器 G：    1011
```

下面每一行都把 `1011` 左移到当前剩余串的第一个 `1` 处，再 XOR。对齐的 `1011` 以 7 位展示，便于看清位置：

```text
1101000
1011000  <- 1011 左移 3 位
-------
0110000

0110000
0101100  <- 左移 2 位
-------
0011100

0011100
0010110  <- 左移 1 位
-------
0001010

0001010
0001011  <- 不再左移
-------
0000001
```

最后余数是 `001`。因此 CRC 字段为 `001`，发送的完整帧是：

```text
T = 1101 001 = 1101001
```

再把 `1101001` 用 `1011` 相除，四轮 XOR 后会恰好全部变成 `0`。这一步也解释了一个常见细节：CRC 不是把任意校验值附在末尾，而是专门选择了一个余数，让“数据 + CRC”满足整除约束。

### 2. 接收端发现一位错误

假设发送的 `1101001` 的第 5 位从 `0` 翻成 `1`，接收端看到 `1101101`。用同一生成器做除法：

```text
1101101
1011000
-------
0110101

0110101
0101100
-------
0011001

0011001
0010110
-------
0001111

0001111
0001011
-------
0000100
```

余数为 `100`，不是 0，因此接收端知道这帧不符合 CRC 规则，应拒绝它。注意它只知道“规则被破坏了”，并不知道第 5 位一定错了；这是 CRC 与汉明码这类纠错码的根本区别。

## 四、余数为何只由错误模式决定

把正确发送的帧写为 `T(x)`，传输中每个翻转位组成错误多项式 `E(x)`。接收到的是：

$$
T'(x) = T(x) + E(x)
$$

正确帧可被 `G(x)` 整除，即 $T(x) \bmod G(x)=0$。在 `GF(2)` 中取余仍满足分配关系：

$$
T'(x) \bmod G(x) = E(x) \bmod G(x)
$$

也就是说，收到帧的余数与原消息内容无关，只反映错误模式是否能被生成器整除。对于单比特翻转，`E(x)=x^i`；只要生成器常数项为 1，它不可能整除 $x^i$，因此 CRC 必然发现所有单比特错误。

### 1. 漏检不是偶然，而是有限校验的边界

如果错误模式本身恰好是 `G(x)` 的倍数，则余数仍为 0。例如当前生成器的比特模式为 `1011`，若某 7 位帧后 4 位恰好发生 `1011` 这一错误模式：

```text
正确帧：1101001
错误模式：0001011
接收结果：1100010
```

由于 `0001011` 对应的就是 `G(x)`，它除以 `G(x)` 的余数为 0；接收结果也会通过校验。真实 CRC 使用精心选择的长生成器，目的正是让实际链路常见的错误模式尽可能难以成为其倍数，而不是声称“任何错误都绝不漏过”。

### 2. 常见的检测保证

对次数为 `r`、首尾系数均为 1 的生成器，可得到这些易用结论：

- 所有单比特错误都能检测到；
- 所有跨度不超过 `r` 位的突发错误都能检测到；
- 若生成器含因子 `x + 1`，所有奇数个比特翻转都能检测到；
- 对没有特殊结构的随机错误，漏检概率通常约为 $2^{-r}$，但这不是对每一种错误的绝对保证。

“突发长度”是第一个错误位到最后一个错误位的跨度，之间的某些位可以没有翻转。CRC 对连续干扰很有效，正是因为长生成器能排除大量短突发模式。

## 五、用 Python 复现模 2 长除法

这段代码没有调用库，直接实现上面的“遇到最高位 `1` 就 XOR”过程。它适合验证原理；生产环境应使用协议规定的 CRC 实现或成熟库，并完整匹配反射、初值、最终异或和字节序等参数。

```python
def mod2_remainder(dividend: str, generator: str) -> str:
    """返回 GF(2) 长除法余数，长度恒为 len(generator) - 1。"""
    if not generator or generator[0] != "1":
        raise ValueError("生成器必须以 1 开头")
    if any(bit not in "01" for bit in dividend + generator):
        raise ValueError("输入必须是二进制字符串")

    work = [int(bit) for bit in dividend]
    divisor = [int(bit) for bit in generator]
    for start in range(len(work) - len(divisor) + 1):
        if work[start] == 1:
            for offset, bit in enumerate(divisor):
                work[start + offset] ^= bit

    return "".join(str(bit) for bit in work[-(len(generator) - 1):])


def crc_encode(message: str, generator: str) -> str:
    degree = len(generator) - 1
    remainder = mod2_remainder(message + "0" * degree, generator)
    return message + remainder


generator = "1011"
frame = crc_encode("1101", generator)
print(frame)                              # 1101001
print(mod2_remainder(frame, generator))  # 000
print(mod2_remainder("1101101", generator))  # 100，第 5 位翻转后的错误帧
```

这段实现还能解释“为什么补零”：若不先预留 `r` 位，余数会覆盖消息的低位；先补零再把余数写回，消息位保持不变，而整个帧变为可整除的码字。

## 六、CRC 与纠错码如何配合

CRC 和 ECC 往往协作，而非相互替代：

| 场景 | 常见组合 | 恢复方式 |
| --- | --- | --- |
| 以太网、分组传输 | CRC + ARQ 重传 | 丢弃坏帧，请发送端重发 |
| 无线、深空通信、闪存 | FEC/ECC + CRC | 先尝试纠错，再用 CRC 确认候选结果 |
| 存储块和文件 | CRC/校验和 + 副本或 RAID | 检出静默损坏，从冗余副本恢复 |

有些纠错译码器会给出“最可能”的数据，而不是数学上绝对确定的数据。此时 CRC 可以作为最后的验收条件：CRC 通过才接受该候选码字。CRC 参与纠错链路，并不等价于 CRC 本身能在通用情形下定位并修复错误。

## 七、总结

- CRC 将比特串视为 `GF(2)` 上的多项式；这里的加减法就是 XOR，没有进位和借位。
- 发送端对消息补零、取模 2 除法余数并填回，构造出能被生成器整除的完整帧。
- 接收端余数非零表示检测到错误；余数只与错误模式有关，通常不足以唯一定位错误位置。
- 特定错误模式是生成器的倍数时会漏检，因此 CRC 提供的是强检错而非绝对检错。
- 发生错误后的恢复通常依赖重传、副本或专门的纠错码；CRC 负责把不可信的数据拦在交付之前。
