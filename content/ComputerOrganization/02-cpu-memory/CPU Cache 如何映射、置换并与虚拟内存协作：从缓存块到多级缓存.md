CPU Cache（高速缓存）常被描述成“主存与 CPU 之间的缓存”。这句话没有错，却省略了真正决定它能否工作的部分：一个内存地址怎样找到某个缓存块；该位置已经被占用时谁该离开；多级缓存、多个核心与虚拟内存又怎样避免各说各话。

先给出总论：**缓存块的查找、填充、置换和脏数据回写，主要由各级 Cache 自己的控制器完成；虚拟地址翻译由 MMU、TLB 和页表机制完成；多核之间的数据一致性由一致性协议及其互连逻辑维持**。它们必须紧密配合，但不是一个部件包办全部工作。

本文以常见的现代处理器设计为背景。具体 Intel、AMD、Arm 或 RISC-V 芯片的层级、策略和命名会不同，因此不要把某一种实现细节误当作所有 CPU 的硬规则。

## 一、为什么 Cache 要按“块”而不是按一个字节管理

主存按字节编址，但 CPU 很少只使用孤立的一个字节。程序顺序执行指令、遍历数组时，刚访问过的数据附近往往很快还会被访问。这叫**空间局部性**；刚访问的数据本身短时间内再次被用到，叫**时间局部性**。

所以 Cache 从主存取数据时，通常一次搬运一整段连续字节，称为**缓存块**或**缓存行**（cache line）。64 字节是很常见的行大小，但不是唯一选择。

设一台机器采用 64 字节缓存行。地址最低的 6 位决定该行内的字节位置，因为：

$$
64=2^6.
$$

例如 CPU 要读取地址 `0x...3C`，控制器不会只保存这个地址对应的一个字节；它会把以该缓存行起始地址为边界的一整行放入 Cache。随后读取同一行的 `0x...3D`、`0x...40` 等地址，通常就不必再次访问更慢的下层存储。

每个缓存行除了数据，还至少有两类元数据：

- **有效位**（valid）：该位置是否装着一行可用数据；
- **标记**（tag）：这行数据原来属于哪一段内存地址。

写回型 Cache 还要有**脏位**（dirty），多核系统还常有一致性状态位。也就是说，Cache 不只是“小一点的 RAM”；它是“数据阵列 + 标签阵列 + 状态位 + 控制逻辑”的组合。

## 二、一个地址如何映射到 Cache：偏移、组号与标记

假设某级 Cache 是 32 KiB、4 路组相联、每行 64 B。它共有：

$$
\frac{32\text{ KiB}}{64\text{ B}\times4}=128
$$

个组（set）。128 是 $2^7$，于是一个地址可概念性地拆成：

```text
|          tag          | set index | block offset |
|       高位标记         |   7 位    |     6 位     |
```

- `block offset`：从命中的 64 B 行中挑出所需字节；
- `set index`：选中 128 组中的哪一组；
- `tag`：与该组内每一路保存的 tag 比较，确认是否真是所要的内存块。

这里的“路”（way）可以理解为同一组中的多个停车位。组号相同的主存块只能停进同一组，但在这一组内可以选择多个停车位。

### 1. 三种映射方式

| 映射方式 | 一个内存块能放到哪里 | 优点 | 代价 |
| --- | --- | --- | --- |
| 直接映射 | 唯一的一组、唯一的一路 | 结构简单、命中判断快 | 两个冲突块会反复互相挤掉 |
| 全相联 | 任意位置 | 几乎没有位置冲突 | 需要比较很多 tag，成本高 |
| 组相联 | 唯一的一组中的任一路 | 速度、成本、冲突率折中 | 组内满时要选择被替换者 |

现代通用 CPU 的 L1、L2、LLC（最后一级缓存）多数采用组相联。直接映射太容易发生冲突，全相联又通常过于昂贵；工程上偏爱折中，并不神秘。

### 2. 命中和未命中由谁判定

CPU 发出一次读写请求后，该级的 **Cache controller** 用 index 读出目标组的 tag 和状态，再并行比较各路 tag：

```text
地址
  -> 用 index 选中一组
  -> 比较该组每一路的 valid + tag
  -> 命中：选择对应的数据路，按 offset 取数
  -> 未命中：向下一层请求整行数据，并安排填入位置
```

因此，“Cache 映射由哪个部件管理”的准确答案是：**由该 Cache 所在层级的控制器硬件在每次访问时完成**。L1 控制器通常紧贴 CPU 核；共享 L3 的控制器通常位于核外的共享缓存/片上互连区域。操作系统会影响可见的内存布局，却不会在每次普通 load/store 时替 CPU 决定“这一行该放 Cache 的哪一路”。

## 三、组满了怎么办：置换、写回和其他状态管理

当一次未命中要填入新行、目标组却没有空路时，控制器必须选一行离开。这就是**缓存置换**。常见候选包括：

- 最近最少使用（LRU）：优先替换最久未访问的行；
- 伪 LRU：用少量状态位近似 LRU，硬件成本低得多；
- 随机或轮转：实现简单，在某些层级表现并不差；
- RRIP 等预测策略：根据重用可能性给行设置较粗粒度的优先级。

真实芯片往往使用“近似策略”，而不是严格 LRU。严格记录高相联大缓存中所有行的精确访问次序很贵，收益又未必配得上这份执着。

被选中的旧行若 `dirty=0`，说明它与下层副本一致，可以直接失效并复用位置；若 `dirty=1`，说明 CPU 曾修改它而数据尚未写到下一层，控制器必须先**写回**（write back）旧行，再填入新行。

这里还要区分两组容易混在一起的策略：

| 问题 | 常见选项 | 含义 |
| --- | --- | --- |
| 写命中后何时向下层写 | write-through / write-back | 立即同步写下层，或只标脏、日后写回 |
| 写未命中时是否先取整行 | write-allocate / no-write-allocate | 先把行取入后再写，或直接把这次写转发到下层 |

典型 CPU 数据缓存常使用 write-back + write-allocate：反复修改同一行不必每次都打扰下层。不过这只是常见组合，不是定义；设备内存、特定层级和不同处理器可能采用不同选择。

## 四、Cache 与虚拟内存：相邻协作，不是同一个功能

程序中的 load/store 指令通常先产生**虚拟地址**。MMU 通过 TLB 或页表把它翻译为物理地址；随后访问 Cache 与主存。关于页表、TLB 和缺页，可先阅读[CPU 如何通过页表访问内存：虚拟地址、物理页与缺页](../os-memory-file-io-course/02-virtual-memory-and-page-tables.md)。

两套机制缓存的东西完全不同：

| 机制 | 缓存的对象 | 未命中的后果 |
| --- | --- | --- |
| TLB | 虚拟页号到物理页框号的翻译结果 | 硬件页表遍历，或因不存在/无权限而触发异常 |
| 数据/指令 Cache | 指令字节和普通数据的副本 | 向下一层 Cache 或 DRAM 请求缓存行 |

TLB 因而常被口语称作“地址翻译缓存”，但它不是用来保存用户数据的普通 Cache。**TLB miss 不等于 Cache miss；缺页也不等于缓存行未命中**。前者可能需要查页表，后者主要是存储层次的取数问题。

### 1. 为什么两者必须配合

Cache 的 tag 最终必须能唯一对应真实内存块，而权限检查也不能被绕过。所以很多设计使用物理地址标记，称为 PIPT（physical index, physical tag）。但若每次都先等完整地址翻译，L1 延迟会变长。

常见折中是 VIPT：**虚拟地址索引、物理地址标记**。页内偏移在翻译前后不变，L1 可以利用这部分位并行启动“选组”和 TLB 查询，等物理 tag 回来后再确认命中。页大小、行大小和组数必须满足相应约束，否则会产生同一物理页因不同虚拟别名落入不同行的 alias/synonym 问题。

这说明虚拟内存电路与 Cache “有交涉”：它们在一次访问的关键路径上协作，并共同处理地址别名、权限、上下文切换后的失效或标记问题；但页表、页面置换和 Cache 行置换仍是不同层次的职责。不要因为两者都叫“缓存/置换”就把它们当作一台机器。

## 五、多级 Cache 不靠一个控制器逐层发问

现代核心通常有私有的 L1 指令缓存（L1I）和 L1 数据缓存（L1D），其下有私有或小范围共享的 L2，再往下是多个核心共享的 LLC/L3，最后才是内存控制器和 DRAM。一个简化图如下：

```text
取指单元 -> L1I --miss--> L2 --miss--> 共享 L3/LLC --miss--> 内存控制器 -> DRAM
执行单元 -> L1D --miss--^       ^
                               片上互连与一致性逻辑
```

这不表示每次访问都由“中央控制器”轮询 L1、L2、L3。实际是**每一层都有本地命中判断和请求接口**：上层 miss 时向下一层发出事务；下一层命中就返回数据，未命中再继续向下。为了让等待中的多个 miss 不互相堵塞，现代 Cache 还会用 MSHR 一类表项记录“哪一行正在请求、哪些 load 正在等它”，因此可以同时在路上保留多个未完成请求。

缓存层之间还有两种组织关系：

- **包含式**（inclusive）：上层有的行保证下层也有副本；下层驱逐时必须让上层副本失效。
- **排他式**（exclusive）：尽量让一行只存在于某一级，以增加总有效容量。
- **非包含非排他**：不强制上述任一关系，现代设计很常见。

不能仅凭“有 L1、L2、L3”就断言它们如何包含；这是具体微架构的选择。

## 六、一次读和一次写，大致如何穿过层级

### 1. 读：从最靠近核心的一层开始

一次普通读取可以概括为：

1. CPU 产生虚拟地址，TLB 查询与 L1D 访问可能并行启动。
2. L1D 命中，直接把数据交给流水线；这是最快路径。
3. L1D 未命中，向 L2 请求整条缓存行；L2 命中则把行返回并通常填入 L1。
4. L2 未命中则继续访问 LLC；LLC 也未命中才经内存控制器访问 DRAM。
5. 数据沿返回路径填入若干层 Cache。到底填哪些层、是否预取相邻行，取决于策略。

“读到 DRAM”并不必然意味着 CPU 完全停住。乱序 CPU 会尝试先执行与该数据无关的其他指令；但若后续指令真正依赖这个值，延迟终究无法被魔法抹掉。

### 2. 写：既要更新数据，也要维护其他核心的副本

若本核心在 L1D 已拥有可写的该行，store 往往只更新本地行并置脏。若该行不存在或处于只读共享状态，控制器除了向下层取行，还要向一致性系统申请独占/修改权限。

以 MESI 一类协议为例，多个核心可以同时保留一行的“共享只读”副本；某核心想写入时，需要让其他核心的副本失效或撤销共享权限，然后自己获得可修改状态。共享 LLC、目录（directory）或 snoop 过滤器会帮助定位/广播这些请求，具体实现各不相同。

所以多核下还有一层不能忽略的分工：

```text
本级 Cache controller：查 tag、选路、填充、置换、脏位
一致性协议/互连：协调其他核心是否也有该行，以及谁能写
MMU/TLB：把当前地址空间的虚拟地址翻译并做权限检查
操作系统：建立页表、分配物理页、响应缺页和管理进程
```

Cache coherence（缓存一致性）只保证“同一地址上的缓存副本如何保持可观察的一致”；它不自动解决线程之间“先写后读必须何时可见”的所有编程语义。多线程程序还必须使用语言提供的原子操作、锁和内存序。硬件替你维护副本，不能替你补上同步设计。

## 七、把几个名字相近的概念分开

| 名称 | 管理粒度 | 主要目标 | 常见管理者 |
| --- | --- | --- | --- |
| Cache 置换 | 缓存行，几十字节量级 | 降低 DRAM 访问延迟 | Cache controller |
| TLB 置换 | 页表翻译项 | 加速虚拟到物理地址翻译 | MMU/TLB 硬件 |
| 页面置换 | 物理页，通常 KiB 量级 | 在 RAM 不足时腾出页框 | OS 内核为主，硬件提供访问/脏位 |
| 多核一致性 | 同一缓存行的多个副本 | 保证读写副本协议一致 | 一致性状态机、互连、目录/侦听逻辑 |

最值得记住的是这条路径：**地址先要被正确翻译，数据再要尽量在近处命中，多个核心还要对同一行的读写达成协议**。它们会在一次 load/store 中相遇，却各自解决不同问题。

## 总结

- 缓存行的映射、tag 比较、填充、置换和脏行写回由各级 Cache 控制器硬件处理。
- 直接映射、组相联和全相联区别在于一个内存块可放的位置范围；现代 Cache 通常采用组相联。
- Cache 置换、TLB 置换、页面置换和多核一致性是四件相关却不同的事。
- 多级 Cache 按 miss 请求逐级协作，每层独立判定命中；共享层和片上互连还负责一致性事务。
- 虚拟内存并不“管理 Cache 数据”，但 MMU/TLB 与 L1 访问必须协作，尤其要处理物理标记、地址别名和权限。
