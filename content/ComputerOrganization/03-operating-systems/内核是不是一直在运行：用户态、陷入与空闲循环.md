学习操作系统时，很容易形成一种印象：内核负责进程、内存、设备和文件系统，那么 CPU 是否每时每刻都在执行内核？

答案是否定的。

> **内核始终存在、始终掌握资源管理权，但内核代码并不始终占用 CPU 执行。**

在正常情况下，CPU 会在用户态执行应用程序的指令；只有系统调用、中断、异常或调度等事件发生时，CPU 才进入内核态执行内核代码。若系统没有可运行的任务，内核通常会让 CPU 进入等待中断的空闲状态，而不是无意义地忙等。

这一区分看似只是措辞差异，实际上关系到理解用户态、内核态、陷入（trap）、中断与进程调度的整个执行模型。

------

## 一、先区分三个不同的问题

“内核一直在运行”这句话容易混淆以下三个层面：

| 问题 | 答案 | 含义 |
| --- | --- | --- |
| 内核是否一直存在并管理系统资源？ | 是 | 内核维护进程、页表、文件、设备状态等系统级数据。 |
| CPU 是否一直在执行某段指令？ | 通常是 | CPU 要么执行用户代码或内核代码，要么处于暂停/低功耗等待状态。 |
| CPU 是否一直在执行**内核代码**？ | 否 | 用户程序运行时，CPU 执行的是用户程序自己的指令。 |

因此，较严谨的说法是：

> **内核不是一个持续在后台抢占 CPU 的普通程序。它是在需要操作系统介入时获得执行权的一组高权限代码与数据结构。**

所谓“后台”只是一种方便的比喻。内核并不是像聊天软件或音乐播放器那样，以某个普通进程的身份一直循环运行。

------

## 二、用户程序运行时，CPU 在做什么

假设浏览器、shell 或一个简单的 C 程序正在计算：

```c
long sum = 0;
for (long i = 0; i < 100000000; i++) {
    sum += i;
}
```

这一循环的大部分时间里，CPU 处于**用户态**，取指、译码、执行的都是这个程序编译出的机器指令。内核当然仍映射在相应的地址空间中（具体映射方式因系统而异），也仍保存着该进程的调度和内存管理信息；但 CPU 此刻没有在执行内核的 `read`、调度器或驱动程序代码。

可以把两者的关系理解为：

```text
CPU 正在执行什么？
│
├─ 用户态：执行应用程序代码
│          例如循环计算、字符串处理、普通函数调用
│
└─ 内核态：执行内核代码
           例如处理系统调用、中断、异常、进程切换
```

用户态不是“没有操作系统”的状态，而是“当前 CPU 正在执行权限受限的用户代码”的状态。内核仍然通过 CPU 的特权级、页表权限、设备访问权限等机制维持边界。

------

## 三、哪些事情会让 CPU 进入内核

CPU 从用户态切换到内核态，通常不是内核随意插话，而是由明确的硬件事件或软件请求触发。常见入口有三类。

### 1. 系统调用：用户程序主动请求服务

用户程序不能直接操作磁盘、网卡、进程表或页表。如果它想读文件、创建进程或申请某些资源，就要通过系统调用请求内核处理：

```c
read(fd, buffer, n);
write(fd, buffer, n);
fork();
```

以 RISC-V 为例，用户态程序执行 `ecall` 后，硬件会切换到相应的陷入处理入口，内核检查系统调用号和参数，完成处理后再通过 `sret` 返回用户态。

一次不阻塞的系统调用可以简化为：

```text
用户态应用代码
    ↓  ecall
内核态：系统调用处理程序
    ↓  sret
用户态应用代码继续执行
```

此时内核确实短暂运行了，但处理结束后 CPU 又回到用户程序。

### 2. 中断：硬件要求内核处理事件

中断来自 CPU 外部或与 CPU 异步到来的事件。例如：

- 时钟设备周期性产生定时器中断；
- 键盘、鼠标等输入设备报告新数据；
- 磁盘或网卡报告 I/O 完成；
- 多核系统中的其他 CPU 发来核间中断。

中断到来时，即使用户程序正在执行一条普通计算指令，CPU 也会在合适的指令边界保存必要现场并转入内核的中断处理程序。时钟中断尤其重要：内核可借此更新时钟、唤醒等待任务，并在需要时进行抢占调度。

### 3. 异常：当前指令无法按正常方式完成

异常是执行当前指令时发现的问题或特殊情况，例如：

- 访问的虚拟页尚未建立映射，产生缺页异常；
- 除零或执行非法指令；
- 用户程序访问无权限的地址；
- 断点、单步调试等调试事件。

异常与中断的一个关键区别是：异常通常与当前正在执行的指令直接相关；中断通常是外部异步事件。但两者都会让 CPU 进入内核，由内核的陷入处理路径接管。

------

## 四、进入内核，不等于一定切换进程

这也是初学者最容易混在一起的两件事。

**用户态/内核态切换**描述的是 CPU 的权限级别和执行代码发生变化；**进程或线程切换**描述的是 CPU 从一个执行上下文换到另一个执行上下文。它们相关，却不是同一件事。

例如，执行一次很快完成的 `getpid()` 或读取已缓存的数据，可能经历：

```text
进程 A 的用户态
    ↓
进程 A 的内核态
    ↓
进程 A 的用户态
```

这里发生了两次特权级转换，却没有换到进程 B。

相反，一个阻塞的 `read()` 可能经历：

```text
进程 A 的用户态
    ↓  read() 等待磁盘数据
进程 A 的内核态
    ↓  A 阻塞，调度器选择其他任务
进程 B 的用户态
```

此时才发生了真正的任务切换。日后磁盘完成 I/O 并产生中断，内核再将 A 标记为可运行；A 什么时候重新获得 CPU，则取决于调度器。

可以用下面的表格概括：

| 情况 | 是否进入内核态 | 是否一定切换任务 |
| --- | --- | --- |
| 普通用户态计算 | 否 | 否 |
| 很快完成的系统调用 | 是 | 否 |
| 时钟中断 | 是 | 不一定 |
| 阻塞 I/O | 是 | 通常会 |
| 进程退出或主动让出 CPU | 是 | 会 |

## 五、xv6 中的实际执行路径

xv6 的结构非常适合用来观察这一点。概念上，CPU 的执行路径不断在下面几段代码之间往返：

```text
调度器 scheduler()（内核态）
    ↓  找到 RUNNABLE 进程
进程的用户代码（用户态）
    ↓  系统调用 / 中断 / 异常
usertrap() 等陷入处理代码（内核态）
    ↓  可能继续运行原进程，也可能调用 sched()
调度器或某个进程的用户代码
```

当 `scheduler()` 选中一个可运行进程后，它会恢复该进程的内核上下文；随后，该进程会从先前保存的位置继续执行。若它正要从陷入返回，就经由 `usertrapret()` 等路径返回用户态，CPU 再次开始执行该进程的用户指令。

用户程序执行 `ecall`、收到设备中断，或出现异常后，控制流会进入内核的陷入处理逻辑。内核会判断陷入原因：

- 系统调用：分发到对应的系统调用实现；
- 设备中断：执行设备相关处理，例如确认时钟中断；
- 异常：根据原因处理或终止出错进程。

时钟中断可能使内核调用 `yield()`，让当前进程从 `RUNNING` 变为 `RUNNABLE`，然后进入 `sched()`。调度器之后可能再选中它，也可能选中另一个进程。

所以，xv6 中“内核在运行”并不意味着一直停留在 `scheduler()`。调度器只在需要寻找下一个可运行进程时运行；大部分普通应用计算时间仍在用户态度过。

## 六、没有用户程序可运行时，内核在做什么

若所有用户进程都在等待磁盘、网络或定时器事件，调度器找不到任何 `RUNNABLE` 进程。此时，合理的做法不是让 CPU 在一个空循环中反复扫描进程表，因为那会白白消耗一个 CPU 核心。

在 RISC-V 上，内核可以执行 `wfi`（wait for interrupt）指令，使当前 CPU 等待下一次中断。CPU 在等待期间不会持续执行普通指令；当定时器、设备或其他中断到来时，它再被唤醒并进入中断处理流程。

```text
没有 RUNNABLE 进程
    ↓
内核执行 wfi，CPU 等待中断
    ↓
设备或定时器中断到来
    ↓
内核处理中断、唤醒可能的任务
    ↓
调度器再次寻找 RUNNABLE 进程
```

这里也应避免另一个极端说法：不能因为 CPU 在等待，就认为内核“不运行了”或系统“失去控制了”。更准确地说，内核已经安排 CPU 进入可被中断唤醒的空闲状态；系统的硬件时钟与设备仍然能够触发后续事件。

实际操作系统常常还会选择更深的节能状态。原理依旧相同：空闲并不等于忙着执行调度代码，恰恰是尽量停止无意义的执行。

## 七、一个连续例子：从用户计算到调度

设想进程 A 正在执行用户态循环，随后发生一次定时器中断：

```text
1. A 在用户态执行自己的指令。
2. 定时器中断到来，CPU 保存必要的现场并进入内核态。
3. 内核处理中断，发现 A 的时间片已经用完。
4. 内核将 A 标记为 RUNNABLE，并调用调度器。
5. 调度器选择进程 B。
6. CPU 恢复 B 的执行上下文；若 B 先前在用户态运行，最终返回 B 的用户态。
7. B 开始执行自己的用户代码。
```

这里，内核只在第 2 至第 6 步执行。A 和 B 的实际业务计算分别发生在用户态。正因为有中断和调度器，单核 CPU 才能在多个进程之间快速切换，制造出“大家好像同时运行”的效果。

------

## 八、结论

关于“内核其实不是无时无刻在运行着的？”这个问题，可以给出以下完整回答：

> **是的，如果“运行”指 CPU 正在执行内核指令，那么内核并非无时无刻都在运行。CPU 大部分时候可能在用户态执行应用代码；只有系统调用、中断、异常和调度等事件发生时，才进入内核态执行内核代码。没有可运行任务时，内核通常让 CPU 等待中断，而不是持续空转。**

但内核仍然始终是系统资源的管理者：它定义权限边界，保存系统状态，决定谁可以运行，并在事件到来时接管处理。把“内核始终管理系统”误解成“CPU 始终执行内核代码”，只是把两种不同层次的“运行”混为一谈而已。
