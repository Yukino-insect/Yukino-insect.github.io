“页分配器需要页描述符，页描述符自己也要占内存；那第一个页描述符放在哪里？”这个问题听起来像一个无限后退的悖论，其实没有那么神秘。它是操作系统中反复出现的 **自举（bootstrap）** 问题：一个成熟机制依赖某些前提，而这些前提必须先由能力较弱、范围更小的早期机制建立。

核心结论是：**内核不会从“什么都没有”开始。固件、启动加载器、内核镜像和一小段已知可用的 RAM 组成种子；早期代码只解决有限问题，随后逐步建立页表、分配器、中断、调度、驱动和根文件系统。每一步都只依赖已经成立的前一步。**

## 一、什么是自举：不是凭空造自己

日常语言里的“自举”常被说得像系统凭空创造自身。计算机中的含义更朴素：用一个**更简单、功能受限但已经能运行的阶段**，构建功能更完整的下一阶段。

编译器是熟悉的类比。第一版编译器可能由汇编或另一门语言写成；有了它，才可以用目标语言编译后续版本的编译器。操作系统也一样：先借助固件和加载器提供的最小执行环境，再构建自己的运行环境。

下面两种说法要严格区分：

| 说法 | 是否正确 | 原因 |
| ---- | -------- | ---- |
| “成熟页分配器一开始就能管理全部 RAM” | 否 | 它的页元数据、空闲链表、锁等结构尚未建立。 |
| “内核最初没有任何可用内存” | 否 | 加载器已把内核和启动数据放入特定 RAM，固件还提供可用内存图。 |
| “先用受限的早期分配，再启用正式分配器” | 是 | 早期分配器只在已知安全区间内单向取用，不依赖完整空闲页账本。 |

## 二、启动时真正已经有什么

CPU 复位后通常从平台规定的入口开始执行固件。以常见 PC 为例，UEFI 或 BIOS 初始化足以找到并执行启动程序；启动加载器再将内核镜像、可选的 initramfs 和启动参数放入 RAM，并跳到内核入口。不同架构细节不同，但内核进入最早代码时一般至少知道：

- 自己的代码和已初始化数据被装载在什么物理地址范围；
- 启动参数和固件提供的内存地图位于哪里；
- 哪些 RAM 区域可用，哪些被固件、设备、内核镜像或启动数据占用；
- 一个暂时可用的栈，或建立它所需的最小条件；
- 少量早期页表或足以先建立页表的能力。

这份信息不必完美，也不必覆盖所有设备；只要足够让内核安全地迈出下一步即可。启动不是一次跳跃，而是逐步缩小“未知与不可用”的范围。

```mermaid
flowchart LR
    Firmware[固件提供内存图和启动入口] --> Loader[加载器放置内核与启动数据]
    Loader --> Early[早期汇编/C：栈、最小映射]
    Early --> Bootmem[早期分配器和关键元数据]
    Bootmem --> Paging[完整页表与物理页分配器]
    Paging --> Core[中断、时钟、调度与对象分配]
    Core --> Devices[总线枚举、驱动、块设备]
    Devices --> Root[挂载根文件系统并启动用户空间]
```

## 三、内存管理如何完成第一轮自举

页分配器最能说明这个过程，因为它的循环依赖最显眼。

### 1. 先有内存地图，再谈“空闲页”

固件给出的内存地图描述物理地址范围的属性，例如可用 RAM、固件保留区、设备 MMIO 窗口。内核还要叠加自己知道的保留范围：内核镜像、启动参数、初始页表、initramfs，以及已经被早期代码取走的区域。

只有“固件说可用”且“当前内核未保留”的区间，才可能进入正式页分配器。物理地址空间并不等于 RAM；把 MMIO 区域当空闲内存分配，当然不是一种勇敢的优化。

### 2. 早期分配器只做单向取用

成熟的伙伴分配器需要知道每个页框的状态，而状态本身保存在页描述符数组中。为打破这个依赖，早期代码常使用类似 **bump allocator（线性/指针碰撞分配器）** 的机制：从已确认安全的一段 RAM 中向前移动指针，需要多少给多少，通常不支持单独释放。

下面是概念性代码，刻意省略架构细节：

```c
struct early_region {
    uintptr_t cursor;
    uintptr_t limit;
};

void *early_alloc(struct early_region *r, size_t bytes, size_t align) {
    uintptr_t start = align_up(r->cursor, align);
    uintptr_t end = start + bytes;

    if (end > r->limit) {
        return NULL;              // 早期阶段宁可明确失败
    }

    r->cursor = end;
    return (void *)start;
}
```

它的限制恰好也是它能早期使用的原因：不需要空闲链表、不需要复杂锁、不需要回收算法，只需一段已知安全的连续 RAM。内核用它安放页描述符数组、早期页表、启动阶段的内部表和少量初始化对象。

### 3. 用早期内存放“管理其他内存的档案”

假设可管理 RAM 中有 `nr_pages` 个 4 KiB 页框，内核需要一份 `page_desc[nr_pages]`，记录每个页框是否保留、空闲、正在 I/O、属于页缓存或页表等。这个数组的地址来自 `early_alloc`：

```c
struct page_desc *pages = early_alloc(&boot_region,
    nr_pages * sizeof(*pages),
    _Alignof(struct page_desc));

for (size_t pfn = 0; pfn < nr_pages; ++pfn) {
    pages[pfn].state = PAGE_RESERVED;
}

mark_usable_ranges_free(pages, firmware_memory_map);
mark_kernel_and_boot_ranges_reserved(pages, kernel_image, boot_region);
buddy_init_from_page_descriptors(pages, nr_pages);
```

这个顺序很重要：先暂时保守地把页都视为保留，再只释放经过验证的可用区间。此后，正式的伙伴分配器就能从页描述符和空闲块集合中工作。早期分配器取走的区域继续标记为保留；它们不会因为“现在有正式分配器了”就神奇地变成空闲。

### 4. 切换不等于把早期机制抹掉

有些早期对象会长期存在，例如内核的页描述符数组、固定的启动参数副本和初始页表；有些早期临时结构会在安全时回收。何时可回收取决于“最后一个使用者是否已经转移”，不是取决于它名字里是否带有 early。

真实内核通常还会处理非连续 RAM、NUMA 节点、不同 DMA 能力区和内核虚拟地址映射。它们使实现复杂，却不改变上述基本因果关系。

## 四、除了页分配器，还有哪些自举细节

内核几乎每个子系统都有自己的“先简后全”。以下不是按严格时间顺序的一张万能清单，而是一组常见依赖。

### 1. 执行环境：入口、栈、BSS 与 C 运行时

内核最先执行的往往是汇编入口代码，因为普通 C 函数默认已经拥有可用栈、正确的寄存器约定和已初始化的全局变量。早期汇编通常负责：

- 建立最小栈指针；
- 清零 BSS 区域，使未初始化全局变量从确定的零值开始；
- 设置架构要求的控制寄存器或特权状态；
- 准备参数后调用较高层的 C 初始化函数。

例如，下面展示的是思想而非可直接运行的启动汇编：

```asm
early_entry:
    la   sp, boot_stack_top     # 先有一个静态或加载器提供的栈
    call clear_bss              # 全局未初始化数据归零
    call build_early_page_table
    call kernel_main            # 此后才适合进入普通内核 C 代码
```

这里的 `boot_stack` 本身位于内核镜像的已知数据区，不是通过 `malloc` 得到的。若先调用依赖栈的函数来“申请栈”，才是真的把顺序写反了。

### 2. 地址空间：先有最小映射，再有完整页表

启用虚拟内存或切换到内核自己的页表时，CPU 仍必须能继续取下一条指令、访问当前栈和启动数据。因此早期页表至少映射：当前执行代码、栈、必要数据，以及切换后的内核虚拟地址。

常见做法是暂时保留一段身份映射（虚拟地址等于物理地址）或同时保留旧映射与新高地址映射。完成页表寄存器切换后，代码再跳到新虚拟地址继续执行。若新页表没有映射“下一条要执行的指令”，切换并不会优雅地失败，只会立即异常。

### 3. 中断：先有描述表，再允许外部打断

启动初期的中断处理器、描述符表和每 CPU 状态尚未完整建立。内核通常先设置最小异常处理路径和中断控制器，再逐步开启外部中断。过早接收设备中断，处理程序可能找不到栈、锁、驱动状态或完成队列；过晚开启则会错过或堆积需要处理的事件。

所以顺序是：**先让异常能被安全接住，再允许更多异步事件发生。** 中断不是“总该越早越好”的开关。

### 4. 锁与并发：先串行建立共享状态，再并行运行

多核机器中，其他 CPU 核也要被启动（SMP bring-up）。在页分配器、调度器、每 CPU 数据和中断路由尚未就绪时，让所有核自由进入普通内核路径只会制造竞争条件。因此引导核通常先建立全局结构，其他核在受控入口等待，之后再分别初始化自己的栈、局部数据和中断状态。

早期阶段也会尽量避免调用依赖调度、可睡眠锁或复杂回收的代码。不是锁没有价值，而是使用一把锁也需要先有确定的锁对象、执行上下文和恢复路径。

### 5. 调度：先有初始执行上下文，再能切换任务

调度器要保存和恢复任务寄存器、内核栈、地址空间和运行队列。最初正在执行的内核路径往往会被包装为“boot/idle 任务”，先建立一个合法的初始任务对象和每 CPU 的空闲任务，之后才可以安全创建内核线程、切换到其他任务或允许普通线程睡眠。

换句话说，初始化函数在调度器完全就绪前不能随意阻塞；否则它要求系统切走自己，而系统甚至还没有一个可切换到的正常任务。

### 6. 对象分配器：先用页，再在页上分配小对象

页分配器擅长交付整页或连续页，但 inode、进程控制块、文件对象和网络缓冲头部往往远小于一页。slab/slub 等对象分配器会先从页分配器获得若干页，再在页内切分为固定或相近大小的对象。

因此小对象分配器不能早于页分配器完全建立；早期代码通常只用静态对象或线性分配。这个依赖与“先有砖，再搭货架存放小盒子”没有本质区别。

### 7. 设备发现与根文件系统：先能读块，再能按路径读文件

内核不能一开始就假设 `/sbin/init` 可被按路径打开。它需要先枚举总线，初始化存储控制器和块设备驱动，识别分区，读取超级块等文件系统元数据，挂载根文件系统。许多系统会用 initramfs 作为早期根：它已随内核加载进内存，所需驱动和初始化工具也可先从这里取得；等真正根设备可用后再切换根目录。

这不是“文件系统先于驱动”，而是先由加载器或内存中的早期文件系统提供最小内容，再建立访问持久化文件系统的能力。

## 五、用依赖图检查启动顺序

自举问题最可靠的思考方式不是背某个内核的函数名，而是问：“这个组件运行前，需要什么已经成立？”例如：

```text
普通 C 初始化
  <- 可用栈、已清零 BSS、最小地址映射

正式页分配器
  <- 内存图、页描述符存放位置、保留区信息

对象分配器
  <- 正式页分配器

可睡眠的驱动初始化
  <- 调度器、定时器、中断与必要锁

挂载持久化根文件系统
  <- 存储驱动、块设备、文件系统实现

启动用户空间
  <- 根文件系统、进程创建、执行装载和基本设备
```

这张图并不声称所有初始化只有一条线性顺序；实际系统会并行初始化一部分子系统，也会为不同平台准备替代路径。它只是揭示一个原则：**依赖必须从已存在的种子向外展开，不能让一个尚未建立的机制充当自己的前提。**

## 六、常见误解

### 1. “早期分配器就是内存泄漏”

不对。它通常故意不支持单独释放，因为启动期对象数量有限且生命周期清楚。部分早期内存会在后续阶段保留为核心结构，部分会在确认无引用后回收。是否泄漏取决于所有权和可回收时机，而不是分配器是否叫 bump。

### 2. “固件已经管理内存，所以内核不用再管理”

固件提供的是启动时的资源地图和服务入口；运行中的进程隔离、页框分配、缓存回收、NUMA 策略和 DMA 保护仍由内核接管。固件给的是地形图，内核随后建立的是持续变化的城市管理账本。

### 3. “自举只发生在开机那一瞬间”

严格说，最明显的自举发生在启动期；但同一模式也会出现在新 CPU 核上线、设备热插拔、容器或虚拟机初始化等过程中：先建立一个最小上下文，再加入完整的共享机制。它是依赖管理方法，不是一段只存在于教科书第一页的仪式。

## 七、总结

- 自举是“用已存在的最小能力建立更完整能力”，不是系统从无到有地制造自己。
- 内核启动时已有固件内存图、加载器放置的镜像与启动数据，以及用于最早执行的一小段安全环境。
- 内存管理通过早期线性分配器安放页描述符、早期页表等关键元数据，再以它们初始化正式页分配器。
- 栈与 C 运行时、页表、中断、多核、调度、对象分配器、设备驱动和根文件系统都有类似的先后依赖。
- 判断启动顺序时，沿着“此机制运行前需要什么”反向追问，通常比记函数名更可靠。

页描述符为什么能占用内存，答案并不绕：它先占用加载器和内存地图明确允许的一小块 RAM；有了这份页框档案，内核才把剩余合格页框纳入正式管理。先搭一张足以记账的小桌子，再管理整间仓库，这就是自举。
