用户态和内核态，本质上是 CPU 为了保护操作系统和硬件资源而提供的两种执行权限级别。

应用程序平时运行在**用户态**。它可以执行普通计算、访问自己的内存、调用普通函数，但不能直接操作硬件、修改页表、控制中断或随意调度进程。操作系统内核运行在**内核态**，拥有更高权限，可以执行特权指令并管理整个系统资源。

所谓“用户态和内核态切换有性能开销”，并不是因为“切换”这两个字有什么神秘之处，而是因为切换时通常伴随着保存和恢复现场、切换执行环境、参数校验、数据拷贝，以及对 CPU cache、TLB、流水线和分支预测的影响。

## 一、什么是用户态和内核态

现代操作系统不会让普通应用程序直接控制所有硬件资源。否则一个普通进程就可能随意读写磁盘、修改其他进程内存，甚至破坏内核自身的数据结构。

因此 CPU 和操作系统会把执行权限分成不同级别。简化理解如下：

- **用户态**：权限较低，普通应用程序运行在这里。
- **内核态**：权限较高，操作系统内核运行在这里。

用户态程序不能直接做这些事情：

- 访问硬件设备
- 修改页表
- 执行特权指令
- 管理中断
- 调度进程或线程
- 直接访问内核内存

如果应用程序想读取文件、发送网络数据、申请大块内存、创建线程，就必须通过操作系统提供的接口进入内核，让内核代为完成。

常见的进入内核的方式有三类：

- **系统调用（system call）**：应用主动请求内核服务，例如 `read`、`write`、`open`、`epoll_wait`。
- **异常（exception）**：CPU 执行过程中发现异常情况，例如缺页异常、除零错误、非法指令。
- **中断（interrupt）**：外部设备或定时器通知 CPU，例如网卡收到数据、磁盘 I/O 完成、时钟中断触发调度。

其中，应用程序最常接触的是**系统调用**。

## 二、为什么需要用户态和内核态

如果没有用户态和内核态的隔离，所有程序都能用最高权限运行，系统会非常脆弱。

### 1. 保护内核

内核维护着进程、内存、文件系统、网络协议栈等关键数据结构。如果普通应用可以直接修改这些数据结构，一个 bug 就可能让整个系统崩溃。

用户态把应用程序限制在较低权限下，应用即使崩溃，通常也只会影响自己所在的进程。

### 2. 保护进程之间的隔离

不同进程拥有各自的虚拟地址空间。用户态程序不能随意访问别的进程内存，也不能直接访问内核地址空间。

这正是操作系统稳定性和安全性的基础。

### 3. 统一管理硬件资源

硬件资源是全局共享的，例如磁盘、网卡、内存、CPU。如果每个应用都能直接操作硬件，就很难保证并发访问的正确性。

由内核统一管理硬件，可以避免资源冲突，并提供统一的抽象，例如文件描述符、socket、进程、线程和虚拟内存。

## 三、用户态如何进入内核态

以一次文件读取为例：

```c
read(fd, buf, len);
```

这行代码看起来只是普通函数调用，但它背后会进入内核。

大致过程如下：

1. 用户态程序调用 `read`。
2. C 标准库或运行时封装系统调用参数。
3. CPU 执行特殊指令进入内核态。
4. 内核根据系统调用号找到对应处理函数。
5. 内核检查参数、文件描述符和用户态缓冲区是否合法。
6. 内核读取数据，并把数据拷贝到用户态缓冲区。
7. 内核返回用户态，应用程序继续执行。

这个过程通常被称为**陷入内核（trap into kernel）**。

需要注意：从用户态进入内核态后，CPU 执行的就不再是普通应用代码，而是内核代码。权限、栈、执行路径、内存访问规则都会发生变化。

## 四、用户态到内核态切换为什么有开销

单纯把 CPU 权限级别从用户态改成内核态，并不是最贵的部分。真正的成本来自伴随这次切换发生的一系列动作。

### 1. 保存用户态现场

进入内核前，CPU 和内核需要保存当前用户态执行现场，例如：

- 程序计数器（PC / RIP）
- 栈指针（SP / RSP）
- 标志寄存器
- 部分通用寄存器

因为系统调用处理完之后，程序还要能回到原来的位置继续执行。如果现场没有保存好，用户程序就无法正确恢复。

### 2. 切换到内核栈

一个线程通常既有用户栈，也有内核栈。

用户态运行普通应用代码时使用用户栈；进入内核后，内核会使用该线程对应的内核栈来执行系统调用处理逻辑。

这不是最重的操作，但它确实意味着执行环境发生了变化。

### 3. 执行系统调用分发

系统调用进入内核后，并不是直接执行目标逻辑。内核还需要根据系统调用号找到对应处理函数。

例如 `read`、`write`、`open`、`futex`、`epoll_wait` 都会走到不同的内核处理路径。

这个分发过程本身需要执行内核代码，也会带来额外开销。

### 4. 参数校验和权限检查

用户态传给内核的参数不能被盲目信任。

比如 `read(fd, buf, len)` 中：

- `fd` 是否是合法文件描述符？
- 当前进程是否有读取权限？
- `buf` 是否指向用户态合法地址？
- `len` 是否合理？
- 目标页是否存在？

内核必须认真检查这些条件。否则应用传一个非法地址，就可能让内核访问错误内存。

### 5. 用户态和内核态之间可能发生数据拷贝

很多系统调用需要在用户态和内核态之间传递数据。

例如：

- `read`：从内核缓冲区拷贝到用户态缓冲区。
- `write`：从用户态缓冲区拷贝到内核缓冲区。
- `recv`：从 socket 接收缓冲区拷贝到用户态。
- `send`：从用户态拷贝到 socket 发送缓冲区。

所以系统调用的成本往往不只是“进去再出来”，还包括参数检查和数据搬运。

### 6. CPU 局部性会被破坏

现代 CPU 为了提高性能，会依赖很多缓存和预测机制：

- 指令流水线
- 分支预测
- L1/L2/L3 cache
- TLB
- 指令 cache

用户态代码正在运行时，CPU cache 中可能已经缓存了应用程序的热点代码和热点数据。

一旦进入内核，执行流跳到内核代码路径，CPU 可能需要加载新的指令和数据。原本属于用户程序的 cache 热点也可能被内核代码污染。

因此，切换成本不只体现在切换那一瞬间，还会体现在切换之后一段时间内的 cache 命中率下降。

### 7. 安全机制可能增加额外成本

现代 CPU 和操作系统为了防御一些漏洞，会在用户态和内核态之间增加额外隔离和屏障。

例如某些系统会启用更严格的页表隔离，减少用户态通过旁路攻击窥探内核数据的可能性。

这些安全机制是必要的，但也会让用户态和内核态切换的成本更高。

## 五、系统调用一定会导致线程切换吗

不一定。

系统调用只表示当前线程进入内核，请求内核执行某个操作。它是否会引发线程切换，取决于这次系统调用会不会阻塞，以及内核调度器是否决定切换执行对象。

### 1. 不阻塞的系统调用

如果系统调用很快完成，例如读取已经在内核缓冲区里的数据，或者获取当前时间，那么它可能只是：

```text
用户态 -> 内核态 -> 用户态
```

这种情况下，不一定发生线程切换。

### 2. 会阻塞的系统调用

如果系统调用需要等待资源，例如：

- 等磁盘 I/O
- 等网络数据
- 等锁
- 等事件
- 等子进程结束

内核可能会把当前线程挂起，然后调度另一个可运行线程。

这时发生的就不只是用户态和内核态切换，而是进一步引出了**线程上下文切换**。

## 六、线程切换为什么更贵

线程切换的核心成本来自三件事：

- 保存当前线程上下文
- 恢复下一个线程上下文
- 调度器参与决策

假设线程 A 被换下，线程 B 被换上，内核大致要做：

1. 保存线程 A 的寄存器、栈指针、程序计数器等状态。
2. 更新线程 A 的状态，例如运行、阻塞、就绪。
3. 调度器选择下一个要运行的线程 B。
4. 恢复线程 B 上次保存的执行现场。
5. 返回到线程 B 的执行位置继续运行。

线程切换还有一个很重要的间接成本：**CPU cache 局部性被破坏**。

线程 A 刚运行时，它的数据和代码可能已经被加载到 cache 中。切换到线程 B 后，B 使用另一批代码和数据，会把 A 的热点缓存挤掉一部分。等下次再切回 A，A 可能又要重新加载自己的工作集。

所以线程切换的成本，往往不只是保存几个寄存器，而是切换后的一段时间内，程序执行效率下降。

## 七、进程切换为什么通常比线程切换更贵

同一个进程内的多个线程共享同一套虚拟地址空间。线程之间切换时，通常不需要切换整套页表。

不同进程则不同。进程之间通常有不同的：

- 虚拟地址空间
- 页表
- 文件描述符表
- 内存映射关系
- 资源权限和统计信息

因此，从进程 A 切换到进程 B 时，除了线程执行现场要切换，还可能涉及**地址空间切换**。

地址空间切换会影响 TLB。

TLB 缓存的是虚拟地址到物理地址的翻译结果。当切换到另一个进程后，原进程的许多地址翻译结果不再适用，TLB 命中率可能下降。之后一段时间内，内存访问会变慢。

这也是为什么通常认为：

```text
同进程线程切换 < 不同进程切换
```

当然，这只是一般情况。实际成本还会受到 CPU 架构、操作系统实现、是否启用 PCID/ASID、线程是否跨核迁移、工作集大小等因素影响。

## 八、用户态线程和协程为什么更轻

前面说的线程切换，指的是操作系统线程切换。例如 Java 中普通的 `Thread`，通常会映射到 OS 线程。

只要 OS 线程发生调度切换，就一定需要进入内核，由内核调度器参与。

但用户态线程、green thread、协程这类机制，可能由语言运行时或框架在用户态自行调度。

它们的切换通常只需要做：

- 保存少量寄存器
- 切换栈或恢复协程帧
- 更新运行时调度状态
- 跳转到另一个用户态任务继续执行

它们通常不需要：

- 进入内核
- 调用内核调度器
- 切换页表
- 触发 OS 线程上下文切换

所以用户态协程切换通常比 OS 线程切换更轻。

但“更轻”不等于“没有成本”。协程切换仍然会有调度逻辑、状态保存和一定的 cache 局部性影响。只是与进入内核并触发 OS 线程调度相比，它的成本小得多。

## 九、I/O 密集型场景为什么怕频繁切换

I/O 密集型程序经常会经历这样的过程：

1. 用户态发起系统调用。
2. CPU 进入内核态。
3. 内核发现数据还没准备好。
4. 当前线程被阻塞。
5. 调度器切换到其他线程。
6. 数据到达后，中断或事件唤醒线程。
7. 线程再次被调度回来继续执行。

这里面会反复发生：

- 用户态和内核态切换
- 线程阻塞和唤醒
- 调度器决策
- 上下文保存和恢复
- cache/TLB 局部性破坏

所以高并发 I/O 优化，经常是在减少这些成本：

- 使用 `epoll` 这类 I/O 多路复用机制，减少线程数量。
- 使用异步 I/O 或事件驱动模型，减少阻塞等待。
- 使用协程，让大量任务在少量 OS 线程上调度。
- 合并小 I/O，减少高频系统调用。
- 减少锁竞争，避免大量线程阻塞和唤醒。
- 控制线程池大小，避免线程数失控。

## 十、几种切换成本的粗略排序

一般可以按下面的顺序理解：

1. **普通函数调用**
   主要是栈帧变化和跳转，成本最低。
2. **用户态协程切换**
   主要是保存少量状态、切换栈或协程帧，不需要进入内核。
3. **用户态和内核态切换**
   需要 trap、切内核栈、做系统调用分发和参数检查。
4. **同一进程内 OS 线程切换**
   需要内核调度器介入，还要保存和恢复线程上下文。
5. **不同进程切换**
   除了线程上下文切换，还可能涉及地址空间切换和更明显的 TLB 影响。

这不是绝对的性能公式，只是理解成本来源的常用顺序。真实开销会受系统调用类型、CPU 架构、内核版本、负载情况和数据局部性影响。

## 十一、放到 Java 里怎么理解

Java 程序里很多性能问题，本质上都和这些切换成本有关。

常见场景包括：

- `synchronized` 或 `Lock` 竞争激烈，导致线程阻塞、唤醒和上下文切换。
- 线程池线程数过多，导致调度频繁，CPU 时间花在切换而不是业务逻辑上。
- 频繁小 I/O，例如大量短连接、频繁小包读写，导致系统调用次数过多。
- 频繁创建线程，带来栈内存、调度和系统资源管理成本。
- 阻塞式 I/O 下连接数过多，导致大量线程等待和调度。

对应的优化方向通常是：

- 控制线程池大小，让线程数匹配 CPU 和业务类型。
- 减少锁竞争，缩小临界区。
- 合并小请求或小 I/O，降低系统调用频率。
- 使用 NIO、事件驱动、异步 I/O 或协程模型减少阻塞线程数量。
- 保持数据局部性，避免无意义的跨线程、跨核迁移。

## 十二、一句话总结

**用户态和内核态是 CPU 与操作系统提供的权限隔离机制。进入内核态本身不是最贵的，真正的开销来自现场保存与恢复、内核栈切换、系统调用分发、参数校验、数据拷贝，以及 CPU cache、TLB、流水线和分支预测等局部性被破坏。**
