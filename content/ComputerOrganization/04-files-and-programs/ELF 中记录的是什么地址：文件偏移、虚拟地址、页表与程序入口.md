写完一个 C/C++ 程序并编译后，我们会得到一个可执行文件。在 Linux 上，它通常是 **ELF 文件**。里面已经有 CPU 能执行的机器指令，也可能有全局变量的初始值、字符串常量等数据。

于是很容易出现一个疑问：既然程序最终要被放进内存执行，ELF 中是不是已经记录了代码段、数据段的内存地址？它记录的是虚拟地址，还是物理地址？CPU 又是从哪里开始执行的？

先给出结论，免得概念还没讲清就被名词牵着走：

> **普通 Linux 用户程序的 ELF 会记录“文件中的位置”和“应放进进程虚拟地址空间的布局”，但通常不会记录最终的物理内存地址。CPU 执行时先使用虚拟地址，硬件再把它翻译成物理地址。**

最关键的不是背字段名，而是始终分清三个问题：

```text
这个字节在文件里的哪里？
这个字节在进程看来位于哪里？
这个字节此刻实际放在 RAM 的哪里？
```

这三个“哪里”分别对应文件偏移、虚拟地址和物理地址。它们都叫地址，却不是同一件事；把它们强行当成一个概念，当然只会越看越乱。

本文讨论的是有操作系统和虚拟内存的普通 Linux 用户程序。裸机程序、bootloader、操作系统内核的装载规则可能不同，最后会单独说明。

## 一、从一个很小的 C 程序开始

先看下面的程序：

```c
int global = 42;

int main(void) {
    return global;
}
```

编译后，至少有两类内容进入 ELF 文件：

- `main` 编译得到的机器指令，通常属于代码；
- `global` 的初始值 `42`，通常属于已初始化数据。

程序还没有运行时，它们只是磁盘文件里的字节。例如，`42` 可能位于“从 ELF 文件开头往后数第 `0x3018` 个字节”的位置。这个编号叫作**文件偏移（file offset）**。

当程序开始运行，CPU 却不能说“请执行 ELF 文件的第 `0x2010` 个字节”。CPU 需要访问的是内存，普通进程看到的又是自己的**虚拟内存**。所以，内核要根据 ELF 提供的信息，把文件的一部分内容安排到进程的虚拟地址空间中。

例如：

```text
ELF 文件偏移 0x2010 的指令字节
        ↓ 装载或按需映射
进程虚拟地址 0x401010
        ↓ MMU 和页表翻译
当前物理地址 0x12345010
```

这三行中的数字只是示例。重点是：同一批内容，在不同层次上有不同的位置描述。

## 二、先认识三种“地址”

### 1. 文件偏移：它在 ELF 文件的第几个字节

把 ELF 文件想成一本从第 0 页开始连续编号的书。**文件偏移**回答的是：某一页内容离书的开头有多远。

```text
文件开头
  |
  +-- 偏移 0x0000：ELF 文件头
  +-- 偏移 0x1000：一部分程序内容
  +-- 偏移 0x2000：另一部分程序内容
```

文件偏移只在“读取文件”时有意义。文件系统会继续把它转换为文件块、磁盘逻辑块地址（LBA）等。至于 SSD 内部最终把这些数据存到哪一片闪存，ELF 无需知道，程序也不应依赖这个位置。

### 2. 虚拟地址：程序眼中的内存地址

程序运行时，指针、函数地址、栈地址等，通常都是**虚拟地址**。例如：

```c
printf("%p\n", (void *)&global);
```

打印出的地址是当前进程看到的地址，不是内存条上的真实地址。

每个进程都有自己的虚拟地址空间。进程 A 和进程 B 都可以使用 `0x400000` 这个虚拟地址，但它们可以指向不同的物理内存；这就是进程隔离的基础。

```text
进程 A：虚拟地址 0x400000  -> 物理页框 X
进程 B：虚拟地址 0x400000  -> 物理页框 Y
```

程序只需要使用自己的虚拟地址，不必知道 X 和 Y 究竟是哪一块 RAM。

### 3. 物理地址：当前实际访问的 RAM 位置

**物理地址**才是内存控制器和 RAM 最终使用的位置。它并不适合让普通用户程序直接操作：如果每个程序都能随意读写物理地址，一个程序写错指针就可能破坏另一个程序甚至操作系统。

物理地址由内核分配和管理。一个页面可能暂时不在内存，可能被换出；文件页也可能在首次访问时才读入 RAM。因此，ELF 不会为普通进程写死“必须使用物理地址 `0x12345010`”。这种写死既没有必要，也根本不可靠。

### 4. 三种地址的对照

| 名称 | 它回答的问题 | 示例 | 主要使用者 |
| ---- | ------------ | ---- | ---------- |
| 文件偏移 | 这个字节在文件中的哪里？ | `0x2010` | ELF、文件系统、装载器 |
| 虚拟地址 | 程序把它当作哪块内存？ | `0x401010` | 程序、CPU、MMU |
| 物理地址 | 它目前实际在哪个 RAM 位置？ | `0x12345010` | 内核、MMU、内存硬件 |

记忆方式很简单：**文件偏移找文件，虚拟地址给程序用，物理地址给真正的内存硬件用。**

## 三、ELF 不是只有一堆机器码

ELF 是一种有结构的文件格式。它至少会告诉操作系统：

- 哪些内容需要装入或映射；
- 文件中这些内容从哪里开始；
- 它们希望出现在进程虚拟地址空间的什么位置；
- 这片内存是否可读、可写、可执行；
- 程序入口在哪里。

初学时常会听到 `.text`、`.data`、`.bss` 等名字。它们是 ELF 的**节（section）**，方便编译器、链接器、调试器和人理解文件：

| 常见节 | 一般保存什么 |
| ------ | ------------ |
| `.text` | 机器指令，即代码 |
| `.rodata` | 字符串常量、只读常量 |
| `.data` | 已初始化的全局/静态变量，例如 `int global = 42` |
| `.bss` | 未显式初始化的全局/静态变量，例如 `int count;` |

但内核装载程序时，最主要看的不是这些节名，而是 ELF 中的**程序头表（program header table）**。程序头描述的是“怎样把文件放进内存”，其中最重要的是可装载段 `PT_LOAD`。

不妨先把它理解成：

```text
节：更适合回答“这些内容按用途叫什么？”
段：更适合回答“操作系统要怎样加载它们？”
```

一个可装载段可以包含一个或多个节。例如代码和只读常量可能被安排在可执行的段中；可写数据则安排在另一个可写段中。

## 四、`PT_LOAD` 里到底记录了什么

一个 `PT_LOAD` 段有几个最重要的字段：

```text
p_offset  该段在 ELF 文件中从哪里开始
p_vaddr   该段预期位于哪个虚拟地址
p_filesz  文件中实际有多少字节属于该段
p_memsz   运行时这段内存总共要有多大
p_flags   权限：读 R、写 W、执行 E/X
```

请先留意 `p_offset` 和 `p_vaddr`：**前者是文件偏移，后者是虚拟地址。两者都在 ELF 中。** 所以“ELF 只记录相对偏移，不记录虚拟地址”是不正确的。

假设 `readelf -lW ./app` 显示了下面的简化结果：

```text
Type   Offset   VirtAddr   FileSiz  MemSiz   Flags
LOAD   0x2000   0x402000   0x1000   0x1000   R E
LOAD   0x3000   0x603000   0x0200   0x0800   RW
```

第一行应读作：

> ELF 文件从偏移 `0x2000` 开始的 `0x1000` 字节，是一段可读、可执行的内容；它应出现在该进程虚拟地址 `0x402000` 开始的位置。

第二行表示一段可读、可写的数据。它在文件中只有 `0x200` 字节，但运行时需要 `0x800` 字节内存。多出来的部分应当是零，常用来容纳 `.bss`。所以未初始化全局变量不必在 ELF 文件中真的占一大片全为零的空间。

在同一个段的“文件实际内容”范围内，文件位置和段内虚拟地址有如下对应关系：

```text
虚拟地址 = p_vaddr + (文件偏移 - p_offset)
```

以第一行举例：文件偏移 `0x2010` 的字节距离段开头 `0x10` 字节，因此它在进程中的虚拟地址是：

```text
0x402000 + (0x2010 - 0x2000) = 0x402010
```

这只是“同一个段在文件中与在虚拟地址空间中的相对位置相同”的布局规则。它不是把物理地址算出来的公式，更不是页表的工作方式。

## 五、ELF 中的虚拟地址会不会每次都一样

答案是：有时接近固定，有时会变。这里不必急着背缩写，先知道原因：为了安全，现代系统常故意让程序每次启动时放到不同的虚拟地址区域，这叫 **ASLR（地址空间布局随机化）**。

### 1. 传统可执行文件：地址通常按 ELF 的布局使用

传统的非 PIE 可执行文件类型通常是 `ET_EXEC`。链接器已经安排好可装载段的虚拟地址，内核通常按该布局建立映射。例如段的 `p_vaddr` 是 `0x402000`，运行时也可能就从该虚拟地址开始放置。

请再确认一次：即使虚拟地址固定，它仍不是物理地址。

### 2. PIE 与共享库：还要加上装载基址

今天常见的主程序会编译为 PIE（位置无关可执行文件），它的 ELF 类型通常是 `ET_DYN`，共享库也是这种类型。这时，ELF 中的地址更像“从程序装载起点算起的地址”。系统会在本次启动时选择一个**装载基址（load bias）**：

```text
实际运行虚拟地址 = 装载基址 + ELF 中的 p_vaddr
```

例如：

```text
装载基址                 0x555555554000
ELF 中某段的 p_vaddr     0x000000002000
实际运行虚拟地址         0x555555556000
```

下一次运行可能选到另一个装载基址。因此，看到 ELF 里的虚拟地址后，不应一概认为它就是每次运行的最终数值；但它依然明确描述了段之间的虚拟地址布局。

## 六、页表的工作：把虚拟地址翻译成物理地址

到这里，ELF 已经告诉内核“文件的哪些部分对应进程的哪些虚拟地址”。接下来就轮到虚拟内存机制发挥作用了。

现代系统通常按固定大小的**页（page）**管理内存。假设页大小为 4 KiB：

```text
4 KiB = 4096 B = 2^12 B
```

一个虚拟地址可以拆成两部分：

```text
虚拟地址 = 虚拟页号 + 页内偏移
```

其中，低 12 位是页内偏移。MMU（内存管理单元）使用虚拟页号去查询页表，得到对应的物理页框号；页内偏移原样保留：

```text
物理地址 = 物理页框号 + 原来的页内偏移
```

因此，CPU 平常的访问方向是：

```text
CPU 的 PC 或普通访存指令给出虚拟地址
  -> MMU 查询 TLB / 页表
  -> 得到物理地址
  -> 访问缓存、DRAM
```

这回答了一个很重要的问题：**不是先有物理地址，再把它转成虚拟地址给 CPU 用；在普通用户进程中，通常是 CPU 先使用虚拟地址，再由 MMU 翻译为物理地址。**

### 建立 ELF 虚拟映射时，页内偏移从哪里来

这里的“生成虚拟内存”，更准确地说，是 `execve` 时内核为 ELF 建立虚拟内存区域（VMA）和页表映射的过程。关键结论是：**页内偏移不是内核从物理页框或文件偏移中算出来的新值；它由虚拟地址本身的低位定义。**

设基础页大小为 `P = 0x1000`（4 KiB）。对于任意虚拟地址 `VA`：

```text
虚拟页基址 = align_down(VA, P)
页内偏移 d = VA - 虚拟页基址 = VA mod P
```

也就是说，若内核决定某个字节位于虚拟地址 `0x401134`，那么它所在虚拟页的起点必然是 `0x401000`，页内偏移也就必然是 `0x134`。这不是一次额外的内存分配或复杂计算，只是把地址按固定页大小切成“页号 + 低位偏移”。当页大小是 2 的幂时，`d` 就是地址的低 `log2(P)` 位；4 KiB 时即低 12 位。

那么，内核为何能把 ELF 文件中的内容放到正确的虚拟地址？答案在 `PT_LOAD` 段的对齐约束。对可装载段，链接器需要安排：

```text
p_vaddr mod P = p_offset mod P
```

这里的两者仍不是同一个量：`p_vaddr` 是该段的虚拟地址，`p_offset` 是该段在文件中的偏移。等式只要求它们**相对于各自页起点的位移相同**。这是为了让内核能够从文件的整页边界开始，映射到虚拟地址的整页边界；否则，同一个文件页中的字节无法原封不动地对应到一个虚拟页中正确的字节位置。

看一个完整的 `PT_LOAD` 段示例：

```text
页大小 P                 0x1000
p_offset（文件中段起点）  0x2120
p_vaddr（虚拟段起点）    0x401120

p_offset mod P = 0x120
p_vaddr  mod P = 0x120
```

内核会按页向下对齐，建立如下对应关系：

```text
ELF 文件页：文件偏移 0x2000 ~ 0x2fff
                │
                │ 映射到同一页内位置
                ▼
虚拟页：    虚拟地址 0x401000 ~ 0x401fff

段的第一个字节：文件偏移 0x2120  <->  虚拟地址 0x401120
```

因此，文件偏移 `0x2134` 的字节距该文件页起点为 `0x134`，它就在虚拟页的 `0x134` 处，即虚拟地址 `0x401134`。这里可写成：

```text
VA = 0x401000 + (文件偏移 - 0x2000)
   = 0x401000 + (0x2134 - 0x2000)
   = 0x401134
```

对于 PIE 程序，内核还会加上本次运行选择的装载基址 `load_bias`；它会按页对齐，所以不会改变上述低 12 位：

```text
实际 VA = load_bias + p_vaddr + 段内相对位移
```

实际实现还可能先只创建 VMA，而不立刻建立所有页表项。某个虚拟页首次被访问时发生缺页，内核才根据这套关系找到对应文件页，将它读入页缓存或物理页框，并补上页表项。这只是“何时把内容放入 RAM”可以延后；虚拟地址及其页内偏移的含义并没有改变。

接着看它为何与物理页框的偏移相同。缺页时，内核可以任选一个**页对齐**的可用物理页框，例如 `0x12345000 ~ 0x12345fff`，并令页表项表示：

```text
虚拟页基址 0x401000  ->  物理页框基址 0x12345000
```

MMU 对虚拟地址 `0x401134` 翻译时，只是用页表把虚拟页基址换成物理页框基址，低位偏移 `0x134` 原样带过去：

```text
物理地址 = 0x12345000 + 0x134 = 0x12345134
```

换句话说，页表表达的是一个页到另一个同样大小页的**平移**：

```text
PA = 物理页框基址 + (VA - 虚拟页基址)
```

若同一虚拟页内的每个字节还要被翻译到不同偏移，页表就不能只存一个物理页框号，而必须保存每个字节的映射；4 KiB 页会退化为 4096 个独立映射单位。分页机制正是通过“页号可替换、页内偏移不变”这一规则，用一个页表项表示整页的连续对应关系。并不神秘，只是很节省页表，也很符合硬件实现。

### 物理页框是谁抽象出来的

“物理页”这个说法很常见，但它实际上把两层事情压缩成了一个词。严格一些，页表映射的目标应称为**物理页框（physical page frame）**；Linux 内核源码和日常讨论中也常把它简称为物理页。它不是又一层由操作系统伪造出来的地址空间。

先有的是**物理地址空间**。CPU 和主板平台把内存控制器、DRAM 以及部分内存映射设备暴露在一个可按字节寻址的物理地址范围中；固件再把哪些范围是实际 RAM、哪些是保留区或设备 MMIO 区域告知操作系统。物理地址 `0x12345678` 的含义，是平台上的这个物理位置，而不是某个进程私有的地址。

在此基础上，**操作系统按照处理器页表机制支持的页大小，把可管理的 RAM 划分成等大的页框**，以便分配、回收、共享和建立映射。这就是“物理页框”作为内存管理单位的来源。MMU 的页表项也恰好以“物理页框号”作为翻译结果的一部分，因此它是操作系统与硬件分页机制之间的共同边界，而不是只属于其中一方的概念。

假设基础页大小仍为 4 KiB，则物理地址也能用相同方式拆开：

```text
物理地址 0x12345678
  = 物理页框基址 0x12345000 + 页内偏移 0x678

物理页框号（PFN）= 0x12345678 / 0x1000 = 0x12345
```

内核可以把 `0x12345000` 到 `0x12345fff` 这 4 KiB RAM 当作一个可分配的页框，并用 `PFN`（Physical Frame Number，物理页框号）标识它。某个进程的虚拟页映射到该页框后，地址翻译正是：

```text
虚拟地址 = 虚拟页号 + 0x678
页表查询  -> 物理页框号 0x12345
物理地址 = 物理页框基址 0x12345000 + 0x678
```

所以，“页内偏移不变”并不是一条碰巧成立的约定；它来自页表的基本设计：页表只替换地址的“页号”部分，不触碰页内的字节位置。若把偏移也改掉，页内每个字节都会错位，页作为固定大小映射单位也就失去意义了。

这里还要避免三个过度简化的说法：

- **物理页框不是一块永远固定归某进程所有的 RAM。** 内核可以在进程解除映射后回收它，再分配给别的用途；同一虚拟页以后也可能被映射到另一个页框。
- **并非每个物理地址范围都是可分配的普通 RAM。** 物理地址空间中还可能有空洞、固件保留区和 MMIO 设备寄存器区。内核只会把可用 RAM 范围纳入通常的物理页分配器管理。
- **4 KiB 只是常见的基础页大小，不是唯一选择。** 页大小由体系结构和系统配置决定；例如 x86-64 常见 4 KiB 基础页，也可用 2 MiB 或 1 GiB 的大页。使用 2 MiB 大页时，保持不变的是低 21 位偏移，而不是低 12 位。

### 文件偏移并不参与页表地址计算

“虚拟地址由页表索引和文件偏移组成”这句话也需要修正。

- 页表索引来自虚拟地址中的**虚拟页号**；
- 文件偏移用于指出“页面内容应该从哪个文件位置读取”；
- 页表保存的是“虚拟页号 → 物理页框号”的映射。

文件偏移和页表会在**缺页**时联系起来，但它们不是同一地址的两半。

例如，程序第一次执行某段代码时，可能发生如下过程：

```text
1. PC 指向代码的虚拟地址，例如 0x402010
2. MMU 发现这个虚拟页目前没有映射到 RAM，产生缺页异常
3. 内核知道：这个虚拟页对应 ELF 文件中从偏移 0x2000 开始的一页内容
4. 内核把这页内容读入一个可用的物理页框
5. 内核更新页表：虚拟页 0x402000 所在页 -> 新物理页框
6. CPU 重试刚才的取指；这次翻译成功，继续执行
```

以后即使这个页面被内核换出、又被读回另一个物理页框，程序看到的虚拟地址仍可保持不变。这就是为什么 ELF 不需要保存最终物理地址。

## 七、CPU 到底从哪里开始执行

ELF 文件头中有一个字段叫 `e_entry`，表示程序的**入口点虚拟地址**。可以用下面命令查看：

```bash
readelf -hW ./app
```

输出中通常会有类似：

```text
Entry point address: 0x401040
```

对于传统 `ET_EXEC` 程序，内核可以根据这个入口设置初始控制流。对于 PIE 程序，实际入口还要加上这次运行选择的装载基址：

```text
实际入口虚拟地址 = 装载基址 + e_entry
```

但是，入口点通常不是你写的 `main` 函数。C/C++ 程序在 `main` 前还要完成很多准备工作，例如准备运行时环境、初始化 C 库、处理命令行参数和全局构造等。入口点通常是启动代码 `_start`，它最终才会调用 `main`。

如果程序依赖共享库，情况还多一层：ELF 中可能有 `PT_INTERP`，它指明动态链接器，例如 `/lib64/ld-linux-x86-64.so.2`。内核会先让动态链接器运行；动态链接器负责装入共享库、处理部分重定位后，再跳到主程序入口。

可以先记住这条简化链路：

```text
执行程序
 -> 内核读取 ELF 的装载信息
 -> 建立进程的虚拟地址空间
 -> 必要时先运行动态链接器
 -> 进入程序启动代码 _start
 -> C/C++ 运行时初始化
 -> main
```

运行过程中，PC（程序计数器）保存下一条要取的指令的**虚拟地址**。PC 指向哪里，取指单元就尝试从哪里取指；MMU 再负责把这个虚拟地址转换为实际物理地址。

## 八、ELF 里的 `p_paddr` 是不是物理地址

在 program header 中，还可能看到一个叫 `p_paddr` 的字段。它的名字确实像 physical address，所以初学时感到困惑非常正常。

但对普通 Linux 用户态程序，`p_paddr` 通常不用于决定实际的 RAM 位置，常见值也可能是 `0`。Linux 装载普通应用时，关注的是：

- 从文件哪儿取内容：`p_offset`；
- 映射到哪片虚拟空间：`p_vaddr`；
- 映射多大：`p_filesz`、`p_memsz`；
- 赋予什么权限：`p_flags`。

`p_paddr` 主要为一些特殊环境保留：例如没有启用虚拟内存的裸机程序、bootloader、固件或特定的内核映像。在这类场景中，程序可能真的必须被装入某个确定的物理位置。普通用户进程则是另一回事，不能因为字段名相同就把两种场景混在一起。

## 九、自己验证：用 `readelf` 看一眼

假设编译出程序 `app`，下面三个命令已经足够完成入门观察：

```bash
readelf -hW ./app
readelf -lW ./app
readelf -SW ./app
```

它们分别适合看：

| 命令 | 重点观察内容 |
| ---- | ------------ |
| `readelf -hW` | ELF 类型、入口点 `e_entry` |
| `readelf -lW` | 可装载段的 `Offset`、`VirtAddr`、大小、权限 |
| `readelf -SW` | `.text`、`.data`、`.bss` 等节的位置与大小 |

最值得先看的就是 `readelf -lW` 的 `LOAD` 行。你会同时看到 `Offset` 和 `VirtAddr` 两列，这正是“ELF 同时描述文件位置和虚拟地址布局”的直接证据。

无需试图立刻看懂输出中的每一行。第一遍只要能辨认出：`LOAD` 是要装载的段、`Offset` 是文件偏移、`VirtAddr` 是虚拟地址、`R E` 和 `RW` 是权限，就已经足够了。

## 十、把整个过程串起来

现在可以把程序从磁盘到 CPU 的过程串成一条线：

```text
1. 编译、链接生成 ELF 文件
   文件中保存机器指令、初始化数据和装载说明

2. 内核执行程序时读取 ELF
   通过 PT_LOAD 知道文件偏移、虚拟地址、大小和权限

3. 内核为进程建立虚拟内存区域
   代码通常是 R-X，数据通常是 RW-，并不一定立刻读完整个文件

4. PC 给出下一条指令的虚拟地址
   CPU 请求从这个虚拟地址取指

5. MMU 根据页表翻译虚拟地址
   得到当前对应的物理地址

6. 若该页尚未在 RAM
   内核根据对应的 ELF 文件偏移读入页面，更新页表，再重试

7. CPU 从缓存或内存取到指令并执行
```

其中每一层各司其职：ELF 描述文件和装载布局；内核管理进程与物理内存；页表记录当前映射；MMU 执行翻译；CPU 根据 PC 取指。这套分工并不复杂，只是它们恰好都带着“地址”二字，容易让人误以为是在重复做同一件事。

## 十一、常见误解与正确说法

### 误解 1：ELF 只记录文件相对偏移

不准确。`PT_LOAD` 段同时有 `p_offset` 和 `p_vaddr`：前者定位文件，后者描述虚拟地址布局。

### 误解 2：ELF 把程序最终物理地址写死

对普通用户进程通常不准确。物理页框由内核运行时分配，可能因缺页、内存回收、换出换入等变化。ELF 一般不需要也不会依赖最终物理地址。

### 误解 3：虚拟地址由页表索引和文件偏移拼成

不准确。虚拟地址按页可分成虚拟页号和页内偏移；页表用虚拟页号找到物理页框。文件偏移用于找到文件里的原始内容，不是虚拟地址的组成部分。

### 误解 4：CPU 必须先把物理地址变成虚拟地址才能执行

方向反了。普通用户进程中，PC 和普通访存指令先产生虚拟地址，MMU 再把它翻译成物理地址。

### 误解 5：`e_entry` 就是 `main` 的地址

通常不是。它通常指向运行时启动代码；若有动态链接器，最开始的控制流还会先进入动态链接器。经过初始化之后，才会调用 `main`。

## 十二、总结

读 ELF 和虚拟内存时，可以一直带着下面这张小抄：

| 看到的内容 | 应该想到什么 |
| ---------- | ------------ |
| `p_offset` | 这段内容在 ELF 文件中的起点 |
| `p_vaddr` | 这段内容在进程虚拟地址空间中的布局起点 |
| `p_filesz` | 文件中实际保存的字节数 |
| `p_memsz` | 运行时需要的内存大小，可能包含全零的 `.bss` |
| `e_entry` | 程序入口的虚拟地址，PIE 时还要考虑装载基址 |
| 页表 | 当前虚拟页映射到哪个物理页框 |

最后只需记住五句话：

- ELF 中既有文件偏移，也有虚拟地址布局。
- 普通用户态 ELF 通常不记录最终物理内存地址。
- 文件偏移用于找到文件内容，虚拟地址用于让程序访问内存。
- CPU 先使用虚拟地址，MMU 再把它翻译为物理地址。
- PC 最初从 ELF 入口相关的位置开始取指，但 C/C++ 的 `main` 还要经过启动代码和可能的动态链接步骤才会被调用。

把“文件里的哪里”“进程眼中的哪里”“RAM 里的哪里”分开之后，ELF、页表和 PC 的关系就清楚了。所谓地址，并不难；难的是一开始就让一个词替三个不同层次的概念背锅而已。
