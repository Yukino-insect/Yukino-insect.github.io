把一个分区挂载到 `/data`，表面上只是一条 `mount` 命令；实际上，内核需要完成一次很严格的“验明身份、恢复账本、建立对象、接入目录树”的过程。它既要确认这确实是一个自己支持的文件系统，又要保证崩溃后遗留的元数据不会立刻被当作正常状态使用，最后还要让后续的路径解析能够穿过 `/data` 进入新文件系统。

本文以 **Linux VFS（Virtual File System）与 ext4** 为主线。VFS 是 Linux 向应用提供统一文件接口的一层；ext4 是一个具体的磁盘文件系统。FAT、XFS、Btrfs、NTFS 和 NFS 的磁盘格式及部分挂载细节不同，但“找到文件系统描述信息、构造内存对象、把根目录接到一个挂载点”这一主线是共通的。

## 一、先给出全景：挂载到底改变了什么

格式化、分区和挂载是三个不同动作。

| 动作 | 操作对象 | 结果 |
| ---- | -------- | ---- |
| 分区 | 整块磁盘的 LBA 范围 | 得到 `/dev/nvme0n1p1` 这类块设备视图 |
| 格式化 `mkfs` | 一个分区或镜像文件 | 写入 ext4、XFS 等文件系统的初始元数据 |
| 挂载 `mount` | 已有的文件系统与一个目录 | 在当前挂载命名空间中建立可访问的目录入口 |

例如：

```bash
sudo mount -t ext4 /dev/nvme0n1p1 /data
```

它不是把 `/dev/nvme0n1p1` 的字节“移动”到 `/data`，也不是把整块磁盘或全部 inode 读进内存。内核只是为该文件系统建立必要的缓存和控制对象，并让路径解析在走到 `/data` 时切换到该文件系统的根目录。

可以先把整体过程记成下面这条链路：

```mermaid
flowchart LR
    A[用户 mount 请求] --> B[解析设备、类型和选项]
    B --> C[打开块设备]
    C --> D[读取并校验磁盘超级块]
    D --> E[创建或复用 VFS 超级块]
    E --> F[读取根 inode 并创建根 dentry]
    F --> G[日志恢复与孤儿清理]
    G --> H[将文件系统根接到挂载点]
    H --> I[路径访问 /data/...]
```

这里有两个看似同名、实则不同的“超级块”：**磁盘上的超级块**描述磁盘格式；**内存中的 `struct super_block`** 是 VFS 对一个已装入文件系统实例的通用表示。前者能在断电后保留，后者在卸载后会消失。

## 二、挂载前，磁盘上已经有什么

### 1. 分区表不是文件系统

一块磁盘可能有 GPT 或 MBR 分区表。它的职责是把整块设备划成若干 LBA 范围，并标识分区类型；它不记录目录、文件名或 inode。

```text
整块磁盘 /dev/nvme0n1
├── GPT：分区边界与分区类型
├── /dev/nvme0n1p1：EFI System Partition，通常是 FAT
└── /dev/nvme0n1p2：Linux filesystem，可能是 ext4
```

所以，内核先通过块层把 `/dev/nvme0n1p2` 当作“从某个起始 LBA 开始、长度有限的一段逻辑块设备”；之后 ext4 驱动才在这段范围内解释自己的元数据。把 GPT 当成 ext4 的一部分，会把设备划分和文件管理混成同一件事。

### 2. `mkfs.ext4` 写入的是一套可解释的账本

格式化并不只是清零数据区。它会写入文件系统可识别的元数据：超级块、块组描述符、块位图、inode 位图、inode 表、根目录 inode、目录项，以及通常位于某个 inode 中的日志区域。

ext4 把设备切分为多个 **block group（块组）**，让某一批 inode、其位图和附近数据块尽量靠近，减少大范围寻址和机械磁盘寻道。简化布局如下：

```text
ext4 分区
├── 前 1024 字节保留区
├── 主超级块（1024 字节）
├── 块组描述符表
├── 块组 0
│   ├── 数据块位图
│   ├── inode 位图
│   ├── inode 表
│   └── 数据块
├── 块组 1
│   └── ...
└── 其他块组及部分元数据备份
```

在典型 ext4 布局中，主超级块从**分区起点偏移 1024 字节**开始，大小为 1024 字节；这不等于“它总在 ext4 的第 1 个文件系统块”。当文件系统块大小为 1 KiB 时，它占用逻辑块 1；块大小更大时，它位于第一个逻辑块中的偏移 1024 处。ext4 还会在部分块组保留超级块与组描述符备份，以降低开头损坏导致整卷完全不可识别的风险。[Linux 内核 ext4 布局文档](https://docs.kernel.org/filesystems/ext4/overview.html)对此有更精确的说明。

### 3. 磁盘超级块回答“这是什么、该怎么读”

超级块不是某个普通文件的元数据，而是**整个文件系统实例的总说明书**。不同文件系统字段不同；以 ext4 为例，重要信息可归为以下几类。

| 信息类别 | ext4 中的典型字段或概念 | 挂载时的用途 |
| -------- | ----------------------- | ------------ |
| 身份与版本 | magic `0xEF53`、UUID、修订版本 | 判断是否像 ext4，并识别该卷 |
| 容量与粒度 | inode/块总数、每组数量、块大小 | 计算元数据和数据区的位置、建立分配器 |
| 格式能力 | `compat`、`incompat`、`ro_compat` 特性位 | 决定内核能否安全读写 |
| 运行与维护状态 | 最近挂载/写入时间、clean 状态、错误策略 | 判断是否需要恢复，以及遇错如何处理 |
| 一致性设施 | 日志 inode/日志设备信息、校验和 | 定位日志、验证元数据、执行恢复 |

其中最容易被误解的是“特性位”。它们不是可忽略的装饰：

- `compat`：内核即使不了解该特性，通常仍可安全挂载；
- `ro_compat`：不了解时可以只读挂载，但不能安全写入；
- `incompat`：不了解时连正确解释布局都无法保证，必须拒绝挂载。

例如，支持 ext4 但不支持某种决定 inode 或 extent 解释方式的 `incompat` 特性时，强行挂载可能把块位置理解错。这时失败不是“系统小题大做”，而是在拒绝对陌生格式写数据。ext4 的磁盘超级块字段、状态位和特性位以[内核文档中的 `struct ext4_super_block`](https://docs.kernel.org/filesystems/ext4/super.html)为准。

### 4. 超级块不能取代块组描述符和 inode

超级块知道“每组有多少 inode、块大小是多少、共有多少组”，但不会直接列出每个文件的所有块。更细的元数据有自己的职责：

```text
超级块
  -> 块组描述符：本组块位图、inode 位图、inode 表在哪里
      -> inode 表：某个 inode 的权限、大小、时间和数据映射
          -> extent / 间接块：文件逻辑块对应哪些设备块
目录数据块
  -> 名称 -> inode 号
```

根目录在 ext 系列中约定使用 inode 号 `2`；它不是“超级块里保存一条根目录绝对地址”的普通字段。ext4 驱动根据超级块和块组描述符定位 inode 表，再读取 inode `2`，由它作为新文件系统的根。关于目录、inode 和 extent 如何定位文件数据，可结合[文件系统如何定位文件数据：路径、目录、inode、extent 与空闲空间](../os-memory-file-io-course/04-file-system-metadata-and-blocks.md)阅读。

## 三、VFS 需要在内存中建立哪些对象

磁盘格式各不相同，应用却希望总能使用 `open`、`read`、`mkdir`、`stat`。Linux VFS 于是抽象出一组共同对象；具体文件系统把自己的磁盘结构翻译为这些对象和操作函数。

| VFS 概念 | 主要含义 | 与磁盘结构的关系 |
| -------- | -------- | ---------------- |
| `file_system_type` | 已注册的文件系统驱动，如 `ext4` | 提供解析选项、取得根目录等回调 |
| `super_block` | 已装入的一个文件系统实例的全局状态 | 内存对象；可关联 ext4 的磁盘超级块和私有信息 |
| `inode` | VFS 中的文件对象元数据 | 通常由磁盘 inode 缓存而来，但可能延迟读取 |
| `dentry` | 名称与 inode 的目录项缓存、路径节点 | 多数是运行期对象，不是磁盘目录项的逐字节镜像 |
| `vfsmount` / 内部 `mount` | 一次“接入目录树”的挂载视图 | 指向一个文件系统根，可携带挂载选项 |
| mount namespace | 一组进程可见的挂载树 | 同一磁盘文件系统可在不同命名空间呈现不同入口 |

因此，同一个 ext4 分区可被绑定挂载到多个路径；也可在容器中只显示其中一部分挂载树。反过来，`/proc`、`sysfs` 这类伪文件系统并没有传统磁盘超级块，却仍然能以 VFS 超级块、inode、dentry 和挂载对象的形式出现在路径树中。

一个必须记住的结论是：**“文件系统实例”和“挂载位置”不是一对一关系**。前者描述一套目录、inode 与块分配规则；后者描述“哪个命名空间中的哪个目录通向它”。

## 四、一次 Linux 挂载的详细过程

下面以把一个 ext4 块设备挂到 `/data` 为例说明。内核版本会改变函数名称和调用层次；现代 Linux 以多阶段的 mount API 组织流程，但下面的职责划分是稳定的。

### 1. 用户态提交“源、类型、目标与选项”

用户可以通过传统 `mount(2)` 系统调用、`mount` 命令，或较新的 `fsopen`、`fsconfig`、`fsmount` 等接口发起挂载。概念上，它们都要提供：

```text
source = /dev/nvme0n1p2        # 源：块设备、远程地址或 none
fstype = ext4                  # 使用哪个文件系统驱动
target = /data                 # 要覆盖的目录
options = rw,noatime           # 选项
```

`mount` 命令本身主要负责解析参数、查找 `/etc/fstab`（若使用）并发起系统调用；真正读超级块和建立 VFS 对象的是内核。内核还会检查调用者权限、挂载命名空间、目标目录、LSM 安全策略和设备访问权限。普通进程不能随意把任意设备覆盖到全局目录树上。

现代 VFS 会先创建 `fs_context`，逐项解析并验证 VFS 选项与 ext4 私有选项，再取得或创建可挂载的根对象。这个分阶段设计使内核可以在尚未改变目录树之前报告参数问题。完整接口由[Linux 文件系统 Mount API 文档](https://docs.kernel.org/filesystems/mount_api.html)描述。

### 2. 块设备层提供受边界限制的读写入口

对于 ext4 这类需要块设备的文件系统，内核会打开对应的 block device，并获得它的逻辑扇区大小、容量和读写能力。若来源是一个分区，分区边界由块设备层约束；ext4 不应访问该范围外的 LBA。

这层只负责“按逻辑块读写”；它不知道 `/home` 或 inode。NVMe、SATA、USB、RAID、设备映射器、LVM 乃至 loop 设备都可以在下面实现同一种块设备接口。文件系统因而不必知道真正是机械盘、SSD，还是一个普通镜像文件。

### 3. 驱动读取超级块，验证它是否可被安全解释

ext4 驱动会从规定位置读出其磁盘超级块，并依次做类似如下的判断：

1. 检查 ext4 magic、字段范围、块大小等基本合法性；
2. 验证 UUID、元数据校验和及关键元数据的一致性；
3. 检查 `compat`、`ro_compat`、`incompat` 特性位；
4. 读取块组描述符，确认位图和 inode 表位置在合法范围内；
5. 根据挂载选项、设备只读状态和特性支持情况决定 `rw`、`ro` 或报错。

这里的“识别文件系统类型”不是只看一个 magic 就结束。magic 可以快速排除绝大多数错误设备，但一个看似 ext4 的结构仍可能已损坏、来自不受支持的未来版本，或者要求只读访问。校验、边界检查和特性协商共同避免内核把任意字节错当成 inode 表。

### 4. 创建或复用内存中的 `super_block`

验证通过后，VFS 需要一个 `struct super_block` 表示此次已装入的文件系统状态。它会保存块大小、挂载状态、根 dentry、超级块操作集合，以及指向 ext4 私有内存信息的指针。ext4 私有信息再保存已解析的磁盘超级块、块组数据、日志句柄、分配器状态等。

这里存在“新建还是复用”的分支。某些场景中，VFS 能按设备和参数找到已经存在的同一文件系统超级块，新的挂载只创建一个新的挂载视图；某些文件系统或参数组合则需要独立实例。不要简单认为“每执行一次 `mount` 就一定重新扫描磁盘并创建一份完全独立的超级块”。VFS 的超级块获取辅助函数正是为这种查找/创建决策设计的。[VFS 概览](https://docs.kernel.org/filesystems/vfs.html)也列出了文件系统类型、超级块、inode 与目录项的职责。

### 5. 取出根 inode，建立根 dentry

接下来，ext4 根据块组描述符找到 inode 表，读取 inode `2`，检查它确实是一个目录，并把它转换为 VFS inode。随后创建根 dentry，得到“这个文件系统内部路径 `/`”对应的 VFS `path`。

注意这时的 `/` 只是**新文件系统内部的根**，并不自动等于整个系统的 `/`。若把设备挂到 `/data`，其根 dentry 在最终接入前还不可由普通进程通过 `/data` 访问。

内核也不会在这一刻遍历整棵目录树：

- 常用的超级块、组描述符、根 inode 和日志相关元数据必须读取；
- 其他 inode、目录块和文件数据一般按需进入 inode 缓存、dentry 缓存与页缓存；
- 只有一致性检查工具或严重损坏恢复才可能进行大范围扫描。

### 6. 必要时先做日志恢复和孤儿清理

若上次正常卸载前未完成所有更新，ext4 的状态位可能表明需要恢复。带日志的 ext4 使用 jbd2：已完整提交的事务可在挂载时重放，未完成或校验不通过的事务不能被当作已提交修改。日志事务以提交记录为边界，正是为了让崩溃恢复能够判断“这组元数据是否完整”。[jbd2 日志格式说明](https://docs.kernel.org/filesystems/ext4/journal.html)给出了 descriptor、revoke 与 commit 记录的关系。

文件系统还可能处理 orphan inode。典型例子是：文件的目录项已删除，但仍被进程打开；或者截断、删除操作在崩溃时中断。恢复逻辑需要把这些“应当回收但未完成回收”的对象收敛到一致状态。

日志恢复不是完整的 `fsck`。它主要利用已经存在的事务记录快速修复可恢复的元数据状态；若超级块、位图、inode 表本身发生严重损坏，内核可能拒绝读写，此时应离线检查和修复，而不是对一个正在读写的文件系统贸然运行修复工具。

### 7. 把根接到 `/data`：挂载树真正改变的地方

当文件系统根已准备好，VFS 才创建一次挂载，并把它附着到当前 mount namespace 中的 `/data`。之后路径解析：

```text
解析 /data/projects/a.txt
  -> 在父文件系统中走到目录项 data
  -> 发现 data 是一个挂载点
  -> 切换到 ext4 的根 dentry
  -> 在该 ext4 内继续解析 projects/a.txt
```

这解释了两个现象：

- 挂载后，原先 `/data` 目录中可见的文件会被**遮蔽**，而不是删除；卸载后它们又可见。
- `/data/..` 不能机械地理解为“在新 ext4 根目录中寻找一个名为 `..` 的普通目录项”。路径遍历需要同时理解 dentry 父子关系和挂载树，才能在跨挂载点时得到正确语义。

容器的 mount namespace 使这件事更明显：宿主机与容器可以对相同目录路径拥有不同的挂载树。容器看见 `/data`，并不推出宿主机同一路径挂着同一文件系统。

## 五、挂载完成后，访问一个文件如何继续

以 `open("/data/report.txt")` 为例，VFS 从进程的根目录或当前目录出发做路径遍历。命中 `/data` 挂载点后进入 ext4 根 dentry，再查找 `report.txt`。dentry 缓存和 inode 缓存命中时，不必读取磁盘；未命中时 ext4 才读取相应目录块和 inode。

成功打开后，`read` 的路径则主要是：

```text
文件描述符
  -> 打开文件对象
  -> inode 与文件偏移
  -> 页缓存
  -> ext4 的逻辑块映射
  -> 块层请求
  -> 设备驱动与 DMA
```

挂载建立的是这套“从路径进入某个文件系统、并调用正确操作函数”的起点；它不是每次 `read` 都要重复的工作。读取数据时的缓存、逻辑块转换和 DMA 链路可继续阅读[一次 read 到底发生了什么：页缓存、缺页与用户缓冲区](../os-memory-file-io-course/05-read-path-and-page-cache.md)。

## 六、卸载是挂载的逆过程，但不能粗暴地反着做

普通 `umount /data` 不能只把目录树边删掉。内核需要确认该挂载没有仍在使用的工作目录、打开文件、子挂载或其他活动引用；否则通常报 `EBUSY`，避免一个仍在被进程使用的路径突然失去语义。

正常卸载大致包括：

1. 阻止新的路径访问进入该挂载；
2. 检查活跃引用和子挂载；
3. 写回脏页、提交必要的日志事务，更新文件系统状态；
4. 从当前 mount namespace 分离挂载；
5. 当最后一个引用消失时，释放 VFS 超级块和文件系统私有资源，并关闭设备。

`umount -l` 使用的是惰性分离：它先从命名空间中隐藏挂载，已有引用在稍后释放。这适合处理某些卡住的挂载关系，却不等于数据已经同步完成，更不该把它当作日常替代方案。是否真的安全落盘仍取决于文件系统、块设备缓存和应用是否正确使用 `fsync` 等持久化边界。

## 七、如何观察一块 ext4 设备和它的挂载状态

以下命令用于查看，默认不会修改文件系统。把示例设备名替换为真实目标；不要对不确定的生产设备执行写入或修复操作。

```bash
# 设备、分区、文件系统类型、UUID 与挂载点
lsblk -f

# 某个设备识别出的文件系统标识
sudo blkid /dev/nvme0n1p2

# 从“挂载树”的角度查看来源、目标、类型和选项
findmnt -T /data
```

若目标未挂载、且你只是想读出 ext4 超级块摘要，可以使用：

```bash
sudo dumpe2fs -h /dev/nvme0n1p2
```

输出中常能看到 UUID、块大小、inode/块计数、特性位、最近挂载时间、文件系统状态和错误策略。`dumpe2fs` 展示的是磁盘格式信息；`findmnt` 和 `/proc/self/mountinfo` 展示的是当前命名空间中已经建立的挂载关系。一个回答“盘上有什么”，另一个回答“此进程眼前接入了什么”，不要互相替代。

若希望无风险地练习，可对普通镜像文件操作，而非真实分区：

```bash
truncate -s 64M /tmp/ext4-mount-demo.img
mkfs.ext4 -F /tmp/ext4-mount-demo.img
mkdir -p /tmp/ext4-mount-demo
sudo mount -o loop /tmp/ext4-mount-demo.img /tmp/ext4-mount-demo

findmnt -T /tmp/ext4-mount-demo
sudo umount /tmp/ext4-mount-demo
```

这里的 loop 设备把普通文件虚拟成块设备，因此其上的 ext4 仍经历“读取超级块、建立 VFS 对象、接入挂载点”的同一类过程。

## 八、常见误解与排障方向

### 1. “挂载会把整块盘读进内存”

不会。挂载优先读取超级块、根路径和恢复所需的关键元数据；其他目录、inode 与文件页通常按需缓存。容量很大的文件系统之所以能很快挂载，正是因为它不需要先扫描每个数据块。

### 2. “超级块就是所有文件元数据”

不是。超级块只描述整个卷；文件级元数据在 inode/MFT 等记录中，名称映射在目录中，空闲空间又由位图或树等结构维护。超级块像图书馆总目录，不是把每本书的每一页都抄在目录页里。

### 3. “看到 dirty 或 needs recovery 就一定要先运行 `fsck`”

不一定。带日志文件系统常能在挂载阶段自动重放已提交事务；是否需要离线 `fsck` 取决于文件系统状态、内核报错和运维策略。若怀疑损坏，先停止写入、保留证据和备份，按照该文件系统的官方修复流程在未挂载状态下处理。对已挂载且活跃的卷直接修复，往往比原故障更危险。

### 4. “同一设备不能出现两次”

同一设备可能对应多个挂载视图，也可能因 bind mount、mount namespace 或不同参数呈现出不同路径关系。但同时以不兼容方式读写同一底层文件系统会破坏一致性；多主机共享块设备还需要集群文件系统或专门协调机制，不能仅靠两台机器各自执行一次普通 `mount -o rw`。

### 5. “卸载成功就等于应用数据已经满足业务持久化要求”

卸载会推动文件系统完成应做的写回与状态更新，但应用真正需要的持久化点应在业务流程中通过正确的写入、同步、事务或数据库协议界定。文件系统日志主要保护自身元数据的一致性，不会替应用判断一笔订单或一组跨文件更新是否在业务上原子完成。

## 九、总结

- 分区定义设备边界，`mkfs` 写入文件系统账本，`mount` 才把这套账本接入某个目录入口。
- ext4 磁盘超级块记录块大小、容量、UUID、特性位、状态和恢复信息；块组描述符、inode、目录项与位图继续承担更细的索引和分配职责。
- Linux VFS 用 `super_block`、inode、dentry 和挂载对象把不同文件系统统一为路径、文件描述符与系统调用接口。磁盘超级块和 VFS 超级块不是同一个对象。
- 挂载的关键步骤是：验证格式与能力、建立/复用内存超级块、取得根 inode、按需恢复日志，再把根接入当前 mount namespace 的目标目录。
- 挂载不扫描整盘，也不复制数据；它建立的是一条从路径名到正确文件系统实现的入口。后续读取和写入再由缓存、元数据映射、块层与设备共同完成。
