当一个 8 位寄存器执行 `127 + 1`，最后留下的位模式是 `1000_0000`。它可以被解释为无符号数 `128`，也可以被解释为有符号补码数 `-128`。那么，CPU 到底有没有“发现”计算出了错误的结果？

答案是：CPU 的加法器会在运算时自然产生足以判断的信号，但**是否称为溢出，取决于这串位按无符号数还是有符号补码数解释**。无符号加法主要看最高位之外的进位；有符号加法主要看符号位前后的进位是否矛盾。两者不能混用。

本文讨论的是固定宽度**整数**的算术溢出，不是递归过深导致的栈溢出，也不是缓冲区越界。读完后，应当能够从一张加法器的进位图推导出常见的 `CF`、`OF`、`V` 标志，并理解为什么 RISC-V 即使没有这些状态标志，仍然能检测溢出。

如果还不熟悉补码的取值范围，建议先阅读[补码为什么多一个数：表示范围与整数溢出](补码为什么多一个数：表示范围与整数溢出.md)。这里不再重复枚举所有补码位模式，而是关注 CPU 在一条指令执行时实际能观察到什么。

## 一、先区分：位模式、数学结果与写回结果

寄存器只有固定的 `n` 位。无论 ALU 在内部算出了多少位，普通 `n` 位运算的目的寄存器通常只能保留低 `n` 位：

```text
完整数学结果 ──> 取低 n 位 ──> 写回寄存器
                         │
                         └── 同时产生进位、符号等状态信号
```

因此，硬件不会因为结果“太大”就凭空增加一个寄存器位。以 8 位加法为例：

```text
  1111_1111    255（无符号）或 -1（有符号）
+ 0000_0001      1
-----------
1_0000_0000
```

写回的低 8 位是 `0000_0000`，额外的第 9 位是 `1`。这件事实本身没有说明“有符号溢出”还是“无符号溢出”：

- 视为无符号数：`255 + 1 = 256`，超出 `0～255`，发生溢出。
- 视为有符号补码：`-1 + 1 = 0`，仍在 `-128～127` 内，**没有**溢出。

所以“最高位有进位就溢出”只适用于**无符号加法**。把它背成适用于一切整数的规则，只会稳定地制造错误；这一点并不神秘，只是经常被省略了。

## 二、加法器实际产生了什么

### 1. 每一位都会产生进位

一个 `n` 位加法器可看作从低位到高位的全加器组合。设：

- `c0` 是最低位的输入进位；普通加法中它为 `0`；
- `ci` 是进入第 `i` 位的进位；
- `cn` 是离开最高位的进位，也就是整个 `n` 位加法器的 `carry-out`；
- `a`、`b`、`r` 分别是两个操作数和写回的 `n` 位结果。

以 4 位加法 `0111 + 0001` 为例：

```text
位编号：        3    2    1    0
a：             0    1    1    1
b：             0    0    0    1
输入进位：       0    0    0    0
--------------------------------
r：             1    0    0    0
输出到下一位：    0    0    0    1

进入符号位 c3 = 1，离开符号位 c4 = 0
```

第 3 位是 4 位数的符号位。这里 `c3` 与 `c4` 不同，正是有符号溢出的关键信号。真实 CPU 的加法器不一定把进位逐位串行传递：它可能使用超前进位、前缀加法器等更快的结构；但无论实现多么复杂，仍可得到这两个等价的进位结果。

### 2. 同一条位加法可服务两种整数解释

ALU 对 `0111 + 0001` 做的位运算，与软件之后把结果读成 signed 或 unsigned 没有关系。它只得到：

```text
r = 1000
c4 = 0
c3 = 1
```

随后，不同语义使用不同判据：

| 解释方式 | 可表示范围（4 位） | 该例的结论 | 判据 |
| -------- | ------------------ | ---------- | ---- |
| 无符号 | `0～15` | `7 + 1 = 8`，可表示 | `c4 = 0`，未溢出 |
| 有符号补码 | `-8～7` | `7 + 1 = 8`，不可表示 | `c3 XOR c4 = 1`，溢出 |

这就是为什么同一串位、同一套加法器，必须保留至少两个不同含义的状态信息。

## 三、无符号运算：范围边界之外的进位与借位

### 1. 无符号加法：看最高位之外的进位

`n` 位无符号整数范围是 `0` 到 `2^n - 1`。若 `a + b` 产生 `cn = 1`，完整和至少为 `2^n`，低 `n` 位显然放不下：

```text
unsigned_overflow_add = cn
```

8 位例子：

```text
  1111_1010    250
+ 0000_1010     10
-----------
1_0000_0100    完整数学结果 260

写回：0000_0100 = 4
cn：1，因此无符号溢出
```

软件若已取得截断结果 `r`，也可不读取标志位而用下面的等价关系检测：

```text
r = a + b（按 n 位回绕）
无符号加法溢出当且仅当 r < a
```

发生回绕时，结果从接近最大值突然变小，因此一定小于任一加数 `a`；未回绕时，`r = a + b` 不会小于 `a`。

### 2. 无符号减法：看是否需要借位

无符号的 `a - b` 在 `a < b` 时会低于 0，因而无法表示。例如 8 位的 `0 - 1` 写回为 `255`：

```text
  0000_0000    0
- 0000_0001    1
-----------
  1111_1111    低 8 位结果 255
```

直接的判断是：

```text
unsigned_overflow_sub = (a < b)
```

减法器一般不必单独实现。它利用补码恒等式 `a - b = a + NOT b + 1`，交给加法器完成。此时最后的 `carry-out` 常被解释为“**没有借位**”：`cn = 1` 表示 `a >= b`，`cn = 0` 表示发生借位。可是 ISA 对公开标志位的约定并不完全一致：

- x86 的 `SUB`/`CMP` 将 `CF = 1` 定义为**发生无符号借位**；
- ARM/AArch64 的减法标志中，`C = 1` 表示**未借位**。

因此，阅读汇编或手写多精度减法时，不能只记“C 是 carry”。必须先看该架构对减法标志的定义；标志名相同，极性却可以相反。

## 四、有符号补码：比较进入和离开符号位的进位

### 1. 有符号加法的硬件公式

`n` 位补码的范围是 `-2^(n-1)` 到 `2^(n-1)-1`。有符号加法溢出只会发生在两种情况：

- 两个正数相加，结果越过正数上界，符号位变成 `1`；
- 两个负数相加，结果越过负数下界，符号位变成 `0`。

对加法器而言，这两种情况可统一成一个门电路：

```text
signed_overflow_add = c(n-1) XOR cn
```

也就是：**进入符号位的进位**与**离开符号位的进位**不同，`V` 或 `OF` 标志置 `1`。这不是另一套加法，而是复用已有的两根进位线，再接一个异或门。

若更容易从操作数看，也可以只使用三个最高位：令 `sa`、`sb`、`sr` 分别为 `a`、`b`、`r` 的符号位，则：

```text
signed_overflow_add = NOT(sa XOR sb) AND (sa XOR sr)
```

它表达的正是“两个操作数同号，而结果异号”。这条公式与 `c(n-1) XOR cn` 完全等价。

### 2. 两个容易混淆的例子

先看 `127 + 1`：

```text
  0111_1111    +127
+ 0000_0001      +1
-----------
  1000_0000    写回后按补码读为 -128

c7 = 1，c8 = 0，OF/V = 1，CF = 0
```

没有最高位外的进位，故**无符号** `127 + 1 = 128` 并未溢出；但 `OF/V = 1`，故**有符号**运算溢出。

再看 `-128 + -128`：

```text
  1000_0000    -128
+ 1000_0000    -128
-----------
1_0000_0000    写回 0000_0000

c7 = 0，c8 = 1，OF/V = 1，CF = 1
```

这一次两个判据都为真：无符号解释 `128 + 128 = 256` 放不下，有符号解释 `-128 + -128 = -256` 也放不下。不要因为这里两个标志恰好一致，就误以为它们始终等价。

相反，`-1 + 1` 的位运算会产生 `CF = 1`，但 `OF/V = 0`：无符号 `255 + 1` 溢出，有符号 `-1 + 1` 却正好为 0。

### 3. 有符号减法的符号规则

减法仍可被 ALU 改写为 `a + NOT b + 1`，所以硬件同样可用：

```text
signed_overflow_sub = c(n-1) XOR cn
```

若从符号直接判断，规则变为“异号相减却得到与被减数异号的结果”：

```text
signed_overflow_sub = (sa XOR sb) AND (sa XOR sr)
```

例如 8 位 `-128 - 1`：

```text
  1000_0000    -128
- 0000_0001      +1
-----------
  0111_1111    写回后为 +127
```

被减数为负、减数为正，数学结果应比 `-128` 更小，却回绕成正数，因此发生有符号溢出。另一方面，`0 - 1 = -1` 虽然对无符号数需要借位，却是完全正常的有符号结果。借位与有符号溢出仍是两件事。

## 五、CPU 如何把这些信号交给程序

加法器产生 `carry-out` 和溢出信号，并不意味着每条 ISA 都把它们保存成同样的寄存器，或在出现时自动中断。可将过程分成三层：

```text
ALU 计算低 n 位结果和内部信号
        ↓
ISA 规定：更新标志、忽略标志，还是触发异常
        ↓
程序或编译器：分支、检查、饱和处理或报告错误
```

### 1. x86：以标志寄存器公开两种信息

x86 的算术指令会更新 `RFLAGS` 中的多个位，其中最重要的是：

- `CF`（Carry Flag）：用于无符号加法的进位和无符号减法的借位；
- `OF`（Overflow Flag）：用于有符号补码溢出；
- `SF`：结果的符号位；
- `ZF`：结果是否为零。

因此，`jc`/`jnc` 一类条件跳转通常服务于无符号比较或多精度进位链，`jo`/`jno` 则检查有符号溢出。`adc` 会把旧的 `CF` 加入下一字，`sbb` 会把借位加入下一字；这使 64 位机器也能用多个机器字实现更宽的整数运算。

不过普通 `add` 只是在标志位中记录状态，通常不会因 `OF = 1` 自动抛异常。是否跳转、记录错误或改用饱和值，是后续指令和程序策略的责任。

### 2. ARM/AArch64：可选择更新 `N、Z、C、V`

在 ARM/AArch64 中，带 `S` 的算术指令（如 `ADDS`、`SUBS`）可更新条件标志：

- `N`：Negative，结果最高位；
- `Z`：Zero，结果是否为零；
- `C`：无符号加法的进位；减法时通常表示未借位；
- `V`：补码有符号溢出。

这里 `V` 与 x86 的 `OF` 职责相同。仍要注意，`C` 在减法中的“未借位”定义与 x86 的 `CF` 正好相反。名称相似并不能替你完成移植工作，这种偷懒很少会有好结局。

### 3. RISC-V：普通整数指令不保留通用标志位

RISC-V 的 `add`、`sub` 计算后直接写回低 XLEN 位，不设置像 `CF`、`OF`、`V` 这样的通用条件码。它并非不能判断溢出，而是把判断显式写成普通比较或更宽计算。

例如对无符号加法，得到 `r = a + b` 后，用 `sltu r, a` 可判断 `r < a`，也就是回绕是否发生。对有符号加法，可利用“同号相加、结果异号”的符号比较，或在有更宽临时类型时先扩展计算再比较范围。这样的设计避免了隐式全局标志的依赖，但需要额外指令。

所以“CPU 如何判断”还应问一句“哪一种 ISA 选择把判断结果怎样暴露给软件”。电路能力与指令集接口并不是同一层问题。

## 六、乘、除、移位的溢出不只靠一个加法标志

加减法的 `CF`/`OF` 规则最常用，却不能机械套到所有算术指令上。

### 1. 乘法：检查被截去的高半部分

两个 `n` 位数的完整乘积最多需要 `2n` 位。因此不少 ISA 提供“低半部分”和“高半部分”结果，或直接写入一对寄存器。

- 无符号乘法：高 `n` 位不全为 0，说明结果不能装入低 `n` 位；
- 有符号乘法：高 `n` 位不等于低 `n` 位符号位的重复扩展，说明结果不能装入 `n` 位补码。

例如 8 位有符号 `100 × 2 = 200`，低 8 位为 `1100_1000`，其符号位为 `1`；完整积的高 8 位却是 `0000_0000`，不等于应有的 `1111_1111` 符号扩展，所以溢出。

### 2. 除法：商是否可表示与除数是否为零

整数除法的主要异常是除数为 0。对有符号补码还存在一个边界：`INT_MIN / -1` 的数学结果是 `2^(n-1)`，比最大正数大 1，无法装入同宽有符号整数。不同 ISA 对这些情况可选择产生异常、返回规定值或交给软件处理；不能用加法的 `OF` 规则来推断。

### 3. 左移：被移出的位是否丢失了有效信息

无符号左移 `k` 位相当于乘以 `2^k`，当被移出最高端的位中有 `1` 时，结果不能在原宽度表示。对有符号数，除了不能丢失有效位外，结果的符号也必须合理；最稳妥的抽象判断是先以更宽精度计算，再检查是否落在目标范围。

当 `0 <= k < n` 时，`n` 位有符号数左移后可表示的必要且充分范围是：

```text
-2^(n-1-k) <= a <= 2^(n-1-k) - 1
```

实际指令对移位计数、标志位更新以及有符号语言表达式的语义可能不同。尤其在 C/C++ 中，不要把“硬件会截断”当作有符号左移一定可安全使用的理由。

## 七、写程序时如何选择正确的检查方式

硬件标志适合汇编、内核或编译器后端；业务代码更应该表达“我需要已检查的算术”这一意图。一个实用的选择表如下：

| 场景 | 合适做法 | 不应依赖的误解 |
| ---- | -------- | -------------- |
| 无符号加法 | 检查 `r < a`，或读取 ISA 的进位标志 | “结果是负数才算溢出” |
| 无符号减法 | 先检查 `a < b` | 把借位当成有符号溢出 |
| 有符号加减 | 使用语言的 checked API、编译器 builtin，或更宽类型计算 | 只看最终 `carry-out` |
| 乘法 | 使用双宽结果或先做范围检查 | 只检查低半部分的符号 |
| 跨平台汇编 | 查目标 ISA 对减法 `C/CF` 的精确定义 | 假定 ARM 与 x86 的借位标志同义 |

在 C/C++ 中，已发生的有符号溢出是未定义行为，因此不宜先写 `int r = a + b;` 再指望对 `r` 做事后补救。应使用编译器提供的 `__builtin_add_overflow` 等接口、明确的范围检查，或先转换到足够宽的类型。Java、Rust 等语言的回绕与检查 API 则各有明确规则，也应按语言规范和库 API 处理，而不是只凭某一款 CPU 的表现猜测。

## 八、总结

固定宽度的 ALU 总会写回低 `n` 位；它不会替程序保留无限精度的数学结果。但在加减法过程中，它能额外得到进位与符号关系，从而以很低成本判断范围是否被突破。

- **无符号加法**：最高位之外有进位，即 `cn = 1`，便溢出。
- **无符号减法**：`a < b` 时需要借位；各 ISA 对公开的借位标志极性可能不同。
- **有符号加法和减法**：进入、离开符号位的进位不同，即 `c(n-1) XOR cn = 1`，便溢出。
- `CF/C` 与 `OF/V` 分别回答无符号和有符号问题，绝不可互相替代。
- x86、ARM 会将这些信号公开为条件标志；RISC-V 普通整数指令不保存通用标志，而让软件用比较或更宽计算显式判断。
- 乘、除、移位要按各自的完整结果与 ISA 规则处理，不能拿加法标志硬套。

一旦把“位运算结果”和“采用何种数值解释”分开，溢出判断就不再是需要死记的零散口诀，而是加法器结构与表示范围共同给出的必然结论。
