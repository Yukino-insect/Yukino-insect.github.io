当只有一个 CPU 核，却有多个进程都处于可运行状态时，操作系统可以采用时间片轮转（Round Robin）调度：进程运行一小段时间，时间片耗尽后暂停，再让下一个进程运行。

这时经常会出现一个直觉上的疑问：**CPU 从进程 A 切到进程 B 时，Cache 里还留着 A 的数据，B 会不会读错？操作系统是不是必须把 Cache 清空？**

先给结论：**普通的进程切换通常不会把整个数据 Cache 清空。**现代 Cache 通常使用物理地址或带有足够物理地址信息的标记来识别缓存行，因此不同进程即使使用相同的虚拟地址，只要它们映射到不同的物理页，Cache 也能把它们区分开。进程切换真正需要重点处理的是 CPU 寄存器、页表和 TLB；Cache 一般保留原内容，但新进程可能因为工作集不同而产生大量 Cache miss，这就是缓存污染和重新预热。

本文以单核 CPU 上的轮询调度为主，再补充多核和安全场景中的差异。

## 一、轮询调度时，CPU 到底切换了什么

假设进程 A 和进程 B 都可以运行，时间片长度为 10 ms。一个简化的调度过程如下：

```text
进程 A 运行 10 ms
  -> 时钟中断
  -> 内核保存 A 的寄存器和内核栈状态
  -> 调度器选择进程 B
  -> 切换到 B 的地址空间
  -> 恢复 B 的寄存器
进程 B 继续运行 10 ms
```

切换时通常需要保存或恢复：

- 程序计数器、栈指针和通用寄存器；
- 浮点、SIMD 或向量寄存器状态（是否立即保存取决于系统实现）；
- 当前进程的内核栈和调度状态；
- 下一进程使用的页表根或地址空间标识。

这里要注意，**进程切换不是把整台 CPU 恢复成某个进程专属的“快照”**。Cache、分支预测器、预取器等微架构状态，通常不会像通用寄存器那样为每个进程保存一份并在切换时完整恢复。它们更像是处理器上的共享工作区，会随着后续访问逐渐改变。

## 二、Cache 里没有“进程 A 的抽屉”

Cache 的基本管理单位是缓存行。缓存行除了数据，还保存有效位、标记（tag）和可能的脏位、一致性状态等信息。控制器用地址中的一部分选择组，再比较 tag，判断当前请求是否命中。

在常见的物理标记设计中，Cache 识别的是**物理内存块**，而不是“某个进程的虚拟地址”。可以把它抽象成：

```text
进程 A 的虚拟地址 0x4000 -> 物理地址 0x1204000 -> Cache 行 X
进程 B 的虚拟地址 0x4000 -> 物理地址 0x8904000 -> Cache 行 Y
```

虽然两个进程看到的虚拟地址都是 `0x4000`，但物理地址不同，Cache tag 也不同，所以不会把 A 的内容误当成 B 的内容。

反过来，如果 A 和 B 通过共享内存映射到了同一个物理页，那么它们访问的本来就是同一份数据。此时 Cache 中可能只有一份对应的物理缓存行，或者在多核场景下存在多个副本；这属于共享内存和缓存一致性问题，不是进程切换导致的“串数据”。

### 1. 虚拟地址相同，不代表数据相同

进程隔离主要依靠页表和权限位完成。一次 load/store 至少要经过这样的逻辑：

```text
虚拟地址
  -> TLB 查询或页表遍历
  -> 得到物理地址并检查权限
  -> 用物理地址相关信息查询 Cache
  -> 命中则返回数据，未命中则向下一级请求缓存行
```

因此，Cache 不是进程隔离的主要边界，页表才是。Cache 保留 A 的行，并不表示 B 可以绕过页表直接读取它；B 只能通过自己的虚拟地址和页表映射访问允许访问的物理内存。

## 三、从 A 切到 B 时，Cache 通常发生什么

下面按一次轮询切换拆开看。

### 1. 进程 A 的热点数据暂时留在 Cache

A 运行期间，循环变量、代码指令和最近访问的数组可能位于 L1、L2 或共享 LLC 中。时间片到期后，这些缓存行通常不会立即消失，仍然占据原来的组和路。

### 2. 调度器切换地址空间和寄存器

内核选择 B 后，会让 CPU 使用 B 的页表根或地址空间标识，并恢复 B 的执行现场。TLB 可能需要失效一部分旧翻译，也可能借助 ASID/PCID 等机制保留不同地址空间的翻译。

这里的“失效 TLB”与“清空 Cache”是两件事：TLB 缓存的是虚拟页到物理页的翻译，Cache 缓存的是指令或数据本身。

### 3. B 第一次访问自己的工作集

B 开始执行后，如果它访问的代码和数据不在 Cache 中，就会发生 Cache miss：

1. 先在 L1 指令或数据 Cache 中查找；
2. 未命中则继续查 L2、LLC；
3. 更下层命中时，把缓存行填回上层；
4. 所有层都未命中时，才需要访问内存控制器和 DRAM。

B 加载自己的数据时，新的缓存行会逐渐挤出 A 的缓存行。这个过程不是一次“清空”，而是由正常的组相联置换策略完成。若时间片很短，A 和 B 每次回来都可能重新加载各自的热点数据，命中率就会下降。

### 4. A 再次获得 CPU

当 A 下一轮运行时，情况可能分为三种：

- A 的热点行还没有被 B 挤出，访问仍然命中；
- 只有部分热点行保留，命中率和性能介于两者之间；
- B 的工作集与 A 冲突严重，A 的热点行大多被替换，只能重新预热。

所以轮询调度的 Cache 成本，通常表现为**切换之后的一段时间变慢**，而不是调度器执行某条指令时突然花费大量时间清空缓存。

## 四、为什么进程切换可能比线程切换更伤 Cache

同一进程的线程共享地址空间，但仍然共享所在 CPU 核的 L1/L2 Cache。线程之间如果访问相近的数据，可能互相受益；如果访问完全不同的大工作集，也可能互相驱逐缓存行。

不同进程除了可能使用不同的代码和数据，还通常拥有不同的页表，因此进程切换更容易同时带来：

- 地址空间切换和 TLB 命中率下降；
- 指令 Cache、数据 Cache 的局部性被破坏；
- 分支预测历史和预取器训练效果变差；
- 跨 CPU 核迁移时，原核心的私有 Cache 无法直接复用。

这也是“线程切换通常比进程切换轻”不能简单理解为“线程切换没有 Cache 成本”的原因。两者都可能污染 Cache，只是进程切换通常还叠加了地址翻译方面的成本。

## 五、操作系统什么时候真的需要处理 Cache

### 1. 普通用户进程切换：通常不全量清空

在现代通用 CPU 上，普通的用户进程轮换通常不会执行“清空所有 L1/L2/LLC”的操作。全量清空代价很高，会让每个进程重新从更低层存储加载代码和数据，吞吐量明显下降。

只要硬件的地址标记、权限检查和一致性机制正常工作，保留旧缓存行并不会破坏进程隔离。

### 2. 地址空间或缓存设计的特殊情况

某些架构、某些旧式 Cache 设计或特定的地址别名问题，可能要求操作系统在切换页表、修改映射或回收页面时执行局部失效、写回或同步。具体动作取决于处理器的 Cache 体系结构，不能把某一种架构的做法当成所有 CPU 的通用规则。

### 3. 设备 DMA 与非一致性 Cache

如果设备通过 DMA 直接读写内存，而 CPU Cache 与设备之间不是硬件一致的，驱动程序可能需要在提交 DMA 前后执行 Cache 写回、失效或内存屏障。这个问题是 CPU 与设备共享内存的一致性问题，不是轮询调度多个用户进程时每次都要做的动作。

### 4. 安全隔离场景

Cache 虽然通常不承担进程的正确性隔离，却可能留下可观测的访问痕迹。恶意进程可以通过测量访问时间，推测另一个进程是否访问过某些缓存行，这类问题属于 Cache side channel（缓存侧信道）。

在虚拟机、不同安全域、密码学代码或内核防护场景中，系统可能采用更严格的措施，例如：

- 在特定边界执行 L1D 等缓存的局部清理；
- 限制或分区 LLC 的使用；
- 使用页面着色、Cache way 分配或硬件 QoS 做资源隔离；
- 改变调度策略，避免高风险工作负载紧邻运行。

这些措施是为了降低信息泄露或资源争用，不代表普通进程切换的基本机制发生了改变。

## 六、时间片长度为什么会影响 Cache 命中率

时间片并不是越短越好。时间片过短，系统响应会更及时，但每个进程还没来得及充分利用刚预热的 Cache，就又被切走；时间片过长，Cache 局部性更好，却可能让交互任务等待更久。

可以用一个简化模型理解：

```text
时间片太短
  -> 切换频繁
  -> TLB / Cache / 分支预测器反复预热
  -> 调度开销和缓存 miss 增加

时间片适中
  -> 每次运行足够久以利用局部性
  -> 仍能在可接受时间内响应其他任务

时间片太长
  -> 缓存局部性较好
  -> 交互任务和低优先级任务等待时间增加
```

真实调度器不会只看 Cache，还要综合优先级、交互性、负载均衡、功耗和实时性。工程上更有价值的做法，是通过性能计数器观察 `cache-misses`、`cache-references`、TLB miss、上下文切换次数和任务迁移次数，而不是凭感觉猜测“是不是 Cache 被清空了”。

## 七、一个具体例子：两个进程轮流扫描数组

假设 A 和 B 都按顺序扫描一个远大于 L1 Cache 的数组：

```text
A: a[0], a[1], a[2], ...
B: b[0], b[1], b[2], ...
```

若两个数组映射到的缓存组高度冲突，且时间片只允许每个进程扫描很小一段，那么可能出现：

1. A 把一批 `a` 的缓存行加载到 Cache；
2. 时间片结束，B 加载 `b` 的缓存行并逐渐驱逐 `a`；
3. A 再次运行时，刚才的 `a` 行已经不在近层 Cache，只能重新加载；
4. 循环往复，内存带宽和 Cache miss 成为主要瓶颈。

如果把时间片调大，让每个进程在一次调度周期内处理更多连续数据，或者减少两个工作集之间的组冲突，命中率和有效吞吐量可能改善。反过来，简单地增加线程或进程数量，并不能自动提高并行度；在单核 CPU 上，它们只会增加轮换和缓存竞争。

## 八、几个常见误解

### 误解一：进程切换必须清空 Cache，否则会读到别人的数据

不对。Cache 命中前仍要经过地址翻译和 tag 检查。不同进程映射到不同物理页时，对应的是不同缓存行；缓存保留旧行不会绕过页表权限。

### 误解二：TLB 清空就等于 Cache 清空

不对。TLB 保存地址翻译，Cache 保存指令和数据副本。切换地址空间时可能影响 TLB，但通常不会因此把所有 Cache 行删除。

### 误解三：Cache 里标记了进程 ID

通常不能这样理解。常见实现主要依靠物理地址相关的 index/tag 和一致性状态来识别缓存行，而不是给每一行加一个软件意义上的进程编号。具体实现仍取决于架构和微架构。

### 误解四：Cache 没清空，所以进程之间没有隔离

不对。正确性隔离由页表、权限检查、异常机制和内核控制完成。Cache 的残留状态可能造成性能影响或侧信道风险，但不是普通 load/store 绕过页表的通道。

## 总结

- 轮询调度切换的是寄存器、执行现场和地址空间上下文，不是为每个进程保存一份完整的 Cache 快照。
- 普通进程切换通常不会全量清空 Cache；旧进程的缓存行会保留，并在新进程访问时逐渐被置换。
- 不同进程使用相同虚拟地址时，硬件通过物理地址相关的 tag 区分不同数据；共享同一物理页时，访问的本来就是共享数据。
- Cache miss、TLB miss、缺页异常和上下文切换是不同事件，可能在一次切换后的访问中连续出现，但不能混为一谈。
- 时间片越短，响应性通常越好，却越容易造成缓存重新预热和调度开销；应结合工作集、负载和性能计数器选择策略。
- 安全敏感场景可能额外清理或分区 Cache，这是为了降低侧信道与资源争用风险，不是普通轮询调度的必要步骤。
