整数是最容易让人产生“比特就是数”错觉的数据类型。实际上，必须先约定每一位的权重以及最高位是否承担符号意义，机器才能把比特解释成数。

## 无符号整数：位权相加

对一个 4 位无符号数 $b_3b_2b_1b_0$，数值定义为：

$$
N = b_3 2^3 + b_2 2^2 + b_1 2^1 + b_0 2^0
$$

例如 `1011` 表示 $1×8+0×4+1×2+1×1=11$。4 位最多表示 $0$ 到 $15$，因为一共有 $2^4$ 种组合。

## 补码：让加法器复用

现代有符号整数通常使用补码。$w$ 位补码的数值可以写成：

$$
N=-b_{w-1}2^{w-1}+\sum_{i=0}^{w-2}b_i2^i
$$

以 8 位为例，`11111111` 的值为 $-128+127=-1$，`10000000` 的值为 $-128$。范围是 $-2^7$ 到 $2^7-1$，负数比正数多一个，因为 0 占用了正数一侧的一个编码。

补码的关键优势是：加法不必区分正数和负数。8 位 `3 + (-1)` 即：

```text
00000011
+11111111
---------
00000010   （最高位进位丢弃）
```

同一个二进制加法器就能完成这两种情况。减法也可以改写为加上减数的补码。

## 符号扩展与截断

把 8 位有符号数 `11111111` 扩展成 16 位时，新增高位必须补 1，得到 `1111111111111111`，数值仍是 -1，这叫**符号扩展**。无符号数则补 0。

反过来把更宽的整数截断成低 8 位，相当于对 $2^8$ 取模。`257` 的二进制低 8 位是 `00000001`，因此转换为 `uint8_t` 后得到 1；这不是“数值仍然是 257”，而是一次明确的模运算。

## 溢出不是进位本身

无符号加法溢出可以用模 $2^w$ 解释。例如 8 位 `255 + 1` 得到 0，同时产生进位标志。对于有符号补码，溢出发生在“两个同号数相加得到异号结果”时：`127 + 1` 的位模式为 `10000000`，按补码解释是 -128。

CPU 的 ALU 会产生进位、零、负数、溢出等状态标志。编译器可以根据语言规则检查或忽略这些标志：C 的无符号溢出是定义好的模运算，而有符号溢出属于未定义行为；Java 的整数运算则按固定宽度丢弃高位。

## 最小实验：观察不同语言的边界

```java
public class OverflowDemo {
    public static void main(String[] args) {
        int x = Integer.MAX_VALUE;
        System.out.println(x + 1); // -2147483648
    }
}
```

Java 保留 32 位结果的低位，因此输出最小负数。若业务需要检测边界，应在相加前检查，或使用 `Math.addExact` 让运行时在溢出时抛出异常。

## 类型转换为何重要

表达式中的整数可能先被提升：`int8_t` 相加通常会先转换为 `int`，再执行加法；把有符号值与无符号值混算还可能触发意外的无符号比较。调试这类问题时，应该同时打印十进制值、十六进制位模式和实际类型，而不能只看一种输出。

## 语言不会共享同一种“溢出”

硬件只会产生固定宽度的低 $w$ 位和一些状态；语言才决定程序是否可继续依赖这个结果。把硬件行为和语言语义混成一句“溢出会回绕”，是许多跨语言移植错误的来源。

| 环境 | 无符号溢出 | 有符号整数溢出 | 实用做法 |
| --- | --- | --- | --- |
| C / C++ | 按模 $2^w$ 定义 | 通常是未定义行为，优化器可据此重排推理 | 先检查范围，或使用编译器的 checked intrinsic / 更宽类型 |
| Java | 提供无符号辅助 API | `byte`/`short`/`int`/`long` 按固定宽度回绕 | 金额/计数用范围检查或 `Math.addExact` |
| Rust | 提供 `wrapping_*`、`checked_*`、`saturating_*` 等明确 API | 不应依赖隐式结果 | 选择能表达业务意图的显式方法 |
| Python | `int` 自动扩展，不会因机器字长回绕 | 同左 | 与 C/数据库/协议交互时显式验证位宽与范围 |

例如 `INT_MIN` 的绝对值是一个经典边界。32 位补码的最小值是 `-2147483648`，但同宽最大正数只有 `2147483647`；因此在同一 `int` 中计算 `-INT_MIN` 没有可表示的正结果。若代码需要“绝对值”，应先处理这个特例、改用更宽类型，或把结果接口定义为无符号/大整数。仅仅写 `abs(x)` 并不会让数学范围变大。

## 端序不是补码的一部分

补码规定一个**位模式如何表示有符号数**；字节序规定多字节模式在内存、文件或网络中按什么顺序放置。两件事经常同时出现，却完全独立。

以 32 位十六进制位模式 `0x12345678` 为例：

```text
大端（网络字节序）：12 34 56 78
小端（常见 x86 内存）：78 56 34 12
```

如果接收端把小端四字节按大端读取，会得到 `0x78563412`；它不是“补码被解错了”，而是字段边界正确、字节排列错误。二进制协议必须指定 `uint32`/`int32`、字节序、长度以及是否允许缺失，不能只写“传一个 int”。

## 如何写出可验证的边界转换

下面的 Python 函数把一个非负数学整数编码为 4 字节大端无符号字段，再严格解码。`to_bytes` 的 `signed`、长度和 `byteorder` 都是协议的一部分：

```python
def encode_u32_be(value: int) -> bytes:
    if not 0 <= value <= 0xFFFF_FFFF:
        raise ValueError("value 不在 uint32 范围内")
    return value.to_bytes(4, byteorder="big", signed=False)

payload = encode_u32_be(0x1234_5678)
print(payload.hex(" "))                 # 12 34 56 78
print(int.from_bytes(payload, "big"))   # 305419896
```

协议转换的正确顺序是“验证数学值范围 → 按字段编码 → 在另一端按同一字段解码”。不要先把一个负数强制转换为无符号数、看见一个很大的正数后再猜它原来是不是 `-1`；那样只是在放弃类型信息后尝试补救。

## 小结

- 无符号整数是位权之和；补码通过给最高位负权重表示有符号整数。
- ALU 执行的是固定宽度的位运算，语言决定如何解释溢出。
- 符号扩展、截断和整数提升是跨类型计算中最常见的边界。
- 补码、端序和语言溢出语义是三层不同约定；二进制协议应把它们逐项写明。
