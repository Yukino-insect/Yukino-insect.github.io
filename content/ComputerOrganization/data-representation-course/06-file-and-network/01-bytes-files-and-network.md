字符串从程序进入文件或网络时，必须经过“文本 → 编码 → 字节”的转换；回来时再执行相反过程。真正可靠的设计，不是让每一层都猜编码，而是在边界处明确约定。

## 文件写入链路

应用调用 `write` 或高级语言的文件 API，库先把文本编码成字节，再把字节交给内核。内核通过文件描述符找到打开文件对象，文件系统把数据放入页缓存并安排写回，块层和驱动把请求提交给存储设备。`fsync` 等接口用于要求数据进一步落到稳定介质，但具体持久性语义仍受文件系统和设备缓存影响。

```text
字符串
  -> 编码器（例如 UTF-8）
  -> 用户态字节缓冲区
  -> write 系统调用
  -> 内核页缓存 / 文件系统
  -> 块设备与存储介质
```

文件系统只认识字节和元数据（名称、权限、长度、时间等）。即使文件名看起来是中文，内核也只是保存文件名的字节序列；具体如何显示由操作系统和桌面环境决定。

## 网络传输链路

应用协议把消息序列化为字节，例如 JSON 使用 UTF-8，Protobuf 使用字段编号和变长整数。TCP 将这些字节切分成报文段并保证可靠有序传输；它不理解字符、JSON 或消息边界。接收端必须依据协议中的长度字段、分隔符或帧格式重新组装消息。

```text
对象 / 文本
  -> 序列化与字符编码
  -> TCP 字节流或 UDP 数据报
  -> 网卡、驱动、协议栈
  -> 接收端重新组帧
  -> 解码与反序列化
```

一次 `recv` 不一定对应一次 `send`：TCP 是字节流，可能拆包也可能粘包。应用协议若没有明确长度或分隔规则，就无法可靠判断一条消息在哪里结束。

## 乱码与数据损坏的区别

如果字节在传输中被修改，通常是校验失败、解码异常或数据校验不一致；如果字节没有改变，却用错误编码解释，就会出现乱码。排查时应先记录十六进制字节，再确认发送端编码、协议声明、接收端解码和数据库连接设置，而不要直接修改字体或“多试几个编码”。

## 一个安全的文本边界示例

```python
from pathlib import Path

message = "温度：25℃"
path = Path("message.txt")

# 在边界处明确编码
path.write_text(message, encoding="utf-8")
restored = path.read_text(encoding="utf-8")
assert restored == message
```

二进制协议也应明确端序和字段宽度。例如网络字节序通常采用大端序，不能直接把本机结构体内存强行发送出去，因为结构体可能包含填充字节、不同端序和不同 ABI 布局。

## 小结

- 文件和网络的底层都是字节序列，文本只是带有编码约定的字节。
- 系统调用、文件系统、TCP 和网卡负责搬运或保存，不负责猜测业务类型。
- 在 I/O 边界明确编码、长度、端序和校验，才能把“类型”安全地跨进程、跨机器传递。
