前一篇已经把 Unicode 码点和 UTF-8 字节分开了。本篇把这条知识放进真实工程链路：编辑器、HTTP、消息队列、数据库驱动和导入脚本都在交接**字节**。所谓乱码并不是“中文显示得不好看”，而是某一端用错误规则把同一批字节解码，或者已经把错误解码后的文本再次编码并写回。

核心结论很朴素：**文本在边界处必须从 Unicode 文本编码为明确的字节序列；另一端必须用同一个约定解码。**编码名、字节、声明和实际实现四者只要有一个不一致，系统就开始猜测。让机器猜含义，大概和让人猜需求一样，通常不会有圆满结局。

## 一、先用一条数据链路定位问题

以用户昵称 `雪乃😀` 为例。程序内存中的文本是两个 Unicode 码点序列；采用 UTF-8 时，传输/保存的字节为：

```text
雪       乃       😀
U+96EA  U+4E43  U+1F600
E9 9B AA  E4 B9 83  F0 9F 98 80
```

它经过一个服务时，正确的链路应是：

```text
Unicode 文本
  -> UTF-8 编码
  -> HTTP / Kafka / 文件 / 数据库中的字节
  -> UTF-8 解码
  -> Unicode 文本
```

这里的“Unicode 文本”是编程语言给你的字符抽象；并不是磁盘、TCP 或数据库页里天然存在的东西。每一条边界都应回答下面四个问题：

- 发送端选择了什么编码？
- 实际字节是什么？
- 协议、文件头或连接参数有没有声明编码？
- 接收端是否真的按该声明解码？

最后一问往往最不体面，也最关键。仅在文档中写“统一 UTF-8”并不会改变某个遗留导出程序实际写出的 GBK 字节。

## 二、乱码、替换字符和数据损坏不是同一件事

先把症状分类，排查会快很多：

| 现象 | 字节是否改变 | 常见原因 | 能否靠改显示设置恢复 |
| --- | --- | --- | --- |
| `ä¸­æ–‡` 之类的乱码 | 通常未改变 | UTF-8 字节被按单字节编码解码 | 可以，只要还能取得原始字节 |
| `�`（U+FFFD） | 可能尚未写回 | 严格解码器发现非法字节并替换 | 取决于原字节是否仍在 |
| `?` 或字段被截断 | 往往已改变 | 目标字符集不支持、长度按字节限制 | 常常不可逆 |
| 字符看着相同却查不到 | 文本码点不同 | Unicode 规范化形式不同 | 可以通过规范化和重建索引处理 |

### 1. 典型的错解码：UTF-8 被当作 Latin-1

汉字“中”的 UTF-8 是 `E4 B8 AD`。Latin-1 会把每一个字节直接映射成一个字符，因此得到 `ä¸­`。若你仍然保存着这三个字符，而它们最初是按 Latin-1 错解得到的，可逆恢复过程是：先按 Latin-1 取回原字节，再按 UTF-8 解码。

```python
broken = "ä¸­"
fixed = broken.encode("latin-1").decode("utf-8")
print(fixed)  # 中
```

这段程序绝不是“乱码万能修复器”。它只在错误路径确实是 `UTF-8 bytes -> Latin-1 decode`，并且中间没有丢字节时成立。若源头是 GBK、发生了两次错转码，或 `�` 已被持久化，照抄只会再制造一层损坏。

### 2. 为什么 `�` 是危险信号

UTF-8 规定续字节必须以 `10` 开头，并禁止过长编码等非法序列。严格解码失败时，很多库为了继续显示会放入替换字符 U+FFFD，即 `�`。这时显示层的“文本”已经不再保留原始非法字节的信息；把它重新写入数据库，就等于用 `EF BF BD` 覆盖证据。

因此导入、迁移和消费程序应优先采用**严格解码**并记录失败位置，而不是默认 `errors="replace"`。后者适合面向人的日志兜底，不适合数据修复管道。

```python
raw = b"name=\xe4\xb8\xad\xff"

try:
    print(raw.decode("utf-8", errors="strict"))
except UnicodeDecodeError as error:
    print(error.start, error.end, raw.hex(" "))
    # 3 4 6e 61 6d 65 3d e4 b8 ad ff
```

异常位置与十六进制字节才是排查依据。截图、肉眼和“换一种字体看看”都不是。

## 三、特殊字符暴露了“长度”的多种含义

`A中😀` 看似三个字符，但不同层的长度并不相同：

| 度量单位 | `A中😀` 在 UTF-8 中的长度 | 为什么不同 |
| --- | ---: | --- |
| Unicode 码点 | 3 | `A`、`中`、`😀` 各一个码点 |
| UTF-8 字节 | 8 | 分别占 1、3、4 字节 |
| Java/JavaScript UTF-16 代码单元 | 4 | `😀` 需要一对代理项 |
| 用户感知字符（字素簇） | 常为 3 | 仍需考虑组合音标、ZWJ 序列等 |

下面的 Python 例子直接把“字符”和“字节”分开观察：

```python
text = "A中😀"
payload = text.encode("utf-8")

print(len(text))       # 3：Python str 的 Unicode 码点数量
print(len(payload))    # 8：UTF-8 字节数
print(payload.hex(" "))  # 41 e4 b8 ad f0 9f 98 80
```

不要把这个结果照搬到 Java 或 JavaScript：二者常把字符串索引、`length` 建立在 UTF-16 代码单元上，单个非 BMP 表情会占 2。C/C++ 的 `std::string` 则通常只是带长度的 `char` 字节容器；若装的是 UTF-8，`size()` 返回字节数，不会突然理解汉字或表情。

### 1. 组合字符和规范化

视觉上相同的 `é` 可以是一个预组合码点 U+00E9，也可以是 `e`（U+0065）加组合重音 U+0301。它们的 UTF-8 字节不同，逐字节比较、哈希、唯一索引或登录名查重都可能把它们当成不同值。

```text
é        -> U+00E9          -> C3 A9
e + ◌́   -> U+0065 U+0301   -> 65 CC 81
```

Unicode 规范化（常见为 NFC/NFD）用于把等价文本归约到约定形式。它是业务规则的一部分：标识符、搜索、去重可以在写入前按 NFC 规范化；密码和二进制签名却不能擅自规范化，因为任何码点变化都会改变凭据或验签结果。更不要把“大小写不敏感”“去重音”和 Unicode 规范化混为一谈，它们是三套不同规则。

### 2. 零宽字符、全角字符和不可见空白

复制粘贴的文本还可能含有不换行空格 U+00A0、零宽空格 U+200B、全角空格 U+3000 或方向控制符。它们不是乱码，而是合法码点；危险在于 UI 可能看不出来，比较和数据库唯一约束却看得很清楚。

对业务标识符应明确允许的字符集，例如只允许 ASCII 小写字母、数字和连字符；对自由文本则不应粗暴“过滤所有非 ASCII”。清洗前先记录码点和来源，才不会以修复之名删掉用户的真实姓名。

## 四、数据库迁移时到底有哪些编码契约

一次导库至少涉及五处契约：源库的数据编码/排序规则、导出文件编码、导入程序解码、数据库驱动连接编码、目标库与列的字符能力。它们不是一个名为“charset”的开关能概括的。

```text
源库文本
  -> 导出工具写出的字节（文件编码）
  -> 导入程序 decode
  -> 驱动按连接编码发送参数
  -> 目标列的字符集/排序规则与长度限制
  -> 客户端按连接编码读取
```

### 1. MySQL：`utf8` 与 `utf8mb4` 不是同一个容量承诺

在 MySQL 的历史命名中，`utf8` 通常指最多 3 字节的 UTF-8 变体，不能存储 U+10000 及以上码点，例如许多表情；`utf8mb4` 才覆盖标准 UTF-8 的 1 到 4 字节序列。数据库、表、列和连接都有可能各自配置字符集，排序/比较还受 collation 影响。

若旧字段是三字节 `utf8`，插入 `😀` 可能报错、被替换为 `?`，或因非严格 SQL 模式发生截断。迁移前不能只把建表语句里的一处 `utf8` 改成 `utf8mb4`；还要确认连接协商、导出工具、客户端和索引长度预算。索引按字节计费，四字节编码会改变旧版本或受限索引下的可用前缀长度。

### 2. PostgreSQL 与 SQL Server：约束位置不同

PostgreSQL 的数据库创建时会确定编码，常见为 `UTF8`；客户端与服务器之间还存在 `client_encoding`。因此导入脚本用错误编码读取 CSV，即使目标数据库是 UTF8，也会在进入服务器前把文本读错。

SQL Server 的 `varchar` 和 `nvarchar` 代表的语义不同：`nvarchar` 用 Unicode（UTF-16 代码单元）保存，而 `varchar` 的解释受排序规则/代码页或 UTF-8 collation 等配置影响。跨库迁移时不能仅凭列名都是 `name` 就当作同一文本合同；需审计每个列的类型、collation、最大长度以及驱动参数类型。

这些细节随数据库版本与部署配置而变化。可迁移的原则是：**先检查实际 schema 和连接协商，再选择导入工具参数；不要根据“我们的库理论上是 UTF-8”推断每一跳都正确。**

## 五、一个可执行的迁移前验收脚本

下面的例子不依赖具体数据库。它用一个 UTF-8 CSV 文件模拟导出物，严格读取、验证关键样本，并同时统计字符数和字节数。真实迁移时，可把 `rows` 换成数据库游标返回的文本列；不要让驱动在未知编码下把原始字节悄悄替你替换掉。

```python
from pathlib import Path
import unicodedata

source = Path("users.csv")

def inspect(label: str, value: str) -> None:
    utf8 = value.encode("utf-8")
    code_points = " ".join(f"U+{ord(ch):04X}" for ch in value)
    print(f"{label}: {value!r}")
    print(f"  code points: {code_points}")
    print(f"  utf-8 bytes: {utf8.hex(' ')}")
    print(f"  chars={len(value)}, utf8_bytes={len(utf8)}")

for line_number, raw_line in enumerate(source.read_bytes().splitlines(), start=1):
    # 严格 decode：不把非法字节伪装成 U+FFFD 后继续导入。
    text = raw_line.decode("utf-8", errors="strict")
    normalized = unicodedata.normalize("NFC", text)

    if "\ufffd" in normalized:
        raise ValueError(f"line {line_number}: 发现替换字符，必须回到原始导出物排查")

    if len(normalized.encode("utf-8")) > 255:
        raise ValueError(f"line {line_number}: UTF-8 字节长度超过目标字段预算")

    inspect(f"line {line_number}", normalized)
```

这个脚本中的 `255` 只是示例预算，不是 Unicode 的限制。目标列若定义为“最多 255 个字符”，数据库究竟按字符、代码单元还是字节计量，要由其类型与版本决定；索引另有自己的长度规则。迁移前应选取中文、emoji、组合音标、带零宽字符的样本，端到端写入再读回，比较码点和 UTF-8 字节而不只是肉眼看起来相同。

## 六、迁移与接口排错的顺序

遇到问题时按数据流从外向内检查，比随机改 `charset` 高效得多：

1. **冻结证据**：保留源文件/源库备份，导出出问题行的原始字节十六进制；不要先用编辑器另存。
2. **确认源头**：导出工具实际使用的编码是什么？文件是否有 BOM？声明是否可靠？
3. **严格解码**：导入端以预期编码严格解析；失败时记录偏移、样本主键和原始字节。
4. **审计连接**：检查驱动参数、会话级连接编码、HTTP `Content-Type` 或消息 schema，而不是只检查服务端默认值。
5. **核对目标能力**：列字符集、collation、最大长度、索引、严格模式和不可表示字符的处理策略。
6. **端到端回读**：按码点、字节和业务比较规则验证迁移后数据；仅截图验收无法发现规范化或隐藏字符问题。

如果已经发生了错误转码，先在隔离副本上用一小批有已知正确值的记录验证“错误路径假设”。确认能完全逆转后才批量修复，并保留修复前后的字节审计。没有原始字节或可靠备份时，声称可以百分之百还原通常只是把不确定性写得很有自信而已。

## 七、总结

- Unicode 定义码点，UTF-8 定义字节；文件、网络和数据库交接的是后者。
- 乱码是错误解码，替换字符和 `?` 常意味着数据已丢失；三者的修复可能性不同。
- “一个字符”可能对应不同数量的 UTF-8 字节、UTF-16 代码单元和用户感知字符，字段与索引长度必须选对度量。
- NFC/NFD、零宽字符和 emoji 会让“看起来相同”的文本在比较、索引和迁移时变得不同；是否规范化必须由业务契约决定。
- 数据迁移要同时验证文件、导入程序、连接、schema 和回读结果；以十六进制字节与严格解码作为证据，而不是依赖肉眼判断。
