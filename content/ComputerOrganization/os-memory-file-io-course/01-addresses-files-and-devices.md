“虚拟内存管理内存映射，文件系统组织磁盘空间；那么 CPU 怎样操作文件所在的磁盘空间？”这个提问的出发点是正确的，但其中的“映射”至少指三件不同的事。先把它们拆开，后面的 `read`、`mmap` 和缺页才不会互相矛盾。

## 一、CPU 的普通指令只读写内存

CPU 执行一条 load/store 指令时，指令携带的是一个**虚拟地址**。MMU 用当前进程的页表把虚拟页号翻译为物理页框号，页内偏移保持不变；随后 CPU 经由 Cache 和内存控制器读写 RAM。

```text
load/store 的虚拟地址
  -> TLB 或页表
  -> RAM 物理地址
  -> Cache / DRAM
```

这个地址不是文件偏移，也不是磁盘块号。即使源代码写着 `buffer[0]`，CPU 也不会先询问“这个字节属于哪个文件”；它只看到一个有效地址并按页表与权限完成内存访问。

一些设备寄存器可以采用内存映射 I/O（MMIO），因而 CPU 的 load/store 也能读写控制器寄存器。但寄存器的含义是“提交命令、写队列门铃、读取状态”等，**不是把任意磁盘 LBA 当成一段可直接寻址的 RAM**。真正的大块传输通常由设备 DMA 完成，见第 3 篇。

## 二、虚拟内存管理什么，又不管理什么

虚拟内存的对象是**一个地址空间中的页**。它负责：

- 虚拟页能否读取、写入或执行；
- 虚拟页当前映射到哪个物理页框；
- 缺页时能否为它找到后备来源，或者判定访问非法；
- 多个虚拟映射怎样共享同一物理页，以及何时回收物理页。

对匿名内存（堆、栈、许多 `malloc` 数据）而言，页面初次写入时通常获得一个新的物理页；必要时可被换出到 swap。对文件映射而言，页面的后备来源是某个文件的某个偏移。无论来源是什么，CPU 真正执行时面对的仍是“虚拟页 -> 物理页框”。

因此以下说法需要修正：

> 虚拟内存把用户的一块内存与磁盘中的文件空间一一映射，所以所有读取都从这块映射内存取得。

只有 `mmap` 或可执行文件按需装载等情形会建立这样的进程虚拟映射。普通 `read` 不需要把文件映射到调用者的地址空间；它通常让内核从页缓存复制字节到调用者传入的用户缓冲区。虚拟内存为两种路径都提供 RAM 页和保护边界，但不替文件系统维护“这个文件占哪些块”。

## 三、文件系统管理什么

文件系统把原始块设备组织成可命名、可共享、可恢复的对象。它要维护至少四类关系：

```text
路径分量
  -> 目录项中的名称 -> 文件标识（如 inode/MFT 记录）
  -> 文件偏移 -> extent / 分配表
  -> 分区中的设备 LBA 范围
```

其中路径是人和程序的名字；文件偏移是“该文件第 N 个字节”；LBA 是主机提交给块设备的逻辑位置。每一箭头都由目录、文件元数据或分区/块层信息回答。文件系统还维护权限、长度、链接计数、空闲空间、日志和崩溃恢复，这些都不是页表的职责。

“没有文件系统，磁盘就无法利用”也要略作限定。没有文件系统时，磁盘仍可作为**裸块设备**使用：数据库、交换区、某些虚拟机镜像或自定义存储引擎都可以自行管理块。只是普通用户无法再用路径、目录和文件名方便地组织数据，而应用必须自己承担分配、索引、崩溃恢复等工作。文件系统并非让磁盘能通电的前提，而是让块变成持久化文件的通用协议。

## 四、页缓存：文件与 RAM 的会合点

内核会把经常访问的文件内容按页缓存在 RAM 中，通常称为**页缓存**。它是以“文件对象 + 文件页索引”为键的一组物理页，而不是某个进程私有的用户内存。

```text
同一个文件的第 5 页
  -> 页缓存中的一个物理页
  -> 可被多个 read 请求复用
  -> 也可被多个进程的 mmap 映射到各自虚拟地址
```

于是同一文件页可能同时有三种视图：文件系统把它视为文件偏移范围；页缓存把它视为缓存页；某个 `mmap` 进程的页表把同一物理页视为一个虚拟页。它们不是互相取代的地址，而是对同一数据在不同层的索引。

页缓存的存在解释了“第二次读取很快”，却不代表数据永久驻留。干净的缓存页可在内存紧张时直接回收，因为内容可从文件重新读取；脏页在回收前则必须写回或按错误策略处理。

## 五、交换空间与普通文件不是同一类后备存储

虚拟内存有时会把不活跃的匿名页写入交换空间（swap 或分页文件）。这使人误以为“虚拟内存管理磁盘”。更精确的说法是：**内存管理器把一块专门的交换后备存储作为匿名页的后备来源之一**。

普通文件的分配、目录结构和文件长度仍由文件系统管理；swap 即使放在一个文件中，内核也常将其以适合分页 I/O 的方式专门使用。文件页被回收后可以从原文件重新读取；已被修改的匿名页若没有 swap 或其他后备，内核就不能凭空重建它。这是两者最重要的语义差异。

## 六、把一次读取放回正确的分工

假设应用读取 `/docs/a.txt` 的第 8192 到 12287 字节：

1. `open` 时，内核解析路径、检查目录和权限，得到文件对象；进程获得文件描述符。
2. `read` 时，内核从打开文件状态取到当前文件偏移。它不是磁盘地址。
3. 页缓存若已有相应文件页，内核直接使用它；没有则请文件系统把文件偏移换算成 LBA。
4. 驱动向设备提交“读取这些 LBA 到这些 RAM 页”的请求。控制器 DMA 写入页缓存页，并报告完成。
5. 普通 `read` 把所需字节复制到用户提供的虚拟地址；CPU 再经该进程的页表访问 `buffer`。

```text
文件名 -> 文件对象 -> 文件偏移 -> LBA -> 页缓存中的物理页 -> 用户虚拟缓冲区
         文件系统负责       块 I/O 负责          内存管理负责
```

没有任何一步要求 CPU “直接操作磁盘空间”。CPU 既负责执行内核代码、配置设备和之后处理内存中的结果，也把耗时的数据搬运交给 DMA。把控制路径和数据路径分开，是理解 I/O 的一个很好的起点。

## 七、总结

- 虚拟地址到 RAM 页框的翻译属于虚拟内存；文件偏移到 LBA 的翻译属于文件系统。
- 页缓存是普通文件数据进入 RAM 后的共享缓存，普通 `read` 与 `mmap` 都能利用它，但交付方式不同。
- swap 是匿名页的专用后备存储，不能据此说虚拟内存管理普通文件的磁盘空间。
- CPU 不能用普通内存指令直接读取磁盘 LBA；它通过驱动/队列发起 I/O，由设备 DMA 把数据带到 RAM。

下一篇只聚焦地址翻译：CPU 手里的虚拟地址怎样经过 TLB、页表和缺页，变成可访问的物理内存。文件系统先暂时放在一边；这一次不混在一起，理解反而会更简单。
