本篇只回答一个问题：CPU 执行一条取指、load 或 store 时，怎样把进程给出的虚拟地址变成 RAM 位置。不要把文件偏移和磁盘块号带进这一步；它们只会在某次缺页需要准备数据时，作为页面后备来源的一部分出现。

## 一、地址翻译的基本单位

设页大小为 4 KiB，一个虚拟地址可拆为：

```text
虚拟地址 = 虚拟页号 VPN + 页内偏移 offset
物理地址 = 物理页框号 PFN + 同一个 offset
```

页表记录的核心正是 `VPN -> PFN`，并附带 present、读/写/执行、用户/内核、访问和脏页等状态。页内偏移不需要被“重新计算”；同页内的第 37 个字节在虚拟页和物理页中都是第 37 个字节。

CPU 先查 TLB——页表项的高速缓存。TLB 命中即可得到 PFN；未命中时，硬件页表遍历器（或某些架构上的内核协助）读取多级页表。页表本身也存放在 RAM，只是 CPU 有专门机制避免让每次内存访问都由软件逐级解释。

## 二、缺页不是一个单一结果

若页表项说该页当前不能直接访问，CPU 触发异常并进入内核。内核首先判定该地址是否属于一个合法虚拟内存区域：

- 合法匿名页第一次访问：分配/清零物理页，或按写时复制复制页面；
- 合法文件页首次访问：定位该文件偏移，准备相应页缓存页；
- 合法但被换出的匿名页：从交换后备读回；
- 不合法地址或违反权限：报告段错误、访问冲突等失败，而不是“自动从磁盘找数据”。

因此“缺页”并不等于磁盘 I/O。零页、已经在页缓存中的文件页、写时复制等情况都可不读磁盘；反过来，缺页也可能根本无法修复。

## 三、页面来源与页表职责

页表只说明当前虚拟页能否映射到某个物理页框。内核的虚拟内存区域和反向映射等元数据还要记录这个页在不在内存时应从哪里恢复。常见来源如下：

| 虚拟页类型 | 初始内容/后备来源 | 回收后如何恢复 |
| ---------- | ---------------- | -------------- |
| 匿名页 | 零页、程序写入的数据 | swap（若已换出）或不能丢失的驻留页 |
| 文件私有映射 | 文件偏移 | 重读文件；被写入后可能转为私有副本 |
| 文件共享映射 | 页缓存中的文件页 | 重读文件；脏页需写回文件 |
| 可执行代码页 | 可执行文件偏移 | 从文件重新读取 |

“虚拟内存使用磁盘”在这里才有精确含义：内存管理器可使用 swap 作为匿名页后备，也可在文件映射缺页时请求文件页。普通文件的长度、目录和块分配仍由文件系统决定。

## 四、共享、权限与回收

多个页表可映射同一物理页：共享库和同一程序的只读代码页如此，`fork` 后尚未写入的页也如此。写时复制把这些页先设为只读；某一方写入才在缺页路径中复制，随后让它独占新的可写页。

内核还必须记录物理页是否空闲、被引用、脏、锁定在 I/O 中或属于页缓存。页表不能单独充当“所有物理页的空闲账本”：一个物理页可能被许多页表引用，也可能暂时根本没有用户页表映射。

## 五、总结

- CPU 的普通内存访问在 TLB/页表层止于物理 RAM，不会直接得到 LBA。
- 缺页先做合法性与来源判断，再可能分配内存、读取文件、读 swap 或报告错误。
- 文件页、匿名页和交换页都可参与虚拟内存，却有不同的后备与写回语义。
