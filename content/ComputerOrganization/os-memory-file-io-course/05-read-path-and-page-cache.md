现在把前几篇的职责串起来。假设应用已经 `open` 了一个普通文件，然后调用：

```c
ssize_t n = read(fd, buffer, 4096);
```

`fd` 是进程文件描述符表中的索引，`buffer` 是调用进程的用户虚拟地址；两者都不是 LBA。

## 一、命中页缓存的快速路径

内核由 `fd` 找到打开文件状态，其中有当前文件偏移和文件对象。它以文件对象和文件页索引查询页缓存。若目标页已经有效：

1. 内核检查长度、访问模式和用户地址可写性；
2. 从页缓存页复制所需字节到 `buffer`；
3. 推进打开文件状态中的偏移并返回实际字节数。

页缓存页在 RAM 中，但 `buffer` 属于进程地址空间。`copy_to_user` 必须按用户页表安全访问它，并可能因用户缓冲区自身尚未驻留而处理另一个缺页。这里的复制保护了内核缓存免受用户随意写入，也使页缓存能够被很多进程复用。

## 二、缓存未命中时

目标文件页不在缓存时，内核创建/锁定页缓存页，请文件系统把相应文件偏移映射为 LBA，并由块层和驱动提交 I/O。设备 DMA 将数据写入该页；完成处理中核验结果、将该缓存页标记为有效、唤醒等待者。随后仍按普通路径复制到用户缓冲区。

```text
read(fd, user_buffer)
 -> 打开文件状态的文件偏移
 -> 页缓存命中？
    -> 是：缓存页 -> copy_to_user -> user_buffer
    -> 否：文件偏移 -> LBA -> DMA 到缓存页 -> copy_to_user
```

第二次读取通常更快，是因为免去了设备 I/O；但缓存页在内存压力下可被回收，速度提升不是永久承诺。

## 三、缺页在此处出现在哪里

“读取文件会不会缺页”要区分对象：页缓存未命中会触发文件 I/O，但它不是调用者用户地址的普通 MMU 缺页；拷贝到 `buffer` 时，如果用户页尚未建立，内核访问用户地址可触发并处理匿名页缺页。使用 `mmap` 时，进程直接访问文件映射地址才会产生典型的**文件缺页**，下一篇详述。

## 四、总结

- `read` 的常规数据落点是页缓存，交付给应用的常规方式是复制到用户缓冲区。
- 文件系统只在缓存未命中时参与“文件偏移 -> LBA”的定位；设备 DMA 填充缓存页。
- 同一次 API 调用中，文件缓存缺失与用户缓冲区缺页是不同层次的事件。

想减少复制时，正确的工具通常是 `mmap`、`sendfile`、`splice` 或合适的直接 I/O；它们的边界比“让用户直接共享内核内存”严格得多。
