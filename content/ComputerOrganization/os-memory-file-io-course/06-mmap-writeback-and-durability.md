`mmap` 才是“文件的一段内容映射到进程虚拟地址空间”的准确机制。它避免了应用显式调用 `read` 后再复制到自己的缓冲区，却没有让 CPU 直接访问磁盘。

## 一、mmap 建立的是延迟的映射关系

内核先记录一个虚拟内存区域：该地址范围对应某文件及其文件偏移。它通常不会马上把整个文件读进 RAM。进程第一次读映射地址时：

1. MMU 发现页表尚无可用映射，产生缺页；
2. 内核确认地址属于这个文件映射，查对应页缓存页；
3. 缓存未命中则按文件偏移定位 LBA、发起 DMA；
4. 将页缓存物理页映射进进程页表，重新执行原指令。

这解释了为什么 `mmap` 可与普通 `read` 共享缓存：最终的数据通常是同一页缓存物理页，只是前者通过页表交付，后者通过复制交付。

## 二、脏页如何回到文件

对共享、可写映射或普通写入，修改先留在页缓存页，页被标记为脏。内核可在后台按内存压力、时间和聚合效率安排写回；文件系统将脏页对应的文件偏移映射成 LBA，再写入设备。写私有映射（`MAP_PRIVATE`）常触发写时复制，修改只属于进程私有匿名页，不会自动写回原文件。

因此“`write` 返回成功”通常只说明内核接受了数据，并不等同于已提交到设备，更不必然等同于断电后仍可靠存在。`fsync(fd)` 要求内核把该文件相关的脏数据和必要元数据推进到文件系统所承诺的持久化点；目录项创建、重命名等还可能需要对目录 `fsync`。设备写缓存、文件系统实现和硬件断电保护共同决定最后的实际边界。

## 三、三种看似相同的成功

| 时刻 | 大意 | 断电时的风险 |
| ---- | ---- | ------------ |
| `write` 返回 | 数据已被内核接收 | 可能仍只在 RAM |
| I/O 完成 | 请求已由设备报告完成 | 取决于设备缓存/屏障语义 |
| `fsync` 成功 | 达到系统承诺的持久化点 | 仍需可信硬件和正确错误处理 |

日志或写时复制保证元数据关系可恢复；它们不自动让任意应用记录成为完整、原子的业务事务。并发修改同一文件还要另行定义记录边界、使用 `O_APPEND`、锁或 `pwrite` 等机制。

## 四、总结

- `mmap` 映射的是文件页到虚拟地址的按需关系，访问时仍经页缓存、缺页与设备 I/O。
- 脏页写回由内核与文件系统安排；共享映射和私有映射的写回语义不同。
- 可见、已交给设备和已持久化是三件事，`fsync` 用于明确推进边界。

最后一篇用可执行文件把上述机制合拢：程序的代码页也只是带有可执行权限的文件页。
