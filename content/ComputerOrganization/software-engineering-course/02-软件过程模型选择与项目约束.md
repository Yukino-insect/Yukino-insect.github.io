过程模型不是背诵“瀑布适合什么、螺旋适合什么”的标签题，而是把项目约束映射到开发节奏、反馈方式和风险控制策略。选择模型时，至少要分析需求稳定性、技术成熟度、交付节奏、合规要求、团队能力和风险暴露时间。

## 一、先把项目约束说清楚

可以用下面的问题整理项目背景：

- 需求是否稳定？哪些需求已经由法规、合同或接口协议固定，哪些仍需要用户探索？
- 技术是否成熟？关键技术、外部系统和性能目标是否存在未知数？
- 是否必须分批交付？用户能否接受先有核心功能，再逐步增加能力？
- 是否需要严格的评审、文档、审计和变更基线？
- 风险一旦发生，影响是局部返工，还是会造成安全事故或重大经济损失？

这些问题的答案比“团队喜欢哪种方法”更能决定模型。模型选择应当形成一段可审查的理由，而不是一句“采用敏捷开发”。

## 二、五种模型的适用边界

| 模型 | 组织方式 | 更适合的情形 | 主要代价 |
| ---- | -------- | ------------ | -------- |
| 瀑布模型 | 阶段依次完成，评审后进入下一阶段 | 需求稳定、合规审查严格、交付物边界清晰 | 反馈较晚，变更回退成本高 |
| 快速原型模型 | 先做可体验的原型澄清需求 | 用户难以描述界面和交互，需求不确定 | 原型可能被误当成正式产品，质量和架构被忽略 |
| 增量模型 | 分批实现并交付功能增量 | 需要尽早获得核心价值，功能可分批验收 | 增量之间的接口和架构需要提前规划 |
| 螺旋模型 | 每一轮先识别、分析并降低风险 | 新技术、高风险、规模大且需求会演化 | 风险分析和管理成本较高，需要成熟团队 |
| 喷泉模型 | 分析、设计、实现反复迭代并相互交叠 | 面向对象开发、模型和代码持续演化 | 阶段边界不如瀑布清晰，管理和度量更难 |

瀑布模型并不禁止反馈，增量模型也不等于“随意迭代”。判断模型时，要看题干强调的控制机制：强调阶段评审的是瀑布，强调先验证用户理解的是原型，强调分批交付的是增量，强调逐轮风险分析的是螺旋，强调分析设计实现交叠的是喷泉。

## 三、用约束矩阵做选择

以“校园借阅系统”为例，若学校要求在开学前交付核心借还功能，但预约和统计可以后续增加，同时需要接入尚未稳定的统一认证接口，可以这样记录决策：

| 约束 | 观察 | 对模型的影响 |
| ---- | ---- | ------------ |
| 核心功能要尽早可用 | 借还功能可独立验收 | 倾向增量模型 |
| 认证接口尚未稳定 | 存在外部技术风险 | 在首个增量中安排原型或风险验证 |
| 个人信息和借阅记录需审计 | 需求和文档必须可追溯 | 每个增量保留评审、测试和配置基线 |

因此，合理结论不是简单贴一个模型名称，而是“以增量交付为主，在高风险接口上采用原型验证，并为每个增量设置受控评审”。实际项目常组合多种策略，课程中的模型是分析工具，不是互斥的宗教派别。

## 四、过程的任务、方法与工具

软件工程中的三个词要分开：

- **过程**规定生命周期阶段、角色、入口条件、输出物和反馈路径；
- **方法**规定如何分析、设计、实现和测试，例如 DFD、面向对象分析、等价类划分；
- **工具**帮助执行方法并保存结果，例如建模工具、版本控制、构建和测试工具。

工具换了，过程和方法不一定改变；使用了 UML，也不代表自动采用某一种生命周期。考试或项目决策应先说明要解决的工程问题，再选择合适的方法和工具。

## 五、单元一的检查清单

- 能从题干找出需求、技术、交付和合规约束。
- 能说明六种常见过程模型的核心机制、适用情形和风险。
- 能解释软件生命周期各阶段的任务，而不是只背阶段名称。
- 能为模型选择写出“依据—决策—代价”的完整理由。
- 能指出过程模型需要反馈和变更控制，不能把阶段图误读成绝对单向流程。

完成这一单元后，才进入需求分析：过程模型决定“怎样组织工作”，需求模型则回答“系统必须做什么”。
