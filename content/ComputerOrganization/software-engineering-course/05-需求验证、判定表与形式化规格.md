需求分析不能止步于“画出来”。验证要检查规格是否正确、完整、一致、无歧义且可验证；精化要把复杂业务规则转换为能实现、能测试的条件组合。判定表、判定树和处理规格特别适合案例题中多个条件共同决定多个动作的情形。

## 一、需求验证的五个角度

- **正确性**：是否真实反映用户需求，而非分析者自行猜测。
- **完整性**：所有功能、异常、接口、性能和约束是否都有说明。
- **一致性**：同一术语、数据定义、业务规则之间是否矛盾。
- **无歧义性**：不同读者是否会得到相同解释。
- **可验证性**：每条需求是否能用检查、演示、测试或分析确认。

“系统应支持大量用户”和“查询应尽量快”不可验证。可改写为“在 500 个并发查询、95% 请求命中现有索引的负载下，借阅状态查询的 95 分位响应时间不超过 2 秒”。这个需求未必容易实现，但至少可以被测量和验收。

## 二、判定表：条件组合完整列举

图书借阅规则：有效读者、未超借阅上限、无超过 20 元的欠费、图书副本可借，四项同时满足才登记借阅；无效读者输出身份拒绝，其余任一条件不满足输出相应拒绝原因。若只写四个 `if` 的自然语言说明，容易漏掉组合。判定表先列条件，再列可能规则列，最后列动作。

| 条件 / 动作 | R1 | R2 | R3 | R4 | R5 |
| ----------- | -- | -- | -- | -- | -- |
| 读者有效？ | Y | N | Y | Y | Y |
| 未超上限？ | Y | - | N | Y | Y |
| 欠费不超过 20？ | Y | - | - | N | Y |
| 图书可借？ | Y | - | - | - | N |
| 登记借阅 | X |  |  |  |  |
| 提示身份无效 |  | X |  |  |  |
| 提示超借阅上限 |  |  | X |  |  |
| 提示欠费限制 |  |  |  | X |  |
| 提示图书不可借 |  |  |  |  | X |

`-` 表示该规则中此条件无关。例如读者无效时，无须继续判断欠费。上表假定拒绝原因按固定优先级返回；若系统要一次性显示所有原因，就必须增加对应动作，不能继续使用“只命中第一个拒绝”的表。

### 化简的边界

判定表可以合并动作相同且无关条件可用 `-` 表示的规则，但不能为了表短而掩盖优先级。例如“逾期且图书损坏”需要同时计算逾期费和赔偿，不能合并成一个仅提示“异常”的规则。题目若问最少测试用例，可先按化简后的规则列构造；题目若问所有条件组合，则要覆盖 $2^n$ 个组合或说明不可达组合。

## 三、判定树：条件有层次时更直观

判定树与判定表表达能力相当，但当后续判断依赖前面结果时更自然：

```text
读者有效？
├─ 否 -> 输出“身份无效”
└─ 是 -> 超过借阅上限？
         ├─ 是 -> 输出“超过上限”
         └─ 否 -> 欠费超过 20 元？
                  ├─ 是 -> 输出“欠费限制”
                  └─ 否 -> 图书可借？
                           ├─ 否 -> 输出“图书不可借”
                           └─ 是 -> 登记借阅并打印凭条
```

判定树的叶节点应是动作或结论，不能停在“图书可借？”这种尚未完成判断的位置。反过来，若规则主要是多个独立布尔条件的组合，表格更方便检查是否漏列。

## 四、处理规格：用 PDL 消除实现歧义

处理规格（mini-spec）用于描述 DFD 中原子处理的内部逻辑。结构化自然语言或伪代码（PDL）应使用明确的控制结构，而非夹杂含糊口号。

```text
处理：1.2 验证借阅条件
输入：有效读者、图书副本状态、当前借阅数、欠费金额
输出：借阅许可 或 拒绝原因

IF 当前借阅数 >= 允许上限 THEN
    输出“超过借阅上限”
ELSE IF 欠费金额 > 20.00 THEN
    输出“欠费限制”
ELSE IF 图书副本状态 <> “可借” THEN
    输出“图书不可借”
ELSE
    输出借阅许可
END IF
```

此处最值得注意的是 `>=` 与 `>`。这两个符号把“上限”和“超过 20 元”变成可测试边界。若不能确定业务含义，正确做法是把疑问列为待确认项，而不是擅自挑一个运算符。

## 五、形式化说明的作用与限度

形式化方法使用有严格语义的数学记号描述系统性质，可用于高可靠或安全关键领域。常见的基本思想是用前置条件、后置条件和不变式说明操作。

例如，借书操作前置条件可写为：

$$
reader.valid \land reader.loanCount < reader.limit \land reader.debt \le 20 \land copy.status = available
$$

成功后的后置条件包括：

$$
copy.status = loaned \land reader.loanCount' = reader.loanCount + 1
$$

其中撇号表示操作后的值。还需补充“生成一条借阅记录”“库存可借数减少”等后置条件。形式化规格的优势是能揭露遗漏的状态变化和矛盾约束；代价是建模门槛高、沟通成本大。因此它通常用于关键部分，而非意味着任何普通管理系统都必须使用完整形式化验证。

## 六、评审会议中的经典问题

对需求条目“超过借阅期限的读者不能续借”应追问：

- 是超过应还日期的次日，还是到当天某个时刻才算逾期？
- 图书馆闭馆日如何计算期限？
- 欠费已产生但尚未缴纳，是否允许归还、续借、预约？
- 是否存在管理员豁免？豁免是否需要记录原因和审批人？
- 接口不可用时，是拒绝、排队还是离线登记？

这不是凭经验增加功能，而是在把自然语言条件转成可判定规则。题目中的“若干”“及时”“必要时”“一般”正是应当被追问的信号。

## 七、作答检查

- 判定表每一列的条件组合是否互斥且覆盖？若不覆盖，是否明确是不可达？
- 同一列是否出现互相冲突的动作？若可能同时发生，是否定义优先级或并行动作？
- PDL 的每个分支是否都有输出或状态变化？
- 形式化的前置、后置条件是否保持关键不变式，如库存不可为负？

模型的意义不是把需求写得更像数学题，而是让遗漏、矛盾和边界被迫显露出来。需求不清时匆忙编码，之后只会以更昂贵的方式重新做一次分析而已。
