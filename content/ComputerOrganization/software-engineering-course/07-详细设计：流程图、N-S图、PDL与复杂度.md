详细设计回答的是模块内部“按什么步骤完成职责”。总体设计中的 `计算罚金`、`验证借阅条件`等模块，到这一阶段要给出可直接编码和测试的算法、控制结构、异常路径和接口约定。它仍不是直接写源代码；设计表达应能让实现者理解，也能让测试者据此构造路径和边界用例。

## 一、常用详细设计工具如何区分

| 工具 | 最适合表达 | 特点 |
| ---- | ---------- | ---- |
| 程序流程图 | 控制流、分支、循环 | 直观，但复杂时箭头交叉多 |
| N-S 图 | 结构化顺序、选择、循环 | 无任意跳转，适合结构化程序 |
| PDL / 伪代码 | 算法和模块契约 | 接近代码又不绑定语言 |
| 判定表 / 判定树 | 多条件组合 | 防止规则遗漏 |
| IPO 图 | 输入、处理、输出 | 快速定义模块边界 |

不要用流程图替代 DFD：流程图的箭头多是**控制转移**，DFD 的箭头是**数据移动**。同一条“借书请求”在 DFD 中是数据流；在流程图中，`资格通过？`的真/假才是控制分支。

## 二、例：计算逾期罚金

假设规则：归还日期不晚于应还日期时罚金为 0；逾期前 7 天每天 0.5 元，之后每天 1 元；丢失图书由另一处理计算赔偿，不在本模块混入。先写 IPO：

| 输入 | 处理 | 输出 |
| ---- | ---- | ---- |
| 应还日期、归还日期 | 计算逾期天数并按分段规则累计 | 逾期天数、罚金金额 |

对应 PDL：

```text
FUNCTION 计算逾期罚金(应还日期, 归还日期)
    overdueDays = 日期差(归还日期, 应还日期)
    IF overdueDays <= 0 THEN
        RETURN (0, 0.00)
    ELSE IF overdueDays <= 7 THEN
        RETURN (overdueDays, overdueDays * 0.50)
    ELSE
        fine = 7 * 0.50 + (overdueDays - 7) * 1.00
        RETURN (overdueDays, fine)
    END IF
END FUNCTION
```

可用下列自然语言流程图描述：开始 → 计算 `overdueDays` → 判断 `overdueDays <= 0`；是则输出 `(0, 0)` 并结束；否则判断 `overdueDays <= 7`；是则输出 `days × 0.5` 并结束；否则输出 `3.5 + (days - 7) × 1.0` 并结束。若需要正式流程图，应使用起止框、处理框、判断菱形和带条件标记的箭头，不能仅画几个矩形并凭读者猜测分支。

### 边界用例直接来自设计

| 应还日期到归还日期 | 预期逾期天数 | 预期罚金 |
| ------------------ | ------------ | -------- |
| -1 天 | 0 | 0.00 |
| 0 天 | 0 | 0.00 |
| 1 天 | 1 | 0.50 |
| 7 天 | 7 | 3.50 |
| 8 天 | 8 | 4.50 |

“第 7 天”和“第 8 天”是分段切换点；仅测试 3 天和 10 天无法证明边界正确。这也说明详细设计、白盒路径和黑盒边界值测试并非互不相干。

## 三、N-S 图的结构化思想

Nassi–Shneiderman 图（N-S 图）用嵌套矩形表达三种基本结构：顺序、选择、循环。其优点是排除了任意 `goto` 式跳转，层次对应程序块。上例的 N-S 结构可文字表示为：

```text
[计算 overdueDays]
[IF overdueDays <= 0]
| 是：返回 0
| 否：[IF overdueDays <= 7]
      | 是：返回 overdueDays * 0.5
      | 否：返回 3.5 + (overdueDays - 7) * 1.0
```

若模块要遍历归还清单，则把“读取下一项 → 处理 → 是否还有下一项”组织为一个循环块；循环体中避免跳到循环外的任意位置。考试题让你将非结构化流程改为结构化程序时，常见答案就是用选择和循环消除交叉跳转。

## 四、McCabe 圈复杂度与独立路径

控制流图中，圈复杂度（Cyclomatic Complexity）可用下式计算：

$$
V(G)=E-N+2P
$$

其中 $E$ 为边数，$N$ 为节点数，$P$ 为连通分量数；对于单入口单出口模块，常用简化是：

$$
V(G)=D+1
$$

$D$ 是判定节点数。上面的罚金模块有两个判定：`<=0` 和 `<=7`，因此 $V(G)=3$。这表示至少需要 3 条线性独立路径作为基本路径测试的起点，例如：

1. `overdueDays <= 0` 为真；
2. 第一个判断为假、第二个判断为真；
3. 两个判断均为假。

圈复杂度不是“缺陷数量”，也不等于必须恰好写 $V(G)$ 个测试后就万无一失。它是控制复杂度和最少独立路径数量的度量。若一个小模块已有十几个判定，优先考虑拆分规则或用判定表，而不是自豪地接受难以测试的巨型分支。

## 五、接口与异常路径也属于详细设计

假设 `登记借阅` 在更新库存后写借阅记录失败，设计必须说明是否撤销库存更新，或二者是否处于同一事务中。只写“先减库存，再插入记录”会留下不一致状态。一个合格的模块规格至少说明：

- 输入是否允许为空、格式错误和重复提交；
- 正常输出和错误输出的形式；
- 持久化更新的原子性边界；
- 外部服务超时的处理方式；
- 不变式，例如“可借册数不得小于零”。

## 六、经典计算题

某控制流图有 12 个节点、15 条边、1 个连通分量，则：

$$
V(G)=15-12+2\times1=5
$$

若同图有 4 个判定节点，也得到 $4+1=5$。两个结果不一致时，应检查：是否漏数边/节点、是否将多出口图错误当成单出口、或判定节点计数不符合实际。公式给出的数值不能脱离图的定义孤立使用。

## 七、作答检查

- 每个判断分支是否都有明确的去向？循环是否说明终止条件？
- 日期、金额、计数等边界是否写出等号属于哪一侧？
- 模块是否混合了不相关职责，如“计算罚金”同时发送短信、修改页面？
- 圈复杂度中的 $P$ 是否正确；是否把判定数和边数混为一谈？

详细设计的目的不是画出比代码更难读的图，而是提前暴露控制分支、边界条件和状态一致性。把这些在纸面上说明白，代码只是相对机械的翻译；反过来，代码再优雅也无法替代未做出的业务决定。
