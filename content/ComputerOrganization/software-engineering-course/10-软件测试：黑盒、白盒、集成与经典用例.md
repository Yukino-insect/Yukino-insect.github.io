测试是为了发现错误而执行程序或检查产物的过程；它能增加信心，却不能证明程序“绝对没有错误”。一个好测试用例应有较高发现缺陷的可能性，一个成功测试是发现此前未发现错误的测试。这种表述看似消极，实际是在提醒我们：测试资源有限，必须选择有辨别力的输入和路径。

## 一、测试层次与对象

| 层次 | 目标 | 常见问题 |
| ---- | ---- | -------- |
| 单元测试 | 验证最小可测模块 | 分支、边界、异常、局部状态 |
| 集成测试 | 验证模块接口与协作 | 参数不一致、调用顺序、数据格式、异常传播 |
| 确认测试 | 验证是否满足需求规格 | 功能、性能、接口、验收条件 |
| 系统测试 | 在完整环境下验证系统属性 | 安全、恢复、并发、安装、负载 |

调试（debugging）与测试不同：测试暴露失败，调试定位原因并修复。修复后应做回归测试，以确认旧功能未被改坏。

## 二、黑盒测试：从规格构造输入

黑盒测试不关注代码内部结构，依据需求、判定表、接口和数据定义设计用例。

### 1. 等价类划分

假设读者编号必须为 8 位数字，借阅册数范围为 0 到上限。可划分：

| 输入项 | 有效等价类 | 无效等价类 |
| ------ | ---------- | ---------- |
| 读者编号 | 恰好 8 位数字 | 少于 8 位、多于 8 位、含非数字、空值 |
| 借阅册数 | `0..limit` | 小于 0、大于 limit、非整数、缺失 |
| 欠费金额 | 非负合法金额 | 负数、格式非法、缺失 |

从每个等价类选择代表值，而不是对每个可能值都测试。注意“无效等价类”也应有代表用例；只测有效输入等于没有验证系统的防线。

### 2. 边界值分析

错误常发生在边界。若“欠费超过 20 元不可借”，关键测试是 `19.99`、`20.00`、`20.01`，而非随机取 5 和 30。若输入范围为 `[1, 100]`，典型边界集为 `0, 1, 2, 99, 100, 101`。这里的“刚外侧、边界、刚内侧”比大量中间值更有信息量。

### 3. 因果图与判定表

条件组合复杂时，先从因果关系导出判定表，再为每条有效规则设计用例。例如借书的“有效读者、未超限、欠费合规、图书可借”有多个条件；只做“全真”和“全假”会遗漏“读者有效但欠费超限”等规则。判定表正是黑盒用例的直接来源。

## 三、白盒测试：从控制结构选择路径

白盒测试关注内部结构，可使用语句覆盖、判定覆盖、条件覆盖、条件组合覆盖和路径覆盖。

| 覆盖标准 | 至少要求 | 不保证什么 |
| -------- | -------- | ---------- |
| 语句覆盖 | 每个可执行语句至少执行一次 | 每个判断真/假都执行 |
| 判定覆盖 | 每个判定的真、假结果都出现 | 每个基本条件都独立取真/假 |
| 条件覆盖 | 每个基本条件都取真、假 | 整个判定真、假都出现 |
| 条件判定覆盖 | 同时满足条件覆盖和判定覆盖 | 所有条件组合 |
| 路径覆盖 | 所有可行路径 | 含循环时通常不可穷尽 |

经典反例：`if (A && B)`。两组测试 `(A=true,B=false)` 与 `(A=false,B=true)`使 A、B 都取过真/假，满足条件覆盖；但整个判定始终为假，不满足判定覆盖。因此不能说条件覆盖必然包含判定覆盖。

### 基本路径测试

基本路径测试依据圈复杂度选择线性独立路径。对有两个二分支判断的模块，圈复杂度为 3，可设计覆盖“第一个真”“第一个假且第二个真”“两个均假”的路径。循环应额外考虑 0 次、1 次、2 次、典型次数、最大次数和超过最大次数；只覆盖一次循环无法发现初始化和终止问题。

## 四、集成测试策略与桩/驱动

| 策略 | 做法 | 辅助模块 |
| ---- | ---- | -------- |
| 自顶向下 | 从主控模块逐步向下集成 | 未实现下层用桩模块 Stub 模拟 |
| 自底向上 | 从基础模块逐步向上集成 | 未实现上层用驱动模块 Driver 调用 |
| 三明治/混合 | 上下并行向中间汇合 | 同时可能使用桩和驱动 |
| 大爆炸 | 所有模块一次集成 | 辅助少，但故障定位困难 |

桩模块代替**被调用的下层模块**，向上层返回受控数据；驱动模块代替**调用者/上层模块**，负责调用待测底层模块。最常见的填空题陷阱正是把二者叫反。

## 五、贯穿案例：借阅资格测试集

设规则与第五篇一致，固定优先级为：无效读者、超上限、欠费超限、图书不可借。一个最小而有针对性的测试集可为：

| 用例 | 有效 | 未超限 | 欠费 | 可借 | 预期 |
| ---- | ---- | ------ | ---- | ---- | ---- |
| T1 | N | - | - | - | 身份无效，不更新任何记录 |
| T2 | Y | N | 0 | Y | 超过上限 |
| T3 | Y | Y | 20.00 | Y | 成功登记 |
| T4 | Y | Y | 20.01 | Y | 欠费限制 |
| T5 | Y | Y | 0 | N | 图书不可借 |
| T6 | Y | Y | 0 | Y | 成功登记且库存/记录一致更新 |

T3 和 T4 是边界对；T6 不仅检查响应，还应检查后置状态。若成功响应却没有创建借阅记录，或创建记录却未更新副本状态，属于集成/事务缺陷，不能只靠界面断言掩盖。

## 六、测试文档与缺陷报告

测试用例至少应包含标识、目标需求、前置条件、输入/步骤、预期结果和实际结果。缺陷报告应记录版本、环境、复现步骤、期望与实际结果、严重性和附件。只写“借书有问题”既不能复现，也不能判断是否已修复。

## 七、作答检查

- 黑盒用例是否来自规格中的等价类、边界和规则，而非猜测代码？
- 白盒覆盖结论是否准确区分语句、判定、条件？
- 集成策略的桩模块与驱动模块是否对应正确方向？
- 成功用例是否验证了状态更新，失败用例是否验证了“不应更新”？

测试不是在项目末尾进行的一次仪式。需求的可测试性、设计的可观察性和模块的可替代性，早在前面阶段就决定了测试的质量；末尾才发现这些条件不存在，通常已经太晚了。
