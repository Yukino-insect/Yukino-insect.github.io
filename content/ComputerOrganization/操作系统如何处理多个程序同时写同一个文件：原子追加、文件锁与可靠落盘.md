两个程序同时向同一个文件写数据，操作系统并不会自动替应用决定“谁的内容更有道理”。它能保证一部分底层动作的原子性，也提供文件锁、原子替换等机制；至于记录如何分界、谁先写、发生故障后怎样恢复，仍然是应用协议的一部分。

核心结论可以先写在这里：**并发写文件要先分清写入位置、记录边界、互斥范围和持久化目标。**追加日志通常使用 `O_APPEND`；写不同的固定区域使用 `pwrite`；必须修改同一段内容时要用进程间锁；需要让读者只看到完整新版本时，应写临时文件后原子 `rename`。单次 `write` 成功返回不等于数据已经落到磁盘，`PIPE_BUF` 的原子写保证也不能套用到普通文件。把这些混在一起，问题就会被一句“文件锁”敷衍过去，实在没有必要。

## 一、先看问题发生在哪一层

假设两个进程都要向 `orders.log` 写一条记录：

```text
进程 A: order=1001, amount=20
进程 B: order=1002, amount=35
```

“同时写”可能意味着截然不同的事情：

| 问题 | 可能结果 | 需要的机制 |
| ---- | -------- | ---------- |
| 两个写入都从偏移 `0` 开始 | 后写者覆盖先写者 | 分配不同位置、`O_APPEND` 或锁 |
| 两个写入都想追加到末尾 | 记录顺序不可预测，定位末尾与写入可能竞争 | `O_APPEND` 或串行化 |
| 两个写入修改同一段字节 | 内容互相覆盖，读者可能看到中间状态 | 范围锁、互斥协议、版本化更新 |
| 一条业务记录分多次 `write` | A 和 B 的片段可能交错 | 一次写完整记录，或在整个记录期间持锁 |
| 数据写入后机器断电 | 数据可能仍只在页缓存或设备缓存中 | `fsync` / `fdatasync` 与恢复协议 |

因此，“操作系统怎么处理”并没有唯一答案。内核首先要完成文件系统层面的并发控制：维护 inode、页缓存、文件大小、块映射和脏页状态的一致性；应用还必须决定自己的数据结构和事务边界。

## 二、文件描述符、打开文件对象与文件偏移

程序使用的是文件描述符（file descriptor，FD），但真正保存“当前读写到哪里”的通常是内核中的**打开文件对象**，也常被称为 open file description。一个文件描述符只是当前进程 FD 表中指向该对象的入口。

```text
进程 A 的 fd 3 ──> 打开文件对象 X ──> inode / 文件 data.log
                         └─ 当前偏移 offset

进程 B 的 fd 4 ──> 打开文件对象 Y ──> 同一个 inode / 文件 data.log
                         └─ 当前偏移 offset
```

上图中两个进程分别 `open` 同一文件，会得到两个打开文件对象 X、Y。它们指向同一个文件，却各自拥有独立的当前偏移，初始位置通常都是 0：

```c
// 进程 A 和进程 B 都这样打开
int fd = open("data.log", O_WRONLY | O_CREAT, 0644);
write(fd, "hello\n", 6);
```

若没有额外标志，二者都可能在偏移 0 写入，于是其中一次写覆盖另一次。内核能正确维护文件系统元数据，不代表它会猜测你其实想要“追加”。

另一种情况是 `fork()` 或 `dup()`：父子进程的两个 FD 可能指向**同一个**打开文件对象。这时当前偏移也被共享。现代遵循 POSIX 语义的系统会协调对这个共享偏移的更新，避免两个 `write` 都取到同一个旧偏移；但记录先后仍由调度决定，应用也不应把共享偏移当作业务层的顺序锁。

## 三、内核内部怎样避免把文件系统弄坏

多个进程写同一文件时，文件系统必须保护自身的数据结构。例如它需要确保：

- 文件长度不会因竞争得到明显错误的值；
- 两个扩展写入不会把同一个数据块错误地分配给不相关的位置；
- 页缓存中的脏页、inode 元数据和回写队列保持可追踪；
- 正在读文件的进程不会因为内核元数据被并发破坏而使系统崩溃。

这些保护由内核内部的锁、引用计数、页锁、日志或写时复制文件系统机制完成。它保护的是**文件系统实现的完整性**，并不承诺你的两条业务记录会以你希望的顺序出现，也不会替你阻止“管理员脚本”和“业务服务”同时改同一份配置。

可以把两层责任分开理解：

```text
内核 / 文件系统：文件大小、页缓存、块映射、元数据不被写坏
应用程序：记录边界、业务顺序、谁可修改、失败后如何恢复
```

内核能防止文件系统在并发下失去结构，不会自动替应用实现订单事务。这种克制其实相当合理，毕竟它也不可能知道哪一个进程更值得信任。

## 四、追加写：O_APPEND 解决的是“末尾位置”竞争

日志是最常见的并发写场景。错误做法通常长这样：

```c
off_t end = lseek(fd, 0, SEEK_END);
write(fd, record, record_len);
```

两个进程可能都在 `lseek` 时看到同一个文件末尾，随后在同一位置写入。把它改成 `O_APPEND`：

```c
int fd = open("orders.log", O_WRONLY | O_CREAT | O_APPEND, 0644);
ssize_t n = write(fd, record, record_len);
```

`O_APPEND` 的语义是：**内核在每次写入时将当前文件末尾定位与实际写入作为一个原子动作处理。**两个写入者无需先自行 `lseek`，它们都会得到不同的追加位置。哪个记录排在前面取决于内核实际执行写入的先后，而不是哪个程序先调用了 `write`。

```text
初始文件： [旧数据]

进程 A、B 都以 O_APPEND 写入
  ├─ 可能结果 1：[旧数据][A 的完整写入][B 的完整写入]
  └─ 可能结果 2：[旧数据][B 的完整写入][A 的完整写入]
```

### 1. O_APPEND 不替你定义一条业务记录

如果一条记录被拆成多次系统调用：

```c
write(fd, "order=1001,", 11);
write(fd, "amount=20\n", 10);
```

那么 A 的两次写之间完全可能插入 B 的写入。`O_APPEND` 会让每一次 `write` 都追加到当时的末尾，但它不会把两次系统调用自动捆成一次事务。

对追加日志，一个实用原则是：**先在用户空间组装完整记录，再用一次 `write` 提交。**同时给记录增加长度字段、换行符、校验和或序列号，便于发现短写、截断和恢复边界。

```c
char record[256];
int len = snprintf(record, sizeof record,
                   "{\"id\":1001,\"amount\":20}\n");

// 真实代码还应处理 EINTR、短写和错误
ssize_t n = write(fd, record, (size_t)len);
```

即便如此，也不能把“单个 `write`”神化为跨所有文件系统、所有故障模式的永久记录事务。磁盘空间不足、I/O 错误、信号和网络文件系统语义都可能使写入部分完成或失败。若记录绝不能损坏，应该用锁保护整条记录提交，或采用带长度、校验和和恢复扫描的日志格式。

### 2. 本地文件系统与网络文件系统的边界

在本地、遵循相应语义的文件系统上，`O_APPEND` 是多写者追加的基础工具。网络文件系统则不一定能够由客户端把“查找 EOF 与写入”作为服务器端单一原子操作完成；例如某些 NFS 使用场景中，客户端模拟追加，多个客户端同时追加可能仍有竞争。

因此，多主机共享文件不能只因代码里出现 `O_APPEND` 就宣称安全。应确认所用网络文件系统、挂载方式与服务端的并发语义；对强一致的业务，往往更适合使用数据库、消息队列或单独的日志服务。

### 3. 控制台日志很像追加流，但不能把它当成普通文件日志的保证

这个类比有一半是对的。多个线程或进程同时向控制台打印日志时，**显示顺序通常确实不可预测**：调度器决定哪个线程先运行，终端或终端模拟器只会按实际收到字节的顺序显示；它不知道哪一行日志在业务上更重要，也不会替你按时间戳、请求 ID 或事务顺序重排。

不过，`stdout` / `stderr` 并不是一种固定对象。它们可能指向终端（TTY 或伪终端）、管道、Socket，也可能在重定向后指向普通文件：

```text
./service                         -> 终端 / 伪终端
./service | collector             -> 管道
./service > service.log 2>&1      -> 普通文件
./service | network-log-forwarder -> 可能再转为 Socket
```

因此，不能仅凭“它显示在控制台”就套用某一种原子性规则。若多个写者写的是同一个管道或 FIFO，POSIX 只对请求长度不超过 `PIPE_BUF` 的**一次 `write`**保证不与其他写者的字节交错；重定向到普通文件后，应回到本文讨论的 `O_APPEND`、锁和落盘语义。终端设备及终端模拟器往往也会把一次较小的写入表现为连续的一段输出，但应用不应把这种常见表现当作跨平台的“每行日志绝不交错”承诺。

还要留意，源码中的一次 `println`、`printf` 或日志 API 调用未必只产生一次 `write`：格式化、标准 I/O 缓冲、异常堆栈和超长消息都可能拆成多次底层输出。许多成熟日志框架会在进程内用锁或专用写入线程把一条事件组装后再输出，这能减少同一进程线程间的穿插；它仍不能给多个独立进程规定一个业务上的先后顺序。

所以，控制台适合观察“发生了什么”，不适合充当并发操作的全局裁判。若日志顺序本身具有审计意义，应在日志记录中加入单调序列号、时间戳、请求 ID 或由中心日志服务分配的顺序，而不要从屏幕上谁先出现来推导因果关系。

## 六、协作文档解决的是应用语义，不是操作系统替人合并文字

腾讯文档、Google Docs 一类协作文档的确不是“两个进程都 `write` 同一个本地文件”那么简单。操作系统会负责网络连接、进程调度、内存和服务器磁盘上的文件系统一致性；但“甲删除了一个词、乙在同一段插入一句话后，最终文档应是什么”属于**应用层的数据模型与并发协议**，操作系统无法从一串字节中推断出来。

一个典型的协作编辑流程更接近下面这样：

```text
客户端 A、B 各自编辑本地副本
  -> 携带文档版本和编辑操作发送给协作服务
  -> 服务端排序、校验权限并合并并发操作
  -> 广播新的操作或文档版本
  -> 客户端根据协议重放、转换或合并，收敛到同一份内容
```

这里的“合并”可能采用操作转换（OT）、无冲突复制数据类型（CRDT）、版本号加冲突检测，或者对某些字段干脆采用最后写入者获胜。算法的选择决定了插入位置、删除范围、离线编辑和冲突提示的含义。若应用只把完整文件下载下来、各改各的、最后直接上传覆盖，那么它得到的也只是较粗暴的“最后提交者覆盖前者”，并不会因为底层文件系统有锁就自动变成协同编辑。

文件锁在这种系统中仍可能被服务器内部用于保护本地索引、快照或日志，却只是实现细节；真正协调的是服务端协议及其版本状态。除非协作文档产品明确设计为直接共享某个网络文件系统上的同一文件，否则不能把它理解为操作系统在替用户逐字符加锁。这样的期待未免太看得起内核，也太低估了应用协议。

### 1. 两个进程同时改“同一个字符”会怎样

先把“字符”换成更准确的“字节范围”。文件系统按字节偏移读写；UTF-8 中一个汉字通常占多个字节，JSON 的一个字段、文本编辑器中的一个字符也常对应不止一个字节。因此，两个进程修改视觉上的同一个字符，可能实际覆盖一段多字节范围。

在本地、遵循 POSIX 常规语义的普通文件上，若两个进程分别用 `pwrite` 对**完全相同的一个字节**写入不同值，而且两次调用都成功，可以将最终结果理解为其中一个写入覆盖另一个：最终字节取哪个值取决于实际发生的顺序，不能从“哪个进程先开始调用”推断。操作系统不会把两个值拼成第三个值，也不会替你保留冲突副本。这正是丢失更新最小的形式。

```text
原字节：X

进程 A: pwrite(fd, "A", 1, 100)
进程 B: pwrite(fd, "B", 1, 100)

最终第 100 字节：A 或 B（顺序不可预测）
```

但“只可能覆盖”只适合这个足够窄的模型，不能再扩大成所有并发修改的通则：

- 两个较长写入只部分重叠时，不同字节区间可能分别保留 A 或 B 的结果；从整段文本看起来便像混合内容。
- 写入 UTF-8 多字节字符、长度字段或结构化记录时，若没有把整个相关范围作为一个原子更新单元，读者可能得到无效编码或不满足格式约束的数据。
- 使用 `mmap(MAP_SHARED)` 后由多个进程直接读写同一内存位置，问题更接近共享内存数据竞争；仍需要进程间同步原语和明确的内存可见性规则，不能把它简化成文件 API 的“最后一次 `write`”。
- 网络文件系统、直接 I/O、写入失败和崩溃恢复的具体表现还可能与本地 POSIX 文件系统不同，不能据此承诺一个统一的“最后写者获胜”模型。

因此，若业务要求“检测到别人刚刚改过同一处就拒绝或合并”，正确做法不是赌覆盖顺序，而是在临界区使用锁，或保存版本号并在提交时做比较（乐观并发控制）。需要像协作文档那样合并文本，则必须在应用层定义操作和冲突规则。

## 七、定点写：用 pwrite 避开共享文件偏移

若多个程序本来就负责文件中互不重叠的区域，例如程序 A 写 `[0, 4096)`，程序 B 写 `[4096, 8192)`，就不应依赖“当前偏移”。可以使用 `pwrite`：

```c
ssize_t n = pwrite(fd, block, block_size, block_index * block_size);
```

`pwrite` 明确给出目标偏移，并且不改变该 FD 的当前偏移。这消除了“谁先移动 offset”的竞争：

```text
pwrite(fdA, blockA, 4096,    0)  -> 区域 A
pwrite(fdB, blockB, 4096, 4096)  -> 区域 B
```

但 `pwrite` 不会检查两段区域是否真的不重叠。若两个进程对同一范围发起写入，最终内容仍可能是最后写入者覆盖先前数据，或在更复杂的缓存与映射场景下出现应用不希望看到的组合状态。**位置由谁分配**仍需要协议、锁或一个中心协调者。

## 八、需要互斥时，用文件锁明确临界区

若多个进程必须执行“读取旧内容 → 判断 → 修改 → 写回”这类读改写操作，单靠原子 `write` 远远不够：两个进程都可能读到同一个旧值，然后后一次写覆盖前一次的修改。这是经典的丢失更新。

```text
初始余额：100

进程 A 读取 100，准备减 10
进程 B 读取 100，准备减 20
进程 A 写回 90
进程 B 写回 80

正确结果应为 70，实际却为 80
```

这时需要把整个读改写过程纳入同一个临界区。Unix/Linux 常见工具如下：

| 机制 | 锁定范围 | 特点 |
| ---- | -------- | ---- |
| `flock` | 通常为整个文件 | 接口简单，适合粗粒度协作 |
| `fcntl` 记录锁 | 可指定字节范围 | 可实现共享锁、排他锁和区间锁 |
| OFD lock | 与打开文件对象关联的记录锁 | 更适合处理 `dup`、线程和 FD 生命周期的某些场景 |
| 应用层锁文件 / 租约 | 由应用约定 | 便于跨语言，但必须设计好崩溃回收 |

以 `fcntl` 的排他范围锁为例，概念流程是：

```text
获取排他锁
  -> 读取当前数据
  -> 校验版本或执行业务判断
  -> 写入新数据
  -> 必要时 fsync
释放锁
```

这些通常是**建议锁（advisory lock）**：内核会记录和协调愿意遵守协议的进程，但一个完全忽略锁、直接 `write` 的程序仍可写入文件。强制锁在现代通用系统中并不常作为可靠设计基础。换言之，文件锁是协作契约，不是给文件套上一层魔法护盾。

### 1. 锁的粒度必须覆盖真正的竞争范围

若只对“写入”加锁，却在锁外读取旧值，丢失更新仍然可能发生。若 A 修改文件头的版本号、B 修改文件尾的数据，使用两个不重叠的范围锁可以并行；若二者都依赖同一个全局索引，就应锁住索引与相关数据的整体不变量。

锁过大导致吞吐下降，锁过小导致一致性失效。正确粒度取决于哪些字节和哪些元数据必须一起保持一致，而不是取决于锁 API 的名字。

### 2. 不要把线程锁当成进程锁

`pthread_mutex_t` 默认只在一个进程地址空间内协调线程。两个独立进程各自创建一把同名的互斥锁，不会互相看见。跨进程互斥应使用文件锁、具备 `PTHREAD_PROCESS_SHARED` 属性的共享内存锁，或由数据库、守护进程等外部协调者负责。

## 九、让读者看到“旧版本或新版本”，而不是半个文件

配置文件、索引文件和生成产物常有另一类需求：读者不能看到写到一半的内容。此时最可靠的思路通常不是原地覆盖，而是**写新文件后原子替换目录项**。

```text
写入 config.tmp
  -> flush config.tmp
  -> rename(config.tmp, config.json)
  -> 必要时 flush 所在目录
```

在同一文件系统、同一目录项替换语义下，`rename` 能让名称从旧文件切换到新文件，读者会看到旧版本或新版本，而不是名字指向一个已经被截断、尚未写完的文件。一个简化的 POSIX 风格过程是：

```c
// 省略错误处理、权限和临时文件安全细节
int tmp = open("config.json.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write(tmp, new_content, new_length);
fsync(tmp);                  // 先确保新文件内容已请求持久化
close(tmp);

rename("config.json.tmp", "config.json");
// 对崩溃后目录项也必须可靠的场景，还应 fsync 配置所在目录。
```

这个模式仍有边界：

- 多个写者同时使用相同临时文件名会彼此冲突，应使用安全的唯一临时文件；
- 两个写者先后 `rename` 时，后者仍会覆盖前者，需要锁、版本号或比较并交换式协议；
- `rename` 解决可见性切换，不自动保证磁盘断电后的持久化；
- 跨文件系统的“移动”不能假设具有同样的原子替换性质。

## 十、写入成功、读者可见与持久化是三件不同的事

一次 `write` 返回成功，通常表示内核已接受数据；它可能在页缓存中等待后续回写。此刻另一个进程通过同一内核的页缓存读取，往往已经可以看到新内容；但机器突然断电时，这些数据未必已经到达稳定存储。

```text
write 成功
  -> 数据进入或更新页缓存：其他读者可能可见
  -> 内核稍后回写：文件系统与设备处理数据
  -> 设备持久化完成：才更接近断电后仍可恢复
```

需要明确持久化边界时，常用：

- `fsync(fd)`：请求把文件数据及必要元数据同步到稳定存储；
- `fdatasync(fd)`：通常聚焦文件数据和使其可访问所需的元数据；
- `O_SYNC` / `O_DSYNC`：让每次写入具有更强的同步语义，但会显著影响延迟与吞吐；
- 对“写临时文件再重命名”模式：同步临时文件后，还要在要求严格的场景同步目录，确保名称变更也经受住崩溃。

这些调用的精确保证还受文件系统、设备缓存和硬件是否正确实现 flush 语义影响。应用层还应设计恢复过程：例如日志记录长度和校验和，启动时从最后一条完整记录恢复，而不是假定断电只会发生在礼貌的边界。

## 十一、一个容易记错的规则：PIPE_BUF 不适用于普通文件

POSIX 对管道和 FIFO 有一个很常用的保证：长度不超过 `PIPE_BUF` 的单次写入不会与其他写者的数据交错。许多人于是把它记成“文件写入小于某个大小就原子”，这是错误的。

`PIPE_BUF` 保护的是**管道/FIFO 的消息边界**，不是普通磁盘文件。普通文件上的并发追加、覆盖、部分写入、网络文件系统和崩溃恢复，应按普通文件的接口及所使用文件系统的语义设计，不能借用管道规则。

## 十二、按场景选择正确方案

| 场景 | 推荐方案 | 仍要注意 |
| ---- | -------- | -------- |
| 多进程写追加日志 | `O_APPEND`，一条记录尽量一次 `write` | 顺序不确定、短写、记录恢复、网络文件系统 |
| 多线程/进程输出控制台日志 | 让日志框架将一条事件整体输出；记录序列号、时间戳和请求 ID | 输出目标可能是终端、管道或普通文件；屏幕顺序不是业务顺序 |
| 多进程写固定分片 | 分片协议 + `pwrite` | 位置分配和范围不得重叠 |
| 多进程读改写同一文件 | `fcntl`/`flock` 锁覆盖整个临界区 | 锁是建议锁，所有参与者必须遵守 |
| 发布完整配置或构建产物 | 唯一临时文件 + `fsync` + 同目录 `rename` | 多写者版本竞争、目录持久化 |
| 多人实时编辑同一篇文档 | 服务端版本协议 + OT、CRDT 或冲突检测 | 这是应用层的合并语义，不是对普通文件逐字符加锁 |
| 高价值事务数据 | 数据库或日志服务 | 让专门的事务与恢复系统承担复杂性 |
| `mmap(MAP_SHARED)` 共享写 | 进程间锁或共享同步原语 | 页级可见性不等于记录级原子性 |

当写者分布在多台机器、需要全局顺序、去重、事务提交或权限审计时，把共享普通文件当作数据库使用通常不是一个好主意。文件系统给出的原子操作很有用，但它们并没有承诺替代事务协调器。

## 十三、总结

- 内核会保护 inode、页缓存和块映射等内部状态，保证并发写不会轻易破坏文件系统；这不等于它会维护应用记录的顺序与事务语义。
- 分别 `open` 同一文件的进程通常有各自的文件偏移；不用 `O_APPEND` 时，两个写者很可能覆盖同一位置。
- `O_APPEND` 使“定位当前 EOF 并写入”成为原子动作，适合追加日志；每条业务记录仍应一次提交或在完整记录期间持锁。
- `pwrite` 适合已分配好的不重叠区域；发生读改写竞争时，要用跨进程锁覆盖读取、判断和写回的整个临界区。
- 控制台日志的显示顺序由实际输出时机决定；它可能经过终端、管道或普通文件，不能凭屏幕上先后推导业务因果，也不能将 `PIPE_BUF` 误套到所有输出目标。
- 腾讯文档等协作编辑器需要在应用层保存版本并合并操作。操作系统保证底层资源可安全使用，却不会理解“同一段文字应如何合并”。
- 两个写者对同一个字节范围直接写入时，典型结果是一个写入覆盖另一个；但多字节字符、部分重叠范围和共享内存写入都使“只会覆盖一个字符”过于粗糙。
- 对完整文件发布，临时文件加原子 `rename` 比原地覆盖更适合；对崩溃恢复，还要考虑 `fsync`、目录同步和可校验的数据格式。
- `write` 成功、其他进程可见、断电后持久存在是不同层次的保证；`PIPE_BUF` 的消息原子性只属于管道/FIFO。

只要先把“字节位置”“一条记录”“完整版本”和“稳定存储”当作四个不同的边界，并发写文件就不再是一个玄学问题。操作系统负责提供原子步骤和同步工具；把这些步骤组织成正确的业务协议，仍然是程序本身必须完成的部分。
