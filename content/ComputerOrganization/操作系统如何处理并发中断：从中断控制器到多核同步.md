键盘、网卡、磁盘、定时器都可能在“同一时刻”需要 CPU 响应。于是又会出现一个看似简单的问题：CPU 一次只能跳到一个中断处理程序，操作系统怎样处理并发中断？会不会漏掉事件，或者两个处理程序把内核数据写坏？

核心结论是：**单个 CPU 核在任一时刻只能执行一条中断处理路径；硬件和内核通过“挂起、仲裁、优先级与延后处理”把同时到来的请求排成可处理的工作。多核机器上，多个核可以真正并行处理不同中断，但共享状态仍必须靠原子操作、锁和每 CPU 数据结构保护。**

这里的“并发”至少有三种含义。若不先分开讨论，答案大概只能停留在“加锁”这种缺乏解释力的层面。

| 情形 | 是否真的同时执行 | 主要处理方式 |
| ---- | ---------------- | ------------ |
| 同一核上多个设备同时请求 | 否 | 中断控制器挂起并仲裁；CPU 依次处理，必要时嵌套 |
| 一项中断处理期间又有中断到来 | 同一核通常不能同时执行 | 屏蔽、挂起、优先级与受控嵌套 |
| 多个核分别收到中断 | 可以 | 中断路由、每 CPU 队列、原子操作与锁 |

## 一、中断不是普通函数调用

中断是外部设备或定时器发出的异步通知。CPU 不知道它会在程序的哪条指令之间到来：应用可能正在计算，内核可能正在修改链表，另一个中断处理程序也可能正在运行。

发生中断时，CPU 与体系结构会先完成一个受控的 trap 进入过程：保存最基本的返回位置和状态，切换到相应特权级，按中断向量跳到入口代码。入口代码再保存更多寄存器、建立可信的内核执行环境，最后调用驱动或通用中断框架的处理函数。

简化为：

```text
普通代码正在执行
      │
设备提出 IRQ 请求
      ▼
中断控制器记录请求、选择目标 CPU
      │
      ▼
CPU 在可响应的边界进入中断入口
      │
      ▼
保存现场 → 确认来源 → 快速处理 → 触发后续工作 → 恢复现场
      │
      ▼
回到被打断的位置，或由调度器换到别的任务
```

异常和系统调用也会走类似的 trap 入口，但它们的来源不同：异常由当前执行的指令同步触发，系统调用由程序主动执行特殊指令，而硬件中断来自 CPU 外部。因此“中断来了以后才处理”在外部中断上成立；对缺页等同步异常，当前指令本身无法继续，必须先处理异常。

## 二、第一道关卡：中断控制器把请求保存并排序

设备不应直接争抢 CPU 的程序计数器。通常它们先通过中断控制器汇聚：传统 PC 常见 APIC/IOAPIC，RISC-V 平台可能使用 PLIC、AIA 等机制；PCIe 设备还可使用 MSI/MSI-X，把中断以总线消息形式发送。

具体寄存器名称因平台而异，但中断控制器大体承担这些职责：

- 记录某个中断源是否**挂起（pending）**；
- 根据掩码、目标 CPU 和优先级决定谁可被投递；
- 在多个请求到来时选择当前最合适的一项；
- 在 CPU 领取中断后标记它处于处理中；
- 在处理结束后接受完成通知，并继续投递下一项。

因此，两个设备同时发出请求时，正常情况不是“后一个覆盖前一个”，而是控制器和设备各自的状态把事件保留下来。CPU 先处理优先级较高或先被仲裁到的一项，另一项保持 pending，直到 CPU 再次允许接收中断。

不过“不会丢中断”也不能理解成无限长的事件队列。许多中断线的语义只是一个待处理位：同一来源在该位已经置位时连续来了十次，控制器可能只表达为“它仍然需要处理”。真实的数据或完成记录通常在设备自己的队列、状态寄存器或 DMA ring 中。高性能网卡正是让一个中断通知“接收队列里有工作”，处理程序随后批量取走多个报文，而不是为每个报文执行一次中断。

## 三、单核上为什么不会同时跑两个硬中断处理程序

一个 CPU 核一次只能取并执行一条指令，所以它不能让两个处理函数真正平行运行。关键在于：进入中断时，体系结构通常会临时关闭或降低本地可接收中断的条件，防止同级中断在入口尚未保存现场时再次打断它。

以常见模型概括：

```text
CPU 0 执行用户代码
  ├─ 网卡 IRQ 到来：进入网卡处理的顶半部
  │    ├─ 磁盘 IRQ 到来：控制器/CPU 将其保持为 pending
  │    └─ 顶半部结束，恢复可接收状态
  └─ CPU 随后进入磁盘 IRQ 处理
```

这是一种**串行处理**，不是忽略磁盘请求。若处理程序很短，延迟通常可以接受；若把复杂工作放在硬中断上下文里，后续中断和普通任务都会被拖慢，系统就会像被自己的热情绊倒一样。

### 1. 中断屏蔽保护的是什么

处理中经常需要暂时禁止本地中断，保护以下极短的临界区：

- 尚未完成的寄存器保存和内核栈切换；
- 同一 CPU 上可能被中断处理程序与普通内核代码同时访问的数据；
- 中断控制器的领取与完成顺序；
- 某些不允许重入的设备寄存器操作。

“禁止本地中断”只会阻止**当前 CPU**响应可屏蔽中断；它不自动阻止其他 CPU 运行，更不能替代多核共享数据的锁。这个差别很重要：把单核时代的 `cli/sti` 直觉照搬到多核系统，往往正好得到一个表面安静、实际竞态的程序。

### 2. 可否在中断中再响应更高优先级中断

可以，但是否允许、允许哪些类型，取决于 CPU 架构、控制器和内核策略。某些系统允许较高优先级中断在低优先级处理程序中嵌套进入；有些内核则倾向于先保持硬中断上下文很短，再尽快恢复中断，以控制复杂度。

嵌套中断需要额外处理两类问题：

- 每一层都要保存独立现场，并使用足够的内核栈空间；
- 被嵌套处理程序访问的共享状态必须可重入或受同步保护。

所以“优先级高就能随时插队”不是免费的优化。优先级和嵌套越多，最坏情况响应时间可能变好，验证正确性的难度也会迅速上升。

## 四、确认中断：先知道是谁，再让来源安静下来

外部中断到达后，内核不能只执行一段通用代码便返回；它必须确认来源并按设备协议清除或确认条件。不同硬件的顺序不同，常见操作包括：

1. 从中断控制器领取（claim / acknowledge）某个 IRQ；
2. 读取设备状态或完成队列，确定发生了什么；
3. 清除设备状态、消费队列条目，或通知设备已处理；
4. 向中断控制器报告完成（end of interrupt / complete）。

若设备采用**电平触发**中断，只要它的请求线仍保持有效，控制器就会认为请求尚未结束。此时若内核没有先清除真正的设备原因，刚完成中断又会再次被触发。若采用**边沿触发**，则必须确保设备内部状态或队列不会在边沿过去后被遗忘。

因此，处理程序的正确顺序依赖驱动和硬件文档，不能机械地记成“先 EOI”或“先清状态”。但原则稳定：**中断通知只是在说“状态可能变了”；真正的事实应以设备状态和队列为准。**

## 五、顶半部与底半部：不要在中断上下文里做太多事

硬中断上下文的首要目标是尽快恢复系统的可响应性。典型做法是把工作分成两段：

```text
硬中断（顶半部）
  领取 IRQ、读取必要状态、确认设备、把工作加入队列
                              │
                              ▼
延后执行（底半部）
  批量处理数据、协议栈、唤醒任务、可能执行更耗时的逻辑
```

在 Linux 中，延后机制可涉及 softirq、tasklet、workqueue、线程化 IRQ 等；它们的执行上下文、是否可被抢占、能否休眠并不完全相同。无需背下所有名称，先掌握分工更有价值：

- **顶半部**：短、不可阻塞、处理紧急的硬件确认；
- **软中断 / bottom half**：适合批量、可延后但仍有实时性要求的工作；
- **工作队列或内核线程**：适合可能等待锁、I/O 或需要睡眠的工作。

例如网卡 IRQ 的顶半部通常只确认设备并安排收包处理；之后网络栈在延后上下文中轮询 DMA 描述符环，一次处理一批包。这既减少中断风暴，也限制了单次中断占用 CPU 的时间。

由此得到一条实用规则：**硬中断处理程序一般不能睡眠。**它没有普通进程那样可以随意阻塞并稍后恢复的执行环境；若持有中断相关锁后等待资源，还可能造成死锁或极长的中断关闭时间。

## 六、多核时，真正的并行从哪里来

多核机器可以把中断路由到不同 CPU。例如一个网卡的多条接收队列配合 MSI-X，把不同队列的中断分散给不同核心；定时器中断也常是每 CPU 各自处理。这样 CPU 0 的网卡处理和 CPU 1 的磁盘完成处理确实能并行执行。

```text
网卡队列 0 ──IRQ──> CPU 0：处理接收 ring 0
网卡队列 1 ──IRQ──> CPU 1：处理接收 ring 1
磁盘完成队列 ──────> CPU 2：处理 I/O completion
```

这提高吞吐量，却把问题从“如何排队”变成“如何同步”。内核通常组合使用以下方法：

### 1. 每 CPU 数据，减少共享

让每个 CPU 拥有自己的中断统计、待处理队列、网络 ring 或缓存，处理时只访问本地数据。需要汇总时再以受控方式合并。减少共享往往比事后给所有数据加一把大锁更有效。

### 2. 原子操作与内存顺序

计数器、标志位、无锁 ring 的生产者/消费者索引等简单状态可用原子读改写维护。DMA 队列和跨 CPU 队列还必须配合内存屏障或语言/内核提供的 acquire-release 语义，保证“描述符内容已经写好”先于“就绪标志已发布”被另一个 CPU 或设备观察到。

### 3. 自旋锁与中断安全锁

对必须共享的内核结构，硬中断上下文通常使用不能睡眠的自旋锁。若同一把锁既可能被普通内核路径持有，也可能被本 CPU 的中断处理程序获取，普通路径在持锁期间还需暂时关闭本地中断，避免发生下面的自我死锁：

```text
CPU 0 的普通代码持有锁 L
      │
      └─ 被 IRQ 打断；IRQ 也试图获取锁 L
             │
             └─ IRQ 自旋等待，但能释放 L 的普通代码无法恢复
```

Linux 中常见的 `spin_lock_irqsave()` 一类接口正是为这类场景保存并关闭本地中断状态。它不是“任何地方都该使用”的万能锤；锁的选择必须依据数据会在哪些上下文、哪些 CPU 上访问。

### 4. 中断亲和性与负载均衡

把某个设备中断固定在处理相关任务的 CPU 上，可以改善缓存局部性；把所有高频 IRQ 堆到一个 CPU 上，则可能让它忙于硬中断而无暇运行用户任务。操作系统会提供 IRQ affinity、队列分配和负载均衡策略，管理员或驱动也可能按工作负载调整它们。

## 七、一次磁盘 I/O 完成的完整视角

把前面的机制连起来，假设进程发起一次读而数据尚未在页缓存：

1. 内核建立块 I/O 请求，并设置设备 DMA 目标页。
2. 当前进程因为等待数据而睡眠，调度器让其他任务运行。
3. 设备完成 DMA，向中断控制器报告完成。
4. 控制器将相应 IRQ 投递给某个可接收的 CPU；若该 CPU 正在处理中断，请求先保持 pending。
5. CPU 进入顶半部，领取 IRQ，读取完成队列并确认设备。
6. 驱动记录请求完成，必要时安排延后处理；内核把等待该 I/O 的任务标记为可运行。
7. 某次调度中，原进程获得 CPU；内核完成数据可见性处理，并将数据复制到其 `read` 缓冲区，或在映射场景中建立页表映射。
8. 系统调用返回用户态。

中断只负责把“设备状态改变了”及时送进内核。它不直接把一个被阻塞的进程瞬间变成正在运行，也不应在硬中断上下文中完成所有文件系统和用户内存操作；调度、页缓存和同步仍各自负责自己的部分。

## 八、常见误解

### 1. “同时来的中断一定按到达时间逐个处理”

不一定。优先级、触发类型、控制器仲裁和目标 CPU 状态都可能影响顺序。同一来源的多次事件还可能合并为一个 pending 状态，真正的工作量应从设备队列中读取。

### 2. “关中断就没有并发问题”

只对当前 CPU 的一部分可屏蔽中断有效。其他 CPU 仍可能同时修改共享数据；NMI 等不可屏蔽事件也不受普通屏蔽控制。因此，多核共享状态仍需正确的同步原语。

### 3. “中断处理程序越快，越应该把所有事都放进去”

恰好相反。顶半部应短，是为了让其他中断和系统任务尽快获得机会。数据量大、可能等待或能批量处理的工作应该延后。

### 4. “一次 IRQ 对应一份数据”

IRQ 是通知，不是数据包或磁盘块本身。一个 IRQ 可能对应一批完成项；多个事件也可能合并成一次可观察的“有工作”状态。

## 九、总结

- 单核上不会并行执行两个硬中断处理程序；中断控制器与 CPU 把未处理请求保持为 pending，并按策略依次投递。
- 中断进入时的屏蔽和现场保存保证入口安全；高优先级嵌套可以存在，但需要额外的可重入与栈空间设计。
- 驱动必须按照设备协议领取、确认和完成中断。真正的数据和完成记录通常在设备队列中，而不在 IRQ 本身里。
- 顶半部只做紧急且短小的工作，耗时任务交给软中断、工作队列或线程化处理，从而控制中断延迟。
- 多核能并行处理中断，但并行意味着共享状态需要每 CPU 设计、原子操作、内存顺序和锁来保护。

理解中断并发时，最可靠的思路是沿着三个问题追踪：**事件在哪里暂存、由哪个 CPU 在何时领取、领取后哪些状态仍可能被其他执行上下文同时访问。**能把这三件事说清楚，复杂的中断路径就不再只是“CPU 被打断了”这么一句模糊的叙述。
