“每个进程仿佛独享一整套内存”与“机器上的物理内存其实由所有进程共享”并不矛盾。前一句描述的是**进程所看到的虚拟地址空间**，后一句描述的是有限的 RAM 页框如何被内核统一分配。两者之间靠页表连接，但“哪块物理内存已经被占用”并不是虚拟内存自己凭空判断出来的，而是由操作系统维护的一套**物理页元数据和分配器**明确记录的。

先给出结论：

- CPU 的 MMU 根据页表回答“这个进程的某个虚拟页，目前映射到哪个物理页框”。
- 内核的物理内存管理器回答“哪个物理页框空闲、归谁使用、能否回收、还有多少引用”。
- 同一个物理页框可以同时被多个虚拟地址、甚至多个进程映射；因此“被占用”不等于“只属于一个进程”。

这三个事实分开看，问题就没有那么神秘了。内存管理本来已经够复杂，不需要再额外赋予它读心能力。

## 一、先区分三种容易混在一起的“内存”

讨论占用情况前，必须先把对象分开。

| 名称 | 管理者 | 它回答的问题 |
| ---- | ------ | ------------ |
| 虚拟页 | 某个进程的页表与内核 | 程序可以用哪个虚拟地址 |
| 物理页框 | 内核的物理内存管理器 | RAM 中哪一个固定大小的块可被分配 |
| 页表项 | MMU 与内核 | 一个虚拟页此刻映射到哪里、有什么权限 |

以常见的 4 KiB 页为例，RAM 会被切成许多个 4 KiB 的**物理页框**（page frame）。每个进程的虚拟地址空间也按同样大小切成**虚拟页**。程序写入的地址先被拆成：

```text
虚拟地址 = 虚拟页号 + 页内偏移
```

页表把“虚拟页号”翻译为“物理页框号”，偏移量保持不变：

```text
进程 A：虚拟页 0x120 ──> 物理页框 0x38A
进程 B：虚拟页 0x120 ──> 物理页框 0x6C1

两者虚拟地址相同，但访问的是不同的 RAM 位置。
```

因此，每个进程并不是逻辑上独享“机器全部真实 RAM”。它是逻辑上拥有一套很大的、彼此隔离的**地址空间视图**。其中有些页已对应 RAM，有些页尚未分配，有些页对应文件或交换空间；它们都不要求一开始占用同样多的物理内存。

## 二、页表能看到映射，却不是“空闲页总账本”

页表项（PTE）通常包含物理页框号以及存在位、读写执行权限、访问位、脏位等信息。例如可以把它简化理解为：

| 进程 A 的虚拟页 | PTE 的状态 | 含义 |
| --------------- | ---------- | ---- |
| `0x120` | present，PFN=`0x38A` | 已映射到 RAM 的页框 `0x38A` |
| `0x121` | not present，但属于合法内存区 | 第一次访问时可按需分配或调入 |
| `0x122` | 无有效映射 | 访问可能是非法地址 |

当 CPU 访问 `0x120` 时，MMU 可以从页表得知它使用了 `0x38A`。但若仅仅扫描所有进程的页表来判断每个页框是否空闲，会立刻遇到几个问题：

- 某些空闲页根本不会出现在任何页表中；
- 内核自身的数据、页表和设备 DMA 缓冲区也要使用物理页；
- 同一页可以被多个页表项共享，扫描时不能把它重复算成多份；
- 页缓存、交换缓存和正在回收的页有自己的生命周期。

所以页表的职责是**地址翻译和访问保护**，而物理页框的全局状态必须由独立的内核数据结构维护。关于“虚拟地址如何翻译”的基础过程，可先阅读[虚拟内存](虚拟内存.md)。

## 三、内核用什么记录物理页的状态

操作系统启动时会从固件或平台获得物理内存布局：哪些区间是可用 RAM，哪些被内核镜像、设备 MMIO、固件保留区占用。随后内核将可管理的 RAM 切成页框，并为每个页框维护元数据。

不同系统的数据结构名称不同。以 Linux 为例，常能在内核概念中看到每页对应的 `struct page` 或较新的 folio 抽象；其他系统也会有等价的页描述符。无需记住具体字段名，关键在于它至少要能表达这些事实：

- 此页是空闲、已分配、页缓存页、匿名页、页表页，还是不可管理的保留区域；
- 页是否被修改，能否直接丢弃，或必须写回文件/交换空间；
- 有多少映射或引用仍在使用它；
- 它在哪个内存节点、内存区域、空闲链表或回收链表中；
- 若被多个页表映射，内核怎样找到并撤销这些映射。

概念上可以想成如下总账本：

```text
物理页框  状态        引用/映射        备注
0x000      保留        -                内核启动代码
0x001      已分配      1                进程 A 的匿名页
0x002      页缓存      3                两个进程映射同一文件页
0x003      空闲        0                可供下一次分配
0x004      DMA 缓冲区  1                设备正在读写，暂不可回收
```

这不是物理 RAM 芯片里自带的一张表，而是内核保存在受保护内存中的管理信息。RAM 只存比特；“这 4 KiB 此刻能否分配给谁”是操作系统赋予它的语义。

## 四、从“空闲”到“被占用”：一次分配的过程

当进程通过 `malloc`、栈增长、加载程序或内存映射等方式需要内存时，用户态并不会直接拿走一个物理页框。一个典型流程是：

```text
进程请求或首次访问一段虚拟地址
        │
        ▼
内核确认该地址属于合法虚拟内存区域
        │
        ▼
物理页分配器从空闲页框集合中取出页框 P
        │
        ▼
更新 P 的页元数据：不再空闲、设置引用与用途
        │
        ▼
在当前进程页表写入“虚拟页 -> P”的映射及权限
        │
        ▼
必要时刷新或失效对应的 TLB 项
```

对于全新的匿名内存，系统通常还要保证进程读不到前一个使用者留下的数据，因此会提供逻辑上的零页内容，或在交付前将页面清零。安全性不能靠“上一位使用者大概没有秘密”这种相当随意的假设。

### 1. 空闲页通常怎样组织

最直观的表示是位图：每个页框对应一个 bit，`0` 表示空闲、`1` 表示已使用。实际内核为了高效处理连续页分配和并发，常会结合空闲链表、分区和分级分配算法；Linux 的伙伴系统（buddy allocator）就是一个典型例子。

伙伴系统将连续的页按 $2^n$ 个页为一组组织。请求 1 页时可从合适的空闲块中切分；释放后，若相邻“伙伴”也空闲，则合并回更大的块。它处理的是“从哪里拿一页或一组连续页”，而不是页表地址翻译本身。

### 2. 为什么物理页可能暂时没有立刻分配

现代系统采用按需分页。`malloc(1 GiB)` 或一次大的匿名映射，往往先只建立一段合法虚拟地址范围；真正写到其中的某个页时，才触发缺页异常并分配实际页框。

所以观察工具中看到的“虚拟内存大小”不等于“此进程当前独占的 RAM”。这也是把虚拟地址空间误读为物理占用时最常见的误会。

## 五、共享页面时，内核如何不把它过早回收

“页面已被占用”还不是二元判断。一个物理页可能由多个对象共同使用，内核必须记录引用关系。

### 1. 共享只读代码和文件页

两个进程运行同一个程序时，可执行文件的只读代码页常可只留一份物理副本：

```text
进程 A 的代码虚拟页 ─┐
                        ├──> 同一个文件页框 P
进程 B 的代码虚拟页 ─┘
```

此时 P 的“映射计数”或引用信息大于 1。只有所有映射撤销、缓存规则又允许回收时，内核才可回收它。对于干净的文件页，即使回收也只是丢弃 RAM 副本；以后访问时可再从文件读取。

### 2. `fork` 的写时复制

`fork` 后父子进程可以先共享原有的匿名页，并把双方映射改为不可直接写入。任意一方首次写该页时会触发保护异常，内核才复制一份新页给写入者，这就是 COW（Copy-On-Write）：

```text
fork 后：父页表 ─┐
                  ├──> 页框 P（只读共享）
        子页表 ───┘

子进程写入：为子进程分配页框 Q，复制 P 的内容，再把子映射改为 Q 可写
```

内核正是依靠页的引用计数、映射信息和页表权限，知道 P 尚不能释放，也知道何时需要复制。

### 3. 反向映射与页回收

从页表出发可找到“虚拟页映射到哪个物理页”；而内核在回收物理页时还经常需要反过来问：“这个物理页被哪些进程映射？”这类关联通常称为**反向映射**（reverse mapping）。

有了它，内核才能在换出、迁移或回收某个页时，撤销相关页表项并让对应 TLB 失效，而不是留下指向已复用页框的陈旧映射。后者若发生，进程就可能访问到别人的数据；这显然不是一种可以被称为“共享”的结果。

## 六、物理内存不足时，谁被腾出来

当没有足够空闲页框时，内核不会简单地随机把某个仍在使用的页标为空闲。它会根据页的类型和活跃程度尝试回收：

- **干净文件页**：内容仍在文件中，通常可以直接丢弃 RAM 副本；
- **脏文件页**：先写回文件，再回收；
- **不活跃匿名页**：可能写入交换空间，之后撤销驻留映射；
- **正在被 I/O 或内核固定使用的页**：通常不能立即回收；
- **仍有引用或锁定的页**：不能因为“看起来不常访问”便直接释放。

之后若进程再次访问已经被换出或丢弃的合法虚拟页，就会发生缺页异常，内核从相应来源重新准备页面。缺页处理首先检查的是“访问是否合法”，不是一概把页面从磁盘搬回来；非法地址访问最终仍会成为访问违规或段错误。

## 七、把问题串起来

可以把“虚拟独享”与“物理共享”画成两层：

```text
进程 A 虚拟页 0x10 ──> 页表 ──> 物理页框 P
进程 B 虚拟页 0x10 ──> 页表 ──> 物理页框 Q
进程 C 虚拟页 0x80 ──> 页表 ──> 物理页框 P（允许共享时）

                                    ▲
                                    │
                   内核页分配器维护 P、Q 的状态、引用、回收资格
```

页表说明的是**某次地址访问会去哪里**；页分配器和页元数据说明的是**哪些物理页可用、哪些正在被谁以何种方式使用**。前者偏向每个地址空间，后者是全局账本。它们共同维持隔离、共享与回收。

## 八、总结

- 进程独享的是虚拟地址空间的视图，不是把全部物理 RAM 复制一份给它。
- 页表记录虚拟页到物理页框的映射和权限；它不承担完整的全局空闲页管理职责。
- 内核为每个物理页维护状态、引用、映射、脏页和回收信息，并通过物理页分配器管理空闲页。
- 多个虚拟页可以共享一个物理页框，代码共享、文件映射和写时复制都是正常情形。
- 回收或复用页面前，内核必须处理引用、反向映射和 TLB，确保没有任何页表仍错误地指向它。

因此，物理内存“知道”自己是否被占用，并不是硬件逐页自我声明，而是内核用严格的页元数据和分配规则持续记账的结果。
