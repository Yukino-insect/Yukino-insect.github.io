我们常说“分配了一块连续内存”，随后会看到 `base + n`、`p++`、`memcpy(dst, src, length)` 这样的操作。于是很自然地会问：这块空间只能加减以字节计的**长度**，为什么不能再加减一个“宽度”？

结论先说：**普通内存地址空间在程序看来是一条一维、通常按字节编号的数轴。**一块连续内存就是数轴上的一个连续区间，只有“从起点向前走多少个地址单位”这一种位移。所谓“访问宽度”“总线宽度”“二维数组的一行有多宽”都是真实而重要的概念，但它们属于不同层次，不是地址空间的第二个坐标轴。

## 一、连续内存是一个半开区间，不是一块平面

若一块内存的起始地址为 `base`，大小为 `size` 字节，最准确的抽象是：

```text
[base, base + size)
```

它包含 `base` 到 `base + size - 1` 的所有字节地址，却不包含 `base + size`。这种“左闭右开”写法与数组下标范围 `0` 到 `size - 1` 完全对应，也便于相邻区域无缝衔接：

```text
地址：  base      base+1    base+2             base+size-1   base+size
       ┌────────┬────────┬────────┬──── ... ───┬────────────┐
内容： │ 1 字节  │ 1 字节  │ 1 字节  │           │   1 字节    │
       └────────┴────────┴────────┴──── ... ───┴────────────┘
       <------------------ size 个字节 ------------------->
                                                              ↑
                                                       区间结束，不属于它
```

这里的“连续”只说明：区间内相邻的逻辑地址依次相差 1，没有地址缺口。它并不表示内存条上真的存在一根可供程序沿“横向”或“纵向”移动的尺子。地址本质上是一个整数编号；对一个地址做加减，就是在这条编号轴上前进或后退。

在 x86、Arm、RISC-V 等常见平台上，地址的基本单位是**字节**。因此：

```text
base + 1  → 后一个字节
base + 8  → 往后第 8 个字节
base - 4  → 往前第 4 个字节
```

少数历史机器或特殊设备会采用字编址等方式，最小地址单位未必是 8 位；不过“地址空间是一维离散编号”这个核心并不改变。所谓按字节加减，只是今天主流机器选择“一个编号对应一个字节”的具体约定。

## 二、“宽度”至少可能指四种不同的东西

“宽度”这个词本身没有错，问题在于它常被拿来指代不相干的概念。先把它拆开：

| 可能说的“宽度” | 所属层次 | 是否能作为 `地址 + ?` 的独立方向 |
| --- | --- | --- |
| 一次读写多少字节 | CPU 指令/访问宽度 | 否；它决定读取范围，不增加坐标轴 |
| 数据总线一次传多少位 | 硬件传输宽度 | 否；它影响传输并行度和带宽 |
| 二维数组的一行有多少列 | 数据布局/逻辑宽度 | 否；它用于把两个下标折叠为一个偏移 |
| DRAM 的 row/column | 内存控制器内部组织 | 否；软件只见线性的物理地址 |

所以“不能加减宽度”并不是说内存没有宽度相关属性，而是说它们不会像平面坐标中的 `x` 和 `y` 一样，成为两个可以独立移动的地址维度。

## 三、访问宽度：一次读 8 字节，不代表地址跳到了另一个维度

CPU 的一条加载或存储指令通常由“起始地址 + 访问大小”决定。例如：

```text
从地址 0x1000 读取 4 字节
覆盖的字节范围是 [0x1000, 0x1004)

从地址 0x1000 读取 8 字节
覆盖的字节范围是 [0x1000, 0x1008)
```

它们都从同一个一维地址 `0x1000` 开始，只是第二条指令覆盖了更长的连续区间。可以把它理解为用一把 4 厘米或 8 厘米的尺子在同一条直线上量一段，而不是把尺子转向了一条新的“宽度轴”。

```text
地址：  0x1000  0x1001  0x1002  0x1003  0x1004  0x1005  0x1006  0x1007
        ├────── 4 字节 load ──────┤
        ├──────────────────── 8 字节 load ────────────────────┤
```

这也解释了为什么一个 8 字节 `long` 或 `double` 往往占据 8 个相邻字节：对象有**大小**，但对象内部第 0、1、2……个字节仍然沿同一地址线排开。CPU 根据 load/store 的宽度、字节序和指令语义，把这些字节组合并解释为一个值。

### 位为什么通常不能直接做地址单位

一个字节有 8 位，但普通 CPU 通常不能对“地址 `0x1000` 的第 3 位”发起独立的内存读写。最低可寻址单位是字节；要读取或修改其中某一位，通常需：

1. 读出包含它的整个字节或机器字；
2. 用掩码、移位、与/或/异或等操作取出或修改目标位；
3. 必要时写回。

例如要判断某字节的第 3 个低位是否为 `1`，可使用 `value & (1 << 3)`。原因与硬件接口、效率和历史设计有关：让每一个比特都拥有独立地址会使地址空间和控制电路复杂得多，而绝大多数软件以字节为粒度处理文本、文件和对象已经足够高效。

## 四、为什么 C 里的 `int* + 1` 看起来不是加 1 字节

C 的指针运算经常造成另一种错觉：

```c
int values[3] = {10, 20, 30};
int *p = values;

p = p + 1;  // 指向 values[1]
```

若 `sizeof(int) == 4`，这个 `p + 1` 在底层地址上是加 **4 个字节**，不是加 1 个字节：

```text
地址偏移 = 元素个数 × sizeof(元素类型)
```

编译器知道 `p` 是 `int *`，于是把“向后一个元素”换算成正确的字节偏移。换成 `char *` 时，`p + 1` 才是加 1 字节；换成 `double *` 时，常见平台上可能加 8 字节。

```c
char   *cp = (char *)base;  // cp + 1：地址 + 1
int    *ip = (int *)base;   // ip + 1：地址 + sizeof(int)
double *dp = (double *)base;// dp + 1：地址 + sizeof(double)
```

这不是内存突然拥有了“按 int 的长度”和“按 byte 的宽度”两套坐标。它只是语言替人完成了单位换算。汇编或机器指令层面最终仍是把一个以字节计的偏移加到地址寄存器上。

还要注意，C 只定义在**同一个数组对象范围内**的指针加减；允许指向“尾后一个位置”以便比较或作为范围终点，但不能解引用它。越过边界继续运算、把随便两个对象的指针相减，在语言层面可能是未定义行为。硬件有地址，绝不等于语言允许你对所有地址为所欲为。

## 五、二维数组的“宽度”如何变成一维偏移

屏幕、图像和矩阵显然有行与列。那它们存进一维地址空间时怎么办？答案是规定一种布局，把二维坐标映射成一个线性偏移。C 的普通二维数组采用**行主序**（row-major order）：先连续存完一行，再存下一行。

```c
int matrix[3][4];  // 3 行、每行 4 个 int
```

逻辑上它像这样：

```text
          列 0   列 1   列 2   列 3
行 0       [0,0]  [0,1]  [0,2]  [0,3]
行 1       [1,0]  [1,1]  [1,2]  [1,3]
行 2       [2,0]  [2,1]  [2,2]  [2,3]
```

实际内存却是一条线：

```text
[0,0] [0,1] [0,2] [0,3] [1,0] [1,1] [1,2] [1,3] [2,0] ...
```

若每个元素大小为 `element_size`，元素 `matrix[row][column]` 的字节地址是：

```text
base + (row × column_count + column) × element_size
```

这里的 `column_count` 常被口语称为“一行的宽度”。它不是一个可以单独加到地址上的方向，而是**计算下一行起点时的步长**。从 `[0,3]` 到 `[1,0]`，并不是“横向走到头后再竖直向下”；内存中只是线性偏移从 3 变为 4。

列主序（column-major order）则先存完一列，再存下一列，公式改为：

```text
base + (column × row_count + row) × element_size
```

Fortran、部分数学库和 GPU 数据布局中常见它。两种方式改变的是“二维逻辑坐标到一维地址”的映射规则，而非底层内存变成二维。

### 图像的宽度与 stride

图像最能说明这个区别。一张宽 1920 像素、每像素 4 字节的 RGBA 图像，紧凑情况下每行数据是：

```text
1920 × 4 = 7680 字节
```

但实际每行可能因对齐而有额外填充，称为 `stride` 或 `pitch`。像素 `(x, y)` 的地址常写成：

```text
base + y × stride + x × bytes_per_pixel
```

`stride` 是“逻辑下一行在一维缓冲区中相隔多少字节”，并非第二个地址轴。它甚至可能大于 `width × bytes_per_pixel`，此时行末填充字节不属于可见像素，却仍占用线性内存空间。

## 六、DRAM 的行、列与内存条宽度为什么也不是软件坐标

DRAM 芯片在物理实现中确实按 bank、row、column 组织，内存通道也确实有例如 64 位数据总线的传输宽度。可是程序使用一个物理地址时，CPU 先经缓存与互连，再由内存控制器把地址位映射到通道、rank、bank、行和列：

```text
物理地址 → 内存控制器的地址映射 → channel / bank / row / column
```

不同平台能以不同规则拆分地址位，甚至交织连续缓存行到不同通道和 bank 以提升带宽。程序无法可靠地对一个指针做“行号加一”或“总线宽度加一”来移动；它唯一稳定、架构提供的抽象仍是地址加字节偏移。硬件的二维或多维组织被地址译码器隐藏起来，这正是分层抽象应做的事，不必为它感到委屈。

## 七、连续的是虚拟地址，还是物理地址

程序申请到的一块连续内存，通常首先意味着**虚拟地址连续**。例如 `malloc(8192)` 返回一个起点后，进程可用连续虚拟地址访问这 8192 个字节。

底层的两个 4 KiB 虚拟页却可以映射到并不相邻的物理页框：

```text
连续虚拟页：  VPN 0x4000      VPN 0x4001
                   │               │
                   ▼               ▼
物理页框：     PFN 0x91A      PFN 0x2C7
```

MMU 在跨页时分别翻译地址，程序仍然得到连续的逻辑空间。只有内核、DMA 或某些硬件接口明确要求**物理连续**内存时，分配器才需要寻找连续的页框；这种资源更稀缺，不能把普通的“连续缓冲区”理所当然地等同于它。

此外，地址连续并不保证所有访问都合法或等价：页边界、读写执行权限、对象生命周期、对齐要求和缓存一致性都可能施加限制。连续只是地址关系的一种性质，并不是一张“什么都可以做”的通行证。

## 八、对齐：为何地址加了正确长度仍可能不该访问

一些类型或指令要求起始地址是特定倍数，例如 4 字节对象最好或必须位于 4 的倍数地址，8 字节对象位于 8 的倍数地址：

```text
4 字节对齐：address mod 4 = 0
8 字节对齐：address mod 8 = 0
```

对齐能使硬件以更少的内部操作读取对象；在某些架构或特定 SIMD 指令上，未对齐访问会更慢、需要多次访问，甚至触发异常。结构体中的 padding（填充）也是因此出现：它让后续成员落在合适的边界上。

例如 `char` 后跟 `int` 的结构体，常见布局不是 1 + 4 = 5 字节，而可能在 `char` 后插入 3 字节填充，使 `int` 从 4 字节对齐的位置开始。内存仍是线性的；只是这条线上有一些不表示业务字段的空位。

## 九、总结

- 一块连续内存可抽象为 `[base, base + size)`：它是一维地址区间，主流平台中每个地址对应一个字节。
- 地址加减移动的是线性字节偏移；访问宽度决定一次覆盖多少相邻字节，不能成为第二个地址方向。
- C 的类型化指针运算会把“几个元素”换算为字节偏移，底层仍是单一地址轴。
- 二维数组、图像宽度和 `stride` 是将二维逻辑坐标压平成线性地址的规则，不意味着内存地址空间是二维。
- DRAM 的行列、总线位宽属于硬件实现；虚拟地址连续也不保证物理页连续。
- 对齐、页权限、对象边界等约束仍然存在。能算出一个地址，不等于可以安全地访问它。
