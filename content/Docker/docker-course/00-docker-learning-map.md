Docker 容易给人一种“记住几条命令就够了”的印象：拉一个镜像，映射一个端口，服务似乎就跑起来了。可一旦数据不见、容器互相连不上、构建变慢、启动顺序出错，或者准备把配置交给团队复用，那些零碎命令很快就不够用了。

## 学完以后应具备什么能力

完成本专题后，你应当能做到：

- 区分镜像、容器、仓库、卷和网络，并说明它们各自的生命周期。
- 用 `docker run` 启动、检查、进入、停止和清理一个容器，而不是遇到异常就删掉重来。
- 阅读并编写基础 Dockerfile，理解构建上下文、分层缓存和多阶段构建为什么会影响速度与安全性。
- 用 Compose 把多个服务、网络、数据卷、健康检查和环境变量声明为一个可重复的开发栈。
- 在容器之间正确使用服务名通信，在宿主机和容器之间正确使用端口映射，并让状态数据落在预期的位置。
- 解释 Docker 的隔离不是虚拟机魔法：它主要依赖 Linux 的 namespace、cgroup 和分层文件系统；同时知道这一隔离的安全边界。
- 对“启动失败、服务不通、数据丢失、内存不足、日志看不到、镜像过大”等常见问题，按证据而不是猜测进行排查。

## 开始前的约定

本文所有命令以 Docker Desktop 或 Linux Docker Engine 的当前 Docker Compose v2 插件为前提，因此使用 `docker compose`（有空格），不使用旧的 `docker-compose` 独立命令。Windows 与 macOS 上运行 Linux 容器时，Docker Desktop 通常通过一个轻量 Linux 虚拟机提供内核能力；这会影响文件挂载性能、路径写法和访问宿主机的方式，课程会专门说明。

请不要把以下示例当成生产模板：`latest` 镜像标签、明文密码、把数据库端口暴露到公网、`privileged: true`、为图省事关闭安全限制。它们有时能使演示更短，却会让故障和安全风险更长。这样的交换并不划算。

## 课程地图

### 1. 从容器的基本操作开始

[Docker 入门：容器、镜像、仓库与第一套日常命令](01-docker-basics.md) 先解决最基本的问题：Docker 到底在运行什么，怎样验证环境、启动首个容器、查看日志和状态、进入容器排查，以及容器删除与镜像删除有什么根本差别。请先完成这一篇的动手步骤，再往下读。

### 2. 将运行环境写成镜像

[Docker 镜像与 Dockerfile：从构建上下文到多阶段构建](02-images-dockerfile.md) 解释 Dockerfile 的每条核心指令、镜像层和缓存命中规则，并解剖案例中的 `neo4j-gds.Dockerfile`：为什么把已验证的插件下载到镜像构建阶段，能避免容器每次启动重复下载。这里还会处理 `.dockerignore`、非 root 运行、标签策略和构建排错。

### 3. 给服务正确的网络与数据边界

[Docker 网络与数据持久化：端口、DNS、卷与备份](03-network-storage.md) 处理最容易混淆的两件事：容器访问容器时为什么用服务名和容器端口，浏览器访问服务时为什么用宿主机端口；以及容器可写层、命名卷、绑定挂载和 `tmpfs` 到底该如何选择。数据库和消息队列的状态数据不能只是“看起来还在”。

### 4. 把多服务项目声明为 Compose 栈

[Docker Compose 实战：从 YAML 到可重复的本地开发栈](04-compose-practice.md) 将前面独立的容器组合为一个项目，详解 `services`、`networks`、`volumes`、环境变量插值、`healthcheck`、`depends_on`、`profiles`、重启策略和调试命令。`local-dev-stack.compose.yaml` 与图谱栈会作为阅读配置的实战素材；先用 `docker compose config` 看最终解析结果，再启动，远比直接祈祷 YAML 没写错可靠。

### 5. 知道隔离如何实现，才能更稳地运维

[Docker 底层原理与工程化运维：namespace、cgroup、OverlayFS 与安全](05-internals-operations.md) 从 Docker Engine、containerd 与 runc 的职责一路讲到 Linux namespace、cgroup、OverlayFS 的写时复制；随后把资源限制、日志、健康检查、安全基线、镜像供应链与故障排查组织成可执行的工程实践。理解它并不要求你亲自实现容器运行时，但可以防止把 Docker 当作不需要边界的黑箱。

## 推荐学习与练习顺序

1. 在第 1 篇完成环境验证和最小容器练习，记录 `docker ps -a`、`docker logs` 与 `docker inspect` 的输出分别回答什么问题。
2. 在第 2 篇先读 Dockerfile，再运行一次构建；只修改源码和只修改依赖文件各构建一次，观察缓存差异。
3. 在第 3 篇用两个容器验证服务名 DNS 与端口映射，并尝试删除容器后检查命名卷的数据是否仍在。
4. 在第 4 篇只挑资源目录里的一个 Compose 文件，用 `docker compose config`、`up`、`ps`、`logs` 和 `down` 走完整生命周期。涉及 `.env` 的栈请复制模板为本地 `.env`，不要提交真实密钥。
5. 最后阅读第 5 篇，把前四篇碰到的“为什么”重新对应到隔离、资源、存储和安全机制上。

## 一份简短的前置检查清单

开始前，在终端运行：

```bash
docker version
docker compose version
docker run --rm hello-world
```

前两条验证客户端、服务端和 Compose 插件是否可用；第三条会拉取一个很小的镜像、创建并运行一次临时容器，成功后自动删除。若这里已经失败，不要跳过错误信息直接安装一堆替代工具：把完整报错、操作系统、Docker Desktop 或 Engine 版本记录下来，按第 1 篇的检查路径处理即可。

## 总结

- Docker 的价值是把应用及其运行依赖变成可声明、可构建、可交付的单元，而不是取代操作系统、网络、备份和安全设计。
- 课程顺序刻意是“单容器 → 镜像 → 网络与数据 → 多服务编排 → 底层与运维”；后面的每一步都建立在前一步已经看清楚的对象和生命周期之上。
- 真正值得形成的习惯是：先检查状态和配置，再根据证据改动；不要用删除容器来代替理解问题。
