很多服务平时只处理 JSON、数据库记录和 HTTP 响应，看起来与字体毫无关系。直到某天它需要生成海报、订单 PDF、验证码图片、数据报表、二维码说明图，或者把网页截图保存为图片：中文突然变成一排方框、空白或问号。应用没有报错，图片文件也成功上传了，结果却不可读。

这类问题的核心不是字符编码，而是**运行环境缺少能够绘制中文字符的字体文件**。如果服务端要把文字渲染为位图、PDF、SVG 或浏览器截图，中文字体包就是运行时依赖，而不是“桌面美化资源”。本文以 Java 在 Docker 容器中生成图片为主线，解释字体包的作用、为什么宿主机能显示而容器不能、怎样正确安装和验证，以及哪些替代方案适合不同场景。

## 一、先区分三件容易混淆的事

遇到中文显示异常时，首先不要把所有问题都归为“乱码”。以下三层的职责不同，修复方法也完全不同。

| 层次 | 负责什么 | 典型故障 | 常见修复 |
| ---- | -------- | -------- | -------- |
| 字符编码 | 字节如何还原为字符，例如 UTF-8 | `中文` 变为 `ä¸­æ–‡` | 统一文件、数据库、HTTP 的编码 |
| 字体 | 某个字符该画成什么形状 | 显示为 `□`、空白或替代符号 | 安装或内置含中文字符的字体 |
| 排版与渲染引擎 | 字符如何断行、组合、定位和输出 | 标点错位、复杂文字连写错误、换行异常 | 选择支持目标文字的渲染引擎与字体 |

UTF-8 只解决“程序知道这是 `中` 这个字符”，并不提供“如何把 `中` 画出来”的字形数据。字体文件保存了这种字形轮廓、度量信息和字符到字形的映射。缺少字体时，渲染引擎只能拿到字符，却找不到对应图案，于是以缺字方框（常被称为 tofu）、问号或空白代替。

可以把流程概括为：

```text
UTF-8 字节
  -> Unicode 字符：中、文、海、报
    -> 字体查找：这个字体是否有对应 glyph（字形）？
      -> 有：按字形与排版规则绘制
      -> 没有：绘制缺字方框 / 替代符号 / 空白
```

因此，数据库里能正确保存中文、日志里也能正确打印中文，并不能证明服务端生成的图片一定正确。前两者通常只需要编码；后者必须真正依赖字体。

## 二、为什么本机正常，容器里却出现方框

开发者经常在 Windows 或 macOS 上测试成功，然后部署到 Linux 容器才发现问题。这不是 Docker 修改了字符串，而是宿主机与容器拥有不同的文件系统和字体集合。

桌面操作系统通常预装了大量字体：Windows 常见微软雅黑、等线、宋体；macOS 有苹方等字体。浏览器或 Java 的字体回退机制能从这些字体中找到中文。相比之下，面向服务端的 JRE 基础镜像会尽量精简，往往只含拉丁文字体，甚至完全没有字体配置。

容器隔离使它不能自动读取宿主机的字体目录：

```text
开发机
  C:\Windows\Fonts 或 macOS 字体目录
  -> 本地 Java / 浏览器可找到中文字体

Linux 容器
  /usr/share/fonts
  -> 只有基础拉丁字体，或没有中文字体
  -> 渲染中文时缺少 glyph
```

即使 Docker Desktop 运行在 Windows 或 macOS 上，Linux 容器看到的仍是 Docker 虚拟机中的 Linux 文件系统，而不是宿主机字体目录。把“我的电脑已经有字体”当作镜像依赖，和把“我的电脑已经装了 Maven”当作生产容器依赖一样，并不成立。

## 三、`SansSerif`、`Arial` 不是中文字体保证

Java、浏览器和图形库常允许使用逻辑字体名，例如 Java 中的 `SansSerif`、`Serif`、`Monospaced`。这类名称表达的是“无衬线”或“等宽”风格，不是某个自带全部字符的字体文件。

例如下面的代码在桌面系统上可能正常，在精简 Linux 镜像中却可能生成方框：

```java
graphics.setFont(new Font("SansSerif", Font.BOLD, 64));
graphics.drawString("校园微墙", 118, 290);
```

Java 会尝试把 `SansSerif` 映射到系统可用字体，并可能继续尝试字体回退。但回退的前提仍然是：系统里至少有一个字体包含这些汉字。如果整个镜像都没有 CJK（Chinese, Japanese, Korean）字形，逻辑字体名再优雅也无济于事。

同理，写成 `Arial`、`Helvetica` 或 CSS 的 `sans-serif` 也不等于支持中文。字体是否可用，应以它能否显示目标字符为准，而不是名称听起来是否“通用”。

## 四、中文字体包实际提供了什么

以 Linux 中常用的 Noto CJK 字体为例，字体包通常提供以下能力：

- **中文字形**：常用汉字、扩展字符、中文标点、全角符号等的轮廓数据。
- **字体元数据**：字体家族、字重、样式、字符覆盖范围等信息，供 Fontconfig、Java、浏览器和 PDF 引擎查找。
- **回退候选**：当应用指定的主字体没有某个字符时，渲染系统可从已安装字体中选择覆盖该字符的字体。
- **排版度量**：字宽、基线、行高等数据，直接影响自动换行、居中、截断和海报布局。

它并不改变文本内容，也不负责把 GBK 转为 UTF-8；它的职责是将已经正确解码的 Unicode 字符变成可见像素或矢量路径。

对于一个生成海报的服务，字体包会影响所有文字区域：用户昵称、帖子正文、分类标签、日期、底部提示、二维码旁说明文字。仅修复标题而遗漏正文，仍然会得到一张半正常、半失效的图片；这种结果并不比完整失败更容易维护。

## 五、在 Docker 镜像中安装中文字体

最简单且可复现的做法，是在 Dockerfile 中显式安装字体。下面以 Debian/Ubuntu 系的 OpenJDK 或 Eclipse Temurin JRE 镜像为例：

```dockerfile
FROM eclipse-temurin:17-jre

RUN apt-get update \
    && apt-get install -y --no-install-recommends fonts-noto-cjk \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY target/app.jar app.jar

ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

这里每一部分都有明确作用：

- `fonts-noto-cjk`：安装包含中日韩字符的 Noto 字体；字体名会随发行版和 Fontconfig 元数据略有差异。
- `--no-install-recommends`：避免因推荐包引入不必要的工具与数据，减少镜像膨胀。
- 删除 `apt` 缓存：缓存只对构建层有用，不应留在运行时镜像中。

若基础镜像是 Alpine，包管理器和包名不同，不能把 `apt-get` 原样复制过去：

```dockerfile
FROM eclipse-temurin:17-jre-alpine

RUN apk add --no-cache fontconfig font-noto-cjk
```

具体包名要以所选 Alpine 仓库为准。有些 Alpine 版本会将字体拆分为多个包；构建失败时，应先查询仓库包名，而不是退回到“先不装字体看看”的侥幸策略。

### 1. 为什么不建议依赖宿主机挂载字体

可以把宿主机字体目录 bind mount 到容器中，但它通常只适合作为临时排障手段：

```yaml
services:
  app:
    volumes:
      - /usr/share/fonts:/usr/share/fonts:ro
```

它的问题在于：

- 镜像不再自包含，换一台机器可能立刻失效。
- 宿主机字体版本与许可状态不受镜像构建记录控制。
- Windows、macOS、Linux 的字体路径不同，部署可移植性很差。
- 挂载过宽的宿主目录会扩大容器可见范围，也让排查更困难。

对需要稳定输出图片、PDF 或截图的生产服务，应把开源、许可清晰的字体作为镜像依赖固定下来。Noto Fonts 是常见选择；若业务对字形、品牌或特定少数民族文字有要求，则应根据字符覆盖、许可证和设计规范选择专门字体。

## 六、应用代码也应显式选择并校验字体

安装字体是必要条件，但代码仍应避免默默接受错误回退。一个更稳妥的 Java 策略是：优先选择已知字体家族，并在启动或首次生成图片时验证它确实能显示业务需要的中文样本。

```java
import java.awt.Font;
import java.awt.GraphicsEnvironment;

public final class PosterFonts {
    private static final String SAMPLE = "校园微墙匿名同学长按扫码";

    private PosterFonts() {
    }

    public static Font resolveBaseFont() {
        for (String family : new String[]{"Noto Sans CJK SC", "Noto Sans SC"}) {
            Font font = new Font(family, Font.PLAIN, 1);
            if (font.canDisplayUpTo(SAMPLE) == -1) {
                return font;
            }
        }

        for (Font font : GraphicsEnvironment.getLocalGraphicsEnvironment().getAllFonts()) {
            if (font.canDisplayUpTo(SAMPLE) == -1) {
                return font;
            }
        }

        throw new IllegalStateException("当前运行环境没有可显示中文的字体");
    }
}
```

`Font.canDisplayUpTo(text)` 返回 `-1` 表示该字体可以显示整段文本；否则返回第一个无法显示字符的位置。样本不应只写一个“中”字，应覆盖应用实际会渲染的类别，例如中文、数字、常见标点和业务提示词。

随后按字号和字重派生字体：

```java
Font baseFont = PosterFonts.resolveBaseFont();
graphics.setFont(baseFont.deriveFont(Font.BOLD, 64F));
graphics.drawString("欢迎来到校园论坛", 118, 290);
```

这一步的价值在于把“输出了方框但没有异常”的静默故障，变成部署或测试阶段可见的明确错误。对于营销海报、票据和对外报告，宁可任务失败并报警，也不应把不可读文件当作成功结果继续发送。

## 七、如何在镜像与容器中验证

不要只看 Dockerfile 写了安装命令。字体包、字体缓存、应用运行用户和实际渲染路径都可能影响结果，应在构建后验证。

### 1. 查看 Fontconfig 识别到的字体

多数 Linux 镜像可使用 `fc-list`：

```bash
docker run --rm your-image:latest \
  fc-list :lang=zh family | sort -u
```

预期能看到类似 `Noto Sans CJK SC` 的字体家族。若命令不存在，说明镜像可能没有 `fontconfig` 工具；这不必然代表字体不存在，但会让诊断不便。可在排障镜像中临时安装工具，或直接检查 `/usr/share/fonts` 下的文件。

### 2. 用真实图片生成链路做集成测试

列出字体只能证明“文件被识别”，不能证明应用参数正确。更可靠的测试应调用实际的海报、PDF 或截图生成路径，然后断言：

- 输出文件格式正确且非空；
- 文件像素中存在预期文字区域，而不是整块空白；
- OCR、快照测试或人工检查确认关键中文可读；
- 在 CI 使用与生产相同的基础镜像执行该测试。

对于图形差异不大的场景，可保存一张基准图片做 snapshot test；对于包含时间、头像、随机二维码等动态内容的海报，可固定输入、屏蔽动态区域，或用 OCR 只验证关键文字。重点不是选择最花哨的工具，而是让“中文字体被意外删除”能在发布前被发现。

### 3. 重建镜像，而不是只重启容器

Dockerfile 改动只影响之后构建的新镜像。以下命令会重新构建并替换服务：

```bash
docker compose build --no-cache app
docker compose up -d --force-recreate app
docker compose logs --tail 100 app
```

是否使用 `--no-cache` 取决于构建缓存是否可信；排查字体安装问题时，它能避免旧的 `RUN` 层让人误以为依赖已经更新。生产发布则应使用明确版本或镜像 digest，并保留构建记录。

## 八、字体包带来的体积、许可与安全取舍

中文字体包通常比拉丁文字体大得多，因此会增加镜像体积。这是合理成本，但仍需要有意识地管理。

### 1. 不要为“减小镜像”牺牲正确性

如果服务根本不生成文本视觉内容，当然没必要安装字体；但一旦服务负责生成中文图片、PDF、邮件截图、Office 文档或浏览器页面，字体就是功能依赖。为了少几十或上百 MB 而让输出随机失效，节省的是镜像体积，增加的却是事故概率和排查时间。

正确的优化顺序是：

1. 选择覆盖业务字符集、许可证合适的字体，而不是安装所有字体包。
2. 使用 `--no-install-recommends`、多阶段构建和合理的基础镜像，删除包管理缓存。
3. 不把构建工具、测试数据和无关语言运行时带入最终镜像。
4. 对极端体积敏感的场景，评估字体子集化，但必须有覆盖率测试。

字体子集化会移除未使用字形，适合字符集合稳定的嵌入式设备或固定模板。它不适合昵称、帖子正文、用户上传文本等开放输入：你无法提前知道下一个用户会输入哪个汉字或符号。对这类服务，完整的 CJK 字体通常更可靠。

### 2. 字体也有许可证

字体不是“网上下载一个 TTF 放进去”就结束了。商业字体常限制嵌入、再分发、Webfont 使用或容器镜像分发；把它复制进镜像可能构成再分发。应在选型时确认：

- 许可证是否允许服务器和容器环境使用；
- 是否允许随镜像、安装包或静态资源再分发；
- 是否需要在产品、文档或许可证文件中保留声明；
- 是否允许子集化、修改和嵌入 PDF。

Noto 系列采用开放字体许可证，是服务端中文渲染的常见工程选择之一。但“开源字体”也不意味着不必阅读许可证；把许可信息纳入依赖审计，才是可维护的做法。

### 3. 将字体当作供应链依赖

字体包来自操作系统仓库或内部制品库，也应和其他依赖一样处理：固定基础镜像版本、定期重建、关注安全公告、在 SBOM 中保留依赖信息。字体解析器曾出现过安全漏洞；虽然攻击面通常低于直接处理不可信字体上传的系统，但不应因为它看起来只是资源文件就完全忽略更新。

若允许用户上传字体并在服务端加载，风险会明显增加。除非确有明确业务需求，否则不要将用户提供的字体直接交给渲染引擎；至少应进行格式、大小、来源、隔离和病毒扫描等控制。

## 九、不同输出方式的字体责任边界

并非所有“显示中文”的场景都由服务端容器负责，判断清楚责任边界可以避免重复安装或错误排查。

| 输出方式 | 字体主要由谁提供 | 容器是否通常需要中文字体 |
| -------- | ---------------- | ------------------------ |
| REST JSON、消息队列、数据库字段 | 客户端或消费者 | 否，只需正确编码 |
| 浏览器直接渲染网页 | 用户浏览器或网页下载的 Webfont | 通常否；除非服务器做截图或 PDF |
| Java AWT / Java2D 生成 PNG、JPEG | 服务端 JVM | 是 |
| 服务端生成 PDF | PDF 库或服务端字体文件 | 通常是；可选择嵌入字体 |
| Puppeteer / Playwright 截图、Headless Chrome 打印 PDF | 容器中的浏览器 | 是，或通过 Webfont 提供 |
| SVG 仅包含文本节点 | 最终查看 SVG 的客户端 | 不一定；若转换为 PNG/PDF 则需要 |
| SVG 将文字转为 path | 生成路径的一方 | 生成时需要，查看时通常不需要 |

PDF 有一个特别常见的陷阱：服务端“生成成功”不等于收件人电脑能显示。若 PDF 没有嵌入字体，查看端仍需要安装对应字体；对需要可靠分发的中文 PDF，应优先使用许可允许嵌入的字体，并在生成时嵌入或子集嵌入它。

## 十、排查清单与结论

当服务端生成的中文图片出现方框时，可按下面顺序排查：

1. 先确认原始字符串和日志中的中文是否正确，排除编码损坏。
2. 确认问题发生在服务端渲染阶段，而不是客户端查看阶段。
3. 在实际运行的容器内列出中文字体，而不是只检查开发机。
4. 检查代码是否依赖 `SansSerif`、`Arial` 等逻辑或不保证中文覆盖的字体名。
5. 在 Dockerfile 中安装并固定合适的 CJK 字体包。
6. 使用字体能力检查与真实渲染集成测试，防止“文件成功生成但文字不可读”。
7. 重新构建、发布新镜像，并用生产相近环境验证结果。

可以把最重要的结论压缩为三句：

- **UTF-8 决定字符能否被正确读出，字体决定字符能否被正确画出。**
- **容器是独立运行环境，不能依赖开发机或宿主机预装的中文字体。**
- **只要后端负责生成中文图片、PDF 或截图，中文字体包就属于生产依赖，应与 JRE、系统库一样在镜像中声明、测试和维护。**

看起来只是一个字体包，实际上它决定了服务端的视觉输出是否可靠。把它写进镜像和测试流程，才不至于在真正要发送海报或报告时，才发现系统认真地替你画出了一排方框。
