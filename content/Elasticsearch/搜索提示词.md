搜索提示词，也叫搜索补全、自动补全、Autocomplete。用户在搜索框里只输入几个字，系统就返回候选词：

```text
ela
  ↓
elasticsearch
elasticsearch tutorial
elasticsearch vector search
```

这件事看起来像是 Elasticsearch 的一个查询功能，但真正上线时，它其实是一个前端、后端、缓存、ES、日志统计一起配合的低延迟系统。

它的目标非常明确：

- 响应要快，通常希望在几十毫秒内返回。
- 返回数量要少，一般 5 到 10 条。
- 结果要稳定，不要每输入一个字符就剧烈跳动。
- 候选词要可控，不能出现黑词、脏词、低质量词。
- 热门搜索、历史行为、业务运营词都可能参与排序。

如果只是在 ES 里随便写个 `match`，当然也能返回一点东西。只是那样做出来的补全，大概会很努力地证明“能跑”和“好用”之间隔着一条河。

## 一、整体链路

典型流程如下：

```text
用户输入
  ↓
前端防抖
  ↓
后端 suggest 接口
  ↓
本地缓存 / Redis
  ↓
Elasticsearch 补全索引
  ↓
业务过滤和排序
  ↓
前端渲染候选词
```

一次请求示例：

```http
GET /api/search/suggest?q=elas&size=10
```

后端返回：

```json
{
  "items": [
    { "text": "elasticsearch", "score": 1000 },
    { "text": "elasticsearch tutorial", "score": 850 },
    { "text": "elasticsearch vector search", "score": 620 }
  ]
}
```

前端真正展示的通常只是 `text`，但后端需要保留热度、来源、权重等信息，方便排序和调试。

## 二、前端为什么要防抖

用户输入时，内容可能是这样变化的：

```text
e -> el -> ela -> elas -> elast
```

如果每次输入都立刻请求后端，会出现几个问题：

- 请求量暴增。
- 后端和 ES 压力变大。
- 旧请求可能比新请求更晚返回，导致候选词闪动。
- 用户体验变差。

因此搜索框通常会做防抖：

```text
用户停止输入 100 到 300ms 后，再发起请求
```

防抖规则：

- 输入事件触发时启动计时器。
- 计时结束前如果又输入，则清除旧计时器。
- 直到用户停下来，才执行最后一次请求。

适合补全的常见参数：

| 场景 | 防抖时间 |
| ---- | -------- |
| PC 搜索框 | 100 到 200ms |
| 移动端输入 | 200 到 300ms |
| 后端压力较大 | 300ms 左右 |

防抖不是为了偷懒，而是为了让系统少做无意义的工作。系统已经够辛苦了，不必让它陪用户的每一次手抖。

## 三、后端接口职责

后端 suggest 接口不应该只是 ES 查询代理。它至少要负责：

- 参数清洗：去除首尾空格、限制长度。
- 黑词过滤：脏词、违规词、不可展示词。
- 缓存读取：优先本地缓存或 Redis。
- ES 查询：缓存未命中时召回候选词。
- 结果去重：不同来源可能出现相同候选词。
- 排序控制：热度、权重、业务规则。
- 限制数量：通常返回 5 到 10 条。

接口处理流程：

```text
q 为空或太短 -> 直接返回热门词
q 命中黑名单 -> 返回空
q 命中缓存 -> 返回缓存
q 未命中缓存 -> 查询 ES
ES 结果 -> 过滤 -> 排序 -> 缓存 -> 返回
```

建议对短前缀做更严格控制。比如只输入一个字母 `a`，可能命中海量候选词，缓存和热词策略比实时查 ES 更重要。

## 四、缓存策略

搜索补全非常适合缓存，因为大量用户会输入相同前缀。

缓存层次：

```text
本地缓存 Caffeine
  ↓ 未命中
Redis
  ↓ 未命中
Elasticsearch
```

缓存 key 示例：

```text
suggest:{lang}:{region}:{prefix}
```

例如：

```text
suggest:zh:CN:elas
```

缓存内容：

```json
[
  { "text": "elasticsearch", "score": 1000 },
  { "text": "elasticsearch 教程", "score": 870 }
]
```

注意事项：

- 缓存要区分语言和地区。
- 黑词更新后要能清理相关缓存。
- 热词变化频繁时 TTL 不宜过长。
- 可以对热门前缀预热，例如 `j`、`ja`、`jav`。

## 五、ES 实现方式对比

ES 实现补全常见有三种方式：

| 方案 | 优点 | 缺点 | 适合场景 |
| ---- | ---- | ---- | -------- |
| `completion` suggester | 查询极快，专为补全设计 | 灵活性较弱，主要做前缀补全 | 纯提示词、热词补全 |
| `edge_ngram` | 可结合普通查询和排序，灵活 | 索引膨胀，分词设计复杂 | 商品名、标题补全 |
| 搜索日志热词 | 结果更贴近用户行为 | 需要统计链路 | 热搜、趋势词 |

生产中常常组合使用：

```text
热词库 / 运营词
  +
completion suggester
  +
edge_ngram 商品名召回
  ↓
合并、去重、排序
```

## 六、`completion` suggester

`completion` 是 ES 专门为补全设计的字段类型。

### 1. 创建索引

```http
PUT /suggest_index
{
  "mappings": {
    "properties": {
      "title_suggest": {
        "type": "completion"
      },
      "weight": {
        "type": "integer"
      },
      "status": {
        "type": "keyword"
      }
    }
  }
}
```

### 2. 写入候选词

```http
PUT /suggest_index/_doc/1
{
  "title_suggest": {
    "input": [
      "elasticsearch",
      "elasticsearch tutorial"
    ],
    "weight": 100
  },
  "status": "ENABLE"
}
```

`input` 是可被补全的候选词，`weight` 用于影响排序。

### 3. 查询补全

```http
POST /suggest_index/_search
{
  "suggest": {
    "title_suggest_result": {
      "prefix": "elas",
      "completion": {
        "field": "title_suggest",
        "size": 5
      }
    }
  }
}
```

返回结果中，前端通常只需要 `options[].text`：

```json
{
  "suggest": {
    "title_suggest_result": [
      {
        "text": "elas",
        "options": [
          {
            "text": "elasticsearch",
            "_score": 100.0
          }
        ]
      }
    ]
  }
}
```

`completion` 适合做词条补全，但如果你需要复杂过滤、召回商品标题、结合类目和业务字段排序，`edge_ngram` 会更灵活。

## 七、`edge_ngram`

`edge_ngram` 的思想是：写入时把词拆成前缀 token。

例如：

```text
elastic -> e, el, ela, elas, elast, ...
```

这样用户输入 `elas` 时，就能通过倒排索引命中完整词。

### 1. 创建索引

```http
PUT /autocomplete_index
{
  "settings": {
    "analysis": {
      "tokenizer": {
        "edge_ngram_tokenizer": {
          "type": "edge_ngram",
          "min_gram": 2,
          "max_gram": 20,
          "token_chars": ["letter", "digit"]
        }
      },
      "analyzer": {
        "autocomplete_index_analyzer": {
          "tokenizer": "edge_ngram_tokenizer",
          "filter": ["lowercase"]
        },
        "autocomplete_search_analyzer": {
          "tokenizer": "standard",
          "filter": ["lowercase"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "autocomplete_index_analyzer",
        "search_analyzer": "autocomplete_search_analyzer"
      },
      "status": {
        "type": "keyword"
      },
      "hot_score": {
        "type": "integer"
      }
    }
  }
}
```

`analyzer` 用于写入阶段生成前缀 token，`search_analyzer` 用于查询阶段正常分析用户输入。

不建议把 `min_gram` 设成 1，除非你确认单字符补全确实必要。单字符会让索引和召回都变得很吵。

### 2. 写入文档

```http
PUT /autocomplete_index/_doc/1
{
  "title": "elasticsearch vector search",
  "status": "ENABLE",
  "hot_score": 1200
}
```

### 3. 查询

```http
POST /autocomplete_index/_search
{
  "size": 10,
  "_source": ["title", "hot_score"],
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "title": "elas"
          }
        }
      ],
      "filter": [
        { "term": { "status": "ENABLE" } }
      ]
    }
  },
  "sort": [
    { "hot_score": "desc" },
    { "_score": "desc" }
  ]
}
```

这种方式可以同时利用相关性分数和热度分数，适合商品、文章、课程等内容标题补全。

## 八、中文补全怎么做

中文补全要比英文更麻烦，因为中文没有天然空格。

常见策略：

### 1. 中文分词 + edge_ngram

先用中文分词器切词，再做前缀。

适合：

- 商品标题。
- 文章标题。
- 搜索词补全。

### 2. 拼音补全

用户输入：

```text
pingguo
```

希望补全：

```text
苹果手机
```

这需要拼音分析插件或业务侧生成拼音字段：

```json
{
  "name": "苹果手机",
  "name_pinyin": "pingguoshouji",
  "name_pinyin_abbr": "pgsj"
}
```

查询时同时查中文字段和拼音字段。

### 3. 热词兜底

中文单字前缀召回噪音很大，短输入时可以直接返回热门词，而不是实时查所有内容。

例如：

```text
用户输入：手
返回：手机、手机壳、手表、手办
```

这些候选词更适合来自搜索日志统计，而不是直接从商品标题里硬查。

## 九、搜索日志与热词统计

提示词不是一份永远不变的静态字典。更常见的做法是从用户搜索行为里生成热词。

采集数据：

- 搜索词。
- 搜索次数。
- 点击次数。
- 点击率。
- 下单或转化。
- 搜索时间。
- 地区和语言。

统计后得到：

```text
keyword = "elasticsearch"
search_count = 12000
click_count = 3600
ctr = 0.30
```

热度分可以简单设计：

```text
hot_score = search_count * 1.0 + click_count * 3.0 + order_count * 10.0
```

然后定时写入 suggest 索引。

流程：

```text
用户搜索日志
  ↓
日志队列
  ↓
实时或离线统计
  ↓
生成热词表
  ↓
写入 ES suggest 索引
  ↓
补全接口查询
```

这样用户看到的提示词就会随真实行为变化，而不是靠程序员手写一份词典。坦率地说，让程序员手写热门词，多少有些为难程序员，也为难用户。

## 十、结果排序与过滤

补全结果通常不只是按 ES `_score` 排。

常见排序信号：

- 前缀匹配程度。
- 热度。
- 点击率。
- 转化率。
- 运营权重。
- 用户历史偏好。
- 地区和语言。
- 是否黑名单。

可以用一个简单的排序公式：

```text
final_score =
  text_score * 0.4
  + hot_score * 0.3
  + ctr_score * 0.2
  + business_boost * 0.1
```

补全还要做过滤：

- 黑词过滤。
- 下架商品过滤。
- 地区不可售过滤。
- 低质量词过滤。
- 成人、政治、违规内容过滤。

过滤必须在返回前做，不能指望前端替你解决。前端不是安全边界。

## 十一、接口降级

补全接口是高频接口，要准备降级方案。

常见降级：

- ES 超时时返回 Redis 热词。
- Redis 故障时返回本地缓存。
- 前缀太短时只返回热门词。
- 后端压力高时延长前端防抖时间或限制请求频率。
- 对异常前缀直接返回空列表。

示例降级链路：

```text
本地缓存命中 -> 返回
Redis 命中 -> 返回
ES 查询成功 -> 返回并写缓存
ES 超时 -> 返回默认热词
```

补全不是核心交易链路，宁可少返回几个候选词，也不要拖垮搜索主链路。

## 十二、总结

搜索提示词可以这样理解：

- 前端用防抖减少无效请求。
- 后端负责清洗、过滤、缓存、排序和降级。
- ES 可以用 `completion` 做高性能词条补全。
- 也可以用 `edge_ngram` 做更灵活的标题前缀召回。
- 热词来自搜索日志统计，而不是纯手工维护。
- 中文补全通常要考虑分词、拼音和短前缀热词兜底。
- 生产中要重视黑词过滤、缓存预热和故障降级。

一个好用的补全系统，表面上只是输入框下面的几行字；背后却是低延迟、高频缓存、搜索质量和业务规则共同妥协的结果。说它简单，未免有些不负责任。
