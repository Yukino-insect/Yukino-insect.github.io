现实中的项目很少完全从零开始。你可能 fork 一个仓库、复制几个模块、重写 UI、替换模型、保留原架构，最后得到一个功能已经大幅不同的新项目。此时最常见的误区是：**“我改得很多，所以已经和上游没有关系。”**

改得很多不等于上游许可证自动消失。只要项目中仍包含、改写或分发上游受版权保护的代码、资源或二进制，就要先弄清上游许可，再决定如何命名、声明、发布和接受贡献。

本文提供一套可执行的方法，尤其适用于 Apache-2.0、MIT、BSD、GPL 等常见上游项目。

> 本文是工程合规学习材料，不替代专业法律意见。面对商业发布、公司代码、复杂 GPL 组合、模型权重或数据集时，应进行针对性审查。

## 一、先判断：你是“参考”，还是“衍生”

这不是看代码相似度百分比，而是看你是否复制、改写、分发了受保护的表达。

| 情况 | 通常的工程判断 | 建议动作 |
| --- | --- | --- |
| 只阅读思路，独立重新实现 | 可能只是思想参考 | 记录灵感来源，建议致谢。 |
| 复制函数、类、配置、模板或 UI 资源 | 明确包含上游表达 | 按上游许可证处理。 |
| 从 fork 开始，持续修改 | 明确的衍生项目 | 保留上游归属、许可证和变更记录。 |
| 重写了多数模块但仍保留关键结构或文件 | 仍可能是衍生作品 | 保守地保留声明并审查文件来源。 |
| 只调用上游已安装库的公开 API | 取决于依赖许可证和分发方式 | 记录依赖许可证，不要擅自复制源码。 |

一个实用原则是：**拿不准时，按衍生项目处理通常比假装“完全原创”更稳妥。**

## 二、第一步：建立来源清单，而不是凭记忆

开始改造前或准备发布前，建立一个来源表：

| 内容 | 上游 URL | 使用方式 | 许可证 | 是否修改 | 发行时动作 |
| --- | --- | --- | --- | --- | --- |
| 初始桌面应用 | 上游仓库与 tag | fork/代码继承 | Apache-2.0 | 是 | LICENSE、NOTICE、修改说明 |
| 模型包装代码 | 上游文件与 commit | 改写/适配 | Apache-2.0 | 是 | 第三方声明、保留归属 |
| 超分网络结构 | 上游库 | 适配 | BSD/Apache | 是 | 附相应许可证 |
| 模型权重 | 下载地址/模型卡 | 运行时下载 | 单独核验 | 否 | 不默认打包 |
| 示例图片 | 作者/站点 | 测试 | 单独授权 | 否 | 替换或取得授权 |

这张表应写进仓库中的 `THIRD_PARTY_NOTICES.md`，而不是只留在开发者脑中。它会帮助你回答：这段代码能不能删版权头？这个模型能不能放进安装包？这个 release 还缺什么文件？

## 三、不同许可证下的改造策略

### 1. 上游是 MIT / BSD

通常需要：

- 保留版权声明；
- 保留完整许可证文本；
- 对 BSD-3-Clause 注意不得暗示上游作者为你的产品背书；
- 在 README 或第三方声明中说明来源。

你通常可以闭源、商用、重新命名和大幅修改，但不能把上游代码的作者信息全部抹去。

### 2. 上游是 Apache-2.0

除保留许可证、版权和归属外，还要重点关注：

- 修改过的文件需要有显著修改说明；
- 上游若有 `NOTICE`，需要在衍生发行物中保留相关内容；
- Apache-2.0 有专利授权和终止条款；
- 许可证不授予上游商标使用权。

一个实用的仓库结构是：

```text
LICENSE
NOTICE
THIRD_PARTY_NOTICES.md
MODIFICATIONS.md
README.md
```

其中 `MODIFICATIONS.md` 应说明：上游是谁、当前项目是否为独立维护的衍生版本、改了哪些类别的功能、哪些文件或目录存在重大本地修改。

### 3. 上游是 MPL-2.0 / LGPL

不要用一句“动态链接就行”草率结束判断。需要具体看：

- 是否修改了受许可文件本身；
- 是否静态链接、动态链接、打包或复制源码；
- 用户能否替换 LGPL 组件；
- 你分发的是源码、二进制还是 SaaS。

这类项目建议保留完整构建信息，并在发布前做针对性审查。

### 4. 上游是 GPL / AGPL

GPL/AGPL 的关键不是“能不能商用”，而是衍生作品分发或网络提供服务时的源码义务。若你计划闭源发行桌面软件或 SaaS，不能在没有深入分析的情况下把 GPL/AGPL 代码直接复制进核心项目。

遇到 GPL/AGPL 时的安全流程是：

1. 确认你是复制代码、链接库，还是只通过独立进程/协议调用；
2. 阅读该许可证版本和上游的额外例外条款；
3. 评估你的发行和服务模式；
4. 必要时使用许可证兼容的替代实现，或咨询专业人士。

## 四、重新命名不是问题，误导关系才是问题

深度改造后改名字是合理的。名称应反映新项目的功能和维护主体，例如：

```text
新项目名：CleanCanvas Studio / 净绘工坊
上游来源：video-subtitle-remover
关系说明：独立维护的衍生与大幅改造版本，非上游官方发行版
```

不应做的事：

- 继续使用上游 logo、商标或官方发布名，却让用户误以为是官方版本；
- 删除所有上游归属信息；
- 在 release 页面宣称获得上游作者推荐或合作，实际上没有；
- 将上游作者名字用于营销文案。

Apache-2.0 第 6 条明确不授予商标权；即使许可证允许复制代码，也不意味着可以随意使用项目品牌。 [Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0)

## 五、一个 Apache-2.0 深度改造项目的模板

假设你基于一个 Apache-2.0 视频工具，加入 AI 模型、重新设计 UI、修改处理流程并改名发布，可以采用下面的声明结构。

### 1. README 中的简短说明

```md
本项目是对 <上游仓库链接> 的独立衍生与大幅改造版本，
在 Apache License 2.0 下发布。

本项目不是上游官方发行版，也不代表获得上游作者背书。
完整归属、修改记录和第三方许可见 LICENSE、NOTICE、
MODIFICATIONS.md 与 THIRD_PARTY_NOTICES.md。
```

### 2. `NOTICE` 中的来源说明

```text
This product includes portions derived from:

<upstream name>
Copyright <upstream contributors>
Source: <upstream URL>
License: Apache License 2.0.
```

### 3. `MODIFICATIONS.md` 中的改造记录

```md
本项目是对 <upstream> 的独立维护衍生版本。

主要改动：

- 重命名与品牌/UI 调整；
- 新增或替换算法；
- 重构任务和配置系统；
- 增加测试、文档和发布流程；
- 替换模型、依赖或输出格式。
```

### 4. 修改过的源文件中的显著说明

对仍保留上游代码的关键文件，可以在文件顶部添加：

```python
# Portions derived from <upstream URL>.
# Modified by CleanCanvas Studio contributors.
# See LICENSE, NOTICE and MODIFICATIONS.md.
```

这并不是为了让每个文件看起来更“正式”，而是为了让源代码被单独复制、拆包或审计时，归属和修改事实不会丢失。

## 六、模型、数据与二进制：最容易漏掉的第二层许可证

AI 项目往往把注意力放在 Python 代码，忽略了更高风险的资产。

### 1. 模型权重

检查：

- 权重是否允许商业使用；
- 是否允许再分发；
- 是否要求署名、限制领域或禁止某类用途；
- 模型卡、下载页和仓库许可证是否一致；
- 安装包中是否真正包含权重。

一个稳妥做法是：默认不提交大权重，运行时从上游下载，记录 URL、版本和哈希；若要离线安装包，再单独完成权重再分发审查。

### 2. FFmpeg、CUDA、系统二进制与 wheels

二进制发行比源码发行更复杂。你发布的安装包真正包含什么，取决于 PyInstaller、Docker、conda、pip wheel、FFmpeg 构建方式和平台。应针对**实际发行物**生成依赖清单，而不是只看源码中的 `requirements.txt`。

### 3. 测试媒体与截图

影视截图、动漫图片、用户视频和网络图片即使只用于测试，也未必适合放进公开仓库。优先使用：

- 自己创作或已明确授权的素材；
- 合成测试数据；
- 允许公开再分发的开放数据；
- 只保留下载脚本和校验值，而不提交原始文件。

## 七、发布前的衍生项目检查表

- [ ] 已记录所有主要上游、版本或 commit；
- [ ] 已确认上游许可证、NOTICE 和版权头；
- [ ] 已保留完整 LICENSE，并在必要时增加 NOTICE；
- [ ] 已增加 `THIRD_PARTY_NOTICES.md` 与 `MODIFICATIONS.md`；
- [ ] README 清楚写明“独立衍生项目，非官方版本”；
- [ ] 修改的上游文件保留归属并标明修改；
- [ ] 没有把上游商标、logo 或作者名用于误导性宣传；
- [ ] 已单独审查模型、数据、字体、素材和二进制；
- [ ] 安装包中包含应交付的许可证和 notice；
- [ ] release note 写清新增功能、破坏性变更和已知限制。

## 八、总结

参考或深度改造开源项目并不是问题。开源生态本来就依赖复用、fork、改进和回馈。真正的问题是：不记录来源、不读许可证、删除声明、混淆品牌关系，或者把模型权重与代码许可证混为一谈。

成熟的做法不是回避上游，而是清楚说明：

```text
我从哪里来；
我改了什么；
我保留了什么；
我现在以什么身份维护；
用户拿到发行物后能看到哪些许可证与归属。
```

做到这些，你的项目即使经过大幅重构，也能既尊重上游，又建立清晰、独立的产品身份。
