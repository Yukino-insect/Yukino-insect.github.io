很多人把“放到 GitHub”理解成“开源”。这并不准确。公开仓库只表示别人能够看到代码；除非你授予明确许可，别人通常没有自动获得复制、修改、再发布和商业使用的权利。**开源协议的作用，就是把这些权利、条件和边界写清楚。**

本文从开发者最常遇到的许可证出发，说明它们允许什么、要求什么、适合什么项目，以及如何避免把“宽松”“开源”“免费”“可以随便商用”混成一件事。

> 本文用于技术学习与工程决策，不构成针对具体争议的法律意见。准备出售软件、分发预装模型的安装包，或处理公司代码时，应让法务或熟悉开源合规的人复核。

## 一、先建立正确认知：许可证到底解决什么

代码是受著作权保护的作品。许可证是著作权人给使用者的授权条件，通常回答四类问题：

- 能否使用、复制、修改和分发？
- 能否商用、闭源集成或出售服务？
- 分发修改版时要保留什么声明？
- 代码、依赖、模型权重、数据集和商标是否适用同一规则？

最后一问尤其重要。一个仓库的代码使用 Apache-2.0，并不自动意味着其中的模型权重、测试图片、logo、数据集也能自由再分发。

```text
公开可见
    ≠ 已获使用授权
代码许可证
    ≠ 模型权重许可证
可以商用
    ≠ 可以删除作者署名或冒充官方版本
```

## 二、许可证的三类主要路线

从工程选择角度，可以先把常见协议分为三组。

| 路线 | 代表许可证 | 核心目标 | 修改版是否必须开源 |
| --- | --- | --- | --- |
| 宽松许可 | MIT、BSD、Apache-2.0 | 最大化复用和商业兼容性 | 通常不要求 |
| 弱 Copyleft | MPL-2.0、LGPL | 保护被修改的开源部分，同时允许较灵活集成 | 视文件级或链接方式而定 |
| 强 Copyleft | GPL、AGPL | 防止修改版重新闭源 | 通常要求，AGPL 还覆盖网络服务场景 |

这里的“强弱”不是质量评价，而是对下游分发约束的强弱。

## 三、宽松许可证：MIT、BSD 与 Apache-2.0

### 1. MIT License

MIT 是最短、最常见的宽松许可证之一。它允许使用、复制、修改、合并、发布、分发、再许可和出售软件。

使用者通常需要做的事并不复杂：在软件副本或重要部分中保留版权声明和许可证文本。

适合：

- 工具库、示例项目、个人开源项目；
- 希望降低接入门槛的 SDK；
- 希望允许商业闭源产品使用代码的项目。

它的优点是简单；代价是没有明确的专利授权条款。对于涉及算法、企业协作或潜在专利的项目，Apache-2.0 往往更完整。

### 2. BSD-2-Clause 与 BSD-3-Clause

BSD 系列与 MIT 类似，也属于宽松许可证。

- BSD-2-Clause：主要保留版权和免责声明；
- BSD-3-Clause：额外加入“不可以用原作者或贡献者名字为衍生产品背书”的限制。

BSD-3-Clause 常用于希望允许广泛复用，但不希望下游宣传“官方推荐”“作者背书”的项目。

### 3. Apache License 2.0

Apache-2.0 也是宽松许可证，但比 MIT/BSD 更完整。它允许商业使用、修改、分发和闭源集成，同时要求下游：

- 向接收者提供 Apache-2.0 许可证副本；
- 在修改过的文件中注明修改；
- 保留原有版权、专利、商标和归属声明；
- 如果上游含有 `NOTICE`，在衍生发行物中保留相关 NOTICE；
- 不把许可证理解为获得上游商标授权。

Apache-2.0 的一个重要特点是**明确的专利授权和专利诉讼终止条款**。这也是许多大型基础设施项目选择它的原因。

适合：

- 希望允许商业使用，但重视归属和专利边界的项目；
- 多贡献者、企业参与或会产生大量衍生版本的项目；
- 需要较完整发行物合规流程的软件。

Apache 官方许可证原文见：[Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0)。

## 四、弱 Copyleft：MPL-2.0 与 LGPL

### 1. MPL-2.0：文件级的边界

MPL-2.0 的核心思路是：**修改了 MPL 文件本身，就应把这个文件的修改公开；但可以与其他不同许可证的文件组合。**

它常被称为文件级 Copyleft。相较 GPL，它更容易与商业闭源模块共存；相较 MIT，它又能确保核心文件的改进回流。

适合：

- 希望核心实现保持开放、插件或外围业务可独立的项目；
- 浏览器、工具链、跨公司协作组件；
- 不希望所有组合代码都被强制开源的团队。

### 2. LGPL：库与链接边界

LGPL 常用于类库。大意是：用户可以将未修改的 LGPL 库与专有程序链接，但如果修改了 LGPL 库本身，或分发方式阻碍用户替换该库，可能产生额外义务。

LGPL 的合规细节比“动态链接就没问题”复杂得多，还要看语言、打包方式、静态链接、可重链接性与具体版本。对初学者而言，遇到 LGPL 依赖时最好先读原许可证和其 FAQ，而不是依据网络上的一句经验判断。

## 五、强 Copyleft：GPL 与 AGPL

### 1. GPL：分发衍生作品时的开源要求

GPL 的目标是确保软件及其衍生作品在分发时仍保有自由使用、修改和再分发的权利。通常可以这样理解：如果你分发了包含 GPL 代码的衍生作品，就需要以 GPL 兼容方式提供对应源代码。

GPL 并不禁止商业使用；你可以收费、卖服务、卖硬件或提供支持。它限制的是把 GPL 衍生代码作为闭源产品分发。

适合：

- 希望所有发布的衍生版本都继续开源的项目；
- 命令行工具、系统软件、社区基础项目；
- 对“防止闭源拿走改进”优先级很高的作者。

### 2. AGPL：网络服务也纳入考虑

传统 GPL 主要在“分发软件”时触发义务。若软件只部署在服务器上，用户通过网络使用，通常不发生传统分发。AGPL 针对这一点增加了网络交互场景：修改后的 AGPL 程序向用户提供网络服务时，通常也要向这些用户提供对应源代码。

适合：

- 希望 SaaS 形式的修改版也回馈源代码的项目；
- 对云服务闭源使用特别敏感的作者。

不适合：

- 你希望企业能毫无顾虑地把代码嵌入闭源 SaaS 的项目。

GNU 的许可证说明与原文见：[GNU licenses](https://www.gnu.org/licenses/)。

## 六、公共领域、CC0 与 Creative Commons 的位置

### 1. CC0 与 Unlicense

CC0 试图尽量放弃权利，把作品贡献到公共领域；Unlicense 也有类似目标。它们适合希望极低门槛复用的代码片段、示例或数据，但在不同法域中“完全放弃权利”的效果可能不同。

### 2. Creative Commons 通常不适合软件代码

Creative Commons 更适合文章、图片、视频和其他创作内容。对软件代码，通常应优先使用 OSI 批准或社区通行的软件许可证，因为软件许可证会更明确处理源代码、专利、分发和免责声明。

## 七、快速对比：选型时真正该问什么

| 你的目标 | 常见选择 | 原因 |
| --- | --- | --- |
| 希望被尽可能广泛使用，包括闭源商用 | MIT、BSD-2-Clause | 条款短、限制少。 |
| 希望商用友好，同时处理专利和 NOTICE | Apache-2.0 | 有明确专利授权与归属规则。 |
| 希望修改核心文件的人公开修改 | MPL-2.0 | 文件级回馈。 |
| 希望衍生发布版整体继续开源 | GPL | 强 Copyleft。 |
| 希望网络服务修改版也公开源码 | AGPL | 覆盖网络交互。 |
| 只是发布文章、图片或课程资料 | CC BY、CC BY-SA 等 | 面向内容作品，而非软件。 |

不要只问“哪个协议最宽松”。更重要的问题是：

1. 你希望别人闭源商用吗？
2. 你是否在意专利授权？
3. 你是否希望改进回流？回流到文件、库还是整个应用？
4. 项目是否会接受企业贡献？
5. 依赖、模型、数据和素材的许可证是否兼容？

## 八、几个常见误区

### 误区一：仓库公开就是开源

没有许可证时，别人可能可以阅读代码，但未必获得复制、修改、分发或商业使用授权。GitHub 的 “Choose a license” 指南专门强调，许可证是向他人授予使用权限的方式。 [GitHub Docs：为仓库添加许可证](https://docs.github.com/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)

### 误区二：Apache-2.0 可以删除所有上游信息

Apache-2.0 很宽松，但不允许你删掉应保留的版权和归属信息；修改文件应有修改声明；上游有 NOTICE 时也应处理。

### 误区三：开源就不能收费

开源许可证通常规范的是权利授予，不等于禁止收费。可以出售托管服务、技术支持、培训、硬件、安装包或商业附加功能；但必须遵守对源码、许可证和衍生作品的约束。

### 误区四：代码开源许可覆盖模型权重

不一定。模型权重、训练数据、测试图片、字体和 logo 可能各自有不同授权。发布 AI 项目时，应分别建立依赖和资产清单。

## 九、总结

- MIT/BSD/Apache-2.0 是宽松许可，区别主要在专利、NOTICE 和署名限制。
- MPL/LGPL 尝试在开放改进与商业组合之间建立边界。
- GPL/AGPL 用更强义务换取衍生版本持续开放。
- 协议不是装饰文件；它决定下游能做什么、必须保留什么。
- 选择许可证前，先确认自己的目标、上游依赖、模型权重和发布方式。
