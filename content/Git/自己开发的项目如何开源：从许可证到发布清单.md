“把代码推到 GitHub”是发布的最后一步，不是开源工作的全部。一个真正可被他人使用、贡献、分发和维护的开源项目，需要回答许可证、依赖来源、贡献规则、安全反馈、版本发布和资产权利等问题。

本文给出一份从零开始的实践流程。目标不是让仓库看起来“文件很多”，而是让使用者、贡献者和未来的你都知道：这个项目是什么、能否使用、如何安装、遇到问题找谁、哪些内容不能随便分发。

> 本文讨论一般工程实践，不构成法律意见。项目涉及公司知识产权、第三方商业 SDK、训练数据、模型权重或付费素材时，应在公开前取得明确授权。

## 一、公开之前：先确认你有权公开

在执行 `git push` 前，先做一次资产盘点。最重要的问题不是“代码是否能运行”，而是“这些内容是否都可以公开”。

### 1. 代码来源

确认每段主要代码属于哪一类：

- 自己独立编写；
- 公司、学校或合作方提供；
- 从开源项目复制或修改；
- 由生成式工具辅助生成，但仍需要人工确认来源和许可证；
- 从博客、问答网站或教程复制的片段。

如果代码来自雇佣关系、课程作业、竞赛或合作项目，先确认合同、学校规定和共同作者约定。你写过，不必然等于你拥有公开授权。

### 2. 非代码资产

以下内容经常被忽略：

- 模型权重和训练数据；
- 测试图片、视频、录音和截图；
- 字体、图标、logo、背景图；
- API key、Token、数据库导出和日志；
- 预编译二进制、安装包、第三方 SDK。

将它们逐项列出。不能公开的内容应删除、替换成合成样例，或改为下载脚本而不是直接提交。

## 二、选择许可证：先决定目标，再选文件

许可证不是“GitHub 推荐哪个就点哪个”。应先回答：

1. 是否允许闭源商业使用？
2. 是否希望修改版必须继续开源？
3. 是否在意明确的专利授权？
4. 项目是否依赖 GPL、Apache、BSD 或其他有条件的上游代码？
5. 未来是否接受外部贡献？

一个常见的快速判断是：

```text
希望最大化复用、条款简单       -> MIT / BSD
希望商业友好且有专利条款       -> Apache-2.0
希望修改核心文件回馈           -> MPL-2.0
希望分发的衍生项目继续开源     -> GPL
希望网络服务修改版也公开源码   -> AGPL
```

GitHub 提供了许可证选择与添加的官方说明，但最终选择应结合项目目标和上游依赖，而不是只看“最流行”。 [GitHub Docs：Licensing a repository](https://docs.github.com/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)

## 三、一个最小但完整的开源仓库应有什么

下面不是所有项目都必须一字不差照搬，但它是一份很好的起点。

```text
project-root/
├─ README.md
├─ LICENSE
├─ NOTICE                       # 需要时使用，尤其是 Apache 衍生项目
├─ THIRD_PARTY_NOTICES.md       # 第三方代码、二进制、模型和资产
├─ CONTRIBUTING.md
├─ SECURITY.md
├─ CODE_OF_CONDUCT.md           # 社区项目建议提供
├─ CHANGELOG.md                 # 有正式版本时建议提供
├─ .gitignore
├─ .editorconfig                # 可选：统一基础格式
├─ .github/
│  ├─ ISSUE_TEMPLATE/
│  ├─ PULL_REQUEST_TEMPLATE.md
│  └─ workflows/
├─ src/ 或实际源码目录
├─ tests/
└─ docs/
```

### 1. README：让陌生人知道是否值得继续看

README 至少应包含：

- 项目一句话定位与主要能力；
- 当前支持的平台和运行环境；
- 安装、启动和最小示例；
- 配置说明和输出说明；
- 已知限制；
- 测试命令；
- 许可证、第三方声明和贡献入口。

不要在 README 中承诺“无损”“万能”“百分百准确”这类无法证明的结论。清楚写出限制，比营销式描述更能建立信任。

### 2. LICENSE：真正授予权利的文件

`LICENSE` 应包含所选许可证的**完整官方文本**，不要只写：

```text
This project uses MIT.
```

这句话不是完整许可证。使用 Apache-2.0 时，还要特别注意保留上游版权和 NOTICE 规则。许可证原文应从官方或可信来源复制，不要自行改写法律条款。

### 3. NOTICE 与 THIRD_PARTY_NOTICES

两者用途不同：

- `NOTICE`：常用于 Apache-2.0 归属说明，也可聚合发行物必须保留的 notice；
- `THIRD_PARTY_NOTICES.md`：面向维护者和用户的第三方清单，可记录源码、依赖、二进制、模型、数据和发布注意事项。

对 AI 项目，第三方清单建议至少记录：

| 项目 | 版本/来源 | 代码许可证 | 权重是否可再分发 | 当前处理 |
| --- | --- | --- | --- | --- |
| 模型包装代码 | 上游 URL 与 commit/tag | 例如 Apache-2.0 | 不适用 | 保留声明 |
| 模型权重 | 下载 URL 与 hash | 单独核验 | 可能受限 | 默认不打包 |
| FFmpeg/二进制 | 发行版本 | 依构建配置而定 | 依许可证而定 | 发布前生成清单 |

### 4. CONTRIBUTING：降低协作摩擦

贡献指南应说明：

- 提 issue 前需要提供什么信息；
- 分支、提交和代码风格要求；
- 本地测试命令；
- 哪些文件不能提交，例如 `.venv`、缓存、模型、密钥；
- 贡献默认采用什么许可证；
- 引入第三方代码时需要记录哪些信息。

如果项目未来接受大量企业贡献，可进一步研究 DCO（Developer Certificate of Origin）或 CLA（Contributor License Agreement）。小型个人项目不一定需要一开始就引入复杂流程。

### 5. SECURITY：给安全问题一条私下通道

安全漏洞不适合和普通 bug 一样公开讨论。`SECURITY.md` 至少应说明：

- 支持哪些版本；
- 如何私下报告漏洞；
- 报告中应包含哪些环境、影响和复现信息；
- 不要在公开 issue 直接发布 exploit、恶意文件或凭据。

处理图片、视频、压缩包、网络下载、模型权重和原生依赖的软件尤其需要这一点。

## 四、配置文件：不要把个人环境提交出去

`.gitignore` 的职责不是“掩盖问题”，而是防止高频生成物和敏感信息进入仓库。

Python 项目常见忽略项：

```gitignore
__pycache__/
*.py[cod]
.venv/
venv/
.pytest_cache/
.mypy_cache/
dist/
build/
*.egg-info/
.env
artifacts/
models/**/*.pth
models/**/*.pt
```

但要注意两点：

1. `.gitignore` 只能阻止尚未跟踪的文件；已经 `git add` 的密钥不会自动消失。
2. 不能因为忽略模型就忘记在 README 说明模型如何下载、哈希如何校验、许可证在哪里看。

建议把配置分为：

```text
config.example.toml     可公开的模板
config.local.toml       本地私有配置，加入 .gitignore
环境变量                密钥和部署差异
```

## 五、依赖、锁定与 SBOM

开源仓库的 `requirements.txt`、`package.json`、`go.mod` 或 `Cargo.toml` 不只是安装说明，也是供应链信息。

建议：

- 写清直接依赖和版本范围；
- 对发布版本保存可复现的锁文件；
- 定期检查依赖许可证与安全公告；
- 对桌面软件、Docker 镜像或二进制发布物生成 SBOM（软件物料清单）；
- 区分开发依赖与运行时依赖。

SBOM 可以回答“某个安装包里到底包含哪些库、版本和许可证”。项目规模变大后，它比手工翻 `requirements.txt` 可靠得多。

## 六、发布前检查清单

### 代码与质量

- [ ] 测试通过，至少有最小可复现检查；
- [ ] README 的安装命令和实际项目一致；
- [ ] 示例不依赖你的本地绝对路径；
- [ ] 没有临时调试代码、个人日志或巨大二进制；
- [ ] `.gitignore` 覆盖虚拟环境、缓存和密钥。

### 权利与合规

- [ ] 已选择并加入完整 `LICENSE`；
- [ ] 已核对上游依赖、代码片段、模型和素材来源；
- [ ] 已保留需要的版权头、NOTICE 和商标限制；
- [ ] 不再分发无权公开的测试数据或权重；
- [ ] 第三方说明与实际打包内容一致。

### 社区与维护

- [ ] `CONTRIBUTING.md` 说明测试和贡献规则；
- [ ] `SECURITY.md` 提供安全问题处理方式；
- [ ] issue/PR 模板引导用户给出最小复现；
- [ ] 用 tag 和 release note 管理正式版本；
- [ ] 明确维护状态，例如 active、maintenance 或 archived。

## 七、一个 Apache-2.0 项目的可执行示例

如果你选择 Apache-2.0，并且项目是自己从零开发，可以按下面顺序完成：

```text
1. 从 Apache 官方复制完整 LICENSE 文本到根目录
2. 在 README 写清项目用途、安装、限制和许可证
3. 建立 NOTICE，写项目归属和必要的第三方归属
4. 建立 THIRD_PARTY_NOTICES.md，登记依赖、二进制、模型和素材
5. 建立 CONTRIBUTING.md、SECURITY.md 和 .gitignore
6. 清理密钥、模型缓存、个人测试媒体
7. 执行测试，打 tag，发布 release
```

Apache-2.0 的第 4 条规定了重新分发时的许可证、修改声明、归属与 NOTICE 义务。选择协议后要读原文，而不是只记“它可以商用”。 [Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0)

## 八、总结

开源不是一次 `push`，而是一份持续维护的承诺：

- 对使用者，提供可理解的权利、安装和限制；
- 对贡献者，提供清晰的协作与测试规则；
- 对上游作者，保留应有的归属和许可证；
- 对自己，保留可复现、可维护、可发布的工程边界。

下一篇会讨论更容易踩坑的情况：当项目不是从零开始，而是参考、复制、fork 或深度改造开源项目时，具体应该怎样做。
