能在 Browser 里画出图，只是开始。真正运行图数据库时，你要能回答：导入有没有破坏约束？慢查询卡在哪里？磁盘故障后能恢复到什么时间点？本章给出单实例 Neo4j 的通用入门 runbook；高可用集群、跨地域灾备和企业版功能应再参考对应版本的官方运维文档。

## 把正确性变成可执行断言

**断言（assertion）**是可自动执行、结果应满足预期的检查。比起“看起来没问题”，它能在导入或发布时立刻发现数据退化。以下查询适合放进测试脚本：

```cypher
// 1. 关键节点必须有业务 ID
MATCH (p:Person) WHERE p.id IS NULL RETURN count(p) AS bad;

// 2. JOINED 只能连接 Person 和 Club
MATCH (:Person)-[r:JOINED]->(x)
WHERE NOT x:Club RETURN count(r) AS bad;

// 3. 必须可追溯的文档关系不能缺来源
MATCH ()-[r:USES|PUBLISHED]->()
WHERE r.sourceChunk IS NULL RETURN count(r) AS bad;
```

预期每个 `bad` 都是 0。对关键业务问题，再准备小型固定数据集和期望答案，例如给定账号网络时“风险节点两跳内有哪些设备”。不要只测试节点总数；关系方向、时间窗口和来源缺失往往不会改变总数。

## 观测查询：从 PROFILE 到日志

当查询变慢，先用实际参数执行 `PROFILE`，记录总耗时、返回行数、每个算子的行数和 DB Hits。若计划从全标签扫描开始，先检查起点属性是否有合适索引；若行数在路径展开阶段暴涨，收紧关系类型、跳数或时间条件。

不要在高峰期对未知重查询反复执行 `PROFILE`，因为它会真正运行查询。先用 `EXPLAIN` 预览计划，在隔离环境复现，再在生产低风险窗口采样。应用侧还应记录查询名称、超时、参数规模和错误类型；原始用户内容或敏感参数需脱敏。

## 容量：关系数量比“节点数”更能说明问题

图数据库的磁盘、页缓存和事务日志需求取决于节点、关系、属性大小、索引、并发写入和备份保留期。尤其要关注高连接度的**超级节点（supernode）**，例如“全体用户都连接的公共标签”；从它开始的多跳查询会有极高分支数。

先在测试环境测量真实工作负载：导入固定批次后的磁盘增长、常用查询的 P95 延迟、写入期间的事务日志增长和内存峰值。容量规划应按增长率和恢复目标预留空间，而不是只按今天的数据目录大小乘一个模糊倍数。

## 持久化、备份与恢复演练

前几章的 `--rm` 容器不持久化数据。想保存本地实验，可显式挂载数据和日志目录；不要在数据库运行时手工复制正在变化的数据文件。一个用于学习的 Docker 示例是：

```powershell
docker run --name neo4j-persistent -d `
  -p 7474:7474 -p 7687:7687 `
  -e NEO4J_AUTH=neo4j/change-this-password `
  -v neo4j_course_data:/data `
  -v neo4j_course_logs:/logs `
  neo4j:5-community
```

预期 `docker volume ls` 能看到两个命名卷。卷避免容器删除时立即丢数据，但它不是备份：同一块磁盘损坏、误删卷、勒索软件仍会让它失效。

备份策略必须先写清两个目标：**RPO（恢复点目标）**是最多可丢多少时间的数据；**RTO（恢复时间目标）**是故障后多久必须恢复服务。不同 Neo4j 版本和版本授权支持的在线备份方式不同；选择方式前先核对当前版本文档。无论采用导出、数据库备份工具还是基础设施快照，都应做到：

1. 备份文件存放在与运行磁盘不同的故障域，并加密、限制访问；
2. 定期校验文件完整性和备份作业结果；
3. 在隔离环境恢复一个副本；
4. 对恢复库运行前述断言与关键查询；
5. 记录实际恢复耗时，检验 RTO 是否真的可达成。

预期的验收不是“备份命令退出码为零”，而是隔离副本能启动、数据量合理、关键关系仍可查询。没有恢复演练的备份，只能算一种乐观情绪。

## 安全与访问边界

不要将 7474/7687 端口直接暴露到公网。使用网络边界、TLS、最小权限账户和密钥管理；应用账户只拥有所需数据库和读写权限。Cypher 一律采用参数化调用，避免把用户输入拼成语句。导出、日志、审计和文档图尤其可能携带敏感属性，设计时就要确定脱敏、保留期和删除流程。

多租户系统还要先决定隔离模型：每租户独立数据库、标签/属性过滤，或独立实例。后两者的查询必须把租户条件放在起点和每个数据访问边界；“最后再过滤”会造成数据泄露风险。

## 常见故障的排查顺序

1. **无法连接**：确认容器/服务是否存活、端口映射、防火墙、认证信息和日志中的启动错误。
2. **导入失败或重复**：检查约束、稳定键、批次重试方式和输入行数；不要先删库重来。
3. **查询很慢**：使用 `EXPLAIN`/`PROFILE`，检查索引起点、路径边界、超级节点和返回字段数量。
4. **磁盘或内存告警**：检查数据、日志、索引、备份临时文件和长事务；先保护数据和停止失控写入，再做清理或扩容。
5. **恢复失败**：保留原始证据，不在唯一副本上反复试验；在新隔离环境验证工具版本、权限和备份完整性。

## 小结

运行图数据库的核心不是记住一组命令，而是建立闭环：用断言证明数据正确，用执行计划定位查询成本，用容量指标预防耗尽，用异地备份和隔离恢复证明可以复原。做到这些，图才会从一次演示变成可信赖的数据系统。
