当 Java 服务出现“连接超时”“读超时”“请求被截断”或 Netty 的 `EventLoop` 被卡住时，只背过 TCP 三次握手通常不够；而在考研复试中，若只能分别说出 HTTP、Socket、TCP 和 DMA 的定义，回答同样很难形成完整的逻辑。

这篇文章的目标，是用**一次 HTTPS 请求的端到端路径**把这些概念连起来。读完后，你应当能够做三件事：

- 日常开发时，按 DNS、路由、TCP、TLS、HTTP、应用的顺序定位网络问题；
- 进阶时，理解网卡、DMA、内核 socket 缓冲区、解包和 I/O 多路复用各自处在什么位置；
- 面对考研或复试追问时，按分层和时序说明“数据到底怎样从一个进程到达另一个进程”。

它是 `Internet` 专题的总纲，而不是另一篇 Netty 或 TCP 首部说明书。若需要逐字段理解 TCP，请阅读 [TCP报文](TCP报文.md)；若需要完整掌握连接建立、关闭和 `TIME_WAIT`，请阅读 [TCP三次握手四次挥手](TCP三次握手四次挥手.md)。先有地图，再走进每一条街道，效率总会高一些。

## 一、先看全景：一次 HTTPS 请求经过了什么

假设浏览器或 Java 客户端访问：

```text
https://api.example.com/orders/42
```

一个典型路径如下。真实环境还会加入缓存、代理、负载均衡、CDN、NAT 和防火墙，但主线并不改变。

```text
应用构造 HTTP 请求
  -> DNS：api.example.com 解析为 IP 地址
  -> 路由：根据路由表选出网卡与下一跳
  -> 链路：ARP / 邻居发现取得下一跳的链路层地址
  -> TCP：建立连接，形成可靠、有序的字节流
  -> TLS：验证服务器身份，协商会话密钥，保护 HTTP 数据
  -> HTTP：请求到达服务端，由 Web 服务器或 Netty Pipeline 解析
  -> 业务、数据库或 RPC：生成响应
  -> 响应沿相反方向返回，客户端解析并展示或处理
```

服务器侧还可以把“数据到达进程前”展开：

```text
网卡收到链路帧
  -> DMA 将数据放入主机内存中的接收队列
  -> 驱动与内核处理链路层、IP、TCP/UDP
  -> 匹配到目标 socket，向其接收缓冲区交付数据
  -> 阻塞 read 被唤醒，或 select / epoll / Selector 报告“可读”
  -> 应用 read，TLS 解密，HTTP 或私有协议解码
  -> 得到业务消息
```

最重要的结论先放在这里：**网络传输不是一次函数调用。每一层只解决自己的问题，并通过缓冲、队列与协议把结果交给下一层。**因此，“`writeAndFlush` 返回”“TCP 已连接”“端口能通”“HTTP 返回 200”分别只说明路径中的不同阶段完成，不能互相替代。

## 二、用分层组织知识，而不是死背层名

### 1. OSI 七层与日常常用模型

OSI 七层适合教学：物理、数据链路、网络、传输、会话、表示、应用。工程中更常把它压缩为 TCP/IP 四层或五层模型：

| 常用五层模型 | 主要职责 | 开发中常见对象 |
| ------------ | -------- | -------------- |
| 应用层 | 定义业务消息、语义与交互规则 | HTTP、DNS、TLS、WebSocket、MySQL 协议 |
| 传输层 | 在主机的进程之间传输 | TCP、UDP、端口 |
| 网络层 | 跨网络把包送到目标主机 | IP、路由、ICMP、NAT |
| 数据链路层 | 在一跳局域链路上传输 | 以太网帧、MAC、交换机、ARP |
| 物理层 | 以电、光或无线信号承载比特 | 网线、光纤、无线电、网卡 PHY |

不要把层数当作真理。它的价值在于定位责任：DNS 是应用层协议，尽管它查询 IP；TLS 常被单列为表示层或安全层，但在现代工程里通常视为位于 HTTP 与 TCP/QUIC 之间的协议；网卡既涉及物理层也涉及链路层。

### 2. 数据在封装中改变了什么

发送端不是把一个“完整 HTTP 包”原封不动扔给网络，而是逐层增加控制信息：

```text
HTTP 消息
  -> （HTTPS 时）TLS record
  -> TCP 字节流中的 TCP 段       或  QUIC 流中的 UDP 数据报
  -> IP 包
  -> 以太网帧
```

接收端按相反方向解封装。常见名词可以这样理解：

- **帧（frame）**：一跳链路上传输的单位；经过路由器时，外层链路帧会被拆掉并重新封装。
- **IP 包（packet/datagram）**：网络层交给路由的单位，源、目的 IP 通常端到端保持不变；经过 NAT 时可能被改写。
- **TCP 段（segment）**：TCP 为可靠传输组织的数据单位。
- **应用消息（message）**：HTTP 请求、聊天消息、RPC 请求等，由应用协议定义边界和语义。

因此，MAC、IP 和端口并非三个重复的地址：MAC 解决“这**一跳**交给哪块网卡”，IP 解决“最终到哪台主机”，端口解决“交给这台主机上的哪个传输端点/服务”。跨路由转发时，下一跳 MAC 会变化，不能说数据包从源 MAC 一路带着同一个目的 MAC 飞到对方。

## 三、从进程出发：IP、端口与 Socket 分别是什么

### 1. IP 找主机，端口找服务，Socket 是操作系统的通信端点

同一台机器可以同时运行浏览器、数据库、Java 服务和 SSH 服务；仅凭 IP 无法决定数据属于谁。传输层用端口把数据交给相应服务，例如客户端临时端口 `51523` 到服务端 `443`。

`socket` 是操作系统提供的网络通信端点与编程接口。在 Linux 中它可通过文件描述符操作；在 Java 中，`Socket`、`ServerSocket`、`SocketChannel` 是对相关系统能力的封装。TCP 服务端至少有两类 socket：

- **监听 socket**：绑定本地 IP/端口，等待可接受的新连接；
- **已连接 socket**：`accept` 成功后得到，代表一条具体的双向 TCP 连接。

一条 TCP 连接通常由本地 IP、本地端口、远端 IP、远端端口区分；协议类型和地址族也参与操作系统的实际匹配。端口本身不是“某个进程的永久身份证”，而是可被操作系统按规则绑定、复用和释放的资源。

Java 阻塞式 `ServerSocket.accept()`、输入流 `read()` 与消息边界的基础示例，可继续阅读 [网络编程](../Java/网络编程.md)。其中的关键提醒值得先记住：**`read()` 读取的是字节，不是“恰好一条业务消息”。**

### 2. 客户端先决定走哪张网卡、交给谁

拿到服务器 IP 后，主机查询路由表，使用**最长前缀匹配**选择路由。例如目标在本地子网，就直接走本地网卡；目标不在本地子网，通常交给默认网关。子网掩码、CIDR 与同网段判断可在 [子网掩码](子网掩码.md) 中深入学习。

这里有一个经常答错的细节：访问异网段服务器时，主机通常通过 ARP（IPv6 中为邻居发现）查询的是**下一跳网关的 MAC 地址**，而不是远方服务器的 MAC 地址。ARP 的作用范围是本地二层网络，路由器之后的链路由下一跳继续处理。

## 四、链路与网络层：帧怎样跨网络到达目标主机

### 1. 先把常见网络硬件放在正确位置

家里常被统称为“路由器”的一台设备，可能同时包含光猫、交换机、无线 AP、路由器、NAT、防火墙和 DHCP/DNS 转发功能。为了理解网络，也为了正确回答考试题，必须按**主要转发依据和职责**将它们拆开；物理设备可以合并，抽象职责不能含混。

| 设备或组件 | 主要处理对象 / 决策依据 | 典型职责 | 关键边界 |
| --------- | ---------------------- | -------- | -------- |
| 网卡（NIC） | 比特、链路帧、队列与 DMA 描述符 | 连接有线/无线介质，收发帧，协助将数据交给主机内存 | 它不是 IP 地址，也不直接把数据送到 Java 进程 |
| 中继器 / 集线器 | 物理信号 | 再生或复制信号 | 不理解 MAC、IP 和帧；传统共享介质上的节点共享碰撞域 |
| 二层交换机 | 目的 MAC 与 VLAN | 在局域网内转发、过滤或泛洪以太网帧 | 通常不按 IP 选路径；每端口独立碰撞域，但同一 VLAN 仍是广播域 |
| 三层交换机 | MAC + IP/FIB | 在局域网内高速二层交换，同时在 VLAN/子网间路由 | 本质上具备路由能力，常用于园区网内部互联 |
| 路由器 | 目的 IP、路由/转发表 | 连接不同 IP 网络，逐跳转发数据报 | 不转发二层广播；每跳会重新封装链路帧 |
| 无线 AP | 802.11 帧、关联状态 | 将无线终端接入有线 LAN | AP 不必然等于路由器；家庭无线路由器通常两者兼具 |
| 光猫 / 调制解调器 | 接入链路的物理/链路信号 | 完成光、电或不同接入介质的调制、解调/终结 | 它可工作在桥接或路由模式，不能只凭外形判断职责 |
| 防火墙 / 安全网关 | 五元组、状态、策略，有时还检查应用层 | 允许、拒绝、审计或限速流量 | 它能拦截连接，但不是路由表、DNS 或业务权限的替代品 |

可以将典型家庭或小型办公网络想成下面的结构：

```text
笔记本 --Wi-Fi--> AP --以太网--> 交换机 --LAN--> 路由器/NAT/防火墙
                                                    |
                                                  WAN
                                                    |
                                             运营商接入设备/Internet
```

若笔记本访问同一 VLAN 的另一台电脑，可能只需经过 AP 和交换机；若访问公网服务器，默认网关上的路由器才会参与三层转发和可能的 NAT。不要认为“所有访问都先经过路由器”；同网段二层转发本就不需要它。

### 2. 交换机怎样依据 MAC 表转发帧

二层交换机每个端口连接一个链路。它维护一张常被称为 MAC 表、CAM 表或转发表的映射：`MAC 地址 + VLAN -> 入/出端口`。这张表不要求管理员为每台终端手工填写，交换机会从**收到帧的源 MAC**学习。

收到一帧时，交换机的基本行为是：

```text
1. 在入端口所属 VLAN 中，学习“源 MAC -> 入端口”，并刷新老化计时器
2. 查找“目的 MAC -> 哪个端口”
3. 若命中且出端口不同于入端口：只向该端口转发（unicast forwarding）
4. 若命中但出端口就是入端口：过滤，不再转发（filtering）
5. 若未命中，或目的 MAC 是广播/相应组播：在该 VLAN 的其他端口泛洪（flooding）
```

这也解释了 ARP 的路径：主机还不知道下一跳 MAC 时发广播 ARP 请求，交换机会在同一 VLAN 泛洪；得到 ARP 应答、学到 MAC 表后，后续普通单播帧通常只走目标端口。MAC 表会老化，设备迁移端口或拓扑变化时才能重新学习，毕竟一张永远不更新的表只会把网络带回过去。

**VLAN** 在同一台物理交换机上划分多个逻辑二层网络。不同 VLAN 的广播相互隔离；接入口（access port）通常只承载一个 VLAN，无线 AP 到交换机、交换机到交换机的链路则常以 trunk 承载多个 VLAN，并用 802.1Q 标签标识所属 VLAN。不同 VLAN/子网之间要通信，仍需要三层接口和路由。

二层拓扑若存在冗余环路，广播或未知单播会不断被泛洪，形成广播风暴。生成树协议（STP/RSTP）会逻辑阻塞一部分冗余链路，形成无环转发树；链路故障后再收敛启用备用路径。这是“冗余链路为什么反而可能让二层网络瘫痪”的标准解释。

### 3. 路由器怎样在不同网络之间转发

路由器有多个三层接口，每个接口连接一个 IP 网络。它收到帧后，不会把原帧原样转发：先校验和解封装二层信息，取得 IP 数据报；然后检查 TTL、路由与策略；最后从选定的出口接口重新封装为下一跳链路帧。

```text
入接口收到：源 MAC A -> 目的 MAC R1，IP: 客户端 -> 服务器
    -> 路由器去除入链路层首尾，TTL 减 1
    -> 对目的服务器 IP 做最长前缀匹配，决定出口与下一跳
    -> 通过 ARP / 邻居发现得到下一跳 MAC
出接口发出：源 MAC R2 -> 目的 MAC 下一跳，IP: 客户端 -> 服务器
```

因此，跨路由器时 MAC 地址逐跳变化，而源、目的 IP 通常保持端到端不变；NAT 是会改写 IP 地址和常常也改写端口的重要例外。若 TTL 变为 0，路由器丢弃数据报并通常返回 ICMP 超时消息，这也是 `traceroute` 能逐跳观察路径的基础之一。

路由器内部还要区分两个平面：

- **控制平面**负责生成和维护路由信息，例如管理员配置静态路由，或通过 RIP、OSPF、BGP 学习路径。它维护的完整信息常称 RIB（路由信息库）。
- **数据/转发平面**在每个包到达时快速查询 FIB（转发表），采用最长前缀匹配决定出口、下一跳及相关动作。它追求每包快速处理，而不是重新运行路由算法。

例如一张 FIB 中同时存在 `10.0.0.0/8`、`10.1.0.0/16` 与 `10.1.2.0/24`，目的地址 `10.1.2.9` 会命中最长的 `/24`。这就是“最长前缀匹配”，不是把地址看起来最像的规则随意猜出来。

路由器的输入/输出端口还存在队列。入端口速率、交换结构能力与出端口带宽不匹配时会排队；队列满时就只能丢包或按队列管理策略处理。TCP 的重传、拥塞控制与应用层限流，正是在端系统层面对这种现实进行协作，而不是认为路由器总能无限暂存数据。

### 4. NAT、家庭路由器与“能上网但不能被访问”

**NAT** 常部署在家庭路由器、云 VPC 出口或企业网关：它在私网与公网之间改写 IP 地址；最常见的 NAPT/PAT 还改写端口，使许多内网连接能够共享一个或少量公网 IPv4 地址。网关维护转换状态，例如：

```text
192.168.1.10:51523  <->  203.0.113.8:40001
```

外部响应带着公网地址和端口返回时，网关根据状态表再映射回内网主机。这解释了内网客户端通常能主动访问外部服务，而公网主机不能无条件反向新建连接到内网服务：没有已有映射时，网关不知道该转给哪一台私网主机。端口映射、反向代理、内网穿透或中继服务就是在补足这条入站路径，详见 [内网穿透](内网穿透.md)。

NAT 缓解 IPv4 地址短缺，却也破坏了“每个端点都可被全局直接寻址”的端到端理想。家庭设备还经常顺带承担 DHCP、DNS 转发、Wi-Fi AP 和状态防火墙；把这些职责都口语化叫成“路由器功能”没有问题，但排障时必须继续问：究竟是 DHCP、DNS、NAT、防火墙策略，还是路由表出了错？

代理与 VPN 也会改变请求路径，但不是一回事。正向/反向代理的工作位置、系统代理模式可见 [系统代理模式](系统代理模式.md)；“代理、VPN 为什么都能访问外部网络”的边界可见 [代理和 VPN](../RandomThoughts/“梯子”、代理和 VPN：它们为什么都能访问外部网络？.md)。

### 5. MTU、MSS 与“分包”不是同一个概念

这三个概念很容易被笼统称为“包太大”，但它们分属不同层次：

| 概念 | 所在层次 | 它限制什么 |
| ---- | -------- | ---------- |
| MTU | 链路层路径能力 | 一帧中能承载的最大 IP 包大小，常见以太网 MTU 为 1500 字节，但不能当作普适常量 |
| MSS | TCP 选项/传输层 | 单个 TCP 段中可承载的最大 TCP 数据长度，通常会随路径 MTU 推导 |
| 应用消息长度 | 应用层 | 一个 HTTP 请求体或私有协议消息能多大，由协议和服务端限制决定 |

TCP 会按合适大小组织字节流，不代表每个 `write` 对应一个 TCP 段。IPv4 在必要时可能发生 IP 分片并在目的端重组；IPv6 不允许路由器分片，路径 MTU 不够时会通过 ICMPv6 通知源端调整。工程上应避免依赖 IP 分片：它增加丢失与排障复杂度，路径 MTU 发现受阻还会出现“能连上、传大内容就卡住”的现象。

`ping` 使用 ICMP，能说明部分网络可达性，却不能证明 TCP 443、TLS 或 HTTP 正常；同样，某些网络会刻意限制 ICMP。所以它只是排障线索，不是业务可用性的判决书。

## 五、传输层：TCP 与 UDP 到底如何选择

### 1. TCP 提供的是可靠、有序的双向字节流

TCP 面向连接、全双工，并为应用提供可靠、有序的**字节流**。它通过序列号、确认号、校验和、超时重传、排序和去重等机制处理丢失和乱序；通过接收窗口实施流量控制；通过拥塞控制避免持续把网络路径压垮。TCP 的标准定义和首部可参考 [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。

三次握手让双方同步初始序列号并建立连接状态，四次挥手反映两个方向可独立关闭；它们的完整时序与 `TIME_WAIT` 原因请阅读 [TCP三次握手四次挥手](TCP三次握手四次挥手.md)。可靠性绝不等于“发出必达且立即送到业务代码”：网络中断、超时、进程崩溃、应用拒绝都可能使业务失败。

特别应区分两个窗口：

- **接收窗口 `rwnd`**：接收方依据自己剩余缓冲与处理能力通告，解决“接收端跟不上”。
- **拥塞窗口 `cwnd`**：发送端依据网络拥塞估计控制，解决“路径和中间设备跟不上”。

发送量同时受二者约束。前者是端点之间的流量控制，后者是对共享网络的拥塞控制，名字相似却不是一回事。

### 2. UDP 保留数据报边界，但不替你保证结果

UDP 直接提供数据报语义：一次接收以一个数据报为单位，而不是 TCP 那样的连续字节流。它本身不提供 TCP 那套连接建立、可靠送达、顺序保证、去重、流量控制和拥塞控制机制。DNS、实时音视频、游戏等可根据自己的需求选择它；QUIC 也以 UDP 为承载，但在其上自行实现可靠传输、拥塞控制与多流。

| 维度 | TCP | UDP |
| ---- | --- | --- |
| 交付语义 | 可靠、有序的字节流 | 尽力而为的数据报 |
| 应用消息边界 | 不保留 | 保留一个数据报边界 |
| 可靠性与顺序 | 协议提供 | 应用按需求补充 |
| 常见用途 | HTTP/1.1、HTTP/2、数据库、传统 RPC | DNS、实时传输、QUIC 承载 |

“UDP 更快”不是选择依据。少了机制可能减少等待，却也把丢包恢复、乱序处理、速率控制等责任交回应用；UDP 数据报过大、接收缓冲区不足时仍会丢失或被截断。反过来，UDP socket 也可以调用 `connect` 固定默认对端，这不改变 UDP 的无连接传输语义。

## 六、接收缓冲区、粘包与解包：不要把三件事混为一谈

### 1. 接收缓冲区不是网卡，也不是 Netty 的 `ByteBuf`

一份到达服务器的数据，可能先经过网卡接收描述符/队列、内核网络栈，才被交给某个 socket 的**内核接收缓冲区**。应用调用 `read` 读到的是可交付给该 socket 的字节；它不是直接从网卡“取数据”。Java 堆数组、直接内存和 Netty `ByteBuf` 又是用户态缓冲，它们也不等同于内核接收缓冲区。

接收缓冲区是有限资源，实际容量、自动调优与记账方式随操作系统而异。当 TCP 应用读得太慢时，接收端可通告更小的接收窗口，最终使发送端放慢；这就是背压的一部分。UDP 没有 TCP 的这套端到端流量控制，缓冲不足更可能直接造成数据报丢失。

发送侧同样有内核发送缓冲区。一次 `write` 或 `ctx.writeAndFlush` 被框架或内核接纳，至多说明数据进入后续发送路径；它**不等于**网卡已经发出、不等于收到 TCP ACK、更不等于对端应用已成功处理。把这几个阶段混成“写成功”，往往正是消息重复、重试和幂等设计的开端。

### 2. “粘包/半包”是应用定界问题，不是 TCP 出错

请严格区分：

1. **IP 分片与重组**：网络层为了适应 MTU 进行的处理。
2. **TCP 的按序字节流交付**：TCP 处理段的丢失、乱序并向应用呈现连续字节；它不保留应用 `write` 的边界。
3. **应用层解包**：应用协议从连续字节中恢复一条条业务消息。

所谓“半包”是一次 `read` 只拿到某条应用消息的一部分；“粘包”是一次 `read` 拿到多条消息，或一条消息尾部紧接下一条消息。它们不是两个 TCP 包神秘地粘在一起，而是程序错误地把 `read` 边界当成了消息边界。网络调度、发送缓冲、接收缓冲、MSS 和读取时机都可能影响一次读取返回多少字节。

例如客户端依次写入两条消息：

```text
HELLO
BYE
```

服务端可能看到下面任一种读取结果：

```text
HEL
LO\nBYE\n
```

或者：

```text
HELLO\nBYE\n
```

因此协议必须定义边界。常见方案如下：

| 定界方式 | 示例 | 优点 | 边界条件 |
| -------- | ---- | ---- | -------- |
| 固定长度 | 每条报文固定 128 字节 | 解析简单 | 浪费空间，不适合可变内容 |
| 分隔符 | `\n`、CSV 的换行 | 直观 | 内容中出现分隔符时需要转义；必须限制最大长度 |
| 长度字段 | 4 字节长度 + 消息体 | 通用、高效 | 必须校验长度上限，防止恶意长度导致内存耗尽 |
| 协议自身规则 | HTTP 的 `Content-Length` 或分块编码 | 标准化 | 必须严格按协议解析，避免前后端解释不一致 |

Netty 的私有二进制协议常使用长度字段解码器：

```java
channel.pipeline()
        .addLast(new LengthFieldBasedFrameDecoder(
                1024 * 1024, // 最大帧长度：1 MiB
                0,           // 长度字段从第 0 字节开始
                4,           // 长度字段占 4 字节
                0,           // 长度值不需要额外调整
                4))          // 向下游交付时跳过长度字段
        .addLast(new LengthFieldPrepender(4))
        .addLast(new BusinessHandler());
```

这个示例的重点不是记住参数，而是理解解码器会在数据不足一帧时保留已累计字节，等下次读取后继续；获得完整帧后才交给业务 Handler。`maxFrameLength` 不是装饰，缺少它会让伪造的大长度字段变成内存攻击入口。HTTP 使用成熟解码器时也仍要限制请求行、请求头和请求体大小；不要无上限使用聚合器处理上传或流式转发。

关于 Java 阻塞读取、NIO 与消息边界的代码背景可阅读 [网络编程](../Java/网络编程.md) 和 [NIO](../Java/NIO.md)；Netty 的读写、Pipeline 与线程分工将在后文给出总览并链接到专文。

## 七、HTTP、HTTPS 与 DNS：应用层真正交换的是什么

### 1. DNS 在建连之前解决名字

应用通常从域名开始，而不是 IP。DNS 负责把 `api.example.com` 映射为地址记录，客户端还可能经过浏览器、操作系统、网络或应用自己的缓存。DNS 失败时，TCP 尚未开始；因此“域名解析失败”不能用调大 HTTP 读取超时解决。DNS 的记录、递归与迭代解析请阅读 [DNS](DNS.md)。

### 2. HTTP 定义语义，不负责可靠传输

HTTP 定义方法、URI、状态码、首部和消息语义，例如 `GET`、`POST`、`200`、`404`、`Content-Type`。HTTP/1.1 常以持久连接复用 TCP 连接，其消息体通过 `Content-Length`、`Transfer-Encoding: chunked` 等规则定界；一条 HTTP 消息不等于一个 TCP 段，也不等于一次 `read`。

HTTP/2 在一条 TCP 连接内以 frame 和 stream 实现多个请求并发，减少 HTTP/1.1 应用层队头阻塞；但 TCP 仍需按顺序交付字节，丢失一个 TCP 段仍可能阻塞同一连接上的其他流。HTTP/3 使用 QUIC，QUIC 以 UDP 承载并实现多流可靠传输，从而避免**跨流的 TCP 队头阻塞**；这不等于它永远没有排队、丢包或拥塞造成的延迟。

### 3. HTTPS 不是“HTTP + RSA”，也不是端口 443 的别名

HTTPS 通常指 HTTP 运行在 TLS 的保护之上；HTTP/3 则是 HTTP 运行在 QUIC/TLS 上。TLS 通过加密保护机密性，通过认证码/AEAD 保护完整性，并在正确验证证书时认证服务器身份；客户端证书认证是可选能力，并非所有 HTTPS 网站都会使用。

证书校验至少涉及域名（SAN）、有效期、用途、证书链和信任根；浏览器或客户端还会验证服务端确实持有相应私钥。证书不是秘密，服务器私钥才必须保密；小锁也不代表网站业务没有漏洞、更不代表用户已获得任何业务权限。关于 CA、证书链和旧系统兼容性，请阅读 [网络证书的作用](网络证书的作用.md)。

TLS 保护的边界也要诚实面对：IP 地址、部分域名线索、数据包大小和通信时序仍可能暴露；是否加密 DNS、是否隐藏 SNI 等取决于额外机制。更具体地说，TLS record 同样不是 Java `read` 或 Netty `channelRead` 的固定边界。

## 八、网卡、DMA 与内核：字节怎样进入 socket

### 1. DMA 减少 CPU 搬运，不等于所有地方“零拷贝”

网卡收到帧后，常可借助 **DMA（Direct Memory Access，直接内存访问）**，依据描述符把数据放入主机内存的接收队列。这样 CPU 不需要逐字节把数据从网卡搬进内存，而可以主要负责配置、调度和协议处理。

之后由网卡驱动和内核处理数据。低流量下，硬件中断常用于通知 CPU；高流量下，Linux 等系统会使用 NAPI 之类的中断配合轮询机制，避免中断风暴。校验和卸载、接收聚合等也可能由硬件或内核协作完成。具体实现随网卡、操作系统和配置而变，因此不要把“每个包必触发一次中断”当作固定流程。

内核继续处理以太网、IP 与 TCP/UDP，查找匹配的 socket，并向其接收缓冲区交付可读数据。DMA 只说明设备和主内存之间的搬运方式；内核与用户态之间是否还复制、是否使用直接缓冲区、是否采用 `sendfile` 等优化，要看 API 和具体路径。把 DMA 直接等同于“零拷贝”，未免太省略了中间真正存在的工作。

### 2. 阻塞 I/O 和 I/O 多路复用在这里接上

阻塞 socket 上调用 `read` 时，若接收缓冲区没有可交付数据，线程会睡眠等待；这段时间它不能继续处理别的文件描述符。传统“一连接一线程”直观，但大量空闲连接会带来线程栈、调度和上下文切换成本。

非阻塞 socket 则会立即返回：Java `SocketChannel.read()` 在暂时没有数据时可返回 `0`，到达 EOF 时返回 `-1`；原生接口常用 `EAGAIN`/`EWOULDBLOCK` 表达暂不可读。非阻塞并不意味着不断空转轮询——I/O 多路复用的关键是把“哪一个 socket 值得尝试读写”交给内核。

```text
EventLoop
  -> select / epoll_wait / Selector.select：阻塞等待一组 socket 的就绪事件
  -> 获得可读、可写或可接受的 socket
  -> 对对应 socket 执行非阻塞 accept / read / write
  -> 继续等待下一批事件
```

“可读/可写”是**就绪通知**，不是“完整 HTTP 请求已到达”或“响应已送达客户端”的完成通知。监听 socket 可接受时仍要调用 `accept`；socket 可读时仍要按协议读取和解码；可写通常只表示内核发送缓冲暂有空间。Java `Selector` 与 Linux `epoll` 的关系、Netty 默认的 `EventLoop` 线程职责、`bossGroup`/`workerGroup` 的典型分工，请阅读 [Netty 中的 I/O 多路复用：阻塞在哪里，线程又如何分工](../Java/Netty%20中的%20I_O%20多路复用：阻塞在哪里，线程又如何分工.md)。

### 3. 为什么业务阻塞仍能拖慢网络服务

Netty 默认情况下，已连接 `Channel` 的 I/O 事件和 Pipeline 回调通常由所属 `EventLoop` 串行推进。一个 EventLoop 可以管理多条连接；若 Handler 同步查库、等待远程 RPC、执行很长的 CPU 任务或发生严重锁竞争，它就不能及时读取其他连接、处理心跳或继续写出响应。

所以“用了 epoll/Netty”不等于业务自动异步。保持 EventLoop 上的工作短小且可预测，把确实会阻塞或显著耗时的业务卸载到有界、可拒绝、有超时策略的执行器，才是正确的职责划分。反过来，任何轻量操作都切线程也会增加排队和切换成本；架构不是越复杂越好，这一点其实不难理解。

## 九、开发排障：按路径逐层缩小，而不要先猜框架有问题

网络故障的高效排查方式，是先判断失败发生在哪一段路径，再向下钻取证。可以按下图组织：

```text
域名解析失败？
  -> DNS、hosts、DNS 缓存、代理 DNS
TCP 连接失败？
  -> 路由、防火墙、安全组、监听地址/端口、NAT
TLS 握手失败？
  -> 证书链、主机名、客户端信任库、协议版本、SNI/ALPN
HTTP 返回异常或缓慢？
  -> 请求方法/首部/重定向、服务端、反向代理、限流
HTTP 成功但业务失败？
  -> 认证、参数、数据库、RPC、应用逻辑
```

### 1. 先把“超时”说清楚

下面这些超时的含义不同，不能只设置一个很大的总超时来掩盖问题：

| 阶段 | 典型现象 | 常见原因 |
| ---- | -------- | -------- |
| DNS 超时/失败 | 域名无法解析 | DNS 服务器、网络、缓存或域名配置 |
| 连接超时 | TCP 握手迟迟未完成 | 路由不可达、防火墙丢弃、安全组、地址错误 |
| 连接被拒绝 | 很快收到 `Connection refused` | 目标主机可达，但端口未监听或被主动拒绝 |
| TLS 握手失败 | 证书或协议协商报错 | 证书、信任库、SNI、TLS 版本/套件不兼容 |
| 首字节超时（TTFB） | 已连上但迟迟无响应首部 | 服务端排队、业务慢、上游或数据库慢 |
| 读取/整体超时 | 响应中途慢或整个请求超时 | 慢客户端、网络抖动、传输或应用处理慢 |

连接重置（`Connection reset`）又不同于拒绝和超时：它通常表示收到了 RST，可能来自对端进程、负载均衡、防火墙或连接状态异常。更详细的超时分类和 Java 场景可继续阅读 [响应超时](响应超时.md)。

### 2. 有用的基础观察命令

命令只能提供证据，不能替代推理。Windows 与 Linux 上常用的最小工具集如下：

| 目的 | Windows / PowerShell | Linux / 通用 |
| ---- | -------------------- | ------------ |
| 查询 DNS | `Resolve-DnsName api.example.com` | `dig api.example.com`、`nslookup` |
| 测试 TCP 端口 | `Test-NetConnection host -Port 443` | `nc -vz host 443` |
| 查看 HTTP/TLS 过程 | `curl -v https://host/` | `curl -v https://host/` |
| 查看连接状态 | `Get-NetTCPConnection` | `ss -tanp` |
| 查看路由 | `route print` | `ip route` |
| 抓包 | Wireshark | `tcpdump`、Wireshark |

抓包时按层确认：有无 DNS 响应、SYN 是否发出并收到 SYN-ACK、TLS alert 是什么、HTTP 请求是否真的离开客户端、服务端是否回包、是否存在重传和窗口收缩。注意 TLS 会加密 HTTP 载荷；若没有适当的解密条件，抓包不一定能展示明文请求体。

### 3. 重试、幂等和背压是网络代码的一部分

客户端读超时后，不能据此断言“服务端一定没有执行”。请求可能已经到达、已经写入数据库，只是响应在路上丢失或客户端来不及收到。因此重试要结合 HTTP 方法语义、业务幂等键、去重记录与可观测性设计；对扣款、创建订单这类操作，盲目重试尤其危险。

同样，队列、连接数、请求体大小、并发流、socket 缓冲与业务线程池都必须有上限。下游慢时，无界排队只会把延迟扩大成内存问题；正确方向通常是超时、限流、背压、熔断和明确的拒绝策略，而不是无限加线程或无限增大缓冲区。

## 十、408 初试补全：把容易被工程实践跳过的基础补齐

日常后端开发会频繁接触 HTTP、TCP、TLS 和 Netty，却很少亲手计算 CRC、信道容量或路由表；这些内容仍是计算机网络初试的重要部分。以全国硕士研究生招生考试计算机学科专业基础考试的公开大纲为例，范围按网络体系结构、物理层、数据链路层、网络层、传输层、应用层展开。[考试大纲](https://yankao.neea.edu.cn/xhtml1/report/21115/4961-1.htm)

下面不是把一整本教材再次誊写一遍，而是给出应能独立推导、计算和口述的最小闭环。若题目需要逐步手算，请在这些锚点上配合真题训练；只看结论，终究会在换一个数字后失效。

### 1. 网络体系结构、交换方式与时延

除了分层和封装，还应能区分协议、服务和接口：**协议**是同层实体通信的规则，包含语法、语义和同步；**服务**是下一层向上一层提供的能力；**接口**是相邻层交互的边界。`Socket API` 是进程使用操作系统网络服务的接口，不是“Socket 协议”。

Internet 采用分组交换：长消息被拆成分组，在链路上与其他流量统计复用。它不需要像电路交换那样预留一条独占通路，适合突发数据；代价是路由器可能存储转发并产生排队、丢失和乱序。IP 提供尽力而为的数据报服务，端系统的 TCP 或应用协议再按需补充可靠性。

一个节点或路径的时延，至少要能拆成四部分：

$$
d_{\text{nodal}} = d_{\text{proc}} + d_{\text{queue}} + d_{\text{trans}} + d_{\text{prop}}
$$

其中发送时延和传播时延最容易混：

$$
d_{\text{trans}} = \frac{L}{R}
\qquad
d_{\text{prop}} = \frac{D}{v}
$$

- `L` 是分组长度（bit），`R` 是链路速率（bit/s）；**发送时延**与报文大小有关，和距离无直接关系。
- `D` 是链路距离，`v` 是信号传播速度；**传播时延**与距离有关，和报文大小无直接关系。
- 排队时延高度依赖负载，不能用一个固定常量替代。

还应分清带宽与传输速率：带宽在物理通信语境通常以 Hz 表示可用频率范围，数据传输速率以 bit/s 表示每秒传输的比特数。理想无噪声信道常用奈奎斯特公式，含噪信道的理论上限常用香农公式：

$$
C = 2W\log_2 V
\qquad
C = W\log_2(1 + S/N)
$$

前者受带宽 `W` 与信号电平数 `V` 限制，后者中的 `S/N` 是线性信噪比；若题目给出 dB，需先换算为线性值。它们不是两道互相替代的万能公式，题干给出的信道条件决定使用哪一个。

### 2. 数据链路层：一跳交付、CRC、以太网与设备

数据链路层主要解决相邻节点的一跳帧传输：成帧、链路寻址、差错检测、介质访问控制等。它与 TCP 的端到端可靠传输并不重复：例如以太网常以 CRC 发现错误帧后丢弃，最终是否重传往往由 TCP 或更高层决定。

考试中需要掌握以下机制：

- **成帧和透明传输**：字符计数、字节填充、比特填充、违规编码等方法如何让接收方识别帧边界。
- **差错检测**：奇偶校验只能发现有限错误；CRC 用生成多项式进行模 2 除法，发送端附加余数，接收端余数非零则发现差错。CRC 擅长检错，不等于自动纠错。
- **可靠传输与滑动窗口**：停止等待、回退 N 帧（GBN）和选择重传（SR）。GBN 接收方通常只按序接收并累计确认；SR 可缓存乱序帧、只重传缺失帧。若序号空间为 `N`，GBN 的发送窗口通常不超过 `N - 1`，SR 为避免新旧帧混淆，发送/接收窗口通常都不超过 `N / 2`。
- **介质访问**：共享半双工以太网曾使用 CSMA/CD 和二进制指数退避；现代交换机上的全双工点到点链路不发生传统碰撞，因此不需要 CSMA/CD。无线网络更常讨论 CSMA/CA。

设备题可以按转发依据回答：集线器主要复制物理信号；二层交换机按 MAC 地址表转发帧，并通过自学习、转发、过滤和泛洪工作；路由器按 IP 路由表转发数据报、隔离广播域。现代设备可能具有多层功能，但这是它们的典型层次职责。

ARP 是本地 IPv4 链路上“已知下一跳 IP，查询其 MAC”的协议。ARP 请求通常广播，应答通常单播；跨网段访问时查询的是默认网关接口的 MAC。VLAN 用逻辑二层隔离广播域；IPv6 的相邻节点地址解析由邻居发现协议完成，而不是 ARP。

### 3. 网络层：IPv4、CIDR、路由与 IPv6

网络层的关键词是**主机到主机的逻辑寻址与逐跳转发**。应当区分：路由是控制平面计算、学习和维护“目的网络该走哪个下一跳”；转发是收到一个具体数据报后查转发表并送往输出接口。路由表查找采用最长前缀匹配，而不是“先写的规则优先”。

IPv4 题至少应熟练掌握地址、前缀和子网的计算。对于地址 `A/p`：

1. 将 IP 与掩码按位与，得到网络地址。
2. `p` 之后有 `h = 32 - p` 位主机位；传统子网中主机位全 0 是网络地址、全 1 是广播地址。
3. 常规可分配主机数为 `2^h - 2`；`/31` 点到点链路、`/32` 主机路由等特殊工程语义须以题干为准。

例如 `192.168.10.37/27` 的掩码是 `255.255.255.224`，最后一段块长为 `32`，所以网络地址为 `192.168.10.32`，广播地址为 `192.168.10.63`，通常可用主机范围为 `.33` 到 `.62`。CIDR 通过前缀长度表达可变大小网络，既减少传统分类地址的浪费，也能通过路由聚合缩小路由表。

IPv4 首部中的 TTL 在每经过一台路由器时递减，用于避免路由环路中的无限转发；ICMP 可报告差错并支持 `ping`、`traceroute` 等诊断。IPv4 可能在路径 MTU 不足时分片，目的端重组；任一分片丢失都可能使整个原始数据报无法交付。IPv6 具有更大地址空间和更简化的固定首部，路由器不负责分片，源端应依据路径 MTU 调整。

动态路由的最小对比也应说得出来：RIP 属于 AS 内距离向量协议，以跳数为主要度量，简单但收敛与规模受限；OSPF 属于 AS 内链路状态协议，以链路状态数据库和 Dijkstra 算法计算路径；BGP 用于 AS 之间，以路径向量和策略为核心。不要只背“RIP 慢、OSPF 快、BGP 大”，它们的作用范围和路由信息表达方式才是区别。

### 4. 传输层与应用层：初试还应会哪些题

本文前文已详细说明 TCP/UDP、可靠传输、窗口、HTTP、DNS 和 TLS。作为初试清单，仍应逐项自检：

- TCP 首部的端口、序号、确认号、标志位、窗口、校验和与常见选项分别做什么；序号按**字节**编号，确认号表示期望的下一个字节。
- 三次握手、四次挥手各报文的序号/确认号如何推算；为什么主动关闭方要 `TIME_WAIT`。
- `rwnd` 与 `cwnd` 的差别；慢开始、拥塞避免、快重传、快恢复的因果关系。
- DNS 的递归查询、迭代查询、缓存和常见资源记录；DNS 成功不等于端口、TLS 和 HTTP 都成功。
- HTTP 请求/响应格式、持久连接、Cookie/Session、代理；FTP 的控制/数据连接，SMTP、POP3、IMAP 的角色等传统应用层考点。

对于滑动窗口、CRC、路由算法和 IP 分片，最有效的复习方法是亲自按位、按序号和按表项算一遍。它们看似细碎，却直接考察是否真正理解协议状态如何演进，而不是能否把概念说得流利。

## 十一、考研与复试：用“主回答 + 追问”组织知识

复试不是把定义按字典顺序背出来。较稳妥的回答结构是：**先给结论，再说链路或机制，最后说边界和实践影响。**下面的问题足以覆盖日常高频追问。

### 1. 输入一个 URL 后发生了什么

可先按以下顺序口述：浏览器解析 URL，查询 DNS 与缓存得到 IP；根据路由表选择出口和下一跳；通过 ARP/邻居发现取得链路地址；与服务器建立 TCP 或 QUIC 连接；HTTPS 场景进行 TLS 证书验证和密钥协商；发送 HTTP 请求；服务端经反向代理、应用和下游处理后返回 HTTP 响应；浏览器继续解析、渲染并加载子资源。

追问时再展开 DNS、三次握手、TLS、缓存、HTTP/2 或 HTTP/3。不要一开始背诵所有协议细节；回答应当像一条可继续展开的路径。

### 2. TCP 为什么可靠

核心不在于“三次握手”。应回答：TCP 用序列号标识字节位置，用确认号、超时和重传修复丢失，用校验和检测传输损坏，用排序和去重恢复有序字节流，用接收窗口做流量控制，用拥塞控制适应网络容量。三次握手解决的是建立连接和初始状态同步，不是 TCP 全部可靠性的来源。

### 3. TCP 与 UDP 怎么选

先从业务语义回答：是否需要可靠、有序传输，是否能容忍丢失和乱序，是否需要自定义时延/恢复策略。TCP 提供可靠有序字节流，适合多数 Web、数据库和传统 RPC；UDP 保留数据报边界但不承诺送达，适合 DNS、实时场景或作为 QUIC 承载。不要用“UDP 一定更快”作为唯一理由。

### 4. 为什么会粘包、怎样解决

先纠正表述：TCP 是字节流，不保存应用消息边界；一次 `read` 可得到半条、一条或多条业务消息。再给出固定长度、分隔符、长度字段、HTTP 等协议规则四类方案，并补充长度上限和累计缓冲。若面试官继续追问，再区分 IP 分片、TCP 段和应用层解包。

### 5. 三次握手为什么不是两次，`TIME_WAIT` 为什么存在

两次握手无法让服务端确认客户端收到了自己的 SYN+ACK，也难以避免旧连接请求造成错误状态；第三次确认完成双方初始序列号同步。主动关闭方进入 `TIME_WAIT`，一是有机会重发最后 ACK，二是让旧连接残余报文过期。完整状态机请回到 [TCP三次握手四次挥手](TCP三次握手四次挥手.md)。

### 6. HTTP、HTTPS 与 TLS 的关系

HTTP 定义应用语义；HTTPS 通常是 HTTP 运行在 TLS 之上。TLS 提供加密、完整性保护和在证书验证正确时的服务器认证。证书链、主机名验证和服务端私钥证明共同降低中间人伪装风险；只说“HTTPS 用 RSA 加密”既过时也不完整。

### 7. MTU 和 MSS 的区别

MTU 是链路可承载的最大 IP 包大小，MSS 是 TCP 单段可承载的最大数据长度，通常由路径 MTU 推导。它们都不等于应用消息大小。额外追问可以说明：IPv4 可能分片，IPv6 路由器不分片；实践中应避免让业务依赖 IP 分片。

### 8. Socket 接收缓冲区和网卡接收队列有什么区别

网卡接收队列/描述符用于设备把已到达的数据交给驱动和内核；socket 接收缓冲区则是内核按连接或端点管理、等待应用读取的数据。用户态的 Java `ByteBuffer` 或 Netty `ByteBuf` 又是第三类缓冲。三者处于不同阶段，容量与背压含义也不同。

### 9. `select`、`poll`、`epoll` 与 Netty 是什么关系

它们是等待多个 I/O 对象就绪的机制或接口。应用将非阻塞 socket 的关注事件注册给内核，少量事件循环线程阻塞等待就绪集合，再实际进行 `accept`/`read`/`write`。Java NIO 以 `Selector` 表达这一模型，底层实现随平台不同；Netty 在其上组织 Channel、Pipeline 和 EventLoop。就绪不是完成通知，慢业务也不会因为用了 Netty 自动变快。

### 10. HTTP/1.1、HTTP/2、HTTP/3 有何关键差异

HTTP/1.1 常以文本形式在持久 TCP 连接上传输，管线化实践受限；HTTP/2 使用二进制 frame 和多 stream，在单 TCP 连接内并发多请求；HTTP/3 使用 QUIC，QUIC 基于 UDP 实现可靠多流，避免一个 TCP 丢包阻塞其他流。但 HTTP/3 仍要面对拥塞、服务器排队、无线丢包和应用性能问题。

## 十二、三条学习路线：学到能用，再学到能解释

### 1. 日常开发的最低闭环

先掌握以下内容，就能处理大多数接口调用与服务联调问题：

- DNS、IP、端口、Socket 和客户端/服务端的角色；
- TCP 与 UDP 的基本语义，尤其是 TCP 字节流和应用消息边界；
- HTTP 请求/响应、状态码、首部、超时与 HTTPS 证书错误；
- `curl -v`、DNS 查询、端口测试、连接状态查看的基本使用；
- 重试必须考虑幂等，连接池、请求体和线程池必须有上限。

### 2. 高并发后端与中间件的进阶闭环

在此基础上继续深入：

- TCP 接收窗口、拥塞控制、重传、`TIME_WAIT`、连接复用；
- 路由、NAT、MTU/MSS、反向代理、负载均衡和 TLS 终止；
- 网卡 DMA、内核 socket 缓冲、NAPI、I/O 多路复用与背压；
- Netty `ByteBuf`、编解码、帧长度限制、EventLoop 与业务线程隔离；
- 通过指标与抓包关联 DNS 耗时、建连耗时、TLS 耗时、TTFB、重传和队列积压。

### 3. 考研与复试的系统闭环

建议按照“层次 -> 机制 -> 时序 -> 口述”的顺序复习：

1. 能画出五层模型，说明 MAC、IP、端口的职责和封装过程。
2. 能说明 ARP、路由、子网、NAT、ICMP、MTU/MSS 的联系与边界。
3. 能完整解释 TCP 可靠性、握手挥手、窗口、拥塞控制以及 TCP/UDP 对比。
4. 能解释 DNS、HTTP、HTTPS/TLS、HTTP/1.1/2/3 与代理的基本差异。
5. 能把“输入 URL 到页面展示”“一次 Netty 读事件”“一次接口超时”组织为连续的时序回答。

练习时，不妨先不看提纲，用两分钟说清一次 HTTPS 请求的路径；每说到一个术语，就追问自己“它属于哪层、解决谁的问题、失败时会看到什么现象”。能够稳定回答这三个问题，才算真正掌握，而不只是把名词暂存在记忆里。

## 十三、总结与继续阅读

计算机网络的核心并不是背下更多缩写，而是保持明确的责任边界：

- 应用层定义消息与业务语义；HTTP 消息边界不是 TCP `read` 边界。
- TCP/UDP 在进程之间提供不同的传输语义；TCP 可靠有序，但只交付字节流。
- IP 和路由负责跨网络寻址，MAC 和 ARP/邻居发现负责当前一跳的交付。
- 网卡、DMA、驱动、内核协议栈和 socket 接收缓冲区共同完成“数据进入进程前”的路径；它们不是同一个缓冲区，也不是同一个概念。
- I/O 多路复用复用的是等待多个 socket 就绪的能力，不会消除业务阻塞或网络传输成本。
- 排障应沿 DNS -> TCP -> TLS -> HTTP -> 业务逐层验证；重试、超时、限流和背压是网络程序的设计内容。
