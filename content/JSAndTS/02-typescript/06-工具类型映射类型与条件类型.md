工具类型的目标不是让类型看起来更复杂，而是减少重复、保留关系、让类型随业务模型自动变化。

如果两个类型之间有明显关系，就不应该完全复制一份。复制出来的类型一开始很安静，后来字段改了，它就开始装作自己一直是对的。工程里最麻烦的错误，往往就来自这种安静。

## 一、为什么需要工具类型

假设有用户类型：

```ts
type User = {
  id: number
  username: string
  password: string
  nickname?: string
  avatarUrl?: string
}
```

页面展示时不能暴露密码：

```ts
type UserPublicInfo = {
  id: number
  username: string
  nickname?: string
  avatarUrl?: string
}
```

这可以运行，但以后 `User` 增加字段，`UserPublicInfo` 不会自动同步。

用 `Omit`：

```ts
type UserPublicInfo = Omit<User, 'password'>
```

类型之间的关系被保留了。

## 二、Partial 与 Required

`Partial<T>` 把所有字段变成可选。

```ts
type User = {
  id: number
  username: string
  avatarUrl?: string
}

type UserPatch = Partial<User>
```

等价于：

```ts
type UserPatch = {
  id?: number
  username?: string
  avatarUrl?: string
}
```

适合局部更新：

```ts
function updateUser(id: number, patch: Partial<Omit<User, 'id'>>) {
  return fetch(`/api/users/${id}`, {
    method: 'PATCH',
    body: JSON.stringify(patch)
  })
}
```

`Required<T>` 把所有字段变成必填：

```ts
type CompleteUser = Required<User>
```

注意它只处理一层字段，不会递归处理嵌套对象。

## 三、Pick 与 Omit

`Pick<T, K>` 从类型中挑选字段。

```ts
type LoginForm = Pick<User, 'username' | 'password'>
```

`Omit<T, K>` 从类型中排除字段。

```ts
type UserWithoutPassword = Omit<User, 'password'>
```

常见组合：

```ts
type CreateUserRequest = Pick<User, 'username' | 'password' | 'nickname'>

type UpdateUserRequest = Partial<Pick<User, 'username' | 'nickname' | 'avatarUrl'>>
```

这样能清楚表达提交参数和领域模型之间的关系。

## 四、Record

`Record<K, T>` 构造键值映射。

```ts
type PostStatus = 'draft' | 'published' | 'archived'

const statusText: Record<PostStatus, string> = {
  draft: '草稿',
  published: '已发布',
  archived: '已归档'
}
```

如果漏掉 `archived`，会报错。如果多写一个不存在的键，也会报错。

配置对象更适合：

```ts
type StatusConfig = {
  text: string
  color: 'gray' | 'green' | 'red'
}

const statusConfig: Record<PostStatus, StatusConfig> = {
  draft: {
    text: '草稿',
    color: 'gray'
  },
  published: {
    text: '已发布',
    color: 'green'
  },
  archived: {
    text: '已归档',
    color: 'red'
  }
}
```

## 五、Readonly

`Readonly<T>` 把对象属性变成只读。

```ts
type AppConfig = Readonly<{
  apiBaseUrl: string
  pageSize: number
}>

const config: AppConfig = {
  apiBaseUrl: '/api',
  pageSize: 20
}

config.pageSize = 50
```

最后一行会报错。

它适合配置、常量、不可变数据约束。不要把所有业务对象都变成只读，否则表单和状态更新会很别扭。

## 六、ReturnType 和 Parameters

`ReturnType<T>` 获取函数返回值类型。

```ts
function createUser() {
  return {
    id: 1,
    name: 'Yuki'
  }
}

type User = ReturnType<typeof createUser>
```

`Parameters<T>` 获取函数参数类型组成的元组。

```ts
function searchPosts(keyword: string, page: number) {
  return {
    keyword,
    page
  }
}

type SearchParams = Parameters<typeof searchPosts>
```

`SearchParams` 是：

```ts
type SearchParams = [keyword: string, page: number]
```

这些工具常用于从已有函数推导类型，避免重复声明。

## 七、Awaited

`Awaited<T>` 获取 Promise 完成后的值类型。

```ts
async function fetchProfile() {
  return {
    id: 1,
    name: 'Yuki'
  }
}

type Profile = Awaited<ReturnType<typeof fetchProfile>>
```

`Profile` 是：

```ts
type Profile = {
  id: number
  name: string
}
```

这在封装 API 时很常见。

## 八、映射类型

工具类型的底层基础之一是映射类型。

```ts
type MyPartial<T> = {
  [K in keyof T]?: T[K]
}
```

含义是：遍历 `T` 的所有键 `K`，把每个字段变成可选。

再写一个只读版本：

```ts
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K]
}
```

去掉只读和可选修饰：

```ts
type MutableRequired<T> = {
  -readonly [K in keyof T]-?: T[K]
}
```

`+` 表示增加修饰，`-` 表示移除修饰。

## 九、键名重映射

映射类型可以通过 `as` 改键名。

```ts
type Getter<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K]
}
```

使用：

```ts
type User = {
  name: string
  age: number
}

type UserGetter = Getter<User>
```

结果类似：

```ts
type UserGetter = {
  getName: () => string
  getAge: () => number
}
```

这种能力在封装库时很有用。业务代码里要适度，不要让类型变成猜谜。

## 十、条件类型

条件类型写法：

```ts
type IsString<T> = T extends string ? true : false
```

使用：

```ts
type A = IsString<string>
type B = IsString<number>
```

`A` 是 `true`，`B` 是 `false`。

常见用途是根据输入类型选择输出类型。

```ts
type ApiData<T> = T extends Promise<infer R> ? R : T
```

这里出现了 `infer`。

## 十一、infer

`infer` 用于在条件类型中推断某一部分类型。

```ts
type UnwrapPromise<T> = T extends Promise<infer R> ? R : T
```

使用：

```ts
type A = UnwrapPromise<Promise<string>>
type B = UnwrapPromise<number>
```

`A` 是 `string`，`B` 是 `number`。

提取数组元素：

```ts
type ElementOf<T> = T extends Array<infer Item> ? Item : never

type User = ElementOf<User[]>
```

`infer` 很强，但也容易写出过度抽象。只有当类型关系确实值得复用时再写。

## 十二、分布式条件类型

条件类型遇到联合类型时，会分发到每个成员。

```ts
type ToArray<T> = T extends unknown ? T[] : never

type Result = ToArray<string | number>
```

`Result` 是：

```ts
type Result = string[] | number[]
```

而不是：

```ts
type Result = (string | number)[]
```

如果不想分发，可以包一层元组：

```ts
type ToArrayNoDistribute<T> = [T] extends [unknown] ? T[] : never
```

这属于进阶知识，读懂即可，不必急着在业务里使用。

## 十三、常见误区

### 1. 滥用 Partial

```ts
type UserForm = Partial<User>
```

这会让所有字段都变成可选，但表单里可能有些字段是必填的。更好的方式是准确挑选：

```ts
type UserForm = Pick<User, 'username' | 'nickname'>
```

### 2. 工具类型叠太深

```ts
type X = Partial<Omit<Pick<User, 'id' | 'name' | 'avatarUrl'>, 'id'>>
```

这类类型读起来很累。可以拆中间类型：

```ts
type UserEditableFields = Pick<User, 'name' | 'avatarUrl'>
type UserUpdateForm = Partial<UserEditableFields>
```

### 3. 用类型运算替代业务命名

工具类型能推导结构，但不能替你表达业务含义。重要类型应该有业务名字。

## 十四、练习

基于下面类型：

```ts
type Post = {
  id: number
  title: string
  content: string
  authorId: number
  createdAt: string
  updatedAt: string
}
```

定义：

- `PostCard`：包含 `id`、`title`、`createdAt`。
- `CreatePostRequest`：包含 `title`、`content`、`authorId`。
- `UpdatePostRequest`：允许局部更新 `title` 和 `content`。
- `PostReadonly`：所有字段只读。

参考：

```ts
type PostCard = Pick<Post, 'id' | 'title' | 'createdAt'>

type CreatePostRequest = Pick<Post, 'title' | 'content' | 'authorId'>

type UpdatePostRequest = Partial<Pick<Post, 'title' | 'content'>>

type PostReadonly = Readonly<Post>
```

工具类型的价值在于表达关系。类型之间的关系越清楚，项目演进时越不容易出现“字段改了，但只改了一半”的问题。
