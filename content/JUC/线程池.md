线程池是一种复用线程、限制并发规模并统一管理任务执行的机制。它解决的不是“如何让任务并发执行”这么简单的问题，而是：**并发数量要可控，任务堆积要可控，异常和关闭也要可控**。

## 一、为什么需要线程池

直接 `new Thread()` 有几个问题：

- 线程创建和销毁都有成本，频繁创建会浪费资源。
- 线程数量没有上限，流量突增时可能把 CPU、内存或数据库连接打满。
- 任务失败、线程命名、关闭流程不容易统一管理。

线程池把这些问题集中起来处理：

- 复用已创建的工作线程。
- 通过核心线程数、最大线程数和队列容量控制并发。
- 通过拒绝策略处理过载。
- 通过 `shutdown`、`awaitTermination` 等方法控制生命周期。

## 二、推荐创建方式

生产环境更推荐直接使用 `ThreadPoolExecutor`，而不是 `Executors` 的快捷方法。

```java
ThreadFactory threadFactory = r -> {
    Thread thread = new Thread(r);
    thread.setName("biz-worker-" + thread.getId());
    return thread;
};

ExecutorService executor = new ThreadPoolExecutor(
        4,
        8,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(200),
        threadFactory,
        new ThreadPoolExecutor.CallerRunsPolicy()
);
```

`Executors.newFixedThreadPool`、`newCachedThreadPool` 等方法写起来方便，但会隐藏关键参数。例如固定线程池默认使用无界队列，任务堆积时可能导致内存风险。并发编程里，隐藏风险并不会让风险消失，只会让它换个时机出现。

## 三、核心参数

| 参数 | 作用 |
| --- | --- |
| `corePoolSize` | 核心线程数，线程池长期保留的基本工作线程数量 |
| `maximumPoolSize` | 最大线程数，队列满后还能继续扩容到的上限 |
| `keepAliveTime` | 非核心线程空闲后的存活时间 |
| `unit` | `keepAliveTime` 的时间单位 |
| `workQueue` | 等待执行任务的阻塞队列 |
| `threadFactory` | 创建线程的工厂，常用于设置线程名和异常处理器 |
| `handler` | 线程池和队列都满时的拒绝策略 |

线程池的参数必须一起看。只调整最大线程数，却使用无界队列，通常不会得到预期效果，因为任务会一直先进队列，线程池不一定扩容到最大线程数。

## 四、任务提交流程

调用 `execute` 提交任务时，线程池大致按下面顺序处理：

```text
提交任务
 -> 当前线程数 < corePoolSize：创建核心线程执行
 -> 否则尝试放入 workQueue
 -> 队列已满且当前线程数 < maximumPoolSize：创建非核心线程执行
 -> 仍然无法处理：执行拒绝策略
```

这个流程可以解释很多线程池现象。例如使用无界队列时，任务通常会一直排队，`maximumPoolSize` 很难发挥作用；使用 `SynchronousQueue` 时，任务不能排队，只能直接交给线程执行，因此更容易触发线程扩容。

## 五、常见队列

| 队列 | 特点 | 常见场景 |
| --- | --- | --- |
| `ArrayBlockingQueue` | 有界数组队列 | 推荐用于明确控制堆积量 |
| `LinkedBlockingQueue` | 可有界，也可无界 | 默认无界时要谨慎 |
| `SynchronousQueue` | 不存储任务，直接移交 | 适合短任务和弹性线程 |
| `PriorityBlockingQueue` | 按优先级执行 | 需要任务优先级的场景 |
| `DelayQueue` | 到期后才能取出 | 延迟任务、超时处理 |

业务线程池一般优先考虑有界队列。无界队列看似温和，其实只是把拒绝推迟到了内存耗尽之后。

## 六、拒绝策略

| 策略 | 行为 |
| --- | --- |
| `AbortPolicy` | 直接抛出 `RejectedExecutionException` |
| `CallerRunsPolicy` | 由提交任务的线程自己执行任务 |
| `DiscardPolicy` | 直接丢弃任务，不抛异常 |
| `DiscardOldestPolicy` | 丢弃队列中最旧的任务，再尝试提交新任务 |

普通业务中常用 `AbortPolicy` 或 `CallerRunsPolicy`。前者能快速暴露过载，后者能对提交方形成反压。静默丢弃类策略要慎用，除非业务明确允许丢任务。

## 七、Spring 中的线程池

Spring 项目中常用 `ThreadPoolTaskExecutor`，它底层仍然是 `ThreadPoolExecutor`：

```java
@Bean
public ThreadPoolTaskExecutor bizExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(8);
    executor.setQueueCapacity(200);
    executor.setKeepAliveSeconds(60);
    executor.setThreadNamePrefix("biz-worker-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.initialize();
    return executor;
}
```

如果用于 `@Async`，还要确认异步方法使用的是这个明确配置过的执行器，而不是默认执行器。

## 八、实践建议

- 线程池要按业务隔离，不要所有任务共用一个池。
- 队列尽量有界，拒绝策略要符合业务语义。
- 线程名要可识别，方便日志和排障。
- IO 密集型任务和 CPU 密集型任务不要混用同一个池。
- 提交任务后要关注异常，尤其是使用 `submit` 时别忘了处理 `Future`。
- 应用关闭时要优雅关闭线程池，避免任务丢失或 JVM 无法退出。

## 九、总结

线程池不是越大越好，也不是写一个 `Executors.newFixedThreadPool` 就算结束。可靠的线程池配置要同时考虑线程数、队列容量、拒绝策略、线程命名、异常处理和关闭流程。能把这些边界讲清楚，线程池才是真的被你控制，而不是反过来控制你。
