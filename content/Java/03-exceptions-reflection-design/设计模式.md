设计模式不是背 23 个名词。它本质上是一些反复出现的代码组织经验，用来解决对象创建、对象组合、行为扩展、流程复用、对象协作这些问题。

真正常用的模式并不多。日常 Java 开发里，最值得掌握的是：

- 创建对象：工厂、Builder、单例。
- 组合能力：适配器、装饰器、代理。
- 组织行为：策略、模板方法、观察者、责任链。

如果一个模式不能降低复杂度，只是让类变多，那它不是设计，是表演。代码已经够辛苦了，别再给它安排节目。

## 一、工厂模式

工厂模式用来封装对象创建逻辑，让调用方不直接依赖具体实现类。

适合场景：

- 创建对象前需要判断类型。
- 创建过程包含校验、默认值、依赖装配。
- 调用方只关心接口，不想知道具体类。

不适合场景：

- 只是把 `new User()` 包一层 `UserFactory.create()`，没有任何额外价值。
- 类型很少且不会扩展。

### 简单工厂

简单工厂不是 GoF 经典 23 种模式之一，但开发中很常见。

```java
interface PayService {
    void pay(long orderId);
}

class AlipayService implements PayService {
    @Override
    public void pay(long orderId) {
        System.out.println("alipay: " + orderId);
    }
}

class WechatPayService implements PayService {
    @Override
    public void pay(long orderId) {
        System.out.println("wechat pay: " + orderId);
    }
}

class PayServiceFactory {
    static PayService create(String channel) {
        return switch (channel) {
            case "ALIPAY" -> new AlipayService();
            case "WECHAT" -> new WechatPayService();
            default -> throw new IllegalArgumentException("unsupported channel: " + channel);
        };
    }
}
```

调用方只依赖 `PayService`：

```java
PayService payService = PayServiceFactory.create("ALIPAY");
payService.pay(1001L);
```

缺点是每新增一种支付方式，都要修改工厂里的 `switch`。如果扩展频率很高，可以改成注册表。

### 注册表工厂

```java
class PayServiceRegistry {
    private final Map<String, PayService> services = new HashMap<>();

    void register(String channel, PayService service) {
        services.put(channel, service);
    }

    PayService get(String channel) {
        PayService service = services.get(channel);
        if (service == null) {
            throw new IllegalArgumentException("unsupported channel: " + channel);
        }
        return service;
    }
}
```

Spring 项目里经常会把所有实现类注入成 `Map<String, PayService>`，这就是注册表工厂的实际形态。

```java
@Service
class PayRouter {
    private final Map<String, PayService> services;

    PayRouter(Map<String, PayService> services) {
        this.services = services;
    }

    void pay(String channel, long orderId) {
        PayService service = services.get(channel);
        if (service == null) {
            throw new IllegalArgumentException("unsupported channel: " + channel);
        }
        service.pay(orderId);
    }
}
```

## 二、Builder 模式

Builder 用来构造参数较多、组合规则较复杂的对象。

适合场景：

- 构造参数很多。
- 有些参数可选。
- 对象创建时需要校验多个字段之间的关系。
- 希望创建出来后对象不可变。

不适合场景：

- 只有两三个字段。
- 对象只是普通 DTO，没有构造约束。

```java
class HttpRequestConfig {
    private final String baseUrl;
    private final int connectTimeoutMillis;
    private final int readTimeoutMillis;
    private final Map<String, String> headers;

    private HttpRequestConfig(Builder builder) {
        this.baseUrl = builder.baseUrl;
        this.connectTimeoutMillis = builder.connectTimeoutMillis;
        this.readTimeoutMillis = builder.readTimeoutMillis;
        this.headers = Map.copyOf(builder.headers);
    }

    static Builder builder(String baseUrl) {
        return new Builder(baseUrl);
    }

    static class Builder {
        private final String baseUrl;
        private int connectTimeoutMillis = 3000;
        private int readTimeoutMillis = 5000;
        private final Map<String, String> headers = new HashMap<>();

        Builder(String baseUrl) {
            if (baseUrl == null || baseUrl.isBlank()) {
                throw new IllegalArgumentException("baseUrl is blank");
            }
            this.baseUrl = baseUrl;
        }

        Builder connectTimeoutMillis(int value) {
            this.connectTimeoutMillis = value;
            return this;
        }

        Builder readTimeoutMillis(int value) {
            this.readTimeoutMillis = value;
            return this;
        }

        Builder header(String name, String value) {
            this.headers.put(name, value);
            return this;
        }

        HttpRequestConfig build() {
            if (connectTimeoutMillis <= 0 || readTimeoutMillis <= 0) {
                throw new IllegalArgumentException("timeout must be positive");
            }
            return new HttpRequestConfig(this);
        }
    }
}
```

使用：

```java
HttpRequestConfig config = HttpRequestConfig.builder("https://api.example.com")
    .connectTimeoutMillis(2000)
    .readTimeoutMillis(3000)
    .header("Accept", "application/json")
    .build();
```

Builder 的重点不是链式调用看起来好看，而是把复杂构造过程收束到一个地方。

## 三、单例模式

单例保证一个类在 JVM 内通常只有一个实例。

适合场景：

- 对象无状态，或者状态只读。
- 创建成本高，并且可以安全复用。
- 需要全局唯一协调者，例如配置中心客户端、线程池管理器。

不适合场景：

- 保存用户上下文、请求状态、临时数据。
- 为了省事把所有工具都塞进全局对象。

Java 中最简单可靠的单例写法是枚举：

```java
enum IdGenerator {
    INSTANCE;

    private final AtomicLong value = new AtomicLong();

    long nextId() {
        return value.incrementAndGet();
    }
}
```

使用：

```java
long id = IdGenerator.INSTANCE.nextId();
```

枚举单例天然处理序列化和反射的一些问题。相比双重检查锁那套写法，它少一些“我很聪明”的气味。通常这是一件好事。

Spring 项目里的 Bean 默认也是单例，但那是容器级单例。不要把 Spring 单例误认为永远线程安全。一个单例 Bean 如果持有可变字段，照样可能并发出事。

## 四、适配器模式

适配器用于把一个已有接口转换成调用方需要的接口。

适合场景：

- 老接口不能改，新代码又需要统一抽象。
- 第三方 SDK 的接口和业务接口不一致。
- 多个外部系统能力类似，但方法名、参数结构不同。

```java
interface SmsSender {
    void send(String phone, String content);
}

class ThirdPartySmsClient {
    void push(String mobile, String text) {
        System.out.println("send sms to " + mobile + ": " + text);
    }
}

class ThirdPartySmsAdapter implements SmsSender {
    private final ThirdPartySmsClient client;

    ThirdPartySmsAdapter(ThirdPartySmsClient client) {
        this.client = client;
    }

    @Override
    public void send(String phone, String content) {
        client.push(phone, content);
    }
}
```

调用方只关心 `SmsSender`：

```java
SmsSender sender = new ThirdPartySmsAdapter(new ThirdPartySmsClient());
sender.send("13800000000", "hello");
```

适配器不要塞太多业务规则。它主要负责接口转换，不应该变成另一个业务服务。

## 五、装饰器模式

装饰器用于在不修改原对象的情况下，给对象动态叠加能力。

适合场景：

- 多个增强能力可以自由组合。
- 不想用继承制造大量子类。
- 增强逻辑和核心逻辑可以独立变化。

Java IO 就大量使用了装饰器：

```java
InputStream input = new BufferedInputStream(
    new FileInputStream("data.txt")
);
```

业务示例：

```java
interface DataLoader {
    String load(String key);
}

class DatabaseDataLoader implements DataLoader {
    @Override
    public String load(String key) {
        return "value from db: " + key;
    }
}

class CacheDataLoader implements DataLoader {
    private final DataLoader delegate;
    private final Map<String, String> cache = new HashMap<>();

    CacheDataLoader(DataLoader delegate) {
        this.delegate = delegate;
    }

    @Override
    public String load(String key) {
        return cache.computeIfAbsent(key, delegate::load);
    }
}

class LogDataLoader implements DataLoader {
    private final DataLoader delegate;

    LogDataLoader(DataLoader delegate) {
        this.delegate = delegate;
    }

    @Override
    public String load(String key) {
        System.out.println("load key: " + key);
        return delegate.load(key);
    }
}
```

组合：

```java
DataLoader loader = new LogDataLoader(
    new CacheDataLoader(
        new DatabaseDataLoader()
    )
);

String value = loader.load("user:1");
```

装饰器和代理都持有目标对象。区别是：装饰器强调**叠加能力**，代理强调**控制访问**。

## 六、代理模式

代理模式让调用方不直接访问真实对象，而是通过代理对象访问。

适合场景：

- 权限校验。
- 事务控制。
- 日志记录。
- 远程调用。
- 延迟加载。

静态代理：

```java
interface OrderService {
    void createOrder(long userId);
}

class OrderServiceImpl implements OrderService {
    @Override
    public void createOrder(long userId) {
        System.out.println("create order for " + userId);
    }
}

class TransactionOrderServiceProxy implements OrderService {
    private final OrderService target;

    TransactionOrderServiceProxy(OrderService target) {
        this.target = target;
    }

    @Override
    public void createOrder(long userId) {
        System.out.println("begin transaction");
        try {
            target.createOrder(userId);
            System.out.println("commit transaction");
        } catch (RuntimeException e) {
            System.out.println("rollback transaction");
            throw e;
        }
    }
}
```

Spring AOP、事务注解、RPC 客户端代理，本质上都能看到代理模式的影子。

代理不要滥用。过深的代理链会让调试变得像剥洋葱，而且每一层都可能让人流泪。

## 七、策略模式

策略模式把一组可替换的算法或业务规则封装起来，让调用方按场景选择。

适合场景：

- 有多个算法分支。
- 分支会继续扩展。
- 希望消除一长串 `if else` / `switch`。

```java
interface DiscountStrategy {
    BigDecimal discount(BigDecimal amount);
}

class NormalDiscountStrategy implements DiscountStrategy {
    @Override
    public BigDecimal discount(BigDecimal amount) {
        return amount;
    }
}

class VipDiscountStrategy implements DiscountStrategy {
    @Override
    public BigDecimal discount(BigDecimal amount) {
        return amount.multiply(new BigDecimal("0.8"));
    }
}

class CouponDiscountStrategy implements DiscountStrategy {
    @Override
    public BigDecimal discount(BigDecimal amount) {
        return amount.subtract(new BigDecimal("10")).max(BigDecimal.ZERO);
    }
}
```

用注册表选择策略：

```java
class DiscountService {
    private final Map<String, DiscountStrategy> strategies;

    DiscountService(Map<String, DiscountStrategy> strategies) {
        this.strategies = strategies;
    }

    BigDecimal calculate(String type, BigDecimal amount) {
        DiscountStrategy strategy = strategies.get(type);
        if (strategy == null) {
            throw new IllegalArgumentException("unsupported discount type: " + type);
        }
        return strategy.discount(amount);
    }
}
```

策略模式最常见的落地方式就是“接口 + 多实现 + Map 路由”。在 Spring 里尤其自然。

## 八、模板方法模式

模板方法把固定流程放在父类，把可变步骤交给子类。

适合场景：

- 流程稳定。
- 某些步骤因业务而异。
- 希望统一控制执行顺序、异常处理、日志、事务等。

```java
abstract class AbstractImportTask {
    public final void execute(Path file) {
        validate(file);
        List<String> rows = read(file);
        List<?> records = parse(rows);
        save(records);
        afterComplete(records.size());
    }

    protected void validate(Path file) {
        if (!Files.exists(file)) {
            throw new IllegalArgumentException("file not found: " + file);
        }
    }

    protected List<String> read(Path file) {
        try {
            return Files.readAllLines(file, StandardCharsets.UTF_8);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }

    protected abstract List<?> parse(List<String> rows);

    protected abstract void save(List<?> records);

    protected void afterComplete(int count) {
        System.out.println("import complete, count=" + count);
    }
}
```

子类只实现变化点：

```java
class UserImportTask extends AbstractImportTask {
    @Override
    protected List<User> parse(List<String> rows) {
        return rows.stream()
            .map(row -> row.split(","))
            .map(parts -> new User(parts[0], parts[1]))
            .toList();
    }

    @Override
    protected void save(List<?> records) {
        System.out.println("save users: " + records.size());
    }
}
```

模板方法的缺点是依赖继承。如果变化点越来越多，父类会变得很别扭。这时可以考虑策略模式或组合。

## 九、观察者模式

观察者模式用于一对多通知：一个对象发生变化，多个监听者得到通知。

适合场景：

- 事件监听。
- 状态变更通知。
- 发布订阅。
- 领域事件。

```java
record OrderCreatedEvent(long orderId, long userId) {
}

interface OrderEventListener {
    void onCreated(OrderCreatedEvent event);
}

class StockListener implements OrderEventListener {
    @Override
    public void onCreated(OrderCreatedEvent event) {
        System.out.println("lock stock for order: " + event.orderId());
    }
}

class CouponListener implements OrderEventListener {
    @Override
    public void onCreated(OrderCreatedEvent event) {
        System.out.println("mark coupon used for user: " + event.userId());
    }
}

class OrderEventPublisher {
    private final List<OrderEventListener> listeners = new ArrayList<>();

    void addListener(OrderEventListener listener) {
        listeners.add(listener);
    }

    void publish(OrderCreatedEvent event) {
        for (OrderEventListener listener : listeners) {
            listener.onCreated(event);
        }
    }
}
```

使用：

```java
OrderEventPublisher publisher = new OrderEventPublisher();
publisher.addListener(new StockListener());
publisher.addListener(new CouponListener());

publisher.publish(new OrderCreatedEvent(1001L, 2001L));
```

观察者模式能解耦主流程和附加动作，但也会让调用链变得不那么直观。事件太多、监听器太散时，排查问题会变困难。

## 十、责任链模式

责任链把多个处理器串起来，请求沿着链路依次处理。

适合场景：

- 多个校验步骤。
- 多个过滤器。
- 多个审批节点。
- Web 拦截器、Servlet Filter。

```java
record LoginRequest(String username, String password, String captcha) {
}

interface LoginHandler {
    void handle(LoginRequest request);
}

class CaptchaHandler implements LoginHandler {
    @Override
    public void handle(LoginRequest request) {
        if (request.captcha() == null || request.captcha().isBlank()) {
            throw new IllegalArgumentException("captcha is blank");
        }
    }
}

class PasswordHandler implements LoginHandler {
    @Override
    public void handle(LoginRequest request) {
        if (request.password() == null || request.password().length() < 8) {
            throw new IllegalArgumentException("password is invalid");
        }
    }
}

class LoginChain {
    private final List<LoginHandler> handlers;

    LoginChain(List<LoginHandler> handlers) {
        this.handlers = List.copyOf(handlers);
    }

    void handle(LoginRequest request) {
        for (LoginHandler handler : handlers) {
            handler.handle(request);
        }
    }
}
```

使用：

```java
LoginChain chain = new LoginChain(List.of(
    new CaptchaHandler(),
    new PasswordHandler()
));

chain.handle(new LoginRequest("tom", "12345678", "9527"));
```

责任链要注意顺序。认证、鉴权、限流、参数校验这些处理器，如果顺序错了，行为可能完全不同。

## 十一、怎么选择

| 问题 | 常用模式 |
| --- | --- |
| 创建对象有分支 | 工厂 |
| 构造参数多且有校验 | Builder |
| 全局唯一且可复用 | 单例 |
| 第三方接口不匹配 | 适配器 |
| 动态叠加能力 | 装饰器 |
| 控制访问或织入横切逻辑 | 代理 |
| 多个算法可替换 | 策略 |
| 流程固定、步骤可变 | 模板方法 |
| 一对多事件通知 | 观察者 |
| 多步骤过滤或校验 | 责任链 |

## 十二、常见误区

### 1. 为了模式而模式

设计模式应该降低复杂度。如果引入模式后只是多了接口、多了类、多了跳转，却没有减少变化带来的影响，那就不要用。

### 2. 把简单工厂当万能药

简单工厂适合创建逻辑集中管理，但类型扩展频繁时，工厂本身会变成大 `switch`。这时注册表、依赖注入、多态会更合适。

### 3. 滥用单例

单例不是全局变量收容所。尤其不要把请求状态、用户信息、临时计算结果放进单例字段。

### 4. 分不清策略和责任链

策略是**选择一个处理方案**。

责任链是**多个处理器依次处理**。

如果一次请求只会走一种算法，多半是策略；如果一次请求要经过多道关卡，多半是责任链。

### 5. 分不清装饰器和代理

装饰器强调增强能力可以叠加，例如缓冲、日志、缓存。

代理强调控制访问，例如权限、事务、远程调用、懒加载。

它们结构相似，但意图不同。设计模式最重要的是意图，不是类图长得像不像。

## 十三、总结

常用设计模式可以用几句话记住：

- 工厂：把创建逻辑藏起来。
- Builder：把复杂构造过程收起来。
- 单例：控制实例数量，但别滥用全局状态。
- 适配器：把不兼容接口接起来。
- 装饰器：给对象叠加能力。
- 代理：控制对对象的访问。
- 策略：把算法分支拆出去。
- 模板方法：固定流程，开放步骤。
- 观察者：状态变化后通知别人。
- 责任链：让请求依次经过多个处理器。

真正写代码时，不必先问“我要用哪个设计模式”。应该先问：这里的变化点是什么？哪个地方会扩展？哪个地方应该稳定？

回答清楚这些问题，模式自然会出现。回答不清楚时，硬套模式只会让代码显得很努力，却不一定更好。
