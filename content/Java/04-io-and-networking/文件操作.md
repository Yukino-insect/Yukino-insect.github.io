文件拷贝看起来只是“从 A 复制到 B”，但底层可能经过用户态缓冲区、内核缓冲区、页缓存、零拷贝，甚至在某些文件系统上只改元数据。

先看最传统的 Java 写法：

```java
try (InputStream in = new FileInputStream(src);
     OutputStream out = new FileOutputStream(dest)) {

    byte[] buffer = new byte[8192];
    int len;
    while ((len = in.read(buffer)) != -1) {
        out.write(buffer, 0, len);
    }
}
```

这段代码清楚、可控，但数据路径大致是：

```text
磁盘 -> 内核缓冲区 -> JVM 用户态缓冲区 -> 内核缓冲区 -> 目标磁盘
```

中间涉及多次数据拷贝，以及用户态和内核态之间的切换。

## 一、Files.copy

普通文件复制，优先考虑 `Files.copy`：

```java
Path source = Path.of("source.txt");
Path target = Path.of("target.txt");

Files.copy(source, target, StandardCopyOption.REPLACE_EXISTING);
```

`Files.copy` 的好处是语义清晰，并且 JDK 可以根据平台和文件系统选择合适的实现。它可能使用普通流，也可能使用更底层的系统能力。你不需要一上来就手写循环。

如果要复制目录，`Files.copy` 只会创建目标目录本身，不会递归复制目录内容。递归复制需要配合 `Files.walkFileTree`。

## 二、FileChannel.transferTo

NIO 的 `FileChannel#transferTo` 可以把数据从一个通道传输到另一个通道：

```java
try (FileChannel source = FileChannel.open(src, StandardOpenOption.READ);
     FileChannel target = FileChannel.open(dest,
             StandardOpenOption.CREATE,
             StandardOpenOption.WRITE,
             StandardOpenOption.TRUNCATE_EXISTING)) {

    long position = 0;
    long size = source.size();
    while (position < size) {
        position += source.transferTo(position, size - position, target);
    }
}
```

注意这里用了循环。某些平台或文件系统上，单次 `transferTo` 不一定传完整个文件，不能默认一次调用就全部完成。

`transferTo` 的优势在于，它可以利用操作系统提供的高效传输能力，减少用户态和内核态之间的数据搬运。

## 三、页缓存

现代操作系统通常会使用 Page Cache 优化文件 I/O。

读文件时，磁盘数据会先进入页缓存。后续再读同一块数据，可能直接命中内存，而不需要重新访问磁盘。

写文件时，数据也可能先写入页缓存，变成脏页，再由操作系统在合适时机刷回磁盘。

这就是为什么有些文件复制看起来非常快：它不一定每一步都立刻触碰真实磁盘。

## 四、零拷贝

传统的文件到网络发送路径通常是：

```text
磁盘 -> 内核缓冲区 -> 用户态 buffer -> socket 内核缓冲区 -> 网卡
```

零拷贝的目标是减少用户态参与的数据搬运。例如 `sendfile` 可以让内核直接把文件页缓存中的数据送到 socket：

```text
磁盘 -> 内核页缓存 -> socket -> 网卡
```

“零拷贝”并不是说物理世界里一次拷贝都没有，而是尽量避免数据在用户态和内核态之间来回搬运。这个名字有点自信，但方向是对的。

## 五、Copy-on-write 和 Reflink

在支持的文件系统上，复制文件甚至可能只是一次元数据操作。

例如某些场景下的 btrfs、XFS reflink、APFS clone、ReFS，可以让源文件和目标文件先共享同一批数据块。只有当其中一方被修改时，文件系统才复制被修改的数据块。

这类能力通常称为 copy-on-write 或 reflink。它非常快，但是否可用取决于操作系统、文件系统和 JDK 调用路径，不能在所有环境里默认依赖。

## 六、什么时候手写循环

手写 `InputStream` / `OutputStream` 循环仍然有价值，尤其是复制过程中需要额外处理数据时：

1. 边读边压缩。
2. 边读边加密。
3. 边读边计算摘要。
4. 限速或统计进度。
5. 从网络流复制到文件。

这时要注意缓冲区大小，不要频繁 `flush`，也不要每读一点就做非常重的同步操作。

```java
byte[] buffer = new byte[64 * 1024];
```

实际大小没有唯一答案，要结合文件大小、磁盘、网络和业务逻辑测试。8KB 并不是错，只是高吞吐场景下可能偏保守。

## 七、总结

普通文件复制：

```java
Files.copy(source, target, StandardCopyOption.REPLACE_EXISTING);
```

需要通道传输或大文件优化：

```java
FileChannel.transferTo(...)
```

需要边复制边处理数据：

```java
InputStream -> buffer -> OutputStream
```

文件 I/O 慢，不只是因为“磁盘慢”，还因为它牵涉系统调用、缓冲区、上下文切换、页缓存策略和刷盘时机。理解这些概念后，选择 API 会轻松很多，至少不会把所有性能问题都甩给那段无辜的 `while` 循环。
