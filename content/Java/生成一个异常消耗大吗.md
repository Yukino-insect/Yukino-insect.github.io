异常不是免费的。

在 Java 中，创建、抛出、捕获异常都存在成本，其中最主要的成本通常来自**填充调用栈信息**。所以异常适合表达异常流程，不适合替代普通业务分支。

先说结论：

> 偶发异常不用害怕；高频路径不要把异常当普通控制流。

## 一、异常成本主要在哪里

创建异常对象时，JVM 通常会记录当前调用栈，生成堆栈跟踪信息。

```java
Exception exception = new RuntimeException("error");
```

这一步可能涉及：

- 创建异常对象。
- 保存 message 和 cause。
- 采集当前调用栈。
- 创建 `StackTraceElement[]`。
- 后续打印日志时格式化堆栈。

其中最贵的往往是采集和保存 stack trace。

## 二、fillInStackTrace

`Throwable` 中有一个关键方法：

```java
public synchronized Throwable fillInStackTrace()
```

它负责填充当前异常对象的调用栈信息。

当你写：

```java
throw new IllegalArgumentException("bad request");
```

大致会发生：

```text
创建异常对象
 -> 填充 stack trace
 -> 抛出异常
 -> 沿调用栈查找 catch
 -> 执行匹配的 catch / finally
```

所以异常比普通返回值重得多。

## 三、抛出异常的运行时成本

抛出异常不是普通跳转。

它需要：

- 沿调用栈向上查找匹配的 `catch`。
- 进行异常类型匹配。
- 展开栈帧。
- 执行途中遇到的 `finally`。
- 处理 try-with-resources 中的 suppressed exceptions。

例如：

```java
try {
    service.process();
} catch (BizException e) {
    log.warn("process failed", e);
}
```

异常路径会跳出正常执行流。JIT 对热路径的优化通常更偏向“正常流程”，频繁异常会让代码更难优化，也会制造大量临时对象。

## 四、打印异常也有成本

创建异常和打印异常是两回事。

```java
log.error("failed", e);
```

打印异常会把 stack trace 格式化成文本。调用栈越深，日志越大。

如果在高频循环里反复打印完整异常：

```java
for (int i = 0; i < 10000; i++) {
    try {
        parse(input);
    } catch (Exception e) {
        log.error("parse failed", e);
    }
}
```

可能带来：

- CPU 消耗。
- 大量日志 IO。
- 磁盘压力。
- 日志系统阻塞。
- 排查时被重复堆栈淹没。

日志不是越多越安全。把同一个错误打印一万遍，通常只是让真正的线索变得更难找。

## 五、异常不适合做普通分支

不推荐：

```java
public int parseOrDefault(String value) {
    try {
        return Integer.parseInt(value);
    } catch (NumberFormatException e) {
        return 0;
    }
}
```

如果非法输入非常少，这样可以接受。

但如果这是高频路径，而且大量输入都不是数字，就不合适。因为你会不断创建和抛出异常。

更稳的是提前判断：

```java
public int parseOrDefault(String value) {
    if (value == null || !value.matches("-?\\d+")) {
        return 0;
    }

    return Integer.parseInt(value);
}
```

当然，`matches` 本身也有正则成本。真实高性能场景可以写更轻的字符判断。重点是：预期内的业务分支不应该全靠异常承担。

## 六、什么时候应该抛异常

适合抛异常：

- 参数违反方法契约。
- 外部资源不可用。
- 数据状态不可能继续处理。
- 安全校验失败。
- 框架需要中断当前流程。
- 事务需要回滚。

例如：

```java
public User getUser(Long id) {
    if (id == null) {
        throw new IllegalArgumentException("id must not be null");
    }

    return userRepository.findById(id)
        .orElseThrow(() -> new UserNotFoundException(id));
}
```

这里异常表达的是“流程不能正常继续”。

## 七、业务异常要不要填充堆栈

有些高频业务异常不一定需要完整堆栈。例如参数校验失败、登录态过期、权限不足，在网关或业务层可能非常常见。

可以自定义异常，关闭栈填充：

```java
public class FastBizException extends RuntimeException {
    public FastBizException(String message) {
        super(message, null, false, false);
    }
}
```

`RuntimeException` 有一个构造方法：

```java
protected RuntimeException(
    String message,
    Throwable cause,
    boolean enableSuppression,
    boolean writableStackTrace
)
```

最后一个参数 `writableStackTrace` 为 `false` 时，不会填充可写 stack trace。

但要谨慎使用。没有堆栈后，排查问题会困难。

建议：

- 系统异常保留堆栈。
- 未知异常保留堆栈。
- 高频、可预期、定位不依赖堆栈的业务异常，才考虑关闭堆栈。

不要为了“性能优化”把所有异常堆栈都关掉。那不是优化，是把监控灯泡拧下来宣称故障减少了。

## 八、异常和返回值怎么选

| 场景 | 建议 |
| ---- | ---- |
| 参数非法，方法不能继续 | 抛异常 |
| 查询不到数据是正常情况 | `Optional` 或空结果 |
| 远程调用失败 | 抛异常或返回明确错误结果 |
| 批量处理单条失败 | 收集错误，不一定中断整体 |
| 高频校验失败 | 返回错误码或错误对象可能更合适 |

例如：

```java
Optional<User> findUser(Long id);
```

比：

```java
User findUser(Long id) throws UserNotFoundException;
```

更适合“查不到是正常业务结果”的场景。

但如果方法语义是“必须拿到用户，否则系统不能继续”，异常也合理。

## 九、总结

异常成本主要来自：

- 创建异常对象。
- 填充 stack trace。
- 栈展开和 catch 匹配。
- 打印日志。
- 频繁异常对 JIT 和 GC 的影响。

使用建议：

- 异常用于异常流程，不要替代普通分支。
- 高频路径避免大量抛异常。
- 打印异常要控制频率和上下文。
- 系统异常保留堆栈。
- 高频业务异常是否关闭堆栈，需要结合排查成本谨慎判断。

一句话：

> 异常不是不能用，而是不要把它当 if/else。它适合让错误尽快暴露，不适合在热路径里反复上下楼。
