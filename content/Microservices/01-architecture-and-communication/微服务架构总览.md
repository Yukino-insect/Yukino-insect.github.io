微服务不是“把一个项目拆成很多服务”这么简单。拆分之后，原来在进程内自然成立的调用、事务、日志、发布和故障隔离，都会变成需要显式设计的工程问题。

如果说单体应用的复杂度主要在代码内部，那么微服务的复杂度会扩散到网络、部署、数据一致性、服务治理和可观测性里。拆得越细，这些问题越明显。

## 什么时候适合微服务

适合考虑微服务的信号：

- 团队规模变大，不同业务域需要独立迭代。
- 系统模块边界清楚，生命周期不同。
- 某些模块需要独立扩缩容或独立部署。
- 故障需要隔离，不能一个模块拖垮整个系统。
- 技术栈或数据模型确实存在差异。

不适合过早微服务化的信号：

- 业务边界还不稳定。
- 团队规模很小，部署和运维能力不足。
- 数据强一致要求很多，却没有对应事务方案。
- 只是觉得“微服务比较高级”。

最后这一条最好早点治。技术选型不是给简历镀金的饰品。

## 核心问题

### 服务边界

服务边界应该围绕业务能力划分，而不是围绕数据库表或 Controller 包名划分。

好的服务边界通常具有这些特征：

- 内部数据高内聚。
- 对外接口稳定。
- 可以独立部署。
- 失败影响范围清楚。
- 团队能对它负责到底。

如果两个服务频繁互相查询、互相更新、互相等待，可能说明边界拆错了。

### 服务调用

服务之间可以同步调用，也可以异步通信。

同步调用适合查询和需要立即返回结果的场景，例如 OpenFeign 调用用户服务查询用户信息。它的问题是调用链会变长，任何一个下游超时都会影响上游。

异步通信适合事件通知、削峰和最终一致性，例如订单创建后发布 `OrderCreated` 事件。它的问题是业务结果不会立刻完成，需要处理重试、幂等、补偿和消息顺序。

### 数据一致性

微服务通常强调“每个服务拥有自己的数据”。这样边界更清晰，但跨服务事务会变复杂。

常见选择：

- 本地事务：单服务单数据库内优先使用。
- Outbox：解决“数据库更新 + 发消息”的双写问题。
- Saga：适合长流程和补偿事务。
- TCC：适合需要业务预留、确认、取消的强语义场景。
- Seata AT：适合关系型数据库上的短事务、常规 CRUD 场景。

不要默认把所有一致性问题都交给分布式事务框架。很多业务其实只需要可重试、可补偿、可对账的最终一致性。

### 服务治理

服务拆开后，需要一套治理能力支撑运行：

- 注册发现：服务实例动态上下线，调用方通过服务名访问。
- 负载均衡：在多个实例之间选择目标。
- 配置中心：动态调整开关、阈值、灰度比例。
- 网关：统一鉴权、路由、限流、灰度和协议入口。
- 熔断降级：隔离故障依赖，保护核心链路。
- 灰度发布：让新版本逐步接流量，支持快速回滚。

这些能力不是装饰。没有它们，微服务只是把一次本地调用变成一次更脆弱的远程调用。

### 可观测性

微服务排障必须同时看三类数据：

- Metrics：看趋势，例如 QPS、错误率、P95、CPU、连接池。
- Logs：看细节，例如异常堆栈、业务参数、错误码。
- Traces：看一次请求经过哪些服务、每段耗时多少。

三者要通过 `traceId` 串起来。否则一次请求跨过十几个服务后，只靠日志关键词定位问题，效率会相当感人。

## 一条典型链路

以下单为例：

```text
客户端
  -> API Gateway
  -> order-service
  -> inventory-service
  -> account-service
  -> MQ
  -> search-service / notification-service
```

这条链路里会出现很多工程点：

- 网关鉴权，并注入用户、租户、traceId。
- `order-service` 使用本地事务创建订单。
- 库存和账户可能同步调用，也可能异步 Saga。
- 订单事件通过 Outbox 可靠发布。
- 下游消费者按 `event_id` 幂等处理。
- Feign 调用设置超时、熔断和降级。
- 日志、指标、Trace 统一进入观测系统。
- 新版本上线时通过 Header 或 metadata 做灰度。

这才是微服务真实的样子：不是一个注解，也不是一个注册中心，而是一组工程约束互相配合。

## 总结

微服务的收益来自独立演进、弹性伸缩和故障隔离；成本则来自网络调用、数据一致性、部署复杂度和观测难度。

真正成熟的微服务架构，不是服务数量多，而是边界清楚、失败可控、数据可恢复、问题可定位。能做到这些，再谈拆分才有意义。
