分布式系统中，日志不能只留在单台机器本地。服务实例会扩缩容，容器会重建，请求也会跨多个服务流转。故障排查时，工程师需要按时间、服务、实例、traceId、错误码等条件统一检索。

因此日志系统的目标不是“把日志集中起来”这么简单，而是让日志可采集、可解析、可查询、可留存、可告警。

## 常见架构

### ELK

ELK 指 Elasticsearch、Logstash、Kibana：

- Elasticsearch：负责索引、存储和检索。
- Logstash：负责采集、解析、过滤和转发。
- Kibana：负责查询和可视化。

Logstash 功能强，插件多，适合复杂解析和加工，但资源消耗较高。

### EFK

EFK 指 Elasticsearch、Fluentd 或 Fluent Bit、Kibana：

- Fluent Bit 更轻量，适合容器和 Kubernetes 节点侧采集。
- Fluentd 插件生态更完整，适合需要较多加工逻辑的场景。

容器环境里常见做法是应用输出到标准输出，由节点上的 Fluent Bit 统一采集。

### Kafka 缓冲

中大型系统通常会在采集端和存储端之间增加 Kafka：

```text
应用日志
  -> stdout / log file
  -> Fluent Bit / Filebeat
  -> Kafka
  -> Logstash / Flink / Consumer
  -> Elasticsearch / ClickHouse / 对象存储
  -> Kibana / Grafana
```

Kafka 的作用是削峰、缓冲和解耦。Elasticsearch 短暂不可用时，日志不会直接在采集端丢失；后续也可以新增消费者做审计、告警或离线分析。

## 存储选型

Elasticsearch 适合全文检索和多条件查询，是日志检索的常见选择。缺点是成本较高，写入量大时需要认真设计索引、分片、生命周期和冷热分层。

ClickHouse 适合高吞吐写入和聚合分析，常用于大规模日志、指标和行为分析。它的全文检索体验不如 Elasticsearch，但成本和聚合性能很有吸引力。

对象存储适合长期归档。热日志放 Elasticsearch 或 ClickHouse，冷日志压缩后写入对象存储，是比较常见的成本控制方案。

## 日志字段设计

日志要好查，关键在结构化字段。至少应包含：

| 字段 | 说明 |
| --- | --- |
| `timestamp` | 日志时间 |
| `level` | `INFO`、`WARN`、`ERROR` |
| `service` | 服务名 |
| `instance` | 实例 IP、Pod 名或容器 ID |
| `env` | `dev`、`test`、`prod` |
| `traceId` | 链路追踪 ID |
| `spanId` | 当前调用 span |
| `userId` | 用户 ID，注意脱敏或权限控制 |
| `tenantId` | 租户 ID |
| `path` | 请求路径 |
| `method` | HTTP 方法 |
| `status` | HTTP 状态码或业务状态 |
| `errorCode` | 业务错误码 |
| `message` | 日志正文 |
| `exception` | 异常堆栈 |

其中 `traceId` 非常重要。没有它，跨服务排查问题只能靠时间和关键词猜，效率会很低。

## 日志格式

生产环境更推荐 JSON 日志：

```json
{
  "timestamp": "2026-08-21T10:00:00+08:00",
  "level": "ERROR",
  "service": "order-service",
  "traceId": "7f3a9b",
  "path": "/api/orders",
  "errorCode": "ORDER_CREATE_FAILED",
  "message": "create order failed"
}
```

JSON 日志更容易被采集器解析，字段也更稳定。普通文本日志虽然可读性好，但解析规则容易随着格式变化而失效。

## 链路追踪关系

日志和链路追踪不是替代关系。

- Trace 告诉你一次请求经过了哪些服务、每一段耗时多少。
- Log 告诉你某个服务内部发生了什么、变量和异常是什么。
- Metrics 告诉你整体趋势，例如 QPS、错误率、延迟、资源使用率。

三者通过 `traceId`、`spanId`、`service` 等字段关联起来，排障效率才会真正提高。

## 留存与清理

日志存储最容易失控。需要提前定义：

- 热日志保留多久，例如 7 天或 15 天。
- 温日志保留多久，例如 30 天或 90 天。
- 冷日志是否归档到对象存储。
- 哪些日志必须满足审计要求。
- 索引按天、按服务还是按业务域拆分。

Elasticsearch 场景下，要配置索引生命周期，避免历史索引无限增长。日志系统如果把业务数据库拖垮，那就有些讽刺了。

## 安全与脱敏

日志里不要直接输出：

- 密码、token、密钥。
- 身份证号、手机号、银行卡。
- 完整请求头中的认证信息。
- 大体积请求体和响应体。
- 用户隐私和业务敏感字段。

脱敏最好在日志打印前完成，而不是指望采集端统一替你清理。采集端可以兜底，但不应该成为唯一防线。

## 告警设计

日志可以用于告警，但不要只靠日志告警。更稳定的做法是以指标告警为主，日志告警为辅。

适合日志告警的情况：

- 出现明确错误码。
- 出现关键异常类。
- 安全审计事件。
- 任务失败、补偿失败、消息死信。

不适合把每一条 ERROR 都变成告警。否则一旦故障发生，告警会淹没真正重要的信息。

## 总结

小规模系统可以从 Filebeat 或 Fluent Bit 加 Elasticsearch 开始。中大型系统建议增加 Kafka 缓冲，并结合链路追踪、指标监控、冷热分层和日志脱敏。

日志系统的价值不在于存了多少，而在于故障发生时能不能快速回答：哪个请求、哪个服务、哪个版本、哪个实例、哪个错误，导致了什么结果。
