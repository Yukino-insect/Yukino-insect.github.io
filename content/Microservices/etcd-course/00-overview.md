假设有三个程序同时运行：它们都要读取一份开关配置；其中只有一个可以定时生成日报；程序崩溃后，其他程序必须知道它已经离开。把这些状态只放在每个进程的内存里，副本之间会各说各话；放进普通数据库又仍要自己解决“两个程序同时抢到职责”和“谁已经失联”。**etcd 是为这类小而关键的协调状态准备的分布式键值存储。**

这门课不假定你接触过任何具体项目。所有示例都是独立的本机实验：一个 etcd 容器、几个以 `/learn/` 开头的键，以及 Docker 自带的 `etcdctl` 命令行客户端。读完后，你应能解释一个 key 是如何被多个节点一致地写入、为什么临时注册会自动消失，以及如何在发生故障后恢复数据。

## 先区分三个角色

一个 etcd 集群由**服务端成员**组成。成员保存数据、彼此复制，并通过 Raft 协议决定写入顺序。通常使用 3 或 5 个成员：3 个成员中至少 2 个在线才可继续安全写入。

应用程序、脚本和 `etcdctl` 则是**客户端**。它们发出读取、写入、监听等请求，但不参与投票。客户端不需要知道所有内部细节；它只需要配置能访问的客户端地址和认证信息。

最后是你写入的**键值对（key-value，KV）**。key 和 value 都是字节串，常被显示为文本。etcd 没有真正的目录；`/learn/config/theme` 看起来像路径，只是因为人们约定用 `/` 分段命名。

```text
应用 A  ─┐                         ┌─ 成员 2
应用 B ─┼─ 客户端请求 ──> 成员 1 ──┼─ 成员 3
etcdctl ─┘       写入由多数成员确认 └─ 成员 1（可能是 leader）
```

## etcd 解决什么，不解决什么

适合 etcd 的数据通常有三个特征：数据很小；多个参与者必须对它达成一致；数据存在明确的生命周期。例如配置版本、服务注册、任务调度者身份、分布式锁和控制面元数据。

不适合放进 etcd 的包括图片、文档正文、高频日志、队列消息体、订单明细和不断增长的分析数据。etcd 为一致性付出了网络复制与磁盘同步的成本；它不是为了做大对象存储、全文检索或海量业务表而设计的。把所有数据都塞进去，颇有把精密天平拿去称行李的意味。

## 实验约定

以下命令以 Windows PowerShell 为例。先创建一个专门放实验数据的当前目录；不要在包含其他服务数据的目录里执行清理命令。Docker 容器映射到本机 `32379`（客户端）和 `32380`（成员间通信）端口，避免占用常见默认端口。

```powershell
New-Item -ItemType Directory -Force .\etcd-learning-lab | Out-Null
Set-Location .\etcd-learning-lab
$env:ETCDCTL_API = '3'
$env:ETCDCTL_ENDPOINTS = 'http://127.0.0.1:32379'
```

`ETCDCTL_API=3` 表示使用 v3 API。课程内的容器中执行 `etcdctl` 时，它会连到容器内的 `127.0.0.1:2379`；在宿主机安装了 `etcdctl` 时，才使用上面的 `ETCDCTL_ENDPOINTS`。不要把“客户端地址”和“成员互相通信的 peer 地址”混为一谈：前者给应用使用，后者只给 etcd 成员复制日志使用。

## 完成后的自检

完成四章后，你应该能实际拿出以下结果，而不是只记住一串名词：

| 目标 | 你应看到的证据 |
| --- | --- |
| KV 与版本 | JSON 结果里的 `create_revision`、`mod_revision` 和全局 `revision` |
| Watch | 一个终端写入或删除后，另一个终端立即显示 `PUT` 或 `DELETE` |
| Lease | 停止续约后，附着的 key 自动消失 |
| 竞争控制 | 两个竞争者中仅一个事务成功，旧持有者不能继续写受保护资源 |
| 恢复 | 从快照启动的隔离实例能读到预期 key |

下一章的概念有些抽象，但每一个都会在后面的命令中变成可观察的输出。先耐心把地基打好；协调系统最擅长惩罚跳过地基的人。
