在运行命令之前，先回答一个简单问题：网络把三台机器隔开时，它们能否各自接受“我是当前调度者”这条写入？如果可以，网络恢复后就可能出现两个调度者。etcd 宁可在没有多数成员时拒绝写入，也不允许这种分裂状态出现。理解这个取舍，才不会把 etcd 当作一个带 HTTP 接口的普通 Map。

## 多数派与 Raft：写入为什么不会各自为政

**Raft** 是一种复制状态机协议。每个成员保存同一份按顺序排列的日志；集群会选出一个 leader（领导者）。客户端的写请求由 leader 接收，leader 把这条日志复制给其他成员；当**多数派（quorum）**确认后，日志才提交并应用到 KV 数据。

3 个成员的多数派是 2，能容忍 1 个成员故障；5 个成员的多数派是 3，能容忍 2 个故障。4 个成员的多数派也是 3，因此仍只容忍 1 个故障，却多了一份复制开销。生产集群常选奇数成员，并分布在不同机器或可用区。

```text
客户端写入 color=blue
        │
        ▼
leader 追加日志 ──复制──> follower A
        │                   follower B
        └── 收到自己 + 任一 follower 确认后提交
```

所谓**线性一致性（linearizability）**，可以粗略理解为：每次成功写入都像在某个唯一时刻发生；之后进行的线性一致读不会再看见它之前的旧状态。它不意味着请求永远快速，也不意味着少数成员离线时仍能写。恰恰相反，等待多数确认正是它的代价。

## KV 不是文件系统：key、范围与版本

etcd 的 key 与 value 都是字节串。`/learn/config/color` 是一个 key，不是磁盘文件。以 `/learn/config/` 做前缀读取，只是读取所有以这段字节开头的 key；因此命名时应保持分隔符，例如用 `/learn/users/` 而非 `/learn/users`，避免误匹配。

每次成功的写事务都会推进一个全局的 **revision（修订号）**。可以把它看成单调递增的逻辑时间，而不是墙上时钟。一个 key 的重要元数据包括：

| 字段 | 含义 |
| --- | --- |
| `create_revision` | 这个 key 第一次创建时的全局版本 |
| `mod_revision` | 这个 key 最近一次修改时的全局版本 |
| `version` | 这个 key 自创建以来被修改的次数 |
| `lease` | 若非零，表示该 key 绑定的租约 ID |

etcd 的存储使用**多版本并发控制（MVCC）**：新写入不会马上抹掉旧版本，而是以新的 revision 追加历史。因此客户端可以读取某一历史 revision 的一致快照，也可以从某个 revision 之后追变化。历史不是无限保留的；压缩会在第四章讨论。

## Range 与 Watch：先取快照，再持续追踪

**Range** 是读取一个 key 或 key 范围的操作。**Watch** 是一个保持连接的订阅：服务器把后续 `PUT`、`DELETE` 事件推给客户端。Watch 很适合让配置缓存或服务发现列表及时更新，却不是可靠消息队列。

一个不会轻易漏状态的客户端遵循这套顺序：

1. 用 range 读取完整前缀，获得当前键集合和响应头中的 revision `R`。
2. 在本地用这份快照替换旧状态。
3. 从 `R + 1` 开始 watch 同一前缀，按事件顺序更新本地状态。
4. 如果连接中断，或服务器提示起始 revision 已被压缩，重新从第 1 步开始。

这叫“快照加增量”。只靠 watch 很脆弱：程序断线时看不到的事件不会自动填进内存；只靠定时全量轮询又会让更新延迟和读取压力不断上涨。

## Lease：让临时身份自动过期

**Lease（租约）**是一段有倒计时的服务器端凭证，以 TTL（time to live，剩余生存秒数）表示。一个或多个 key 可以附着到同一个 lease。客户端不断发送 keep-alive（续约）时，TTL 被刷新；客户端崩溃、网络长期断开或主动撤销 lease 时，TTL 归零，etcd 会删除所有附着 key。

这适合表达“此实例目前仍活着”或“此锁目前由我持有”，但不适合表达永久业务记录。租约删除 key 只是协调层的事实，并不会撤销持有者此前已向外部系统发出的写操作。后面讲锁时会用 **fencing token（隔离令牌）** 处理这个更棘手的问题。

## 单节点与集群的边界

单节点 etcd 是理解 API 的好工具：没有副本、没有网络多数派，也就没有容错。它停机时，所有依赖它的协调请求都会失败。三节点集群让其中一台故障后仍可工作，但它仍需要可靠磁盘、稳定网络、认证和恢复演练。

现在不必背诵 Raft 的每一个状态转换。请记住四条能指导实践的结论：成功写入需要多数确认；revision 给变化排出全局顺序；watch 必须能回到快照重建；lease 只表达暂时有效。下一章会让它们逐一出现在屏幕上。
