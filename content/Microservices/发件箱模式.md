Transactional Outbox，也叫发件箱模式或本地消息表模式，用来解决微服务里最常见的一类一致性问题：**本地数据库已经提交，但消息没有可靠发出去**。

它不追求多个系统同时提交，也不是 2PC。它的目标更朴素：只要本地事务成功，表示这次业务变更的事件就一定被持久化，之后可以通过轮询或 CDC 可靠发布到消息系统，最终让下游系统完成同步。

## 要解决的问题

很多业务都会同时做两件事：

1. 修改本服务数据库。
2. 向 MQ、Kafka 或其他服务发送一条事件。

例如：

- 订单创建成功后通知库存服务扣减库存。
- 支付成功后通知积分、账单、风控系统。
- 商品信息变更后通知搜索系统更新 ES 索引。
- 用户注册成功后发布 `UserRegistered` 领域事件。

如果业务代码直接写成“先提交数据库，再发送消息”，中间任何网络抖动、进程重启、MQ 不可用，都可能造成数据库成功但消息丢失。

反过来，如果先发消息再提交数据库，也可能出现消息已经被消费，但数据库事务最终回滚。所谓“双写问题”，麻烦就在这里。

## 核心思路

Outbox 的做法是：**把业务数据变更和待发送消息写入同一个数据库事务**。

```java
@Transactional
public void createOrder(CreateOrderCommand command) {
    Order order = Order.create(command);
    orderMapper.insert(order);

    OutboxEvent event = OutboxEvent.of(
        "Order",
        order.getId().toString(),
        "OrderCreated",
        JsonUtils.toJson(new OrderCreatedEvent(order.getId()))
    );
    outboxEventMapper.insert(event);
}
```

事务提交后，业务表和 `outbox_event` 表要么都存在，要么都不存在。这样就避开了“业务成功但消息完全没记录”的危险情况。

后续由发布器负责把 `outbox_event` 里的事件投递到 MQ。投递失败可以重试，长期失败可以进入死信或人工处理。

## 表结构设计

一张典型的 `outbox_event` 表可以包含这些字段：

| 字段 | 作用 |
| --- | --- |
| `id` | 主键，通常用雪花 ID 或数据库自增 ID |
| `event_id` | 全局唯一事件 ID，消费者幂等去重使用 |
| `aggregate_type` | 聚合类型，例如 `Order`、`Product` |
| `aggregate_id` | 聚合 ID，例如订单 ID、商品 ID |
| `event_type` | 事件类型，例如 `OrderCreated`、`ProductUpdated` |
| `payload` | 事件内容，通常是 JSON |
| `headers` | 扩展头，例如 traceId、tenantId、version |
| `status` | `NEW`、`SENDING`、`SENT`、`FAILED` |
| `retry_count` | 已重试次数 |
| `next_retry_time` | 下次允许重试时间 |
| `last_error` | 最近一次失败原因 |
| `created_at` | 创建时间 |
| `published_at` | 发布时间 |

`event_id` 很重要。Outbox 发布通常是至少一次投递，消费者必须用它做幂等。

## 两种发布方式

### 轮询发布

应用内或独立 Worker 定时扫描 `outbox_event` 表，把 `NEW` 或到达重试时间的事件发送到 MQ。

```java
public void publishPendingEvents() {
    List<OutboxEvent> events = outboxEventMapper.findPending(100);

    for (OutboxEvent event : events) {
        try {
            messageTemplate.send(event.getTopic(), event.getPayload());
            outboxEventMapper.markSent(event.getId());
        } catch (Exception ex) {
            outboxEventMapper.markFailed(event.getId(), ex.getMessage());
        }
    }
}
```

这种方式实现简单，适合多数业务系统先落地。需要注意的是，扫描时要避免多实例重复抢同一批数据，可以使用状态机、乐观锁、`SELECT ... FOR UPDATE SKIP LOCKED` 或分片扫描。

### CDC 发布

CDC 方式通过订阅数据库 binlog 或 WAL 捕获 `outbox_event` 的新增记录，再推送到 Kafka 等消息系统。典型方案是 Debezium 加 Outbox Event Router。

CDC 的好处是发布逻辑更少侵入业务应用，吞吐和可靠性也更适合中大型系统。代价是需要维护 Kafka Connect、Debezium、Schema 变化和运维监控。

## 消费端幂等

Outbox 只能把“消息不丢”变得可控，并不能保证消费者只收到一次。发布器发送成功后还没来得及更新状态、或者 MQ 重试投递，都可能导致重复消费。

常见幂等方式：

- 建 `processed_event` 表，以 `event_id` 做唯一键。
- 目标业务表使用唯一约束，例如 `order_id + event_type`。
- 更新语句带状态条件，例如只允许 `CREATED -> PAID`。
- 使用业务天然幂等的覆盖写，例如按商品 ID 更新 ES 文档。

消费者不要把幂等当成“最好有”。在事件驱动系统里，它属于入场券。

## 与 ES 同步的关系

Outbox 不是“ES 和 MySQL 的对账表”。更准确地说，它记录的是 **MySQL 中哪些业务变化需要被发布出去**。

如果下游消费者负责写 ES，那么 Outbox 记录的可以是 `ProductUpdated`、`ProductDeleted` 这类事件。消费者收到事件后更新 ES。是否需要额外记录 ES 同步状态，要看业务要求：

- 只要求最终同步：Outbox 加消费者重试通常足够。
- 要能按业务对象查询同步结果：可以增加 `index_sync_status`。
- 要能发现长期不一致：需要定时对账任务。

## 适用场景

适合使用 Outbox 的场景：

- 本地数据库更新后必须可靠通知其他系统。
- 可以接受最终一致性。
- 不想引入 XA 或强协调事务。
- 业务已经事件驱动，或者准备改造成 Saga。
- 下游失败可以通过重试、补偿或人工处理恢复。

不适合的场景：

- 要求所有系统在同一时刻强一致提交。
- 外部操作不可重试、不可幂等、不可补偿。
- 跨多个数据库写入必须表现为一个数据库级原子事务。

## 落地清单

1. 业务事务中同时写业务表和 `outbox_event`。
2. 每条事件生成全局唯一 `event_id`。
3. 发布端保证可重试，失败记录原因。
4. 消费端按 `event_id` 或业务唯一键做幂等。
5. 设置死信、告警和人工补偿入口。
6. 成功发布的历史数据按时间归档或清理。
7. 关键链路透传 `traceId`，方便从业务日志追到事件发布和消费。

## 总结

Outbox 的本质是把“要发出去的消息”也纳入本地事务。它不神秘，也不昂贵，但它要求系统承认一个现实：微服务之间很难靠一次同步调用解决所有一致性问题。

把业务状态先稳稳落库，再让事件可靠地向外传播，这就是 Outbox 最有价值的地方。
