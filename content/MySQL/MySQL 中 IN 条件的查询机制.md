`IN` 条件用于判断某个字段是否属于一组候选值。它看起来像多个 `OR` 条件的简写，但 MySQL 优化器在执行时不一定会简单地逐个比较。

## 一、常量 IN 列表

最常见的写法是：

```sql
select *
from user
where id in (1, 3, 5, 7);
```

如果 `id` 上有索引，MySQL 通常可以对每个候选值走索引查找，再合并结果。对于主键或唯一索引，这类查询通常效率较高。

如果 `IN` 列表很长，优化器需要评估成本。列表过大时，SQL 解析、优化和执行成本都会上升，甚至可能导致执行计划不稳定。

## 二、IN 和 OR

从逻辑上看：

```sql
where id in (1, 2, 3)
```

等价于：

```sql
where id = 1 or id = 2 or id = 3
```

但执行计划由优化器决定。不能简单认为 `IN` 一定比 `OR` 快，也不能认为 `OR` 一定会导致索引失效。关键要看字段是否有索引、候选值数量、数据分布和最终执行计划。

## 三、子查询 IN

子查询写法如下：

```sql
select *
from orders
where user_id in (
    select id
    from user
    where status = 1
);
```

MySQL 可能把它改写为半连接，也可能使用物化子查询等策略。具体行为取决于 MySQL 版本、优化器开关、索引和数据规模。

对于子查询 `IN`，要重点关注：

1. 子查询结果集大小。
2. 子查询字段是否有索引。
3. 外层关联字段是否有索引。
4. 是否可以改写为 `EXISTS` 或 `JOIN`。

## 四、实践建议

如果 `IN` 列表来自业务参数，应限制列表长度。几百个值通常还能接受，几千甚至更多就要考虑临时表、批量查询或改写业务逻辑。

排查性能时，不要只看 SQL 写法，应使用：

```sql
explain select ...
```

确认是否使用了预期索引、扫描行数是否合理、是否出现临时表或文件排序。

总结来说，`IN` 是常用条件表达式，不是性能问题本身。真正影响性能的是索引、候选值数量、数据分布和优化器选择。
