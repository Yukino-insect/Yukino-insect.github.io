MySQL InnoDB 的主要索引结构是 B+ 树。选择 B+ 树的核心原因是：数据库数据主要存储在磁盘或页缓存中，索引结构必须尽量减少随机 IO，并支持范围查询。

## 一、磁盘 IO 是关键成本

内存数据结构通常追求 CPU 计算效率，而数据库索引首先要考虑磁盘页访问次数。

InnoDB 默认以页为单位读取数据。一个索引节点通常对应一个页，页中可以放很多 key。B+ 树的分叉很多，因此树高很低。即使数据量达到千万级，树高也可能只有三到四层。

树高越低，从根节点查到叶子节点需要访问的页越少，随机 IO 成本也越低。

## 二、为什么不是普通二叉树

普通二叉搜索树每个节点最多只有两个子节点。数据量一大，树高会很高；如果数据插入顺序不理想，还可能退化成链表。

数据库索引需要稳定的查询成本，所以不能依赖普通二叉树。

## 三、为什么不是 HashMap

Hash 结构适合等值查询，但不适合范围查询。例如：

```sql
where age between 20 and 30
order by create_time
```

B+ 树的叶子节点按 key 有序，并且叶子节点之间有链表连接，天然适合范围扫描和排序优化。Hash 索引很难高效支持这类查询。

另外，数据库索引还要支持最左前缀匹配、范围查找和有序遍历，这些都是 B+ 树更擅长的地方。

## 四、为什么 Redis 不一定使用 B+ 树

Redis 主要工作在内存中，访问数据的主要成本不是磁盘随机 IO，而是内存访问和 CPU 操作。不同场景下 Redis 会选择哈希表、跳表、压缩列表、整数集合等结构。

例如有序集合常用跳表，是因为跳表实现相对简单，范围查询也方便，且在内存场景下性能足够好。

## 五、总结

B+ 树适合数据库索引，是因为它能用较低树高减少磁盘页访问，同时支持范围查询和有序扫描。HashMap 适合内存等值查找，跳表适合内存有序集合。不同系统选择不同结构，本质上是访问介质和查询模式不同。
