数据库字段映射到 Java 对象时，要特别注意 `null`、基本类型、包装类型之间的差异。很多看似正常的默认值，实际上可能已经掩盖了数据质量问题。

## 一、问题场景

假设数据库中有一个字段 `covered`，语义是是否覆盖，通常使用 `0` 和 `1` 表示。

如果数据库字段允许为 `null`，而 Java 实体类中使用的是基本类型：

```java
private short covered;
```

那么 ORM 框架或映射过程可能会把数据库中的 `null` 转换成 Java 基本类型默认值 `0`。这样业务代码看到的是 `0`，但真实数据其实是未知状态。

## 二、为什么基本类型有风险

Java 基本类型不能表示 `null`。例如：

```java
int 默认值是 0
boolean 默认值是 false
short 默认值是 0
```

这些默认值在业务上可能是合法值。于是 `null` 和合法值被混在一起，后续判断就会失真。

## 三、推荐做法

如果数据库字段允许为空，Java 实体类应优先使用包装类型：

```java
private Short covered;
```

这样可以保留三种状态：

1. `null`：没有值或未知。
2. `0`：明确为否。
3. `1`：明确为是。

如果业务不允许为空，则应在数据库层和应用层同时约束：

```sql
covered tinyint not null default 0
```

同时在 DTO 校验中使用 `@NotNull` 或枚举校验，避免脏数据进入系统。

## 四、总结

数据库字段是否允许为 `null`，必须和 Java 类型设计保持一致。允许为空就用包装类型，不允许为空就用数据库约束和参数校验明确兜住。不要让 Java 基本类型的默认值替业务语义做决定。
