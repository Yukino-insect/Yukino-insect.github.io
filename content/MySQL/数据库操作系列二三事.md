数据库开发中，很多问题不是 SQL 写不出来，而是边界条件没有想清楚。主键、类型转换、逻辑删除和动态条件拼接，都属于容易在项目后期放大成本的细节。

## 一、主键设计

企业项目中不一定绝对禁止自增主键，但在分库分表、数据迁移、多机写入和跨系统合并数据时，自增主键会带来额外约束。

常见选择有：

1. 单库单表：自增主键简单高效。
2. 分布式系统：可以使用雪花算法、号段模式或 UUID v7。
3. 需要按时间大致有序：UUID v7 比随机 UUID 更适合索引写入。

主键不应承载业务含义。业务唯一性应由单独的唯一索引保证。

## 二、类型转换

不同数据库对隐式类型转换的容忍度不同。MySQL 在某些场景下会做隐式转换，例如字符串字段和数字比较；PostgreSQL 更严格，类型不匹配时通常直接报错。

隐式转换有两个风险：

1. 查询结果可能和预期不一致。
2. 索引可能失效，导致全表扫描。

更稳妥的做法是让参数类型和字段类型保持一致。如果必须转换，应显式使用 `CAST`，并确认不会破坏索引使用。

## 三、逻辑删除

使用逻辑删除时，要避免唯一索引和已删除数据冲突。常见方案是：

1. 唯一索引中加入删除标记。
2. 使用业务无关主键作为主键。
3. 对仍然有效的数据建立唯一约束。

例如同一个手机号允许历史记录存在，但只允许一个未删除用户使用，就需要把唯一性约束设计在“手机号加删除状态”或等价方案上。

## 四、动态条件

使用 MyBatis-Plus 条件构造器时，要注意空值条件。没有使用 `condition` 参数时，空值可能被拼接成不符合预期的条件。

推荐写法：

```java
queryWrapper.eq(name != null, User::getName, name);
```

这样只有 `name` 不为空时才追加条件，避免生成错误 SQL 或查不到数据。

## 五、总结

数据库操作要尽量显式。主键含义、字段类型、唯一约束、动态条件都不要依赖“框架应该懂”。数据库越靠近系统底层，越应该把规则写清楚。
