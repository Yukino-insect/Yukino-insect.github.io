我实习时做过一个建表功能，第一反应是用自增主键。后来被提醒：生产环境里不一定都适合用自增主键，尤其涉及数据迁移、分库分表和跨系统合并时，自增 ID 会带来额外约束。

自增主键不是坏设计。它在单库单表里简单、紧凑、写入顺序友好。但它也不是万能答案。更准确的判断应该是：**自增主键适合表内标识，不一定适合全局标识和对外暴露。**

## 一、自增主键的优点

自增主键常见优点有：

1. 简单：数据库自动生成，业务不用关心 ID 生成。
2. 紧凑：`bigint` 比 UUID 字符串更省空间。
3. 顺序写入：对 InnoDB 聚簇索引友好，页分裂通常更少。
4. Join 成本低：短数字主键适合关联表保存和比较。
5. 表内唯一：单表内天然适合作为技术主键。

所以在单库单表、内部系统、数据不出域、并发压力可控的场景，自增主键仍然很好用。

## 二、自增主键的问题

生产里不喜欢自增主键，通常不是因为它“慢”，而是因为它会限制架构演进。

### 1. 多库多实例容易冲突

一旦出现分库分表、多主写入、离线导入、灾备回放，每个库都从 1 开始生成 ID，就可能撞号。

可以通过设置不同步长解决一部分问题：

```ini
auto_increment_increment = 2
auto_increment_offset = 1
```

但这只是特定部署下的规避方案，并没有让自增 ID 变成真正的全局 ID。

### 2. 数据迁移和合库成本高

如果两个系统都有 `id = 10001` 的订单，合并时就必须改 ID，并同步修改所有引用它的外键、日志、缓存、明细表和历史数据。

主键一旦参与大量关联，迁移时改它就很痛。是的，痛不是什么技术术语，但工程里它通常相当准确。

### 3. 对外暴露可预测

自增 ID 连续递增，如果直接出现在接口里：

```text
/order/detail?id=10001
```

用户可能枚举 ID，探测其他数据，甚至推断业务量增长。权限校验当然必须做，但对外 ID 仍应尽量避免过于可预测。

### 4. 极高并发下可能出现热点

递增主键会让新数据集中写入 B+ 树最右侧叶子页。优点是顺序写入，缺点是极高并发时可能出现右端热点、页级并发争用或自增分配相关等待。

这不是说自增主键普遍性能差。大多数业务系统里，它反而比随机 UUID 更友好。只有在高并发写入、批量插入、特殊复制模式或热点表设计下，才需要重点评估。

## 三、事务回滚后自增值为什么不回退

一个常见现象是：

```sql
create table t (
  id bigint primary key auto_increment,
  name varchar(32)
) engine = InnoDB;

begin;
insert into t(name) values ('a'); -- 分配到 id = 100
rollback;

insert into t(name) values ('b'); -- 可能得到 id = 101
```

表里最后可能只有 `101`，没有 `100`。这不是异常，而是自增机制的正常结果。

原因是：**自增值的首要目标是唯一、快速、低冲突地发号，不是保证编号连续。**

如果自增值要跟着事务回滚，数据库就要追踪：

1. 哪些号被哪个事务取走。
2. 哪些事务提交了。
3. 哪些事务回滚后可以归还。
4. 已经被其他事务看见或等待的号码如何处理。
5. 崩溃恢复后哪些号码还能复用。

这会让发号机制变慢、变复杂，还可能引入更强的锁竞争。数据库通常选择更务实的策略：**号一旦分配，就视为消耗，不保证复用。**

因此，自增主键只能保证唯一和大体递增，不能用来保证“业务流水号连续”。如果业务必须要连续编号，例如发票号、财务凭证号，应单独设计严格的业务编号机制，并接受它带来的串行化和审计成本。

## 四、AUTO_INCREMENT 和 sequence 的区别

MySQL `AUTO_INCREMENT` 是表字段属性：

```sql
id bigint primary key auto_increment
```

它通常在 `insert` 时由数据库自动分配，和表绑定。

PostgreSQL、Oracle、Kingbase 等数据库常见的 sequence 是独立发号对象：

```sql
select nextval('order_seq');
```

sequence 可以插入前取号，也可以被多张表共用。二者实现方式不同，但在一个核心点上很像：**已经发出去的号通常不会因为事务回滚而回退。**

## 五、业务主键和技术主键

不要把“主键”和“业务唯一字段”混成一件事。

常见更稳妥的设计是：

```sql
create table asset (
  id bigint primary key,
  asset_no varchar(64) not null,
  name varchar(128) not null,
  deleted tinyint not null default 0,
  unique key uk_asset_no_deleted (asset_no, deleted)
) engine = InnoDB;
```

其中：

1. `id` 是技术主键，负责表内关联、索引和稳定引用。
2. `asset_no` 是业务编号，负责业务唯一性。
3. 唯一索引保证业务规则，而不是靠代码先查再插。

业务字段直接做主键只有在它短、稳定、全局唯一、不敏感、几乎不会变更时才适合。现实项目里，这些条件经常并不同时成立。

## 六、逻辑删除下的唯一约束

逻辑删除常见字段：

```sql
deleted tinyint not null default 0
```

查询时默认加：

```sql
where deleted = 0
```

问题在于：逻辑删除并没有真的删掉数据库行。如果业务字段有唯一约束，删除后再新增同一个业务编号，可能仍然报唯一冲突。

常见处理方式有：

1. 唯一索引中加入删除标记或删除版本。
2. 删除时把业务唯一字段改写为带删除版本的值。
3. 使用支持条件唯一索引的数据库特性，只约束未删除数据。
4. 让 `id` 作为技术主键，业务字段单独建符合业务语义的唯一约束。

MySQL 没有 PostgreSQL 那样直接的 partial unique index。用 `(business_key, deleted)` 时要注意：如果 `deleted` 只有 `0/1`，同一个业务键最多只能保留一条已删除记录。想保留多条历史，通常要把删除时间、删除批次或版本号纳入唯一约束设计。

## 七、应用层 ID 方案

分布式系统常见替代方案包括：

| 方案 | 优点 | 风险 |
| ---- | ---- | ---- |
| 雪花 ID | 趋势递增、可离线生成、空间较小 | 依赖时钟，时钟回拨要处理 |
| UUID | 全局唯一、生成简单 | 随机 UUID 对索引局部性不友好，字符串占空间 |
| UUID v7 / ULID | 时间有序，兼顾分散性 | 实现和存储格式要统一 |
| 号段模式 | 数据库发号次数少，吞吐高 | 需要号段服务和容灾设计 |

MyBatis-Plus 的 `IdType.ASSIGN_ID` 属于应用层生成 ID，通常会在插入前回填到实体对象。数据库自增 ID 则是在执行 `insert` 后由数据库生成，再通过 JDBC `getGeneratedKeys` 或 MyBatis 的主键回填机制写回实体。

这个差异很重要：插入前就需要 ID，用应用层生成更自然；只需要落库后拿到表内 ID，自增主键也可以。

## 八、怎么选择

可以按这个规则判断：

1. 单库单表、内部系统、数据不迁移：自增主键很合适。
2. 对外接口暴露：使用不可枚举的业务 ID 或 public id。
3. 分库分表、多系统合并：优先考虑全局唯一 ID。
4. 业务编号必须连续：不要依赖自增主键，单独设计业务流水号。
5. 逻辑删除较多：技术主键和业务唯一约束分开设计。

最后的结论很简单：**自增主键适合作为表内技术主键，但不要把它当成分布式全局 ID、业务流水号或安全边界。**
