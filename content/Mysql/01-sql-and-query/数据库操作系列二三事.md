数据库开发中，很多问题不是 SQL 写不出来，而是边界条件没有想清楚。主键、字段类型、逻辑删除、动态条件、迁移变更，这些看似小的地方，后期都可能放大成数据事故。

这篇更像一份实践清单，不追求把每个主题讲到最深，而是提醒自己：哪些规则必须提前写清楚。

## 一、主键设计

主键尽量使用无业务语义的技术主键，例如 `bigint id`、雪花 ID、UUID v7。业务唯一性由单独的唯一索引保证。

推荐：

```sql
create table user_account (
  id bigint primary key,
  username varchar(64) not null,
  mobile varchar(20),
  deleted tinyint not null default 0,
  unique key uk_user_account_username_deleted (username, deleted)
) engine = InnoDB;
```

这样做有几个好处：

1. 业务字段变更时，不影响表间关联。
2. 主键短，二级索引和 join 成本更低。
3. 数据迁移和历史版本保留更方便。
4. 业务唯一性明确交给唯一索引，不靠代码侥幸。

自增主键不是不能用。单库单表里它简单高效。真正要警惕的是把自增 ID 当作全局 ID、业务流水号或对外安全标识。

## 二、类型映射

数据库字段映射到 Java 对象时，要特别注意 `null`、基本类型、包装类型之间的差异。

假设数据库字段允许为空：

```sql
covered tinyint null
```

如果 Java 实体类写成：

```java
private short covered;
```

数据库里的 `null` 可能被映射成 Java 基本类型默认值 `0`。业务代码看到的是 `0`，但真实语义可能是“未知”。这会掩盖数据质量问题。

更稳妥的写法：

```java
private Short covered;
```

这样可以保留三种状态：

1. `null`：没有值或未知。
2. `0`：明确为否。
3. `1`：明确为是。

如果业务不允许为空，就在数据库层和应用层都明确约束：

```sql
covered tinyint not null default 0
```

```java
@NotNull
private Short covered;
```

不要让 Java 基本类型的默认值替业务语义做决定。它没有那么聪明，只是沉默地给你一个零。

## 三、隐式类型转换

MySQL 对隐式类型转换比较宽容，但宽容不等于安全。

例如字段是字符串：

```sql
phone varchar(20)
```

查询时却传数字：

```sql
where phone = 13800138000
```

MySQL 可能进行隐式转换，带来两个风险：

1. 查询结果和预期不一致。
2. 转换发生在字段侧时，索引可能无法正常使用。

推荐做法：

1. SQL 参数类型和字段类型保持一致。
2. 不依赖数据库自动转换。
3. 必须转换时显式写 `cast`，并用 `explain` 确认执行计划。

## 四、逻辑删除

逻辑删除通常这样设计：

```sql
deleted tinyint not null default 0
```

业务查询默认追加：

```sql
where deleted = 0
```

它的好处是保留历史数据，缺点是唯一约束会变复杂。比如用户名逻辑删除后又重新注册，如果只有：

```sql
unique key uk_username (username)
```

旧记录还在，新增就可能报唯一冲突。

常见方案：

1. 唯一索引中加入删除标记或删除版本。
2. 删除时改写业务唯一字段，例如追加删除时间戳。
3. 只允许保留一条已删除历史时，可以使用 `(business_key, deleted)`。
4. 要保留多条历史时，不要只用布尔 `deleted` 参与唯一索引。

逻辑删除不是“免费删除”。它只是把删除问题从物理层转移到了查询、唯一约束、归档和数据治理层。

## 五、动态条件

使用 MyBatis-Plus 或类似条件构造器时，要明确控制空值条件。

不推荐：

```java
queryWrapper.eq(User::getName, name);
```

如果 `name` 为空，生成的 SQL 可能不符合预期。

推荐：

```java
queryWrapper.eq(name != null && !name.isBlank(), User::getName, name);
```

对于集合条件也一样：

```java
queryWrapper.in(ids != null && !ids.isEmpty(), User::getId, ids);
```

动态 SQL 的原则是：**条件是否参与查询，必须由代码显式表达。**

## 六、迁移和变更

数据库变更要比普通代码更保守，因为数据不是发版失败后重新编译一下就回来。

常见建议：

1. 字段新增优先兼容旧代码，先加字段，再发应用。
2. 字段删除分阶段做，先确认没有读写，再删除。
3. 大表加索引要评估锁表、回放延迟和磁盘空间。
4. 字段类型变更要提前清洗脏数据。
5. 迁移脚本要可重复执行，至少要能判断当前状态。
6. 关键数据迁移后要有校验 SQL。

常用校验：

```sql
select count(*) from old_table;
select count(*) from new_table;

select business_key
from new_table
group by business_key
having count(*) > 1;
```

## 七、总结

数据库操作要尽量显式：主键含义要显式，字段类型要显式，唯一约束要显式，动态条件要显式，迁移过程也要显式。

框架可以减少样板代码，但不负责替你理解业务规则。数据库越靠近系统底层，越不应该把关键约束藏在“应该没问题”的假设里。
