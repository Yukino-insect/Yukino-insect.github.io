索引是数据库为了提高查询效率而维护的数据结构。它的本质是：**用额外的存储空间和写入维护成本，换取更少的数据扫描、更稳定的查询路径。**

索引不是“加了就一定快”。它能不能发挥作用，取决于查询条件、排序方式、字段选择性、数据分布和优化器最终选择的执行计划。

## 一、为什么需要索引

没有索引时，数据库通常只能全表扫描：

```sql
select *
from orders
where user_id = 10001;
```

如果 `orders` 有几百万行，这条 SQL 可能要逐行判断 `user_id`。有索引后，数据库可以通过索引结构快速定位候选行，减少读取的数据页数量。

索引常用于：

1. 高频查询条件，例如 `where user_id = ?`。
2. 连接字段，例如 `join user on user.id = orders.user_id`。
3. 排序字段，例如 `order by create_time desc`。
4. 分组字段，例如 `group by status`。
5. 唯一性约束，例如手机号、订单号、业务编号。

## 二、常见索引类型

MySQL 中常见索引包括：

| 类型 | 作用 | 说明 |
| ---- | ---- | ---- |
| 主键索引 | 唯一标识一行 | 一个表只能有一个主键，InnoDB 中主键索引也是聚簇索引 |
| 唯一索引 | 保证列或列组合唯一 | 可以有多个，允许业务字段唯一 |
| 普通索引 | 加速查询 | 不保证唯一 |
| 联合索引 | 多列组合索引 | 遵循最左前缀原则 |
| 全文索引 | 文本检索 | 适合全文搜索场景，不等同于普通 `like` |

创建示例：

```sql
create table user (
  id bigint primary key,
  username varchar(64) not null,
  mobile varchar(20),
  create_time datetime not null,
  unique key uk_user_mobile (mobile),
  key idx_user_create_time (create_time)
) engine = InnoDB;
```

查看索引：

```sql
show index from user;
show create table user;
```

删除索引：

```sql
drop index idx_user_create_time on user;
```

## 三、为什么 InnoDB 常用 B+ 树

InnoDB 的主要索引结构是 B+ 树。选择 B+ 树的核心原因不是它在内存里最炫，而是它适合数据库的磁盘页模型。

B+ 树有几个重要特点：

1. 树高低：一个节点能放很多 key，千万级数据也常见只有几层。
2. 非叶子节点主要保存索引键和指针，可以容纳更多分支。
3. 叶子节点按 key 有序，适合范围查询。
4. 叶子节点之间有链表，适合顺序扫描和排序。

普通二叉树每个节点最多两个孩子，数据量大时树高很高，甚至可能退化。红黑树适合内存场景，但数据库读取数据通常以页为单位，树高越低，随机 IO 越少。

Hash 结构适合等值查询：

```sql
where id = 100
```

但它不擅长范围查询和排序：

```sql
where age between 20 and 30
order by create_time
```

B+ 树正好兼顾等值查询、范围查询、最左前缀匹配和有序扫描，所以更适合作为通用数据库索引结构。

## 四、聚簇索引和二级索引

InnoDB 表的数据本身按聚簇索引组织。一般情况下：

1. 如果表有主键，主键索引就是聚簇索引。
2. 如果没有主键，会选择第一个非空唯一索引。
3. 如果都没有，InnoDB 会生成隐藏的聚簇索引。

聚簇索引的叶子节点保存完整行数据。二级索引的叶子节点保存二级索引键和主键值。

例如：

```sql
create table orders (
  id bigint primary key,
  user_id bigint not null,
  amount decimal(10, 2) not null,
  key idx_orders_user_id (user_id)
) engine = InnoDB;
```

查询：

```sql
select amount
from orders
where user_id = 10001;
```

如果走 `idx_orders_user_id`，InnoDB 会先在二级索引里找到对应的主键 `id`，再通过主键索引取完整行数据。这个过程叫回表。

如果查询的列都在二级索引里：

```sql
select user_id, id
from orders
where user_id = 10001;
```

就可能形成覆盖索引，减少回表成本。

## 五、主键唯一性如何保证

数据库保证主键唯一，不是每次插入前全表查一遍，而是靠 **主键约束 + 唯一索引** 在写入时做强制校验。

定义主键：

```sql
primary key (id)
```

数据库会建立主键约束，并为主键维护唯一索引。插入 `id = X` 时，数据库在唯一索引中定位 `X`：

1. 如果已经存在，插入失败。
2. 如果不存在，才允许写入索引项和数据行。

并发插入同一个主键时，唯一索引层面会进行原子检查和必要的锁控制。最终最多只有一个事务成功，其他事务会等待后报唯一冲突，或直接报唯一冲突。具体等待方式和隔离级别、存储引擎实现有关，但结果不会漏。

所以，`select count(*)` 再判断是否存在，不是保证唯一性的可靠方式。真正的底线应该交给主键或唯一索引。

## 六、联合索引和最左前缀

联合索引的列顺序非常重要：

```sql
create index idx_orders_user_status_time
on orders(user_id, status, create_time);
```

它比较适合：

```sql
where user_id = ?

where user_id = ? and status = ?

where user_id = ? and status = ?
order by create_time
```

但通常不适合直接只查：

```sql
where status = ?
```

因为没有从联合索引最左列 `user_id` 开始使用。

联合索引设计时要围绕真实 SQL，而不是把字段随便凑在一起。通常把等值过滤字段放前面，范围和排序字段放后面，但最终仍要看数据分布和执行计划。

## 七、索引失效的常见原因

索引失效并不是索引真的消失，而是优化器无法高效使用它，或认为使用它不划算。

常见原因包括：

1. 对索引列使用函数：

```sql
where date(create_time) = '2026-08-21'
```

2. 对索引列做表达式运算：

```sql
where id + 1 = 100
```

3. 字段类型和参数类型不一致，引发隐式转换。
4. 联合索引没有满足最左前缀。
5. 前置模糊匹配：

```sql
where name like '%Tom'
```

6. 查询返回数据比例太高，优化器选择全表扫描。

需要注意，很多“索引失效口诀”都不是绝对规则。比如 `is null`、`is not null`、`or` 是否用索引，都要看字段选择性、索引情况、统计信息和 MySQL 版本。排查时应以 `EXPLAIN` 和真实执行情况为准。

## 八、深度分页

深度分页是常见性能问题：

```sql
select *
from orders
order by id
limit 1000000, 10;
```

数据库需要先找到前面的一百万行，再丢弃它们，只返回后面十行。偏移量越大，成本越高。

更好的做法是基于上一页最后一个位置继续查：

```sql
select *
from orders
where id > 1000000
order by id
limit 10;
```

如果排序条件不止一个，需要把游标条件写完整：

```sql
select id, create_time, amount
from orders
where status = 1
  and (
    create_time < :last_create_time
    or (create_time = :last_create_time and id < :last_id)
  )
order by create_time desc, id desc
limit 20;
```

这个方式通常叫 keyset pagination 或 seek pagination，适合“下一页”场景。不适合任意跳到第 N 页，但能显著降低深分页的扫描成本。

## 九、索引设计建议

设计索引时，按这个顺序思考：

1. 这条 SQL 的过滤条件是什么。
2. 哪些字段选择性高。
3. 是否需要排序或分组。
4. 是否能用联合索引同时覆盖过滤和排序。
5. 是否能减少回表。
6. 写入频率是否能承受额外索引维护成本。

索引不是越多越好。每多一个索引，`insert`、`update`、`delete` 都要额外维护它。读多写少的表可以适当多建，写多读少的表要更克制。

一句话总结：**索引的价值是减少扫描和排序成本，代价是存储空间和写入维护成本。真正好的索引，一定是贴着业务查询长出来的。**
