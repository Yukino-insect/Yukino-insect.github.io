多数据源是指一个应用同时连接多个数据库、多个数据库实例，或者同一类数据库的多个逻辑库。它能解决隔离、扩展、迁移、读写分离等问题，也会显著增加事务、路由和排查复杂度。

不要把多数据源当作普通性能问题的第一选择。很多时候，索引、SQL、缓存、归档和表结构优化还没做完，直接拆数据源只是在制造更大的问题。

## 一、常见场景

多数据源常见于：

1. 读写分离：写走主库，读走从库。
2. 业务隔离：用户库、订单库、报表库分开。
3. 多租户：不同租户使用不同数据库。
4. 新旧系统迁移：应用同时访问旧库和新库。
5. 异构系统集成：同时访问 MySQL、PostgreSQL、Oracle 等。
6. 分库分表：按用户、订单、区域或时间分散数据。

这些场景的共同点是：数据边界发生了变化。只要边界变化，事务、查询和运维都会跟着变化。

## 二、常见实现方式

Spring 项目里，多数据源通常有几类实现：

1. 配置多个 `DataSource`。
2. 使用 `AbstractRoutingDataSource` 按上下文动态路由。
3. 用注解标记当前方法应该走哪个数据源。
4. 每个数据源配置独立的事务管理器。
5. 读写分离场景使用数据库代理或中间件。

动态路由的核心思想是：应用调用的仍然是一个代理数据源，代理数据源根据上下文 key 决定把请求交给哪个真实数据源。

简化模型：

```text
业务代码
   |
RoutingDataSource
   |
   +-- masterDataSource
   +-- slaveDataSource
   +-- reportDataSource
```

路由 key 通常放在线程上下文里，例如 `ThreadLocal`。这也意味着跨线程时要格外小心，线程切换后上下文可能丢失。

## 三、事务风险

单数据源事务只需要一个连接即可保证提交和回滚。

多数据源下，一个业务操作可能同时写两个库：

```text
insert order_db.orders 成功
insert stock_db.stock_log 失败
```

如果只是普通本地事务，通常只能保证其中一个数据源回滚，不能保证两个库整体原子提交。

常见风险：

1. 事务管理器绑定错数据源。
2. 方法里动态切换数据源，导致同一事务中拿到多个连接。
3. 读写分离下，写后立即读走从库，读到旧数据。
4. 跨库 join 无法直接执行，需要应用层聚合。
5. 故障排查要同时看多个数据库日志和链路。

## 四、跨库一致性方案

跨数据源写入要先判断一致性要求。

强一致可以考虑：

1. XA 事务。
2. JTA / 2PC。
3. 数据库或中间件提供的分布式事务能力。

但强一致通常会降低性能和可用性，也会增加运维复杂度。

更多业务场景会使用最终一致：

1. 可靠消息。
2. 本地消息表。
3. Outbox pattern。
4. 补偿任务。
5. 幂等接口。
6. 对账修复。

最终一致不是“放弃一致性”，而是把一致性从同步事务改成可重试、可补偿、可观测的流程。

## 五、读写分离的延迟

读写分离最常见的问题是主从延迟。

用户刚提交订单：

```text
写主库成功
立刻查订单详情
读请求路由到从库
从库还没同步到这条数据
```

用户就会看到“刚提交的数据不存在”。

常见处理方式：

1. 写后短时间内强制读主库。
2. 对强一致接口直接读主库。
3. 根据主从延迟指标动态选择是否读从库。
4. 对弱一致页面接受短暂延迟。
5. 用缓存或业务状态兜住用户体验。

读写分离不是自动提升一切性能。它提升的是读扩展能力，同时引入一致性延迟。

## 六、实践建议

引入多数据源前，先确认：

1. 数据边界是否真的清晰。
2. 是否允许跨库最终一致。
3. 是否存在必须跨库强事务的核心流程。
4. 路由规则是否可观测、可测试。
5. 故障时是否知道哪些请求会受影响。
6. 数据迁移和回滚方案是否准备好。

代码层面建议：

1. 同一事务内尽量不要切换数据源。
2. 每个数据源的事务管理器命名清楚。
3. 数据源路由注解只放在明确的服务边界。
4. 跨库写入必须有幂等和补偿。
5. 读写分离接口要标注一致性要求。

## 七、总结

多数据源能解决隔离和扩展问题，但代价是事务、路由、排查和运维复杂度明显上升。

使用它之前，先把业务边界想清楚；使用它之后，就不要再假装所有数据还在一个本地事务里。数据库不会因为注解写得漂亮，就自动跨库保持原子性。
