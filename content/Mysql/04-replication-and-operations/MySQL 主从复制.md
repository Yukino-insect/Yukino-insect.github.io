MySQL 主从复制用于把主库的数据变更同步到从库。它常用于读写分离、备份、容灾、数据分析和迁移。

主从复制不是自动高可用。复制只解决“数据怎么过去”，不自动解决“谁来检测故障、谁来切换主库、应用怎么路由”。完整高可用至少还需要故障检测、主从切换和流量切换。

## 一、复制的基本链路

典型复制链路如下：

```text
主库写入
  |
记录 binlog
  |
从库 I/O 线程拉取 binlog
  |
写入 relay log
  |
从库 SQL 线程重放 relay log
  |
从库数据更新
```

核心组件：

| 组件 | 作用 |
| ---- | ---- |
| binlog | 主库记录数据变更 |
| relay log | 从库保存从主库拉取到的日志 |
| I/O 线程 | 从主库读取 binlog |
| SQL 线程 | 在从库重放日志 |

## 二、binlog 格式

常见 binlog 格式：

| 格式 | 说明 |
| ---- | ---- |
| STATEMENT | 记录 SQL 语句 |
| ROW | 记录每行数据的变更 |
| MIXED | 根据情况在语句和行之间切换 |

生产中通常更推荐 `ROW`，因为它记录的是行级变更，更容易避免某些非确定性 SQL 在从库重放时结果不同。

配置示例：

```ini
[mysqld]
server-id=1
log_bin=mysql-bin
binlog_format=ROW
```

## 三、搭建示例

主库配置：

```ini
[mysqld]
server-id=1
log_bin=mysql-bin
binlog_format=ROW
```

创建复制账号：

```sql
create user 'repl'@'%' identified by 'repl_password';
grant replication slave on *.* to 'repl'@'%';
flush privileges;
```

查看主库日志位置：

```sql
show master status;
```

示例输出：

```text
+------------------+----------+--------------+------------------+
| File             | Position | Binlog_Do_DB | Binlog_Ignore_DB |
+------------------+----------+--------------+------------------+
| mysql-bin.000001 |     1546 |              |                  |
+------------------+----------+--------------+------------------+
```

从库配置：

```ini
[mysqld]
server-id=2
relay-log=relay-log-bin
```

设置复制源：

```sql
change master to
  master_host='主库IP',
  master_user='repl',
  master_password='repl_password',
  master_log_file='mysql-bin.000001',
  master_log_pos=1546;
```

启动复制：

```sql
start slave;
```

查看状态：

```sql
show slave status\G
```

MySQL 8.0 新版本中也提供了 `SOURCE` / `REPLICA` 相关语法，用来替代旧的 `MASTER` / `SLAVE` 命名。实际项目里要以当前 MySQL 版本为准。

## 四、复制模式

### 1. 异步复制

主库提交事务后立即返回客户端，不等待从库接收或应用日志。

优点是性能好，缺点是主库宕机时，如果从库还没同步到最新 binlog，可能丢失数据。

### 2. 半同步复制

主库提交事务时，至少等待一个从库确认收到日志后再返回客户端。

它降低了主库宕机导致数据丢失的概率，但不要求从库已经应用完成。因此读从库仍可能有延迟。

### 3. 组复制

MySQL Group Replication 用于更强的一致性和高可用场景。它不只是传统主从复制，而是基于组成员、事务认证和一致性协议来协调多个节点。

是否使用组复制，要结合运维能力、延迟要求和故障切换策略评估。

## 五、主从延迟

主从复制常见问题是延迟：

```text
主库已经写入
从库还没重放完成
应用读从库
读到旧数据
```

造成延迟的原因可能包括：

1. 主库写入量太大。
2. 从库机器性能不足。
3. 大事务阻塞重放。
4. 从库 SQL 线程重放慢。
5. 网络抖动。
6. 从库上跑了重查询，占用资源。

排查时看：

```sql
show slave status\G
```

重点关注复制线程状态、错误信息、延迟指标和 relay log 应用进度。

## 六、读写分离一致性

读写分离不是 MySQL 自动完成的。MySQL 提供复制能力，但“写请求走主库、读请求走从库”通常由应用、多数据源框架、中间件或数据库代理实现。

写后立刻读的接口要注意一致性：

1. 支付、下单、权限变更等强一致接口读主库。
2. 写操作后短时间内按用户维度强制读主库。
3. 延迟可接受的列表、报表读从库。
4. 结合主从延迟动态降级。

如果业务刚写完就必须看到最新结果，读从库就不合适。这个结论并不华丽，但很有用。

## 七、故障切换

完整高可用方案至少包括：

```text
1. 数据复制
2. 故障检测
3. 主库选举或提升
4. 应用流量切换
5. 旧主恢复后的数据处理
```

MySQL 原生复制本身不等于自动故障切换。生产常见方案会配合：

1. MHA、Orchestrator 等管理工具。
2. Keepalived、ProxySQL、HAProxy 或云数据库代理。
3. 云厂商 RDS 的高可用能力。
4. 应用层动态数据源。

主库故障后，最麻烦的通常不是“把从库升主”，而是确认旧主是否还有未同步数据，以及应用是否已经全部切到新主。

## 八、常见实践建议

1. 生产优先使用 `ROW` 格式 binlog。
2. 控制大事务，避免从库长时间追日志。
3. 从库不要承担过重的分析查询，必要时单独建报表库。
4. 关键业务写后读主。
5. 监控复制线程、延迟、错误和磁盘空间。
6. 定期演练故障切换。
7. 备份不能只依赖从库，仍要有可恢复的备份策略。

## 九、主从复制和分库分表

主从复制解决的是同一份数据的副本同步。分库分表解决的是数据拆分和扩展。二者不是一个问题。

主从复制：

```text
同一份数据 -> 多个副本
```

分库分表：

```text
一份大数据 -> 按规则拆到多个库表
```

它们可以同时存在，但不要混为一谈。读写分离、复制延迟、分片路由、跨库事务，是不同层面的复杂度。

## 十、总结

MySQL 主从复制的核心是 binlog、relay log 和从库重放。它能提供数据副本和读扩展能力，但会带来延迟和故障切换问题。

真正的生产方案不能只问“复制开没开”，还要问：延迟怎么看，故障谁切，写后读走哪里，旧主回来怎么办。能回答这些问题，主从复制才算真的进入工程状态。
