数据库学习很容易落入两个极端：要么只背概念，把“范式、事务、索引”当成互不相干的名词；要么只会拼接 `SELECT`，一遇到并发扣库存、慢查询或数据不一致便无从判断。本课程以 Silberschatz、Korth、Sudarshan 的《Database System Concepts》（第七版）的常见脉络为骨架，但不按教材目录逐页复述，而是挑出在学校、面试和实际开发中最常用的部分，建立一条从**数据如何表示**到**系统如何可靠运行**的连续路径。

全程使用一个在线书店作为案例。读者会看到同一个需求如何先被描述为实体和联系，再被转换为关系表、用 SQL 查询与更新，并最终延伸到索引、事务、恢复和运维。这样学习的好处是，每一项技术都有明确要保护的业务事实，而不是孤零零的语法规则。

## 课程范围与最终目标

课程主要面向以 MySQL 等关系型数据库为起点的初学者，也适合曾经写过简单 SQL、但希望补齐设计与原理的人。完成后，你应能做到以下几件事：

- 把“商品、作者、订单、库存”这类自然语言需求建模为边界清楚的表和约束；
- 写出可解释的查询、分组统计、子查询、连接和数据修改语句；
- 理解主键、外键、范式与索引为什么存在，避免以“能跑”为唯一标准；
- 区分并发控制、事务隔离、日志恢复和高可用分别解决什么问题；
- 面对 Redis、Elasticsearch、ClickHouse 等系统时，先判断数据访问模式，再决定是否需要它们。

本课程不会把某一家数据库的每个管理命令都当作重点。例如，具体云厂商控制台、极少使用的 SQL 方言差异、复杂分布式共识算法不会在正文中展开。它们重要，但应建立在关系模型、查询处理与事务语义已经稳固的前提上。

| 学习层次 | 需要回答的问题 | 在线书店中的例子 |
| -------- | -------------- | ---------------- |
| 建模 | 应保存哪些事实、事实之间如何关联？ | 一本书可由多位作者合著 |
| 查询 | 如何从保存的事实得出结果？ | 找出近 30 天销量最高的图书 |
| 设计 | 如何避免矛盾、重复和难以维护？ | 订单创建后保留当时成交价 |
| 运行 | 故障和并发下如何仍然正确？ | 支付成功与扣库存不能只完成一半 |

## 统一案例：一个可逐步扩展的在线书店

先约定几条简化的业务规则，之后的文章都会在此基础上增加细节：

- 图书有 ISBN、书名、定价和当前库存；一本图书可以有多个作者。
- 一个用户可以创建多个订单；一张订单至少有一个订单项。
- 订单项记录购买数量与**下单时的成交单价**，不能只在查询时读取图书当前价格。
- 支付成功时必须同时写入订单状态并减少库存；库存不足则整笔下单失败。

这些规则里已经包含了建模、查询与事务问题。比如“订单项存成交价”看似重复，其实是刻意保留历史事实：图书后来调价，旧订单的金额仍应不变。相反，若把作者姓名直接复制到每本书和每个订单项中，则会带来改名时多处不一致的风险。数据库设计并非机械地消除一切重复，而是分辨**不应重复的事实**与**必须留存的业务快照**。

```mermaid
flowchart LR
    R[业务需求] --> M[概念模型：ER]
    M --> S[关系模式与约束]
    S --> Q[SQL 查询与更新]
    Q --> P[索引与执行计划]
    P --> T[事务、并发与恢复]
    T --> O[备份、复制与运行维护]
```

## 建议的学习顺序

第一部分先回答“数据库是什么、为什么能让程序与数据分离”。接着学习关系模型和关系代数；关系代数不是为了手算符号，而是 SQL 的思维底座。第三步从 ER 图转换到关系模式，之后再进入 SQL：表定义、增删改查、连接、聚合与嵌套查询。表、键、外键和约束会在这些步骤中反复出现：它们共同决定一个模式是否能表达业务规则，是否应保留历史快照。

课程的后半段从“语句写对”走向“系统在压力下仍正确”：索引与查询优化解释为什么同一句 SQL 会有截然不同的速度；事务与并发控制解释两个用户同时购买最后一本书时该如何处理；恢复、复制、备份和权限则解决机器或人为错误之后如何继续服务。建议按编号阅读。前文的概念会在后文反复出现，而不是一次用完便被遗忘。

## 与现有技术文章如何配合

站点中已有的 MySQL 零散文章更适合在你遇到某个实际问题时按主题查阅，例如特定查询写法、索引细节、锁与复制配置。本课程的职责是提供由浅入深的主线；后续遇到 MySQL 专有行为时，再回到那些文章查实现细节。换言之，课程负责“为什么、何时、基本怎样做”，专题文章负责“某个版本中怎样精确配置和排障”。

Redis、Elasticsearch、ClickHouse 也不是关系数据库的替代品清单。Redis 擅长低延迟缓存、会话和部分原子操作，却不能因为它快就自动取代订单真相；Elasticsearch 擅长全文检索，适合按书名、简介和作者名搜索；ClickHouse 擅长分析型聚合，适合报表，但并非高频订单事务的默认落点。一个常见架构是让关系数据库保存订单、支付和库存的权威状态，再经可靠同步把可搜索文本写入 ES、把聚合分析数据写入 ClickHouse，并以 Redis 缓存热点读。

```text
用户下单 -> 关系数据库：订单与库存的权威记录
图书搜索 -> Elasticsearch：倒排索引与相关性排序
热门书页 -> Redis：可失效、可重建的缓存
运营报表 -> ClickHouse：大规模扫描与聚合
```

这里的关键词是“权威数据源”。缓存和索引常常可以重建，订单事实一旦错误却很难补救。因此，先学会用关系约束与事务守住真相，再学习围绕它扩展能力，会比把每种存储都当作数据库万能替身稳妥得多。

## 前置知识与学习方法

你只需会基本编程、理解变量和集合，并能安装一个数据库客户端即可。没有高等数学要求；关系代数中的“集合”只需理解筛选、取列、合并和匹配。准备一个 MySQL 8.0 实例会更有帮助，但文章中的标准概念不会依赖某个 GUI 工具。所有示例 SQL 均尽量采用清晰、常见的写法，涉及方言时会明确说明。

学习时不要只复制执行。每看到一条 SQL，都试着回答三件事：输入的是哪几张关系、每一步保留了哪些行和列、结果是否符合业务规则。对更新语句尤其要先用等价 `SELECT` 验证影响范围；对设计决定则追问“若作者改名、图书调价、支付失败，会不会产生矛盾”。这种反问比记住更多命令更能形成可靠的数据库直觉。

## 本篇小结

- 课程沿着“建模—查询—设计—可靠运行”的顺序组织，统一使用在线书店案例。
- 关系数据库首先承担业务事实的权威保存，其他数据系统按访问模式补充能力。
- SQL 只是数据库学习的一部分；模式、约束、事务和恢复共同决定系统是否可信。
