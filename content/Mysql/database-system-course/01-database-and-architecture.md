“把数据存进数据库”听起来像一个动作，实际上至少包含三层含义：业务要记录什么事实、软件如何表达和访问这些事实、系统如何在多人同时使用与机器故障时保护它们。本篇建立这三个层次的地图。理解它以后，表、SQL、索引和事务才不会变成彼此割裂的技巧。

仍以在线书店为例：用户看到的是“购买《数据库系统概念》”；应用程序看到的是创建订单的接口；数据库则需要长期、可共享地保存用户、图书、订单、库存及它们的约束。真正困难的并非把一个 JSON 写到磁盘，而是确保“订单项属于某张订单”“库存不能变为负数”“工作人员修改价格不会改写历史成交额”等规则能持续成立。

## 数据、数据库与 DBMS

**数据**是可被解释的事实记录，例如 ISBN、订单创建时间、购买数量；脱离语境的字节并不自动成为有意义的数据。**数据库**是一组相互关联、持久保存的数据集合；它强调共享和组织，而不只是许多文件放在同一目录。**数据库管理系统**（DBMS）则是管理这些数据的软件，如 MySQL、PostgreSQL、Oracle。应用通过 DBMS 定义结构、读写数据、控制权限，并在故障后恢复。

完整的**数据库系统**还包括数据本身、DBMS、应用程序、硬件、运维规则以及使用它的人。把 MySQL 安装好不等于系统已经可靠：没有备份策略、账户权限和数据质量约束，业务仍可能在一次误操作后失去关键事实。

| 概念 | 在线书店中的对应物 | 不应混淆的点 |
| ---- | ------------------ | ------------ |
| 数据 | `978730...`、订单状态、库存数 | 单条值不等于完整业务含义 |
| 数据库 | 用户、图书、订单等相互关联的记录 | 不是任意文件的集合 |
| DBMS | MySQL 服务器 | 不是业务前端或商城程序 |
| 数据库系统 | DBMS 加数据、应用、人员与流程 | 可靠性由整体共同决定 |

文件也能保存数据，为什么还需要 DBMS？当单机脚本只写一个私有配置文件时，普通文件往往足够；但多个进程共享订单数据时，DBMS 提供了受控并发、查询语言、约束、崩溃恢复、访问控制和备份接口。将这些能力散落在每个应用程序中，会造成重复实现和不一致的规则。

## 数据模型：从现实到可操作的表示

现实世界不会天然长成表。所谓**数据模型**，是描述数据结构、关系、约束和操作的一套抽象工具。它决定我们用什么单位看待数据，以及什么变化被允许。概念设计阶段常用 ER 模型表达“用户下订单”；逻辑设计阶段常用关系模型表达表、行、列与键；物理层则关心页、索引和文件如何落盘。

同一个书店事实可有不同模型视角。概念层说“订单由用户创建，订单包含订单项”；关系层会把它拆为 `customer`、`book_order`、`order_item` 等关系；文档模型则可能把订单项嵌入一份 JSON。它们不是谁更先进，而是约束、查询、更新频率和扩展方式不同。课程将以关系模型为主，因为它有成熟的声明式查询、完整性约束与事务语义。

```text
业务事实：张三购买两本《关系数据库》
        ↓ 概念模型
客户 --创建--> 订单 --包含--> 订单项 --购买--> 图书
        ↓ 关系模型
customer / book_order / order_item / book 四张相互引用的表
        ↓ 物理实现
数据页、B+ 树索引、日志文件与备份
```

注意“模型”不是表格软件的同义词。一张只有列名的表仍可能无法表达关键规则。例如 `order_item` 缺少订单外键时，数据库无法阻止一条孤立订单项；`stock` 只是普通整数而未受更新事务保护时，两个并发支付仍可能超卖。结构、约束和操作语义必须一起考虑。

## 三层模式与数据独立性

经典数据库架构把数据描述分为外模式、概念模式和内模式。它们分别面向不同的观察者：

| 层次 | 描述对象 | 书店示例 |
| ---- | -------- | -------- |
| 外模式 | 某类用户可见的数据视图 | 客服只看订单号、状态和收货信息 |
| 概念模式 | 全库的逻辑结构和约束 | 用户、订单、订单项及主外键关系 |
| 内模式 | 数据在存储介质上的组织 | 索引、数据页、分区、压缩和日志 |

外模式不等于应用界面，但它可借助 SQL 视图向不同角色隐藏不必要字段；概念模式也不是某个 ORM 的实体类，而是数据库自身认可的整体逻辑定义。内模式通常由 DBMS 管理，开发者会在索引和分区设计中部分参与，却不需要手工指定每条记录的磁盘地址。

三层划分追求的是**数据独立性**。物理数据独立性表示，给 `book` 增加索引、移动数据文件或更改存储结构时，正常情况下不必改订单业务 SQL。逻辑数据独立性表示，在概念模式演进时，已有外部视图可通过兼容视图维持稳定。例如，将地址从 `customer` 拆成 `customer_address` 后，旧的客服查询可以暂时读取一个视图，而不是让所有调用者同时崩溃。

```sql
-- 拆表迁移后，给旧报表提供兼容的外模式视图
CREATE VIEW customer_contact AS
SELECT c.customer_id, c.name, a.city, a.detail
FROM customer AS c
LEFT JOIN customer_address AS a
  ON a.customer_id = c.customer_id
 AND a.is_default = TRUE;
```

视图不是“永远不用改代码”的魔法。若原字段语义已改变，例如一个客户允许多个地址而旧接口只支持一个，系统仍需明确默认规则并安排迁移。数据独立性减少无关变更的传播，并不能抹去真实的业务语义变化。

## 谁在使用数据库

数据库用户不只包括写 SQL 的开发者。不同角色需要的权限和关注点不同：

- **终端用户**通过商城页面下单，通常不会接触表名；他们要求结果正确、响应及时。
- **应用开发者**编写接口、SQL 或 ORM 映射，应理解事务边界与约束，不能把校验只留在前端。
- **数据分析人员**读取经过治理的数据做销量、转化和库存分析，常需要只读权限与脱敏视图。
- **数据库管理员（DBA）/平台工程师**负责账户、备份、监控、容量、复制和故障恢复。
- **数据架构或领域人员**定义术语与规则，例如“取消订单是否释放库存”“收入按支付还是发货确认”。

这也是为什么最小权限原则很重要。运营报表账号不应拥有 `DROP TABLE` 权限；应用连接不应使用 root；支付服务也只应写它负责的订单字段。权限不是对可信员工的冒犯，而是将偶然错误和被盗凭据的损害范围限制在必要边界内。

## 关系数据库与 NoSQL 的定位

“NoSQL”是多种非关系模型的统称，并非单一产品或“没有 SQL”的严格定义。键值、文档、宽列、图与搜索引擎各有擅长的访问方式。选择时先问数据的权威性、关联查询、事务要求、读写模式和规模，而不要先按流行度选技术。

| 需求 | 优先考虑 | 原因 |
| ---- | -------- | ---- |
| 订单、支付、库存扣减 | 关系数据库 | 关联、约束和多行事务是核心 |
| 热门图书详情短时缓存 | Redis | 低延迟、过期与缓存数据结构方便 |
| 书名与简介全文检索 | Elasticsearch | 倒排索引、分词和相关性排序 |
| 长期行为日志的聚合报表 | ClickHouse | 面向分析的列式扫描与聚合能力强 |

把订单先写 Redis、再异步“也许”写入 MySQL，通常会把缓存误当作账本；把所有字段塞入文档数据库，也会在复杂关联、唯一性和跨文档一致性上付出代价。另一方面，把模糊全文检索硬塞给关系数据库也不一定经济。较常见的实践是：以关系数据库保存权威交易数据，使用可靠同步或消息机制派生搜索、缓存和分析副本，并明确副本存在延迟。

## 本篇小结与下一步

- 数据库系统的价值在于让共享的业务事实得到结构化、受约束且可恢复的管理。
- 数据模型连接现实需求和具体实现；ER、关系模型和物理存储分别服务不同抽象层。
- 三层模式的目标是数据独立性：让存储或部分逻辑变化不必无谓地击穿所有调用方。
- 关系数据库适合作为高一致性交易事实的核心，但应与缓存、检索、分析系统按职责协作。
