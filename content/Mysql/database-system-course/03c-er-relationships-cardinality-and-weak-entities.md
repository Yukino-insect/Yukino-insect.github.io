E-R（Entity-Relationship，实体—联系）模型不仅要说明“系统中有哪些对象”，还要准确描述对象之间的业务事实。例如，教师和学生之间可以存在 `advisor`（指导）联系；课程和课程班次之间存在“开设”联系；同一实体集还可能通过不同角色参与同一个联系。

本篇从联系集的数学含义开始，逐步解释联系属性、递归联系、基数约束、参与约束和弱实体集，并说明这些概念如何落到关系数据库中的主键、外键和唯一约束上。读完后，应该能够看懂常见的 Chen E-R 图，也能够把图中的约束翻译成表结构。

## 实体、实体集、联系与联系集

### 实体和实体集

**实体（entity）**是现实世界中一个可以区分的对象。例如：

- 编号为 `22222` 的教师 Einstein；
- 编号为 `44553` 的学生 Peltier；
- 编号为 `CS101` 的课程。

同类实体的集合称为**实体集（entity set）**。`instructor` 表示所有教师组成的实体集，`student` 表示所有学生组成的实体集，`course` 表示所有课程组成的实体集。E-R 图中的矩形通常表示实体集，而不是某一条具体记录。

### 联系和联系集

一个或多个具体实体之间的一次关联称为**联系（relationship）**。例如：

```text
44553 (Peltier) —— advisor —— 22222 (Einstein)
```

这表示学生 Peltier 与教师 Einstein 之间存在一次指导关系。

同类联系的集合称为**联系集（relationship set）**。所有学生和教师之间的指导关系组成 `advisor` 联系集。可以用下面的层次来区分这些概念：

| 层次 | 含义 | 示例 |
| --- | --- | --- |
| 实体 | 一个具体对象 | 学生 `44553` |
| 实体集 | 同类实体的集合 | `student` |
| 联系 | 一次具体关联 | Peltier 由 Einstein 指导 |
| 联系集 | 同类联系的集合 | `advisor` |

## 联系集的数学表示

一个联系集可以看作若干实体集笛卡尔积中的一个子集。对于二元联系，可以写成：

```text
advisor ⊆ student × instructor
```

其中每一条联系是一个元组：

```text
(44553, 22222) ∈ advisor
```

这句话表示：编号为 `44553` 的学生与编号为 `22222` 的教师之间存在 `advisor` 联系。

更一般地，n 元联系集可以表示为：

```text
R ⊆ E1 × E2 × ... × En
```

也就是说，每个联系实例都是一个 n 元组，元组的第一个元素来自 `E1`，第二个元素来自 `E2`，依此类推。元组中元素的顺序由联系定义决定，而不是由图上实体摆放的左右位置决定。

## 联系属性：属性可以属于联系

实体的属性描述对象自身的特征，例如：

```text
instructor.name
instructor.salary
student.name
student.tot_cred
```

但有些属性描述的是实体之间的关系。例如，学生开始接受某位教师指导的日期，应该写在 `advisor` 联系上：

```text
student —— advisor —— instructor
                         |
                       date
```

`date` 不能简单地放进 `student`，因为同一个学生可能先后有不同导师；也不能放进 `instructor`，因为一个教师指导不同学生的开始日期可能不同。它依赖的是“某个学生与某个教师的组合”，所以是**联系属性（relationship attribute）**。

同理，学生选修某个课程班次后获得的 `grade` 也属于 `takes` 联系：

```text
student —— takes —— section
                       |
                     grade
```

同一学生在不同课程中的成绩不同，同一课程班次中不同学生的成绩也不同。`grade` 只有在确定了学生和课程班次之后才有意义。

判断属性归属时，可以问：

> 这个值只由一个实体决定，还是必须由两个或多个实体的组合才能决定？

如果必须依赖实体组合，它通常应该建模为联系属性。

## 角色与递归联系

一个联系中的实体集不一定互不相同。同一个实体集可以多次参与同一个联系，这称为**递归联系（recursive relationship）**或**自关联**。

课程先修关系就是典型例子：

```text
course —— prerequisite —— course
```

两端都是 `course` 实体集，但两个位置的含义不同：

- `course_id`：当前课程，也就是需要先修课程的课程；
- `prereq_id`：先修课程，也就是必须提前学习的课程。

因此，下面的元组：

```text
(CS201, CS101)
```

表示 `CS201` 的先修课程是 `CS101`，而不是反过来。`course_id` 和 `prereq_id` 被称为**角色（role）**，用于说明同一个实体集在联系的不同位置上扮演什么语义角色。

在关系数据库中，这通常转换为两个都引用 `course` 的外键：

```sql
CREATE TABLE prerequisite (
    course_id VARCHAR(20) NOT NULL,
    prereq_id VARCHAR(20) NOT NULL,
    PRIMARY KEY (course_id, prereq_id),
    FOREIGN KEY (course_id) REFERENCES course(course_id),
    FOREIGN KEY (prereq_id) REFERENCES course(course_id)
);
```

角色名不能省略。若只写两个都叫 `course_id` 的列，数据库和读者都无法判断哪一列是当前课程，哪一列是先修课程。

## 基数约束：一方最多对应多少个

**基数（cardinality）**描述一个实体通过某个联系最多可以关联多少个对方实体。在本组 E-R 记法中：

- 从联系集指向实体集的箭头表示这一侧最多一个；
- 没有箭头的普通线表示这一侧可以有多个。

### 一对一联系

```text
instructor ← advisor → student
```

两边都有箭头，表示：

- 一个学生最多关联一个教师；
- 一个教师最多关联一个学生。

这是 `1:1` 联系。但“最多一个”不等于“一定有一个”，是否允许没有联系还要看参与约束。

### 多对多联系

```text
instructor — advisor — student
```

两边都是普通线，表示：

- 一个教师可以关联多个学生；
- 一个学生也可以关联多个教师。

这是 `M:N` 联系。`many` 表示允许多个，不意味着一定至少有两个；实际参与数量还可能是 0 或 1。

### 一对多联系

箭头只出现在一侧时，就是 `1:N` 或 `N:1`。例如：

```text
instructor → advisor — student
```

箭头指向 `instructor`，表示一个学生可以对应多个教师，而一个教师最多对应一个学生。判断时不要只背箭头方向，而要固定一侧实体，数它沿联系能找到多少个对方实体。

## 参与约束：实体是否必须参加

基数约束说明“最多多少个”，而**参与约束（participation constraint）**说明“至少多少个”。

### 完全参与

实体集与联系之间用双线表示**完全参与（total participation）**：实体集中的每个实体都至少参加一次该联系。

如果 `student` 到 `advisor` 是双线，就表示：

> 每个学生都必须有至少一名导师。

这不允许存在一个完全没有导师的学生。

### 部分参与

单线表示**部分参与（partial participation）**：实体集中的实体可以不参加该联系。

如果 `instructor` 到 `advisor` 是单线，就表示：

> 某些教师可以暂时没有指导任何学生。

因此，参与约束通常可以这样记忆：

```text
双线：至少参加一次
单线：可以一次也不参加
```

参与约束与基数约束是两个不同维度。例如“学生必须且只能有一个导师”需要同时满足：

- 双线：最少一个；
- 箭头：最多一个。

## 最小—最大基数 `l..h`

更精确的写法是在连线上标出 `l..h`：

- `l` 是最小参与次数；
- `h` 是最大参与次数。

常见组合如下：

| 表示 | 含义 | 解释 |
| --- | --- | --- |
| `0..1` | 可选且最多一个 | 可以没有，但不能超过一个 |
| `1..1` | 必须且只能一个 | 恰好一个 |
| `0..*` | 可选且数量不限 | 可以没有，也可以有多个 |
| `1..*` | 至少一个且数量不限 | 必须有一个或多个 |

在上一节的学生—导师例子中，如果学生一侧是完全参与并且有箭头，那么它的约束是 `1..1`；如果教师一侧是部分参与并且没有箭头，那么它的约束是 `0..*`。把双线看作最小值 `1`、单线看作最小值 `0`，把箭头看作最大值 `1`、普通线看作最大值 `*`，就能把图形翻译成数值范围。

## 弱实体集：依赖其他实体才能被识别

### 强实体与弱实体

强实体集拥有自己的主键，可以独立地在整个实体集中唯一标识实体。例如：

```text
course(course_id, title, credits)
```

`course_id` 可以单独确定一门课程。

弱实体集自身没有足够的信息形成全局唯一标识，必须依赖某个强实体的主键。课程班次 `section` 就是常见例子：

```text
section(sec_id, semester, year)
```

`sec_id` 只表示某门课程内部的班次编号。不同课程都可能有 `sec_id = 1`，不同学期也可能重复使用相同编号。因此，`section` 不能仅靠自己的属性被全局识别。

### 弱实体的完整标识

弱实体的完整标识由两部分组成：

```text
拥有者实体的主键 + 弱实体的判别属性
```

在课程—班次例子中：

```text
(course_id, sec_id, semester, year)
```

才是一个 `section` 的完整标识。例如：

```text
(CS101, 1, Fall, 2026)
```

表示课程 `CS101` 在 2026 年秋季的第 1 个班次。

### 弱实体的图形符号

在 Chen E-R 图中：

- 双矩形表示弱实体集；
- 弱实体的判别属性或部分键使用虚线下划线；
- 连接弱实体和拥有者的识别联系使用双菱形；
- 弱实体到识别联系通常是双线，表示每个弱实体必须依附于拥有者。

概念结构可以表示为：

```text
course  ——  sec_course  ——  section
强实体       识别联系          弱实体
```

`section` 不能脱离 `course` 独立存在。一个没有所属课程的“第 1 班”没有完整业务含义，因此每个 `section` 都必须参与 `sec_course` 识别联系。

### 转换为关系表

弱实体转换为关系表时，拥有者主键通常同时是弱实体的外键和主键的一部分：

```sql
CREATE TABLE course (
    course_id VARCHAR(20) PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    credits INT NOT NULL
);

CREATE TABLE section (
    course_id VARCHAR(20) NOT NULL,
    sec_id VARCHAR(20) NOT NULL,
    semester VARCHAR(20) NOT NULL,
    year INT NOT NULL,
    PRIMARY KEY (course_id, sec_id, semester, year),
    FOREIGN KEY (course_id) REFERENCES course(course_id)
);
```

这里的 `course_id` 同时承担两个角色：

- 作为外键，保证每个 `section` 都属于一门存在的课程；
- 作为联合主键的一部分，参与唯一标识 `section`。

这正是弱实体映射到关系模式后的典型结构。

## 如何把 E-R 图读成数据库约束

阅读一条 E-R 联系时，可以按下面的顺序检查：

1. 两端连接的是哪些实体集？它们是否实际上是同一个实体集的不同角色？
2. 联系自身是否有属性，例如 `date` 或 `grade`？
3. 箭头或最大值说明每个实体最多关联多少个对方实体？
4. 双线或最小值说明实体是否必须参加联系？
5. 是否存在双矩形弱实体？如果存在，它依赖哪个拥有者实体？
6. 弱实体的判别属性与拥有者主键如何组成完整主键？

转换到关系数据库后，常见对应关系是：

| E-R 概念 | 关系数据库实现 |
| --- | --- |
| 强实体主键 | `PRIMARY KEY` |
| 联系中的引用 | `FOREIGN KEY` |
| 一对多联系 | 在多的一侧保存一的一侧主键 |
| 多对多联系 | 单独的中间表 |
| 最小基数为 1 | 通常使用 `NOT NULL`，必要时配合额外约束 |
| 最大基数为 1 | `UNIQUE` 或唯一索引 |
| 弱实体 | 拥有者外键参与联合主键 |

需要注意，数据库外键可以保证“引用的对象存在”，但不一定自动保证“每个拥有者至少有一条子记录”。例如，要求每个订单至少有一条订单项，通常还需要事务逻辑、断言替代方案或应用层校验。E-R 图中的约束必须结合数据库实际支持的约束机制落地。

## 常见误解

### 把联系属性放进实体表

`grade` 不是学生的永久属性，`date` 也不是教师或学生的单独属性。它们依赖实体组合，应放在联系表或转换后的关联表中。

### 把箭头理解成“必须存在”

箭头只表示最大值为 1，不表示一定存在。是否至少有一个要看双线或最小值。`0..1` 与 `1..1` 都有箭头，但前者可缺失，后者不可缺失。

### 把弱实体等同于所有复合主键表

有复合主键的表不一定是弱实体。只有当实体的身份在语义上依赖拥有者及识别联系时，才具有弱实体含义。弱实体的关键不是“主键有多列”，而是“能否脱离拥有者独立被识别和存在”。

### 忽略递归联系中的角色

`course_id` 和 `prereq_id` 都引用 `course`，但语义完全不同。没有角色名，`(CS201, CS101)` 的方向就无法确定，数据库结构也难以正确表达业务规则。

## 小结

- 实体集描述对象的集合，联系集描述实体之间的关联集合。
- 联系可以有自己的属性；当属性依赖实体组合时，应归属于联系。
- 同一个实体集可以多次参与联系，每次参与都需要一个明确的角色。
- 箭头表示最大基数为 1，普通线表示最大基数为 `*`。
- 双线表示完全参与，单线表示部分参与；`l..h` 同时表达最小和最大参与次数。
- 弱实体没有完整的独立标识，必须依赖拥有者主键和自己的判别属性。
- 弱实体使用双矩形，判别属性使用虚线下划线，识别联系使用双菱形。
- 将 E-R 图转换为表时，应把这些语义落实为主键、外键、`NOT NULL`、`UNIQUE` 和中间表等数据库约束。
