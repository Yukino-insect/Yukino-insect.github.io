索引不是给慢 SQL 贴上的加速标签，而是一种额外维护的数据结构：它用更多空间和写入成本，换取更少的数据页访问。前一篇说明了页和缓冲池；本篇进一步回答优化器可以沿什么路径找到订单，以及怎样根据查询而不是直觉设计索引。示例以 MySQL 8 的 InnoDB 为参照，结构原理具有普遍性，具体实现和可用索引类型仍以产品文档为准。

## B+ 树：把有序键装进页层次

关系数据库最常用的通用索引是 **B+ 树**。它不是二叉搜索树：一个节点通常容纳许多有序键和子页指针，内部节点负责导航，叶子节点保存完整索引条目，并按键顺序相连。一次查找从根页逐层选择子页，最终抵达叶子；范围查询抵达起点后可沿叶子链表持续读取。这种高扇出、浅层结构很适合以页为单位的存储。

```text
                 [ 订单号 M | 订单号 T ]
                   /          |          \
            叶子页 A      叶子页 B      叶子页 C
       ... K,L,M  <---->  N,O,P,Q <----> R,S,T,U ...
```

“平衡”是 B+ 树的重要性质：正常查找不会因键值不同走到极深的分支。插入时某页放不下可能分裂，删除或更新也可能触发维护；所以索引并非只读结构。将随机且很长的字符串作为聚簇主键，可能扩大每个条目和二级索引中的主键引用，增加页分裂与缓存压力。主键选择还要考虑业务唯一性、生成方式和分布式需求，没有一个绝对通用的答案。

## 聚簇索引、二级索引与回表

InnoDB 将表数据组织在主键的聚簇索引叶子页中；若没有显式合适主键，行为会由引擎规则决定，因此应主动定义主键。二级索引的叶子条目含二级键以及定位主键记录所需的主键值。下面先保证订单号的业务唯一性：

```sql
ALTER TABLE customer_order
ADD CONSTRAINT uk_customer_order_no UNIQUE (order_no);

CREATE INDEX idx_order_customer_time
ON customer_order (customer_id, ordered_at);
```

查询仅需 `customer_id`、`ordered_at` 和 `order_id`，且这些值都可由二级索引条目取得时，优化器可能使用**覆盖索引**，不必再读取完整聚簇记录。若还要取 `status` 而它不在索引中，通常先从二级索引找到主键、再访问聚簇索引取整行，这一步常称为回表（或 key lookup）。InnoDB 二级索引已携带主键，并不意味着它自动覆盖每个未列入索引的列。

```sql
-- 可能由 idx_order_customer_time 覆盖（order_id 为主键）
SELECT order_id, ordered_at
FROM customer_order
WHERE customer_id = 42
  AND ordered_at >= '2026-10-01';

-- status 不在该索引中，可能需要再取聚簇记录
SELECT order_id, ordered_at, status
FROM customer_order
WHERE customer_id = 42
  AND ordered_at >= '2026-10-01';
```

覆盖是减少访问的一种可能路径，而不是把所有 `SELECT` 列都塞进宽索引的理由。过宽索引占用更多空间、降低缓冲池有效容量，也使每次写订单都必须维护更多页。

## 联合索引与最左前缀

联合 B+ 树按列的字典序排列。`(customer_id, ordered_at)` 先按客户分组，在同一客户内再按下单时间排序，因此适合“某客户在一段时间内的订单”。它可用于以 `customer_id` 开头的等值查找，也可在此基础上按 `ordered_at` 做范围扫描；单独只有 `ordered_at` 的条件却通常不能有效利用该有序前缀来直接定位一段连续索引范围。这就是常说的**最左前缀**，但它是排序结构的结果，不是死记规则。

```sql
-- 与 (customer_id, ordered_at) 的顺序匹配
SELECT order_id, ordered_at
FROM customer_order
WHERE customer_id = 42
  AND ordered_at >= '2026-10-01'
  AND ordered_at < '2026-11-01'
ORDER BY ordered_at;

-- 缺少 customer_id；是否使用该联合索引需要由代价和实现决定
SELECT order_id, customer_id, ordered_at
FROM customer_order
WHERE ordered_at >= '2026-10-01';
```

等值条件后遇到范围条件时，后续列往往不能再像连续等值前缀那样精确缩小范围或同时提供完整排序；优化器仍可能采用其他技巧，不能把简化口诀误读为“后列完全无用”。`ORDER BY` 能否避免额外排序还取决于排序方向、筛选条件、连接和所选索引。必须用执行计划验证。

## 从访问模式推导书店索引

索引应服务稳定、频繁且代价高的访问模式。假定书店有如下请求：按订单号查详情、用户订单列表按时间倒序、按订单关联全部订单项。可先从约束和连接键得到基础设计：

```sql
-- order_no 的唯一约束已经形成可查找的索引
CREATE INDEX idx_order_customer_time
ON customer_order (customer_id, ordered_at);

-- 从订单头连接/删除订单项，并按行号读取明细
CREATE INDEX idx_item_order_line
ON order_item (order_id, line_no);
```

若 `(order_id, line_no)` 同时就是 `order_item` 的主键或唯一键，就不应重复创建等价索引。设计前要盘点已有主键、唯一键和外键支持索引；MySQL/InnoDB 对外键所需索引有自己的规则，实际 DDL 和版本行为应核验。索引不是按“每个 WHERE 列各建一个”产生的：单列索引往往无法同时满足组合过滤、排序和连接，重复索引又会只增加写成本。

## 哈希与它的边界

哈希索引用哈希值定位桶，适合等值查找，例如严格按唯一令牌查缓存条目；它不保留原键的全局顺序，因此不天然适合 `BETWEEN`、前缀匹配、范围扫描和按键排序。哈希冲突也需要额外比较验证。不同产品支持范围不同：MySQL 8 的 InnoDB 常规持久化索引主要是 B+ 树，InnoDB 的自适应哈希是引擎内部优化，不是让应用用 `CREATE INDEX ... USING HASH` 任意设计的通用持久化结构；MEMORY 引擎有不同选项，但不应据此推断交易表的 InnoDB 行为。

对于 `WHERE order_no = ?`，B+ 树已能高效等值定位并兼顾排序和范围，通常没有必要为了“哈希更快”改变交易表设计。全文搜索、空间检索和特定分析索引也各有专门结构，应从查询语义出发，而不是一概套用 B+ 树或哈希。

## 维护成本与验证

每个 `INSERT`、`UPDATE`、`DELETE` 都必须同步维护受影响索引。更新被索引的订单状态或时间，可能同时改变多个索引页；写多读少的表上堆叠索引，吞吐和存储都会受损。唯一索引还要在写入路径检查冲突。索引选择因此是读性能、写放大、空间、备份恢复时间和运维复杂度之间的权衡。

建立前后应以真实或脱敏的代表性数据，比较扫描行数、返回行数、执行时间和写入影响。不要仅因 `EXPLAIN` 显示“用了索引”便判定成功：低选择性条件用索引可能仍读大量页；而优化器选择全表扫描也可能是合理代价。下一篇[SQL 执行计划与查询优化](10-query-execution-and-optimization.md)会系统说明如何读这些证据。

## 小结

- B+ 树用有序叶子页同时支持等值定位和范围扫描，索引也有分裂、空间和写入维护成本。
- InnoDB 的主键聚簇组织与二级索引回表影响读取局部性；覆盖索引只应为明确查询服务。
- 联合索引的最左前缀来自字典序，组合过滤和排序必须结合具体条件推导。
- 哈希主要服务等值访问，不能替代 B+ 树的范围与排序能力；MySQL/InnoDB 的可用实现要按产品事实理解。
- 用真实访问模式、现有约束和执行计划验证索引，而不是按列名机械建索引。
