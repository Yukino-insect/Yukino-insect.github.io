同一句 SQL 的逻辑结果是声明式的，执行方式却不唯一。数据库可以扫描 `order_item` 后再找订单，也可以先筛选少数订单再连接订单项；可以用索引范围扫描，也可以读取整表；可以在内存排序，也可以利用已有顺序。**优化器**的职责是在保持语义不变的前提下选择预计代价较低的物理计划。调优的起点不是“强迫它走某个索引”，而是弄清它实际做了什么、估计为什么偏差、结果集是否真的需要这么大。

本文以 MySQL 8 为实践参照，连接算法、成本模型和计划展示格式会随数据库产品、版本和配置变化。SQL 中的表、列仍来自在线书店；读者应在自己的版本和数据上执行，而不是把示例输出数字当成结论。

## 从 SQL 文本到结果的几个阶段

数据库通常经历解析、绑定/校验、重写、优化和执行。解析将文本变成语法树；绑定确认 `status` 属于哪张表、用户是否有权限；重写可能将视图展开或把等价表达式规整；基于代价的优化器枚举或搜索候选访问路径、连接顺序和算子；执行器按最终计划拉取并处理记录。这些阶段的划分是理解模型，具体实现可能交织或采用更多步骤。

```text
SQL 文本
  -> 解析与语义校验
  -> 逻辑重写（视图、谓词等）
  -> 候选计划与成本估算
  -> 物理算子：扫描、连接、排序、聚合
  -> 返回结果
```

常见物理算子可先这样理解：

| 算子 | 它做什么 | 书店中的例子 |
| ---- | -------- | ------------ |
| 表扫描 | 顺序读取许多数据页 | 全站月度销售报表 |
| 索引查找/范围扫描 | 在索引中定位一条或一段键 | 某客户本月订单 |
| 连接 | 按连接条件组合两个输入 | 订单与订单项 |
| 排序 | 产生 `ORDER BY` 所需顺序 | 最近订单优先展示 |
| 聚合 | 计算 `COUNT`、`SUM` 等 | 每本书销量 |

表扫描不等于错误：若报表确实需要大多数已支付订单，连续读取可能是最合理选择。索引扫描也不必然快：若条件选出大部分行又需要频繁回表，它可能比扫描更昂贵。

## 基于代价的选择为何会出错

优化器的**代价**是内部相对估算，不是用户可直接等同的毫秒。它通常综合预计读取量、CPU、排序、临时结构和连接次数等因素，选择最低估算计划。估算的根源是统计信息：表行数、索引键值分布、不同值数量以及某些实现中的直方图等。统计过期、数据强烈倾斜、列之间有关联却被按独立处理、参数值差异很大时，估算行数就可能偏离事实，进而选错连接顺序或访问路径。

例如 `status = 'PAID'` 在一个成熟书店中可能占多数，索引的选择性不高；而某个罕见错误状态可能只匹配极少订单。同一列的两个值不该想当然地享有相同计划。解决路径应是检查数据分布和统计信息、审查谓词可否利用索引、确认实际执行行数，再考虑修改索引或 SQL。先加 hint 往往把今天的偶然数据分布固化成明天的负担。

## 用 EXPLAIN 读访问路径

MySQL 8 可用 `EXPLAIN` 查看优化器选择的计划；`EXPLAIN FORMAT=TREE` 提供树形展示，`EXPLAIN FORMAT=JSON` 提供更多结构化信息。常规 `EXPLAIN` 不执行原查询，显示的是估算。MySQL 8.0.18 起提供 `EXPLAIN ANALYZE`，它会实际执行语句并报告各步骤的实际行数和时间等运行信息；因此不能拿可能修改数据的 DML 随意执行它，且它本身有测量开销。先在可控环境对只读查询使用最安全。

```sql
EXPLAIN FORMAT=TREE
SELECT o.order_id, o.ordered_at, SUM(oi.quantity) AS book_count
FROM customer_order AS o
JOIN order_item AS oi
  ON oi.order_id = o.order_id
WHERE o.customer_id = 42
  AND o.ordered_at >= '2026-10-01'
  AND o.ordered_at < '2026-11-01'
GROUP BY o.order_id, o.ordered_at
ORDER BY o.ordered_at DESC;

EXPLAIN ANALYZE
SELECT o.order_id, o.ordered_at, SUM(oi.quantity) AS book_count
FROM customer_order AS o
JOIN order_item AS oi
  ON oi.order_id = o.order_id
WHERE o.customer_id = 42
  AND o.ordered_at >= '2026-10-01'
  AND o.ordered_at < '2026-11-01'
GROUP BY o.order_id, o.ordered_at
ORDER BY o.ordered_at DESC;
```

阅读计划时不要只盯 `key` 是否非空。更有用的问题是：每张表采用什么访问类型？估计扫描多少行、实际扫描多少行？连接的外侧输入是什么、内侧被重复访问多少次？有没有额外排序、临时表或大范围聚合？预测行数与实际行数相差很大吗？显示 `Using filesort` 不表示一定把内容写进磁盘文件，它是 MySQL 对额外排序过程的术语；是否成为瓶颈仍需结合数据量和实际计划判断。

## 一个可解释的改写过程

需求是展示用户 42 最近一个月的订单及总件数。糟糕的写法常把日期列包进函数：

```sql
-- 对列求函数往往削弱 ordered_at 上普通索引的范围利用
SELECT o.order_id, COUNT(*) AS line_count
FROM customer_order AS o
JOIN order_item AS oi ON oi.order_id = o.order_id
WHERE o.customer_id = 42
  AND DATE(o.ordered_at) BETWEEN '2026-10-01' AND '2026-10-31'
GROUP BY o.order_id;
```

更直接的半开区间表达既避免了时间部分边界歧义，也更容易和 `(customer_id, ordered_at)` 的联合索引匹配。若订单项以 `order_id` 开头组织，连接可从筛出的少量订单开始，逐个匹配其明细：

```sql
SELECT o.order_id, o.ordered_at, COUNT(*) AS line_count
FROM customer_order AS o
JOIN order_item AS oi
  ON oi.order_id = o.order_id
WHERE o.customer_id = 42
  AND o.ordered_at >= '2026-10-01 00:00:00'
  AND o.ordered_at <  '2026-11-01 00:00:00'
GROUP BY o.order_id, o.ordered_at
ORDER BY o.ordered_at DESC;
```

这不是保证“必定使用某索引”的咒语。若该用户订单本来就很多、统计信息显示全表更便宜，或索引列顺序不同，计划仍可能变化。改写的价值是让谓词表达原本的时间范围，并减少不必要的计算；是否更好要由 `EXPLAIN ANALYZE` 与真实负载验证。

## 连接、排序与聚合的优化边界

连接本身不会“自动去重”。若一本书关联多个订单项，连接后有多行是正确事实；为掩盖连接条件或一对多关系错误而盲加 `DISTINCT`，可能引入昂贵去重且得到错误业务含义。应先确认连接键、关系基数和是否确实需要聚合。

排序与聚合需要处理输入集，先通过高选择性 `WHERE` 过滤常常比事后 `HAVING` 过滤更好；但依赖聚合结果的条件本来就应放 `HAVING`。`LIMIT` 也只有在排序语义正确时才可减少返回和排序工作，不能为了快而悄悄把“全部结果”改成前几条。查询只取需要的列，并不等于总是更快，却可减少网络传输、回表和应用内存压力。

当一个接口需要跨页、深翻大量历史订单时，`OFFSET` 很大可能仍要求数据库跳过前面大量有序记录。对于按稳定时间和主键顺序浏览的场景，可考虑键集分页（seek pagination）：将上一页末尾的 `(ordered_at, order_id)` 作为下一页边界，并据此设计索引。它改变了接口语义，必须明确排序稳定性与新增数据可见性，不能未经产品确认直接替换页码分页。

## 一套克制的排查顺序

1. 确认慢的是哪条 SQL、在何种参数和数据量下慢，先排除网络、锁等待和外部服务。
2. 记录计划与实际运行证据，比较预计行数、实际行数、扫描范围、排序和连接次数。
3. 检查谓词、连接条件、类型转换和时间边界是否表达了真实语义；先删掉无意义的 `SELECT *`、函数包列和错误去重。
4. 根据已验证的访问模式调整或合并索引，并衡量写入代价；更新统计信息或处理数据倾斜。
5. 在接近生产的数据与并发条件下复测，确认结果集、延迟和写入没有退化，再小范围发布和持续观察。

索引 hint、强制连接顺序和参数改动是最后的实现手段，不是通用答案。它们可能在数据增长、版本升级或统计改变后失效，使用时应记录前提并建立回归验证。

## 小结

- SQL 的逻辑含义固定，优化器根据统计与成本选择扫描、连接、排序和聚合等物理算子。
- `EXPLAIN` 显示估算计划；MySQL 8.0.18 及以后可用会实际执行的 `EXPLAIN ANALYZE` 比较估计与现实。
- 优化应从结果语义、谓词可用性、数据分布和实际扫描量入手，不要仅追求“走索引”。
- 先过滤、再连接/聚合只是常见方向；最终决定需要以计划和真实工作负载验证。
