事务承诺“要么全部发生，要么全部不发生”，但机器会在最不合适的时刻停止：进程崩溃、操作系统异常、电源中断都可能发生在订单写了一半时。恢复机制的任务不是假装故障不存在，而是让数据库在重新启动后回到一个符合事务语义的状态。本篇承接[磁盘、缓冲池与记录存储](08-storage-pages-and-buffer-pool.md)的页和 WAL 概念，并为后续事务、并发与高可用主题建立边界。

仍以在线书店为例。用户支付成功后，事务将订单状态改为 `PAID`、写入支付记录并扣减库存。若数据库在 `COMMIT` 前崩溃，这些改变不能部分留下；若已经确认提交，即使相关数据页尚未写回表文件，重启后也必须能恢复它们。恢复首先处理数据库内部一致性，不会自动撤销已经发往支付网关的外部请求。

## 三类稳定信息与 WAL

数据库运行时至少涉及三类状态：内存中的数据页与脏页、数据文件中的较旧页副本、描述修改的日志。**预写日志**（WAL）要求先让恢复该修改所需日志达到稳定存储，再允许相应数据页被写回；在提交语义要求的时点，也要先保证提交有关日志。这样即使数据文件暂时落后，系统仍能在日志中找回已提交变更。

```text
事务修改订单和库存
        ↓
缓冲池中的页变脏，同时生成日志记录
        ↓
日志满足持久化要求，事务提交
        ↓
数据页由后台在之后的时机刷回
```

不同数据库的日志记录格式不完全一样，但通常需要足够的信息来重做（redo）或撤销（undo）修改，并能识别事务是否完成。InnoDB 使用 redo log 支持崩溃恢复，也维护 undo 相关信息以支持回滚和多版本读取；实现中的日志序号、刷盘策略、双写保护等不应脱离具体版本和配置绝对化。可迁移的原理是：**数据页可以晚到，恢复所需的日志不能晚到。**

## Redo 与 undo：分别修复两种半成品

恢复面对两类不完整状态。第一类是“已提交但数据页没来得及写回”：需要依据日志**重做**（redo），使持久化页面至少包含已提交的改变。第二类是“未提交却已经把修改带进内存或写入部分页面”：需要**撤销**（undo），使这些影响消失。很多真实实现把页面更新、事务状态和版本信息结合处理；把它们概念上区分，能避免误以为 redo 单独就能保证原子性。

假设订单 90001 的付款事务做了三步：

```sql
START TRANSACTION;

UPDATE customer_order
SET status = 'PAID'
WHERE order_id = 90001 AND status = 'PENDING_PAYMENT';

INSERT INTO payment_record (payment_no, order_id, amount)
VALUES ('PAY-90001', 90001, 158.00);

UPDATE book
SET stock = stock - 2
WHERE book_id = 101 AND stock >= 2;

COMMIT;
```

若第三句后进程崩溃、`COMMIT` 从未完成，恢复必须让订单状态、支付记录和库存回到事务开始前的一致状态，而不是保留其中两项。若 `COMMIT` 已确认但 `customer_order` 对应的数据页尚未刷回，恢复则要把状态改动重新做到数据页上。真实下单还需检查每个条件更新影响的行数、保证 `payment_no` 唯一并处理外部支付幂等；恢复算法无法把逻辑错误变成正确业务。

## 检查点不是“立即备份”

随着运行时间增加，日志会不断增长；每次重启都从最早日志重放显然不经济。**检查点**（checkpoint）记录一个恢复可从较近位置开始的进度，并协调一部分脏页写回，让恢复不必回看无限久以前的历史。检查点不是把所有数据瞬间复制到另一个安全地点，也不是一个用户可随意等同于 `COMMIT` 的命令。它的具体触发条件、是否模糊检查点、如何与刷页协同均由实现决定。

```mermaid
flowchart LR
    A[日志持续追加] --> B[内存页持续变脏]
    B --> C[后台刷回部分数据页]
    C --> D[推进检查点]
    D --> E[崩溃后从较近日志开始恢复]
```

检查点减少的是**恢复工作量**，而非替代持久性。即使刚完成检查点，数据文件所在设备整体损坏、误执行 `DELETE` 并提交、火灾导致主机丢失，仍需要独立的备份和异地副本。

## 崩溃恢复、介质恢复与逻辑纠错

这几件事常被都称为“恢复”，实际边界不同：

| 场景 | 例子 | 主要依赖 |
| ---- | ---- | -------- |
| 进程/系统崩溃 | 断电、数据库异常退出 | WAL、事务状态、启动恢复 |
| 介质或实例丢失 | 数据盘损坏、整机不可用 | 经验证备份、日志/副本、恢复流程 |
| 逻辑错误 | 误删订单、错误程序批量更新 | 时间点恢复、审计、业务补偿 |
| 外部副作用不一致 | 付款成功但回调超时 | 幂等键、状态机、对账与补偿 |

备份提供一个较早但完整的基线；若保留连续日志，某些系统可在恢复基线后向前重放到指定时间点。是否支持、怎样操作、需要什么权限，强烈依赖产品和备份方案。最危险的做法是只看到备份文件存在就认为万事大吉：必须在隔离环境实际恢复，验证能启动、能查询、能达到 RPO（可接受的数据丢失量）与 RTO（可接受的恢复时长）。

复制也不是备份的同义词。若一个已提交的误删被复制到副本，副本会忠实地同步错误；而某些异步副本在故障瞬间还可能落后。副本提高可用性与读扩展，备份应承担可回到历史正确状态的职责，两者都不能省略。

## 对应用代码意味着什么

数据库报告提交成功之后，客户端仍可能因网络断开而没有收到响应。此时应用不能根据“超时”推断事务一定失败，更不能无条件再执行扣库存。应给下单、支付等命令设置业务幂等键（例如唯一 `request_no` 或 `payment_no`），重试时先查已持久化结果。数据库恢复保证的是它管理范围内的原子和持久事实；跨 HTTP、消息队列、邮件和支付渠道的协作还需要可靠事件、幂等消费者与补偿设计。

日志参数和刷盘策略会影响性能与可承受风险，生产变更必须理解其持久性语义、进行压测并有回滚方案。切勿为了降低延迟随意削弱刷盘保障，再在断电后惊讶于丢失已确认订单。另一方面，频繁的长事务会保留更多版本和日志、拖慢清理与恢复；事务应短小，并把外部慢调用移出持锁区间。

## 小结

- WAL 让恢复所需日志先于相应数据页持久化，使已提交变更可在脏页尚未刷回时重做。
- redo 处理“已提交但未落页”，undo 处理“未提交却留下影响”；二者共同服务原子性与持久性。
- 检查点缩短崩溃恢复路径，却不是备份，更不能抵御介质损坏或已提交的逻辑错误。
- 备份、日志、复制、审计和幂等业务设计各自解决不同故障，可靠系统必须明确它们的边界并定期演练。
