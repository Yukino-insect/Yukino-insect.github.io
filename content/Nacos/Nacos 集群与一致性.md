生产环境的 Nacos 通常以集群方式部署。集群要解决两件事：**高可用**和**数据一致性**。

高可用指的是某个 Nacos 节点故障时，整体服务仍然可以对外提供能力；一致性指的是多个 Nacos 节点对服务实例、配置、元数据等信息不能长期处于互相矛盾的状态。

## 一、为什么需要集群

单机 Nacos 适合本地学习或简单测试，但不适合生产。

原因很简单：

- 单机故障会导致注册中心和配置中心不可用。
- 单机重启期间客户端可能无法注册或拉取配置。
- 单机容量有限，无法承载大量实例和配置监听。
- 配置和服务治理是基础设施，不能轻易成为单点故障。

典型集群结构如下：

```text
                 应用 / 客户端
                      |
                      v
              SLB / Nginx / VIP
                      |
        +-------------+-------------+
        |             |             |
    Nacos-1       Nacos-2       Nacos-3
        |             |             |
        +-------------+-------------+
                      |
                外部数据库
```

客户端一般连接负载均衡入口，而不是写死某台 Nacos 节点地址。

## 二、部署要点

生产集群至少要关注：

- Nacos 节点数量，常见是 3 个节点起步。
- 节点之间网络互通，`cluster.conf` 中地址准确。
- 外部数据库可用，且本身具备高可用能力。
- 客户端访问统一入口，例如 SLB、Nginx、VIP 或 Kubernetes Service。
- 开启鉴权，配置合理的用户、角色和权限。
- 日志、监控、告警和备份都要齐全。

如果 Nacos 集群用了外部数据库，而数据库本身是单点，那只是把单点故障换了个地方摆着。它不会因为位置改变就变得高贵。

## 三、外部数据库的作用

Nacos 单机默认可以使用内置数据库，便于快速启动。但生产环境通常配置外部数据库，用于持久化配置、权限、用户、角色以及部分元数据。

常见配置项形式如下：

```properties
spring.datasource.platform=mysql
db.num=1
db.url.0=jdbc:mysql://mysql.example.com:3306/nacos_config?characterEncoding=utf8&connectTimeout=1000&socketTimeout=3000&autoReconnect=true&useSSL=false
db.user.0=nacos
db.password.0=your_password
```

实际参数会随 Nacos 版本和部署方式调整，应以当前版本的官方部署文档为准。

外部数据库解决的是持久化和多节点共享存储问题，但它不等于所有运行时数据都只靠数据库同步。Nacos 内部仍然会根据数据类型使用不同的一致性协议和同步路径。

## 四、Distro 和 Raft 分别解决什么

Nacos 集群中经常会看到两个词：`Distro` 和 `Raft`。

可以先用一句话区分：

- **Distro** 更偏 AP，用于临时服务这类运行时状态同步，优先保证可用性和最终一致。
- **Raft** 更偏 CP，用于需要多数派确认的一致性场景，优先保证一致性。

这不是说 Nacos 只有这两个机制，也不是说所有数据都走同一条路径。Nacos 会根据数据类型、服务类型和版本实现选择不同处理方式。

## 五、临时服务为什么偏 AP

大多数微服务实例是临时的。它们的生命周期跟应用进程绑定：

```text
应用启动 -> 注册实例
应用运行 -> 维持心跳或连接
应用故障 -> 租约过期或连接断开 -> 实例被摘除
```

对这类数据来说，可用性很重要。即使集群短暂出现网络抖动，注册中心也应该尽量继续服务，并在网络恢复后同步状态。

所以临时服务更适合 AP 风格：

- 允许短时间内不同节点看到的实例状态略有差异。
- 通过同步机制最终收敛。
- 避免因为局部网络问题就让服务发现完全不可用。

代价也很清楚：极短时间内，消费者可能看到稍旧的实例列表。因此客户端侧还需要本地缓存、健康过滤、超时、重试和熔断配合。

## 六、持久服务为什么偏 CP

持久服务不是普通业务进程那种“挂了就自动消失”的实例。它更像一个由注册中心管理的资源。

持久服务需要更明确的一致性语义：

- 实例不应该因为短暂心跳问题就被误删。
- 多个 Nacos 节点对服务元数据要尽量保持一致。
- 更新、删除、管理操作需要更谨慎。

因此持久服务和部分元数据场景更偏 CP。它会牺牲一些可用性来换取更明确的一致性。

## 七、Raft 的基本逻辑

Raft 是一种分布式一致性算法。它的核心目标是让多个节点对同一批变更达成一致。

Raft 中常见角色包括：

| 角色 | 说明 |
| ---- | ---- |
| Leader | 处理写请求，负责复制日志 |
| Follower | 跟随 Leader，同步日志 |
| Candidate | 选举过程中的候选节点 |

写入流程可以简化成：

```text
1. 客户端写请求到达 Leader
2. Leader 生成日志
3. Leader 把日志复制给 Follower
4. 多数节点确认后，Leader 提交日志
5. 状态机应用变更
```

Raft 的关键点是多数派。只要多数派节点确认，集群就可以对某个变更达成一致。反过来，如果多数派不可用，系统就不能继续安全地提交新写入。

## 八、配置中心的一致性要怎么理解

配置中心保存的是应用运行所依赖的配置。配置写入后，Nacos 集群需要保证多个节点不会长期保存不同版本的配置。

但这里要区分几个层面：

- **配置存储一致性**：配置内容是否可靠保存。
- **Nacos 节点视图一致性**：不同节点是否能看到同一份配置版本。
- **客户端感知延迟**：应用多久能通过监听机制发现配置变化。
- **应用刷新成功**：应用是否真的把新配置绑定到运行对象上。

不能简单说“配置中心用了 Raft，所以所有客户端任意时刻都强一致”。即使服务端已经保存了新配置，客户端也要经过监听、拉取、环境刷新这些步骤。应用代码是否支持动态刷新，也是另一回事。

更准确的说法是：Nacos 通过持久化存储、一致性协议、监听机制和客户端缓存共同保证配置管理的可靠性；客户端最终生效还取决于应用侧刷新机制。

## 九、CAP 在 Nacos 中的体现

CAP 指分布式系统在网络分区下无法同时完全满足一致性、可用性和分区容错性。

在真实分布式系统里，网络分区不能假装不存在，所以主要是在 C 和 A 之间权衡。

| 取舍 | 说明 | Nacos 中的直观例子 |
| ---- | ---- | ------------------ |
| AP | 优先可用，允许短暂不一致，最终收敛 | 临时服务实例状态 |
| CP | 优先一致，多数派不可用时拒绝部分写入 | 持久服务和一致性元数据场景 |

这也是为什么学习 Nacos 时不要只记一句“Nacos 是 AP”或“Nacos 是 CP”。Nacos 是同时支持不同一致性语义的系统，具体要看你讨论的是哪类数据。

## 十、常见故障判断

### 1. 集群节点启动失败

检查：

- `cluster.conf` 中 IP 和端口是否正确。
- 节点之间是否互通。
- 数据库连接是否正常。
- 节点时间是否偏差过大。
- 端口是否被占用。

### 2. 控制台节点列表异常

检查：

- 负载均衡是否把请求转发到不同节点。
- 集群节点配置是否一致。
- Nacos 节点间通信端口是否放行。
- 是否存在节点使用了错误的本机 IP。

### 3. 配置发布后部分应用未更新

检查：

- 应用是否连到正确的 Namespace、Group、DataId。
- 客户端监听是否正常。
- `refresh-enabled` 是否开启。
- 使用 `@Value` 的 Bean 是否加了 `@RefreshScope`。
- 应用是否实际支持对应配置的运行时变更。

### 4. 实例下线后仍被调用

检查：

- 实例是临时服务还是持久服务。
- 健康检查是否正常。
- 消费者本地缓存是否过期。
- 负载均衡规则是否过滤不健康实例。
- 调用侧是否有超时、重试和熔断。

## 十一、生产建议

生产环境建议：

- 使用至少 3 个 Nacos 节点。
- 客户端连接统一入口。
- 外部数据库做高可用。
- Namespace 按环境隔离。
- 开启鉴权和权限控制。
- 配置变更走审核和回滚流程。
- 对 Nacos 做监控和告警。
- 客户端保留合理的本地缓存和容错策略。
- 不随意调整 Distro、Raft 等内部协议参数。

尤其不要在没有诊断依据时调整一致性协议参数。那不是调优，那更像是在闭着眼睛改承重墙。

## 十二、总结

Nacos 集群不是简单地把三个进程启动起来。它背后有三层问题：

- **部署层**：节点、负载均衡、数据库、网络、权限。
- **数据层**：哪些数据持久化，哪些数据走运行时同步。
- **一致性层**：哪些场景偏 AP，哪些场景偏 CP。

理解 Distro 和 Raft 的价值，不是为了背协议名，而是为了知道不同数据为什么会有不同表现。临时服务追求可用和自动摘除，持久服务追求管理语义和一致性，配置中心还要额外考虑客户端刷新链路。把这些边界分清，排查问题时就不会只剩下“重启试试”这种朴素但贫乏的方案。
