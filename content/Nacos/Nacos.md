Nacos 是微服务体系中常见的基础设施，主要解决两类问题：**服务注册发现**和**动态配置管理**。

在单体应用中，一个模块调用另一个模块通常只是一次本地方法调用；到了微服务架构中，服务拆成多个独立进程，IP、端口、实例数量和健康状态都会变化。如果仍然把地址写死在配置文件里，扩容、下线、故障摘除都会变得笨重而危险。Nacos 的价值就在这里：它让服务地址和配置从“写死在应用里”变成“由中心化组件统一管理”。

## 一、Nacos 解决什么问题

Nacos 的核心能力可以分成四块：

- **服务发现与健康检查**：服务启动后注册实例，消费者按服务名发现可用实例。
- **动态配置管理**：把应用配置放在 Nacos 中统一管理，并支持运行时刷新。
- **服务与元数据管理**：管理服务、实例、权重、集群、metadata 等信息。
- **控制台与运维能力**：通过 Web 控制台查看服务状态、编辑配置、管理命名空间和权限。

用一张简化图表示：

```text
服务提供者 ---> 注册实例 ----+
                          |
                          v
                      Nacos Server
                          ^
                          |
服务消费者 ---> 订阅服务 ----+

应用启动 ---> 拉取配置 ---> Nacos Config
配置变更 ---> 长轮询通知 ---> 应用刷新配置
```

## 二、核心概念

理解 Nacos 时，先把几个概念分清楚，会少很多误会。

| 概念 | 作用 |
| ---- | ---- |
| Namespace | 顶层隔离单位，常用于区分 dev、test、prod 或租户 |
| Group | Namespace 下的二级分组，常用于业务线或系统分组 |
| Service | 服务发现的基本单位，例如 `order-service` |
| Cluster | Service 下的实例集群，常用于机房、区域或可用区 |
| Instance | 一个具体服务实例，由 IP、端口、健康状态、权重、metadata 等描述 |
| Metadata | 实例元数据，例如 `version`、`tag`、`region`，通常用于自定义路由 |

在注册中心里，层级可以粗略理解为：

```text
Namespace
  -> Group
    -> Service
      -> Cluster
        -> Instance
          -> Metadata
```

在配置中心里，配置由三元组定位：

```text
Namespace + Group + DataId
```

这两个模型不要混在一起。注册中心关心“服务实例在哪里、是否健康、怎么路由”；配置中心关心“应用应该读取哪份配置、配置变化后如何刷新”。

## 三、服务注册发现

服务注册发现回答的是：

- A 服务要调用 B 服务，如何知道 B 服务当前有哪些实例？
- B 服务扩容后，消费者如何感知新实例？
- 某个实例挂了，如何从调用列表中摘除？
- 多个实例之间，如何做负载均衡和路由？

典型流程如下：

```text
1. 服务提供者启动
2. 提供者向 Nacos 注册自己的 IP、端口、服务名、metadata
3. 服务消费者按服务名订阅实例列表
4. 消费者本地负载均衡器选择一个可用实例
5. 实例变更时，Nacos 通知客户端刷新本地列表
```

服务发现不是“前端直接访问 Nacos 后拿到后端 IP”。在常见架构中，前端只访问网关或后端入口；真正的服务发现、实例筛选和负载均衡发生在后端、网关或客户端负载均衡组件中。

## 四、配置中心

配置中心回答的是：

- 配置能不能从应用包中剥离出来？
- 多个实例能不能读取同一份配置？
- 修改开关、阈值、灰度比例后，能不能不重新发版？
- 配置能不能按环境、业务线、应用进行隔离？

Nacos 配置中心通常用于管理：

- 数据库、Redis、MQ 等连接配置。
- 功能开关、灰度比例、限流阈值。
- 第三方接口地址。
- 业务规则参数。

它的基本流程是：

```text
应用启动
  -> 根据 Namespace、Group、DataId 定位配置
  -> 从 Nacos 拉取远程配置
  -> 合并到 Spring Environment
  -> 应用运行

配置变更
  -> Nacos 记录新版本
  -> 客户端通过长轮询感知变化
  -> 拉取新内容
  -> 刷新可刷新的 Bean
```

需要注意的是，配置刷新不是魔法。通过 `@Value` 注入的字段通常需要配合 `@RefreshScope`；通过 `@ConfigurationProperties` 绑定的配置，在 Spring Cloud Alibaba 的刷新机制下更适合承载结构化配置。

## 五、临时服务与持久服务

Nacos 的服务发现里有临时服务和持久服务的区别。

| 类型 | 维护方式 | 典型场景 |
| ---- | -------- | -------- |
| 临时服务 | 依赖客户端连接、心跳或租约状态，失效后自动摘除 | 大多数微服务应用 |
| 持久服务 | 作为持久化资源管理，需要更明确的上下线控制 | 基础设施、固定地址服务、特殊治理场景 |

多数业务微服务都应该使用临时服务。服务进程挂掉后，实例应该自动从可调用列表里消失，否则消费者可能继续把请求打到失效节点。

## 六、集群与持久化

生产环境通常不会用单机 Nacos。常见部署方式是：

```text
             客户端 / 应用
                  |
                  v
          SLB / Nginx / VIP
                  |
      +-----------+-----------+
      |           |           |
  Nacos-1     Nacos-2     Nacos-3
      |           |           |
      +-----------+-----------+
                  |
            外部数据库
```

部署时通常要关注：

- Nacos 节点数量，生产常用 3 个或更多节点。
- `cluster.conf` 中节点地址是否互通。
- 外部数据库是否可用、是否高可用。
- 客户端连接的是负载均衡入口，而不是某个临时节点。
- 鉴权、命名空间、权限和网络访问控制是否配置。

Nacos 内部会根据数据类型和服务类型使用不同一致性路径。临时服务更偏 AP 和运行时可用性，持久服务及部分元数据更偏 CP 和一致性。不要简单写成“Nacos 全部靠 Raft”或者“Nacos 全部靠 MySQL”，那样显然过于粗糙。

## 八、总结

Nacos 不是单纯的“注册中心”，也不是单纯的“配置文件管理页面”。它处在微服务运行时的关键位置：服务能否被发现、配置能否及时更新、实例能否正确摘除、流量能否按规则路由，都可能和它有关。

学习 Nacos 时，不必一开始就陷入所有参数。先抓住两条主线就够了：

- **注册中心**：服务怎么注册、发现、摘除和路由。
- **配置中心**：配置怎么定位、加载、刷新和隔离。

这两条主线清楚之后，再看集群、一致性、灰度发布和权限控制，知识才会自然地连起来。
