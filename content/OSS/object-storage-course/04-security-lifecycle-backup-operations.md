上传和下载成功后，真正棘手的问题才开始出现：一个泄漏的 URL 能读取多久？误删的对象在哪里？Docker volume 算不算备份？磁盘满时该先删什么？本章把对象存储从“开发环境里可用”推进到“数据出事时知道怎样恢复”。

## 1. 权限设计从“谁能做什么”开始

不要让应用使用管理员/root 凭据。先列出身份与动作，再授予最小集合：上传服务只能向 `incoming/app-a/` 写入；图片处理服务只读这个前缀、只写 `derived/app-a/`；下载 API 只负责签发 URL；运维角色才有删除、策略和生命周期权限。

策略语言因实现而异，但思想相同：限定 action、bucket 和 object key 前缀。概念示例：

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": ["arn:aws:s3:::media-prod/incoming/app-a/*"]
  }]
}
```

这不自动允许 `ListBucket`，也不允许删除或写入 `derived/`。上线前用每个角色的实际凭据验证允许和拒绝两条路径：只测试成功请求会漏掉越权。

密钥应由密钥管理系统、工作负载身份或受限部署配置提供，定期轮换；日志、错误上报、浏览器代码与镜像层中都不该包含长期 secret。管理员凭据只能用于初始管理，绝不能作为常规应用凭据。

## 2. 网络、TLS、CORS 与预签名 URL

生产环境使用 HTTPS；否则 token、签名和文件内容都可能在网络上泄漏。对象端点应放在受控网络、网关或私有连接之后，并限制管理控制台的来源地址。

浏览器跨域上传还需要 CORS。不要使用 `*` 加允许凭据这种含糊配置；明确写出可信 Origin、PUT/GET 方法、允许的 headers 和浏览器需要读取的响应 headers。CORS 是浏览器约束，不是服务端授权：即使 CORS 拒绝，错误的 bucket policy 仍可能造成泄漏。

预签名 URL 要短期、单对象、单方法。签发端必须检查用户是否可操作该业务对象；上传完成后再进行 `HEAD`、大小/checksum、恶意文件扫描或内容解析。它是“暂时委托一次请求”，不是访问控制系统的替代品。

## 3. 版本、删除标记和生命周期如何配合

未开启版本控制时，同 key 的覆盖会丢掉旧字节，DELETE 通常立刻不可见。开启版本后，每次写入产生 version，DELETE 常创建 delete marker；你可以删除 marker 或指定旧 version 进行恢复。代价是旧版本继续占空间，账单和容量会慢慢增长。

建议先在新 bucket 做一次恢复演练：上传 `v1`，覆盖为 `v2`，删除当前对象，列出 versions/delete markers，恢复 `v1`，再下载并核对 SHA-256。具体命令和能力随服务不同，以部署版本文档为准。没有亲手恢复过的“版本保护”，在事故时常常等同于没有。

生命周期规则将某类对象在指定时间后转存、过期或清理未完成 multipart upload。例如临时上传 7 天后删除、非当前版本 30 天后删除、未完成分片 1 天后中止。规则应先对 `sandbox/` prefix 灰度，并观察实际删除结果；错误的 prefix 或天数会造成大范围数据损失。生命周期任务通常异步执行，不保证到点立刻删除。

## 4. Docker volume 不是备份：制定可验证的恢复计划

volume 只说明数据跨容器重启仍存在；同一台主机磁盘坏了、误执行删除、勒索软件或错误生命周期规则时，volume 无法救你。可靠策略至少回答四个问题：

- 要恢复到什么程度：RPO（允许丢多少时间的数据）和 RTO（多久恢复服务）。
- 备份放在哪里：与主存储不同的账号、故障域或权限边界，而不只是另一个目录。
- 如何证明副本可用：定期列举、比对对象数/大小/checksum，并在隔离环境恢复抽样对象。
- 谁有删除副本权限：备份凭据应与生产写入凭据隔离，必要时使用不可变/保留策略。

可使用服务提供的 replication、备份工具或 `rclone` 等工具做副本；工具并不改变上述原则。一次简化演练的记录至少包括：源 bucket、时间范围、manifest、复制结果、隔离 bucket 中的下载 SHA-256、恢复耗时和清理步骤。不要在恢复演练中直接覆盖生产 key。

## 5. 容量和可观测性：在满盘前发现问题

至少监控可用容量、对象数、请求延迟/4xx/5xx、上传/下载字节、未完成 multipart 数量与空间、备份任务最近成功时间和副本滞后。对关键 bucket 还应监控版本数快速增长和删除操作异常升高。

容量估算不要只算当前对象总大小。还应加上版本保留、multipart 残留、冗余/纠删编码开销、增长率和恢复期间需要的临时空间。发现空间逼近阈值时，先停止非必要写入，确认是否有异常大对象/无限版本/未完成分片，再根据已批准的生命周期或扩容方案处理；不要临时用管理员权限批量删除“看起来旧”的 key。

## 6. 小型故障 Runbook

| 现象 | 先做什么 | 不要做什么 |
| --- | --- | --- |
| 403 / 签名失败 | 检查 endpoint、时间、凭据身份、策略、代理改写 | 把管理员密钥发给开发者试试 |
| 某对象误删 | 停止相关写入；查 version/delete marker；在隔离处下载校验 | 立即用同 key 上传一个空文件覆盖线索 |
| 发现下载内容不对 | `HEAD` 比对 size/metadata，重新计算 SHA-256，保留原始证据 | 只看 ETag 就宣布数据完好 |
| 磁盘持续增长 | 查版本、未完成分片、备份滞后和异常写入 | 直接删除未知前缀 |
| 服务不可达 | 查健康端点、DNS/网络/TLS、服务日志和存储挂载 | 在未确认故障范围前重建数据目录 |

## 课程结论

对象存储的核心不是“把文件传上去”，而是使用稳定的 `bucket + key` 模型，通过 S3 API 在不可信网络中完成认证、传输、校验和恢复。你已经从文件系统与对象模型出发，亲手走过 CLI、SDK、分片和预签名 URL；接下来无论选 RustFS、MinIO、云厂商 S3 或其他兼容实现，都应带着同一套问题评估：权限是否最小、字节能否验证、删除能否恢复、备份是否真的演练过。
