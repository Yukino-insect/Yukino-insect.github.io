系统异常处理的目标不是“把所有异常都 catch 掉”，而是让异常在合适的边界被转换成稳定、可理解、可观测的响应。

在一个 Spring 项目里，异常通常会经过三类边界：

- Controller 层：处理业务接口异常。
- Spring Security 过滤器链：处理认证、授权异常。
- Gateway 网关层：处理路由、过滤器、下游服务调用异常。

如果边界搞错了，就会出现一个常见误区：明明写了全局异常处理器，Security 里的 401/403 却还是不走它。不是框架任性，是你站错了门口。

## 异常分类

项目里最好先把异常分清楚。

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 业务异常 | 参数不合法、余额不足、状态不允许变更 | 返回明确业务错误码和提示 |
| 认证异常 | 未登录、Token 过期、Token 无效 | 返回 401 |
| 授权异常 | 已登录但没有权限 | 返回 403 |
| 系统异常 | NPE、数据库异常、第三方服务异常 | 记录日志，返回通用提示 |

业务异常可以提示给用户，系统异常通常不应该把内部细节暴露出去。比如 SQL、堆栈、服务地址、配置字段这些内容，一旦原样返回，除了显得粗糙，还可能泄露系统信息。

## Spring MVC 全局异常处理

Controller、Service、Mapper 调用链中向上抛出的异常，可以交给 `@RestControllerAdvice` 统一处理。

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BizException.class)
    public Result<Void> handleBizException(BizException e) {
        return Result.fail(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValidException(MethodArgumentNotValidException e) {
        String message = e.getBindingResult()
                .getFieldErrors()
                .stream()
                .findFirst()
                .map(DefaultMessageSourceResolvable::getDefaultMessage)
                .orElse("请求参数不合法");

        return Result.fail(400, message);
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        log.error("Unexpected server error", e);
        return Result.fail(500, "系统繁忙，请稍后重试");
    }
}
```

这里有两个重点。

第一，业务异常和系统异常要分开。业务异常是系统主动表达规则，系统异常是系统出现了未预期问题。

第二，兜底异常必须记录日志，但响应不要返回 `e.getMessage()`。用户不需要看你的空指针，攻击者倒是挺愿意看。

## Spring Security 异常

Spring Security 的异常发生在过滤器链中，很多时候还没有进入 Controller，所以 Spring MVC 的全局异常处理器接不到。

这里主要有两类异常：

- `AuthenticationException`：未认证，例如未登录、Token 过期、Token 无效。
- `AccessDeniedException`：已认证但无权限。

对应处理器是：

- `AuthenticationEntryPoint`：返回 401。
- `AccessDeniedHandler`：返回 403。

### AuthenticationEntryPoint

```java
@Component
public class JsonAuthenticationEntryPoint implements AuthenticationEntryPoint {

    @Override
    public void commence(HttpServletRequest request,
                         HttpServletResponse response,
                         AuthenticationException exception) throws IOException {
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("""
                {"code":401,"message":"未登录或登录已失效"}
                """);
    }
}
```

### AccessDeniedHandler

```java
@Component
public class JsonAccessDeniedHandler implements AccessDeniedHandler {

    @Override
    public void handle(HttpServletRequest request,
                       HttpServletResponse response,
                       AccessDeniedException exception) throws IOException {
        response.setStatus(HttpServletResponse.SC_FORBIDDEN);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("""
                {"code":403,"message":"权限不足"}
                """);
    }
}
```

注册到 Security 配置：

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
            .exceptionHandling(ex -> ex
                    .authenticationEntryPoint(authenticationEntryPoint)
                    .accessDeniedHandler(accessDeniedHandler)
            )
            .build();
}
```

如果项目使用 JWT，自定义 `JwtAuthenticationFilter` 中解析失败时一般不要直接写响应。可以清空上下文后继续放行，让后续的 Security 机制统一返回 401。

```java
try {
    Authentication authentication = parseToken(request);
    SecurityContextHolder.getContext().setAuthentication(authentication);
} catch (JwtException e) {
    SecurityContextHolder.clearContext();
}

filterChain.doFilter(request, response);
```

## Spring Cloud Gateway 异常

Spring Cloud Gateway 基于 WebFlux，不走 Spring MVC 的 `@RestControllerAdvice`。网关层异常通常通过 `ErrorWebExceptionHandler` 统一处理。

```java
@Component
@Order(-1)
public class GlobalGatewayExceptionHandler implements ErrorWebExceptionHandler {

    private final ObjectMapper objectMapper = new ObjectMapper();

    @Override
    public Mono<Void> handle(ServerWebExchange exchange, Throwable exception) {
        ServerHttpResponse response = exchange.getResponse();

        if (response.isCommitted()) {
            return Mono.error(exception);
        }

        response.setStatusCode(HttpStatus.INTERNAL_SERVER_ERROR);
        response.getHeaders().setContentType(MediaType.APPLICATION_JSON);

        Map<String, Object> body = Map.of(
                "code", 500,
                "message", "网关服务异常"
        );

        byte[] bytes;
        try {
            bytes = objectMapper.writeValueAsBytes(body);
        } catch (JsonProcessingException e) {
            bytes = new byte[0];
        }

        DataBuffer buffer = response.bufferFactory().wrap(bytes);
        return response.writeWith(Mono.just(buffer));
    }
}
```

注意状态码不要随手写成 `200`。除非你的团队明确约定“HTTP 永远 200，业务 code 表示结果”，否则网关异常就应该保持正确的 HTTP 状态。混乱的成功码，是排查问题时最会装无辜的东西。

## 日志与响应

异常处理还要兼顾两件事：对用户友好，对开发者可排查。

响应里应该有：

- 稳定的业务 code。
- 可以给用户看的 message。
- 可选的 requestId 或 traceId，方便客服和研发定位。

日志里应该有：

- 异常堆栈。
- 请求路径、用户 ID、关键业务 ID。
- 外部服务名、超时时间、重试次数等上下文。

日志里不应该有：

- 密码、Token、密钥。
- 身份证、手机号完整明文。
- 大段请求体或响应体。

## 小结

异常处理的关键是边界：MVC 管 MVC，Security 管认证授权，Gateway 管入口和路由。业务异常给明确提示，系统异常给统一兜底，日志保留排查信息，响应避免泄露细节。把这些边界处理清楚，系统即使出错，也能出得有点教养。
