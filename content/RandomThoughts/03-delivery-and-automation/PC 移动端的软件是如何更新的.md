PC 和移动端软件更新通常不是服务端“主动推送安装包”，而是客户端在启动、进入前台、定时任务或用户手动检查时，主动向服务器询问是否有新版本。

核心模型是：

```text
设备信息 + 当前版本 + 渠道信息 -> 更新服务 -> 返回更新策略
```

## 检查更新请求

客户端可能请求：

```http
POST /api/app-updates/check
Content-Type: application/json
```

请求体：

```json
{
  "deviceId": "a9f3c7d8",
  "platform": "android",
  "model": "Pixel 7",
  "osVersion": "Android 14",
  "appVersion": "3.2.1",
  "buildNumber": 321,
  "region": "SG",
  "channel": "stable"
}
```

服务端根据这些信息判断：

- 平台：Windows、macOS、Android、iOS。
- 当前版本和构建号。
- 发布渠道：stable、beta、灰度渠道、应用商店渠道。
- 地区和语言。
- 设备型号和系统版本。
- 用户或设备是否命中灰度规则。

## 更新响应

响应可能是：

```json
{
  "hasUpdate": true,
  "version": "3.3.0",
  "buildNumber": 330,
  "force": false,
  "title": "发现新版本",
  "description": "修复若干问题并优化启动速度",
  "downloadUrl": "https://cdn.example.com/app/app-3.3.0.apk",
  "checksum": "sha256:...",
  "size": 73400320
}
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `hasUpdate` | 是否有可用更新 |
| `version` | 展示版本号 |
| `buildNumber` | 用于比较的新构建号 |
| `force` | 是否强制更新 |
| `downloadUrl` | 安装包下载地址 |
| `checksum` | 文件校验值 |
| `size` | 安装包大小 |

客户端拿到结果后，决定展示弹窗、后台下载、强制拦截进入，或什么都不做。

## 灰度发布

更新服务通常不会一次性给所有用户发新版本，而是灰度发布：

```text
1% -> 5% -> 20% -> 50% -> 100%
```

命中规则可以基于：

- 用户 ID 哈希。
- 设备 ID 哈希。
- 地区。
- 渠道。
- 系统版本。
- 指定白名单。

用哈希命中灰度可以保证同一用户结果稳定：

```text
hash(deviceId) % 100 < rolloutPercent
```

否则用户今天看到更新，明天又看不到，体验会显得很随缘。软件更新可以灰度，用户耐心通常不行。

## 强制更新

强制更新一般用于：

- 旧版本存在严重安全漏洞。
- 后端接口协议不再兼容。
- 法务、合规或支付规则变化。
- 旧版本有严重崩溃问题。

强更响应：

```json
{
  "hasUpdate": true,
  "force": true,
  "minSupportedBuild": 330,
  "downloadUrl": "https://cdn.example.com/app/app-3.3.0.apk"
}
```

客户端如果发现当前 `buildNumber < minSupportedBuild`，就禁止继续使用，要求更新。

强制更新要谨慎。尤其是移动端，如果下载地址不可用、应用商店审核延迟、用户网络差，就可能把正常用户挡在门外。

## 安装包安全

安装包下载后应该校验：

- 文件大小。
- SHA-256 等摘要。
- 代码签名。
- 版本号和包名。

PC 客户端通常还会有更新器进程，负责下载、校验、替换文件、回滚。移动端则受系统和应用商店限制更多，尤其是 iOS，通常依赖 App Store 发布和更新。

## 热更新和配置更新

有些“更新”不需要重新安装应用：

- 远程配置。
- 功能开关。
- 活动配置。
- WebView 页面。
- 插件或资源包。

这类更新也常由客户端主动拉取。它们发布更快，但也要注意版本兼容和回滚能力。

## 小结

软件更新本质上是客户端主动询问服务器，服务器根据设备、版本、渠道和灰度策略返回更新结果。真正重要的不只是“有没有新版本”，还包括灰度、强更、校验、回滚和渠道控制。更新系统写得好，用户几乎感觉不到；写得差，用户会立刻知道。
