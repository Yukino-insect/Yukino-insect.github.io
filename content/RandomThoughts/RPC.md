RPC 是 Remote Procedure Call 的缩写，意思是远程过程调用。它的目标是让调用远程服务像调用本地方法一样自然。

## 一、RPC 解决什么问题

在单体应用中，一个方法可以直接调用另一个方法。拆成多个服务后，方法可能部署在另一台机器上，此时就需要通过网络通信完成调用。

RPC 框架会把网络通信、序列化、寻址、负载均衡、超时、重试等细节封装起来，让业务代码只关注接口调用。

## 二、基本流程

一次 RPC 调用通常包括以下步骤：

1. 客户端调用本地代理对象。
2. 代理对象把方法名、参数和元数据序列化。
3. 客户端通过网络发送请求。
4. 服务端接收请求并反序列化。
5. 服务端定位目标方法并执行。
6. 服务端把结果序列化后返回。
7. 客户端反序列化结果并返回给调用方。

动态代理常用于生成客户端代理对象，因此调用方看起来像是在调用本地接口。

## 三、RPC 和 HTTP

RPC 不是某一种具体协议。它是一种调用模型。底层可以使用 TCP、HTTP/2、HTTP/1.1 或其他协议。

例如 gRPC 通常基于 HTTP/2 和 Protobuf。Dubbo 可以使用自定义协议，也可以支持多种序列化方式。

因此，不能简单地把 RPC 和 HTTP 对立起来。HTTP 可以作为 RPC 的传输协议。

## 四、RPC 的关键问题

RPC 调用本质上仍然是网络调用，所以必须处理：

1. 超时。
2. 重试。
3. 幂等。
4. 负载均衡。
5. 服务发现。
6. 熔断降级。
7. 序列化兼容性。

如果忽略这些问题，把远程调用当成本地调用使用，系统很容易在延迟、失败和重试风暴中出问题。

## 五、总结

RPC 的价值是降低服务之间调用的复杂度，但它不能消除网络的不可靠性。使用 RPC 时，应始终记住：接口形式像本地调用，故障模型仍然是远程调用。
