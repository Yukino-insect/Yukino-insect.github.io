缓存的核心作用是减少重复计算和重复查询。对于大量 CRUD 接口来说，性能问题往往不是单条 SQL 慢，而是一次请求中重复查询太多，或者在循环中不断访问数据库。

## 一、典型问题

常见性能问题包括：

1. N + 1 查询：先查主表列表，再对每条记录查询关联数据。
2. 动态 SQL 拼接不当：条件组合后产生大量重复查询。
3. 笛卡尔积：多表关联条件缺失，导致结果集异常膨胀。
4. 频繁读取配置或字典数据：每次请求都访问数据库。

这些问题会让接口响应时间从几百毫秒上升到数秒甚至更久。此时缓存或预加载可以明显降低查询次数。

## 二、本地缓存

最简单的缓存是本地内存，例如把字典表、配置项、枚举映射加载到 `Map` 中：

```java
Map<Long, User> userMap = users.stream()
    .collect(Collectors.toMap(User::getId, Function.identity()));
```

后续组装数据时，就可以用 `O(1)` 的方式从 `Map` 中取值，避免循环查库。

本地缓存适合：

1. 数据量不大。
2. 变化频率低。
3. 单机内使用即可。
4. 对短时间不一致可以接受。

## 三、分布式缓存

Redis 这类缓存数据库适合多实例共享缓存。它可以缓存热点数据、接口结果、字典配置、登录态和限流计数。

使用 Redis 时要考虑网络开销。缓存不是免费午餐，如果缓存对象很小、查询本身很快，频繁访问 Redis 也可能得不偿失。

## 四、缓存一致性

缓存最容易出问题的地方是数据更新。常见策略有：

1. 先更新数据库，再删除缓存。
2. 给缓存设置过期时间。
3. 对配置类数据监听配置中心变更。
4. 对高一致性数据避免长期缓存。

如果数据来自 Nacos 配置，并且运行时可能变化，可以配合刷新机制更新内存中的值。如果是自己维护的本地 `Map`，至少要考虑过期、刷新或重建机制。

## 五、总结

缓存适合解决重复读取和热点访问问题，但不能替代正确的数据建模和 SQL 优化。引入缓存前，应先确认慢在哪里；引入缓存后，应重点处理过期、穿透、击穿、雪崩和一致性问题。
