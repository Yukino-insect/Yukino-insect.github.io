分布式系统中，日志不能只留在单台机器本地。服务实例会扩缩容，容器会重建，故障排查也需要跨服务串联调用链。因此日志需要集中采集、统一存储和可检索查询。

## 一、常见方案

常见的集中式日志方案主要有 ELK 和 EFK。

ELK 指的是：

1. Elasticsearch：负责日志索引和查询。
2. Logstash：负责日志采集、解析和加工。
3. Kibana：负责日志检索和可视化。

EFK 指的是：

1. Elasticsearch：负责日志索引和查询。
2. Fluentd 或 Fluent Bit：负责日志采集和转发。
3. Kibana：负责日志检索和可视化。

两者的主要差异在采集层。Logstash 功能强，但资源消耗相对更高；Fluent Bit 更轻量，更适合容器和 Kubernetes 环境。

## 二、日志链路

典型链路如下：

```text
应用输出日志 -> 本地文件或标准输出 -> 采集 Agent -> 消息队列或缓冲区 -> Elasticsearch -> Kibana
```

如果系统规模较大，采集端和 Elasticsearch 之间通常会增加 Kafka。这样可以削峰、缓冲，也能避免 Elasticsearch 短暂不可用时日志直接丢失。

## 三、日志字段设计

日志要好查，关键在结构化字段。至少应包含：

1. 时间。
2. 服务名。
3. 实例 IP 或容器 ID。
4. 日志级别。
5. traceId。
6. spanId。
7. 请求路径。
8. 错误码。
9. 异常堆栈。

其中 `traceId` 非常重要。没有它，跨服务排查问题只能靠时间和关键词猜测，效率很低。

## 四、实践建议

日志系统不是越多越好。生产环境要控制日志级别，避免把大量 DEBUG 日志写入集中存储。异常日志要保留完整堆栈，但敏感信息必须脱敏，例如手机号、身份证号、token、密码和密钥。

总结来说，小规模系统可以直接使用 Filebeat 或 Fluent Bit 写入 Elasticsearch；中大型系统建议增加 Kafka 缓冲，并配合链路追踪系统一起使用。
