实习中遇到过一个敏感数据加密场景：客户不允许手机号、身份证等信息以明文存入数据库。项目最终通过第三方 KMS 平台完成加解密，业务系统按接口规范远程调用 KMS。

这个方案安全性有优势，但也暴露出一个性能问题：如果列表页有几十条数据，每条手机号都要远程解密一次，分页查询就会变成高频 KMS 调用。接口本身也许不慢，但 N 次远程调用叠起来，用户不会替你的架构感动。

借这个场景，把常见加密概念和工程落地整理一下。

## 加密、哈希、签名

先区分三个概念。

| 类型 | 是否可逆 | 解决什么问题 |
| --- | --- | --- |
| 加密 | 可逆 | 保护内容不被未授权方读取 |
| 哈希 | 不可逆 | 生成摘要、校验完整性、做指纹 |
| 签名/MAC | 不可逆验证 | 证明内容未被篡改，并确认发送方身份 |

如果目标是之后还能看到手机号明文，就必须使用可逆加密。如果只是登录密码，绝不应该加密后存储，而应该使用带盐的慢哈希算法，例如 BCrypt、Argon2。

## 对称加密

对称加密使用同一把密钥加密和解密。

特点：

- 性能好，适合加密大量数据。
- 常用于文件、数据库字段、通信内容。
- 难点在于密钥管理。

常见算法：

- `AES`：国际通用分组加密算法。
- `SM4`：国密分组加密算法。
- `ChaCha20`：流加密算法，常见于移动端和高性能场景。

对称加密还需要选择工作模式。现代业务中优先考虑 `GCM` 这类带认证的模式，因为它同时提供保密性和完整性校验。

不要使用 `ECB`。它会泄露明文模式，看起来像加密了，实际上很有表演性质。

## 非对称加密

非对称加密使用一对密钥：

- 公钥：可以公开。
- 私钥：必须保密。

常见算法：

- `RSA`
- `ECC`
- `SM2`
- `DH/ECDH`

非对称加密性能比对称加密差，不适合直接加密大文件或大量字段。它更常用于密钥协商、数字签名、证书体系，或者加密一把较短的对称密钥。

## 哈希和 HMAC

哈希算法把任意长度输入转换成固定长度摘要。

常见算法：

- `SHA-256`
- `SHA-512`
- `SM3`

哈希不可逆，适合做完整性校验、文件指纹、数据去重、索引辅助字段等。

但普通哈希不能证明“是谁生成的”。任何人拿到原文都能算出同样摘要。

HMAC 在哈希基础上加入密钥：

```text
HMAC = Hash(message + secret)
```

准确说 HMAC 有标准结构，不是简单字符串拼接。它的重点是：只有持有密钥的一方才能生成正确 MAC，所以它能同时提供完整性校验和身份认证。

## 数字信封

数字信封是一种组合方案：

```text
真实数据 -> 用对称密钥加密
对称密钥 -> 用非对称公钥或 KMS 主密钥加密
```

它解决的是两个矛盾：

- 对称加密快，但密钥不好分发。
- 非对称加密方便分发密钥，但加密大数据慢。

所以工程上经常这样做：

```text
1. 生成一把数据密钥 DEK。
2. 用 DEK 加密业务数据。
3. 用 KMS 或公钥加密 DEK，得到 encryptedDEK。
4. 数据库存业务密文和 encryptedDEK。
5. 解密时先解开 encryptedDEK，再用 DEK 解开业务数据。
```

这就是信封加密的基本思路。

## KMS 模式

KMS 的核心价值是让业务系统不直接持有主密钥。

常见能力：

- 密钥托管。
- 权限控制。
- 调用审计。
- 密钥轮换。
- 禁用和吊销。
- 对接 HSM 或云厂商安全能力。

业务系统一般只拿 `keyId`、`encryptedDEK` 或调用凭证。主密钥材料不出 KMS，这比把密钥写在配置文件里靠谱得多。把密钥写进 `application.yml`，再把配置传进 Git 仓库，那已经不是安全方案，是事故预告。

## 敏感字段落库方案

对手机号、身份证这类字段，常见表结构可以这样设计：

| 字段 | 含义 |
| --- | --- |
| `phone_cipher` | 手机号密文 |
| `phone_mask` | 脱敏展示字段，例如 `138****1234` |
| `phone_hash` | 查询用摘要，例如精确匹配手机号 |
| `encrypted_dek` | 被 KMS 保护的数据密钥 |
| `key_id` | KMS 密钥标识 |
| `key_version` | 密钥版本 |
| `iv` | 初始化向量 |
| `tag` | GCM 认证标签 |
| `alg` | 加密算法 |

列表页通常只展示 `phone_mask`，不解密明文。详情页、导出、客服核验等确实需要明文的场景，再走解密流程。

这样能把高频路径从“每条记录调用一次 KMS”变成“普通查询直接返回脱敏字段”。

## 高频解密优化

如果业务确实必须批量解密，可以考虑这些优化：

- 优先让 KMS 或加密服务支持批量接口。
- 使用信封加密，本地完成数据解密，只让 KMS 解开 DEK。
- 对 `encryptedDEK -> plaintextDEK` 做短 TTL 缓存。
- 按 `encryptedDEK` 去重，减少重复解包。
- 区分列表展示和详情查看，列表不返回明文。
- 对解密操作做审计、限流和告警。

缓存明文 DEK 要非常谨慎，TTL 要短，权限要严，日志不能打印。优化性能不能把安全边界拆了；那不叫优化，叫换一种方式出事。

## 防重放和防篡改

很多接口加密只解决“别人看不到内容”，但还要考虑篡改和重放。

常见补强：

- `timestamp`：限制请求有效时间。
- `nonce`：一次性随机数，避免重放。
- `requestId`：幂等和追踪。
- `HMAC` 或签名：校验内容未被篡改。
- HTTPS：保护传输通道，防窃听和中间人攻击。

如果接口已经走 HTTPS，业务层是否还要加密，要看威胁模型。比如防数据库泄露、日志泄露、内部越权读取，就需要字段级加密；如果只是防网络窃听，HTTPS 已经解决了主要问题。

## 小结

敏感数据加密不是简单地“调一个加密接口”。算法只是工具，真正难的是密钥管理、查询设计、展示脱敏、审计追踪和性能控制。KMS 能降低密钥泄露风险，但不能替业务系统设计好所有访问路径。安全这件事，最讨厌的不是不知道，而是知道一点就以为足够了。
