多数据源配置是指在同一个应用中配置多个 `DataSource`，并根据业务场景选择不同的数据源执行 SQL。

## 一、数据库连接池

应用访问数据库时，不应为每次请求都创建和销毁 JDBC 连接。连接创建成本较高，而且频繁创建会增加数据库压力。

连接池会提前创建一批连接，并在请求结束后复用连接。Java 中连接池的标准接口是 `javax.sql.DataSource`。

常见连接池包括：

1. HikariCP。
2. Druid。
3. Tomcat JDBC Pool。

Spring Boot 默认常用 HikariCP。

## 二、AbstractRoutingDataSource

Spring 提供了 `AbstractRoutingDataSource` 用于运行时动态选择数据源。

它的核心思路是维护一个数据源标识到 `DataSource` 实例的映射关系，并在获取连接时调用 `determineCurrentLookupKey` 判断当前应该使用哪个数据源。

常见做法是把当前数据源标识保存在 `ThreadLocal` 中：

```java
public class DataSourceContextHolder {
    private static final ThreadLocal<String> CONTEXT = new ThreadLocal<>();

    public static void set(String key) {
        CONTEXT.set(key);
    }

    public static String get() {
        return CONTEXT.get();
    }

    public static void clear() {
        CONTEXT.remove();
    }
}
```

请求或方法执行前设置数据源，执行结束后清理。

## 三、注解切换

实际项目中常通过注解切换数据源，例如 `@DS("slave")`。这类能力通常由 AOP 实现：

1. 方法执行前读取注解。
2. 把数据源 key 写入上下文。
3. 执行业务方法。
4. 在 `finally` 中清理上下文。

`dynamic-datasource-spring-boot-starter` 就是常见方案之一。

## 四、事务注意点

数据源切换和事务顺序非常重要。如果事务已经开启，数据库连接可能已经从某个数据源获取，此时再切换数据源通常不会生效。

因此，多数据源场景下应明确事务边界，避免一个本地事务中混用多个数据源。跨库写入应考虑最终一致性或分布式事务方案。

## 五、总结

多数据源配置可以解决读写分离、业务隔离和多租户问题，但它会增加事务和排查复杂度。使用注解切换时，必须注意 `ThreadLocal` 清理和事务执行顺序。
