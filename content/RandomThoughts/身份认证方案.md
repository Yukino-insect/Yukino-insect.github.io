身份认证用于确认当前请求是谁发起的。常见方案包括 Session、Token、Session 共享和 JWT。它们解决的是登录态维护问题，但安全边界和适用场景不同。

## 一、基于 Session 的认证

传统 Web 应用常使用 Session。

流程如下：

1. 用户提交账号密码。
2. 服务端校验成功后创建 Session。
3. 服务端把 `sessionId` 写入浏览器 Cookie。
4. 浏览器后续请求自动携带 Cookie。
5. 服务端根据 `sessionId` 找到用户信息。

这种方式的优点是服务端可以主动失效会话。缺点是服务端需要保存会话状态，集群部署时要处理 Session 共享。

## 二、Session 共享

多实例部署时，如果 Session 只存在单机内存中，请求打到另一台机器就会找不到登录态。

常见解决方式是把 Session 存到 Redis：

```text
sessionId -> userInfo
```

这样多个应用实例都可以通过 Redis 读取会话。Spring Session 就是常见实现方式。

## 三、基于 Token 的认证

Token 方案中，客户端登录后拿到一个 token，后续请求在 Header 中携带：

```text
Authorization: Bearer <token>
```

服务端收到请求后解析 token，或拿 token 到 Redis 中查询用户信息。

如果 token 只作为随机字符串，用户状态仍然保存在 Redis 中，那么它本质上和 Session 共享很接近，只是传输位置从 Cookie 变成了 Header。

## 四、JWT

JWT 通常是签名 token，而不是加密 token。常见 JWS 形式的 JWT 可以被客户端解码看到 payload 内容，但不能被篡改，因为服务端会验证签名。

JWT 的优点是服务端可以不存储登录态，适合分布式校验。缺点是主动失效困难，token 泄露后在过期前可能一直可用。

因此 JWT 中不要放敏感信息，并且应设置较短过期时间。需要强制下线时，可以结合 Redis 黑名单、版本号或 token 状态表。

## 五、选择建议

后台管理系统、需要强控制登录态的系统，可以使用 Session 或 Redis Token。

开放 API、网关鉴权、跨服务认证，可以使用 JWT 或 OAuth2 体系。

无论选择哪种方案，都要配合 HTTPS、合理过期时间、刷新机制和服务端权限校验。认证只解决“是谁”，授权还要解决“能做什么”。
