看代码时发现一种处理 Redis key 常量的写法，比到处拼字符串清爽很多，记录一下。

```java
public final class UserProfileKeys {

    private static final String DIRTY_PREFIX = "user:profile:dirty:";
    private static final String AGG_PREFIX = "user:profile:agg:";
    private static final String VIEW_PREFIX = "user:profile:view:zset:";
    private static final String SEARCH_PREFIX = "user:profile:search:zset:";
    private static final String VECTOR_PREFIX = "user:profile:vector:";

    private UserProfileKeys() {
    }

    public static String dirtyKey(Long userId) {
        return DIRTY_PREFIX + userId;
    }

    public static String aggKey(Long userId) {
        return AGG_PREFIX + userId;
    }

    public static String viewKey(Long userId) {
        return VIEW_PREFIX + userId;
    }

    public static String searchKey(Long userId) {
        return SEARCH_PREFIX + userId;
    }

    public static String vectorKey(Long userId) {
        return VECTOR_PREFIX + userId;
    }
}
```

这种写法有几个好处：

- 类声明为 `final`，避免被继承。
- 构造方法私有化，避免被实例化。
- 前缀集中管理，减少散落在业务代码里的魔法字符串。
- 对外暴露方法，而不是暴露拼接细节。
- 方法名表达业务含义，调用处更短、更清楚。

调用时：

```java
String key = UserProfileKeys.viewKey(userId);
redisTemplate.opsForZSet().add(key, articleId, score);
```

比下面这种写法更可维护：

```java
String key = "user:profile:view:zset:" + userId;
```

字符串拼接本身不难，难的是它散落在几十个类里之后，没有人知道哪个前缀才是正确的。

## 常量应该放哪里

常量可以按归属放置。

| 常量类型 | 建议位置 |
| --- | --- |
| Redis key | 独立 key 工具类，例如 `UserProfileKeys` |
| 业务状态 | 枚举，例如 `OrderStatus` |
| 配置项 | `application.yml` + `@ConfigurationProperties` |
| 错误码 | 错误码枚举或错误码类 |
| 通用数字 | 尽量命名后放在使用范围附近 |

不要把所有常量都塞进一个 `Constants` 类。那种类最后会变成杂物间，什么都有，也什么都不好找。

## 枚举比字符串常量更适合状态

如果常量表示一组有限状态，优先考虑枚举。

```java
public enum OrderStatus {
    CREATED,
    PAID,
    SHIPPED,
    FINISHED,
    CANCELED
}
```

枚举能表达取值范围，也能承载行为：

```java
public enum OrderStatus {
    CREATED("待支付"),
    PAID("已支付"),
    FINISHED("已完成");

    private final String label;

    OrderStatus(String label) {
        this.label = label;
    }

    public String label() {
        return label;
    }
}
```

如果用字符串常量，调用方可以随手传 `"PAYED"`、`"paid"`、`"已支付"`，然后你就获得了三个状态和一份混乱。

## 小结

常量处理的原则是：集中定义、按领域归类、隐藏拼接细节、避免魔法值。Redis key 适合用工具类方法生成，业务状态适合用枚举，配置值适合交给配置文件。常量不是小事，它们只是平时太安静，等出错时才显得特别有存在感。
