前端排错并不是盯着控制台里一行红字，然后期待它自己交代罪行。一个看似简单的“按钮没反应”，可能来自事件没有绑定、状态没有更新、接口失败、响应数据不符合约定，或渲染条件把结果隐藏了。高效调试的关键，是把模糊现象逐步缩小为**可验证的假设**。

这篇文章以浏览器 DevTools 为主，结合 Vue 3 项目说明如何查看日志、复现问题、定位运行时错误和网络错误，并给出可用于生产环境的最小监控思路。

## 一、先建立排错路径，而不是四处猜测

遇到问题时，先回答三个问题：

1. **现象是什么**：在哪个页面、经过什么操作、得到什么结果。
2. **预期是什么**：正常情况下页面、接口或状态应该如何变化。
3. **边界在哪里**：问题发生在浏览器、前端代码、网络传输，还是服务端。

可以把常见问题按数据流拆开：

```text
用户操作
  -> 事件处理函数
    -> 前端状态 / 参数组装
      -> HTTP 请求
        -> 服务端响应
          -> 数据转换
            -> 组件重新渲染
```

每一层都能通过证据确认。只要逐层验证，就不必凭感觉同时修改多个地方；那种做法通常只会让原本清楚的问题失去现场。

### 1. 写出最小复现步骤

不要用“偶尔打不开”作为问题描述。应该记录可重复的步骤，例如：

1. 使用测试账号进入“文章列表”。
2. 输入关键字 `Vue` 并点击搜索。
3. 第一次列表正常显示；快速再点击两次搜索后，加载状态一直不消失。

同时记录环境：浏览器和版本、页面地址、账号角色、网络条件、发生时间，以及是否只在生产环境出现。时间、请求 ID 和用户操作顺序，往往比一句“有 bug”有用得多。

### 2. 一次只验证一个假设

例如列表没有更新时，可以按顺序验证：

- 点击事件是否执行？
- 请求是否真的发出？
- 响应状态和内容是否正确？
- 响应数据是否写入状态？
- 模板绑定的是否就是这份状态？

每步都能用断点、日志或 Network 面板确认。若事件根本没有执行，就没有必要先怀疑后端接口；这个顺序并不华丽，却能避免大部分无效劳动。

## 二、浏览器 DevTools：先熟悉四个核心面板

在 Chrome、Edge 等 Chromium 浏览器中按 `F12` 或 `Ctrl + Shift + I` 打开开发者工具。不同浏览器名称略有差异，但核心能力相近。

| 面板 | 主要用途 | 适合回答的问题 |
| ---- | -------- | -------------- |
| `Console` | 日志、异常、表达式求值 | 代码执行到哪里、变量是什么、报错来自哪里？ |
| `Sources` | 源码、断点、调用栈 | 哪一行触发了错误、谁调用了它？ |
| `Network` | 请求、响应、资源加载 | 请求是否发出、参数是否正确、为何失败？ |
| `Elements` | DOM 与样式 | 元素是否渲染、CSS 是否被覆盖、事件是否绑定？ |

调试前建议开启两个选项：

- Console 的 **Preserve log**：页面跳转或刷新后保留日志，适合排查登录跳转、白屏和初始化失败。
- Network 的 **Preserve log**：保留跳转前的请求；必要时勾选 **Disable cache**，避免缓存掩盖资源更新或请求结果。

`Disable cache` 只在 DevTools 保持打开时生效，不应把“关缓存”当作线上问题的修复方案。缓存本身没有错，错的是没有判断它是否参与了问题。

## 三、Console：让日志成为证据，而不是噪声

### 1. 使用正确的日志级别

不要把所有信息都写成 `console.log`。至少区分以下语义：

```ts
console.debug('[post-search] keyword changed', { keyword })
console.info('[post-search] request started', { requestId, keyword })
console.warn('[post-search] empty result', { requestId, keyword })
console.error('[post-search] request failed', { requestId, error })
```

- `debug`：只在排查时需要的细节。
- `info`：关键流程的正常节点，例如请求开始、登录完成。
- `warn`：不符合预期但系统还能继续处理的情况。
- `error`：需要关注的失败，例如未捕获异常、关键请求失败。

给日志加上模块前缀和关键上下文，筛选时可以直接搜索 `[post-search]`。不要只打印“失败了”；至少带上操作、参数摘要、请求 ID、状态码和原始错误对象。密码、token、身份证号和完整响应正文等敏感信息则不应该出现在日志里。

### 2. 查看对象时要注意“延迟展开”

下面的写法很常见：

```ts
const payload = { page: 1, keyword: 'Vue' }
console.log('payload', payload)
payload.page = 2
```

在某些开发者工具中，稍后展开日志对象时看到的可能是修改后的对象状态。若要保留当时的快照，可以输出拷贝：

```ts
console.log('payload snapshot', { ...payload })
```

对嵌套对象可以使用 `structuredClone(payload)`；但它不能复制函数等特殊值。调试时最重要的是知道：控制台展示的对象未必等于打印那一刻的对象。

### 3. 在 Console 中直接验证表达式

断点暂停后或页面正常运行时，可以在 Console 输入表达式检查当前上下文：

```js
location.href
localStorage.getItem('token')
document.querySelector('#search-input')?.value
```

这适合快速验证 DOM、存储和简单变量。对于会修改状态的表达式要格外克制；调试现场已经够脆弱，没必要亲手把证据改掉。

## 四、Sources 断点：停止猜测，查看真实执行路径

日志适合观察流程，断点适合检查某一刻的完整现场。打开 `Sources`，找到对应的 TypeScript、Vue 或 JavaScript 源文件，在行号处单击即可设置断点。

### 1. 优先在边界处下断点

比起在每一行都停住，更推荐从这些边界开始：

- 点击、输入、提交等事件处理函数入口。
- 请求函数调用前后。
- 响应数据转换处。
- 状态赋值处。
- 抛出异常或显示错误提示处。

例如搜索函数：

```ts
async function searchPosts(keyword: string) {
  const requestId = crypto.randomUUID()
  const response = await fetch(`/api/posts?keyword=${encodeURIComponent(keyword)}`, {
    headers: {
      'X-Request-Id': requestId
    }
  })

  if (!response.ok) {
    throw new Error(`搜索失败：${response.status}`)
  }

  return response.json()
}
```

可以先在 `fetch` 前停住确认 `keyword` 和请求地址，再在 `response.ok` 处确认状态码。若请求没有到达此处，沿调用栈向上查找；若到达但状态码异常，再转到 Network 检查完整请求和响应。

### 2. 读懂暂停后的四类信息

代码暂停后，不要只盯着当前行：

- **Scope / 作用域**：查看局部变量、闭包变量和模块变量的实际值。
- **Call Stack / 调用栈**：从当前函数向上看是谁调用了它；第一段属于自己业务代码的栈帧通常最值得看。
- **Breakpoints**：管理、启用或禁用已有断点。
- **Watch / 监视表达式**：持续观察 `loading.value`、`route.query.keyword` 等关键表达式。

单步执行快捷键的含义也应分清：

| 操作 | 常见快捷键 | 用途 |
| ---- | ---------- | ---- |
| Step over | `F10` | 执行当前行，但不进入被调用函数 |
| Step into | `F11` | 进入当前行调用的函数 |
| Step out | `Shift + F11` | 执行完当前函数并返回调用处 |
| Resume | `F8` | 继续运行到下一个断点 |

进入第三方库、框架运行时代码后若与问题无关，使用 Step out 返回业务代码即可。调试不是一次源码考古，先定位职责边界更有效。

### 3. 条件断点和 Logpoint

循环或频繁触发的函数不适合普通断点，否则页面会不停暂停。可以右键断点，改成：

- **条件断点**：只在 `page === 3`、`userId === targetId` 时暂停。
- **Logpoint**：不暂停，只输出例如 `加载第 {page} 页` 的信息。

这两种方式尤其适合排查偶发错误、滚动加载和复杂表单。它们让观测范围足够窄，而不是制造更多干扰。

### 4. 让浏览器在异常发生时暂停

在 Sources 的暂停设置中启用 **Pause on exceptions**。建议先选择“仅在未捕获异常时暂停”；若异常被框架或 `try...catch` 吞掉，再临时切换到“所有异常”。

它很适合解决“控制台有错误，但不知道是哪一段代码最先出错”的问题。暂停时查看调用栈和变量，再决定异常是预期分支还是应该修复的缺陷。

## 五、Network：接口问题不能只看状态码

打开 Network，按类型筛选 `Fetch/XHR`，然后复现操作。点开单个请求后，按以下顺序检查。

### 1. 先确认请求是否存在

如果 Network 中没有请求，问题通常在前端：事件没有触发、条件提前 `return`、防抖没有执行、代码在请求前抛出了异常。

如果请求存在，继续检查它的时间、状态和发起方（Initiator）。同一个接口出现多次时，Initiator 能帮助找到重复调用的函数或组件。

### 2. 核对请求的五项内容

| 项目 | 要检查什么 | 常见错误 |
| ---- | ---------- | -------- |
| URL 与方法 | 路径、查询参数、`GET`/`POST` | 请求了旧地址、参数没有编码 |
| Request Headers | `Authorization`、`Content-Type`、追踪 ID | token 缺失、JSON 请求却未声明类型 |
| Payload | 请求体字段和类型 | `page` 传成字符串、字段名不一致 |
| Status Code | HTTP 状态与重定向 | `401` 未登录、`403` 无权限、`404` 地址错误、`5xx` 服务端失败 |
| Response / Preview | 返回内容和业务错误码 | HTTP 200 但业务 `code` 表示失败 |

HTTP `200` 不等于业务成功。例如服务端可能返回：

```json
{
  "code": "VALIDATION_ERROR",
  "message": "keyword 长度不能超过 50",
  "data": null
}
```

前端应根据项目约定处理业务状态，而不是只写 `response.ok`。接口契约若没有明确，排错会反复变成猜谜；这件事本身就值得被修复。

### 3. 区分几类常见网络失败

- **`401` / `403`**：登录态、权限或跨域预检相关配置可能有问题。先确认请求是否带了正确凭证，再看服务端日志。
- **`404`**：路径、环境变量、代理前缀或 history 路由配置可能错误。
- **`429`**：请求过快或重复请求，检查防抖、按钮禁用、重试策略。
- **`5xx`**：请求通常已到服务端；保存请求 ID、时间、参数摘要，交给后端查对应日志。
- **`(failed)` / `CORS`**：可能是网络中断、证书、DNS、浏览器跨域策略或服务没有响应。Console 往往有更具体原因。
- **请求长期 Pending**：检查接口耗时、取消逻辑、网关连接与浏览器并发限制，不要让 `loading` 永远停留。

排查跨域时要记住：浏览器报 CORS，不表示“前端加一个请求头”就能解决。是否允许来源、方法、请求头和凭证，是服务端响应决定的；前端需要做的是确认真实 Origin、请求方式及预检请求，而不是伪造答案。

### 4. 使用 “Copy as cURL” 复现请求

在 Network 中右键请求可选择 **Copy as cURL**。将它在终端执行，能帮助区分：

- cURL 成功、浏览器失败：更可能是 CORS、Cookie、浏览器扩展或前端请求配置。
- 两者都失败：更可能是接口、环境或服务端数据问题。

复制的命令可能包含 Cookie、Authorization 等敏感凭证。不要把原样命令贴进工单、聊天记录或公开文档；发送前应脱敏。

## 六、DOM、样式与事件：页面“没显示”不一定是没渲染

在 Elements 面板选择页面元素，检查以下事项：

1. DOM 节点是否真的存在。
2. 是否被 `display: none`、`visibility: hidden`、`opacity: 0` 或条件渲染隐藏。
3. 尺寸是否为零，或被父元素的 `overflow: hidden` 裁掉。
4. `z-index` 和定位上下文是否让元素被遮住。
5. Computed 样式最终来自哪一条规则，是否被覆盖。

右键元素可使用 **Break on**，例如在子树发生变化时暂停。它适合排查“某个弹窗刚出现就消失”“列表 DOM 被谁清空”的问题。

事件问题还可以在 Elements 的 Event Listeners 中检查监听器。更直接的做法是在事件处理函数入口打断点，并确认遮罩层、`pointer-events`、禁用状态或表单默认提交是否拦截了点击。

## 七、Vue 3 项目的专门检查点

Vue 会帮你管理 DOM，但不会替你判断状态是否放对、数据是否符合预期。

### 1. 先看组件树和响应式状态

安装 Vue Devtools 后，可在浏览器扩展面板中查看组件树、`props`、`data`、组合式状态和 Pinia 状态。它适合快速确认：

- 当前页面是否挂载了预期组件。
- 父组件传给子组件的 `props` 是否正确。
- `ref`、`computed` 对应的值有没有变化。
- Pinia 中的数据是否更新，而页面是否订阅到它。

工具提供的是观察窗口，不是解释器。看到 `posts` 有值而列表为空时，仍要回到模板检查 `v-if`、`v-for`、过滤条件和键值。

### 2. 常见响应式误区

错误示例：从 `reactive` 对象解构后直接使用，可能丢失响应式连接。

```ts
const state = reactive({ keyword: '', loading: false })
const { keyword, loading } = state
```

推荐使用 `toRefs`：

```ts
const state = reactive({ keyword: '', loading: false })
const { keyword, loading } = toRefs(state)
```

另一个高频问题是异步竞态：较早发出的请求反而较晚返回，覆盖了新搜索结果。可以使用序号忽略过期响应：

```ts
let latestRequest = 0

async function loadPosts(keyword: string) {
  const requestNo = ++latestRequest
  loading.value = true

  try {
    const data = await searchPosts(keyword)
    if (requestNo !== latestRequest) {
      return
    }
    posts.value = data
  } catch (error) {
    if (requestNo === latestRequest) {
      console.error('[post-list] load failed', { keyword, error })
      errorMessage.value = '加载失败，请稍后重试'
    }
  } finally {
    if (requestNo === latestRequest) {
      loading.value = false
    }
  }
}
```

调试这种问题时，在请求发出、响应返回和状态写入处记录 `requestNo` 与 `keyword`，很快就能看出是否发生了乱序覆盖。

### 3. 区分 Vue 警告和真正的根因

Vue 警告通常会指出可疑位置，例如重复的 `key`、未处理的事件或访问了未定义属性。不要无视它们，但也不要把每条警告都当作当前故障的唯一原因。

先确认警告是否能稳定复现，是否与页面异常在同一操作路径上，再沿组件栈和数据流继续验证。控制台很诚实，但它只陈述它观察到的事实，不替你完成因果推理。

## 八、从堆栈信息找到第一处业务代码

运行时错误常见形式：

```text
TypeError: Cannot read properties of undefined (reading 'name')
    at formatUser (user.ts:12:15)
    at UserCard.vue:28:7
```

处理顺序如下：

1. 点击堆栈中最靠前、属于自己项目的文件和行号。
2. 查看该行读取的变量，确认究竟是对象不存在，还是字段不存在。
3. 沿调用栈向上检查这个值从哪里来：接口、props、路由参数还是缓存。
4. 决定应修复数据契约、调用时机，还是在边界处做合理的空值处理。

不要用可选链把所有错误压下去：

```ts
// 这可能只是隐藏了数据不完整的问题
const name = user?.profile?.name ?? '-'
```

可选链适合“字段缺失是允许的”场景；若用户资料按契约必须存在，就应该调查缺失原因，并在用户可见处显示合适错误或降级状态。吞掉异常得到的往往不是稳定，只是更安静的错误。

## 九、生产环境：日志、Source Map 与错误监控

本地能打开源码，但生产构建通常会压缩、拆包和混淆。没有正确的 Source Map，错误堆栈可能只指向难以阅读的压缩文件位置。

### 1. Source Map 的发布策略

生产环境可以生成 Source Map 并上传到错误监控平台，用于将压缩堆栈还原为源代码文件和行号。通常不建议把完整 Source Map 公开部署在静态站点上，因为它可能暴露源码和模块结构。

发布时应保证三者版本一致：

- 前端构建产物。
- Source Map 文件。
- 监控事件中的 `release` 版本号。

任何一个不一致，平台都可能把错误还原到错误版本。这个问题很隐蔽，因此版本号应由构建流水线统一生成，而不是人工随手填写。

### 2. 捕获全局错误，但保留原始上下文

可以在应用启动处登记全局兜底；这里的代码应只做采集和上报，不能让错误处理器再次抛错：

```ts
type ErrorContext = {
  type: 'runtime' | 'promise'
  message: string
  stack?: string
  url: string
  release: string
}

function reportError(context: ErrorContext) {
  navigator.sendBeacon('/api/frontend-errors', JSON.stringify(context))
}

window.addEventListener('error', (event) => {
  reportError({
    type: 'runtime',
    message: event.message,
    stack: event.error instanceof Error ? event.error.stack : undefined,
    url: location.href,
    release: import.meta.env.VITE_APP_RELEASE
  })
})

window.addEventListener('unhandledrejection', (event) => {
  const reason = event.reason
  reportError({
    type: 'promise',
    message: reason instanceof Error ? reason.message : String(reason),
    stack: reason instanceof Error ? reason.stack : undefined,
    url: location.href,
    release: import.meta.env.VITE_APP_RELEASE
  })
})
```

真实项目还应增加用户匿名标识、路由、浏览器版本、网络类型和采样率，并对字段做脱敏和长度限制。上报接口自身也要避免无限重试，否则故障期间会制造第二场故障，实在很没有必要。

### 3. 请求日志要能关联前后端

为每次关键操作生成 `requestId`，放入请求头并在前端日志、后端日志和错误监控事件中记录它：

```ts
async function request<T>(url: string, init: RequestInit = {}) {
  const requestId = crypto.randomUUID()
  const response = await fetch(url, {
    ...init,
    headers: {
      ...init.headers,
      'X-Request-Id': requestId
    }
  })

  if (!response.ok) {
    throw new Error(`请求失败：${response.status}，requestId=${requestId}`)
  }

  return response.json() as Promise<T>
}
```

这样当前端报告“保存失败”时，后端能用同一个 ID 查到网关、应用和数据库相关日志。没有关联 ID 的分布式排错，像是在一堆同样的纸片里寻找某一张；理论上能找到，实际常常令人失去耐心。

## 十、一个完整案例：点击保存后页面一直转圈

假设用户反馈：编辑文章后点击保存，按钮一直显示“保存中”。按下面顺序排查：

1. **复现并保留现场**：打开 Console、Network 的 Preserve log，按用户步骤操作。
2. **确认事件**：在 `handleSubmit` 首行打断点；若未停住，检查按钮禁用、遮罩、事件绑定和表单默认行为。
3. **确认状态**：断点中检查 `loading.value`、表单值和校验结果；确认没有在请求前 `return` 后却遗漏复位 `loading`。
4. **确认请求**：在 Network 看是否有 `POST /api/posts/:id`，核对 Payload、token、状态码和响应正文。
5. **确认异步分支**：若请求成功但一直转圈，在 `try`、`catch`、`finally` 分别下断点，看 `finally` 是否执行、是否有更晚的请求覆盖状态。
6. **确认渲染**：若 `loading.value` 已经是 `false` 但按钮仍显示“保存中”，检查组件收到的 props、模板条件和 CSS。

可靠的提交代码通常会将状态复位放在 `finally`，而不是只放在成功分支：

```ts
async function handleSubmit() {
  if (loading.value) {
    return
  }

  loading.value = true
  errorMessage.value = ''

  try {
    await savePost(form.value)
    successMessage.value = '保存成功'
  } catch (error) {
    console.error('[post-edit] save failed', { id: form.value.id, error })
    errorMessage.value = '保存失败，请检查网络后重试'
  } finally {
    loading.value = false
  }
}
```

这里的目标不是“让异常看不见”，而是无论成功还是失败，页面都回到一个用户可以继续操作的确定状态。

## 十一、可直接使用的排错清单

### 页面行为异常

- 是否有稳定复现步骤、页面地址和发生时间？
- Console 是否存在同一操作链路上的错误或警告？
- 事件处理函数是否执行？
- 关键状态在操作前后是否按预期变化？
- DOM 未出现，还是出现后被样式隐藏？

### 接口或数据异常

- Network 中是否有对应请求？
- URL、方法、参数、请求头和请求体是否符合接口契约？
- HTTP 状态码与业务错误码分别是什么？
- 是否有重复请求、取消请求或响应乱序？
- 能否用脱敏后的 cURL 或请求 ID 与后端共同复现？

### 线上偶发异常

- 错误监控是否记录了堆栈、路由、浏览器、release 和发生次数？
- Source Map 是否与当前 release 对应？
- 是否能按错误类型、版本、浏览器或接口关联 ID 聚合？
- 日志是否已经脱敏，且不会因上报失败影响正常业务？

## 十二、总结

前端调试的核心不是记住多少 DevTools 功能，而是建立从现象到证据、从证据到根因的过程：

- 用清晰的复现步骤固定问题。
- 用 Console 观察关键流程和上下文。
- 用 Sources 的断点、调用栈和异常暂停还原执行路径。
- 用 Network 检查完整请求、响应与时序，而不只看状态码。
- 用 Elements 和 Vue Devtools 确认 DOM、样式、组件与响应式状态。
- 用 Source Map、release 和 request ID 让生产错误可以追踪。

排错并不神秘。把每个猜测替换为一次验证，把每次验证留成可关联的证据，问题最终会收敛到具体的代码、数据或契约上。毕竟，错误不会因为你避开它就消失；只是会挑一个更不合时宜的时机回来。
