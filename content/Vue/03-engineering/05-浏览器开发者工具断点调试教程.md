前端代码的断点通常就打在浏览器的开发者工具（DevTools）里，主要使用 `Sources` 面板。它的作用不是让页面“卡住看看”，而是让 JavaScript 在某一行暂停，使你能在那个瞬间检查变量、调用者、执行路径和页面状态。

如果 `console.log` 像在路边问路，断点就是直接走进现场。两者并不冲突：日志适合观察连续流程，断点适合在一个关键时刻把所有上下文固定下来。

本文以 Chrome、Edge 等 Chromium 浏览器为主。Firefox 的功能与术语基本相近；Safari 需要先在设置中启用开发者菜单。示例使用 Vue 3，但断点机制属于浏览器，与是否使用 Vue、React 或原生 JavaScript 没有本质区别。

## 一、断点到底做了什么

考虑一个搜索函数：

```ts
async function searchPosts() {
  loading.value = true
  errorMessage.value = ''

  try {
    const response = await fetch(`/api/posts?keyword=${keyword.value}`)
    posts.value = await response.json()
  } catch (error) {
    errorMessage.value = '加载失败'
  } finally {
    loading.value = false
  }
}
```

在 `fetch` 这一行打断点后，当用户点击搜索、代码执行到这里时，浏览器会暂停 JavaScript：

```text
点击搜索
  -> searchPosts() 开始执行
    -> 在 fetch 行暂停
       -> 查看 keyword、loading、请求地址、调用栈
       -> 单步执行或继续运行
    -> 再继续后，浏览器才会发送请求
```

暂停期间可以回答这些问题：

- `keyword.value` 到底是什么？空格、旧值或错误编码是否已经出现？
- `loading.value` 是否在正确时机改变？
- 这次调用来自按钮点击、路由监听，还是某个重复触发的 `watch`？
- 当前请求地址是否正确？

断点只暂停当前页面的 JavaScript 执行。网络响应、CSS 动画和浏览器本身不一定完全停下，因此不要把“页面暂停”理解成整个世界都被冻结；浏览器没有那么体贴。

## 二、打开开发者工具与 Sources 面板

### 1. 常用打开方式

| 系统 | 打开 DevTools |
| ---- | ------------- |
| Windows / Linux | `F12` 或 `Ctrl + Shift + I` |
| macOS | `Command + Option + I` |

打开后选择顶部的 `Sources` 标签。若标签被折叠到 `>>` 中，也可以从那里找到。中文浏览器界面通常将它翻译为“源代码”。

`Sources` 的典型区域如下：

```text
左侧：文件树（Page / 工作区 / 扩展程序）
中间：源码编辑器与行号
右侧：断点、作用域、调用栈、监视表达式、暂停控制按钮
底部：Console 抽屉，可在暂停时直接执行表达式
```

开发者工具停靠在页面右边时编辑区可能很窄。可以点击右上角三点菜单，选择停靠到下方、独立窗口，或暂时放大 DevTools。看不清代码还要坚持调试，大概和隔着雾找针差不多。

### 2. 找到自己的源文件

启动本地 Vite / Vue 项目后，文件树常见位置有：

```text
Page
  localhost:5173
    src/
      views/
        PostList.vue
      api/
        post.ts
```

开发环境通常可以直接看到 `.vue`、`.ts` 等源文件，因为构建工具提供了 Source Map。文件树很深时，使用快捷键更快：

- `Ctrl + P`（macOS 为 `Command + P`）：按文件名快速打开文件。
- `Ctrl + Shift + P`（macOS 为 `Command + Shift + P`）：打开命令菜单，可搜索 “Disable JavaScript”“Show Network conditions” 等命令。
- `Ctrl + Shift + F`：在所有已加载源码中搜索文本。

若只看到 `assets/index-xxxx.js` 之类压缩后的文件，先不要急着在里面逐字符阅读。后文会解释 Source Map 和“断点为什么打不上”的问题；开发模式下优先确认打开的是本地开发地址和正确的构建环境。

## 三、最基础的断点：在行号上单击

在 Sources 中打开目标文件，找到想暂停的可执行语句，**单击左侧行号**。行号会出现蓝色标记，表示普通断点已经生效。

下面是一个 Vue 组件中的完整示例：

```vue
<script setup lang="ts">
import { ref } from 'vue'

type Post = {
  id: number
  title: string
}

const keyword = ref('')
const posts = ref<Post[]>([])
const loading = ref(false)
const errorMessage = ref('')

async function searchPosts() {
  loading.value = true
  errorMessage.value = ''

  try {
    const response = await fetch(`/api/posts?keyword=${encodeURIComponent(keyword.value)}`)
    if (!response.ok) {
      throw new Error(`请求失败：${response.status}`)
    }
    posts.value = await response.json()
  } catch (error) {
    console.error('[post-list] search failed', error)
    errorMessage.value = '加载失败，请稍后重试'
  } finally {
    loading.value = false
  }
}
</script>

<template>
  <input v-model="keyword" placeholder="搜索文章">
  <button :disabled="loading" @click="searchPosts">搜索</button>
  <p v-if="errorMessage">{{ errorMessage }}</p>
  <p v-else-if="loading">加载中…</p>
  <ul v-else>
    <li v-for="post in posts" :key="post.id">{{ post.title }}</li>
  </ul>
</template>
```

第一次练习可以在 `const response = await fetch(...)` 上打断点，然后：

1. 回到页面，在输入框输入 `Vue`。
2. 点击“搜索”。
3. 页面会停在断点对应的行，DevTools 自动切到 Sources。
4. 在右侧 Scope 中展开 `Local`，查看 `keyword`、`loading` 等变量。
5. 在底部 Console 输入 `keyword.value` 或 `encodeURIComponent(keyword.value)`，验证当前表达式。
6. 点击继续按钮，让请求继续发送。

注意应打在**会执行的语句**上。注释、空行、类型声明、纯 `import` 声明通常不能停住；浏览器会把断点自动挪到附近可执行的位置。

## 四、暂停之后看什么：不要只盯着当前行

断点命中后，右侧面板是主要信息来源。

### 1. Scope：变量当前的真实值

`Scope`（作用域）通常包含：

- `Local`：当前函数的局部变量和参数。
- `Closure`：闭包捕获的变量；Vue 组合式 API 的 `ref` 常会出现在这里。
- `Global`：全局对象，例如 `window`。

展开变量时尤其要确认“值”而不是变量名。比如 `keyword` 是 `RefImpl`，真正文本位于 `keyword.value`；`posts` 是一个 `ref`，数组位于 `posts.value`。看到对象存在并不能证明内部数据正确。

可以右键变量选择 **Add to watch**，把它加入 Watch（监视表达式）区域。适合持续观察：

```js
keyword.value
loading.value
posts.value.length
route.query.page
```

### 2. Call Stack：是谁调用了当前函数

`Call Stack`（调用栈）从上到下展示当前函数及其调用者。若 `searchPosts` 被执行了两次，调用栈能帮助判断一次来自按钮事件，另一次是否来自 `watch`、`onMounted` 或路由守卫。

```text
searchPosts          PostList.vue:19
onSearchClick        PostList.vue:42
callWithErrorHandling runtime-core.esm-bundler.js
```

优先查看属于自己项目的栈帧。框架栈帧不是错误，只是 Vue 正在正常调度事件；没有明确目标就一路钻进框架源码，通常会让问题从一个变成十个。

单击调用栈中的上一层，可跳转到调用位置并查看那一层的局部变量。

### 3. Console：在暂停现场验证表达式

暂停时打开 Console，输入的表达式会在当前栈帧上下文中执行：

```js
keyword.value.trim()
response?.status
posts.value.map(post => post.id)
```

这很适合验证假设，但要避免随手修改状态，例如 `posts.value = []`、调用删除接口等。断点提供的是现场，不是允许你篡改现场的许可证。

## 五、四个单步按钮怎么用

Sources 顶部暂停控制区常见操作如下：

| 操作 | 常见快捷键 | 什么时候使用 |
| ---- | ---------- | ------------ |
| Resume script execution | `F8` | 继续运行到下一个断点或代码结束 |
| Step over | `F10` | 执行当前行，不进入调用的函数 |
| Step into | `F11` | 进入当前行调用的函数内部 |
| Step out | `Shift + F11` | 执行完当前函数，回到调用者 |

不同操作系统、浏览器扩展或笔记本功能键设置可能占用 `F8` 至 `F11`。按钮图标始终比快捷键可靠：向右三角是继续，弯箭头通常表示跨过，向下箭头表示进入，向上箭头表示跳出。

一个实用原则：

- 想知道“这一行执行后变量怎么变”时用 **Step over**。
- 确定问题在被调用函数内部时才用 **Step into**。
- 误入框架、请求库或不相关工具函数时用 **Step out** 回到业务代码。
- 只想让程序继续跑时用 **Resume**。

### 异步代码为何会“跳来跳去”

执行到 `await fetch(...)` 时，当前函数会先让出执行权，响应回来后再从 `await` 后面继续。单步时看到代码暂时跳到浏览器或框架内部，并不意味着断点失效。

更容易理解的调试方法是在三个位置分别下断点：请求发出前、`await` 返回后、状态赋值后。这样可以把“请求有没有发出”“响应有没有回来”“数据有没有写入页面状态”分开确认。

## 六、比普通断点更有用的六种断点

普通行断点适合首次定位。代码频繁执行、问题只在特定条件发生，或你根本不知道对应文件在哪里时，应选择更有针对性的断点。

### 1. 条件断点：只在特定数据出现时暂停

右键行号或已有断点，选择 **Add conditional breakpoint**，填入一个返回布尔值的 JavaScript 表达式。

例如列表加载函数会被调用很多次，但只想在第三页暂停：

```js
page.value === 3
```

只想在搜索关键字包含 `error` 时暂停：

```js
keyword.value.includes('error')
```

条件表达式在每次经过该行时都会执行，因此应保持简单、无副作用。不要在其中发请求、修改数组或调用可能改变页面状态的方法。

### 2. Logpoint：不暂停，只按断点位置记录日志

右键行号选择 **Add logpoint**。它会在代码经过时向 Console 输出信息，但页面不会暂停。

适合观察高频函数、滚动事件、重复请求或线上复现困难的问题。例如在状态赋值前增加：

```text
准备写入文章列表：{posts.length}，关键字：{keyword.value}
```

花括号中的表达式会在执行时被求值。Logpoint 的好处是无需修改源码，也不会像 `console.log` 那样被遗忘在提交里。既然临时观察可以不留下痕迹，就没有理由把调试语句养成项目里的常住人口。

### 3. Exception breakpoint：异常抛出时立即暂停

在 Sources 的暂停控制区找到“暂停异常”图标，可选择：

- **Uncaught exceptions**：仅未捕获异常暂停，适合作为默认选项。
- **Caught exceptions**：即使异常会被 `try...catch` 捕获也暂停，适合排查异常被悄悄吞掉的情况。

例如下面代码把请求失败转换成页面提示：

```ts
try {
  const response = await fetch('/api/posts')
  if (!response.ok) {
    throw new Error(`请求失败：${response.status}`)
  }
} catch (error) {
  errorMessage.value = '加载失败'
}
```

若只启用未捕获异常，`throw` 后会被 `catch` 接住，浏览器不会暂停。启用所有异常后会停在 `throw` 行，让你观察状态码、调用栈和原始响应。排查完成后应切回未捕获异常，否则框架内部用于控制流程的异常也可能频繁打断你。

### 4. Event Listener breakpoint：不知道点击事件在哪时使用

Sources 右侧展开 **Event Listener Breakpoints**，可勾选：

- `Mouse` → `click`：任意点击事件触发时暂停。
- `Keyboard`：键盘输入或按键事件时暂停。
- `Control` → `submit`：表单提交时暂停。
- `Timer`：定时器回调时暂停。

当“按钮点了没反应”，却找不到绑定函数时，勾选 `Mouse > click` 后回到页面点击按钮。浏览器会在事件处理链路中暂停；看 Call Stack，就能找到真正的业务事件处理函数。

这个断点覆盖范围很大。页面上任何点击都可能暂停，因此只在找入口时临时启用，找到后立即关闭。用捕鱼网抓一条鱼是可行的，只是别忘了收网。

### 5. XHR / fetch breakpoint：请求即将发送时暂停

Sources 右侧展开 **XHR/fetch Breakpoints**，点击 `+`，输入 URL 中稳定的一部分，例如：

```text
/api/posts
```

之后任何 URL 包含这段文本的 `XMLHttpRequest` 或 `fetch` 请求，浏览器都会在请求发送前暂停。它特别适合：

- 不知道哪个组件发起了某个接口。
- 发现同一接口重复请求，想找每次的调用者。
- 想在请求发出前检查参数、token 和拼接后的 URL。

断点命中后查看 Call Stack；不要只去 Network 看结果。Network 告诉你“请求发生了什么”，XHR/fetch 断点能告诉你“是谁让它发生”。

### 6. DOM breakpoint：元素为什么突然消失

在 `Elements` 面板选中某个 DOM 节点，右键 **Break on**，可选择：

- `subtree modifications`：子节点增删或修改时暂停。
- `attribute modifications`：`class`、`style` 等属性变化时暂停。
- `node removal`：节点被删除时暂停。

例如弹窗刚显示又消失，先选中弹窗根元素，在 `node removal` 上打断点；当某段代码、框架渲染或第三方组件删除它时，浏览器会暂停。通过调用栈可找到修改 DOM 的源头。

Vue 项目应优先检查状态、`v-if`、`v-show` 和组件 props。DOM 断点是当你已确认 DOM 确实被异常改动、但不知道是谁改的最后一段追踪线，不是每次页面问题的第一选择。

## 七、在代码中写 debugger：快速验证一次性的路径

还可以在源码中临时写入：

```ts
async function submitPost() {
  debugger
  await savePost(form.value)
}
```

当 DevTools 打开时，执行到 `debugger` 语句会自动暂停，效果类似在这一行打断点。它适合快速验证某条明确路径，尤其是文件难以从 Sources 找到时。

但它只是临时工具：确认问题后应删除，不要把 `debugger` 提交到生产代码。若 DevTools 未打开，浏览器通常不会因为这条语句而对普通用户暂停；这不代表它可以安心留在代码里。

## 八、完整实战：搜索接口为何被调用两次

假设页面出现两个现象：第一次进入页面会请求一次，点击搜索后却一次发出两条完全相同的请求。不要先在每个可能位置加入 `console.log`，按以下步骤查。

### 1. 先在 Network 确认事实

打开 Network，筛选 `Fetch/XHR`，输入 `/api/posts`，然后点击搜索。确认确实有两条请求，而不是一条请求产生了两份 UI 数据。记录它们的时间和 Initiator 列。

### 2. 在 XHR/fetch Breakpoint 填入接口片段

在 Sources 的 XHR/fetch Breakpoints 新增：

```text
/api/posts
```

再次点击搜索。第一次暂停时，查看 Call Stack：

```text
searchPosts       PostList.vue:22
onMounted         PostList.vue:36
```

这表示页面初始化调用了 `searchPosts`。按 `F8` 继续，第二次暂停后如果调用栈是：

```text
searchPosts       PostList.vue:22
watch.immediate   PostList.vue:47
```

那么根因已经非常明确：初始化逻辑与一个 `immediate: true` 的 `watch` 同时触发了请求。

```ts
onMounted(() => {
  searchPosts()
})

watch(keyword, () => {
  searchPosts()
}, { immediate: true })
```

修复不是给接口加一个“莫名其妙的防抖”就结束，而是决定初始化请求究竟由谁负责。保留其中一处即可：

```ts
watch(keyword, () => {
  searchPosts()
}, { immediate: true })
```

如果用户持续输入时确实会触发请求，再针对输入场景增加防抖。先识别重复调用来源，再选择正确的控制方式；顺序颠倒时，代码通常只会更像补丁集合。

## 九、断点打不上、没有停住，逐项检查

“我在行号上点了，为什么代码没有停？”最常见的原因如下。

### 1. 当前页面没有执行这一行

断点不会主动让代码运行。确认操作路径是否真的触发了函数：路由是否进入正确页面、按钮是否被禁用、条件分支是否提前 `return`、事件是否被遮罩层拦截。

不确定入口时，先用 Event Listener breakpoint 的 `click` 或 XHR/fetch breakpoint 找到实际执行路径。

### 2. 打开了错误的文件或错误的环境

可能本地编辑的是 `src/views/PostList.vue`，浏览器打开的却是旧开发服务、另一个端口或已经部署的测试环境。检查地址栏中的域名和端口，确认热更新已生效；必要时在页面显眼处暂时改一个文本，验证当前浏览器确实加载了这份代码。

### 3. Source Map 不存在或版本不匹配

浏览器实际执行的是构建后的 JavaScript。Source Map 负责把它映射回 TypeScript 和 `.vue` 文件的原始行号。开发模式下通常由 Vite 自动提供；生产构建若未生成、未部署或版本不匹配 Source Map，可能出现：

- Sources 中只有压缩后的 `index-xxxx.js`。
- 断点变成空心或灰色，无法绑定。
- 断点停在附近但不是预期行。

排查时应确认构建配置、部署产物和 Source Map 来自同一个 release。不要把本地源码的行号直接当成生产压缩文件的行号。

### 4. 断点被禁用，或脚本已被忽略

Sources 的“禁用所有断点”按钮若处于启用状态，所有断点都会暂时失效。右侧 Breakpoints 列表中也可单独勾选、取消某条断点。

如果把某个脚本加入 Ignore List（以前也叫 blackbox），调试器会跳过它。这对忽略框架代码有用，但误把业务目录加入后，自然不会在里面暂停。检查 Settings → Ignore List 中的规则。

### 5. 代码在 Worker、iframe 或浏览器扩展中运行

Web Worker、Service Worker、iframe 和浏览器扩展各自有独立的执行上下文。需要在 Sources 的上下文选择器或文件树中切换到对应 Worker / frame；页面主线程的断点无法自动拦截它们。

### 6. 刷新后断点消失

普通浏览器断点通常会按 URL 和 Source Map 尝试保留，但文件指纹变化、构建更新或无痕窗口都可能使其消失。对需要反复复现的问题，可以使用 Local Overrides 或将明确的临时 `debugger` 放入本地分支；完成后务必清理。

## 十、断点与 Network、Console 应该怎样配合

断点不是唯一工具，最稳妥的组合如下：

```text
用户操作
  -> Event Listener / 行断点：确认事件进入业务函数
  -> XHR/fetch 断点：确认谁发起请求、请求参数是什么
  -> Network：确认 HTTP 请求、响应和时序
  -> 异常断点：确认错误最早从哪里抛出
  -> Console / Scope：确认变量、堆栈与状态
  -> Elements / DOM 断点：确认最终渲染是否被异常修改
```

例如“接口返回成功但页面没有数据”：

1. 在 Network 确认响应体确实有数组。
2. 在 `posts.value = await response.json()` 打断点，看赋值前后的 `posts.value`。
3. 若数据已经写入，在模板的 `v-for` 条件、筛选计算属性或子组件 props 处打断点。
4. 若状态正确而 DOM 仍为空，再到 Elements 检查 `v-if`、样式和节点是否被移除。

把问题放到这一条链路中，就不会因为看到一个红色控制台错误，便武断地认定“肯定是后端的问题”。这种判断并不比掷硬币可靠，只是语气通常更笃定。

## 十一、生产环境调试边界

生产环境可以调试，但比本地环境需要更多约束：

- 不要直接在真实用户的敏感操作中随意暂停；暂停会影响当前页面交互。
- 不在 Console 输出 token、Cookie、身份证号、完整用户资料或接口密钥。
- 若使用 Source Map，应将它上传到错误监控平台或受控存储，而不是默认公开给所有访问者。
- 通过 `release`、请求 ID、时间、用户匿名标识和错误堆栈关联线上问题，再在测试环境复现。
- 对偶发问题优先用 Logpoint、错误监控和请求关联日志，避免靠长期保留的 `debugger`。

线上排错的目标是准确收集证据并安全复现，不是把生产页面变成私人实验台。两者的差别并不微妙。

## 十二、第一次使用断点的最短操作清单

如果你现在只想解决一个按钮或接口问题，按下面做即可：

1. 用 `F12` 打开 DevTools，进入 `Sources`。
2. 用 `Ctrl + P` 搜索相关 `.vue` 或 `.ts` 文件。
3. 在点击处理函数或请求前一行的行号上单击，添加普通断点。
4. 回页面复现操作；停住后先看 Scope 的局部变量，再看 Call Stack 的业务调用者。
5. 用 `F10` 跨过一行，或用 `F8` 继续运行；不要一开始就钻进框架源码。
6. 若找不到入口，添加 `Mouse > click` 事件断点；若找不到请求来源，添加 XHR/fetch 断点。
7. 若只在异常时出问题，开启“未捕获异常暂停”；被吞掉的异常再临时开启“所有异常暂停”。
8. 用 Network 验证请求和响应，用 Console 验证表达式，用 Elements 验证最终 DOM。
9. 找到根因后删除临时 `debugger`、Logpoint 和不再需要的断点。

## 十三、总结

开发者工具里的断点，是前端调试最直接的观察手段：

- 在 `Sources` 的行号上单击，可以设置普通断点。
- 暂停后重点看 Scope、Call Stack、Watch 和当前上下文的 Console。
- `F10` 跨过、`F11` 进入、`Shift + F11` 跳出、`F8` 继续，分别对应不同的观察范围。
- 条件断点、Logpoint、异常断点、事件断点、XHR/fetch 断点和 DOM 断点，解决的是不同的定位问题。
- 断点不生效时，优先确认代码是否执行、环境是否正确、Source Map 是否匹配、断点是否被禁用。

断点的价值不是让你逐行“看代码运行”，而是用最少的暂停验证最关键的假设。知道该停在哪里，往往比知道怎样多按一次 `F11` 更重要。
