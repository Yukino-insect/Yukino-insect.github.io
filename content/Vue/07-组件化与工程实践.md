会写 Vue 语法只是开始。真实项目要长期维护，就必须考虑组件边界、命名、样式复用、跨端兼容、接口错误、构建校验和调试流程。否则项目能跑，但会越来越难改。能跑不等于能维护，这一点前后端都一样。

本文以常见的论坛类 Vue/uni-app 工程为参照，讲如何把页面、组件、接口、状态和构建流程组织成一个可维护的整体。

## 一、页面与组件的边界

页面负责组织业务流程，组件负责封装可复用 UI 和局部交互。

例如首页 `pages/index/index.vue` 负责：

- 加载首页帖子。
- 加载热榜。
- 加载话题。
- 下拉刷新。
- 触底加载更多。
- 切换推荐、最新、最热。
- 组织瀑布流左右列。

而 `WaterfallCard.vue` 负责：

- 展示单个帖子卡片。
- 显示封面图。
- 显示标题和作者。
- 处理点赞点击。
- 打开帖子详情。

这就是合理拆分。页面管理列表和数据流，卡片管理单项展示和单项操作。

## 二、组件输入输出

一个好组件应该有清晰输入和输出。

`WaterfallCard.vue` 的输入：

```ts
const props = defineProps<{ post: Post }>()
```

它的输出不是 emit，而是自己调用导航和 store：

```ts
function open() {
  navPostDetail(props.post.id, props.post.author.seed)
}

function like() {
  if (!requireLogin('like')) return
  void feed.toggleFlag(props.post.id, 'liked')
}
```

这种写法适合业务组件，因为帖子卡片本身就强绑定信息流业务。

而 `ImageGrid.vue` 更像表单子组件，它不应该自己决定如何选择图片或删除图片，所以使用 emit：

```ts
defineEmits<{
  (e: 'add'): void
  (e: 'remove', index: number): void
}>()
```

判断标准：

- 通用展示组件：多用 props + emit。
- 强业务组件：可以直接使用业务 store 和导航。
- 基础 UI 组件：尽量不要依赖业务 API。
- 页面组件：可以编排多个 store、API 和组件。

## 三、避免组件职责膨胀

组件变复杂通常有几个信号：

- 一个 `.vue` 文件超过几百行。
- `script` 中有多个互不相关的业务流程。
- 模板里出现大量嵌套条件。
- 样式选择器越来越多且互相影响。
- 修改一个功能会影响另一个功能。

处理方式：

- 把重复 UI 拆成子组件。
- 把复杂逻辑抽成 composable。
- 把纯函数放到 `utils`。
- 把共享数据放到 store。
- 把接口请求放到 API 模块。

但不要为了拆而拆。一个组件如果只有当前页面使用，且逻辑不复杂，留在页面里也可以。工程不是比谁文件多。

## 四、组合函数实践

`src/composables/useLoginGate.ts` 是一个典型组合函数。

它适合处理这种逻辑：

```text
用户点击需要登录的操作
 -> 检查是否登录
 -> 未登录打开登录弹窗
 -> 已登录继续执行原操作
```

业务组件使用：

```ts
const requireLogin = useLoginGate()

function like() {
  if (!requireLogin('like')) return
  void feed.toggleFlag(props.post.id, 'liked')
}
```

组合函数的优点：

- 避免每个组件重复判断登录。
- 登录弹窗策略可以统一修改。
- 组件代码更聚焦。
- 可以复用 store、computed、生命周期。

适合抽 composable 的逻辑通常具有这些特征：

- 被多个组件复用。
- 包含响应式状态。
- 包含生命周期。
- 包含跨组件一致的交互规则。

## 五、表单组件

项目中 `compose` 目录包含：

```text
EditorShell.vue
FormField.vue
ImageGrid.vue
SettingRow.vue
TopicPicker.vue
```

这是发布编辑场景的组件集合。

表单页面要考虑：

- 字段初始值。
- 输入绑定。
- 校验。
- 图片选择。
- 话题选择。
- 提交中状态。
- 提交失败回显。
- 成功后刷新列表或跳转。

表单子组件一般不直接提交后端，而是把变化交给父页面。原因是提交往往需要组合多个字段，父页面更适合掌握完整上下文。

## 六、图片组件

`ImageGrid.vue` 展示图片九宫格。它的关键点：

### 1. 固定比例

```css
.grid-item {
  width: calc((100% - 16px) / 3);
  padding-bottom: calc((100% - 16px) / 3);
  position: relative;
}
```

通过 `padding-bottom` 撑出正方形。这种方式兼容性较好。

### 2. 绝对定位填充

```css
.full-absolute {
  position: absolute;
  left: 0;
  top: 0;
  width: 100%;
  height: 100%;
}
```

图片和占位图都填满格子。

### 3. 删除按钮覆盖

```css
.close-btn {
  position: absolute;
  top: 4px;
  right: 4px;
  z-index: 2;
}
```

### 4. 事件停止冒泡

```vue
<view class="close-btn" @click.stop="$emit('remove', i)">
</view>
```

删除按钮点击不应该触发图片预览或外层点击。

这些细节看起来小，但图片上传体验基本就是由这些细节堆出来的。

## 七、列表与瀑布流

首页信息流使用左右两列：

```ts
const waterfallColumns = computed(() => splitPostsIntoColumns(posts.value))
const leftCol = computed(() => waterfallColumns.value[0] || [])
const rightCol = computed(() => waterfallColumns.value[1] || [])
```

模板：

```vue
<view class="waterfall" :key="active">
  <view class="wf-col wf-col-left">
    <WaterfallCard v-for="p in leftCol" :key="p.id" :post="p" />
  </view>
  <view class="wf-col wf-col-right">
    <WaterfallCard v-for="p in rightCol" :key="p.id" :post="p" />
  </view>
</view>
```

瀑布流要注意：

- 图片加载前要占位，减少抖动。
- `key` 要稳定。
- 加载更多时避免重复请求。
- 切换 tab 时要重置列表状态。
- 触底加载要有节流或 loading 防重复。

项目中 `loadingMore` 就是防重复请求的关键状态。

## 八、空状态、加载状态和失败状态

一个完整页面至少要考虑：

```text
初始加载
加载成功且有数据
加载成功但为空
加载失败
下拉刷新
加载更多
没有更多
登录失效
```

首页 footer 文案就是状态机：

```ts
const footerText = computed(() => {
  if (loadingNextSession.value) return '正在加载下一轮内容'
  if (loadingMore.value) return '正在加载更多'
  if (hasMore.value) return '- 滑动到底继续加载 -'
  if (canStartNextSession.value) return '- 点击开启下一轮内容 -'
  return '- 没有更多帖子了 -'
})
```

这种 computed 比在模板里写一串条件更清楚。

## 九、样式组织

建议分三层：

```text
全局 token
 -> 页面布局样式
   -> 组件局部样式
```

全局 token 在 `src/styles/tokens.css`：

```css
:root {
  --brand: #ff5a47;
  --bg-2: #f6f6f8;
}
```

页面样式负责大结构：

```css
.app {}
.scroller {}
.waterfall {}
```

组件样式负责内部细节：

```css
.wfItem {}
.cover {}
.meta {}
```

不要让页面样式深度控制子组件内部结构。否则组件就失去独立性。

## 十、跨端兼容

uni-app 跨端开发要注意：

- 优先使用 `uni.*` API。
- 优先使用 `view`、`text`、`image` 等跨端组件。
- 小程序端对 CSS 支持不完全等同浏览器。
- 条件编译只在必要时使用。
- 事件名和事件对象可能有差异。
- H5 能跑不代表小程序一定能跑。

项目中微信分享使用条件编译：

```ts
// #ifdef MP-WEIXIN
showWechatShareMenu()
// #endif
```

这是合理的，因为微信分享菜单是平台能力。

## 十一、环境配置与代理

`vite.config.ts` 配置了开发代理：

```ts
server: {
  proxy: {
    '/api': {
      target: backendTarget,
      changeOrigin: true,
    },
    '/files': {
      target: backendTarget,
      changeOrigin: true,
    },
  },
}
```

开发 H5 时，浏览器请求前端服务器的 `/api`，再由 Vite 代理转发到后端。这样能减少跨域问题。

生产环境则通常通过 `VITE_API_BASE` 或部署网关决定请求地址。

注意：前端环境变量不是秘密。只要打包进客户端，用户就能看到。

## 十二、类型检查

项目脚本：

```bash
npm run type-check
```

实际执行：

```bash
vue-tsc --noEmit
```

`vue-tsc` 能检查 `.vue` 文件中的 TypeScript，包括 props、模板引用、导入类型等。

建议在这些场景运行：

- 提交代码前。
- 改 API 类型后。
- 改 store 后。
- 改组件 props 后。
- 升级 Vue、TypeScript、uni-app 后。

类型检查不是形式主义。它是前端项目最便宜的一道质量门。

## 十三、构建检查

常用构建：

```bash
npm run build:h5
npm run build:mp-weixin
```

类型检查通过，不代表构建一定通过。构建还会检查：

- 模块解析。
- 资源路径。
- 平台编译。
- 条件编译。
- Vite 插件。
- uni-app 产物生成。

如果改了 `pages.json`、`vite.config.ts`、环境变量、条件编译、小程序组件，应该跑对应构建。

## 十四、调试思路

前端问题可以按链路排查：

### 1. 页面没显示

检查：

- 页面是否在 `pages.json` 注册。
- 路径是否正确。
- 组件是否导入或 easycom 配置。
- 条件渲染是否为 false。
- 数据是否为空。

### 2. 接口失败

检查：

- `VITE_API_BASE`。
- Vite 代理。
- 请求 path。
- token 是否注入。
- 后端响应格式是否符合 `{ code, data, msg }`。
- 浏览器网络面板或小程序调试器。

### 3. 状态不同步

检查：

- 是否有多个地方各存一份状态。
- 是否应该放入 Pinia。
- 更新后是否调用了 `patchPost` 或 `upsert`。
- 解构 store 时是否使用 `storeToRefs`。

### 4. 样式错乱

检查：

- 父容器尺寸。
- Flex 子项是否被压缩。
- absolute 父级是否 relative。
- scoped 是否影响选择器。
- 小程序是否支持对应 CSS。

## 十五、后端协作建议

前后端联调时，建议明确：

- 接口路径。
- 请求方法。
- 请求参数。
- 响应格式。
- 错误码。
- 分页规则。
- token 规则。
- 文件上传和访问路径。
- 空值字段。
- 枚举值。

前端最怕的不是接口复杂，而是接口语义不稳定。今天字段叫 `userName`，明天叫 `nickname`，后天可能为空但文档没说，这才是真正消耗时间的地方。

TypeScript 类型可以缓解这个问题，但不能替代清晰的接口契约。

## 十六、推荐代码习惯

建议：

- 页面只编排业务，不堆工具逻辑。
- 组件 props 和 emits 写类型。
- API 函数写返回值类型。
- Store state 写 interface。
- 异步操作处理 loading 和 catch。
- 用户操作需要考虑失败回滚。
- 复杂条件提取成 computed。
- 重复逻辑抽 composable。
- 样式优先使用 token。
- 提交前跑类型检查。

不建议：

- 页面里直接到处 `uni.request`。
- 用 `any` 跳过所有类型问题。
- 在模板里写复杂表达式。
- 组件直接修改 props。
- 所有状态都塞 Pinia。
- 所有函数都抽 utils。
- H5 调好就认为小程序没问题。

## 十七、上线前检查清单

前端功能上线前，至少检查下面几类问题：

- 首屏是否有 loading、空状态和失败状态。
- 触底加载、下拉刷新、重复点击是否会重复请求。
- 登录失效、接口 401、接口 500 是否有统一处理。
- 图片加载失败时是否有兜底。
- 表单提交时是否禁用重复提交。
- 小程序端和 H5 端是否都跑过关键流程。
- `npm run type-check` 是否通过。
- 对应目标平台的 build 是否通过。

如果改动涉及状态共享，还要额外检查跨页面一致性：列表页点了赞，详情页是否同步；详情页删除内容，列表页是否移除；用户登出后，缓存状态是否清理。前端不是只把当前页面画对就结束了，它还要对用户在多个页面之间来回跳转负责。

## 十八、小结

前端工程实践的本质是边界管理：

- 页面和组件的边界。
- 局部状态和全局状态的边界。
- API 层和 HTTP 层的边界。
- 业务组件和通用组件的边界。
- 全局样式和局部样式的边界。
- H5 和小程序平台能力的边界。

把这些边界处理好，项目会自然变得可维护。处理不好，哪怕每一行代码看起来都能解释，整体也会越来越难改。工程就是这样，它很少因为某一行代码突然崩坏，更多时候是因为很多小边界被轻轻放弃，最后一起回来讨债。
